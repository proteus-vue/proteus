# M2 验收报告 · **荣耀10（中低端对照）**

> 执行日期：2026-09-29 · 设备：**HONOR COL-AL10（荣耀10）· Kirin 970 · Android 10（API 29）· 1080×2280 @480dpi · 60Hz**
> 对比基线：**Redmi M098FE · Android 17（API 37）· 1200×2608 @480dpi · 120Hz**（见 `ACCEPTANCE.md`）
> 被测：`proteus-layout-core 0.1.0 · engine=taffy-0.14`
> 脚本：`bash hosts/android/acceptance.sh --runs 3` · 原始数据：`hosts/android/results/acceptance/20260928-213322/`

---

## 0. 为什么要做这一档

上次验收只有**一台高端机**（Redmi）。`docs/Proteus_App端高性能渲染落地方案.md` §9.2 的合格线是
「≤ 原生」—— **只在旗舰机上成立不足以说明可移植**（旗舰机的余量能掩盖常数开销）。
本档用一台 **2018 年中端机（Kirin 970）**做对照，回答两个问题：

1. 三项指标在中端机上**是否仍达标**？
2. 验收链路本身**是否依赖高端机形态**？（这一条后来证明是更主要的发现）

## 1. 三项指标（荣耀10 实测）

| 指标 | 合格线 | 目标 | **荣耀10** | **Redmi（高端）** | 判定 |
|---|---|---|---|---|---|
| 布局（4050 元素） | ≤ 原生 | ≤ ×0.6 | **43ms vs 270ms → 0.159** | 0.063 | ✓ 达标 |
| 绘制（同进程·软件路径） | ≤ 原生 | ≤ ×0.6 | **14ms vs 24ms → 0.583** | 2.0（见下） | ✓ 达标 |
| 绘制（同进程·硬件录制） | — | — | **5ms → 0.208** | — | ✓ |
| **不拍平**（2000 RenderNode） | ≤ 原生 | 同上 | **81ms vs 894ms → 0.091** | 0.275 | ✓ 超目标 |
| 增量内存（app 自报自包含窗口） | ≤ 原生 ×1.15 | ≤ ×0.8 | **2219KB vs 6675KB → 0.332** | 0.331 | ✓ 达标 |
| 与浏览器基准一致性 | ≤ 0.5dp | — | **0.375dp**（17 用例 / 67 节点） | 0.375dp | ✓ 一致 |
| 跨端命中一致性 | 逐位相同 | — | **6/6 探针 · mismatch 0** | 同 | ✓ |

**绝对值（同进程 `compareAgainstNative`，三段分开）**

| 段 | Proteus | 原生 View（4051 个） |
|---|---|---|
| 布局（建树+排版） | **43ms**（20 次中位 **20.0ms**） | **270ms**（`create_views` 600ms 另计） |
| 绘制（软件路径） | **14ms** | **24ms** |
| 绘制（硬件录制） | **5ms** | 同上 |
| 合计 | **50ms** | **894ms** → **0.056** |

> ★注：上表"布局"两侧口径对齐为「建树+排版」；原生 894ms 里含 **600ms 建 4051 个 View**——
> 那是 View 体系的固有成本（Proteus 只有 1 个宿主 View），**不是同口径**。
> 同口径对比只看前两行。

## 2. ★★中低端机暴露的第一个问题：**§9.3 帧率达不上 60Hz**

| | Redmi（**120Hz**） | **荣耀10（60Hz）** |
|---|---|---|
| 总帧数 | 1233 | 605 |
| **Janky** | 1（**0.08%**） | 597（**98.68%**） |
| **p50 绘制** | **5ms** | **19ms** |
| p95 绘制 | 5ms | 23ms |
| Slow issue draw commands | — | **57** |

**判读（诚实，不粉饰）**：

- 荣耀10 的 **p50 = 19ms > 16.67ms**（60Hz 的一帧预算）⇒ **滚动场景在中端机上掉帧**。
- 但**成因不是本框架的调度**：`Slow issue draw commands: 57` + `Slow UI thread: 2` 说明
  瓶颈在**绘制命令提交**，而这一档设备（2018 中端 SoC + 1080p）的 GPU/合成能力本身有限。
- **对照组缺失**：本档**没有测"原生 4051 View 的滚动帧率"** ⇒ 无法据此判定
  "Proteus 比原生差"。**在补齐原生对照前，本项不能称达标，也不能称不达标。**
  （本仓纪律：拿不到对照就说拿不到，不用"看起来还行"替代。）

⇒ **已记为开项**：中低端机上的**滚动帧率需补原生对照**（见 §5）。

## 3. ★★中低端机暴露的第二个问题：**验收链路本身写死了高端机形态**

这一档最大的产出其实是**四个验收装置的设备假设** —— 每一个都会让"换机跑验收"得到**错的数**：

| # | 装置假设 | 荣耀10 上的实际 | 后果 |
|---|---|---|---|
| 1 | **核心分档写死核号**（`cpu_class: n>=6 ⇒ prime`，频率只采 cpu6/cpu0） | Kirin 970 = **cpu0-3 A53@1.844GHz + cpu4-7 A73@2.362GHz（只有两档）** | cpu4/5 被算成"普大核"（其实是最快档），而"超大核"指向不存在的第三档 ⇒ **判据误报"数据作废"** |
| 2 | **温度只读 `/sys/class/thermal`** | 该目录对 app 与 shell **都 Permission denied**（SELinux） | app 侧恒 **-1**、脚本侧恒**空**，而调用方不检查 ⇒ **-1 被读成"温度未变化"** |
| 3 | **绘制测量只测 1 次、无预热**（布局却有 20 次中位数） | ART 上首次调用走解释执行 | 同一份代码 `optimized_hw_record_ms` = **35ms（honor10）vs 2ms（Redmi）**，**17×** ——不是设备慢 17 倍，是**装置误差** |
| 4 | **Perfetto 固定写 `/data/misc/perfetto-traces/`** | 该目录**不存在**；`/data/local/tmp` 又 `errno 13` | perfetto **静默失败**，日志里只有标题、**一个字都没输出** ⇒ 极易被当成"跑过了" |

**另有一个"跑不完"的缺陷**（第 5 个，与设备无关但同批暴露）：

| 5 | **`cross-device-hit.py` 失败 ⇒ 整条验收中断** | `set -o pipefail` + 该脚本非零退出 | **Perfetto / gfxinfo / 汇总全都没跑**（首跑日志停在 38 行）；且该处**从不生成** Android 侧命中报告 ⇒ 必然缺失 |

**修法**（均在 `acceptance.sh` / `MainActivity.java`）：

- ① 改**按实测频率聚档**（`readCoreMaxFreq()` 读全部核）；§9.2 判据重述为
  「**主线程只落在最快档**」——两档设备上那是它唯一的快档，**不是超频作弊**。
- ② 温度改**多源回退**（thermal_zone → `dumpsys thermalservice` → 显式标注 `unavailable`）。
- ③ 绘制同样**预热 + 7 次取中位数**（原生 / proteus 软件 / proteus 硬件三处）。
  **实测效果：31ms → 15ms**（比值 1.348 → **0.682**）。
- ④ Perfetto 改**可写路径探测 + 失败显式报出**（无可用路径时跳过并说明，不静默）。
- ⑤ 辅助检查 `|| true` **不杀主流程**，并补上 `hit` 通路的采集。

## 4. ★★顺带挖出：**上一份验收报告的"绘制合格"不成立**（口径错配）

跑本档时核对字段才发现：`ACCEPTANCE.md` 里的「绘制 **2ms** → 0.667」取的是
**`draw_attribution_rects_only_ms`** —— 那是**只画色块、不画文字**的**归因拆分子项**
（用于回答"绘制时间花在色块还是文字上"），**不是整体绘制耗时**。

| 口径 | Redmi 实测 | vs 原生 draw 3ms |
|---|---|---|
| 整体绘制（色块 + 文字）= `canvas_draw_software_ms` | **6ms** | **2.0（不达标）** |
| 归因拆分：只色块 = `draw_attribution_rects_only_ms` | 2ms | 0.667 |
| 归因拆分：只文字 = `draw_attribution_text_only_ms` | 5ms | — |

⇒ **原判定"绘制合格"不成立**；已在 `ACCEPTANCE.md` 顶部加「★口径更正」并改正表内数值与判定。
★纪律：**判据取数必须取整体口径，子项不得冒充整体**。

**为什么会这样（诚实归因）**：原生 4051 个 View 的 `draw` 只要 3ms —— View 体系有
**硬件加速 + DisplayList 复用**（不变的部分不重放），而本路径是**每次全量重放 2000 条指令**。
⇒ 绘制路径**在高端机上确实慢于原生**（2.0），**在中端机上反而快**（0.583）——
因为中端机原生侧的 View 体系开销更大（`create_views` 600ms）。

## 5. 结论与开项

**结论**

1. **布局 / 不拍平 / 内存 / 一致性**四项在中端机上**达标且余量充足**（0.159 / 0.091 / 0.332 / 0.375dp）。
2. **绘制**：中端机软件路径 **0.583（达标）**、硬件录制 **0.208**；但**高端机上整体绘制是 2.0（不达标）**
   —— 上一份报告的"合格"是口径错配，已更正。
3. **§9.3 滚动帧率在中端机上掉帧（p50 19ms vs 16.67ms 预算）**，瓶颈是绘制命令提交
   （`Slow issue draw commands: 57`）；**但缺原生对照，不能据此判定框架优劣**。
4. 验收链路本身有 **5 处设备形态假设**，已全部改为**测量驱动**（不再写死核号/路径/单次读数）。

**开项（本轮如实记为未闭）**

- [ ] **中低端机的滚动帧率需补原生对照**（同一台荣耀10 上跑 4051 View 的滚动，比 p50/Janky）
- [ ] 绘制路径的**整体**耗时优化（高端机上 2.0；根因是每次全量重放指令，
      候选方向：显示列表复用 / 脏区重绘 / 拍平更多静态子树）
- [ ] Perfetto 在 honor10 上不可用（SELinux）——核判定改用 app 自报，**跨核分布的权威读数缺失**

**★诚实边界**

- 本档只用 **1 台中端机**（Kirin 970），不足以代表"中低端"整体（更低的还有 4 核 A53 级别）。
- 温度读数来自 `dumpsys thermalservice`（app 侧 `unavailable`），与 sysfs 口径的数值不可直接比。
- 荣耀10 是 60Hz、Redmi 是 120Hz ⇒ **两档的"帧预算"不同**，帧率数字不可直接横比
  （p50 5ms vs 19ms 里含屏刷新率差异，非纯性能差异）。
