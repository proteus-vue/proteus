## 0. 结论

**三项指标全部达标**（§9.2 的合格线 = ≤ 原生；目标 = ≤ 原生 × 0.6 或 × 0.8）：

| 指标 | 合格 | 目标 | **实测比值** | 判定 |
|---|---|---|---|---|
| 4050 渲染耗时 vs 原生 View | ≤ 原生 | ≤ ×0.6 | **布局 0.063 · 绘制 2.0** | △ 布局远超目标 / **绘制未达标**（见下「★口径更正」） |
| **不拍平时的耗时**（§9.2 第二行） | ≤ 原生 | 同上 | **22ms vs 原生 80ms → 0.275** | ✓ 超目标 |
| 增量内存 vs 原生 | ≤ 原生 | ≤ ×0.8 | **0.331** | ✓ 超目标 |
| 与浏览器基准一致性 | — | ≤ 0.5dp | **0.375dp**（17 用例 / 67 节点） | ✓ |

> ★★**口径更正（2026-09-29，跑 honor10 时发现）**：上表原写「绘制 **0.667**」，来源是
> `draw_attribution_rects_only_ms = 2ms` —— 那是**只画色块、不画文字**的**归因拆分子项**
> （用于回答"绘制时间花在色块还是文字上"），**不是整体绘制耗时**。
> 整体绘制（色块 + 文字）实测 `canvas_draw_software_ms = **6ms**` ⇒ 比值 **6/3 = 2.0**。
> ⇒ **原判定"绘制合格"不成立**：`2ms` 是子项冒充整体（本仓纪律：**判据取数必须取整体口径**）。
> 真实结论：**绘制路径比原生慢**（原生 4051 个 View 的 `draw` 只要 3ms —— View 体系的
> 绘制**有硬件加速与显示列表复用**，而本路径是**每次全量重放 2000 条指令**）。
> 详见 §「绘制为何慢于原生」与「honor10 中低端复测」。

### 「拍平 vs 不拍平」两种形态（§9.2 的第二行指标）

| 形态 | 结构 | 耗时 | 对比原生 |
|---|---|---|---|
| **真拍平**（主路径） | 0 个独立绘制对象（指令直下发宿主 Canvas） | 绘制 **6ms**（色块 2 + 文字 5）· 拆分见归因 | 原生 draw 3ms → **2.0**（★见上方口径更正） |
| **不拍平** | **2000 个 `RenderNode`**（每元素一个独立绘制对象） | **22ms**（建 16ms + 画 1ms + 排版 5ms） | 原生合计 80ms → **0.275** |
| 原生 | 4051 个 View | 80ms（建 63 + 量 17） | — |

> 拍平只对**静态子树**生效（§12.3 `flattenEligible`）；列表滚动、动态内容走不拍平路径
> → 故不拍平是**能力下限**，它达标说明「即使最坏形态也不输原生」。

**绝对值**
| 项 | Proteus | 原生 View |
|---|---|---|
| 布局（4050 元素） | **5 ms** | 17 ms（measure+layout，不含 4051 个 View 的创建） |
| 绘制（拍平） | **6 ms**（色块 2 + 文字 5，归因拆分） | 3 ms |
| 绘制（**不拍平**） | **22 ms**（2000 个 RenderNode） | 80 ms（含 4051 个 View 的创建） |
| 增量内存 | **12.0 MB** | **36.3 MB** |

### ★★对标 uni-app x「创建元素」场景：**应用级口径**（2026-09-29 新增）

> **为什么必须新开一档**：本档此前的 4050 数字是**引擎级**（`buildCmds()` 直接造 2000 条绘制指令，
> 核心实测 **9ms**），而 uni-app x 基准的 229.2ms 是**应用级**（点击 → 完整框架链路 → 指令送达 OS）。
> 两者不可比。本档改用 **真 SFC 编译产物**（`assets/app-4050-tree.json`）走完整链路。

**规格（逐条照搬基准）**：**2050 view + 2000 text = 4050 元素**（+1 根 = 4051 节点）·
每格有背景色 · 行列 50×40 · 两侧消费**同一份夹具**（原生对照 1:1 建 View，杜绝"画的东西不同"）。

**计时口径（与基准对齐）**：起点 = 触发；终点 = **渲染指令送达 OS 渲染进程侧**
（Proteus：`RenderNode.endRecording()`；原生：`column.draw(RecordingCanvas)` 结束）。

**冷 / 稳态双口径**（★2026-09-29 追查"为什么倍率差这么多"时补的仪器）：

| | 逐轮（ms） | 均值 | 倍率 |
|---|---|---|---|
| **冷读**（进程内首次完整运行 = 新进程里用户第一次点） | | | |
| · Proteus | 47.3 / 46.4 / 47.6 / 50.3 / 48.6 | **48.0** | **0.518** |
| · 原生 View | 93.7 / 92.7 / 93.5 / 88.1 / 95.9 | **92.8** | |
| **稳态**（进程内第二次运行，类加载/JIT 已就绪） | | | |
| · Proteus | 40.8 / 40.0 / 41.6 / 40.6 / 39.4 | **40.5** | **0.458**（快 **2.18×**） |
| · 原生 View | 90.0 / 88.4 / 94.8 / 88.2 / 81.0 | **88.5** | |

- **判定主口径 = 冷读**（保守：与"新进程里的首次交互"一致）；稳态作次口径一并列出；
- ★**冷读效应实测很小**（Proteus 1.22× / 原生 0.99×）——**"基准的 5× 差异来自冷读"这一假设被证伪**
  （见下节）；顺带修掉此前的一处过度测量（旧实现把"预热那次 draw"也算进了计时区间）。

> ★★**2026-09-29 修正一处"对我们有利的不公平"（并加机器门禁）**：`Cmd` 此前**没有字号字段**
> ⇒ Proteus 侧所有文本用 `textPaint` 默认 **12px** 绘制，而原生对照用 **8sp**——本机 480dpi
> （density 3.0）⇒ 8sp = **24px** ⇒ 原生字形线性尺寸是本侧 **2×**（面积 **4×**）。
> 即"我们画的字只有一半大"。修法：`Cmd` 加 `fontSize`（设备像素）+ 两侧共用同一常量 24px +
> 报告记录 `text_px_effective`，并在跑后自检加 **H5 门禁**（两侧字号不一致 ⇒ 本次数据不可用于对标；
> 破坏性验证：注入 12 vs 24 → 精确报"面积比 4.00×"）。
> **实测影响很小**（0.557 → 0.563）——即本场景瓶颈不在文本光栅化，此修正主要是**排除公平性质疑**。

- ★**5 轮 + 逐轮原始值**均落盘（基准 §1.3.3 的硬要求：只报平均会被质疑"挑最好的一次"）——
  `app-4050-ab.txt` + `app-4050-r{1..5}.json` / `app-4050-native-r{1..5}.json`；
- **内存增量**（两次冷启动隔离，避免同进程互污）：Proteus **+68.6 MB** · 原生 **+96.4 MB** = **0.71×**；
- **分段时间构成**（Proteus）：布局 15.2ms · 指令生成 15.2ms · 录制 DisplayList 22.5ms。

| | 框架 | 该设备原生基线 | 倍率 |
|---|---|---|---|
| uni-app x（小米 Fold4 · 8 Gen 3） | 229.2 ms | **461.8 ms** | 0.496（快 2.01×） |

★**结论：差距几乎全在分母上**（461.8 vs 92.8 = **5.0×**），不在分子（229.2 vs 48.0 = 4.8×，
同比例缩小）。**我们无法从本侧解释那 5×**——本仓自己的数据反而加重了这个疑问：

| 我方自己两台设备的同一操作（原生 4050） | 耗时 |
|---|---|
| Redmi M098FE（2025/26 旗舰） | **92.8 ms** |
| honor10（Kirin 970 · 2018 中端） | **894 ms**（本文件另一档实测） |

两台自有设备差 **9.6×**，远超芯片代差（约 4–5×）；基准的 461.8ms 落在这条区间里，
出现在一台**比我们都新/更强的芯片上**——按我们的斜率推算它"应该"在 150–250ms 量级。

**已排除**：冷读/预热差异（实测 Proteus 1.22× · 原生 0.99×，见上表）。
**尚可能**（本侧无法证伪，需对方实现细节或同设备复跑）：
① 他们的原生对照**挂到窗口并等真实帧**（含 attach 与光栅化），而本档两侧都只测到"录制 DisplayList"；
② 他们的对照走 **XML inflate**（真实 App 写法）而非程序化建 View；
③ 他们的树**嵌套更深**（长列表规格提到 10+ 层）或多轮测量；
④ 设备状态差异（热降频/后台）。
⇒ **在查清之前，本档只主张"我们的倍率与 uni-app x 宣称的倍率同级（0.52 vs 0.50）"，

**★诚实边界（不得省略）**

- 未含图片/视频元素（本场景基准定义为 view + text）。

### ★★绘制常数开销：根因已量化，修法已验证（2026-09-29）

> 本档此前的开项：「绘制路径的常数开销——根因是**每次全量重放 2000 条指令**（原生 View 有
> DisplayList 复用）」。本轮做了**对照实验**（`layout-flat-redraw.json`，run 目录内可复算）。

**① 根因成立，且量级确认**：真实 App 的绘制路径是**整个宿主录成一个 DisplayList**
（`RenderNode`），任何一处变化 ⇒ **重录全部 2000 条**。实测（Redmi，2000 条指令）：

| 读数 | 值 | 说明 |
|---|---|---|
| 单帧全量重录（稳态中位） | **2.67 ms** | 每帧预算 16.67ms 的 **16%** |
| 首次调用（冷读） | **9.19 ms** | ★单点/首次读数**不可用**——差 3.4× |
| 复刻既有路径形状（mimic） | **2 ms** | 与上一条同量级，互校通过 |

⇒ 这是**每帧固定成本**：无论改了多少内容，都要付这 2.7ms。

**② 修法：行级显示列表复用**（与已落地的滚动复用池**同粒度**）
只重录**被改动的行**，其余行复用已录好的 `RenderNode`：

| | 每帧成本 | 
|---|---|
| 全量重录（现状） | **2.67 ms** |
| 行级复用（候选） | **0.045 ms** |
| **提速** | **59×** |

- **正确性**：与平铺绝对坐标**逐像素 0 差异**（两组判据：translate 等价 0 / Picture 路径 0）；
- **对象数有界**：50 个行节点（非 2000 个元素节点——后者实测 **22ms**，比平铺还慢，
  见上表「不拍平」，故**粒度选行**而非元素）；
- **初次建行成本**：3–4ms（一次性，非每帧）。

**③ 诚实边界**
- 只测 **UI 线程侧录制成本**（常数开销所在）；**不含** RenderThread 重放与 GPU；
- 正确性判据用 `Picture` 路径（验证「分组 + 相对坐标不改变绘制结果」），
  **不直接证明 `RenderNode` 类本身**；
- 「脏行」由本对照**按索引算出**；真实产品的脏区判定需**IR 层**提供
  （`flattenEligible` 分组）——**本对照只证明机制收益，不含脏区计算的建设成本**；
- 以 Redmi（120Hz）测得；**honor10 上未复测**（该机不在线）。

**④ ★本轮附带修掉的测量装置缺陷（3 个，均属「读数恒假/静默错」）**

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | 对照实验的 per-frame 值被**除了两次 `FRAMES`** | 绝对值小 60×（0.045ms 而非 2.7ms），会得出"常数开销根本不存在"的**相反结论** | 由 mimic 与既有读数**对不上**而暴露；已修并写进注释 |
| 2 | `acceptance.sh` 的 **A/B 逐轮读数不落盘** | 报告里的中位表**无法复算**（honor10 那轮的 6 轮表就是如此） | 每轮每通路各存 `gfxinfo-<path>-rN.txt` |
| 3 | 原生对照读 `gfxinfo-native.txt`，**该文件无人写** | 对照永远走「缺 gfxinfo」分支（静默缺失） | 改从 A/B 逐轮产物取；`layout-scroll-native.json` 的**同名覆盖**也已修（截图场景改名） |

## 1. §9.2 测试环境要求 → 逐条落实

| §9.2 要求 | 落实方式 | 证据 |
|---|---|---|
| 必须 **release 包** | `build-and-run.sh --release`（清单去掉 `debuggable`） | 构建日志「构建模式：release」 |
| 每次测试前**杀进程重进** | 每轮 `am force-stop` → `am start` → sleep 3 | `raw.txt` 每轮独立 |
| **重复 5 次取均值** | `--runs 5` | 下表 5 轮原始值 |
| **Perfetto 确认跑在普大核** | app 内**持续采样** `/proc/self/task/<tid>/stat` 的 processor 字段（每 3ms 一次，覆盖整个测量窗口）；cpu0–5 = 3.6GHz 普大核，cpu6–7 = 4.6GHz 超大核 | 见下表（**proteus-mem 有 1 次落在 cpu6，已如实标注**） |

**★核归属：两种口径都做了，结论不同（如实并列）**

**口径 A · 进程内采样**（app 每 3ms 读 `/proc/self/task/<tid>/stat` 的 processor 字段）
| 通路 | 观测到的 CPU | 判定 |
|---|---|---|
| `native` / `proteus` / `proteus-noflatten` | 全在 `[0,1,2,3,4,5]` | ✓ 普大核 |
| `proteus-mem` | `[0,1,3,4,5,6]` | ⚠️ 含 1 次超大核 |

**口径 B · Perfetto trace**（`hosts/android/perfetto-analyze.py`，`thread_state` 视图按 CPU 聚合运行时长）
```
主线程 cpu 分布（24.97s trace 窗口，滚到底再回滚）：
  cpu0  466.9ms (23.58%) 普大核
  cpu7  202.1ms (10.21%) ★超大核 —— 仅 6 个时间片
  cpu5/4/1  各 ~60ms     普大核
  cpu6    1.2ms (0.06%)  ★超大核
  → 合计 852.7ms，其中 23.8% 在超大核
```
**时间分布**：超大核时间片集中在 trace 的 **6.7s–10.2s**（滚动测量窗口内）——
**即：滚动期间主线程确实有部分时间被调度到超大核。**

> ### ★关于这个差异的诚实结论
> | 口径 | 结论 | 说明 |
> |---|---|---|
> | 进程内采样 | 「全在普大核」 | **采样率不足**（每 3ms 一次，且只读瞬时值）→ 漏掉了 6 个时间片 |
> | **Perfetto trace** | 「23.8% 在超大核」 | **权威**：基于内核调度事件的**统计量**，不受采样时机影响 |
>
> **⇒ §9.2 的核判定应以 Perfetto 为准。** 按严格口径，本轮的滚动性能数字
> （124.5 FPS）**含超大核贡献**，不能作为「普大核下的性能」声明。
> 若要严格满足 §9.2，需**重跑并约束到普大核**（`taskset` 对普通应用进程无权限，
> 需 root 或系统签名——本机不具备），或**接受以实测混合调度为准**（真实用户场景本就是这个调度）。
>
> 本报告的处理：**如实呈现两种口径，并标注该限制**（不掩盖、不挑选有利数据）。

**★Perfetto 接入的两个实测坑**
| # | 坑 | 正解 |
|---|---|---|
| 1 | trace 里进程名对不上 | Android 的 **comm 字段有 15 字符硬上限**，且**从头部截断**：`dev.proteus.layoutcore` 在 trace 里是 **`teus.layoutcore`** → 匹配要取**尾部 15 字符** |

## 2. 三条测量口径的关键决策（否则数据不可比）

§9.2 原文「**严格复刻，否则数据不可比**」——本轮为此做了三处口径隔离：

| # | 问题 | 做法 |
|---|---|---|
| 1 | **测量装置自身吃内存** | 性能归因需要 7 个 1080×2400 ARGB 位图（每个 9MB，共 ~63MB）——这是**测量仪器的重量**，不是渲染路径的成本。故内存对比走**独立的纯结构通路**（`proteus-mem` / `native`，都不分配位图） |
| 2 | **两条通路的组成不同** | 原生的「创建 4051 个 View」与 Proteus 的「Rust 建树」必须同段比较；绘制则都比「录制 DisplayList」（同口径）。故分三段计时，不合成单一数字 |
| 3 | **PSS 采样时点** | 见 §3 |

## 3. ★★两个被自检抓出的测量缺陷（都曾产生 3 倍误差）

| # | 缺陷 | 症状 | 修法 |
|---|---|---|---|
| 1 | **被测结构失去强引用** | `ViewGroup tree` / `cmds` 是局部变量，方法返回后 GC 可回收 → 同一份代码两次运行测出 **42.5MB / 12.8MB（差 3 倍）** | 加 `keepAlive` 字段持有强引用；采样前 `System.gc()` + sleep 300ms |
| 2 | **PSS 读数为空** | 脚本用 `grep -E '^\s+TOTAL'`——Android 的 **toybox grep 不支持 `\s`** → PSS 恒空、比值算出 `-1` | 改 POSIX 字符类 `[[:space:]]`；核判定改为**以 app 自报为准**（app 读自身 `/proc` 无权限限制） |

**教训**：内存测量的最大风险不是"测不准"，而是**测的不是你想测的东西**。
两次误差都源于"被测对象在采样前已经消失"。**内存测量必须显式 keep-alive，并在采样前稳定堆状态。**

## 3.5 §9.3 长列表验收（M3）

**规格**（方案 §9.3）：死亡长列表 = 4000 行 · 滚到底再回滚到顶 · 统计帧率与内存。

**本轮实现**：`packages/layout-core-rust/src/recycle.rs` —— **平台无关**的复用池 + 生命周期状态机
（方案 §1：「复用池逻辑与平台无关，写一遍」）。真机经 `proteus_recycle_bench` 调用，结果与
Rust 侧单测**逐位一致**（说明该逻辑确实是纯计算、无平台依赖）。

### 实测（Redmi · Android 17 · **普大核**）

```
4000 行 / 400 帧（滚到底再回滚到顶）：
  created=42      ← ★「滚动不触发堆分配」的直接证据
  reused=7926     ← 复用 7926 次
  reuse_ratio=0.9947
  max_live_rows=22 · final_live_rows=22   ← 有界且收敛（无累积）
  demoted_total=4788                      ← 滚出可见区即降级（释放高质量资源）
```

| 判据 | 结果 | 说明 |
|---|---|---|
| **滚动不触发堆分配** | ✓ | **42 个对象服务 7968 次获取**（创建数与**行数无关**，只与窗口大小相关） |
| **内存有界** | ✓ | 存活行数峰值 22（窗口 = 可见 12 + 预加载 ≤10），不随滚动累积 |
| **回滚收敛** | ✓ | 回滚到顶后存活 22 行（不残留滚到底时的行） |
| **生命周期降级** | ✓ | 4788 次降级（不降级则高质量资源永不释放） |

### 实现的两个关键点

1. **方向敏感的预加载区**（§12.6 核心细节）：`leading` 归给**前进方向**、`following` 归给**离开方向**。
   ★两个方向下前进方向在行号的**哪一侧相反**：
   - 向下滚：前进方向 = 行号增大侧（下方多留 8 行）
   - **回滚**：前进方向 = 行号减小侧（**上方**多留 8 行）

   本仓实测教训：初版把两个分支写成同一组参数（都「下方多留」）→ 回滚时**刚滚过的行立刻被释放**，
   回滚要重建。修好后新增回归锁：断言回滚时 `[92,98)` 这些刚滚过的行**仍在预加载区**。
2. **先降级、后释放**：行离开可见区时**先降级**（释放高质量资源），离开预加载区才**释放**。
   初版顺序反了（直接 `on_release` 删除）→ 降级计数恒为 0（跑批暴露）。

### 平台侧验收（真实滚动 + RenderNode 池 + 系统帧率）

**方法**：把列表绘制挂到**窗口内的真实 `View`**，由 `invalidate()` 驱动真实帧
（★关键：初版自建 `RenderNode` 但**未挂窗口** → 显示系统收不到帧，`gfxinfo` 只有 31 帧，
测到的"帧间隔"只是 `Choreographer` 的回调节拍，**与渲染无关**）。

**结果（4000 行 · 600 帧 · 滚到底再回滚到顶）**

| 读数 | 值 | 来源 |
|---|---|---|
| **平均帧率** | **124.5 FPS**（avg 8.04ms） | app 内 `Choreographer` vsync 间隔 |
| p50 / p95 / p99 帧间期 | **8 / 8 / 8 ms** | 同上（8.33ms = 120Hz 预算内） |
| max 帧间期 | 21 ms（1 次） | 同上 |
| 节拍不齐（>2 vsync） | **1 / 599（0.17%）** | 同上 |
| **系统掉帧率** | **0.16%（2 / 1231 帧）** | **`dumpsys gfxinfo`（权威）** |
| **p50 / p95 绘制耗时** | **5 ms / 5 ms** | 同上 |
| Slow UI thread | 1 次 | 同上 |
| **平台侧 RenderNode 池** | 创建 **24** · 复用 **7941** · 复用率 **0.997** · 峰值活跃 24 | app 自报 |

**★两侧复用率一致（Rust 决策 0.9947 ↔ 平台执行 0.997）** → 决策逻辑与执行层对齐，
这是「滚动不触发堆分配」在**真实渲染路径**上的确证。

### ★★三次掉帧判据校准（都被真机打脸，如实记录）

| 版本 | 判据 | 结果 | 问题 |
|---|---|---|---|
| ① | 硬编码 60Hz（>17ms 算掉帧） | 0.67% | **偏低**——设备是 120Hz 屏，8ms 帧间期也正常 |
| ② | 设备刷新率（>8.75ms 算掉帧） | 48.75% | **偏高**——帧间隔是 8/16ms 两档量化，「落在 16ms 档」≠ 渲染慢 |
| ③ | **最终认识** | — | `Choreographer` 间隔**不是渲染耗时**，只是回调节拍 → **以 `gfxinfo` 为权威读数**，app 内读数降级为辅助观测 |

### 与 §9.2 的关系

§9.3 验证的是**列表特性**（复用、收敛、滚动流畅度），§9.2 验证的是**单屏渲染性能**；
两者共用同一 Rust 核心（`recycle` 模块与 `engine` 并列）。

## ★★M3 手势验收 —— `--es path gesture`

方案 §6 的映射表：tap→`GestureDetector`、longPress→`LongPressGesture`、swipe→`FlingGesture`
—— **各端用平台识别器**。本仓只做两件事：① 归一为**语义事件**（跨端同形 API）
② 用**核心命中**给事件标注 `target`（这是自绘才需要补的那一环）。

### 验证点

| 手势 | 期望 | 判据 |
|---|---|---|
| tap | 识别到，`target=4` | 手势归属 = DOWN 时刻命中的节点 |
| longpress | 识别到，`target=4` | 依赖**真实时间**超过平台阈值（`ViewConfiguration`，实测 400ms） |
| fling（向右） | 识别到，`direction=right` | 方向按速度主轴判定 |
| 慢速小位移拖动 | **不**产生 longpress、**不**构成 fling | ★**负向检查**：`longpress_count==1 && fling_count==1` |

四个手势的 `target` 都应为 **4**（`absolute` 子级——绘制在在流之上），
`chain` 都应为 `[4, 3, 1]` ⇒ 证明「**核心命中 → 手势标注**」的接线正确。

### ★★两个时序坑（都实测踩到，源码注释有完整记录）

1. **一次性 `postDelayed` 排队会作废**：`runAll` 此前已占主线程数秒（bench + 文本对比），
   消息被处理时**截止时刻已全部过期** → 背靠背零间隔执行 → longpress 永不触发
   （现象像「平台识别器不工作」，实为**测量装置时序设计错误**）。
2. **改成链式仍不够**：首步延迟与汇总延迟若仍按**排队时刻**算 → 汇总比手势序列**先执行**。
   ⇒ 正解：整条脚本只在主线程空闲后**开始计**，每步延迟从**上一步实际执行时刻**起算，
   汇总**串在链尾**（不作为独立定时任务）。

### ★诚实边界

- **仅 Android 已验收**。iOS / 鸿蒙 的手势映射（`UIGestureRecognizer` / 鸿蒙手势系统）**尚未实现**。
  未做的原因：iOS 上**程序化合成真实触摸序列**没有像 Android `MotionEvent.obtain` 那样的等价手段，
  需要一个明确的合成方案（否则只能测「映射层」而测不到「平台识别器」）——**这个问题先记下，不假装已验**。
- `scroll` 事件在 fling 手势的 MOVE 过程中也会触发（平台语义如此），故它是**过程观测**而非独立手势。
