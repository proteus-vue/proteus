# iOS 端 4050 元素测试（M4）

方案 §9.4 的 iOS 指标：**内存增量 ≤ 原生 × 1.15**。

## 运行

```bash
bash hosts/ios/run-layout-bench.sh
```

## 结果（iPhone 12 · 4051 节点 · 几何全部来自 Rust 核心）

| 形态 | 对象数 | 建 | 绘 | 内存增量 | vs 原生 |
|---|---|---|---|---|---|
| **拍平**（§12.3 真拍平：内容画进 row layer 的 backing store） | **50** layer | 0.86ms | 21.87ms | **+4.0MB** | **0.236** ✓ |
| 不拍平（每元素一个 CALayer） | 4051 layer | 11.99ms | 32.63ms | +6.1MB | 0.363 ✓ |
| 原生 UIKit（UIView + UILabel） | 4050 view | 109.8ms | 8.48ms | **+16.8MB** | 基准 |

**★方案 §9.4 指标大幅达标**（目标 ≤1.15，实测 **0.236**）。

**★拍平的三重收益**（与不拍平对照）：
- 对象数 **50 vs 4051**（↓98.8%）
- 建树 **0.86ms vs 11.99ms**（↓93%）
- 内存 **+4.0MB vs +6.1MB**（↓34%）
- 代价：绘制 **21.87ms vs 32.63ms**（↓33%，因为 batch 进父 layer 少一次合成）

## ★★一个重要的量化发现：JSON 通道的成本

`create_total_ms = 75.84ms` 而 `read_rects_ms = 4.99ms` → **71ms 在「解析 JSON + 建 taffy 树 + 首帧布局」**。

进一步对照（本机 release，4051 节点）：

| 请求 | 字节数 | create | read_rects |
|---|---|---|---|
| 无 textMeasures | 209KB | **62.64ms** | 4.74ms |
| 含 2000 条度量（iOS 侧实际） | 281KB | **46.00ms** | 4.28ms |

**而纯布局只有 ~2ms**（Android 侧同规模实测）。

**⇒ 这量化证实了 M0 计划的判断**：
> 「序列化为 FlatBuffers 或紧凑二进制（**非 JSON，避免运行时解析开销**）」

**当前 95%+ 的「布局耗时」其实是 JSON 通道成本，不是排版算法成本。**
生产实现必须走二进制扁平化 —— 这条从「设计建议」变成了**有数字支撑的硬需求**。

## 规格修正记录（重要）

初版请求**只有 2051 节点**（每个 item 一个节点 + `isText` 标记），
而 §9.2 要求 **4051**（2000 view + 2000 **text**）。
→ 修正为 **item = view（不设宽高）+ text 子节点**，并对 2000 个 text 提供**平台度量**
（§9.2 原文：「view 不设宽高，尺寸由内部文字撑开」——无度量则尺寸为 0，实测踩到）。

## 实测坑

| # | 坑 | 正解 |
|---|---|---|
| 1 | **`\(itemW).0` 生成 `30.0.0`（非法 JSON）** | `CGFloat` 的默认描述已含小数 → 用 `String(format: "%.1f", ...)` |
| 2 | 该失败的**症状具有误导性**：与规模无关（4051 失败、**4101 成功**） | 用**二分探测**（递增规模）区分「语法错」与「容量问题」 |
| 3 | item 不设宽高但无 textMeasures → 尺寸全 0 | 必须提供平台度量（真实场景是 CoreText 注入） |
| 4 | `UIView` 已内建 `CALayerDelegate` 一致性 | 不加 `: CALayerDelegate`（redundant），但**要 `override draw`** |
| 5 | 免费账号新 bundle id 需设备信任 | 复用已信任的 id（`dev.proteus.layoutcore`） |
