# iOS 端 4050 元素测试（M4）

方案 §9.4 的 iOS 指标：**内存增量 ≤ 原生 × 1.15**。

## 运行

```bash
bash hosts/ios/run-layout-bench.sh
```

## 结果（iPhone 12 · 4051 节点 · 几何全部来自 Rust 核心）

### ★★★口径更正（2026-10-02，用户当场追问「iOS 为什么反向优化」）

**旧表有一处误导**：原生侧那格里写的「**绘 8.48ms**」其实是 **`layout_ms`**
（只跑 `layoutIfNeeded` 算 frame，**一个像素都没画**——原生视图的绘制由 CoreAnimation
render server（独立进程）异步完成，不在该计时窗口内）；而 Proteus 侧的 `draw_ms` 是
`layer.render(in:)` **真 CPU 光栅化**（2000 次 fill + 2000 段 CoreText 文字画进位图）。
⇒ 拿"我们画完了"比"原生还没开始画"，得出"反向优化"的错误印象。

**修正后**（L2 真对照 = 两侧都**同步 CPU 光栅化到 1x 位图**；原生侧用
`drawHierarchy(in:afterScreenUpdates:true)` 强制同步渲染）：

| 形态 | 对象数 | 建（L1） | 光栅（L2） | 内存增量 | vs 原生 |
|---|---|---|---|---|---|
| **拍平**（§12.3 真拍平） | **50** layer | 0.85ms | **20.82**ms | +8.1 MB | L2 **0.148** ✓ |
| 不拍平 | 4051 layer | 12.13ms | 32.63ms | +6.1MB | — |
| **原生 UIKit** | 4050 view | **97.83**ms（建 97 + layout 7） | **140.8**ms（同步光栅） | +21.5 MB | 基准 |

- **L2 真对照：Proteus 拍平 20.82ms vs 原生 140.8ms
  ⇒ 比值 0.148（我们更快）**——"反向优化"在统一口径下不成立；
- **内存**：§9.4 判据用**光栅前**读数（与 Proteus 侧同法）——光栅后 4050 视图的 backing store
  全部物化会临时抬到 135MB（`footprint_post_raster_mb`），不入判据；
- ★**建树段仍是同一面倒的对比**：`build_ms 0.85 vs 97ms`（同口径"建结构"）——这是拍平的主收益。

**★方案 §9.4 内存指标大幅达标**（目标 ≤1.15，实测 **0.377**）。

**拍平的三重收益**：对象数 ↓98.8% · 建树 ↓93% · 内存 ↓34%；绘制也 ↓33%（batch 进父 layer 少一次合成）。

## ★★真机分解计时：一个被纠正的错误归因（重要）

**我最初的归因是错的**，特此记录完整过程：

| 阶段 | 我的判断 | 实测结果 |
|---|---|---|
| ① | 「76ms 里 95% 是 **JSON 解析**」 | ❌ **错**：解码 JSON 仅 **3.18ms** |
| ② | 用 `proteus_layout_profile` 分解后 | ✅ 真相：**布局段 69.15ms** |

**真机分解（4051 节点）**：
| 段 | 内容撑开 | 定宽高（对照） |
|---|---|---|
| 解码 JSON | 3.18ms | 0.93ms |
| 建树 | 2.01ms | 0.55ms |
| **布局** | **69.15ms** | **11.33ms** |

### ⇒ 结论：6.1 倍差异来自 **尺寸模式**，不是节点规模、也不是 JSON

### ★★度量缓存键：从「节点寻址」改为「**内容寻址**」（Profile §5.3 的规范键）

**发现的设计缺陷**：初版缓存键是 `(node_id, max_width)` —— **节点寻址**。
而 Profile §5.3 明确规定键是 **(文本 hash, 字体, 宽度约束)** —— **内容寻址**。
差别是本质的：节点寻址下，**2000 个相同文案的节点各度量一次**；内容寻址下只需 1–2 次。

**实测（4051 节点，桩度量函数）**：
| 文案分布 | 真实度量次数 | 说明 |
|---|---|---|
| 同文案（2000 个都是 "item"） | **2 次** | 从 4000 次 → **2000× 减少** |
| 多变（40 种 × 重复 50 行） | **80 次** | 从 4000 次 → **50× 减少** |

### ★★踩到的陷阱：**空文本字面量 ≠ 内容相同**

改动后 conformance **17 用例中文本相关全部失败**（max_delta 12.6dp）。根因：

golden 用例的文本节点是 `text: ""`（真值由「按节点 id 查表」提供）——
我把空串归入「内容已知」→ **所有文本节点 hash 到同一个空串** → 不同文本错误共用缓存项。

**正解（三种情形必须分开）**：
| 情形 | 键 |
|---|---|
| ① 有**非空**文本字面量 | **内容寻址**（文本 hash ⊕ 字体签名） |
| ② 无文本请求（非文本节点） | 节点寻址（node_id） |
| ③ **文本请求存在但字面量为空串** | ★**回退节点寻址**（内容未知 ⇒ 不能假设"同文案"） |

已加 3 条回归锁：`empty_literal_falls_back_to_node_addressing` /
`same_literal_shares_cache_key` / `different_style_key_shares_nothing`。

### ★诚实标注：内容寻址在**本 bench 场景下收益有限**

真机布局耗时：**17.16ms**（上轮 16.95ms）—— **没有明显变化**。原因：

1. bench 场景的 2000 个文本**文案都是 "item"**（重复）→ 原本命中率已极高，
   而上轮的 O(1) 直取 + 扁平键已把「命中成本」压到很低
2. **桩度量函数几乎零成本** → 「减少真实度量次数」的收益测不出来
3. 内容寻址真正受益的是：**多变文案**（真实业务：列表项各不相同）+ **平台度量昂贵**时
   （真实文本 shaping 是毫秒级）

> ★**方法论**：用桩函数做基准有其固有局限——它能测出「框架开销」，
> **测不出「平台调用次数」的价值**。要量化后者，需要**计数**（本次已用 `measure_calls`）
> 或接入**真实平台度量**。这个局限必须如实标注，不能把「耗时没变」说成「优化无效」。

### ★优化（已落地，真机实测 4.1× 提升）

定位到热点后做了两处优化（`taffy_engine.rs`）：

| 热点 | 问题 | 修法 |
|---|---|---|
| **`nodes.iter().find()` 线性扫描** | 每节点 id 查找是 O(n)；4051 节点 × 22000 次度量回调 → **O(n × 回调数)**，是最大热点 | 建 **id → 索引** 映射，回调内 O(1) 直取 |
| **嵌套 HashMap 度量缓存** | 每次命中要「两次哈希 + 两轮探测」 | 改**扁平键** `(node_id << 32) \| max_width.to_bits()` → 一次哈希 |

**真机效果**（iPhone 12 · 4051 节点）：
| 场景 | 优化前 | **优化后** | 提升 |
|---|---|---|---|
| 内容撑开（§9.2 规格） | 69.15ms | **16.95ms** | **4.1×** |
| 定宽高（对照） | 11.33ms | **4.82ms** | **2.4×** |

**★优化正确性**：用 git stash 对拍「优化前 vs 优化后」——**checksum 与抽样节点逐位一致**
（`7709134.00`），确认零语义变化。

**★关键读数**：内容撑开场景下 taffy 产生 **22000 次度量缓存命中**（4000 次真实调用 + 22000 次命中）
—— 这正是「线性扫描」被放大成热点的原因：**回调次数越多，O(n) 查找的代价越致命**。

**§9.2 要求的「view 不设宽高、尺寸由内部文字撑开」正是性能杀手**：
每个 item 走**内容测量**（auto 尺寸链触发 min/max-content 探测——
DCP-1 实测过，taffy 每节点有界常数 13 次测量）。

> ★**这不是 Rust 或 Taffy 的缺陷**，而是「内容自适应尺寸」的**内禀成本**：
> 要让尺寸由文字决定，就必须先量文字、再由文字反推盒子。
> **可行的优化方向**（未做，如实标注）：
> 1. **文本度量缓存**（平台侧按 (文本, 字体, 宽度约束) 缓存）——本项目已在 Android 侧实现并实测有效
> 2. 编译期**批量度量**：编译产物里预置文本尺寸（同文案只需量一次）
> 3. **定宽高优先**：能定尺寸的节点不要留 auto（这条应写进 Profile 的 lint 建议）

### 关于二进制 blob（已实现，但收益需重新定位）

`packages/layout-core-rust/src/blob.rs` —— 紧凑二进制产物（实测证实的价值）：

| 指标 | JSON | **blob** | 提升 |
|---|---|---|---|
| 体积（4051 节点） | 281–389KB | **105KB** | 小 2.7–3.7× |
| 解码耗时（本机） | 1.45ms | **0.56ms** | **快 2.6×** |
| 解码耗时（真机） | 3.18ms | **0.53ms** | **快 6×** |

**★诚实修正**：blob **不是**「消除 95% 成本」的方案（那个 95% 原本就不存在，是我的误判）；
它是**消除通道解析成本**的方案（真机上省 ~2.6ms / 4051 节点）。
**它仍然值得做**（编译器直接产 blob、零文本解析、体积小利于加载），
但**不要期待它解决内容测量成本**——那是另一个问题。

## 规格修正记录

初版请求**只有 2051 节点**（每个 item 一个节点 + `isText` 标记），
而 §9.2 要求 **4051**（2000 view + 2000 **text**）。
→ 修正为 **item = view（不设宽高）+ text 子节点**，并对 2000 个 text 提供**平台度量**
（§9.2 原文：「view 不设宽高，尺寸由内部文字撑开」——无度量则尺寸为 0，实测踩到）。

## 实测坑

| # | 坑 | 正解 |
|---|---|---|
| 1 | **`\(itemW).0` 生成 `30.0.0`（非法 JSON）** | `CGFloat` 默描述已含小数 → `String(format: "%.1f", …)` |
| 2 | 该失败**症状误导**：与规模无关（4051 失败、**4101 成功**） | **二分探测**（递增规模）区分「语法错」与「容量问题」 |
| 3 | item 不设宽高但无 textMeasures → 尺寸全 0 | 必须提供平台度量 |
| 4 | `UIView` 已内建 `CALayerDelegate` 一致性 | 不加 `: CALayerDelegate`，但**要 `override draw`** |
| 5 | 免费账号新 bundle id 需设备信任 | 复用已信任的 id |
| 6 | ★**`isText`/`nativeHost` 缺 `#[serde(default)]`** | 不写 `isText:false` 的请求**整个解析失败**，症状是「create 返回 0 + 耗时异常」→ 极其误导（我因此误判为「JSON 通道慢」）。已修 + 加回归锁 `omitted_optional_fields_are_accepted` |

**★方法论**：错误的归因比没有归因更危险——它会导向错误的优化方向。
**必须做「变量分离」对照实验**（本例：同规模 × 两种尺寸模式），而不是从单一数字推断因果。
