# 模块代号体系

框架有几十个包、十几个子系统。给它们起名字时，我们没有用 `core` / `utils` / `engine-v2` 这类工程代号，而是用**希腊罗马神话里的神名**——因为**神职就是职责**。

这套体系不只是一套命名，它是我们组织代码时的**约束机制**：名字必须说清这个模块在框架里干什么，说不清就说明职责没想清。

## 「神职即职责」怎么落地

选名的方法很直接：**先定位模块的职责，再找一个神职恰好与之契合的神话名**。

| 模块职责 | 选用的神职 | 为什么契合 |
|---|---|---|
| 框架本体——同一份源码变换成多种形态 | **Proteus**，海神，善变形 | "千变万化"就是跨端的本质 |
| 原生能力与 JS 的双向复用 | **Janus**，罗马双面门神 | 一面朝原生、一面朝 JS，正是双向门 |
| 触摸交互的极限压测 | **Dactyl**，Δάκτυλοι「手指一族」 | 把触摸当作需要严肃对待的第一公民 |

这套做法的好处是**名字自带一句话说明**：新人看到 `Janus` 不需要先查"这个包是干嘛的"，神职已经解释了它。

## 三条纪律

名字起得好不好，靠三条硬纪律兜住，而不是靠自觉。

### 只收神话神名

万神殿**只收神话神名**（神祇、泰坦、原初神、缪斯、神话人物；神话生物可用但须标注），**不收**普通名词、材质名、建筑名或技术术语。

> 这条纪律是**踩过坑才立的**：玻璃组件库初稿用过 `Hyaleos` / `Krystallos`（希腊语的"玻璃/水晶"）——名字很贴切，但它们是**材质普通名词**，破坏了"神名"这条轴。最终改名为 **Aether**（原初之神，指澄澈的上层天光——光之介质），既守住轴，又准确表达了"通透的承光外壳"。

### 体系内一名一模块

一个名字一旦登记，就归那个模块；备选名被别处占用也要排除。

> 实例：`Argus`（百眼巨人，怎么看都是"监控/遍历"的天然名字）曾被内存安全模块选为备选，但因为与另一个模块已登记的备选冲突，最终**归给内存模块并从前者的候选里移除**。宁可换一个，也不要两个模块共用一个联想。

### 定名前必须做商标与包名检索

每个代号在正式定名前，都要检索**商标**与**包名**是否已被占用。**检索未通过，不得对外使用**——内部可以先用，对外一律写职能描述。

## 诚实边界：被排除的名字

有些神名神职很契合，但我们最终放弃了——因为它们**在外部世界已经是知名项目**，用了会让使用者搜不到我们：

| 被排除的代号 | 原因 |
|---|---|
| **Iris** | 与一个 Rust + Vue3 动画引擎同名，领域高度重合 |
| **Athena** | AWS Athena 强占用 |
| **Theia** | Eclipse Theia（IDE 框架），领域相近 |
| **Eos** | EOS 区块链 / EOS 相机 |
| **Metis** | 已有同名 JS 框架 |
| **Hermes** | Hermes JS 引擎（React Native 默认引擎） |
| **Nike** | 商标强占用 |

宁可换一个名字，也不要让使用者搜的时候先撞上别人。这条边界我们写在内部规范里，也应当写在这里——**命名的克制，本身就是产品克制的一部分**。

另外有两个名字我们主动排除：
- `Logos` / `Eos` 这类**过短的泛词**——检索不可靠，也无法定位
- 与 **HarmonyOS** 谐音的 `Harmonia`——在鸿蒙语境下会造成致命混淆

## 对外披露的现状

目前**只有三个代号完成了商标与包名检索，可以对外使用**：

| 代号 | 模块 |
|---|---|
| **Proteus** | 框架本体 |
| **Janus** | 原生资产复用与统一开发体验 |
| **Dactyl** | 交互视觉极限压测与性能验收 |

其余内部子系统在对外文档里**一律使用职能描述**（"声明式动画引擎"、"多端一致 CSS 引擎"、"OS 级组件库"……），不披露代号。等各自的检索完成、状态转为"已定名"，才会逐步出现在文档里。

> 你可能会在文档里看到个别代号提前出现——那是我们在收口过程中的残留，会逐步清理或转正。**在我们没有明确说"已定名"之前，请以职能描述为准。**

其中两处需要单独说明，因为它们不是"残留"，而是**已经作为对外产品名在用、但检索尚未完成**：

- **动画引擎**的代号出现在[动画分区](/docs/animation/00-overview)的标题里（该分区有独立产品页）
- **玻璃系统外壳组件库**的代号出现在[液态玻璃指引](/docs/31-liquid-glass)里（该库**尚在规划、未落地**）

这两处是我们在"对外一致"与"检索未完成"之间还没收口的地方——**按内部纪律它们本应先完成检索再对外**。此处如实标注，而不是假装不存在。

## 这套体系为什么值得写出来

因为它解决的问题是通用的：**当一个系统有几十个部件时，命名是最便宜也最容易被忽视的设计**。

- 用 `core` / `common` / `utils` 命名，等于承认自己没想清职责边界
- 用业务缩写命名，新人每次都要查表
- 用"神职即职责"命名，名字本身就是职责的一句话说明，**且每年都会提醒你一次：这个模块到底是干什么的**

这也是 Proteus 整体方法论的缩影：**先把语义想清楚，再让实现去适配语义**——命名如此，布局如此，能力接入也如此。
