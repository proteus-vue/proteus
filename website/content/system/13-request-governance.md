# 请求治理层

**一个 App 里几十个业务团队共用一套网络，还管得住吗？**

Proteus 的请求层不是"又一个 axios"。主流请求库优化的是**业务少写几行代码**；我们优化的是另一个问题——当支付、商品、客服、直播四个团队同时用一套网络栈出网时，平台方能否回答：谁连了哪儿？谁把配额打满了？这笔下单到底成功了没有？

这三个问题，主流库都答不上来。不是因为它们做得不好，是因为它们的设计目标里没有这个位置。

## 一个超时，三种命运

支付失败和商品列表失败，在多数请求库里长得一模一样：一个 `error`，一个 `catch`。

但对支付来说，超时**不是失败**——它是一个必须去查的状态。请求可能已经到了服务端、订单可能已经创建、钱可能已经扣了。把它当失败处理然后重试，就是重复下单。

Proteus 把结果分成三态，而不是两态：

| 结果 | 含义 | 业务该做什么 |
|---|---|---|
| `success` | 确定成功 | 正常走 |
| `failed` | 确定失败（明确没被处理） | 可以重试 |
| **`unknown`** | **结果未知** | **去查单，不要重试** |

判不出来的时候，我们保守地归入 `unknown`。宁可让业务多查一次单，也不能让它以为失败而重发。这是整层的设计起点——后面所有机制都围绕它展开。

## 为什么 WebSocket 需要同一套规矩

加固只做在 HTTP 那一层，是行业里最常见的漏洞形态。

平台给 HTTP 配了域名白名单、配了审计、配了每业务配额。业务换一个 API——`useWebSocket`——就绕过了全部限制。而且 WebSocket 在审计里看起来"只是条连接"，比一堆 POST 干净得多，却是一条可以无限期收发的常驻通道。**它是最适合把数据悄悄外传的形状。**

所以这一层的策略链对两条通道同时生效：

- **域名白名单**一处配置、两条通道，业务无法通过换 API 逃逸
- **审计**记下谁在什么时候连了哪个 host、活了多久、收发多少条——但**绝不记录消息正文**
- **配额**按业务分配，长连接占用额度直到真正断开

最后一条容易做错：配额必须在连接**关闭**时释放，不是 `open()` 返回时。否则一个正常的直播长连接会把额度永久占作"在飞"，跑几小时后新页面全连不上。

## 多租户下，去重会串号

去重是请求库的常规优化：两个相同的在飞请求，合并成一个。

问题在于"相同"怎么定义。如果键里只有 `method + url + body`，那么——

> A 业务和 B 业务同时请求 `GET /api/me`，各自带自己的 `Authorization`。
> 键相同，请求被合并。**A 拿到了 B 的用户信息。**

这不是理论风险。本仓旧实现的去重键恰好就是这样，注释里写着"鉴权头由拦截器加，同资源应共享"——这条理由在**同一个鉴权域内**成立，一旦引入多租户就变成了数据泄漏。

修法不是"把所有 header 都塞进键"——那样 `x-request-id`、`traceparent` 这类每请求都变的追踪头会让去重永不命中，功能名存实亡。我们只收**会改变应答内容**的头：身份、租户、幂等键、内容协商。

同样地，如果业务配了请求拦截器，去重会**直接跳过**。因为拦截器可以改 URL 和 header，而它在去重键算好之后才执行——键代表不了最终请求身份。这个决定会降低命中率，但不会串号。跳过时结果里会明确写出原因，不让业务以为"去重坏了"。

## 重试不会重发你的订单

```ts
// 业务写了这一行
const r = await client.post('/order', data, { retry: { attempts: 3 } })
```

多数库在这里会重试三次。如果第一次其实成功了、只是响应超时，用户就下了四单。

HTTP 语义上，只有幂等方法（GET / HEAD / OPTIONS / PUT / DELETE / TRACE）可以无条件重试。POST 不是。所以这里的默认行为是：**拒绝重试**，并在结果里说明原因。

要重试 POST，得满足一个条件：提供幂等键。服务端按它去重，重试才是安全的。门面层在有幂等键时会自动放行；直接调底层 `useFetch` 时，必须自己显式打开。

被拦住的时候，结果里会带 `retryRefused`，写清"因为你的方法非幂等且没有幂等键"。这条不难加，但没有它，业务只看到 `attempts: 1`，会以为库坏了——排查方向完全错。

## 抖动必须真的抖动

重试退避带抖动，是为了让同时失败的客户端错开时间，避免所有请求在同一毫秒重新砸向刚恢复的服务。

如果抖动是确定性计算（比如按重试次数交替正负号），所有客户端会算出**完全一样**的退避时长——它们仍然同步重试。抖动名存实亡，功能看着有、作用为零。

这里的抖动是真随机的。

## 出问题时你看到什么

一层请求基础设施的价值，一半在正常路径，一半在出问题时能告诉人什么。

每一次请求结束，无论成败，都会产出一条审计：业务标识、host、结果三态、耗时、重试次数、错误码。URL 经过脱敏——路径只留前两段、query 整个去掉，因为 token 经常就藏在那里。

WebSocket 的审计形状不同（长连接没有 HTTP status，但有开-关时长和关闭码），但脱敏规则是同一份实现。

**日志里不会有请求体，也不会有 WebSocket 消息内容。** 这是刻意的：把载荷写进日志，等于把数据复制到第二个地方——而日志会被采集、导出、存得比业务数据更久。审计要回答的是"谁、什么时候、去了哪、成不成"，不是"传了什么"。

## 边界

写清楚这一层不做什么，比写它能做什么更有用。

- **不接支付渠道 SDK**。这里只管请求的可靠性语义，微信支付/支付宝/Apple IAP 的原生集成是另一件事。
- **不做 schema / OpenAPI 代码生成**。仓库没有这块基础设施。
- **断路器与配额是进程内状态**。跨进程共享需要宿主支持，当前不提供。
- **脱敏是字段名匹配，不是内容识别**。业务把 token 塞进自定义 header 而没加进黑名单，就会漏出去。
- **`unknown` 之后代码能否正确处置，是业务的责任**。这一层只保证状态是诚实的，不保证业务拿它做对了事。

最后一条尤其重要：三态模型的价值在于让业务**看见**该去查单，而不是替业务去查。一个把 `unknown` 当 `failed` 处理的业务，用再好的库也还是会重复下单。
