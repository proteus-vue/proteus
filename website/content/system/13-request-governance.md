# 请求治理层

**一个 App 里几十个业务团队共用一套网络，还管得住吗？**

主流请求库优化"业务少写几行代码"。这一层优化另一个问题：支付、商品、客服、直播四个团队同时用一套网络栈出网时，平台方能不能回答 —— 谁连了哪儿？谁把配额打满了？这笔下单到底成功了没有？

这三个问题主流库都答不上来。不是做得不好，是它们的设计目标里没有这个位置。

> **产品主页：[Phylax 请求治理层](/phylax)**（沉浸式产品页，含三态闸门可视化与机器数字）。
> **想直接上手：** [使用手册](/docs/system/14-request-quickstart)。
> 本页讲**为什么这样设计** —— 是上面两处的补充，不是门面。

---

## 一、一个超时，三种命运

支付失败和商品列表失败，在多数请求库里长得一样：一个 `error`，一个 `catch`。

但对支付来说，超时**不是失败** —— 它是一个必须去查的状态。请求可能已经到了服务端、订单可能已经创建、钱可能已经扣了。当成失败处理然后重试，就是重复下单。

所以这一层把结果分成三态：

```
              ┌──────────────────────────────────────────────┐
   请求发出 ─→│  success   确定成功        → 正常走            │
              │  failed    确定失败        → 可重试            │
              │  unknown   结果未知        → 去查单，别重试     │
              └──────────────────────────────────────────────┘
                        ▲
                        └── 判不出来时，保守归入 unknown
```

**关键取舍**：判不出来的时候，宁可让业务多查一次单，也不能让它以为失败而重发。

这条决定了后面所有机制的形状 —— 幂等键、重试门禁、乐观更新回滚、WebSocket 审计，都是为了让 `unknown` 这个状态**可靠可达且不被误判**。

```ts
const r = await client.post('/order', data)
if (r.ok) return done()
if (r.outcome === 'failed') return retryWithIdempotencyKey()
// unknown：不重试，去确认
await refreshOrders()
```

## 二、这套能力在哪个包

三层的分工是刻意的，不是拆着玩：

```
  @proteus-vue/request     ← 你写的代码在这里
  useQuery / useMutation / useRequest
         │  只做：响应式容器 · 竞态裁决 · 卸载取消
         ▼
  @proteus-vue/api/request ← 策略内核（平台中立 · 零 Vue 依赖）
  三态 · 幂等 · 断路器 · 离线队列 · 审计 · 脱敏 · 配额
         │
         ▼
  useFetch → bridge.request → OkHttp / URLSession / RCP
  三端宿主
```

**为什么响应式要单独一层**：`@proteus-vue/api` 的内核要能跑在小程序逻辑层、Node、以及任何非 Vue 环境 —— 把 Vue 塞进去就废了这个能力。而"模板自动重渲染"是 Vue 特有的东西。所以拆成两个包，Vue 在上、内核在下。

这跟 `@proteus-vue/pinia-sync` 的做法一致：内核可选、`vue` 是 peer dependency、不引入就没有开销。

## 三、三个 composable，一句话分工

| | 场景 | 自动发起 | 乐观更新 |
|---|---|---|---|
| `useQuery(url)` | 进页面就拉的**读** | ✅ | — |
| `useMutation(url)` | 用户动作触发的**写** | ❌ | ✅ |
| `useRequest()` | 用户动作触发的**读** | ❌ | — |

判断口诀：**读用 Query，写用 Mutation，点了才发的读用 Request。**

选错的代价很实际：用 `useQuery` 做"点搜索才查"，页面一进来就会发一次没人要的请求；用 `useRequest` 做列表，进来是空白，用户以为没数据。

## 四、三件内核不做、但前端一定会踩的事

内核把策略做对了，前端仍然会在这三个地方翻车。这三件事只在产品层解决：

### 4.1 失败不该清空数据

手写请求状态最常见的写法：

```ts
loading.value = true
const r = await fetch(...)
loading.value = false
if (r.ok) data.value = r.data
else error.value = r.error      // ← data 还留着，看起来对
```

但只要你在 `catch` 或错误分支里写了 `data.value = null`（"清一下状态"），刷新失败时页面就从**有内容**变成**空白**。用户看到的是"数据没了"，而不是"刷新失败"。

→ 本层语义：**失败保留上一次成功的数据**，只置 `error` 与 `outcome`。

### 4.2 旧响应不该覆盖新响应

```
用户点「价格↑」 → 请求 A 发出
用户点「价格↓」 → 请求 B 发出     （A 还在路上）
B 先回来  → 界面显示降序
A 后回来  → 界面显示升序          ← 筛选项是"降序"，数据是升序
```

这种 bug 极难复现（要网络慢到特定程度），但线上一定有。手写时几乎没人加序号裁决。

→ 本层内建：每次发起自增 `seq`，只有最新那次的结算被采纳。

### 4.3 卸载后回调还在跑

路由快速切换时，上一个页面的请求回来会改已销毁组件的状态。轻则警告，重则内存泄漏。

→ 本层接管 `onScopeDispose`，组件卸载时取消在飞请求。

## 五、乐观更新的三态回滚

乐观更新是"先改界面再发请求"。难点不在改，在**失败时怎么收场**。

```
  提交
   ├─ success → 用服务端返回值覆盖（服务端才是权威）
   ├─ failed  → 回滚乐观值（确定没生效）
   └─ unknown → ★ 保留乐观值，不回滚
                 因为可能已经成功了
```

**`unknown` 不回滚是这一层最反直觉、也最重要的一条。**

回滚看起来"安全"（回到提交前），但它的前提是"提交没成功"。而 `unknown` 恰恰意味着这个前提**不成立** —— 回滚等于把一个可能真成功的写入在界面上撤销掉。用户看到"失败了"，实际数据库已经改了。接着他会再提交一次，就是重复写入。

所以 `unknown` 时界面必须显示"结果待确认"，而不是成功或失败中的任何一个。

## 六、为什么 WebSocket 需要同一套规矩

加固只做在 HTTP 那一层，是行业里最常见的漏洞形态。

平台配了域名白名单、审计、每业务配额 —— 全在 HTTP。业务换一个 API（`useWebSocket`）就绕过了全部。而且 WebSocket 在审计里看起来"只是条连接"，比一堆 POST 干净，却能无限期收发。**它是最适合把数据悄悄外传的形状。**

所以策略链对两条通道同时生效：

| | HTTP | WebSocket |
|---|---|---|
| 域名白名单 | ✅ | ✅ 同一份实现 |
| 业务隔离（bizId） | ✅ | ✅ |
| 审计 | ✅ | ✅ 开/关都记，含存活时长与**条数** |
| 配额 | ✅ | ✅ 长连接占用至断开 |
| 消息内容进日志 | — | ❌ **绝不** |

**审计不记正文是刻意的**：把载荷写进日志等于把数据复制到第二个地方 —— 而日志会被采集、导出、存得比业务数据更久。审计要回答的是"谁、什么时候、去了哪、成不成"，不是"传了什么"。

**配额释放点容易做错**：必须在连接**真正关闭**时释放，不是 `open()` 返回时。否则一个正常的直播长连接会把额度永久占作"在飞"，跑几小时后新页面全连不上。

## 七、多租户下，去重会串号

去重是常规优化：两个相同的在飞请求合并成一个。问题在"相同"怎么定义。

如果键里只有 `method + url + body`：

```
A 业务请求 GET /api/me  Authorization: Bearer tenant-a
B 业务请求 GET /api/me  Authorization: Bearer tenant-b
                        ↑ 键相同 → 合并 → A 拿到 B 的用户信息
```

反过来，把**所有** header 都放进键也不行：`x-request-id`、`traceparent` 这类每请求都变的追踪头会让去重**永不命中**，功能名存实亡。

→ 只收"会改变应答内容"的头：身份、租户、幂等键、内容协商。**正确性优先，但不矫枉过正。**

**第二层**：配了请求拦截器时直接**跳过去重**。拦截器在键算好之后才执行、可以改 url 和 header —— 键代表不了最终身份。这会降低命中率，但不会串号。跳过时结果里写明原因。

## 八、重试不会重发你的订单

```ts
// 业务写了这一行
const r = await client.post('/order', data, { retry: { attempts: 3 } })
```

多数库会重试三次。如果第一次其实成功了、只是响应超时，用户就下了四单。

HTTP 语义上只有幂等方法（GET / HEAD / OPTIONS / PUT / DELETE / TRACE）能无条件重试。POST 不是。

→ 默认**拒绝重试** POST，并在结果里说明原因（`retryRefused`）。

要重试 POST 得给幂等键 —— 服务端按它去重。门面层看到幂等键会自动放行。

---

## 九、出问题时你看到什么

一层请求基础设施的价值，一半在正常路径，一半在凌晨两点能告诉人什么。

每条请求结束都产出一条审计：业务标识、host、三态、耗时、重试次数、错误码。URL 脱敏 —— 路径只留前两段、query 整个去掉，因为 token 经常藏在那里。

**日志里不会有请求体，也不会有 WebSocket 消息内容。**

## 十、边界

- **不接支付渠道 SDK**（微信/支付宝/Apple IAP）。这里只管请求可靠性语义。
- **不做 schema / OpenAPI 代码生成**。仓库没有这块基础设施。
- **断路器与配额是进程内状态**。跨进程共享需要宿主支持。
- **脱敏是字段名匹配，不是内容识别**。token 塞进没登记的自定义 header 就会漏。
- **`unknown` 之后能否正确处置是业务的责任**。这层只保证状态诚实，不能替你决定去查单还是忽略。

最后一条最重要：三态模型的价值是让业务**看见**该去查单，不是替业务去查。一个把 `unknown` 当 `failed` 处理的业务，用再好的库也还是会重复下单。
