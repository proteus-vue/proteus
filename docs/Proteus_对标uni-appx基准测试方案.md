# Proteus 对标 Benchmark 落地方案

> 定位：**以 uni-app x 官方 Benchmark 的同一套测试基准，跑出 Proteus 的可对比数据**
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4）
> 对标来源：uni-app x 官方性能基准测试（小米 Fold4 / 骁龙 8 Gen 3 / Android 16）
> 依赖：《Benchmark 案例规格》§8（测量口径）、《实战采集埋点清单》§3（运行时打点）

---

## 0. 一个必须先说的重要发现

**Proteus 已有的两项实测，规格与 uni-app x 的基准高度吻合：**

| 项 | uni-app x 基准 | Proteus 已有实测 | 是否对齐 |
|---|---|---|---|
| 元素数 | 4050（2050 view + 2000 text） | 4050 | ✅ **完全一致** |
| 长列表行数 | 4000 行 | 4000 行 | ✅ **完全一致** |
| 每行元素数 | 40+ | 40+ | ✅ **完全一致** |
| 嵌套深度 | 10+ 层 | 10+ 层 | ✅ **完全一致** |
| 总元素数 | 2 万 | 2 万 | ✅ **完全一致** |

**这意味着你的数字与 uni-app x 的数字是同负载的。** 剩下的唯一变量是**设备**。

### 0.1 因此本方案的核心任务不是"重新造测试"，而是三件事：

1. **严格复现 uni-app x 的环境控制**（剔除超大核、AOT 闲时优化、普大核确认等）
2. **补齐对照组**（原生 View、Compose UI，并加 Flutter / RN）
3. **统一倍率口径**——因为设备不同，只能比倍率不能比绝对值

### 0.2 测试项总览（三项，缺一不可）

| # | 测试项 | 基准是否有量化数字 | 本方案章节 |
|---|---|---|---|
| 1 | **创建元素**（4050：2050 view + 2000 text） | ✅ 有（耗时 + 内存增量） | §1.3 |
| 2 | **死亡长列表**（4000 行 / 2 万元素） | ✅ 有（平均帧率） | §1.4 |
| 3 | **组件级**（rich-text / swiper / canvas） | ⚠️ **仅定性展示，无数字** | §1.3-bis |

> **说明**：基准称其为「view 和 text 渲染测试」，实质动作是
> **点击按钮后创建 2000 个 view、各嵌套一个 text**——即"创建元素测试"。
> 本方案 §1.3 即对应此项，为避免混淆已统一命名。

## 1. 基准规格精确复现

### 1.1 测试设备

| 项 | uni-app x | Proteus 方案 |
|---|---|---|
| 主测设备 | 小米 Fold4 × 2（骁龙 8 Gen 3，Android 16） | **建议直接采购同款**（见 §1.2） |
| 中端对照 | 无 | **荣耀 10（麒麟 970 / Android 10 / 60Hz）** ← 你的独有优势 |

### 1.2 ★ 强烈建议：采购同款设备

**理由**：只有同设备，倍率对比才无懈可击。

设备成本远低于"数据被质疑"的代价。若无法采购，则必须在报告中**明确标注设备差异**，且只比倍率。

### 1.3 测试一：4050 元素渲染

**原基准定义（逐条复现）**：

```
动作：点击按钮后，在屏幕上创建 2000 个 view
      每个 view 有一个背景色
      每个 view 中再套入一个 text 组件
      合计 4050 个元素（2050 view + 2000 text）

计时起点：按钮 click 事件触发时刻
计时终点：主线程渲染指令已全部送达 OS 渲染进程
```

**Proteus 实现要求**：

| 项 | 要求 |
|---|---|
| 元素构成 | 严格 2050 view + 2000 text，背景色必须设置 |
| 计时起点 | 按钮 click 事件触发（与基准一致） |
| 计时终点 | 主线程渲染指令全部送达 OS 渲染进程 |
| **重复次数** | **5 次取平均**（与基准一致，见 §1.3.3） |
| **内存增量** | **必须采集**（基准有此项，见 §1.3.2） |
| **必须采集** | 布局耗时 / 绘制耗时**分开**（你已有此能力，基准没有） |

> ⚠️ **计时终点的口径必须严格对齐**。「送达 OS 渲染进程」不等于「GPU 完成光栅化」，
> 后者无法在主线程侧测量。**不要自行延伸终点定义**，否则数字不可比。

#### 1.3.2 内存增量测量（★ 基准有此项，方案上一版遗漏）

**基准原数据**（创建元素测试配套的「内存增量」列）：

| 状态 | 技术方案 | 5 次平均耗时 | 内存增量 |
|---|---|---|---|
| 初次安装 | uni-app x（非拍平） | 278.4 ms | 48,868 |
| 初次安装 | 原生 View | 483.8 ms | 78,676 |
| 闲时优化 | **uni-app x（拍平）** | **229.2 ms** | **41,642** |
| 闲时优化 | Android View | 461.8 ms | 78,760.8 |

**Proteus 必须按同一口径采集内存增量。**

> ⚠️ **口径差异必须处理**：
> Proteus 已有的内存数据是「相对原生增量 **0.328** 倍」（比值），
> 基准给的是**绝对值**。两者不可直接比较。
>
> **处理方式**：本次测试同时采集——
> 1. **绝对值**（与基准对齐，可比）
> 2. **相对原生倍率**（你已有的口径，用于内部优化）
>
> 并注明：以原生 View 的绝对值为分母换算，Proteus ≈ 0.328 × 78,760 ≈ **25.8**，
> 低于 uni-app x 的 41,642——**这是一个值得实测确认的强信号**。

#### 1.3.3 重复次数与数据呈现

基准采用 **5 次取平均**，且列出了每次数据（如 `101.7(102.37 107.71 102.67 93.46 102.61)`）。

**Proteus 必须同样执行**：每组测试跑 5 次，**同时报平均值与 5 个原始值**。
只报平均值会被质疑"挑了最好的一次"。

### 1.3-bis 测试三：组件级性能（★ 本方案上一版遗漏）

> 基准除两项主测试外，还展示了三个组件级场景。
> 这三个在基准中**只有定性描述，无量化数字**——
> 但对 Proteus 而言是可量化的差异化机会。

| 组件 | 基准场景 | 基准数据 | Proteus 策略 |
|---|---|---|---|
| **rich-text** | 加载 5 万字长文，含 59 张插图 | 无量化数字 | **量化**：加载耗时、滚动帧率、内存 |
| **swiper** | 无等待呈现 59 张图片 | 无量化数字 | **量化**：首图呈现延迟、切换帧率、图片内存 |
| **canvas** | 屏幕上 2 万个小球同时边缘碰撞而不掉帧 | 无量化数字 | **量化**：小球数上限、帧率、掉帧率 |

**处理建议**：

1. **不要跳过**——这三个是基准覆盖而我们上一版没覆盖的项
2. **基准没有数字，我们要有**——这是"人有我优"的机会，直接量化即可形成差异
3. **canvas 需谨慎**：2 万小球碰撞是**计算密集型**（每帧 2 万次位置更新 + 碰撞检测），
   主要考验逻辑层而非渲染层。**若 Proteus 的 canvas 尚未落地或性能不占优，
   建议标注"暂不参与对比"，不要硬测**——否则会成为一个明显的失分项

### 1.4 测试二：死亡长列表

```
数据：加载 4000 行，7.4M 的 JSON
      每行超过 40+ 元素：文字、图片、视频、自定义 vue 组件
      每行嵌套深度 10+ 层
      列表共渲染 2 万个元素

采集：关闭 HWUI 呈现模式条形图
      通过 adb 提取滚动期间的平均帧率数据
      避开首尾
```

**Proteus 实现要求**：

| 项 | 要求 |
|---|---|
| 数据量 | 4000 行，JSON 约 7.4M（**必须对齐体积**，它影响解析与内存） |
| 元素构成 | 文字 + 图片 + 视频 + 自定义 vue 组件 |
| 嵌套深度 | 10+ 层 |
| 采集方式 | 关闭 HWUI 条形图 → adb 提取 → 避开首尾 |

> ⚠️ **"视频"这一项需要注意**：视频是原生组件（B 档），涉及混合渲染。
> 若 Proteus 的视频组件尚未落地，需明确标注"视频元素以占位替代"，
> **并在报告中声明差异**——否则对比不公平（视频成本主要在媒体管线）。

### 1.5 两种渲染模式

uni-app x 区分**拍平**与**非拍平**两种模式：

| 模式 | uni-app x（闲时优化后） | Proteus |
|---|---|---|
| 非拍平 | 278.4ms | 需实测 |
| 拍平 | **229.2ms** | 需实测 |

**Proteus 也必须两种模式都测**——这正好复用你的 RenderCmd 拍平开关。

> **★ 这是最有价值的一张图**：同一设备、同一代码，只切拍平开关。
> 你的两台设备都已有这两条路径的数据：**Redmi（高端）拍平 2.0 ✗ / 不拍平 0.275 ✓**；
> **荣耀 10（中端）绘制 0.583 ✓ / 不拍平 0.091 ✓**。格式可直接复用。

## 2. 环境控制清单（★ 严格照搬，不得删减）

uni-app x 的环境控制做得非常严谨，这是其数据可信度的基础。**逐条执行：**

| # | 控制项 | 具体要求 |
|---|---|---|
| 1 | **电量** | ≥ 90% |
| 2 | **性能模式** | 禁用节能模式、禁用性能模式 |
| 3 | **后台应用** | 禁用所有其他应用 |
| 4 | **温度** | 监控温度防降频 |
| 5 | **核调度** | 观测 Perfetto，被 OS 偶发调度到**超大核**导致变快的数据**一律剔除** |
| 6 | **运行环境** | 确保在**普大核**运行 |
| 7 | **作弊禁止** | 禁止应用层强制提升（如 nors 等手段） |
| 8 | **包名** | 普通包名，不预载 |
| 9 | **AOT 状态** | 区分**初次安装**与**闲时优化**两组数据 |

### 2.1 AOT 闲时优化（这条最容易漏，也最关键）

uni-app x 明确指出：**闲时优化状态是大多数 Android 用户的真实使用场景**。

手动触发命令：

```bash
adb shell cmd package compile -m speed -f <包名>
```

**必须两组数据都出**：

| 状态 | 说明 |
|---|---|
| 初次安装 | 未触发 AOT |
| 闲时优化 | 已 AOT 预编译 ← **这才是常态，应作为主数据** |

### 2.2 补充：Proteus 自身还需加的环境控制

沿用 Benchmark 规格 §8.4：

- 每次测试前**杀进程重启**
- 测试前**重启手机静置 2 分钟**

## 3. 对照组实现

### 3.1 必做对照组（对齐 uni-app x）

| 对照组 | 说明 |
|---|---|
| **Android 原生 View** | 基准真值，定义"原生是什么水平" |
| **Android Compose UI** | 声明式 UI 的代表 |

### 3.2 建议追加对照（uni-app x 未做，但对你更有价值）

| 对照组 | 为什么值得加 |
|---|---|
| **Flutter** | 自绘路线代表；GC 与内存是它的软肋，你有结构性优势 |
| **React Native** | JS 桥接路线代表；新架构 + Hermes |

### 3.3 对照组实现的公平性三条硬规则（沿用 Benchmark 规格 §9.2）

1. **同一份业务逻辑，各框架用各自最佳实践实现**
   — 不是"把 Proteus 代码硬翻一遍"，那是故意让对手写错
2. **同一台设备、同一轮测试、同一套采集方式**
3. **负载参数完全一致**（元素数、行数、嵌套层数、数据量）

### 3.4 一个必须诚实处理的点

**uni-app x 本身也应作为对照组之一**（若可行）。

但需注意：uni-app x 是商业产品，能否在同等条件下测试、是否允许公开对比，
**涉及合规与授权问题，建议先咨询法务**，不要默认可以直接拿它当对照组。

## 4. Proteus 特有的增强测量项

> 这些是 uni-app x 基准**没有**的，但正是你的优势所在。
> **原则：基准项严格复现，增强项额外附加——不得修改基准项的定义。**

### 4.1 4050 测试增强项

| 增强项 | 说明 |
|---|---|
| **布局 / 绘制分离** | 基准只给总耗时；你已能分开（Redmi：布局 **0.063** / 绘制 **2.0**——★绘制未达标，见 `ACCEPTANCE.md` 口径更正；honor10：**0.159 / 0.583**） |
| **GC 暂停次数** | 对 Flutter / RN 对比时的杀手锏 |
| **增量内存** | 你有 0.328 这个数字，基准没有 |

### 4.2 长列表测试增强项

| 增强项 | 说明 |
|---|---|
| **RenderNode 创建 / 复用数** | 你已有 24 / 7941 / 0.997——**这是拍平有效性的直接证据** |
| **每帧 work time（P95/P99）** | 平均帧率会被 vsync 饱和（见 §4.4） |
| **掉帧率** | 比平均帧率更能反映尾延迟 |
| **内存曲线（5 分钟）** | 长跑泄漏检测 |
| **输入延迟** | 触摸 → 提交 |

### 4.3 ★ 一个必须指出的方法论问题

**uni-app x 用的是"平均帧率"，而平均帧率在 vsync 锁频下会饱和。**

你的 124.5 FPS 那组数据就出现过 `p50 = p95 = p99 = 8ms`——被 120Hz（8.33ms）量化，
**测不出真实余量**。

**处理方式**：

| 用途 | 用什么 |
|---|---|
| **与 uni-app x 对比** | 用**平均帧率**（口径必须一致，否则不可比） |
| **内部优化与对外展示余量** | 用 **work time P95/P99 + 掉帧率** |

**两套都出，但标注清楚各自用途。不要混用。**

### 4.4 增强项的价值定位

这些增强项**不能直接和 uni-app x 比**（它没测）。
它们的作用是：

1. 解释"你为什么快"（归因，不是结论）
2. 与 Flutter / RN 对比时作为杀手锏
3. 对外展示余量

## 5. 对比方法与表述边界（★ 最关键）

### 5.1 设备不同时的正确对比方式

| 对比对象 | 能比什么 | 不能比什么 |
|---|---|---|
| **vs Android 原生 View** | ✅ **倍率**（若同设备） | ❌ 绝对值（若设备不同） |
| **vs uni-app x** | ✅ **倍率**，且需标注设备差异 | ❌ 绝对值 |

**倍率对比的逻辑**：

```
uni-app x / 原生View = X 倍（小米 Fold4）
Proteus   / 原生View = Y 倍（你的设备）
```

**只有 X 和 Y 都基于各自设备上的原生基线，倍率才可横向比较。**
这就是为什么**原生 View 对照组是必需的**——它是跨设备对比的换算基准。

### 5.2 三重呈现（建议的对外表格格式）

| 设备 | 框架 | 4050 耗时 | vs 原生倍率 | 长列表 FPS | vs 原生倍率 |
|---|---|---|---|---|---|
| 小米 Fold4 | 原生 View | — | 1.0× | — | 1.0× |
| 小米 Fold4 | uni-app x | 229.2ms | 约 2× | 109 fps | 约 2.4× |
| **你的设备** | **原生 View** | **实测** | **1.0×** | **实测** | **1.0×** |
| **你的设备** | **Proteus** | **实测** | **实测** | **实测** | **实测** |
| 荣耀 10（60Hz） | 原生 View | 实测 | 1.0× | 实测 | 1.0× |
| 荣耀 10（60Hz） | **Proteus** | 实测 | 实测 | 实测 | 实测 |

**这样呈现的好处**：不声称"我们比 uni-app x 快"，而是让**倍率自己说话**，且完全可验证。

### 5.3 三个禁止的表述

| ❌ 禁止 | 原因 |
|---|---|
| "比 uni-app x 快 N 倍"（跨设备直接比绝对值） | 设备不同，不成立 |
| "109 fps → 我们 124.5 fps"（不同设备不同刷新率） | 刷新率不同，帧率不可比 |
| 只报旗舰机数据 | 必须含中端机 |

### 5.4 一个你的独有优势，要突出

**uni-app x 的基准只有 Android 数据**（原文明确"仅提供了 Android 平台性能测试，未包含 iOS 和鸿蒙"）。

**Proteus 有荣耀 10（60Hz / 老 U）的中端数据**——这是基准没有的维度，
也是"真实存量设备表现"的直接证据。**建议在报告中单列一章。**

## 9. 给实现 LLM 的执行指令

1. **UB0 环境控制设施未完成前，禁止产出任何对比数据。** 不符合 §2 九条的数据一律作废。
2. **4050 与长列表的规格必须逐条严格复现**，不得"优化"或"改进"基准定义。
3. **计时终点严格为"主线程渲染指令全部送达 OS 渲染进程"**，禁止自行延伸。
4. **必须采集 AOT 闲时优化后的数据作为主数据**，初次安装数据作为对照。
5. **Perfetto 必须观测核调度**，被调度到超大核的数据一律剔除并记录。
6. **对标对比用平均帧率**（口径一致），**内部余量展示用 work time**，两套标注清楚，禁止混用。
7. **视频元素若未落地，必须标注"以占位替代"并说明差异**。
8. **对照组必须用各框架最佳实践实现**，禁止硬翻代码。
9. **中端机数据必须有**，只报旗舰机视为未完成。
10. **禁止跨设备比绝对值**，只能比基于各自原生基线的倍率。
11. 若要将 uni-app x 作为对照组，**先咨询法务**。
