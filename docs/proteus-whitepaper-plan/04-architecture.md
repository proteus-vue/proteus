## 4.1 全景图

```
                     业务组件（.vue / 小程序 DSL）

        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   【渲染层 G-27】       【能力层 G-28】       【资源层 G-46】
    Render IR            Capability IR         ResourcePool IR
        │                     │                     │
   Backend SPI           Backend SPI           Backend SPI
   ├ VueDom              ├ Native              ├ Cookie
   ├ Skia                ├ Wechat              ├ Token
   ├ Flutter             ├ Alipay              └ SSO
   └ Native              └ Harmony
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              ▼
                    【宿主运行时 G-39】
                     HostRuntime SPI
                              │
        ┌─────────────────────┼─────────────────────┐
        ▼                     ▼                     ▼
   【容器 G-42】        【所有权 G-43】       【基座 G-45】
    Container SPI        Ownership IR         DevHost SPI
        │                     │                     │
        └─────────────────────┼─────────────────────┘
                              ▼
                    【验证层 G-44/51/52】

```

**关键**：验证层是**唯一"反向约束"层**——它要求前面所有层都必须自带 Test IR。**没有验证层的架构 = 没有免疫系统的架构。**

## 4.2 七层详解

| 层 | 编号 | 语义 | 关键能力 |
|----|------|------|---------|
| **渲染** | G-27 | Render IR | 同一 App 不同页面用不同渲染引擎（G-27.7） |
| **能力** | G-28 | Capability IR | 跨端能力收敛（登录/支付/分享/设备） |
| **资源** | G-46 | ResourcePool IR | 登录态/请求/缓存跨端共享 |
| **宿主** | G-39 | HostRuntime SPI | bootstrap / 事件 / 线程归它管 |
| **容器** | G-42 | Container SPI | 安全网关 + 签名校验 |
| **所有权** | G-43 | Ownership IR | 跨端内存治理（Rc/Arc/GC/手动） |
| **基座** | G-45 | DevHost SPI | 装一次，换插件，永不重打 |

---

## 4.3 渲染层：G-27.7 的杀手场景

**"同一 App 不同页面用不同渲染引擎"**——这是竞品架构上做不到的：

> 按页选后端的完整映射（商品详情→Native、品牌动效→Flutter、数据大屏→Skia、H5→VueDom）与 Flutter Web 同构对比，见 **05 §5.2**（方案侧完整展开），此处不重复。

> **诚实边界**：切换的**最小粒度是"页面"，不是"组件"**。
> 一个页面内禁止动态切换渲染后端（状态迁移成本极高、收益极小）。
> 要做，整个页面重新挂载（G-42 五原子销毁保证无泄漏）。

## 4.4 资源层：G-46 三层资源池

```
L1 登录态   Cookie ⇄ Token 自动降级（同根域走 Cookie，跨域走 Token）
L2 请求     SSO + 拦截器（原生/WebView 用同一发件箱）
L3 缓存     TTL + 命名空间隔离（按 origin 分桶，登出全清）
               ↓
       跨页所有权（G-43 Rc/Weak 应用）
    登录态归宿主所有，页面借用，销毁时归还
```

**双轨不是妥协，是必然**：微信小程序 SSO 用 `accountId` + 临时 code，不是直接共享 Cookie——**所以必须 Cookie + Token 两条腿走路**。

---

## 4.5 所有权层：G-43 的差异化

**跨端内存治理**——这是别人不做，我们做到的：

| 范式 | 支持 |
|------|------|
| Rust 风格所有权 | 编译期 move/borrow 检查 |
| C++ RAII | 作用域析构 |
| GC（JS/Java） | 自动回收 |
| **混合（PSS 分级）** | **按场景静态分级，JS 部分尽力而为** |

**DevTools 所有权图**：可视化资源持有关系，**泄漏直接报出"谁持有、凭什么持有、在哪行创建"**。

> **诚实边界**：JS 无法全编译期借用检查（PSS 分级），conformance 未完备——**已知缺口，不是遗漏**。

## 4.6 基座层：G-45 的 Install-Once

**传统循环 vs G-45 循环**：

```
uni-app（自定义基座循环）：
  改原生插件 → 云打包自定义基座（分钟级，页面越多越慢）
            → 卸载重装 → 登录态丢失 → 验证 → 再改 → 再打包 …… 循环往复

Proteus（Install-Once Host）：
  改原生插件 → dev server push 插件模块（秒级）
            → 基座装载即验证（签名 + conformance 快检）
            → pending 调用自动回放 —— 基座 0 次重打，JS 上下文 0 次重启
```

**构建时间从 O(业务规模) 变为 O(改动)**——基座 cacheKey 只由「框架版本 + ABI」决定，与页面数/插件数彻底无关。

## 4.7 验证层：唯一的反向约束层

```
G-44 Test IR    测试语义（断言/用例/结果格式）
G-51 Runner     执行环境（文档/模拟/真机）+ 三阶梯度
G-52 跨设备     设备形态（屏幕/系统/输入/环境）+ 等价类
```

**三阶梯度门槛**：

```
L0 文档自检  → 证明"写了"
L1 IR 模拟   → 证明"算得对"
L2 真运行时  → 证明"真机能跑"（模拟器永远无法验证真进程隔离）
```

> **任何一层都不可替代，缺一层就有盲区。**

## 4.8 成熟度模型（L0-L6）

| 级别 | 状态 | 依赖 |
|------|------|------|
| **L0** | 文档自检 | G-50 selfcheck |
| **L1** | IR 模拟 | G-51 InMemory 后端 |
| **L2** | 真运行时 + 设备矩阵 | G-51 + G-52 |
| **L3** | 跨设备云端（定义中） | G-52 接口，调度留 G-53 |
| **L4** | 开放生态 | **依赖 G-49 L3** |
| **L5** | 开发者门户 | G-50 A 工具链 |
| **L6** | 治理与分佣 | G-50 B 生态 |

## 4.9 七层的对称性

```
渲染一致  → G-27（外）
数据一致  → G-46（内）
组合一致  → G-47（接缝）
运行时    → G-48（小程序）
隔离      → G-49（沙箱）
平台      → G-50（开发者）
验证      → G-44 + G-51 + G-52
```

**七层 SPI 全部有"接口 + conformance + 参考实现 + 铁律"——这是整套体系可信度的根基。**
