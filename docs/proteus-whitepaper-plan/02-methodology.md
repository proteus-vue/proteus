# 02 · SPI-First 五步法（元方法论）

> **这是整套体系的元方法论，不绑定 Proteus，可套用到任意大工程。**

> **来源注**：本文为对外速写（含 Proteus 侧实例）；五步法**完整定义**与 8 反模式 AP-01~08 的 SSOT = `docs/spi-first-methodology/SPI-First-Methodology.md`（+ `anti-patterns.md`）。

---

## 2.1 五步法总览

| Step | 动作 | 关键判定 |
|------|------|---------|
| ① 找耦合点 | `grep -c "具体实现名"` | 出现 ≥2 文件 = 候选 |
| ② 语义收敛 | 接口只用业务语言 | **禁用技术/厂商名词** ← 成败关键 |
| ③ 可插拔后端 | ≥2 个实现，含 Mock | 单后端 SPI = 假 SPI |
| ④ conformance | 同一份测试跑所有后端 | 把质量从"靠人记"变"靠断言" |
| ⑤ 诚实边界 | 声明性能/能力/适用三条 | 防止被包装成银弹 |

---

## 2.2 Step ①：找耦合点（The Coupling Audit）

扫描系统，问一个问题：

> **"如果我要换掉 X，需要改多少文件？"**

换数据库、换 UI 库、换消息队列、换鉴权方案……**凡是"改动会扩散到业务层"的，都是耦合点，都是候选。**

| 耦合点 | 传统做法 | SPI-First |
|--------|---------|-----------|
| 数据库 | 业务代码直接 SQL | Repository SPI + 多后端 |
| 消息队列 | 硬编码 Kafka | MessageBroker SPI |
| 鉴权 | `if (isAdmin)` | Policy SPI |
| 存储 | 直接 S3 SDK | Storage SPI |

**这就是"逐个攻破"的对象清单。**

---

## 2.3 Step ②：语义收敛（Define the Semantic）—— ★ 成败关键

**定义"做什么"，不定义"怎么做"。** 接口必须由**业务语言**描述，不是由实现细节描述。

**坏例子**：`interface SaveToS3(bucket, key)` ← 泄漏了 S3
**好例子**：`interface StoreArtifact(id, bytes)` ← 纯语义

> **接口一旦含实现名词，后端就无法替换。**
> 二十一次泛化里每次都踩过这个坑——
> G-27 最早定义 `<pg-glass>`（语义）而非 `backdrop-filter`（实现）就是这个道理。

**判定标准**：看接口签名，能不能猜出底层用了什么技术？
- 能猜出来 → 语义泄漏，不合格
- 猜不出来 → 合格

---

## 2.4 Step ③：可插拔后端（Pluggable Implementations）

**至少两个后端，其中一个是 Headless / Mock。**

**为什么必须两个？**

> **单后端 SPI 是假 SPI**——你从来没验证过可替换性，
> 等到真要换时才发现接口被写死了。

| 后端类型 | 作用 |
|---------|------|
| 生产后端 A | 主实现 |
| 生产后端 B | **证明可替换性**（这是 SPI 存在的意义） |
| Mock / Headless | 测试用，无外部依赖（G-44 的 Headless、G-45 的降级后端） |

---

## 2.5 Step ④：conformance 验证（The Verifier）—— ★ 把"拆分"变成"可量化逐个攻破"

**每个 SPI 配一套 conformance 测试，任何后端实现都必须通过同一套测试才能接入。**

| | 结果 |
|--|------|
| 没有 conformance | 接口是约定俗成的，会随时间漂移（**99% 项目的命运**） |
| 有 conformance | 接口是机器强制的，实现可以自由替换 |

> **conformance 就是把"质量"从"靠人记住"变成"靠测试断言"。**

**五条铁律（Proteus 实践总结）**：

1. **同 IR 跨 Backend 语义等价**（G-44.4）——同一份 IR，不同后端必须产出同 shape 结果
2. **负向测试必须有**（校验器有牙齿）——注入故障，断言它**确实会失败**
3. **验证器本身要被验证**——防止"断言与输出格式漂移"（G-46/G-47/G-52 都踩过）
4. **PASS 计数动态抓取**——禁止硬编码"37/37"（G-51 AP-19 反模式）
5. **环境隔离**——测试之间必须 `freshEnv()`，防状态污染

---

## 2.6 Step ⑤：诚实边界（The Honesty Layer）—— ★ 防止反噬

**明确声明这套抽象不解决什么。** 三条必答：

| 维度 | 要回答的问题 |
|------|-------------|
| **性能** | 抽象层带来了多少开销？什么时候不该用？ |
| **能力** | 哪些能力会降级？降级到什么程度？ |
| **适用** | 什么场景下**不该**用这套抽象？ |

**为什么必须有？**

> **抽象必然有成本**（间接层、调试难度、学习曲线），
> **不承认成本的方法论，会在规模上来时反噬。**
> 诚实边界让使用者能做出**明知的选择**。

**Proteus 的实例**：
- G-40 CMP046：未实测的数据禁止宣称
- G-45.9：Install-Once 是**开发态语义**，禁止宣称线上热更新
- G-48：标准小程序 API 兼容目标 90%+，平台特有能力走显式适配
- G-49 CMP-117：iOS 无法应用内多进程，承诺**语义等价**，不承诺机制一致

## 2.7 八个反模式（自检清单）

| ID | 反模式 | 症状 |
|----|--------|------|
| **AP-01** | 单后端 SPI | 声称可插拔，但只有一个实现 |
| **AP-02** | 接口含技术名词 | `SaveToS3` 而非 `StoreArtifact` |
| **AP-03** | 无 conformance | 接口靠文档约定，随时间漂移 |
| **AP-04** | 业务绕过接口 | 业务代码直接调具体实现 |
| **AP-05** | 类型 Only | 只定义 TypeScript 类型，无运行时契约 |
| **AP-06** | 过度设计 | 只有 1 个实现可能，却做了 SPI |
| **AP-07** | 后端爆炸 | 后端数量失控，无治理 |
| **AP-08** | 成本不透明 | 不承认抽象开销 |

## 2.8 跨领域实例：支付模块重构

假设重构一个硬编码支付宝的老电商系统：

**① 找耦合点**：`grep -c "alipay"` → 37 处业务文件。候选锁定。

**② 语义收敛**：`interface PaymentProvider { charge / refund / query }`，接口里**不准出现 alipay 专有名词**。

**③ 可插拔**：`AlipayProvider`（现有逻辑搬进来）+ `WechatProvider`（新增）+ `MockProvider`（测试用）。

**④ conformance**：`payment-conformance.ts`——任何 Provider 必须通过"重复扣款幂等""部分退款""网络中断重试"等 20 个用例。**加微信支付时，跑同一套测试即可证明可用。**

**⑤ 诚实边界**：声明"SPI 不解决支付渠道的合规差异，合规仍由各 Provider 自行负责"。

> **这和 G-27 定义渲染后端、G-28 定义 NativeBackend、G-44 定义 TestBackend——是同构的。**
> 文档结构、命名、验证方式都一模一样。

## 2.9 不适用场景（诚实边界）

SPI-First **不该用**在这些情况：

1. **只有一个实现可能，且永远不会变**——直接写死，别过度设计（AP-06）
2. **性能极端敏感的热路径**——间接层开销不可接受时，绕过 SPI（但要有铁律约束）
3. **接口尚未稳定**——先用具体实现跑通，等模式浮现再抽象
4. **团队规模 < 3 人**——conformance 的维护成本可能超过收益

> **方法论的价值在于"知道什么时候不用它"。**
