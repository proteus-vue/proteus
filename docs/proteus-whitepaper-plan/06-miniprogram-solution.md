## 6.1 三层架构

```
┌─────────────────────────────────────────────┐
│    任意标准小程序（微信/支付宝/抖音/鸿蒙）      │
│    遵循标准结构：.js / .json / .wxml / .wxss  │
└──────────────────┬──────────────────────────┘
                   │ ① 标准小程序运行时（宿主内核）
                   ▼
┌─────────────────────────────────────────────┐
│    StandardMiniProgramRuntime（标准运行时）   │
│  · 双线程：逻辑层(JS Engine) + 视图层(Web)   │
│  · AppService + PageFrame + 生命周期调度     │
│  · setData 通信 + 代码包加载/分包            │
│  · 安全沙箱（AppID 隔离、资源配额）           │
└──────────────────┬──────────────────────────┘
                   │ ② Platform Adapter SPI（★ 关键）
                   ▼
┌─────────────────────────────────────────────┐
│  ┌────────┬────────┬────────┬──────────┐   │
│  │ WeChat │ Alipay │ Douyin │ HarmonyOS │   │

│  └────────┴────────┴────────┴──────────┘   │
│   抹平平台差异：登录/支付/分享/组件/API       │
│   通过 G-46 资源池共享登录态/凭证             │
└─────────────────────────────────────────────┘
```

## 6.2 为什么"兼容容器"优于"自造平台"

| 维度 | 造开发者平台 | **兼容运行容器** |
|------|-------------|----------------|
| 生态 | 从零拉开发者（极难） | **承接已有小程序**（微信 400万+） |
| 标准 | 自定（无人跟从） | **用现成标准（微信已成事实标准）** |
| 工作量 | 巨大（IDE+审核+文档+社区） | **集中在 Adapter（可并行）** |
| 冷启动 | 死循环（无开发者→无用户） | **无：现有小程序直接跑** |
| 价值 | 长期（不确定） | **短期可见（存量迁移）** |

> **微信小程序标准已是事实标准**——支付宝/抖音/鸿蒙**全部兼容或部分兼容**微信小程序语法。
> **所以"做兼容容器"的本质是"把微信标准当标准，其他平台做 Adapter"——顺势而为。**

## 6.3 G-48：兼容式运行容器

### 兼容矩阵（L0/L1/L2/L3）

| 等级 | 含义 | 处理 |
|------|------|------|
| **L0** | 标准 API，直接可用 | 零适配 |
| **L1** | 语义等价，名称不同 | Adapter 映射 |
| **L2** | 能力存在，形态不同 | 显式适配（Capability IR） |
| **L3** | **平台特有，不支持** | 兼容矩阵报告明确指出 |

> **诚实边界（G-48 铁律）**：
> **标准小程序 API 兼容目标 90%+**；
> 平台特有能力（支付/登录/分享）走 Capability IR 显式适配，**不承诺自动兼容**。

**运行时检测**小程序用到的能力，给出**兼容矩阵报告**——**而不是默默失败**。

### 双线程是硬约束

微信/支付宝小程序强制双线程（逻辑层不可操作 DOM，通过 `setData` 通信）。
**运行时必须真实实现双线程隔离**，不能用单线程模拟——否则标准小程序跑不起来。

### MVP 策略

**微信 Adapter + 单进程模拟双线程 + 凭证级隔离**——理由：
- 微信标准是事实标准，Adapter 几乎零工作量，**最快证明容器可用**
- 单进程模拟双线程**先验证架构正确**（G-40 教训：先跑通再优化）
- 进程级沙箱是工程量，后置不影响架构验证

## 6.4 G-49：进程级沙箱（打开 G-50 的钥匙）

### 隔离强度分层

```
L1 逻辑隔离      独立 Context              ← G-48 已有
L2 存储/权限隔离  数据目录 + 网关           ← ★ G-49
L3 进程隔离      android:process 等        ← ★ G-49
L4 运行时隔离    V8 Isolate / microVM      ← G-50（明确后置）
```

**关键判断**：不一步到位做 V8 Isolate（那是服务端思路，Cloudflare/Deno 的路），
而是**先做移动端宿主内可落地的 L1-L3**。L4 留给 G-50，因为**它就是"运行任意第三方代码"的量级**。

### 五条安全铁律

| 铁律 | 内容 |
|------|------|
| **G-49.1** | **deny-by-default**（默认拒绝所有能力） |
| **G-49.2** | **无开放 bridge**（禁用 `addJavascriptInterface` 式全量桥接） |
| **G-49.3** | **跨小程序零共享**（`ISOLATION_BREACH` 检测 + Drop 级联） |
| **G-49.4** | **配额超限不抛宿主**（`QUOTA_EXCEEDED` recoverable） |
| **G-49.5** | **崩溃隔离**（一个小程序崩不影响宿主） |

### 诚实边界

- **iOS 无法应用内多进程**（系统限制）→ 靠 WebContent 系统级隔离
  → **CMP-117：承诺语义等价，不承诺机制一致**
- **G-49 = L1+L2+L3**，L4 留给 G-50
- **不承诺"任意第三方代码安全运行"**——需 G-49 L3 + G-50 审核体系

## 6.5 G-50：开发者平台（A 工具链 + B 生态）

### Scope 二分

| 子集 | 内容 |
|------|------|
| **A. 工具链** | CLI 流水线 / 脚手架 / 调试协议 / 能力生成 / **发布运行时** |
| **B. 生态** | 开发者门户 / **提审与双签名** / 分发灰度 / **治理与分佣** |

**AppPackage 是 A 与 B 的解耦点**——CLI `publish()` 是唯一桥接点，**A 工具链可完全独立用**（即使不做 B 生态）。

### 双签名（★ G-45 扩展）

```
开发者签名（证明来源）+ 平台审核签名（证明已审）
        ↓
两个缺一即拒装
```

**"审核过的包才可运行"是 B 生态的安全地基。**

### 撤销 = 应用级 Drop 级联

```
revoke(packageId)
   = G-46（清凭证）+ G-43（Drop 级联）的推广
        ↓
又一次方法论泛化
```

## 6.6 编号路线

```
G-48 兼容式小程序运行容器  （AppID 级隔离，自有 + 受控第三方）
G-49 进程级沙箱（L1-L3）   ← 打开 G-50 的前置条件
G-50 开发者平台            （最后做：开放平台 / 审核 / 生态）
```

> **G-48 + G-49 合起来 = "兼容式小程序运行容器 + 进程级隔离"**
> 已具备**受控第三方小程序安全运行**的能力。
> **G-50（开放平台）的资格条件是"G-49 L3 落地 + 真原生隔离后端"——门槛明确。**

## 6.7 方案价值：你到底能得到什么

| 目标 | 是否达成 | 依赖 |
|------|---------|------|
| **开发属于自己的小程序 App** | ✅ **完全可以** | G-48 |
| **打造自有容器（跑自己的小程序 + 受控接入）** | ✅ **完全可以** | G-48 + G-39 |
| **造微信式开放平台（任意第三方代码安全运行）** | ⚠️ 骨架能，**需 G-49 L3 + G-50** | 真原生后端 |

> **诚实边界**：G-48 承诺"**兼容运行**"，不承诺"**任意第三方代码安全运行**"——
> 后者需 G-49 进程级隔离 + G-50 审核体系，才具备开放平台资格。
> **这条边界特别重要**——宣称"能运行任意第三方小程序"就触及微信/支付宝级别的**安全责任**。
