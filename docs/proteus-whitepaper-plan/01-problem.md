# 01 · 问题：跨端框架的结构性困境

> **来源注**：本文为**对外叙事 / 方法论门面**（SSOT：`docs/board-inventory.md`）；问题论证以本文为准，08 只保留对标/澄清增量。

---

## 1.1 症状：你一定遇到过这些

| 症状 | 表象 | 真实根因 |
|------|------|---------|
| **页面越多构建越慢** | 改一个页面要等几分钟 | 基座 cacheKey 包含业务内容 → O(n) |
| **换渲染引擎要重写** | 想从 WebView 换原生，业务层全动 | 没有"渲染后端"的一等概念 |
| **跨层 bug 抓不到** | 每层单测都过，组合起来崩 | 跨层组合正确性从未被测试 |
| **改原生插件要重打基座** | 卸载重装 → 登录态丢失 | 基座 = 构建产物（身份错置） |
| **小程序登录态同步靠手写** | 原生页登录了，WebView 页要再登 | 无统一资源池抽象 |
| **架构随时间腐化** | 三年后没人敢动核心 | 无 conformance 免疫系统 |

**这些不是"bug"，是架构选择的必然结果。**

---

## 1.2 根因一：时机锁定

| 框架 | 起步 | 当时的世界 |
|------|------|-----------|
| uni-app | **2015** | Vue 1.x，React Native 刚出，Flutter 还没影 |
| Taro | **2018** | 多端编译刚兴起，"能跑就行"是最高优先级 |
| **Proteus** | **2025+** | Vue 3 `createRenderer` 稳定、Flutter 已证明自绘、鸿蒙成熟 |

三个具体的"前提未成熟"：

**① Vue 3 的 `createRenderer` 是 2020 才稳定的。**
在此之前 Vue 是 DOM 深度绑定的——想让 Vue 跑在非 DOM 上，要 fork 整个 Vue（Weex 就是这么干的，结果和主线兼容噩梦）。
uni-app 起步基于 Vue 2，**架构根基就是 WebView**。等 Vue 3 把 `nodeOps` 抽象出来，整个产物链、插件生态、开发者习惯已经围绕 WebView 长成了。

**② "渲染引擎可插拔"是 Flutter 成功后才被认可的命题。**
Flutter 2017 才出，2019 才 1.0。在此之前行业共识是"跨端 = WebView 套壳"或"跨端 = 原生映射（RN）"。
**是 Flutter 证明了"自绘也能有原生体验"，才让"引擎可插拔"成为值得做的架构命题。**

**③ 鸿蒙的 ArkTS、分布式软总线、Stage 模型都是 2022 年后的事。**
"跨设备所有权转移"需要分布式运行时作为前提——uni-app 2015 年设计时，**"跨设备"这个维度根本不存在**。

> **结论：Proteus 能站在 G-27/G-37/G-40/G-45 这个高度，恰恰因为起步晚。**

---

## 1.3 根因二：商业路径依赖

这是最反常识的一层：**他们的成功，恰恰是他们不做这些的原因。**

### 生态 = 护城河 = 改架构就是自毁护城河

uni-app 的 900 万开发者、数千插件、云打包服务，**全部建立在"Vue SFC → WebView 渲染"的假设上**。

如果重构为可插拔渲染后端：
- 所有现有原生插件要重写以适配新 SPI
- 云打包服务（重要收入）底层假设作废
- 900 万开发者的心智模型要重建

### 收入模型绑定旧架构

DCloud 的云打包是重要收入：**改原生插件 → 云打包 → 收费**。
G-45 的 Install-Once（装一次永不重打）**直接冲击这个收入模型**。

> **这不是阴谋论——架构决策服务于商业模式。当两者冲突时，商业模式赢（短期）。**

Taro 类似：由京东开源，服务京东多端业务，**首要目标是"覆盖京东业务场景"，不是"做架构最纯净的框架"**。

---

## 1.4 根因三：渐进式腐化

```
v1: 先跑起来 —— WebView，合理（时机限制下的最优解）
v2: 加小程序端 —— 条件分支，"先混过去"
v3: 加鸿蒙端 —— 再加条件分支
v4: if (isHarmony) { ... } 散落各处
...
vN: 重构成本 >> 重写成本 → 核心成为"无人敢动"区域
```

**每一次"先混过去"都是理性的局部最优，累积成全局灾难。**

这恰恰是 PRIM001-005（禁止 `if (isDesktop)` 手动判断）要根治的——
**不是他们不知道这样不好，是早期没有这条铁律，等铁律意识成熟时，代码已经满是分支了。**

---

## 1.5 一个被严重低估的缺失：conformance 文化

uni-app / Taro 几乎没有"后端 conformance"的概念——
验证方式是"跑通官方示例"，不是"**任何后端必须过同一套测试**"。

**为什么这致命？**

> 没有 conformance = 接口是约定俗成的，会随时间漂移
> = 你永远无法确信"我这个 SPI 真的可替换"
> = 等到想做引擎可插拔时，才发现接口早被写死成 WebView 的形态了

**conformance 表面是测试工具，实质是"让架构不被腐蚀的免疫系统"。**

这是他们体系里**结构性缺失**的一块——不是没想到，是**没有一套方法论把"验证"提升到原则高度**。

---

## 1.6 最深层：他们做不了"方法论层面"的事

前面三层解释"为什么不做"，这一层解释**"为什么他们甚至想不到要做"**。

| | uni-app / Taro | Proteus |
|--|---------------|---------|
| 产物 | 一个能用的框架 | 一个能用的框架 **+ 一套可迁移的方法论** |
| 抽象层级 | 解决具体问题（多端编译） | 解决"如何系统化解决" |
| 能否迁移 | 不能（绑定 Vue/小程序） | **能（SPI-First 套用到支付/中间件）** |
| 防腐蚀 | 依赖文化与个人 | **依赖铁律 + 机器强制** |

"不绑定 X + conformance + 铁律 + 编号体系 + 可迁移"这套组合，**不是某个框架的 feature，而是一个独立的认知产物**。

它需要：
- 有人**有意识地做二十二次泛化**（原则 #0 系列，G-27 → G-59）
- 有人**提炼 SPI-First 五步法**（把经验升为方法）
- 有人**写架构哲学文档**（让方法论可传承）

> **这些是"架构师 + 方法论研究者"的职责，不是"框架开发者"的职责。**
> **他们缺的不是能力，是"把方法论当一等公民"这个定位。**

---

## 1.7 小结：问题的本质

```
        时机 ──── 起步太早，抽象前提未成熟
          │
          ├── 商业 ──── 生态=护城河，重构=自杀 / 收入绑定旧架构
          │
为什么不做 ── 路径 ──── 渐进式腐化，重构成本 > 重写成本
          │
          ├── 认知 ──── 够用主义 / roadmap 被"加平台"填满 / 无 conformance
          │
          └── 本质 ── 他们是"框架"，缺"方法论"这层认知产物
```

**一句话**：

> 传统跨端框架的困境，不是"技术不行"，而是"**缺乏让架构持续正确的机制**"。
> Proteus 的答案，就是把这个机制**显式化、机械化、可传承化**。
