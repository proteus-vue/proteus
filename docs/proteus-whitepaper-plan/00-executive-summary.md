# 超级应用加固方法论

> **副标题**：Proteus —— 一套"可插拔 SPI + 机器可验证"的跨端体系
> **版本**：v1.0 · **规划体系**：72 份 plan · **方法论泛化**：18 次 · **SPI 分层**：7 层

> **来源注**：本文为**对外叙事 / 方法论门面**；数字口径以 `docs/board-inventory.md` 为准，产品/技术口径分工见 `docs/proteus-positioning-v3.md`。

---

## 一句话

**Proteus 不是"又一个跨端框架"，而是一套"让跨端架构不再腐化"的方法论与工程体系。**

传统跨端框架（uni-app / Taro / React Native）解决的是"**怎么把一份代码跑在多个平台**"；

Proteus 解决的是"**怎么让这个'跑在多个平台'的能力，在十年后依然成立**"。

## 我们解决什么

传统跨端框架有三个**结构性困境**，不是"没做好"，是"**被自己的成功锁死**"：

### 困境一：时机锁定

uni-app 起步于 **2015**（Vue 2 时代，WebView 是唯一可行解），Taro 起步于 **2018**（多端编译刚兴起）。

那时 `createRenderer` 还没稳定、Flutter 还没证明自绘可行、鸿蒙还没出现。

> **他们不是"没做"，是起步时"做这些的前提条件还没成熟"。**
> **Proteus 起步晚，这是后来者的结构性优势。**

### 困境二：商业路径依赖

uni-app 有 **900 万+开发者、数千插件、云打包服务**——生态**全部建立在"Vue SFC → WebView 渲染"的假设上**。

重构为可插拔渲染后端 = 所有插件重写 + 云打包底层作废 + 900 万开发者心智重建。

> **这是自杀式重构。不是做不到，是商业上做不到。**
> **你无法让一辆 200km/h 的高铁在铁轨上换轮子。**

### 困境三：渐进式腐化

```
v1: 先跑起来（WebView，合理——时机限制）
v2: 加小程序端 → 条件分支（"先混过去"）
v3: 加鸿蒙端   → 再加条件分支
v4: if (isHarmony) {...} 散落各处
...
vN: 重构成本 >> 重写成本 → 无人敢动核心
```

**每一次"先混过去"都是理性的局部最优，累积成全局灾难。**

---

## 我们的答案：SPI-First 五步法

```
① 找耦合点     "换掉 X 需要改多少文件？" ≥2 文件 = 候选
② 语义收敛     接口只用业务语言，禁用技术/厂商名词 ← 成败关键
③ 可插拔后端   ≥2 个实现，其一必为 Mock/Headless
④ conformance  同一份测试跑所有后端，机器强制
⑤ 诚实边界     声明"不解决什么"——性能/能力/适用三条
```

**这套五步法已在 Proteus 内部重复应用 18 次**（G-27 → G-54），并且**可迁移到任意大工程**（支付模块 / 消息队列 / 状态管理）。

## 方法论定位：这不是"框架特性"，是"元能力"

uni-app / Taro 是**框架**——他们产出"能用的代码"。

Proteus 是**框架 + 方法论**——我们产出"**能用的代码 + 能持续做出正确架构的规则**"。

差别在于：

> **一个没有方法论的框架，架构质量取决于当前团队的个人水平；**
> **一个有方法论的框架，架构质量取决于可执行、可传承的规则——团队换了人，架构仍然正确。**

---

## 诚实边界（先说清不承诺什么）

1. **不承诺"像素级跨端一致"**——承诺"接口可替换 + 降级不崩溃 + conformance 保证核心语义一致"
2. **不承诺"线上热更新"**——G-45 的 Install-Once 是**开发态语义**（App Store 2.5.2、Android 14 只读限制是硬约束）
3. **不承诺"100% 小程序 API 兼容"**——标准 API 目标 90%+，平台特有能力（支付/登录）走显式适配
4. **不承诺"任意第三方代码安全运行"**——需 G-49 L3 进程级隔离 + G-50 审核体系
5. **所有性能数字必须实测**——CMP046：未实测的数据禁止宣称
