# 03 · 二十一次泛化：方法论的证据

> **原则 #0「不绑定」系列——同一套动作，重复二十一次。**

> **来源注**：本文为对外叙事；库内映射（每行 G 的"不绑定 X"口径）SSOT = `docs/spi-first-methodology/proteus-mapping.md`（已扩至 G-58），编号为**官方唯一 G 表**（G-01~G-58，`docs/board-inventory.md`）。

---

## 3.1 同一个动作，重复二十一次

```
找到系统中一个"被硬编码的具体实现"
        ↓
把它提升为一个"语义接口 + 可插拔后端"
        ↓
定义 conformance，让任何实现都可验证
```

**这不是巧合，是一条规则**：沿着"**接口与实现的耦合点**"切——这个结构在**所有复杂系统里都存在**。

## 3.3 洞察：这不是"我们设计得好"

**所有活过十年的大工程，最终都自己长出了这套结构**：

| 系统 | 长出的结构 |
|------|-----------|
| 操作系统 | 驱动模型（VFS / 设备驱动） |
| 数据库 | 存储引擎插件（InnoDB / MyISAM / RocksDB） |
| 编译器 | 前端-中端-后端（LLVM IR） |
| IDE | 插件系统（VSCode Extension） |
| 浏览器 | 渲染引擎可替换（Blink / Gecko / WebKit） |

> **我们只是把它显式化了，还配上了 conformance 和铁律。**
> **所以它能迁移——不是因为设计得好，是因为这个结构在所有工程里都存在。**

---

## 3.4 每一次泛化的共性结构

```
定义语义（XXX IR）
   + 后端实现（XXXBackend SPI）
   + conformance 验证（CMP-XXX）
   + 铁律（G-XX.1-N）
   + 诚实边界（不承诺什么）
```

**五件套齐全，才算一次完整的泛化。**

缺任何一件：
- 缺 IR → 语义泄漏（AP-02）
- 缺多后端 → 假 SPI（AP-01）
- 缺 conformance → 接口漂移（AP-03）
- 缺铁律 → 无约束力
- 缺诚实边界 → 会被包装成银弹（AP-08）

把二十一次泛化按五步法拆成表格，**缺哪格就是缺口**：

| 编号 | ①耦合 | ②语义 | ③后端 | ④conformance | ⑤边界 |
|------|-------|-------|-------|--------------|-------|
| G-27 渲染 | ✓ | ✓ | ✓ | ✓ | ✓ |
| G-43 所有权 | ✓ | ✓ | ✓ | **PSS 分级（未完备）** | ✓ |
| G-44 测试 | ✓ | ✓ | ✓ | 跨层 INT 套件 | 模拟器 ≠ 真机 |
| ... | | | | | |

> **比"感觉哪里不太对"精确一万倍。**
> G-43（所有权/PSS）的 Step ④ 是"JS 无法全编译期检查（PSS 分级）"——
> 说明 conformance 未完备，是**已知缺口，不是遗漏**。

## 3.6 复利效应：为什么泛化越做越快

| 泛化次数 | 工作量 | 原因 |
|---------|-------|------|
| 第 1-3 次 | 大 | 摸索模式、踩坑 |
| 第 4-8 次 | 中 | 模式成熟，模板化 |
| 第 9-21 次 | 小 | **几乎全复用**，只需定义语义层 |

**实例**：G-48（小程序运行时）定义了自己的 **Runtime SPI + PlatformAdapter SPI**，但其 SPI 语义大量复用既有泛化——
渲染（G-27）+ 原生能力（G-28）+ 宿主（G-39）+ 凭证（G-46）+ 组合验证（G-47）。

> **G-48 的真正增量是"运行时形态收敛"**：把微信/支付宝/抖音/鸿蒙的 API 通过 PlatformAdapter 翻译进既有语义，并给出兼容矩阵——这是独立的泛化，不是重复计数。

**这就是方法论的复利**：前 N 次的投入，让第 N+1 次的边际成本趋近于零。

## 3.7 二十一次泛化的"元教训"

1. **沿着耦合点切，不要随便切模块**——耦合点才是真正需要抽象的地方
2. **语义层是核心，后端是细节**——语义一旦泄漏，整个抽象失效
3. **conformance 不是测试，是免疫系统**——它决定抽象能活多久
4. **诚实边界不是示弱，是专业**——不承认成本的抽象会反噬
5. **可迁移性才是方法论的标志**——能拆自己系统叫模块化，能拆任意系统才叫方法论

> **你现在拥有的不是"框架设计方法论"，而是一个判断力**：
> 看到任何大工程，能立刻回答——它有没有被正确拆开？接口是否语义化？
> 有没有 conformance 保证可替换？诚实边界在哪？
> **四问里有一问答不上，就知道它会在哪里出问题。**
