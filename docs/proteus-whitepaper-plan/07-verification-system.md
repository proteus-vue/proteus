## 7.1 为什么验证层是整个体系的地基

回到起点的一个**结构性风险**：

> 前七次泛化的 SPI plan（G-27/29/31/39/40/42/43）每一份都声称"conformance 验证通过"，
> 但"**通过**"这件事本身**没有统一标准**。

| 问题 | 表现 |
|------|------|
| **PASS 不可横向比较** | 各套件测试数、编号、报告格式、失败语义各不相同 |
| **跨层组合从未测试** | 每层单独 conformance 都过，但完整链路没人写过端到端测试 |
| **三维断点无覆盖** | G-25 的 W×H×F 是差异化核心，但全靠"文档说应该这样" |

> **如果"可验证"这件事本身没有被测试，那整套主张的可信度是脆弱的。**

## 7.2 G-44：Test IR（测试语义）

### 第八次泛化：不绑测试实现

```
传统测试：测试代码直接调用被测函数，断言写在测试里，结果各框架自己报告
        ↓
Proteus：测试代码产出 Test IR（断言语义）+ TestBackend SPI 统一执行
```

| 传统 | Proteus |
|------|---------|
| 测试代码直接调被测函数 | 测试产出 **Test IR**（可序列化、可传输） |
| 断言写在测试里 | 断言是 **IR 节点** |
| 结果各框架自报 | **TestBackend SPI** 统一消费，标准化报告 |
| 跨端测试人肉对齐 | **同一份 Test IR，不同 Backend 跑，结果可比** |

### 五个官方后端

```
NodeBackend      → 纯 JS 环境
JSCarrierBackend → JSI 载体上跑（G-40）
AOTBackend       → AOT 编译后跑
HostBackend      → 真实宿主运行时（G-39）
DeviceBackend    → 模拟器/真机（三维断点矩阵）
```

**关键红利**：三维断点（W×H×F）的 100 个 profile，**不需要写 100 套测试代码**。
写一份 Test IR 描述"在 profile X 下，p-adaptive 应该渲染为 Y 形态"，然后在不同后端跑。

## 7.3 G-51：三阶梯度（执行环境维度）

### 三层验证体系

```
L0 文档自检    selfcheck.js      ← G-50 已有（结构完整性）
L1 IR 模拟     TestIRRunner      ← ★ G-51（不依赖原生，验证 IR 语义）
L2 真运行时    NativeAdapter     ← ★ G-51（真进程/真引擎/真签名）
        ↓
  G-51.4 三阶梯度 + 门槛机制（L1=100%，L2 渐进）
```

**为什么必须三层**：
- 文档自检只能证明"写了"，不能证明"算得对"
- 模拟能证明 IR 语义正确，但**模拟器永远无法验证"真进程隔离生效"**
- **任何一层都不可替代，缺一层就有盲区**

### 唯一核心接口

```typescript
interface TestIRRunner {
  execute(suite: TestSuite, opts?): Promise<TestReport>
}
```

**就一个方法。** 承载"不绑定验证执行环境"的泛化。

### 七条不变量

| 编号 | 命题 |
|------|------|
| **INV-01** | 同一 TestSuite 在 L1/L2 结果可比 |
| **INV-02** | 能力缺失 → 降级 ≠ 崩溃 |
| **INV-03** | 断言 FAIL 必有定位 + 分类 |
| **INV-04** | 超时 / 资源超限可恢复 |
| **INV-05** | 真运行时隔离泄漏可被检测 |
| **INV-06** | 报告可序列化、可 diff（CI 门槛） |
| **INV-07** | Runner 自身有回归（runner-regression.gold） |

### G-51 抓到的真问题

| # | 问题 | 性质 |
|---|------|------|
| 1 | `execute` 用 async 但测试同步取值 → Report 字段丢失 | 接口契约 vs 调用方式不一致 |
| 2 | 初版 verify 硬编码"31/31"，实际 36 → 自检失灵 | **AP-19 反模式**（CMP-134） |
| 3 | 超时阈值设为 0ms → CI 必然误报 | 阈值脱离现实 |
| 4 | 模拟栈抛"native-only"而非降级 | 违反 G-46 RSC-01 精神 |

> **第 4 条证明了**：G-46 的铁律（"缺失即降级，永不崩溃"）**必须贯穿到测试基础设施本身**，
> 否则测试框架会在真机验证阶段自毁。

## 7.4 G-52：跨设备一致性（设备形态维度）

### 四维漂移空间

| 维度 | 变量 |
|------|------|
| **屏幕** | dp / density / foldable / safe area |
| **系统** | API level / JS engine / permission model |
| **输入** | touch / mouse / keyboard / pen |
| **环境** | language / timezone / dark mode / a11y |

**四维笛卡尔积 → 组合爆炸**（100+ 设备 × 10 场景 = 不可穷举）。

**不做穷举，做划分 + 代表采样 + 指纹比对**：

```
DeviceEquivalenceClass  等价类，每类取代表设备
DriftFingerprint        四维指纹，用于跨设备 FAIL 归因
ε 阈值                  允许轻微浮动（渲染/触摸天然有误差）
归一化                  报告去噪后可 diff
```

### 五条不变量

| 编号 | 命题 |
|------|------|
| **INV-D1** | 同一设备、同一快照 → 结果稳定（幂等） |
| **INV-D2** | 等价类内代表偏差 ≤ ε |
| **INV-D3** | 跨设备 FAIL 可归因到四维之一 |
| **INV-D4** | 报告归一化后可 diff |
| **INV-D5** | 本地优先 → 云端补充（不强制联网） |

### 二维验证空间

```
             执行环境 →  L0 文档 | L1 模拟 | L2 真机   (G-51)
             设备形态 →  等价类代表 × 四维        (G-52)
```

> **G-52 在 G-51 之上加"设备层"**——**扩展，不重写**。

## 7.5 验证层的元教训（血泪总结）

### 五条铁律

1. **负向测试必须有**（校验器有牙齿）——注入故障，断言它**确实会失败**
2. **验证器本身要被验证**——防"断言与输出格式漂移"
3. **PASS 计数动态抓取**——禁止硬编码"37/37"
4. **环境隔离**——测试之间 `freshEnv()`，防状态污染
5. **数字宣称必须实测**——CMP046：未实测的数据禁止宣称

### 踩过的坑（都已修复并沉淀为铁律）

> 完整踩坑清单（坑 → 修复）见 **10 附录 E**（本目录权威处，此处不重复）——
> 每个坑都是"只有真跑才会发现"的，现在全部沉淀为可复用的铁律，**后面的 plan 不会再犯**。

## 7.6 验证层的价值

| 维度 | 没有验证层 | 有验证层 |
|------|-----------|---------|
| 架构正确性 | 靠人记住 | **机器断言** |
| 接口漂移 | 随时间必然发生 | **conformance 强制** |
| 跨层 bug | 上线才发现 | **组合测试提前捕获** |
| 团队更替 | 质量取决于个人 | **质量取决于规则** |
| 新 plan 成本 | 重新摸索 | **套用模板 + 铁律** |

> **验证层是"让架构不被腐蚀的免疫系统"，也是整套体系可信度的根基。**
