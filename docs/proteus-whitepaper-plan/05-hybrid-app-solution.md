# 05 · 超级应用加固方案

> **G-27（渲染）+ G-46（数据）+ G-47（组合）= 混合 App 的完整一致性**

> **来源注**：本文为对外叙事 / 方法论门面（SSOT：`docs/board-inventory.md`）；本目录内同一份"按页选后端"映射以本文 §5.2 为权威处（04 §4.3 只保留架构层结论）。

---

## 5.1 混合 App 的一致性是个"全集"问题

你的两轮洞察合起来，正好是完整定义：

```
外（渲染/体验）一致  ← G-27：同一 App 不同页面切换渲染后端
内（登录态/请求/缓存）一致 ← G-46：宿主级统一资源池
        ↓ 两者组合
   G-47：接缝一致性（切后端时数据链不断）
```

> **缺了 G-46，G-27 的"按页切后端"就有个致命漏洞**：
> 页面 A（原生）登录了，页面 B（WebView）还得再登一次——
> **渲染一致了，数据链断了。**

**这正是行业现状**：uni-app 等靠业务手写同步，**无统一抽象**。

## 5.2 外：G-27 渲染一致性

```
业务组件（同一份代码）
       ↓
  统一 Render IR（p-grid / pg-glass / ...）
       ↓ Backend SPI
  ┌────┴────┬─────────┐
VueDom    Skia     Native/Flutter
（DOM，   （Canvas，  （App 原生/
 SEO/      一致性好）  跨页混合）
 a11y 好）
```

**运行时按页面/场景选择**（G-27.7）：

| 页面类型 | 后端 | 理由 |
|---------|------|------|
| 商品详情 | Native | 原生控件，体验优先 |
| 品牌动效 | Flutter | 跨端一致性 |
| 数据大屏 | Skia | 高频绘制 |
| H5 落地 | VueDom | Web 生态复用 |

**与 Flutter Web 的同构**：

| Flutter Web | Proteus | 说明 |
|------------|---------|------|
| CanvasKit（Skia→WASM） | SkiaBackend | 一致性高、体积大 |
| HTML DOM | VueDomBackend | 体积小、SEO 好、一致性差 |

> **同一个 IR 的两个 Backend——Flutter 的两种渲染器，在我们的架构里就是 SPI 的两个实现。**

**诚实边界**：
- Web 端通常**不需要切**，真正杀手场景是 **App 内按页混合**
- IR 的表达力是天花板——IR 丢了语义，切换就会丢失信息（降级不崩溃兜底）
- DOM 和 Canvas 能力差无法消除（a11y/SEO），**是 fidelity 分档，不是等价替换**

## 5.3 内：G-46 数据一致性

### 三层资源池

```
L1 登录态   Cookie ⇄ Token 自动降级
L2 请求     SSO + 拦截器（统一发件箱）
L3 缓存     TTL + 命名空间隔离（按 origin 分桶）
```

### 双轨策略（★ 核心设计）

| 场景 | 轨道 | 原因 |
|------|------|------|
| 同根域 | **Cookie 同步轨** | Wildcard Cookie + HttpOnly/Secure/SameSite |
| 跨域 / 第三方小程序 | **Token 注入轨** | 鸿蒙 Header 注入 / SSO code 换取 |
| Cookie 不可用 | **自动降级到 Token** | **降级不崩溃**（原则 #4） |

**为什么必须双轨**：微信小程序 SSO 用 `accountId` + 临时 code（OpenID/UnionID），**不是直接共享 Cookie**。

### 三平台事实前提（已核实）

| 平台 | Cookie 容器 | 关键 API | 关键坑 |
|------|------------|---------|--------|
| Android | `CookieManager` | `setCookie()` + `flush()` | **默认不自动同步**，OkHttp CookieJar 与 WebView 是两个世界 |
| iOS | `WKHTTPCookieStore` | `setCookie { completion }` | 异步须 await；**`WKProcessPool` 必须单例** |
| 鸿蒙 | `WebCookieManager` | `setCookie()` + `onInterceptRequest` | **推荐 Header 注入**（比 Cookie 安全） |

### 五条 RSC 铁律（CMP095-102）

| 铁律 | 内容 |
|------|------|
| **RSC-01** | **HttpOnly Cookie 永不透出**（原生层强制隔离，JS 只读 Token） |
| **RSC-02** | **登出清理全池**（L1+L2+L3 级联销毁，含跨页 Weak 引用） |
| **RSC-03** | **跨域同步须同源白名单**（默认拒绝，显式 opt-in） |
| **RSC-04** | **Token 须可刷新 + 可吊销**（refresh rotation，泄漏可即时失效） |
| **RSC-05** | **SSO code 一次性**（防重放） |

### 跨页所有权（★ 独有增量）

**把 G-43 的所有权模型应用到登录态**——这是别的混合 App 方案没做的：

```
登录态归宿主所有，页面借用，销毁时归还
        ↓
Rc 强引用（宿主持有）+ Weak 跨页观察
        ↓
页面销毁 → 五原子 Drop → 归还借用
        ↓
循环泄漏检测 → 报出"谁持有、凭什么持有、在哪行创建"
```

## 5.4 组合：G-47 接缝一致性

**核心命题**：G-27（渲染）× G-46（资源池）组合后，"**切后端时数据链不断**"。

### 六条不变量

| 编号 | 含义 |
|------|------|
| **INV-01** | 切后端登录态不丢 |
| **INV-02** | 切后端缓存不丢 |
| **INV-03** | 登出 × 切换**交换律**（顺序无关） |
| **INV-04** | 并发不崩溃 |
| **INV-05** | 同 IR 同资源视图 |
| **INV-06** | 降级不崩溃 |

### G-47 抓到的真实问题

**双轨优先级的数据陷阱**：`getAuth(domain, origin)` 的 "sid_+domain" 匹配让 Token 轨**在同域永远走不到**。

> 这是 G-46 设计的正确反映，不是 bug——
> **但只有跨层测试能暴露使用误区。**

**验证器验证不到被验证物**：参考实现的 `ok()` 只在失败时打印名称，PASS 名称从不输出 → verify 的 grep 永远匹配不到。

> **这类"验证器验证不到被验证物"的元问题，正是 G-44 要治的。**

## 5.5 方案价值

| 维度 | 传统方案 | Proteus |
|------|---------|---------|
| 渲染一致性 | 编译期选定（nvue 后缀） | **运行时按页选择** |
| 数据一致性 | 业务手写同步 | **宿主级统一资源池** |
| 组合正确性 | 从未测试 | **六条不变量机器验证** |
| 登录态共享 | 各端各自实现 | **双轨自动降级** |
| 登出清理 | 容易漏（Token 池） | **级联销毁 + conformance 断言** |

**一句话**：

> 混合 App 在架构层面被完整覆盖——
> **外（渲染可换）、内（数据共享）、接缝（切换不断）三者缺一不可，而我们是唯一三者齐备的。**
