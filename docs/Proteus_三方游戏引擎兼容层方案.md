# Proteus 三方游戏引擎兼容层方案

> 目标：不自建游戏能力，做**三方游戏引擎的兼容层接口**
> 让开发者在 Proteus 中直接使用 Three.js / Unity / Unreal 等能力
> 状态：v1 · 待评审
> 关联：原生能力接入方案、Host ABI 设计方案、游戏能力扩展评估与落地方案、Morpheus 方案

## 1. ★ 核心洞察：它是「不自绘」原则在游戏领域的同构应用

### 1.1 与既有架构完全同构

| 原则 | 渲染领域 | 游戏领域 |
|---|---|---|
| 不自绘 | 重活交给**系统渲染管线** | 重活交给**专业游戏引擎** |
| 自己只做 | 指令生成与调度 | **协作层与生命周期** |
| 换来什么 | 原生生态可融合 | **游戏引擎生态可融合** |

**这是同一招，只是换了个对手。**

### 1.2 它是「原生组件」，不是新架构

Unity / Unreal 的 view 本质是一个**特殊的高性能原生组件**——
与 map / video / webview / 广告 SDK **完全同类**。

**因此可直接复用已有的原生组件融合能力（Host ABI §2.7、CSS Profile L3、兼容方案 B 档），无需新建架构。**

### 1.3 ★ 一个你独有的优势：没有「两层合成」问题

Flutter 自绘 → PlatformView 必须由系统 Window Manager 合成
"native 层 + Flutter 层"，**计算更贵**，且 Impeller 时代新增性能回归。

**Proteus 不自绘 → 渲染层与引擎 surface 都由系统合成器处理，这个坑天然不存在。**

> 这是选原生渲染管线换来的结构性优势，应在对外材料中明确记录。

## 2. 引擎分级（有硬事实约束，不能并列）

### 2.1 分端支持矩阵（v3：完整版）

| 引擎 | Web | 小程序 / 小游戏 | **鸿蒙** | **Android** | **iOS** | 判定 |
|---|---|---|---|---|---|---|
| **团结引擎**（Unity 中国） | ✅ WebGL | ✅ 微信/抖音/快手/Tap/小米/233 | ✅ 原生一键 HAP | ✅ | ✅ | 🏆 **端覆盖最全** |
| **Three.js** | ✅ 天然 | ✅ 原生支持 WebGL | 🟡 需 GL surface | 🟡 需 GL surface | 🟡 需 GL surface | 🏆 **轻量主线** |
| **Cocos Creator** | ✅ | ✅ 覆盖平台最多 | ✅ 全球首个支持 | ✅ | ✅ | 🏆 **轻量候选** |
| Unity 国际版 | 🟡 4MB 首包极残酷 | 🟡 同上 | ❌ **不支持** | ✅ | ✅ | ⚠️ 鸿蒙不可达 + 已退出中国 |
| **Unreal** | ❌ **无 WebGL 导出** | ❌ 不可能 | 🟡 工程极重 | 🟡 | 🟡 | 🔴 **暂缓** |

> 🆕 **v3 再次修正**：上一版把团结引擎定位为"鸿蒙唯一解"——**仍然是低估**。
> 官方 FAQ 明确其支持 **Android / iOS 全平台**，实为
> **"Unity 国际版全部平台 + 小游戏 + 开源鸿蒙 + 车机"**。

> 🔴 **重大修正（v2）**：原方案假设"Unity 支持鸿蒙"——**这是错的**。
> 华为官方 FAQ 明确："截止 2025 年 9 月 4 日，Unity 尚未支持 OpenHarmony 平台。
> 且由于 Unity 在中国下架，后续若需要 Unity 新特性，也只能使用团结引擎开发。"
> **准确表述：团结引擎（Unity 中国）支持鸿蒙，Unity 国际版不支持。**

### 2.2 🔴 Unity 的三条官方硬限制

来源：Unity 官方文档《在其他应用程序中将 Unity 用作库》

1. 🔴 **Android / iOS 仅支持全屏渲染**——不支持局部嵌入
2. 🔴 **无法加载或集成多个 Unity 运行时实例**
3. 🔴 卸载后仍保留 **80–180MB** 内存（取决于图形分辨率）；
   **iOS 上调用 `Application.Quit` 后，无法在同一应用会话中再次加载**

**第 1 条直接决定产品形态**：
> Unity 只能**整屏切换**，做不了"列表里嵌一个 3D 卡片"。

**第 3 条意味着生命周期必须框架托管**：
> Unity 实例**不能反复销毁重建**（IL2CPP 运行时重建代价极高，会掉帧甚至崩溃）。

### 2.3 🔴 Unreal 为什么暂缓

| 事实 | 来源 |
|---|---|
| **无 WebGL 导出**，不能跑在浏览器 | 引擎横评（2026） |
| 空项目占数 GB，构建与存储成本成倍增长 | 同上 |
| 移动默认 Metal(iOS)/Vulkan(Android)，OpenGL ES 已弃用 | Unreal 移动指南 |
| 面向高保真 3D，2D 属过度设计 | 同上 |

**结论：Unreal 在 Web 与小程序端根本不可达，与"跨端"定位冲突。**

### 2.5 🆕 鸿蒙专项：团结引擎 vs Cocos

Cocos 是另一个必须认真评估的选项：

| | 事实 | 权威性 |
|---|---|---|
| **2021 年 3.2 成为全球首个支持 HarmonyOS 的游戏引擎** | ✅ | 极高（Cocos 官网） |
| 2.4.15+ / 3.8.7+ 支持 HarmonyOS 5.0+ | ✅ | 极高（华为官网） |
| **双核架构**：C++ core（原生）+ TS core（Web / 小游戏） | ✅ | 极高（Cocos 文档） |

**★ Cocos 的双核架构特别值得注意**：
> TS core 跑 Web 和小游戏，C++ core 跑原生——
> **这与"一份源码、编译器化作千端形态"是同一个思路**，和我们架构同构。

| 对比 | 团结引擎 | Cocos Creator |
|---|---|---|
| 鸿蒙成熟度 | ✅ 2000+ 应用 | ✅ 首个支持，但生态规模待核实 |
| 小游戏 | ✅ 微信/抖音深度集成，1.3 万款 | ✅ 覆盖平台最多（微信/抖音/手Q/快手/淘宝/荣耀） |
| 3D 能力 | 🏆 更强（Unity 血统，URP/虚拟几何） | 🟡 中等，偏 2D/轻 3D |
| 包体 | 🔴 大 | ✅ 更小（2.x 系列尤其） |
| 授权 | 需确认 | 需确认 |

> **结论：重度 3D → 团结引擎；轻量 2D/小游戏 → Cocos。**
> 两者都值得接，**不必二选一**——兼容层本就是"按端选后端"。

### 2.6 🆕 鸿蒙适配已知坑（Cocos / 团结引擎都踩过）

这些坑我们做兼容层时**必然遇到**，提前知道能省大量时间：

| # | 坑 | 处理 |
|---|---|---|
| 1 | 🔴 **鸿蒙不支持 WebAssembly** | 需屏蔽相关代码路径，否则直接报错 |
| 2 | 🔴 模块必须显式声明依赖，**`moduleType` 必须设 `commonjs`** | 否则模块找不到 |
| 3 | 🔴 资源必须统一放 `assets/` 目录 | 需通过 bundle 方式加载 |
| 4 | **不支持 DevEco 模拟器**，只能真机调试 | 需准备鸿蒙真机 |
| 5 | 团结引擎要求 **OpenHarmony API ≥ 10** | 低版本打包直接报错 |
| 6 | 平台判断需新增 `OS_OPENHARMONY` 分支 | 否则功能静默缺失 |
| 7 | 图标需"按鸿蒙分辨率生成" | 否则真机显示模糊 |

> **第 1 条最致命**：如果引擎侧依赖 WASM，鸿蒙端直接不可达——
> 选引擎时**必须把"是否有 WASM 依赖"作为一票否决项**。

## 3. 分层设计

```
┌─────────────────────────────────────┐
│ ① 声明层   开发者写 Vue/声明式        │  <Engine3D src=... />
├─────────────────────────────────────┤
│ ② 适配层   编译器按端选择后端         │  Web→Three / 小程序→Three+adapter
│                                      │  App→Unity(整屏) / GL surface
├─────────────────────────────────────┤
│ ③ 桥接层   生命周期 + 通信 + 事件路由  │  各端原生实现（platform/）
├─────────────────────────────────────┤
│ ④ 引擎层   Three.js / Unity / Unreal │  第三方，我们不实现
└─────────────────────────────────────┘
```

**我们只实现 ①②③，④ 是别人的。**

### 3.1 命名建议

| 候选 | 含义 | 风险 |
|---|---|---|
| **Chimera**（主推） | 嵌合体——正是"把不同引擎组合进一个框架" | 有同名项目（分子可视化 / Linux 发行版），**需商标与包名检索** |
| **Talos**（备选） | 青铜自动机，代指被驱动的巨物 | 占用较少 |

> 命名仅为建议，落地前必做正式检索。

## 4. ★ 真正的价值在「协作层」，不在「嵌入」

嵌入本身不难（宿主加个 view 即可）。**难的是嵌入之后这五件事**：

| 协作项 | 说明 | 痛点 |
|---|---|---|
| **生命周期同步** | 宿主页面前后台 ↔ 引擎暂停/恢复 | Unity 卸载后内存不释放；iOS 退出不可重载 |
| **通信桥** | Vue 状态 ↔ 引擎 | Unity 的 `UnitySendMessage` 是**字符串序列化** |
| **UI 叠加** | Vue UI 覆盖在 3D 之上 | Unity 全屏限制下尤其麻烦 |
| **资源加载与分包** | 小程序端 **4MB 首包**是硬约束 | Three.js 完整包都未必放得下 |
| **事件路由** | 触摸事件给引擎还是给 Vue | 需明确优先级与手势竞争规则 |

**这五项正是别的项目要自己干的活，也正是兼容层该提供的东西。**

> 对外叙事落点：
> **"我们不做游戏引擎，我们做游戏引擎的协作层。"**

---

## 5. ★ 端覆盖不一致：既是最大风险，也是最大机会

### 5.1 风险

Three.js 覆盖 Web + 小程序但 App 端另说；
Unity 覆盖 App 但小程序需 WebGL 构建、**鸿蒙完全不可达**——
**同一个 3D 需求，各端要落不同后端。**

> 🆕 **v2 缓解**：团结引擎是唯一同时覆盖小游戏 + 鸿蒙 + WebGL 的引擎，
> **它把鸿蒙这一端的缺口补上了**。剩余风险主要在 Three.js 的 App 端 GL surface。

### 5.2 但这恰好是主场

> **"一份声明 → 各端落到不同引擎"**
> 与「一份 Vue 源码 → 编译器化作千端形态」是**同一个模式**。

别人要手写三套适配；**你可以把它编译掉。**

### 5.3 降级策略必须显式

| 场景 | 策略 |
|---|---|
| 目标端无可用引擎 | **编译期报错**，不得静默空白 |
| 目标端需降级（如 Unity 全屏限制） | 编译期标记为 **degraded**，参照埋点清单三类分级 |
| 小程序端超 4MB | 强制分包 + 编译期体积检查 |

> 🔴 **禁止静默失败。** 这是"零静默失败"原则的又一次应用。

## 6. 三个必须提前设计的点

### 6.1 🔴 单例生命周期必须由框架托管

Unity 不能多实例、iOS 退出后不可重载——
**这些约束必须封装在框架内，不得暴露给开发者。**

设计要点：
- 引擎实例为**进程级单例**
- 页面切换是 **pause/resume**，不是 destroy/create
- 开发者 API 只暴露 `mount/unmount`，内部映射到暂停/恢复

### 6.2 🔴 通信桥必须声明式，禁止开放任意消息

`UnitySendMessage("GameObject", "Method", "string")` 是字符串序列化。
**开放任意字符串 = 又一个逃生口**，会毁掉：
- conformance 机器判定
- AI 可校验
- 跨端一致性

**正确做法**：消息 schema 声明化 → 编译期校验 → codegen 出静态绑定
（与《原生能力接入方案》"codegen 取代运行时反射"完全同理）。

### 6.3 4MB 首包要提前算

小程序端硬约束。Three.js 完整包都未必放得下——
**需裁剪 + 分包，且编译期就要做体积检查**，不要等到提审才发现。

## 7. 与收敛模型的关系（护栏）

### 7.1 强制约束

🔴 **游戏引擎相关原语不得进入 187 原语体系。**

理由（与《游戏能力扩展评估与落地方案》§0-bis 一致）：
核心卖点是"编译期封闭"，**原语集被游戏需求撑大，这个卖点就开始稀释**。

### 7.2 独立命名空间

建议：`@proteus-vue/engine3d`，作为**可选扩展包**。

### 7.3 但表现层仍归 Morpheus

3D 场景之外的 UI 动画、HUD、转场、列表让位——
**照旧由 Morpheus 承担**。是分层，不是排斥。

### 8.1 🆕 GE11：后端选型决策（最高优先级的结构性决策）

v3 发现团结引擎实为**全平台引擎**后，出现两条互斥路线：

| | 方案 A：团结引擎统一全端 | 方案 B：Three.js + 团结混合 |
|---|---|---|
| 端覆盖 | ✅ **完全一致** | 🟡 两套后端，降级规则变复杂 |
| 包体 | 🔴 **大**（WebGL/小游戏端尤其） | ✅ 轻量场景用 Three.js 省包体 |
| 授权成本 | 🔴 商业项目付费 | 🟡 仅重度场景付费 |
| 维护 | ✅ 一套桥接 | 🟡 两套桥接 |
| 3D 能力上限 | 🏆 高（虚拟几何体/URP） | 🟡 Three.js 够用但上限低 |

**这个决策会决定兼容层的整体形状，必须在 GE0 之后立刻做**，
不要等各端都做完再回头改——那时改动成本会高一个量级。

**建议倾向**：以 **方案 B 起步**（Three.js 覆盖轻量、团结覆盖重度），
保留切换到方案 A 的能力——这同时也是对 §2.8.2 所有权风险的架构对冲。

## 9. 执行指令（给 LLM）

1. 🔴 **不实现游戏引擎，只做兼容层**——引擎是第三方的
2. 🔴 **游戏引擎原语不进 187 原语体系**，独立可选包
3. 🔴 **通信桥禁止开放任意字符串消息**，必须 schema 声明 + codegen
4. 🔴 **引擎实例必须框架托管为单例**，pause/resume 而非 destroy/create
5. 🔴 **禁止静默失败**：目标端无可用引擎必须编译期报错
6. **优先做 Three.js**——Web + 小程序最顺的引擎
7. **引擎按"整屏场景"设计**，不要试图做局部嵌入（官方限制）
8. **Unreal 暂缓**——无 WebGL 导出，与跨端定位冲突
9. **小程序端 4MB 预算提前算**，编译期就要体积检查
10. **UI 叠加与事件路由规则必须在 GE1 定死**，不能留到后面
11. 表现层（HUD/转场/列表）复用 Morpheus，不另起一套
12. 命名（Chimera / Talos）落地前必做商标与包名检索
13. 🆕 🔴 **鸿蒙端必须走团结引擎或 Cocos**，Unity 国际版不支持 OpenHarmony
14. 🆕 🔴 **选引擎时把"是否有 WASM 依赖"作为一票否决项**（鸿蒙不支持 WASM）
15. 🆕 团结引擎要求 **OpenHarmony API ≥ 10**，环境搭建时就要确认
16. 🆕 **鸿蒙端只能真机调试**，需提前准备设备（不支持模拟器）
17. 🆕 GE8 排在**鸿蒙宿主主线 HM0–HM2 之后**，不要并行
18. 🆕 重度 3D 用团结引擎、轻量 2D/小游戏用 Cocos，**不必二选一**
19. 🔴 **GE11 后端选型决策必须在 GE0 后立刻做**，它决定兼容层整体形状
20. 🔴 **授权成本必须进决策依据**——团结引擎商业项目 ¥18,888+/年，激活费按营收流水 2.5% 抽成
21. 🔴 **不要把团结引擎设为唯一硬依赖**（所有权变更风险，§2.8.2），保持按端可切换
22. 团结引擎基于 **Unity 2022 LTS**，可能不兼容 2023 LTS 及后续——资产迁移要评估
23. 移动端图形 API 门槛：**Metal 需 1.6.0+、Vulkan 需 1.8.0+**
