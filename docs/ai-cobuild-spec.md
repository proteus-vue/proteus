# AI 共建规范（Proteus × 外部实战项目）

> **这份规范解决什么问题**：AI 参与的跨项目协作，最大的风险不是「写得不好」，而是
> **报了的没修、修了的没验、验了的没发、发了的没人知道**——四类断点全靠人记，一断就静默。
> 本规范把这条链路的每个断点变成**机器判据**，并在仓库里跑起来（`pnpm check:cobuild`）。
>
> **战场**：本仓（框架方）↔ 外部实战项目（使用方，当前为 OPERATOR/web 创作台前端）。
> **状态**：v1（2026-09-20 建立；六轮实战报告 + 26 条台账条目沉淀）。

---

## 0. 一句话

**三方产物，机器对齐，闭环判定。**

```
        ┌──────────────────────────┐
        │ ① 外部实战报告（问题）    │  使用方写：见到了什么、怎么复现、影响面
        │   实战报告_xxx.md        │  ★必须带：版本 + 最小复现 + 证据
        └───────────┬──────────────┘
                    │  报告 → 立项（机器强制，防「报了没立项」）
        ┌───────────▼──────────────┐
        │ ② 台账（对账单一事实源）  │  维护方写：每条一个 id，字段化（状态/修复版本/验证结论）
        │   外部报告台账.json      │  ★判据：resolved = fixed + published + verification=passed
        └───────────┬──────────────┘
                    │  修完 → 回执（机器强制，防「修完没回音」）
        ┌───────────▼──────────────┐
        │ ③ 处理回执（回应+证据）   │  维护方写：逐条「改了什么、怎么验的、什么时候发的」
        │   报告里的「处理回执」节  │  ★必须带：修复版本 + 验证方式（不是「已修复」三个字）
        └──────────────────────────┘
                    │
        ┌───────────▼──────────────┐
        │ 门禁：cobuild-check      │  三方交叉一致（5 条规则）+ ledger-check（台账自身自洽）
        └──────────────────────────┘
```

## 1. 四条铁律

| # | 铁律 | 判据（机器可查） | 违反后果 |
|---|---|---|---|
| **1** | **报了必须立项** | 报告每个「第 N 轮复测」小节 → 台账该轮 ≥1 条 | 问题停在散文里，下一轮才被外部复测撞出来（F-26 实例） |
| **2** | **修了必须发布才算数** | `fix_state=published` 且 `fixed_in` 有值 | 只有工作树 → **npm 用户拿不到**，等于没修 |
| **3** | **发了必须被独立验证** | `verification=passed` | 自己说「修好了」不算——原样复现报告的最小复现才算 |
| **4** | **闭环必须留回执** | 某轮条目全部收口 → 报告须有「处理回执（第 N 轮）」 | 使用方不知道能不能升级，形成「等版本」黑洞 |

> **收口（resolved）的唯一判据**：`status=fixed` **且** `fix_state=published` **且** `verification=passed`。
> 三者缺一，不计入收口率。**「真实收口率」的分母含未发布与部分修复**——只算用户拿得到且被独立验证过的。

## 2. 三个工件的写作规范

### ① 外部实战报告（使用方写，本仓镜像一份）

**每轮一节，标题格式固定**（机器靠它对齐）：

```markdown
## 十四、★ 第六轮复测：`0.3.0-beta.9`（2026-09-20）—— 一句话结论
```

- **必须有**：轮次（第 N 轮）、**被复测的版本号**、日期、一句话结论；
- **每个问题必须有**：现象 / **最小复现** / 影响面（本工程几个文件命中）/ 根因（能定位到就写）；
- **必须区分**「框架缺陷」与「我方适配」——不要把使用方的平台适配算成框架问题（反之亦然）；
- **诚实标注**：自己测试脚本的误报、可疑但未证实的猜测，单列一节说明（第六轮的两处审计误报就是好例子）。

### ② 台账（维护方写，**对账的单一事实源**）

`docs/外部报告台账.json`——字段见其自描述 `schema`。要点：

- **id 一旦分配不得更改**（它是跨工件的锚点）；
- **blocker 必须带 `repro`**（没有最小复现的阻断项无法复核——门禁强制）；
- **`status=partial` 必须带 `related`** 指向跟踪条目（防「修一半当修完」——Bug B 的教训）；
- **`fix_state` 只是二选一**：`published`（已上 npm）或 `worktree`（仅工作树）。**没有第三种**——
  「我记得发了」不算，`fixed_in` 要能被 `npm view` 验证；
- **版本口径**：第 4 轮起本仓用 changesets `fixed` 分组（41 包统一版本），此前的「多版本时代」
  由 `version_scheme_note` 说明。**跨工件对齐的锚点是 `round`，不是版本号。**

### ③ 处理回执（维护方写，追加在报告末尾）

**每条必须给三样**：改了什么（文件/机制）+ 怎么验的（**可执行的验证方式**）+ 哪个版本发的。

- ❌「已修复」——没有信息量；
- ✅「改为 `mapCodeOutsideLiterals` 统一原语；**破坏性验证**：撤掉包装 → 守卫测试当场红；随 `0.3.0-beta.10` 发布」；
- **必须包含自我批评**：如果上一轮修得不完整（如 Bug B 只修 1/3），回执要**明确承认并说清为什么没发现**；
- **修复过程中自己踩的坑也要写**（如声明位保护的死代码被门禁抓住）——这是最有价值的部分。

## 3. 机器门禁（规范能被强制执行的部分）

```bash
pnpm check:ledger     # ① 台账自身：schema / 枚举 / blocker 必带 repro / partial 必带 related / fixed_in 不自相矛盾
pnpm check:cobuild    # ② 三方交叉：报告 ↔ 台账 ↔ 回执 五条规则（报了没立项 / 立项没出处 / 版本漂移 / 修完没回执 / 回执无轮次）
pnpm ledger:check     # ③ 收口率报告：有未收口项 → exit 1（**发布前**用，不进 CI）
```

| 命令 | 何时跑 | 判据 |
|---|---|---|
| `check:ledger` | CI + `pnpm verify` | 台账不合格 → **exit 2** |
| `check:cobuild` | CI + `pnpm verify` | 三方有缺口 → **exit 1** |
| `ledger:check` | **发布前手动** | 未发布/未充分验证/部分修复 → exit 1（提示还差什么） |

> **为什么 `ledger:check` 不进 CI**：它会把「已修未发布」也算未收口 → 常驻红。
> **未发布是正常中间态，不是 CI 该拦的；但它是发布前必须被看见的状态。**

**破坏性验证**（门禁自己也要被验证——本项目铁律）：

- `check:ledger`：植入 3 处腐化（blocker 缺 repro / partial 缺 related / `fixed_in` 超前）→ 全部抓出、exit 2；
- `check:cobuild`：删第 6 轮台账条目 → 报「报了没立项」；改台账版本 → 报「版本口径漂移」；
  删回执小节 → 报「修完没回执」（均已实测）。

## 4. 一次完整的共建循环（照着做）

```
使用方                            维护方（框架）
  │                                  │
  │ ① 在真实项目里用框架              │
  │ ② 撞到问题 → 写报告一节            │
  │    （版本 + 最小复现 + 影响面）    │
  │ ────────── 报告 ────────────────► │
  │                                  │ ③ 用最小复现**当场复现**（不轻信、不猜测）
  │                                  │ ④ 台账立项（分配 id + severity + repro）
  │                                  │ ⑤ 修（先数清同类实现有几处——「修一份等于没修」）
  │                                  │ ⑥ 加回归锁 + **破坏性验证**（回退修法必须红）
  │                                  │ ⑦ 真机/真实工程端到端验证（不只单测）
  │                                  │ ⑧ 发布（换版本号；npm 不可变）
  │                                  │ ⑨ 写回执（三样：改了什么/怎么验/哪个版本）
  │ ◄──────── 回执 + 新版 ─────────── │
  │ ⑩ 用最小复现复测 → 结果回写报告    │
  │ ────────── 下一轮 ─────────────► │ ⑪ 台账更新 verification=passed
  │                                  │ ⑫ `pnpm ledger:check` 看收口率
```

**关键约定**：

- **③ 必须自己复现**：维护方不得仅凭描述就改——用对方的最小复现跑一遍确认（本项目每轮都这么做，
  六轮里没有一次「描述属实但复现不出来」是靠猜过去的）；
- **⑤ 先数实现再动手**：`grep` 特征正则数清「同一类改写/同一类判断」在全仓有几处；
- **⑥ 回归锁必须能红**：不能红的测试不算测试（本项目每个修复都做破坏性验证）；
- **⑩ 复测是使用方的事**：维护方的自测**不算**独立验证（`verification=passed` 只能由使用方给出，
  或在台账里明确标注 `found_by=framework` 的自查项）。

## 5. 反模式（真实踩过的）

| 反模式 | 实例 | 教训 |
|---|---|---|
| **「修一半当修完」** | Bug B 有三处实现，只修一处就报「已修」 | 修「某类缺陷」先数实现处数，再改；加**结构性断言**防新增 |
| **「验证了但验的是别的」** | `--dry-run` 跳过提升分支，而缺陷恰在提升分支 | 演练覆盖度要对着**风险最高**的那段设计，不是最方便的那段 |
| **「报了的没立项」** | 报告第九节报的 fluid 缺件（阻断级）没进台账 | 三方一致性门禁（`check:cobuild` 规则 A） |
| **「已修 = 用户能用了」** | 只改工作树未发布，使用方拿到的还是旧包 | `fix_state=published` 强制区分 |
| **「自测通过 = 修好了」** | 框架自测在 workspace 软链上跑，源码树里文件齐全 → 漏掉「发布物缺件」 | 验证必须用**真实安装形态**（干净目录装 registry 包） |
| **「文档说了就是做了」** | 官网统计「40 个包」长期与实际 41 不符，且同页两个数字 | 数字要能**机器重算**（`check:stats`） |
| **「假阳性当缺陷报」** | 测试脚本改进程选择器，误报三处失败 | 报之前先确认**探针自己可靠**（报告第六轮的澄清是好示范） |

## 6. 平台适配 vs 框架缺陷：怎么分

这是共建里最容易吵的一类。**判据**：

| 情形 | 归属 | 处置 |
|---|---|---|
| 框架承诺 `aligned` 的能力没对齐（如 `onMounted` 支持异步，但 async 标记被丢） | **框架缺陷** | 框架修（有对照实验可证「本可做到」） |
| 平台本身不支持（WXML 不支持 `?.`、不支持函数调用） | **平台限制** | 使用方适配；框架侧**给明确报错**（不能静默） |
| 框架未注册某插件导致功能静默不生效（`p-fluid`） | **框架缺陷** | 框架修（Web 分支默认注册） |
| 使用方自己的路由逻辑跳页（工作台未选作品跳首页） | **使用方行为** | 报告里澄清，不计为缺陷 |
| 框架产出**语法合法但语义错**的产物（`/\s/` → `/\this.s/`） | **框架缺陷（最危险）** | 框架修 + **产物侧门禁**（语法扫描抓不到这类，要加改写特征扫描） |

> **框架方的责任边界**：凡「静默失败」（不报错但行为错、或报错指向无关模块）一律归框架——
> 因为它让使用者无从排查。**报错指路**（告诉我该放哪、哪个版本不支持）是框架的义务。
