## 1. 痛点诊断

### 1.1 🔴 最硬的一条：静默失败（三类，全部不报错）

uni-app 实践中确认的三个坑（来源权威性：较低-中等，但技术链条完整，且与微信机制一致）：

| # | 现象 | 后果 |
|---|---|---|
| 1 | 事件名含非法字符（只允许字母、数字、下划线） | **微信侧直接静默丢弃** |
| 2 | 参数值越界：字符串 >256 字符、数字 >±9007199254740991、布尔写成字符串 `"true"` | **全部不报错但不上报** |
| 3 | 生命周期时机错位（`onLoad` 里调 `uni.report`，页面未 ready） | 事件丢失 |

**这三条的共同点是"不报错"。** 与我们反复批判的 `switchTab` 静默失败、`boundingClientRect` 返回 0、层级失效**完全同类**——都是"开发者以为生效了，实际没有"。

### 1.2 🔴 `#ifdef` 平台的静默失效（最典型的跨端病）

```
#ifdef MP-WEIXIN  引入 umtrack-wx
#ifdef H5         引入 umtrack-web
```

在微信小程序编译时 H5 块被**完全剔除**，反之亦然。结果是：**某些平台根本不执行这些条件块里的代码，也没报错，静默跳过初始化**。

> **H5 端一条数据都收不到，而没有任何人知道。**

这条与层级规范里"Skyline 的 `position:fixed` 静默失效"、Janus 里"缺属性只在日志打 `pip: context not ready`"是同一类病——**平台能力差异以"静默不生效"的形式暴露**。

### 1.3 自动埋点覆盖不全：tabBar 是黑洞

uni-app 自动埋点**默认只覆盖非 tabBar 页面**；tabBar 页面需手动调用 `trackPageStart` / `trackPageEnd`。

**这恰好印证《导航体系方案》的诊断**：小程序把 tabBar 做成"另一类页面"，与普通页面栈物理隔离。所以 tabBar 页面在**所有**自动化机制里都是黑洞——路由拦截漏它、页面栈 `getCurrentPages()` 漏它、自动埋点漏它。

一处架构缺陷，四处漏。

### 1.4 各端口径天然不同（不是 bug，是模型差异）

友盟实践总结（权威性中等）原话：

> "跨端埋点最难的从来不是怎么写，而是接受**同一套逻辑在不同端必然产出不同数据**"

具体差异：

| 端 | 页面生命周期基准 |
|---|---|
| App | Activity / ViewController 生命周期 |
| H5 | 路由变化（SPA 还要区分物理加载 vs 虚拟路由） |
| 小程序 | Page 实例 |

所以"页面曝光"在三端的**定义就不同**，对齐要靠"路由拦截 + 生命周期补全 + tabBar 特殊处理三层兜底"，**漏掉任意一层数据就断档**。

### 1.5 Flutter 侧：observer 机制本身有洞

| 问题 | 来源 |
|---|---|
| 嵌套 Navigator 的 push/pop，**app 级 observer 完全看不到** | 官方机制（权威性中等偏高） |
| go_router **ShellRoute 下 observer 停止触发**，是已知 open limitation | 官方 issue（权威性中等） |
| B 页面 pop 回 A，**收不到 A 的 push 事件** | 业界实践（权威性较低） |
| Dialog / BottomSheet 也走 push，会被误判为"页面离开" | 业界实践（权威性较低） |
| 无痕埋点靠 `visitChildElements` 遍历，**push 时遍历会报错**（页面正在渲染，element 正在生成） | 业界实践（权威性较低） |

**最后一条最关键**：Flutter 的无痕埋点必须等到渲染完成才能遍历树——**这是自绘 + 不可见树的直接代价**。

### 1.6 RN 侧：三个结构性挑战

RN 埋点实践总结（权威性中等）：

1. **跨语言通信开销**：每次埋点都要过 JS-Native 桥
2. **生命周期差异**：RN 组件挂载/卸载与 Native 视图**不同步** → 数据丢失
3. **上下文缺失**：Native 层难以获取 JS 组件树与状态

第 2 条尤其致命——**它意味着"页面关闭"与"上报时机"天生对不齐**。

### 1.7 数据丢失：有公开的量化数字

Simon Hearne 的 field 数据（权威性较高）：

| 上报时机 | 捕获率 |
|---|---|
| `unload` | **86.4%** |
| `pagehide` + `visibilitychange` | **92.8%** |

**即使用了正确的时机，仍有 7.2% 丢失。** 而且 `sendBeacon` 返回 `true` **只代表浏览器接受了排队，不代表送达**。

## 2. ★ 我们的结构性优势（三条，全部来自架构）

### 2.1 编译期可见完整节点树 → oid 可静态生成

**业界方案都在运行时找元素：**

| 方案 | 找元素的方式 | 缺陷 |
|---|---|---|
| 有赞无痕埋点 | 点击元素的 **xpath** | "按钮位置不固定、名称重复或**页面重构时，无法做到准确标识**" |
| 曙光埋点 | 自建对象树 + SPM/SCM | 解决了 xpath 问题，但要**运行时维护对象树** |
| Flutter | `visitChildElements` 遍历 | 渲染未完成时遍历报错 |
| RN | 高阶组件包装 + 编译期注入 | 需要替换业务组件（去哪儿方案） |

**曙光埋点官方明确说了它解决的是什么**（权威性较高）：

> "解决了业界基于 **x-path 和 Accessibility** 的各种 UI 自动化方案未曾根本解决的**对象准确快速查找**和**用例稳定性差及运行效率低**问题"

**而我们不需要运行时查找**——编译器在编译期就看到完整的模板结构与语义原语，**oid 是编译产物，不是运行时查询结果**。

```
业界：运行时遍历树 → 找元素 → 生成标识（慢、不稳定、重构即失效）
Clio：编译期生成 oid → 运行时只查表（快、稳定、重构不失效）
```

### 2.2 内核事件入口 → 无痕埋点不需要 hook（★仅自绘端，见入库对账 ②）

因为绕开原生控件树，**自绘端（App/鸿蒙）所有触控事件都经过内核**（`hit.rs` 的冒泡链语义已有实现级证据）：

| 框架 | 无痕埋点要做什么 |
|---|---|
| 小程序 | hook 所有事件函数，且**组件事件不冒泡、catchtap 捕获不到** |
| RN | 用高阶组件替换 `Touchable*` |
| Flutter | 遍历 element 树（且时机受限） |
| **Proteus（自绘端）** | **内核已有事件入口，登记一个观察者即可** |

★**诚实边界（入库对账 ②）**：**Web 端事件是 DOM 事件、MP 端是微信事件系统——这两端不经过内核**。
它们的无痕埋点靠**编译期在产物里注入采集点**（oid 编译期生成的优势仍在，只是入口不是内核消息）。
**不得宣称"所有端事件都经过内核"。**

这是"绕开原生控件树"的**第五次兑现**（前四次：鸿蒙 C-API、全局挂载点、可停靠滚动容器、内存单一所有权账本）——★**兑现范围限自绘端**（Web/MP 的事件入口不归我们，见上）。

### 2.3 同一份声明五端落地 → 口径不需要"对齐"

别人的多端一致性是**四套 SDK 对齐到一套规范**：
- 曙光：Android / iOS / Web / RN **四端各自实现**
- 友盟："各端只处理采集差异，业务事件结构保持一致"

**我们是编译器生成，只有一个真相源。**

> 不是"五端对齐了"，是**根本不存在五份实现可对齐**。

这与一致性方案里"数值比对取代像素比对"、Janus 里"契约驱动"是同一种降维。

## 3. 分层设计

```
┌─ L0 声明层   业务方写 <track> / track() 声明，带 schema
├─ L1 编译层   生成 oid、校验事件名与参数边界、注入采集代码   ← 关键增值
├─ L2 采集层   内核事件入口 → 采集 PV / 曝光 / 点击
├─ L3 上报层   队列 + 落盘 + 批量上报 + 各端传输适配
└─ L4 对接层   输出标准化事件流，可接业务方数仓或第三方 SDK
```

**L1 是全部差异所在。** L2–L4 是各框架都有的东西，我们的护城河在 L1。

## 4. L1 编译层：把静默失败变成编译错误

### 4.1 事件名与参数边界：编译期强制

对照 §1.1 那三个静默坑，逐条封死：

| 检查项 | 规则 | 违反时 |
|---|---|---|
| 事件名字符集 | `^[a-z][a-z0-9_]{0,63}$` | **编译期报错** |
| 字符串参数长度 | ≤ 256 | **编译期报错**（字面量）/ 运行期截断+计数（动态值） |
| 数值范围 | \|n\| ≤ 2^53-1 | 编译期报错 |
| 布尔类型 | 禁止字符串 `"true"`/`"false"` | 编译期报错 |
| 嵌套对象 | 禁止（各平台序列化不一致，iOS 可能丢深层字段） | **编译期报错** |
| 参数个数 | ≤ 20 | 编译期报错 |

> **硬约束：以上全部是错误不是警告。** 警告会被忽略，最后变成静默失败——这正是我们要消灭的东西。

### 4.2 ★ oid 编译期生成：基于语义而非位置

**为什么不能基于位置**：xpath 的痛点就是"页面重构即失效"。

**生成规则（建议）**：

```
oid = hash( 文件路径 + 组件名 + 声明的语义 id )
```

其中**语义 id 是开发者声明的**，不是推导的：

```vue
<button track:id="submit_order" @click="onSubmit">提交订单</button>
```

- 声明了 `track:id` → oid 稳定，**重构布局不影响**
- 未声明 → 编译器**自动生成并回写**（保证不重不漏），但标记为"自动 oid"，重构时可能变
- **禁止编译器基于 DOM 位置推导 oid**——那就是 xpath 换了件衣服

### 4.3 SPM 位置标识：编译期静态拼接

去哪儿方案（权威性中等）的做法是：编译期注入 `AQMProps`，运行时通过 `autoPath` 函数**逐层透传拼接**层级信息。

**我们不需要运行时透传**——编译器在编译期就看到了完整层级树，直接**静态算出 SPM 并内联为常量**。

```
去哪儿：编译注入 + 运行时 autoPath 拼接（每层组件都要传参）
Clio  ：编译期算出，运行时零成本
```

这消除了运行时开销，也消除了"透传链断裂导致 SPM 不完整"的可能。

### 4.4 曝光检测：与滚动容器方案的交集

曝光需要知道元素在视口内的可见比例。我们已有：

- 《可停靠滚动容器方案》提供滚动位置与视口信息
- 指令流带物理像素整数坐标（《单位系统与舍入规范》）

所以曝光检测**可以复用滚动容器的视口状态**，不用另建一套 IntersectionObserver 适配（各端行为不一致）。

**硬约束**：曝光检测必须走内核统一实现，**不得各端用原生 API**（Web 的 IntersectionObserver / 小程序 `createIntersectionObserver` / 各端实现语义不同，会产生口径差异）。

## 5. L3 上报层：与内存方案复用落盘机制

### 5.1 复用 last-will 的持久化设施

《全链路内存安全方案》已设计"terminal 档同步写归因快照到本地，下次启动读快照上报"。

**埋点队列应复用同一套落盘通道**：

| | 内存方案 | Clio |
|---|---|---|
| 落盘时机 | terminal 水位 / 进程将死 | 页面隐藏 / 应用进后台 / 队列达阈值 |
| 读回时机 | 下次启动 | 下次启动 |
| 通道 | **同一套本地持久化** | |

**硬约束：不得各写一套本地存储。** 两套存储会导致：配额冲突、写放大、以及最麻烦的**落盘时机互相抢占**（进程将死时两者同时写）。

### 5.2 各端传输适配（必须用对的机制）

| 端 | 机制 | 禁忌 |
|---|---|---|
| **Web** | `sendBeacon`（优先）+ `fetch({keepalive:true})` 兜底 | 🔴 **绝不用 `unload`/`beforeunload`**（移动端不触发、破坏 bfcache） |
| Web 触发时机 | **`visibilitychange` → hidden** + `pagehide` | 不用 `beforeunload` |
| App | 队列落盘 + 后台批量上报 | 不在 `onPause` 阻塞主线程 |
| 小程序 | `wx.request` + 本地缓存补报 | — |
| 鸿蒙 | 同 App | — |

**两个必须知道的数字（权威性较高）**：

- `sendBeacon` 与 `keepalive` fetch **共享 64 KiB 累积配额**，超出返回 `false`
- `sendBeacon(url, jsonString)` 发 `text/plain`，**是 CORS simple request，无预检**；若传 `Blob({type:'application/json'})` 会**重新引入 OPTIONS 预检**，而 `pagehide` 时来不及完成

> 所以：**发字符串，不要发 JSON Blob。** 这个细节会直接决定退出时上报的成败。

### 5.3 🔴 必须诚实的地方：7.2% 丢失无法消灭

即使做到最好，`pagehide` + `visibilitychange` 也只有 **92.8%** 捕获率。

**所以 Clio 必须提供「上报成功率」这个可观测指标**，而不是声称"不丢数据"：

| 指标 | 定义 |
|---|---|
| **客户端排队成功率** | `sendBeacon` 返回 true / 总调用 |
| **服务端接收率** | 服务端收到 / 客户端声称发出 |
| **前后端对账偏差** | 两端同一事件计数差异 |

> **对外禁语："我们的埋点不丢数据。"**
> ✅ 正确表述："我们把丢失率变成可观测、可对账的，而不是任其静默。"

## 6. 三个必须处理的交叉

### 6.1 与全局挂载点的冲突（C3）

《全局挂载点方案》C3 规定：**全局层不得引用 `useRoute`**（防业务污染常驻层）。

但埋点恰恰需要"当前页面"上下文。

**解法**：页面上下文由**内核注入**，不是组件自己取。全局层的埋点组件通过内核提供的**只读当前页面标识**获取上下文，不通过 `useRoute`。

**硬约束**：埋点上下文是**单向只读**的，业务不得反向修改页面栈。

### 6.2 与导航方案的多栈模型

导航方案用"每分支独立栈"（Flutter `StatefulShellRoute` 语义）。所以**页面标识必须包含 branch**：

```
pageId = branchId + routePath + 实例序号
```

否则多栈下两个 tab 的同名路由会**互相覆盖 PV**。这与 Flutter 嵌套 Navigator observer 看不到事件是同一个坑，只是我们从模型层就避免了。

### 6.3 与一致性校验的对接

埋点 schema 应进 **L1 编译期静态校验**（已有 VC 系列）：

| 新增卡 | 内容 |
|---|---|
| **VC1-e** | 埋点事件 schema 校验（事件名、参数边界、嵌套禁止） |
| **VC2-f** | 跨端埋点口径校验（同一事件五端字段一致性） |

**与 VC1-d（原生能力支持度矩阵）同构**——都是"声明 → 各端支持度/合法性 → 编译期判定"。

### 6.4 可视化埋点：明确不做

| 理由 | 说明 |
|---|---|
| 依赖运行时遍历树 | 我们有编译期 oid，**不需要圈选** |
| 配置下发有空窗 | 可视化埋点 SDK 拉取配置需要时间，**这段时间的行为全丢** |
| 圈选后才有数据 | **历史数据无法回溯** |

**我们的替代方案更强**：因为 oid 编译期全量生成，**可以默认全量采集 + 后台按需定义事件**（即无埋点的回溯能力），且不依赖圈选。

> 但要警惕：全量采集的数据量与存储成本。建议**默认全量但可分级采样**，见 §9 决策点 3。

## 7. 与 Flutter / RN / uni-app 的诚实对照

| 维度 | Flutter | RN | uni-app | **Proteus** |
|---|---|---|---|---|
| 元素标识 | 运行时遍历 element 树 | 高阶组件包装 / 编译注入 | xpath 或手写 | 🏆 **编译期生成 oid** |

### 7.1 必须承认：这不是全新发明

| 已存在的 | 说明 |
|---|---|
| **编译期注入** | 去哪儿 RN 方案已做（但我们是编译期**算出**而非注入后运行时拼接） |

> ❌ "我们首创了多端埋点一致性"

## 9. 三个决策点

| # | 决策 | 建议 |
|---|---|---|
| 1 | **是否默认全量采集？** | 建议**分级采样**：全量 event 但可配置采样率，避免数据量失控 |
