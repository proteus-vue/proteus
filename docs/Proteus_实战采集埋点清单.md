# Proteus 实战采集埋点清单

> 定位：**在上百页面级真实应用接入之前，把采集埋进去**
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4 / 微信基础库 2.29.2+）
> 依赖：《Benchmark 案例规格》§8（测量口径）、《CSS Profile 规格》§7（lint 规则）
> 本文档中的三类采集，指标定义**一律复用 Benchmark 规格**，不另起口径

---

## 0. 为什么现在做

### 0.1 实战能覆盖广度，但覆盖不了系统性边界

| 类型 | 实战能发现吗 |
|---|---|
| 某个写法 187 原语表达不了 | ✅ 能，但**被动、随机、分散** |
| 长跑内存泄漏 | ✅ 用户会滑很久——**但不采集就等于没发生** |
| 极端参数（2 万元素同屏） | ❌ 实战不一定触发 |
| 端对齐偏差 | ⚠️ 能遇到，但**不量化就无法归因** |

**核心差别**：实战是"问题会发生"。但若不埋采集，它就只是"发生过"，而不是"被记录下来"。

用户遇到一次掉帧、一次白屏——**不打点，你永远不知道那是什么**。

### 0.2 应用上线后再加，成本差一个量级

- 埋点需要改编译流水线与运行时，上线后改动风险高
- **早期数据补不回来**——冷启动阶段的问题只出现在那个阶段

**结论：在接入超级应用之前做完，成本约几天。**

## 1. 三类采集总览

| 类别 | 采什么 | 时机 | 主要价值 |
|---|---|---|---|
| **A. 编译期漏点统计** | 无法用现有原语表达的写法 | 每次编译 | 主动拿到"187 原语漏点清单" |
| **B. 运行时性能打点** | 帧耗时、内存、GC、长跑衰减 | 运行全程 | 真实设备上的分布数据 |
| **C. 端对齐偏差采集** | Web 与 App 端的渲染差异 | 运行 + 构建 | 定位哪类属性容易崩 |

---

## 2. A · 编译期漏点统计

### 2.1 做法

在编译流水线中加**计数器**：遇到无法用现有原语表达的写法，**记录但不阻断**。

```
编译 → 命中"无法表达" → 记录（文件、行号、写法、归类）→ 继续编译
```

**关键设计：不阻断。**
目的是收集数据，不是拦截开发者。阻断会让编译流水线变成噪音源，最后被人关掉。

### 2.2 记录字段

```ts
interface PrimitiveGapRecord {
  file: string
  line: number
  construct: string        // 具体写法（脱敏后的代码片段）
  category: string         // 归类：CSS / 模板指令 / 生命周期 / API / 其他
  severity: 'fallback' | 'unsupported' | 'degraded'
  // fallback   = 已降级到通用路径，功能可用但性能受损
  // unsupported= 编译期报错
  // degraded   = 已降级且行为可能不一致
  suggestedPrimitive?: string  // 若可映射到近似原语
  timestamp: number
}
```

### 2.3 输出

```
【编译期漏点报告】
  总计 37 处
  ├─ fallback     22 处（功能可用，性能受损）
  ├─ degraded      9 处（行为可能不一致）
  └─ unsupported   6 处（已报错阻断）

  按类别：
    CSS 特性        18 处
    模板指令         9 处
    API             6 处
    生命周期         4 处

  Top 写法：
    backdrop-filter    7 处
    v-html             5 处
    ::v-deep           4 处
    ...
```

### 2.4 这份报告的直接用途

| 用途 | 说明 |
|---|---|
| **判断 187 原语是否完备** | 收敛模型的核心验证（架构收敛模型说明 §6.1） |
| **决定 Profile 是否该扩** | 高频漏点应纳入 Profile，而非让每个项目各自降级 |
| **量化"Capability Hook 体温计"** | 83 个 Hook 是否够用，用这份报告回答 |

**★ 这是本清单里价值最高的一项。** 它把"被动等反馈"变成"主动拿清单"。

### 2.5 一个重要约束

**`degraded` 类必须单独高亮。**

`fallback` 只是慢，`degraded` 是**行为可能不一致**——后者才是端对齐问题的来源，且不会报错，是最难查的一类。

## 3. B · 运行时性能打点

### 3.1 指标定义：一律复用 Benchmark 规格 §8

**不要另起口径。** 已在 Benchmark 规格中定义：

| 指标 | 说明 |
|---|---|
| **每帧 work time** | 主指标，不用 FPS（vsync 饱和问题见 Benchmark §0.2） |
| work time P50 / P95 / P99 | 分位数 |
| **掉帧率** | 错过 vsync 的帧占比 |
| **GC 暂停次数与时长** | 对 Flutter 对比的杀手锏 |
| **输入延迟** | 触摸时间戳 → 提交帧时间戳 |
| 内存峰值与增量 | 含长跑曲线 |

### 3.2 埋点位置

```
① 帧调度入口     → work time 起点（Host ABI §2.5 的 proteus_frame）
② 绘制指令提交   → work time 终点
③ 触摸事件到达   → 输入延迟起点（必须带系统时间戳，Host ABI §2.4）
④ 内存采样       → 固定间隔 + 关键节点（页面进出、列表滚动）
⑤ 长跑衰减       → 按会话时长分段统计
```

### 3.3 采样策略（重要）

真实应用不能全量采集——开销会污染数据本身。

| 策略 | 说明 |
|---|---|
| **分层采样** | 按设备档位分组，每组抽一定比例 |
| **关键路径全采** | 首屏、列表滚动、转场——这三个全采 |
| **低频路径采样** | 其余按 1% ~ 5% |
| **可远程调整** | 采样率与开关支持下发配置，出问题能立刻关 |

### 3.4 长跑衰减是重点

**这是两个月项目最典型的"延后爆发"点。**

按会话时长分段统计：

```
0–30s / 30s–2min / 2–5min / 5min+
各段：FPS、内存、work time P95
```

**看什么**：后半段是否显著劣于前半段。若是 → 内存泄漏或热节流。

麒麟 970 这类老 U **尤其容易热节流**——现有两组真机验收（Redmi M098FE **1231 帧** / 荣耀10 **603 帧**）都只有约 10 秒，长跑数据完全缺失。

### 3.5 上报与聚合

- 本地聚合后上报，不上报原始逐帧数据（流量与隐私）
- 按「设备档位 + 页面 + 场景」三维聚合
- **必须可一键关闭**（隐私合规）

## 4. C · 端对齐偏差采集

### 4.1 为什么单独做

一致性当前实测 **0.375 dp**（合格线 0.5），但这是**聚合值**。

聚合值达标不代表每类属性都达标——**可能某类属性已经超线，被其他类平均掉了**。

### 4.2 做法

**以浏览器为真值基准**（Benchmark §9.3、CSS Profile §8.1）：

```
Web 端：getComputedStyle / getBoundingClientRect  → 基准真值
App 端：实际布局结果
差异 → 按属性分类记录
```

### 4.3 记录字段

```ts
interface AlignmentDeviation {
  property: string          // width / height / margin / borderRadius / ...
  platform: 'skyline' | 'android' | 'ios' | 'harmony'
  expected: number          // 浏览器基准
  actual: number
  deviation: number         // abs(expected - actual)
  nodeKind: string          // view / text / image / ...
  context?: string          // 是否处于 flex 容器、是否有嵌套等
}
```

### 4.4 输出

```
【端对齐偏差分布】
  总体 P95：0.375 dp  ✅

  按属性：
    borderRadius     P95 0.61 dp  ⚠️ 超线
    width            P95 0.28 dp
    margin           P95 0.19 dp
    ...

  按平台：
    skyline   P95 0.31 dp
    android   P95 0.38 dp
```

**这份分布表的价值**：把"一致性达标"变成一个**可持续监控的、可归因的**指标，而不是一个静态数字。

### 4.5 与舍入策略的关系

若发现某平台偏差系统性偏大，**先查舍入时机**——
内核产出指令时必须已舍入，平台层不得再舍入（架构收敛模型说明 §3.2）。

## 5. 接入时序

```
T0  编译期漏点统计          ← 最先做，无需运行时
T1  运行时打点（关键路径）   ← 首屏、列表、转场
T2  端对齐偏差采集          ← 构建期比对，可离线
T3  长跑衰减分段统计        ← 依赖 T1 稳定后
T4  全量开启 + 接入超级应用
```

**建议顺序理由**：T0 零运行时风险，最先做；T1 有性能开销风险，先只开关键路径；T2 可离线跑，不影响线上；T3 依赖 T1 稳定。

## 6. 验收标准

| 指标 | 合格线 |
|---|---|
| 编译期漏点统计 | 覆盖全部 fallback / degraded / unsupported 三类 |
| **degraded 类是否单独高亮** | **是**（不可与其他类混在一起） |
| 运行时打点开销 | 对 work time 影响 ≤ 可测量阈值（需实测） |
| 采样率可远程调整 | 是 |
| **一键关闭** | **是**（隐私合规硬要求） |
| 长跑分段统计 | 至少 4 段 |
| 端对齐偏差 | 可按属性、按平台下钻 |
| 与 Benchmark 口径一致性 | 复用，不得另起 |

## 7. 坑位清单

| # | 坑 | 应对 |
|---|---|---|
| 1 | **漏点统计阻断了编译** | 只记录不阻断，见 §2.1 |
| 2 | **degraded 类被淹没** | 单独高亮，见 §2.5 |
| 3 | **全量采集污染数据** | 分层采样 + 关键路径优先，见 §3.3 |
| 4 | **另起一套指标口径** | 复用 Benchmark §8 |
| 5 | **只看聚合一致性** | 必须按属性下钻，见 §4.4 |
| 6 | **忘记长跑** | 分段统计是重点，见 §3.4 |
| 7 | **无法一键关闭** | 隐私合规硬要求 |
| 8 | **上报逐帧原始数据** | 本地聚合后上报 |
| 9 | **上线后才想起埋点** | 本文档的存在意义，见 §0.2 |

## 8. 给实现 LLM 的执行指令

1. **编译期漏点统计只记录不阻断**，阻断会让流水线变噪音源并最终被关掉。
2. **`degraded` 类必须单独高亮**——它是行为可能不一致的一类，不报错，最难查。
3. **所有指标口径复用 Benchmark 规格 §8**，禁止另起定义。
4. **运行时采集必须分层采样 + 可远程调整 + 可一键关闭**，全量采集会污染数据本身。
5. **不得上报逐帧原始数据**，本地聚合后上报。
6. **长跑必须分段统计**（至少 4 段），它是两个月项目最典型的延后爆发点。
7. **端对齐偏差必须可按属性下钻**，只报聚合值等于没做。
8. **T0（编译期）最先做**，它零运行时风险且价值最高。
9. 采集设施**必须在接入超级应用之前完成**，上线后补不回早期数据。

## 9. 现有可复用设施（★先接线，不重建）

落地前置核对：三类采集在本仓**都不是从零**——先把现有设施接上，再谈新增。

### 9.1 编译期漏点（A 类）

| 现有设施 | 位置 | 与本文档的关系 |
|---|---|---|
| `proteus explain` + 决策 trace | `packages/compiler/src/explain.ts` · `trace.ts` | 已有规则命中与决策记录 ⇒ `PrimitiveGapRecord` 在此聚合输出即可 |
| 结构化诊断通道 | `packages/compiler/src/index.ts`（`VaporDiagnostic`） | 已有分级诊断类型 ⇒ fallback / degraded / unsupported 三档可复用 |
| 属性三级降级门禁 | `scripts/audit-degradation.mjs`（`pnpm check:degradation`） | 已有 supported / fallback / unsupported 判定 + 反黑盒校验 ⇒ **`degraded` 高亮沿用该口径** |
| 覆盖审计 | `proteus audit coverage`（`packages/cli/src/coverage-audit.ts`） | 已有官方 579 项（组件 84 · API 495）归类 ⇒ 漏点报告与之并列输出 |

⇒ **A 类的工作量主要在聚合与报表，不在新建判定逻辑。**

### 9.2 运行时打点（B 类）

`hosts/android/acceptance.sh` 已有：`dumpsys gfxinfo`（权威帧数据）· Perfetto（核判定；
honor10 因 SELinux 不可用）· 热控读数 · 进程隔离冷启动 · PSS 内存采集。

**B 类只需在其上补三项**：输入延迟（触摸 → 提交帧时间戳）· GC 暂停 · 长跑分段统计
（现有两组真机验收均只有约 10 秒，见 §3.4）。

⚠ 采样策略（§3.3）与聚合口径（§3.5）**不得脱离该脚本另建**——否则又出现"两套口径"。
