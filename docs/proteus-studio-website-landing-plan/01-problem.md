# G-60 问题定义

> 原则 #0「不绑定」系列，第 23 次泛化（官方链：…G-54=18、G-56=19、G-57=20、G-58=21、G-59=22，G-55 落地不占序；#397 修正，原稿误作 19）。
> 编号：G-60 · 依赖：G-56（自有宿主壳）、G-58（插件 API）、G-59（生态治理）
> 被依赖：G-61+

## 1. 问题：官网不是"做个网站"

这句话听起来像废话，但它决定了整份文档的走向。

**错误的问题定义**：做一个介绍 Proteus Studio 的网站。
→ 产出：漂亮的落地页 + 几篇文档 + 下载按钮。**三个月后文档与代码不一致，下载链接失效。**

**正确的问题定义**：

> 官网是**开发者与框架之间唯一的契约界面**——
> 它承载"能不能 10 分钟跑起来"和"我能不能相信这份文档"这两件事。

按 P1 的实证，**文档漂移是默认结局，不是意外**。所以官网的核心难题不是"写出来"，
而是**在框架持续演进的过程中，保证它不腐烂**。

## 2. 官网要承担的五件事

| # | 职责 | 失败后果 |
|---|------|---------|
| 1 | **让人 10 分钟跑起来** | 首屏流失 |
| 2 | **API 文档永远准确** | 开发者按错文档写代码 → 提 issue → 团队信任崩塌 |
| 3 | **多版本插件 API 可查** | 插件作者无法针对旧版本维护 |
| 4 | **下载与更新通道可信** | 私钥丢失 = 永久失去推送能力（P5） |
| 5 | **品牌一致性** | 与 3D 吉祥物、小程序头像割裂 |

**第 2 和第 3 件是技术难题，其余是工程与运营问题。**
本份的重点在前两件。

## 3. 核心矛盾：文档要"跟着版本走"，但内容要"不重复"

这两件事天然冲突：

- 插件 API 有 `since_v0_0_1` → `since_v0_8_0` 多版本并存（G-58），文档必须**分版本**
- 但"安装前置条件"、"术语表"、"架构概述"这类内容**版本无关**
- 若每个版本复制一份 → P2.2：**一处修正要手工应用 N 次，且必然漏掉至少一次**

**解法**：`/shared` 单一源 + transclusion 引入。
这与原则 #0 同源：**复制 N 份 = 绑定 N 次**。

## 4. 与既有体系的接缝

```
G-56  Studio 自有宿主壳      → 官网要分发它（下载页 / 更新通道）
G-58  插件 API（WIT 版本化）  → 官网要文档化它（★ 本份重点）
G-59  生态治理与性能契约      → 官网要公示它（插件市场 / 性能预算看板）
G-19  运行时面板              → 官网要指向它（可观测性文档）
G-37  未实测不宣称            → 官网是数字虚报的高发区（★ 重点防守）
```

**最后一条最危险**：官网是**对外宣称的出口**。
G-37 说"未实测不宣称"，而官网天然倾向于把数字写好看。
所以本份设 **G-60.7「数字不粉饰」** 为铁律，并给出可断言的防守机制。

## 5. 五条不变量

- **INV-W1** 插件 API 文档从 WIT 单一数据源生成，漂移即 CI 失败
- **INV-W2** 版本快照由 release tag 触发，**禁止人工决定时机**
- **INV-W3** 版本无关内容存 `/shared` 单一源，**禁止跨版本复制**
- **INV-W4** 每页显示版本上下文横幅（版本号 + 状态 + 最新版等价页深链）
- **INV-W5** 废弃状态由元数据驱动注入，**禁止手工编辑 markdown**

## 6. 诚实边界

- 本份**不含**官网视觉设计（配色、排版、插画）——那是设计任务，不属架构
- 本份**不含**插件市场后端（评审、计费、评分）——属运营系统，留给 G-61
- **未真实构建过站点**——选型基于文档与第三方记录，非实测
- 性能预算（首屏时间等）**是目标非实测**，按 G-60.7 不得对外宣称
