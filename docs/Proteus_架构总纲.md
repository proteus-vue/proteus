## 3. 关键路径（Critical Path）

**这是唯一不能延期的链条，任何一环阻塞都会推迟整体交付：**

```
M0（IR 扩展）
  → M0.5（排版核心语言决策：C++ / Rust）★ 决策点
  → M1（排版核心骨架 + LayoutEngine 抽象 + dirty 压力测试）
  → M2（三组件验证 + 4050 对打）★ 生死关
  → M3（绘制侧优化）
  → Vapor IR V1–V3（消除 Vue diff）
  → RT0（动画指令 spike）★ 决策点
  → BM0（测量设施）→ BM1（B1 主案例）
```

### 3.1 三个生死关

| 关卡 | 判据 | 不通过怎么办 |
|---|---|---|
| **M2** | 4050 场景渲染耗时 ≤ 原生 | 重估路线，不得带疑问进入 M3 |
| **V0**（Vapor 探针） | 加 `v-memo` / 拆组件后 70ms 显著下降 | 说明瓶颈不在 VNode 重建，**停止并重新归因** |
| **RT0**（动画 spike） | 指令路径 vs JS 路径有实测对比 | 未验证不得开始 RT1/RT2 |

### 3.2 三个决策点（逾期变更成本极高）

| 编号 | 决策 | 时点 | 影响 |
|---|---|---|---|
| **DCP-1** | 排版核心语言 C++ / Rust | **M0.5，M1 之前** | 换语言 = 重写核心 |
| **DCP-2** | Profile 是否开放 Grid | M0.5 | Yoga 无 Grid，与 DCP-1 耦合 |
| **DCP-3** | 动画走 IR 指令 / 第二 JS runtime | RT0 | 决定是否需要额外 runtime |

## 6. 实测基线（所有性能决策的锚点）

| 项 | 实测值 | 出处 |
|---|---|---|
| 宿主侧（Rust 排版核心 + JSI） | **1 ms** | 对话实测 |
| 4001 节点全量重排（vapor + 兄弟平移特调） | **0.08 ms**（提升四十余倍） | 对话实测 |
| 布局 / 绘制（4050 场景） | **0.063 / 0.667** | 验收结论 |
| 内存增量 vs 原生 | **0.328** | 验收结论 |
| 与浏览器一致性 | **0.375 dp**（合格线 0.5） | 验收结论 |
| 长列表滚动（4000 行 × 40 元素 × 10 层 = 2 万） | **124.5 FPS**，掉帧 0.16%，p50=p95=p99=8ms | 性能监测 |
| RenderNode 创建 / 复用 | **24 / 7941**，复用率 **0.997** | 性能监测 |
| 绘制耗时 p95 | 5 ms（120Hz 预算 8.33ms，占 60%） | 性能监测 |
| **★单节点更新 P95（Vapor 线）** | 类A **0.36ms**（基线 81ms，**285×**） | `docs/Proteus_VaporIR更新编译器设计方案.md` §9 V3 · 真机报告 `bench-filtered-V0.json` |
| **★结构变更跨边界字节** | 增 336KB→**56KB** · 删 280KB→**526B** · 头部插入 308KB→**28KB** | 同上（`--cases=S5`，真机 A/B） |
| **★文本变更跨边界字节** | 281KB→**15KB**（150ms→75ms） | 同上（`--cases=S4`） |
| **★整树重排 relayout** | **17.16ms→1.52ms**（持久 taffy 树；度量调用 6003→0） | 同上报（`--cases=V0`） |
| **★跨节点度量复用** | CoreText 调用**降 4×**（4000 行 8002→2001 次） | 同上（`--cases=S1`） |

### 6.1 三条从实测中提炼的结论

1. **布局侧已打穿，绘制侧是唯一瓶颈**
   — 4050 场景绘制占剩余耗时 91%；列表场景绘制占预算 60%。**两个不同负载指向同一处。**
   → 所有性能预算转向绘制侧。

2. **FPS 指标已饱和，必须换 work time**
   — p50=p95=p99=8ms 表明被 vsync（8.33ms）量化，测不出真实余量。
   → Benchmark 主指标改用每帧 work time + 掉帧率 + GC + 输入延迟。

3. **瓶颈会移动，必须持续重测**
   — 渲染侧打赢后，瓶颈已永久转移到 Vue 的 JS 侧（70ms）。
   → 每完成一个里程碑，重新 profile 再定下一步。

## 8. 对外叙事建议

### 8.1 主打什么

| 维度 | 是否主打 | 理由 |
|---|---|---|
| **内存 + GC** | ✅ **主打** | 结构性优势，Flutter 有引擎 + VM 固定税、Dart GC 长期未解 |
| **O(1) 更新**（单节点更新） | ✅ 主打 | 架构代差，所有 VDOM / widget 框架的共同软肋 |
| **原生性能 + 动态化兼得** | ✅ 主打 | UTS / Kuikly 做不到（编译到原生即失去动态化） |
| **FPS / 帧率** | ❌ 不主打 | 各框架都能跑满 120，且指标已饱和 |

### 8.2 两个必须避免的表述错误

| ❌ 错误说法 | ✅ 正确说法 |
|---|---|
| "超越 Skyline" | **App 端**超越；Skyline 端是能力对齐（④ §0.1） |
| "兼容 uni-app" | 给出**覆盖率数据**，不做模糊宣称（⑧ §7） |

### 8.3 最有杀伤力的三个数字

1. **2 万元素 → 24 个 RenderNode**（拍平 + 复用池的直接证据）
2. **全量重排 0.08ms**（O(n) 场景下的降维）
3. **内存增量 0.328**（vs Flutter 的 40–75MB 固定税）
