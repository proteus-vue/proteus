# G-56 附：生态兼容边界

> 本节回答一个反复被提出、必须一次说清的问题：
> **Tauri 自研的 Studio，能不能接 VSCode 插件生态？**

---

## 1. 结论先行

| 问题 | 答案 |
|------|------|
| 能装 `.vsix` 吗？ | ❌ **不能** |
| 能用官方 Marketplace 吗？ | ❌ **不能（许可禁止）** |
| 能获得语言智能吗？ | ✅ **能，走 LSP/DAP** |
| 损失什么？ | 闭源专有扩展（Pylance / C# Dev Kit 等） |

**并且：Studio 不应追求 VSCode 扩展兼容。** 理由见第 5 节。

---

## 2. 为什么装不了 .vsix（技术层面）

VSCode 扩展的本质是：**跑在 Node.js 运行时里、通过宿主注入的 `vscode` 模块调用 API 的一段 JavaScript**。

这个 API 有数千个方法，**全部由 VSCode 宿主进程实现**。

Studio（Tauri）三样都没有：

| 依赖 | Studio 现状 |
|------|------------|
| Node.js 运行时 | ❌ 无（Rust + WebView） |
| VSCode 宿主进程 | ❌ 无 |
| `vscode` 模块实现 | ❌ 无 |

> **扩展拿不到宿主，等于没有地基。**

这跟"兼容性做得多好"无关——**是插件模型的地基不同**。

---

## 3. 为什么不能用官方 Marketplace（许可层面）

Microsoft 官方 Marketplace **只授权给 Microsoft 官方发行版**（VSCode / VS Code for the Web）。

第三方发行版（VSCodium、code-server、Windsurf 等）只能用 **OpenVSX**（Eclipse 基金会运营的开源市场）。

**这是许可条款，不是技术问题。** 意味着：

> 任何自有产品都**无法合法使用**官方 Marketplace，无论技术实现多完美。

---

## 4. 三条间接路径及其真实代价

| 路径 | 能获得什么 | 代价 | 判定 |
|------|-----------|------|------|
| **嵌入 code-server / VSCodium** | 完整扩展生态（OpenVSX） | 等于套壳，回到 Electron 性能天花板 | ❌ **违背 G-56 初衷** |
| **实现 LSP/DAP 客户端** | 语言智能（补全/跳转/诊断/重构） | 需要自己写客户端 | ✅ **推荐** |
| Microsoft 开源 Extension Host | 托管真实 VSCode 扩展 | 需 WebView2 + .NET，Windows 优先 | ⚠️ **待核实** |

**注意区分两个概念**：

```
LSP/DAP 生态      ≠   VSCode 扩展生态
（开源语言服务器）      （含大量 UI/主题/工具类扩展）
```

LSP 服务器（rust-analyzer、gopls、ts-server）是**独立进程、开源、可合法分发**的。
Zed、Neovim、Lapce 走的都是这条路。

> ⚠️ **Extension Host 那条路径我掌握的细节不足以判断**，跨平台性存疑。若有人要推进，需先核实，**不得凭此文档下结论**。

---

## 5. ★ 为什么不追求 VSCode 扩展兼容

### 5.1 需求摊开看，依赖度很低

| Studio 需要什么 | 来源 | 依赖 VSCode 生态？ |
|----------------|------|------------------|
| 编辑器 | CodeMirror 6 | ❌ |
| 语言智能 | **LSP 服务器** | ❌ 开源独立进程 |
| 调试 | DAP | ❌ |
| 终端 | xterm.js + portable-pty | ❌ |
| **框架语义能力** | **G-54 六项独占能力** | ❌ **VSCode 生态根本没有** |
| 模拟器嵌入 | libmpv | ❌ |

**唯一真实损失**：闭源专有扩展。

### 5.2 这个损失与 Studio 的核心价值无关

Studio 的立命之本恰恰是 VSCode 生态**给不了**的东西：

- 框架语义能力（G-54）
- 移动端形态（G-56 INV-ST-08）
- 原生设备嵌入

### 5.3 追着生态兼容不放，恰恰违背自身原则

回顾"不要 fork VSCode"的论证：

> **为一个你不需要的能力，付架构上的全部代价。**

生态兼容是同一个逻辑的延伸。而 code-server 套壳更严重——它同时违反 **G-56.1（不自研编辑器内核）的精神**：

> **既然不自研，那也不该"假自研"。**

### 5.4 四个宿主的分工已经覆盖

```
VSCode 扩展    ← 需要 VSCode 生态的用户
IntelliJ 插件  ← JetBrains 用户
Zed MCP       ← Zed 用户
★ Studio      ← 要高性能 + 移动端的用户
        └──── 同一内核，零改动 ────┘
```

**Studio 不需要拥有 VSCode 生态——因为需要它的人走 VSCode 那条路就行了。**

---

## 6. 诚实标注：真实损失

以下损失是真实的，**必须写清而非含糊带过**：

| 损失项 | 影响人群 | 缓解 |
|--------|---------|------|
| **Pylance / C# Dev Kit 等闭源专有扩展不可用** | Python / C# 重度用户 | 走 VSCode 宿主路线 |
| **OpenVSX 覆盖率低于官方市场** | 部分扩展只有官方市场有 | 同上 |
| 新生态从零建设 | 所有 Studio 用户 | 插件 API 方案见后续插件生态 plan（未编号，见 rules.md 编号避让登记） |

> **若目标用户重度依赖闭源专有工具链，Studio 短期不适合他们。**
> 这句话必须对外明说，不能用"兼容性良好"含糊带过。
