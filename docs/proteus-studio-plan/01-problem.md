# G-56 Proteus Studio：自有宿主壳

> 原则 #0「不绑定」系列，第 19 次泛化（官方链：G-51=15、G-52=16、G-53=17、G-54=18，G-55 落地不占序；#393 修正，原稿误作 16）。
> 编号：G-56 · 依赖：G-54（编码期能力）、G-55（落地形态）、G-53（设备编排）
> 被依赖：G-58+

## 1. 问题：三个宿主有共同天花板

G-55 确立了「内核唯一 + 前端可换」，落地了三个宿主。但复盘发现三者**各有一块做不到的地方**，而这些地方恰恰重叠在同一类需求上。

### 1.1 三宿主能力矩阵（实测版）

| 能力 | IntelliJ | VSCode | Zed |
|------|----------|--------|-----|
| 自定义面板 | ✅ ToolWindow | ✅ Webview | ❌ **无 UI panel API** |
| 自定义按钮 | ✅ | ✅ | ❌ 仅 gutter icon |
| 控制台自定义 | ✅ | ✅ | ❌ 无 output monitoring |
| 设备画面嵌入 | ⚠️ 需自绘视频流 | ⚠️ Webview `<img>` | ❌ 只能唤起外部浏览器 |
| 原生性能 | ❌ Electron/JVM | ❌ Electron | ✅ Rust + GPUI |
| 移动端形态 | ❌ | ❌ | ❌ |

**观察**：**没有任何一个宿主同时满足"能嵌入 + 高性能 + 移动端"。**

- IntelliJ 面板能力最强，但跑在 JVM 上
- Zed 性能最好，但 UI 扩展能力最弱
- VSCode 折中，但 Electron 是性能天花板

### 1.2 三个具体痛点

**痛点 1：Zed 用户的设备预览是"二等公民"**

G-55 的降级链里 Zed 档只能返回 `DEGRADED`——功能无损，但画面在外部浏览器。**这是 Zed 扩展 API 的结构性限制，不是我们做得不够好。**

**痛点 2：模拟器嵌入在三个宿主都是"自绘视频流"**

IntelliJ 里要写 `JComponent.paintComponent()` 逐帧绘制；VSCode 里要 Webview 挂 `<img>`；Zed 里做不到。**同一件事写三遍，且第三遍还做不成。**

**痛点 3：真机上没有调试界面**

三个宿主都是桌面端。**装在手机上的 App 无法在一个宿主里看到自己的 SPI 后端、隔离状态、conformance 结果。**

## 2. 核心判断：自研宿主壳 ≠ 自研编辑器

这是本份最重要的区分，也是会让项目生死的判断。

### 2.1 自研编辑器内核 = 死亡陷阱（有实证）

| 项目 | 结局 |
|------|------|
| **xi-editor**（Raph Levien，Google） | **已死**，仅收 bug 修复 |
| **Lapce** | 3 万 star，**至今 pre-alpha**；自研 GUI 框架 Floem **两年未发新版** |
| **Floem** | 实测：**输入法切不出来**、屏幕阅读器读不到内容 |

Lapce 主程自述：*"GUI is just such a beast of complexity"*，团队至今无人全职。

Raph Levien 对 xi 的反思更值得记：其模块化设计 **"解决的更多是项目管理问题，而非技术卓越"**。

> **自研编辑器内核 = 用最贵的工程师，去补一个行业补了十年还没补完的洞。**

### 2.2 正确姿势：自研宿主壳，集成编辑器组件

```
┌─────────────────────────────────────────┐
│  Proteus Studio（自有宿主壳，Tauri 2）    │
│  ┌───────────┬───────────┬───────────┐  │
│  │ CodeMirror│ xterm.js  │  libmpv   │  │ ← 全部集成，不自研
│  │ 6 (编辑器) │ + pty     │ (模拟器)   │  │
│  ├───────────┴───────────┴───────────┤  │
│  │  面板 UI + 编排（自研）             │  │ ← 真正自研的部分
│  ├───────────────────────────────────┤  │
│  │  Rust 知识内核（G-55，已有）        │  │ ← 复用，零改动
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

**自研占比**：编辑器 ❌、终端 ❌、模拟器嵌入 ❌、GUI 框架 ❌
**自研占比**：知识内核复用 ✅（已有）、面板 UI ✅、编排 ✅

**真正自研的只有"编排 + 面板 UI"，其余全是集成。**

## 3. 第 19 次泛化

前 18 次泛化的模式：把「不绑定 X」的 X 逐级拔高（官方链：G-51=15 验证环境、G-52=16 设备形态、G-53=17 设备供给、G-54=18 IDE 形态；G-55 为 G-54 落地不占序）。

| 层级 | 不绑定 |
|------|--------|
| G-27 | 渲染后端 |
| G-46 | 数据后端 |
| G-51 | 验证执行环境 |
| G-52 | 设备形态 |
| **G-54** | **IDE 形态** |
| **G-56** | **宿主形态本身** |

G-54 说"不绑定 IDE"——但那时"IDE"指的是别人做的 IDE。
**G-56 往前一步：如果这个宿主是我们自己做的呢？**

> **「不绑定宿主来源」**：宿主可以是别人的（VSCode/IntelliJ/Zed），也可以是我们自己的（Studio）。
> **内核对两者一视同仁，不做任何特化。**

这不是推翻 G-54，而是 G-54 的完备化——**证明"不绑定"在"自有宿主"这个极端情形下依然成立**。

---

## 4. 与 G-55 的关系：并行，非替代

```
G-55 内核（唯一）
   ├─ VSCode 适配器      （别人做的宿主，生态最大）
   ├─ IntelliJ 适配器    （别人做的宿主，面板最强）
   ├─ Zed 适配器         （别人做的宿主，性能最好）
   └─ ★ Studio 适配器    （自己做的宿主，唯一能上移动端）
```

**四个宿主共用同一个内核，Studio 不享有任何特权接口。**

这条由 G-55 的"架构试金石"延续并加强：

> **加自有宿主时若被迫改内核，说明三层分层没做对。**
> （比加第三方适配器更能暴露问题——因为自有宿主最容易获得"开后门"的诱惑）

## 5. 诚实边界（明确不承诺）

1. **不自研编辑器内核**——本份明确排除，任何提案触碰此线应被否决
2. **Tauri 性能数字是框架级 benchmark，非 Proteus 实测**——不得对外宣称（G-55.7 纪律）
3. **Linux WebKitGTK 有已知硬伤**（NVIDIA 白屏 / 版本不兼容 / WebGL 静默降级），已设计降级但**未实测**
4. **移动端伴侣是推演，无先例**——Tauri 2 支持 iOS/Android，但"手机上看自己 App 的 SPI 状态"没有可参考的实现
5. **不承诺 Studio 能替代任一宿主**——它是第四个选项，不是最优选项
