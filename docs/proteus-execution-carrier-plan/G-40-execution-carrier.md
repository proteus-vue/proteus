# G-40 执行载体抽象与 JSI 边界治理

> **一句话**：不要绑定任何一种执行载体。JSI 是插槽上的默认实现，不是架构绑定。

---

## 1. 动机：三个无法回避的批评

在讨论架构之前，必须先诚实承认 JSI 的三个硬伤。这三条不是"可以优化"的范畴，
其中一条是"能做到 vs 做不到"的质变差异。

### 1.1 批评一：跨边界成本不为零

JSI 干掉了 Bridge 的 JSON 序列化，但**不是免费的**。实测数据：

| 调用方式 | 100 万次耗时 | 单次成本 |
|---------|------------|---------|
| HostObject 路径 | 181 ms | ~181 ns |
| HostFunction 路径 | 27 ms | ~27 ns |

**差 5 倍。** JSI 的开销集中在四处：

1. **边界跨越**（JS 栈 → C++ 栈 → JS 栈）
2. **属性解析**（HostObject 的 `get`/`set` 需要运行时查找）
3. **虚派发**（`HostObject::get` 是虚函数，无法内联）
4. **字符串转换**（JS `String` ↔ C++ `std::string`）

**编译型框架（Flutter / Compose）没有这个边界**——产出的就是原生对象，函数调用就是函数调用。

### 1.2 批评二：字符串默认拷贝，非零拷贝

JSI 中 `jsi::String` 与 `std::string` 之间的转换**默认是拷贝**。
真正能共享底层字节的通道只有 **`jsi::ArrayBuffer`**。

后果：大块数据（图片、音频 PCM、IR diff 树）如果走字符串通道，
每次跨界都是一次完整拷贝——这在高频场景下是灾难性的。

### 1.3 批评三：线程亲和性 —— 这是质变，不是程度问题

> `jsi::Runtime` 有**严格的线程亲和性**。从其他线程访问 `jsi::Runtime`
> 或任何 `jsi::Value` 都会导致 **undefined behavior**。

这不是"慢一点"的问题，是**根本做不到**：

- JS 侧本质上仍是**单线程**
- 一个耗时 50ms 的同步原生调用会**阻塞整个 JS 线程**
- 触摸事件、定时器、回调**全部停摆**
- **实时系统（音频回调、传感器高频流、游戏循环）根本没法从 JS 驱动**

**这一条决定了：某些能力领域，JS 驱动的路径在架构上就是错的。**

## 2. 核心立场：修正一个表述

之前有一处表述需要修正——

> ❌ 旧表述：**"逻辑层始终 JSI"**

这句话说窄了。准确的架构表述是：

> ✅ **"逻辑层始终运行在宿主运行时提供的执行环境上。
> JSI 是默认载体（JS 引擎路径），不是唯一载体。"**

### 为什么这不是事后找补

G-39 的 `ProteusHostRuntime` 接口里**已经存在**这个方法：

```typescript
// G-39 宿主运行时接口
interface ProteusHostRuntime {
  // ★ 执行环境创建 —— 插槽在这里
  createEngine(config: EngineConfig): JSEngine
  // ...
}
```

`createEngine` 的存在，就意味着**执行环境从第一天起就是可插拔的**。
JSI 只是"当前默认选择了 JS 引擎"这个**实现决策**的结果，不是架构绑定。

### 竞品为什么无解

| 框架 | 绑定 | 结果 |
|------|------|------|
| React Native | **绑死 JSI** | 上述三个问题无解，只能缓解 |
| Flutter | **绑死 Dart** | 无 JS 生态，Web 场景弱 |
| uni-app | **绑死 JS 引擎** | 同上，且无 AOT 路径 |
| Lynx | 双线程 + 原生渲染 | 逻辑仍在 JS 线程，亲和性限制仍在 |
| **Proteus** | **执行载体可插拔** | JSI / AOT / WASM 三条路径按场景选 |

**这就是方法论第五次应用**：

```
不要绑定平台 API      → G-31/32 已做
不要绑定渲染引擎      → G-27/37 已做
不要绑定编译器        → G-29/38 已做
不要绑定宿主运行时    → G-39 已做
不要绑定执行载体/JSI  → ★ G-40（本次）
```

## 3. 解法总览：五条缺口 → 五条约束

现有文档里，这些能力**有接口但无约束**。缺约束的下场是：
AOT 路径因为没有强制保障，会慢慢退化成"理论上可行但实际没人敢切"。

| # | 缺口 | 现状 | G-40 补的约束 |
|---|------|------|--------------|
| 1 | 执行载体可替换 | G-39 `createEngine` 有接口 | **铁律**：业务禁止假设 JS 运行时存在 |
| 2 | AOT 路径 | G-38 `emit` 列了产物类型 | **策略**：何时必须走 AOT + 语义等价保证 |
| 3 | 实时能力逃逸 | G-39 native-bridge 有注册机制 | **铁律**：实时能力禁止 JS 驱动 |
| 4 | 零拷贝通道 | 未定义 | **契约**：大块数据强制 ArrayBuffer |
| 5 | 批处理差分 | IR 层天然支持，未约束 | **接口**：nodeOps 批处理化 |

## 4. 解法一：三条执行路径与选择策略

### 4.1 三条路径的能力画像

```
┌─────────────┬──────────────┬──────────────┬──────────────┐
│             │  JSI (默认)   │  AOT (原生)   │  WASM        │
├─────────────┼──────────────┼──────────────┼──────────────┤
│ 跨边界成本   │ 27–181 ns/次 │  0（无边界）  │  ~10 ns/次   │
│ 并发能力     │ ✗ 线程亲和   │  ✓ 真并发    │  ✓（受限）   │
│ 实时系统     │ ✗ 不可用     │  ✓ 可用      │  △ 部分      │
│ 动态性       │ ✓ 热更新     │  ✗ 需重编译  │  ✓ 可热载    │
│ JS 生态      │ ✓ 完整       │  ✗ 需静态化  │  △ 部分      │
│ 启动速度     │ △ 需解析     │  ✓ 立即      │  △ 需实例化  │
│ 调试体验     │ ✓ 最好       │  △ 需符号    │  △ 需工具    │
└─────────────┴──────────────┴──────────────┴──────────────┘
```

**没有一条路径是全能的。** 这正是"可插拔"的价值——不是选一个最好的，
而是**按场景选最合适的**。

### 4.2 选择策略（决策树）

```
                    ┌─────────────────┐
                    │ 业务需要实时性？  │
                    │ (音频/传感器/游戏)│
                    └────────┬────────┘
                       Yes   │   No
              ┌──────────────┴──────────────┐
              ↓                              ↓
       ★ 实时能力逃逸                  ┌──────────────┐
       （原生闭环，见 §6）              │ 需要并发计算？ │
                                      └──────┬───────┘
                                       Yes   │   No
                              ┌──────────────┴──────────────┐
                              ↓                              ↓
                        ┌──────────┐                  ┌──────────┐
                        │ AOT 或   │                  │ 需要热更新│
                        │ Worker   │                  │ /动态性？ │
                        └──────────┘                  └────┬─────┘
                                                      Yes  │  No
                                            ┌──────────────┴──────┐
                                            ↓                     ↓
                                       JSI (默认)            AOT（性能优先）
```

### 4.3 关键：路径切换对业务透明

```typescript
// proteus.config.ts
export default defineConfig({
  execution: {
    // 整个 App 走 AOT
    mode: 'aot',
    // 或按模块粒度
    overrides: {
      'pages/realtime-audio': { mode: 'aot' },
      'pages/settings':       { mode: 'jsi' },   // 需要动态配置
    }
  }
})
```

**业务代码完全不变**——这是铁律 G-40.2 的强制保障（见 §5）。

## 5. 铁律：业务禁止假设 JS 运行时

### G-40.1（铁律）：执行载体无关性

> **业务代码不得假设 JS 运行时存在。**

具体禁止项（机器可检查）：

| 禁止 | 原因 |
|------|------|
| 直接使用 `window` / `globalThis` | AOT 路径无此全局对象 |
| 使用 `eval` / `new Function` | AOT 路径无法动态求值 |
| 依赖 `setTimeout` 的精确时序 | AOT 路径调度模型不同 |
| 直接操作 `jsi::Value` / `jsi::Runtime` | 直接违反载体抽象 |
| 依赖 `Promise` 微任务顺序做同步 | 各载体调度顺序可能不同 |
| 使用 `Proxy` 做运行时拦截 | AOT 路径需静态分析 |

**检查方式**：Compiler 在 IR 层做静态扫描，命中即编译错误（不是警告）。

### G-40.2（铁律）：语义等价保证

> **同一份源码，在 JSI / AOT / WASM 三条路径下必须产出语义等价的行为。**

这与 G-38.2（编译器产物语义等价）是同一原则在**执行层**的延伸。

验证方式：三路径跑同一 conformance 测试集，行为差异即为 bug。

## 6. 解法二：实时能力逃逸协议

### 6.1 问题重申

`jsi::Runtime` 的线程亲和性意味着：
**任何由 JS 驱动的实时循环都是架构错误。**

50ms 同步调用 → 整个 JS 线程阻塞 → 触摸/定时器/回调全停。

### 6.2 正确姿势：原生侧闭环

```
❌ 错误范式（JS 驱动实时循环）：
   JS 每 10ms 调一次原生 → 渲染音频
   → 阻塞 JS 线程，且时序无法保证

✅ 正确范式（原生闭环 + 事件回传）：
   ① JS 下发配置：audioEngine.start({ sampleRate: 48000, ... })
   ② 原生侧在专用实时线程闭环运行（音频回调）
   ③ 原生侧通过事件/共享内存回传状态
   ④ JS 只做：配置下发 + 事件接收
```

### 6.3 G-40.3（铁律）：实时能力禁止 JS 驱动

> **实时能力（音频、高频传感器、游戏循环、视频帧处理）
> 必须在原生线程闭环运行，禁止由 JS 侧驱动循环。**

开放给 JS 的只有三个动作：

```typescript
interface RealtimeCapability {
  // ① 配置下发（一次性，非循环）
  configure(config: RealtimeConfig): void
  // ② 启停控制
  start(): void
  stop(): void
  // ③ 事件订阅（原生 → JS，低频）
  onEvent(handler: (e: RealtimeEvent) => void): Unsubscribe
}
```

**注意 `start()` 之后 JS 不再参与**——循环完全在原生侧。

### 6.4 事件回传的节流约束

原生侧事件可能高频（如音频电平每秒 60 次），直接回传 JS 会打爆 JS 线程。
因此：

```
原生侧事件 → 聚合/节流 → 批量回传 → JS 侧处理
```

节流策略由 G-39 的 `enqueue(task, priority)` 支持，实时事件走 `high` 优先级队列。

## 7. 解法三：零拷贝通道契约

### 7.1 数据分类

| 类别 | 典型 | 通道 | 原因 |
|------|------|------|------|
| **标量** | 配置、状态码、ID | 常规 JSI 通道 | 拷贝成本可忽略 |
| **结构化小数据** | 表单、JSON 配置 | 常规通道 + 批处理 | < 4KB |
| **★ 大块二进制** | 图片、音频 PCM、视频帧 | **ArrayBuffer** | 唯一零拷贝通道 |
| **★ 结构化大数据** | IR diff 树、大型列表 | **ArrayBuffer + 二进制编码** | 避免字符串拷贝 |

### 7.2 G-40.4（铁律）：大块数据强制零拷贝

> **超过 4KB 的数据跨界传输，必须使用 `ArrayBuffer` / `SharedArrayBuffer`，
> 禁止走字符串通道。**

接口层面保证：

```typescript
interface ProteusNativeBridge {
  // 标量/小数据
  invoke<T>(name: string, args: unknown[]): Promise<T>

  // ★ 大块数据（强制零拷贝语义）
  invokeBinary(name: string, buffer: ArrayBuffer, meta?: unknown): Promise<ArrayBuffer>
}
```

**`invokeBinary` 的实现约束**：
- 必须传递 `ArrayBuffer` 的**底层字节视图**，不得 `.slice()` 拷贝
- 若目标端不支持零拷贝，必须**显式声明**（capabilities），由上层决策降级

### 7.3 Capabilities 声明

```typescript
interface BridgeCapabilities {
  zeroCopy: {
    supported: boolean
    mechanism: 'arraybuffer' | 'sharedarraybuffer' | 'native-pointer' | 'none'
    maxSize?: number        // 零拷贝上限，超过降级
  }
}
```

不支持零拷贝时，Compiler/运行时**必须记录指标**并可选降级到拷贝路径（G-40.6 可观测性）。

## 8. 解法四：批处理差分接口

### 8.1 现状问题

传统 nodeOps 范式是**一次属性变更一次跨界**：

```
setProp(A) → JSI跨界 → setProp(B) → JSI跨界 → ... → N 次跨界
```

按 181 ns/次计，一帧 100 个属性变更 = **18.1 μs 纯跨界开销**。

### 8.2 批处理化

G-27 的 `ProteusRenderBackend` 增加批处理接口：

```typescript
interface ProteusRenderBackend {
  // 现有单节点操作（保留，用于简单场景）
  updateNode(handle: NodeHandle, changes: IRDiff): void

  // ★ 新增：批处理提交（必须实现）
  commitBatch(ops: RenderOp[]): void
}

type RenderOp =
  | { kind: 'create';   node: ComponentIRNode; parent: Handle; at: number }
  | { kind: 'update';   handle: Handle; changes: IRDiff }
  | { kind: 'delete';   handle: Handle }
  | { kind: 'insert';   parent: Handle; child: Handle; at: number }
  | { kind: 'remove';   parent: Handle; child: Handle }
  | { kind: 'setStyle'; handle: Handle; style: StyleIR }
  | { kind: 'setText';  handle: Handle; text: string }
```

**一帧的所有变更聚合为一个 `RenderOp[]`，一次跨界提交。**

### 8.3 收益估算（需实测验证）

| 项 | 值 |
|----|-----|
| 单帧属性变更数 | 100 |
| 旧范式跨界次数 | 100 |
| 新范式跨界次数 | 1 |
| 旧范式跨界成本 | 100 × 181ns = **18.1 μs** |
| 新范式跨界成本 | 1 × 181ns + diff 序列化 ≈ **1–2 μs**（粗估） |
| **净收益** | **约 10–18 倍** |

> ⚠️ **这是工程推算，不是实测结论。** M1 必须建立跨界成本基准测试，
> 用真实数据替换此表。在此之前，不作为对外宣称的性能数据。

### 8.4 G-40.5（铁律）：nodeOps 必须支持批处理

> **所有 RenderBackend 必须实现 `commitBatch`。
> 框架默认走批处理路径，单节点操作仅用于调试/回退。**

## 9. 解法五：Worker 池与 AOT 并发

### 9.1 Worker 路径（JS 生态内）

G-39 已有 `createWorker` / `postMessage`：

```typescript
interface ProteusHostRuntime {
  createWorker(script: string): WorkerHandle
  postMessage(target: WorkerHandle, msg: unknown): void
}
```

**约束**：每个 Worker 独立 Runtime，Worker 间**不能共享 `jsi::Value`**，
必须序列化传递。这是并发的固有隔离成本，可接受。

### 9.2 AOT 路径（真正的并发）

AOT 产出的原生代码：

- 运行在**原生线程**，无 `jsi::Runtime` 亲和性限制
- 可**真正并发**（多线程访问共享内存）
- 无跨界成本（函数调用即函数调用）

**这同时解决了批评一（跨界成本）和批评三（并发）——
因为 emit 阶段的产物选择本来就定义了这条路径。**

### 9.3 AOT 的代价（诚实说明）

| 代价 | 说明 | 缓解 |
|------|------|------|
| 失去动态性 | 不能热更新 | 按模块粒度：核心 AOT，业务 JSI |
| 调试困难 | 需符号表 | 保留 debug 产物 |
| JS 生态受限 | 动态特性需静态化 | 静态子集 + 编译期检查 |
| 构建时长 | 编译为原生代码 | 增量编译（G-38） |

**因此 AOT 不应该是默认路径，而应该是"性能关键模块"的选择。**

## 12. 诚实边界

G-40 **不承诺**：

| 不承诺 | 原因 |
|--------|------|
| JSI 路径能解决线程亲和性 | 这是 `jsi::Runtime` 的固有约束，只能绕开不能修复 |
| AOT 路径支持全部 JS 动态特性 | 动态求值、Proxy 需静态子集 |
| 批处理收益是实测值 | 需 M1 建立基准测试后才有真实数据 |
| 零拷贝在所有端可用 | 依赖端能力，不支持时降级并上报 |
| 实时能力在 Tier 3/4 可用 | 无原生能力宿主时不可用 |

**明确边界比无限承诺更有说服力。** 这也是原则 #11（可插拔必须有可验证支撑）的要求。

---

## 13. 结论

> **G-40 的价值不在于"解决了 JSI 的问题"，而在于证明了：
> 我们从来没有绑死 JSI。**

三条批评之所以对 RN / uni-app 是**无解的架构死结**，
对我们是**可选择的工程权衡**——因为：

- `createEngine`（G-39）提供了执行载体插槽
- `emit` 产物选择（G-38）提供了 AOT 路径
