## 1. 单位模型

### 1.1 统一公式

鸿蒙官方文档给出最清晰的表达（权威性极高）：

> **fp2px**：`px = fp × 像素密度 × 字体缩放系数（Configuration.fontScale）`
> **vp2px**：`px = vp × 像素密度`

该公式在四个平台**完全同构**：

| 平台 | 设计单位 | 密度因子 | 字体缩放因子 | 物理单位 |
|---|---|---|---|---|
| Flutter | 逻辑像素 | `devicePixelRatio` | `TextScaler` / `SystemTextScaler` | 物理像素 |
| Android | dp / sp | `density` | `fontScale`（合称 `scaledDensity`） | px |
| iOS | point | `UIScreen.scale` | Dynamic Type | 物理像素 |
| **鸿蒙** | **vp / fp** | **像素密度** | **fontScale**（官方明列） | px |
| Web | CSS px | `devicePixelRatio` | 浏览器字体设置 | 设备像素 |

> **物理像素 = 设计单位 × 密度 × 字体缩放（仅文本）**

**这是一条可以写进标准的统一模型。** Rust 排版核心产出设计单位，宿主层按此公式换算。

### 1.2 各端 API 期望的输入单位（关键差异）

| 端 | 绘制 API | 期望单位 |
|---|---|---|
| Android | Canvas / RenderNode | **px（物理）** |
| iOS | CALayer / CoreGraphics | **point（逻辑）** |
| 鸿蒙 | RenderNode（API 20+） | 待核实（§9 待核实 1） |
| Web | CSS | **CSS px（逻辑）** |

**🔴 由此推出一个非常重要的结论：**

**Android 的 dp 与 iOS 的 point 数值并不相同。**

- Android `dp` 基准为 160dpi，且密度桶**离散**（1.0 / 1.5 / 2.0 / 2.75 / 3.0…）
- iOS point 基准约 163dpi，scale 也是**离散**（1 / 2 / 3）

**同一物理尺寸的屏幕，dp 数与 point 数可能不同。**

因此**内核既不能产出 dp 也不能产出 point**——必须产出一个跨端统一的单位。**物理像素是唯一跨端一致的单位。**

## 2. 指令流单位定案

### 2.1 定案：物理像素整数

```
Rust 排版核心
  → 布局计算（设计单位，浮点精确）
  → × 密度 × 字体缩放（文本）
  → snap 到整数物理像素
  → 指令流携带【整数物理像素】
       ↓
宿主层：只做单位换算（× 或 ÷ scale），零舍入
```

### 2.2 为什么不是逻辑像素

| 维度 | 物理像素（定案） | 逻辑像素 |
|---|---|---|
| 跨端一致性 | ✅ 唯一跨端统一单位 | ❌ dp ≠ point（§1.2） |
| 物理像素对齐 | ✅ 可直接 snap | ❌ 逻辑空间 snap 会产生系统性偏差 |
| 清晰度 | ✅ 无亚像素模糊 | ❌ 非整数 DPR 下必然模糊 |
| DPR 变化 | ❌ 需重排 | ✅ 只改系数 |

### 2.3 代价与接受理由

**代价：DPR 变化必须触发重排。**

接受理由：

1. DPR 变化是**极低频事件**（跨屏拖动、系统显示设置变更、外接显示器）
2. 单次全量重排成本为 **0.08ms**——重排代价可忽略
3. 且 DPR 变化后**物理对齐本身就需要重算**，即使指令流带逻辑像素也免不了

> **结论：用一次 0.08ms 的重排，换取跨端统一 + 物理对齐 + 清晰度，划算。**

### 2.4 硬约束

- [ ] 指令流中所有几何值为**整数物理像素**
- [ ] 内核产出前已完成 snap，**宿主层不得再舍入**（静态检查）
- [ ] 宿主层仅做单位换算，且换算为**一次乘法或除法**，不含任何 `round/floor/ceil`
- [ ] DPR 变化事件触发全量重排

## 3. 🔴 修正 I2 卡：舍入必须在物理像素空间做

### 3.1 现有 I2 卡规则的风险

I2 卡原文：「内核产出指令时完成舍入，平台层不得再舍入」——**方向正确，但未指明在哪个空间舍入。**

若在**逻辑空间**先舍入，会产生系统性偏差：

```
逻辑 12.5dp × DPR 3 = 37.5 px
若在逻辑空间先舍入为 13dp → 39px
与 37.5 相差 1.5px  ← 三端一致地偏，但都是错的
```

**注意这种偏差的性质：三端一致，所以 golden test 全绿，但渲染结果与预期不符。** 这正是 I2 卡标题里那句「golden test 全绿但三端差 1px」的另一种形态——**比跨端不一致更难发现**。

### 3.2 正确顺序（硬约束）

```
逻辑精确值（浮点）
    ↓ × 密度
    ↓ × 字体缩放（仅文本）
    ↓ round-half-up  ← 舍入只在这一步
物理像素整数
```

**顺序不可颠倒。任何在逻辑空间进行的舍入都是 bug。**

### 3.3 舍入策略

| 项 | 规定 |
|---|---|
| 算法 | **round-half-up**（与 I2 卡一致） |
| 位置 | **仅内核，且仅在物理像素空间** |
| 平台层 | **零舍入**（静态检查） |

### 3.4 关于 PixelSnap——决定是否比 Flutter 更激进

第三方库记录了一个 Flutter 的公开问题（权威性中等，技术链条完整）：

> DPR = 1.5（Windows 150%）时，1 逻辑像素宽的线渲染为 1.5 物理像素，
> **无法点亮半个像素，只能抗锯齿 → 看起来模糊**

**Flutter 默认不做 pixel snapping**，连 100% 缩放下居中都可能因落在半像素而模糊。

要真正清晰需三件事：
1. 尺寸 snap 到物理像素边界
2. 布局保证子元素落在物理像素边界
3. **DPR 变化时重算布局**

**第 3 条与本方案 §2.3 的代价完全一致——我们已经设计进去了。**

> 建议：**做 snap。** 理由有二：
> ① 你复用系统管线，系统合成器本身就有 snap 行为，主动 snap 更贴合；
> ② 这是**能直接看出来比 Flutter 清晰**的点，属于「超越 Flutter」的具体落点之一。

## 4. 文本：字体缩放必须在度量之前

### 4.1 Flutter 源码实证（权威性极高）

`TextPainter.textScaler` 官方注释：

> "The `TextStyle.fontSize` of the text will be adjusted by the `TextScaler`
> **before the text is laid out and rendered.**"

且 `TextScaler.scale()` 的签名注释明确：

> "Computes the scaled font size **(in logical pixels)** with the given unscaled fontSize **(in logical pixels)**."

### 4.2 两个推论

**① 缩放发生在布局/度量之前**——不是度量完再乘系数。

若先度量再缩放，或忘记缩放，**三端算出的文本宽度全都不对**，且误差随文本长度累积。

**② 缩放是逻辑像素空间内的独立乘数**，不参与 DPR 转换。

```
文本最终物理尺寸 = 字号(设计单位) × 字体缩放 × 密度
                              ↑ 先应用        ↑ 后应用
```

### 4.3 硬约束

- [ ] 内核持有的 `text_measure`（平台注入：Android StaticLayout / iOS CoreText / 鸿蒙 / Web）
      **接收的必须是已应用字体缩放后的字号**
- [ ] 指令流携带**已度量完成的几何 + 文本内容 + 最终字号**（方案 A，与 I4 卡一致）
- [ ] 平台层只负责绘制，**不参与排版、不参与缩放**
- [ ] 文本度量结果纳入 conformance

### 4.4 与 I4 卡的关系

I4 卡建议「选方案 A：绘制文本指令 + 内核已度量几何」——**本规范确认该选择**，并补上此前缺失的一条：**度量前必须先应用字体缩放**。

## 5. 非整数 DPR 处理

### 5.1 事实

Flutter 官方文档（权威性极高）：

> "This number might not be a power of two. Indeed, it **might not even be an integer**.
> For example, the Nexus 6 has a device pixel ratio of **3.5**."

Android 密度桶：ldpi 0.75x / mdpi 1.0x / hdpi 1.5x / xhdpi 2.0x / xxhdpi 3.0x / xxxhdpi 4.0x（**含 2.75 等非整数档**）。

### 5.2 处理规则

物理像素对齐在非整数 DPR 下**仍然可行**（物理像素是整数，总能对齐）。真正的取舍在**细线/边框**：

| 场景 | 规则 |
|---|---|
| 一般尺寸与位置 | 正常 snap：`round(x × dpr)` |
| **细线 / hairline 边框** | `max(1, round(x × dpr))`——**保证至少 1 物理像素，不得舍入为 0** |
| 1 设计单位边框 @1.5x | 得 1.5 → snap 应为 1 或 2，**由设计意图决定，需可配置** |

### 5.3 硬约束

- [ ] **任何几何值 snap 后不得为 0**（细线消失是可见缺陷）
- [ ] hairline 策略可配置（`thin` / `thick`），默认 `thin`（`max(1, ...)`）

## 6. 字体缩放跟随策略（决策点）

### 6.1 取舍

| 选择 | 后果 |
|---|---|
| **跟随系统缩放** | 无障碍友好；但**三端缩放因子不同 → 几何不一致** |
| **不跟随** | 一致性好；但违反无障碍规范 |

鸿蒙给出第三条路（权威性极高）：`setDefaultDensityEnabled` 可禁用全局显示缩放适配，也可直接用 `px` 单位绕开。

### 6.2 定案

**做成框架配置项，框架不替业务方决定。**

| 配置 | 行为 | 建议场景 |
|---|---|---|
| `follow`（**默认**） | 跟随系统字体缩放 | 一般业务，无障碍优先 |
| `fixed` | 固定 1.0，不跟随 | 一致性敏感场景（如金融 K 线、设计还原验收） |

### 6.3 硬约束

- [ ] 该配置**必须在指令流或渲染环境参数中显式传递**，不得隐含
- [ ] 一致性校验时**必须锁定该配置**（否则跨端基线不可比，见 §7）

## 7. 校验手法：锁 DPR + 锁测试字体

### 7.1 借自 Flutter golden test 的手法

Flutter golden 社区的标准做法（权威性中等）：

> golden scene 渲染到物理像素，DPR=1.75 时逻辑 30 → 52.5，产生抗锯齿 → flaky
> **解法：`tester.view.devicePixelRatio = 1.0`**

Flutter 同时用 `Ahem` 测试字体（方块字形，度量完全确定）消除字体不确定性。

### 7.2 应用到 L2 几何校验

| 锁定项 | 消除的不确定性 |
|---|---|
| **锁 DPR**（建议 1.0 或 2.0） | 亚像素吸附、抗锯齿噪声 |
| **锁测试字体** | 文本度量差异 |

```
锁 DPR + 锁测试字体  →  L2 几何校验 100% 确定
```

**这是《多端一致性标准方案》§10.1「L2 完全确定」的技术前提。不做这两件事，L2 就不是完全确定的，整个「可验证一致性」的论证会松动。**

### 7.3 硬约束

- [ ] 校验环境强制锁定 DPR，记录进报告
- [ ] 校验环境强制锁定测试字体，记录进报告
- [ ] 真实字体的文本差异**另行单列**，走容差带（见 §8）
- [ ] 字体缩放配置在校验时锁定（§6.3）

## 8. 真实字体的差异：容差带

锁测试字体是**校验手段**，不是生产行为。生产环境用真实字体，差异必然存在：

| 差异源 | 说明 |
|---|---|
| 度量引擎不同 | Web 浏览器 / Android StaticLayout / iOS CoreText / 鸿蒙各自实现 |
| 字体 fallback 不同 | 各端字体族配置不同 |
| 字形版本不同 | 如 iOS 18 起苹方分为「苹方」与「新苹方」两版 |

**必须显式设计容差带，且按属性分级**（与《一致性校验任务卡清单》VC5-a 一致）：

| 属性类 | 容差 |
|---|---|
| 结构类（位置 / 尺寸） | 严格 |
| 颜色类 | 极严格（如 ±1/255） |
| **文本度量** | **唯一需要宽带的** |
| 圆角 / 阴影 / 渐变 | 不比数值，走 L4 像素 |

**🔴 禁止全局差异阈值。** 一个 50×20 的按钮变色只占全高清页 0.001% 像素，在 0.01% 全局阈值下必然漏报——这正是传统视觉回归漏报的根源。

## 14. 实施记录（Proteus 仓库 · 2026-10-02）

> ★本节由实施会话追加，记录本规范**已落地**的部分与**已暴露的真实缺陷**（作为规范本身的实证）。

### 14.1 Android 宿主（VaporRenderHost）已按 §1/§3 改造

**换算点唯一化**（`physicalizeTree` / `physicalizeSpec`）：
- 位置：**树的唯一入口**（`mount` / `mountVirtual` / `updatePatches` 的 patch style）
- 范围：标量长度白名单（`LEN_SCALARS`）+ 边缘对象（margin/padding 四边）+ `glow.radius`
- 排除：比例/枚举/分数（flexGrow/flexShrink/opacity/clipPath.params/mask.*/transformOrigin/gradient offset）
- 性质：**仅 `× scale`，零舍入**（符合 §2.4）

**★两版失败换来的教训（规范 §3.2 的实证）**：
1. 第一版在 **JS 侧**改模板 style ⇒ 漏**动态绑定**（`:width="item.w"` 走求值器、不经模板字典）
   ——chip 高缩放对了（96=32×3）而**宽没缩放**（40，应 120）；
2. 第二版改为 `coreNodes()` **局部缩放** ⇒ 只覆盖布局标量，漏**绘制侧长度**
   （borderRadius / fontSize（绘制读取处）/ glow.radius / strokeWidth）——
   chip 圆角变方、蓝点由圆变方、字"度量 3× 而绘制 1×"两边打架（用户目视当场抓出）；
3. **正解**：换算**只做一次**（树入口），把 spec 全部改写为物理单位后落表 ⇒
   所有消费者（内核 / 绘制 / 度量 / 命中）读到的天然全是物理值，不存在"半物理化"中间态。
