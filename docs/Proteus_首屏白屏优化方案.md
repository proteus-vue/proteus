# Proteus 首屏白屏优化方案

> 定位：**把首屏等待压到用户感知不到**，参考 Lynx IFR 的成熟思路但按 Proteus 架构重做
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4 / 微信基础库 2.29.2+）
> 依赖：《App 端高性能渲染落地方案》M2、《Vapor for Proteus IR》V1、《Host ABI》§8.5、`proteus_prewarm()`
> 设计参照：Lynx Instant First-Frame Rendering (IFR) + Element Templates

## 0. 决策与前提

### 0.1 默认选择（可调）

| # | 决策项 | 本文默认 | 理由 |
|---|---|---|---|
| ① | 首屏骨架载体 | **编译进 App 二进制做兜底 + 随产物下发做常态** | 前者零 IO 最稳；后者保动态化。两者结合 |
| ② | 占位值来源 | 三级：编译期常量 → 本地缓存 → 留空 | 缓存命中时几乎无"加载中"感知 |
| ③ | 是否阻塞主线程 | **短暂阻塞至首帧完成**（同 Lynx） | 前提是首帧足够快；见 §4.3 的预算约束 |

若 ① 与你的判断不符请指出——若只做"随产物下发"，方案会简化，但 Playground 扫码场景的白屏风险无法覆盖。

### 0.2 Lynx 的 IFR 到底是什么（先准确理解再谈参考）

Lynx 官方定义 [citation:2][citation:18]：

> 页面被加载时直接展示内容，而不产生白屏或其他中间状态。
> 主线程 bundle 携带运行时与应用代码，**在 `loadTemplate` 期间同步渲染**，
> 同时后台线程并行启动。首屏在任何后台 JS 执行之前就已出现。

**关键机制**：`loadTemplate → render → paint` 全在主线程同步完成，
**短暂阻塞 UI 线程直到首帧完整渲染**。Lynx 的判断依据是可用性研究——
**如果渲染足够快，就不需要任何中间反馈（骨架屏/loading）** [citation:13]。

### 0.3 ★ Lynx 明确承认 IFR 会失效的两种情况

这点极其重要，官方写在文档里 [citation:2][citation:18]：

1. **页面的 Bundle 无法同步加载时**（例如异步文件 I/O）——白屏主因是异步 I/O
2. **页面主要内容需要异步加载时**（例如需要请求网络数据）——白屏主因是异步网络请求

**对 Proteus 的直接推论**：
- 场景 1 对我们基本不成立——IR 二进制经 mmap 构造，无解析步骤（方案 §5.2）
- **场景 2 正是 Playground 扫码运行的真实情况**（产物需下载）→ **这才是本方案要解决的重点**

### 0.4 一个意外发现：Element Templates ≈ 我们已有的拍平

Lynx 的 **Element Templates** 是这样工作的 [citation:5]：

```
编译器可折叠的静态子树：
  无 ET：vnode → ShadowElement → 逐节点 ops → 跨线程 → 解释器 → PAPI
  有 ET：单个 vnode → INSTANTIATE_TEMPLATE → 直线 PAPI create()
动态文本/class/样式/属性成为「洞（holes）」，通过常规 SET_* ops 更新
```

**准入条件**：结构编译期已知、每个节点都是普通元素、只有属性值或文本内容动态；
组件、slot、`v-if`/`v-for` 宿主仍走普通路径 [citation:5]。

**对照 Proteus**：

| Lynx Element Templates | Proteus 已有机制 |
|---|---|
| 静态子树折叠为一条 op | **`flatten` 拍平**（2 万元素 → 24 个 RenderNode） |
| 动态部分成为 holes | **Slot 槽位**（Vapor IR §3） |
| `INSTANTIATE_TEMPLATE` | **`tree_build(template_bytes)` 直接构造** |

**结论：这套机制的等价物我们早就有了，而且实测更彻底**（拍平后 24 个节点）。
所以本方案**不是照搬 Lynx 的 ET**，而是补上我们缺的那部分：**首屏数据从哪来、骨架何时上屏**。

## 1. 先测后做：六段启动耗时拆解

**在写任何代码之前，必须先把白屏拆开。** 这是本方案的第一步。

### 1.1 六段模型

```
① 进程 / 壳启动          平台固有，改不了
② 内核初始化             可预热（proteus_prewarm）
③ 产物加载（本地 / 网络） 可预置、可缓存
④ 节点树构造             mmap，极快
⑤ 排版 + 绘制            0.08ms + 绘制（已解决）
⑥ 首帧提交
```

### 1.2 打点规格

| 段 | 起点 | 终点 | 采集 |
|---|---|---|---|
| ① | 进程创建 | 壳 `onCreate` 开始 | 系统时间戳 |
| ② | `proteus_prewarm()` 入 | 内核 ready | 高精度计时 |
| ③ | 产物加载发起 | bytes 可用 | 区分本地 / 网络 |
| ④ | `tree_build` 入 | 节点树可用 | 高精度计时 |
| ⑤ | `tree_layout` 入 | 绘制指令就绪 | 高精度计时 |
| ⑥ | 指令提交 | 首帧上屏 | vsync 时间戳 |

**输出**：六段耗时 + 占比，明确"白屏到底花在哪"。

### 1.3 关键判读

**⑤ 我们已经解决了**（布局 0.08ms、宿主侧 1ms）。
**④ 因为 mmap 设计也几乎为零。**
**所以真正值得投的是 ②（预热）+ ③（预置/缓存兜底）。**

**若实测显示 ①②占绝对大头**（平台固有 + 内核初始化），
那么"秒启动"就不该是重点投入方向——做骨架兜底即可，不要过度工程。

## 2. 首屏骨架方案（核心）

### 2.1 思路

```
编译期产出「首屏骨架」
  ├─ 静态结构（LayoutTemplate 的子集）
  ├─ 静态文本（编译期已知的文案、标签、占位符）
  └─ 动态槽位留空 → 数据到达后 O(1) 填充
```

用户点击图标 → 壳启动 → **骨架直接上屏**（数据未到）→ 数据到达 → 槽位填充。

### 2.2 为什么这比 Lynx 更彻底

Lynx 的 hydration 需要处理"主干已渲染、后台线程重跑后对账"：

> 两个线程用相同初始数据执行同一应用。主线程渲染记录它应用的每个 ops batch，
> 后台线程的初始 batch 与之对账：相同的 batch 跳过；文本/样式/属性差异就地 patch；
> **结构差异则移除首屏树并从后台 ops 重建** [citation:5]。

**Proteus 没有这个问题**——槽位机制（Vapor IR §3）本身就是"可变的强类型容器"，
**数据到达是"填充"，不是"替换"**。不存在结构对账、不存在重建、不存在 mismatch warning。

这是架构带来的简化，不是调参成果。

### 2.3 占位值三级来源（★ 决定体验上限）

```
编译期识别首屏动态槽位
  → 为每个槽位标注可用的占位值来源：
      ├─ 一级：编译期已知常量    → 直接用（文案、标签、图标）
      ├─ 二级：本地缓存的上次值  → 用缓存（★ 体验提升最大）
      └─ 三级：无              → 留空 / 占位样式
```

**二级是关键优化**：第二次启动时用上次的真实数据填充骨架，
用户几乎感知不到"加载中"。对列表 / 信息流场景效果极好。

**对照 Lynx**：官方也建议"提前在宿主平台准备首屏数据以省掉一次往返" [citation:11]，
并提供 `initData` / `useInitData()` 从宿主取预置数据 [citation:2]。
我们的"缓存值"是同一思路，但**自动化程度更高**（不需开发者手写 `initData`）。

### 2.4 骨架的两种载体（决策①的落地）

| 载体 | 时机 | 优点 | 缺点 | 角色 |
|---|---|---|---|---|
| **编译进 App 二进制** | 启动即渲染 | **零 IO、零网络、最稳** | 不可动态更新 | **兜底** |
| **随产物下发** | 产物下载后 | 可动态更新 | 需 IO / 网络 | **常态** |

**组合时序**：

```
壳启动 + proteus_prewarm()
   → 加载二进制内置骨架 → 骨架上屏          ← 兜底，立即
   → 并行下载 / 读取产物
   → 产物就绪 → 切换到真实产物              ← 常态
   → 网络数据到达 → 槽位填充
```

### 2.5 骨架 → 真实产物的切换一致性

**必须避免闪烁 / 跳变**。三条规则：

1. **骨架的静态结构必须与产物一致**（同一份 LayoutTemplate 生成，不手写）
2. **切换只填槽位，不重建结构**
3. **若产物版本与骨架不兼容**（版本协商失败），保留骨架 + 提示，不得白屏

## 3. 与 `proteus_prewarm()` 的组合

Host ABI 方案 §8.5 已定义预热接口（参照 Flutter Add-to-App 的已知问题：
引擎初始化约 100–200ms，不预热会白屏闪烁）。

**完整时序**：

```
App 启动（Application.onCreate / didFinishLaunchingWithOptions）
  → proteus_prewarm()            内核初始化（后台或启动阶段）
  → 加载编译进二进制的首屏骨架    零 IO
  → 骨架上屏                     ← 用户此时已看到内容
  → 网络数据到达 → 槽位填充
```

**★ 对 Playground 尤其重要**：扫码后必然有网络下载，
那段等待正是白屏高发期——**而这也正是 Lynx 承认 IFR 失效的场景 2**（§0.3）。
骨架方案正好把它完全盖住。

## 4. 关键设计约束

### 4.1 骨架必须是编译期产物，不得手写

与 `LayoutTemplate` 同源生成，保证结构一致。
开发者手写骨架会导致与真实产物漂移——这是最容易埋的坑。

### 4.2 骨架体积必须受控

内置进二进制的部分要有体积预算：

| 约束 | 说明 |
|---|---|
| 只含首屏可见区域 | 不含全部页面 |
| 静态资源（图片）用占位符 | 不进二进制 |
| 体积上限 | 需在 M0 实测后设定，纳入体积棘轮 |

### 4.3 阻塞主线程的前提是"足够快"

Lynx 敢阻塞主线程，是因为它快到用户感知不到 [citation:13]。
**Proteus 采用同样策略的前提是首帧在预算内**：

| 预算 | 值 |
|---|---|
| 首帧总耗时（阻塞窗口） | 建议 ≤ 50ms |
| 若超时 | **不得阻塞**，改为异步渲染 + 骨架 |

**这条必须实测决定，不能假设。**

### 4.4 缓存失效

模板缓存必须建立在**版本完全匹配**的基础上——
产物版本 / IR 版本任一变更，旧缓存立即失效。
（业界经验：模板缓存若版本不匹配会导致难查的渲染错误 [citation:17]）

## 8. 给实现 LLM 的执行指令

1. **FS0 拆解未完成前，禁止开始 FS1。** 不知道白屏花在哪就优化，等于瞎猜。
2. **骨架必须与 `LayoutTemplate` 同源生成**，禁止手写。
3. **骨架 → 产物切换只填槽位，不得重建结构**；出现闪烁视为未完成。
4. **必须提供二进制内置骨架作为兜底**，不得只做随产物下发。
5. **缓存占位值必须版本匹配才命中**，版本变更立即失效。
6. **阻塞主线程策略必须先实测首帧耗时**，超 50ms 改为异步 + 骨架。
7. **敏感槽位值不得进缓存**。
8. **不得宣称"消除网络等待"**——骨架是盖住它，不是消除它。
9. **Playground 扫码场景必须单独验证**，它是白屏风险最高的场景。
10. 骨架体积纳入**体积棘轮门禁**，防止无节制增长。

## 附：关键事实依据

- Lynx IFR：页面加载时直接展示内容，无白屏或中间状态；主线程 bundle 携带运行时与应用代码，在 `loadTemplate` 期间同步渲染，后台线程并行启动；首屏在任何后台 JS 执行前出现 [citation:2][citation:18]
- Lynx 官方明确 IFR 失效的两种情况：**Bundle 无法同步加载**（异步文件 I/O）；**主要内容需异步加载**（网络请求）[citation:2][citation:18]
- Lynx 的做法依据可用性研究：**若渲染足够快，就不需要任何中间反馈**；通过短暂阻塞主线程直至首帧完整渲染来消除白屏 [citation:13][citation:16]
- Lynx Element Templates：编译器把静态子树折叠为一条 `INSTANTIATE_TEMPLATE` op，动态文本/class/样式/属性成为 holes 经 `SET_*` ops 更新；准入条件为结构编译期已知、每节点为普通元素、仅属性值或文本动态；组件/slot/`v-if`/`v-for` 宿主仍走普通路径 [citation:5]
- Lynx hydration：两线程以相同初始数据执行同一应用；主线程记录所应用的 ops batch，后台初始 batch 与之对账——相同 batch 跳过，文本/样式/属性差异就地 patch，**结构差异则移除首屏树重建**并告警 [citation:5]
- Lynx 建议"提前在宿主平台准备首屏数据以省掉一次往返"；提供 `initData` / `useInitData()` 从宿主取预置数据 [citation:11][citation:2]
