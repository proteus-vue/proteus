# iOS 渲染路线假设验证报告（开工前）

> **本文回答**：`docs/Proteus_App端高性能渲染落地方案.md` 押在 iOS 侧的几条关键假设，
> **哪些成立、哪些不成立、哪些无法在本机验证**——把文档 §附 的未核实外部数字，换成本机可复跑的实测基线。

## 0. 结论速览

| # | 文档主张 | 实测结论 | 证据强度 |
|---|---|---|---|
| **H1** | 跳过 UIView 直接用 CALayer 更快 | ✅ **成立**（UIView 层占该路线总收益的 **51%**） | 强（4 次重跑，方差可控） |
| **H2** | AutoLayout CPU 随视图数**指数级**上升 | ⚠️ **结论成立、理由不成立**：实测是**线性**（每项成本恒定），但绝对代价确实大（占 **49%**） | 强（80→1600 项曲线平坦） |
| **H3** | UILabel 30 FPS vs CATextLayer 58 FPS | 🟡 **方向一致，但没验到同一件事**：我测的是批量创建+布局（1.4× 差距），不是滚动 FPS | 中（测的不是 FPS） |

| **H5** | 文本度量「可缓存」（未给量级） | ✅ **强收益**：**38–49×** 加速 | 强（4 次重跑一致） |

## 1. 实验设计（严格复刻文档 §9.2 的 4050 元素定义）

| 项 | 规格 |
|---|---|
| 元素数 | **4050**（2000 view + 2000 text + 50 行容器），40 列 × 50 行 |
| 尺寸 | view **不设宽高**，由内部文字撑开 → 完整走测量/布局/绘制 |
| 计时 | 三段：`build`（建树）/ `layout`（度量+定位）/ `commit`（提交渲染进程） |
| 路线 | **A** UIView+AutoLayout（原生基线）· **B** UIView+手算 frame · **C** CALayer+手算 frame |
| 重复 | 每路线 5 次取中位；**整套实验重跑 4 次**（评估跑间方差） |
| 文本 | 50 条不同文案循环（避免重复文案掩盖度量成本） |

**变量控制**：同一 host、同一份结构定义、同一组文本；A→B 只改「布局方式」，B→C 只改「节点类型」——
使收益可**归因分解**（见 §2.1）。

## 2. 实测结果

### 2.1 H1 + H2：三条路线对打（4050 元素，中位）

| 路线 | build | layout | commit | **total** |
|---|---|---|---|---|
| A UIView + AutoLayout | 346.2 | 246.2 | 7.2 | **651.3 ms** |
| B UIView + 手算 frame | 0.0 | 196.1 | 264.2 | **465.7 ms** |
| C CALayer + 手算 frame | 0.0 | 24.9 | 240.8 | **272.2 ms** |

（4 次重跑：A 600.8/679.1/884.8/623.5 · B 467.7/463.7/781.9/404.8 · C 273.0/259.4/271.5/372.8）

**归因分解**（这是本报告最有价值的数字）：

```
A 651.3ms ──[省 185.6ms]──> B 465.7ms ──[省 193.4ms]──> C 272.2ms
                ↑                                          ↑
         AutoLayout 的代价                        UIView 层的代价
         （占 C 路线总收益 49%）                  （占 C 路线总收益 51%）
```

**⇒ CALayer 路线比原生 AutoLayout 基线快 2.4×（省 58%）**，且**两个因素各占一半**——
文档强调「必须绕开 AutoLayout」是对的，但**「跳过 UIView」的收益与它相当**，不应被当作次要项。

### 2.2 H2 细查：AutoLayout 是线性，不是指数级

| 元素数 | AutoLayout 每项 | 手算每项 | 比值 |
|---|---|---|---|
| 80 | 396 μs/item | 244 μs/item | 1.6× |
| 400 | 384 μs/item | 247 μs/item | 1.6× |
| 800 | 527 μs/item | 219 μs/item | 2.4× |
| 1600 | 358 μs/item | 259 μs/item | 1.4× |

**每项成本基本恒定**（358–527 μs，无系统性上升）⇒ **线性复杂度**，不是文档说的「指数级上升」。
结论「必须绕开 AutoLayout」**仍然成立**（绝对代价 ~1.6×），但理由要改成「**线性但系数高**」。

> 为什么值得较真：如果真是指数级，那「视图数 > N 就必须换方案」；线性则意味着
> **小列表用 AutoLayout 是可以接受的**——这直接改变 M4 的取舍边界（不是全盘禁用，而是规模阈值）。

### 2.3 H3：文本通道（1000 节点，中位）

| 通道 | 耗时 | 相对 |
|---|---|---|
| CATextLayer | **168.3 ms** | 1.0× |
| UILabel | **238.7 ms** | 1.42× |

**方向与文档一致**（CATextLayer 更轻），但**测的不是同一件事**：
文档给的是长列表滚动 FPS（30 vs 58），本实验测的是**批量创建 + 布局**耗时。
⇒ 「CATextLayer 更适合大量文本节点」有本机证据支持；**「58 FPS」这个数字本报告不作背书**。

### 2.4 H4：layer tree 深度 —— **本机无法验证**

| 深度 | commit 耗时 |
|---|---|
| 1（2000 个平铺） | 5.44 ms |
| 10 | 4.25 ms |
| 50 | 3.95 ms |
| 100（20 条链） | 3.81 ms |

**深度对 commit 无影响，甚至方向相反（越深越快）** ⇒ 这不是「结论」，而是**测量无效**：

- **模拟器的 Render Server 与 App 同进程**（真机是 IPC 到 `backboardd`）→ 提交成本结构完全不同；
- 且同一轮内多次 commit 会命中各种缓存。

⇒ **H4 必须真机验证**（Instruments 的 Core Animation + 真机 IPC 才能看出）。
**在真机数据之前，不应把「拍平是刚需」写进架构约束**——它可能对（官方文档确实说 commit 递归），
但我们**没有自己的证据**。

### 2.5 H5：文本度量缓存 —— 最强收益项

| 场景 | 2000 次度量 | 加速 |
|---|---|---|
| 无缓存 | 87.1 ms | — |
| 有缓存（50 条不同文案） | **2.26 ms** | **38–49×** |

（4 次重跑：39×/39×/49×/38×）

**⇒ 度量缓存是「成本极低、收益极高」的优化**，且实现简单（key = 文本 hash + 字体 + 宽度约束，
与文档 §5.3 一致）。**建议提到 M1 首批实现**，而不是留到 M3 优化阶段。

## 3. 实验自身的三个缺陷（诚实记录）

做这轮验证时我自己踩了三个坑，它们**都曾产出看似合理但实际错误的数据**：

| # | 缺陷 | 造出的假象 | 修法 |
|---|---|---|---|
| 1 | **游离视图**：每个实验各自 `UIView(frame:)` 但**从未加入窗口层级** | 屏幕全黑；exp4 出现「越深越快」的反常数据（游离 layer 不产生真实提交） | 全局 `visibleHost` 挂到 vc.view，所有实验复用 |
| 2 | **主线程死锁**：`DispatchSemaphore.wait` 等 `CATransaction.setCompletionBlock` | 表现为「进程活着但永不落盘」，差点误判为「实验太慢」 | 改用 `CATransaction.flush()` 同步提交 |
| 3 | **轮询读到残留文件**：App 重启后 Documents 里上一轮报告还在 | 三次「重跑」数字完全一致（不可能），差点当成「方差为零」 | 每次重跑前先删报告文件 |

> **教训（已验证两次的模式）**：性能实验的**假数据比没数据更危险**——
> 「越深越快」「方差为零」这类信号，第一反应该是**怀疑测量**，不是接受结论。
> 这与本仓既有的「破坏性验证」纪律同源：**先证明测量能反映真实，再相信测量结果**。

## 4. 对落地方案的影响（可执行结论）

| 文档位置 | 原表述 | 本报告的建议 |
|---|---|---|
| §6.2 / 坑位 #6 | 「AutoLayout CPU 消耗**指数级**上升」 | 改为「**线性但系数高**（实测 ~1.6×/项）」；
随之**不要全盘禁用**，而是定规模阈值（本项目 4050 元素下 AutoLayout 651ms 不可接受） |
| §6.2「跳过 UIView」 | 与「绕开 AutoLayout」并列提及 | **提升优先级**：实测两者收益各占一半（51% : 49%） |
| §附（UILabel 30 vs CATextLayer 58 FPS） | 外部数字 | 保留但标注「**未在本机验证**」；本机可验证的是**批量创建 1.42× 差距** |
| §6.2 / 坑位 #7（commit 递归、拍平刚需） | 作为架构约束 | **降级为待验证假设**：模拟器测不出，需真机 Instruments 验证。**在拿到真机数据前，拍平按「可能有益」实现，不作为架构硬约束** |
| §5.3（度量可缓存） | 列为 M1 模块之一 | **提升到首批实现**（38–49×，成本极低） |
| §附 ArkUI/UIKit 对比数字 | 外部未核实 | 本报告不背书；如需引用**必须补来源** |

## 5. 未完成 / 需真机（下一轮）

| 项 | 为什么本机做不了 | 建议做法 |
|---|---|---|
| **H4 真机 commit 成本** | 模拟器 Render Server 同进程 | 真机 + Instruments（Core Animation 模板），对比 layer 深度 1 vs 100 |
| **H3 滚动 FPS** | 需持续滚动 + 真机渲染负载 | 真机长列表滚动，用 CADisplayLink 统计丢帧率 |
| **离屏渲染**（文档坑位 #5） | 需真机 GPU 计数器 | Instruments 的 Color Offscreen-Rendered |
| **内存占用**（文档 §9.2 验收项） | 模拟器内存结构不同 | 真机 + Instruments Allocations |
| **Android 侧对应验证** | 本机工具链就绪但缺系统镜像 | 补镜像后复刻本实验（Canvas/DisplayList 路线） |
