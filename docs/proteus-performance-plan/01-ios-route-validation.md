## 1. 实验设计（严格复刻文档 §9.2 的 4050 元素定义）

| 项 | 规格 |
|---|---|
| 元素数 | **4050**（2000 view + 2000 text + 50 行容器），40 列 × 50 行 |
| 尺寸 | view **不设宽高**，由内部文字撑开 → 完整走测量/布局/绘制 |
| 计时 | 三段：`build`（建树）/ `layout`（度量+定位）/ `commit`（提交渲染进程） |
| 路线 | **A** UIView+AutoLayout（原生基线）· **B** UIView+手算 frame · **C** CALayer+手算 frame |
| 重复 | 每路线 5 次取中位；**模拟器重跑 4 次 / 真机重跑 3 次**（评估跑间方差） |
| 环境 | ① 模拟器（iOS 27，402×874@3x）② **真机 iPhone 12 / iOS 26.3**（`device/` 变体，加 os_signpost） |
| 文本 | 50 条不同文案循环（避免重复文案掩盖度量成本） |

**变量控制**：同一 host、同一份结构定义、同一组文本；A→B 只改「布局方式」，B→C 只改「节点类型」——
使收益可**归因分解**（见 §2.1）。

## 2. 实测结果

### 2.1 H1 + H2：三条路线对打（4050 元素）— 模拟器 vs 真机

| 路线 | 模拟器（4 次中位） | **真机 iPhone 12（3 次中位）** | 真机各轮 |
|---|---|---|---|
| A UIView + AutoLayout | 651.3 ms | **547.7 ms** | [547.7, 556.0, 547.7] |
| B UIView + 手算 frame | 465.7 ms | **381.0 ms** | [381.0, 373.2, 381.0] |
| C CALayer + 手算 frame | 272.2 ms | **197.6 ms** | [197.6, 189.5, 197.6] |

**归因分解（真机）**：

```
A 548ms ──[省 167ms]──> B 381ms ──[省 183ms]──> C 198ms
                  ↑                                        ↑
           AutoLayout 的代价                        UIView 层的代价
```

**⇒ 真机 CALayer 路线比 AutoLayout 基线快 2.8×（省 64%）**，
两个因素各占约一半（与模拟器结论一致，**真机复现了同一模式**）。

★**真机 vs 模拟器的两点差异（重要）**：
1. **真机更快**（A 548 vs 651 · B 381 vs 466 · C 198 vs 272 ms，快 15–30%）——模拟器跑在 Mac 的
   共享 CPU 上且有额外转换层，真机是原生执行。
2. **真机方差小得多**（C 路线 197.6/189.5/197.6，波动 <5%；模拟器 273/259/272/373，波动 37%）
   ⇒ **做性能决策应优先信真机数据**；模拟器只适合快速探路。

### 2.2 H2 细查：AutoLayout 是线性，不是指数级

| 元素数 | AutoLayout 每项 | 手算每项 | 比值 |
|---|---|---|---|
| 80 | 396 μs/item | 244 μs/item | 1.6× |
| 400 | 384 μs/item | 247 μs/item | 1.6× |
| 800 | 527 μs/item | 219 μs/item | 2.4× |
| 1600 | 358 μs/item | 259 μs/item | 1.4× |

**每项成本基本恒定**（358–527 μs，无系统性上升）⇒ **线性复杂度**，不是文档说的「指数级上升」。
结论「必须绕开 AutoLayout」**仍然成立**（绝对代价 ~1.6×），但理由要改成「**线性但系数高**」。

> 为什么值得较真：如果真是指数级，那「视图数 > N 就必须换方案」；线性则意味着
> **小列表用 AutoLayout 是可以接受的**——这直接改变 M4 的取舍边界（不是全盘禁用，而是规模阈值）。

### 2.3 H3：文本通道（1000 节点，中位）

| 通道 | 耗时 | 相对 |
|---|---|---|
| CATextLayer | **168.3 ms** | 1.0× |
| UILabel | **238.7 ms** | 1.42× |

**方向与文档一致**（CATextLayer 更轻），但**测的不是同一件事**：
文档给的是长列表滚动 FPS（30 vs 58），本实验测的是**批量创建 + 布局**耗时。
⇒ 「CATextLayer 更适合大量文本节点」有本机证据支持；**「58 FPS」这个数字本报告不作背书**。

### 2.4 H4：layer tree 深度 vs commit —— **真机证伪**（原假设为「拍平是刚需」）

**第一步（原 exp4）**：固定总数 2000、只变深度 → 深度无明显影响。但这**区分不了两种假设**：

> 成本由「深度」决定 vs 由「节点总数」决定——原设计对后者无对照，故不足以定论。

**第二步（补测 exp6，二维对照）**：总数 {500, 2000, 5000} × 深度 {1, 20}：

| 总数 | 深度 1 | 深度 20 | 深度效应 |
|---|---|---|---|
| 500 | 0.76 ms | 0.63 ms | **−17%** |
| 2000 | 2.99 ms | 2.64 ms | **−12%** |
| 5000 | 7.37 ms | 6.19 ms | **−16%** |

| 深度 | 总数 500 | 总数 5000 | 总数效应 |
|---|---|---|---|
| 1 | 0.76 ms | 7.37 ms | **+870%** |
| 20 | 0.63 ms | 6.19 ms | **+883%** |

**⇒ 结论：commit 成本由「节点总数」决定（+870%），与「layer tree 深度」无关（−12~17%，反而略降）。**

**这推翻了方案文档 H4「commit 递归 → 拍平是刚需」**：
- 拍平**仍然有益**（减少节点总数 → 直接减少 commit 成本），但**理由不同**：
  不是「降低树深度」，而是**「减少节点数量」**；
- ⇒ D4（拍平）应作为**减少节点数的手段**实现与验收（度量口径：宿主视图数），
  **不应**以「保持 layer tree 扁平」作为架构约束；
- 真机各深度实测：3.03ms（深度1）→ 2.41ms（深度100）。

> **诚实边界**：本结论基于「同数量节点、不同深度」的对照，覆盖 500–5000 节点、深度 1–20。
> 未测**极端深度**（如 >1000 层）与**含 CALayer 层级**的场景——理论上极深树会有栈/递归风险，
> 但那属于「防崩溃」而非「性能」问题。

### 2.5 H5：文本度量缓存 —— 最强收益项

| 场景 | 2000 次度量 | 加速 |
|---|---|---|
| 无缓存 | 87.1 ms | — |
| 有缓存（50 条不同文案） | **2.26 ms** | **38–49×** |

（4 次重跑：39×/39×/49×/38×）

**真机**：32.1×（各轮 [32.1, 37.3, 32.1]）——与模拟器 38–49× 同量级。

**⇒ 度量缓存是「成本极低、收益极高」的优化**，且实现简单（key = 文本 hash + 字体 + 宽度约束，
与文档 §5.3 一致）。**建议提到 M1 首批实现**，而不是留到 M3 优化阶段。

## 3. 实验自身的三个缺陷（诚实记录）

做这轮验证时我自己踩了三个坑，它们**都曾产出看似合理但实际错误的数据**：

| # | 缺陷 | 造出的假象 | 修法 |
|---|---|---|---|
| 1 | **游离视图**：每个实验各自 `UIView(frame:)` 但**从未加入窗口层级** | 屏幕全黑；exp4 出现「越深越快」的反常数据（游离 layer 不产生真实提交） | 全局 `visibleHost` 挂到 vc.view，所有实验复用 |
| 2 | **主线程死锁**：`DispatchSemaphore.wait` 等 `CATransaction.setCompletionBlock` | 表现为「进程活着但永不落盘」，差点误判为「实验太慢」 | 改用 `CATransaction.flush()` 同步提交 |
| 3 | **轮询读到残留文件**：App 重启后 Documents 里上一轮报告还在 | 三次「重跑」数字完全一致（不可能），差点当成「方差为零」 | 每次重跑前先删报告文件 |

> **教训（已验证两次的模式）**：性能实验的**假数据比没数据更危险**——
> 「越深越快」「方差为零」这类信号，第一反应该是**怀疑测量**，不是接受结论。
> 这与本仓既有的「破坏性验证」纪律同源：**先证明测量能反映真实，再相信测量结果**。
