## 1. 为什么用真项目而不是合成样本

本仓纪律：**别用假数据自证**。合成样本（如上一轮 bench 用的"单文件 SFC"）会漏掉真实代码形状
带来的成本：语义标签密度、slot 嵌套、scss 变量、长模板、分包引用。

**载体 = `showcase/`**：真项目、有 121 个页面级文件、含 subpackages 分包、覆盖两端产物。
⇒ 这是本仓现有的、最接近"上百页面级超级应用"的样本。

**诚实边界**（读数字前必须知道）：
1. **绝对毫秒不跨机可比** —— 本仓既有认识（`scripts/benchmark.ts` 注释原文：
   "绝对耗时跨环境/Node 不可比（实测基线代码在异构 CI 同机即 1.6x）"）⇒ 基线判据**以比值为主**
   （体积膨胀比是机器无关的），绝对耗时只作 **3× 宽松上界**（防"真的慢到离谱"，不做精确对标）。
2. 这里测的是 **Proteus 编译器**（SFC → 小程序产物）的**纯编译耗时**，**不含**
   Vite 打包 / Babel 转译 / 依赖预构建 —— 那是构建链的其它段。
3. 读数为**单进程串行**；真实构建是 Vite 多模块并行 ⇒ 只作**编译器单核成本的上界估计**。
4. 跳过 1 个文件并**标注原因**（不静默）：`showcase/router/RouterView.vue` 的产物含
   `import.meta`，纯编译模式下 `assertValidResult` 的语法校验会拒（真构建里由 Vite 处理该语法）。

## 2. 四类读数

### 2.1 全量编译

| 项 | 冷（首遍） | 热（次遍） |
|---|---|---|
| 总耗时 | 645.8 ms | **346.4 ms** |
| 每文件 | 5.01 ms | **2.71 ms** |
| 吞吐 | 928 KB/s | **1730 KB/s** |

★冷/热差 **1.86×** ⇒ **V8 JIT 预热是真实成本项**：冷启动（一次构建 = 一次冷启动）
付的是 5.01 ms/文件 而非 2.71。**这是构建链优化的第一个着力点**（见 §4.1）。

### 2.2 增量编译

单文件改一处 → 重编译（取真项目最大文件 12.5 KB）：**中位 5.06 ms**。

★与冷全量对比：增量给单文件的预算是 **5ms 级**（热路径 JIT 已在）
⇒ 改一个文件 ≈ 全量的 1/68（346/5.06），符合"增量只重编译受影响文件"的预期。

**诚实边界**：本仓编译器**无跨文件缓存**（每次调用是独立的 SFC → 产物）；
真实"增量"在 **Vite 层**（模块失效 + 该文件重编译）。本读数测的是**单文件重编译**这一项，
不含 Vite 的模块图扫描与 HMR 传输。

### 2.3 产物体积

| 项 | 值 |
|---|---|
| 产物（wxml + js + wxss） | 890.3 KB |
| 源码 | 599.2 KB |
| **膨胀比** | **1.486x** |

★膨胀比是**机器无关**的 ⇒ 被选为基线门禁的主判据（阈值：> 基线 × 1.15 即红）。

### 2.4 瓶颈识别（★卡明确要求的一项）

**按阶段**（编译产物 trace 事件数）：

| 阶段 | 事件数 | 占比 |
|---|---|---|
| **template** | **6154** | **72.3%** |
| script | 1628 | 19.1% |
| style | 736 | 8.6% |

**最热规则 top 6**（真项目里触发次数）：

| 次数 | 规则 | 说明 |
|---|---|---|
| **1727** | `tag/unknown-kebab` | 未知 kebab 标签归一（★最高——本仓 `<p-*>` 语义标签密度大） |
| **1623** | `template/scope-attr` | 作用域属性注入（每元素一次） |
| **1385** | `directive/v-bind` | 动态绑定转换 |
| 681 | `script/const-to-data` | `const` → `data` 提升 |
| 526 | `component/root-class` | 根类注入 |
| 354 | `slot/named-template` | 具名插槽模板化 |

**最慢文件 top 5**：

| 耗时 | 源码 | 文件 |
|---|---|---|
| 9.2ms | 12.5KB | `subpackages/components/pages/p-scroll-view.vue` |
| 7.8ms | 8.5KB | `subpackages/components/pages/p-checkbox.vue` |
| 7.1ms | 4.1KB | `pages/backends.vue` ← **4.1KB 却 7.1ms**（成本/字节异常高，见 §4.2） |
| 6.7ms | 10KB | `subpackages/components/pages/p-input.vue` |
| 6.5ms | 8.2KB | `subpackages/components/pages/p-draggable.vue` |

## 3. 瓶颈清单（按可优化性排序）

| # | 瓶颈 | 证据 | 可能的优化方向 | 风险 |
|---|---|---|---|---|
| **B1** | **冷启动成本**（JIT 预热） | 冷 645.8ms vs 热 346.4ms（**1.86×**） | ① 构建常驻进程（watch 模式下天然缓解）② 减少启动期一次性工作 | 低（watch 场景已缓解） |
| **B2** | **模板阶段占 72%** | template 6154 事件 / script 1628 / style 736 | 模板转换是热点 ⇒ 规则级优化收益最大（如 `scope-attr` 每元素必跑） | 中（改模板转换风险高于脚本） |
| **B3** | **`tag/unknown-kebab` 1727 次** | 真项目 `<p-*>` 标签密度大 | 未知标签归一可否**缓存/短路**（同一标签名结果必然相同） | 低（纯查表语义） |
| **B4** | **`pages/backends.vue` 成本/字节异常** | 4.1KB 却 7.1ms（而 12.5KB 才 9.2ms） | 需先归因（可能是特定语法触发重路径，如大对象字面量 / 深层嵌套） | 低（先测量再定） |
| **B5** | **体积膨胀比 1.486x** | 产物/源码 | 小程序产物有固定开销（wxml/js/wxss 三份 + 运行时代码），需判断是否有冗余 | 中（需与其它框架对标才有意义） |

★**本卡不做的**（诚实边界）：以上都是**瓶颈识别**，**不含优化实施**——
卡 C3 的验收是"有基线数据 + 识别并列出瓶颈"，优化属后续独立课题（避免"边测边改"污染基线）。

## 4. 门禁设计（防静默劣化）

`pnpm check:compile-baseline` 与 `benchmarks/compile-baseline.json` 比对：

| 判据 | 阈值 | 为什么 |
|---|---|---|
| **体积膨胀比** | > 基线 × 1.15 | ★**机器无关** ⇒ 主判据 |
| 文件数变化 | ≠ 基线 | 目标项目变了 ⇒ 基线需**重设**（不是回归）——避免"样本变了却怪编译器" |
| 全量热编译 | > 基线 × 3 | 宽松上界（绝对耗时跨机不可比） |
| 增量中位 | > 基线 × 3 | 同上 |

**★破坏性验证过**：把基线 `sizeRatio` 篡改为 0.5 ⇒ `--check` 立刻红并准确报
"体积膨胀比 1.486 > 基线 0.5 × 1.15"（exit 1）；还原后绿。

**为什么归 LOCAL_ONLY 不接 CI**：绝对耗时在 CI 共享 runner 上波动会产生**噪声红**
（本仓已有 T4/V11 两次实测教训：CI 比本机慢 14×、并行执行下比值 0.18~0.76）。
⇒ 本门禁面向**开发机**（改编译器后本地跑）；`check:gates-sync` 已登记理由。

## 5. 与卡 C1（NativeBackend）的关系

卡 C3 的验收之一是"识别并列出编译性能瓶颈"。上面的清单**直接回答**了"编译期是否成为瓶颈"：

- **是**（有数据）：模板阶段占 72%，`tag/unknown-kebab` 单条规则 1727 次调用；
- **当前可接受**：128 文件全量热编译 346ms ⇒ 按线性外推，**1000 页面级文件约 2.7 秒**，
  小于典型 CI 构建预算（本仓既有构建含 Vite 打包在 10 秒级以上）；
- ⇒ **C1 不必先做编译期优化**（风险低），可先落 NativeBackend 的地基；
  编译期优化作为独立课题，用本基线做前后对比。

## 6. 复算方式

```bash
npx tsx scripts/bench-compile.mjs            # 人读基线
npx tsx scripts/bench-compile.mjs --json     # JSON（CI/工具消费）
npx tsx scripts/bench-compile.mjs --check    # 与基线比对（回归即红）
npx tsx scripts/bench-compile.mjs --update   # 写回基线（★人工确认后）
```
