## 0. 结论速览

| 维度 | 方案 A（内核持度量） | 方案 B（平台参与排版） |
|---|---|---|
| 指令流是否自包含 | ✅（携带已定几何） | ❌（平台需回头查节点/回调） |
| 平台层职责 | **只光栅化** | 排版 + 光栅化 |
| 三端一致性 | ✅ 几何由**同一份内核**算出 | ❌ 各端排版差异直接体现为几何差异 |
| golden 可比性 | ✅ 指令流是纯数据，可逐字节对拍 | ❌ 度量在平台内，无法在本仓对拍 |
| 增量更新 | ✅ 度量变化只发尺寸补丁 | ⚠ 需平台重排回流 |
| 代价 | 平台必须能"只度量"（CoreText/StaticLayout 均可） | 看似省事，代价在上行 |

**决策：方案 A。** 决定性理由见 §2。

## 1. 背景：本卡要解决的分歧

任务卡 I4 的原文分歧：

- **方案 A**：绘制文本指令 + **内核已度量**几何（平台层只管画，最薄）
- **方案 B**：文本节点 + 测量回调（平台层参与排版）

卡建议选 A（"这是唯一能把平台层压到最薄的选择。文本是唯一无法完全平台无关的一块"）。

**本次落地的验证方式**：不看设计文档怎么写的，而是查**现有实现实际走了哪条**，并补齐缺的判据。

## 2. 决定性理由（**已由现有实现与实测数据支持**，非纸面论证）

### 2.1 现有实现**本来就是方案 A**（本次核实的结论）

| 证据 | 位置 |
|---|---|
| 内核持有平台注入的度量：`TextMeasurer` trait + `TableTextMeasurer` | `packages/layout-core-rust/src/engine.rs` |
| 度量在**内核**参与几何求解（taffy measure 回调内转调注入的 measurer） | `packages/layout-core-rust/src/taffy_engine.rs` |
| 指令流携带**已度量完成的几何**：`RenderCmd` 的 x/y/width/height 即最终几何 | `packages/layout-core/src/render-cmd.ts` |
| 平台层**只读指令**绘制（Android `Canvas.drawText` / iOS `CTLine`），不做排版 | `hosts/android/.../ProteusHostView.java` · `hosts/ios/ProteusHost/selfdraw-scene.swift` |

⇒ 本卡要的"定案"不是**选型**（实现已选 A），而是把选择**写成可追溯的决策**（本文件）+ 补齐**被判据覆盖的空白**（§3）。

### 2.2 为什么 B 不可行（三条否决性理由）

1. **指令流不再自包含** ⇒ "平台顺序消费纯数据"这一架构红利消失（本仓 `render-cmd.ts` 文件头的核心设计）；
2. **三端一致性失去保障**：iOS CoreText 与 Android StaticLayout 的断行/字距算法不同，几何会**天然分叉**；
   而方案 A 下两者只影响"度量输入"，几何由同一份内核算出 ⇒ 差异被限制在**一个可对拍的接口**上；
3. **golden 无法对拍**：本仓已有"浏览器真值 → Rust 内核"的对拍通道（`browser-layout.json`）；
   B 方案下度量发生在平台内，这条通道**在结构上不可用**。

### 2.3 方案 A 的代价（诚实记录）

- 平台**必须**能提供"只度量不绘制"的能力。三端均有：CoreText（`CTLine` 排版）+ `boundingRect` ·
  Android `StaticLayout`/`Paint.measureText` · Web 用浏览器自身排版测量。
- 度量是**最贵的一步**（文本 shaping）⇒ 必须记忆化。本仓已有：按
  `(文本 hash, 字体签名, 最大宽)` 内容寻址缓存（`measure_key`），实测"二帧 0 次向平台要度量"。

## 3. 本次补齐的判据（卡 I4 的两条未达标项）

### 3.1 「文本度量进 conformance」（原：21 用例里 textMeasures 全为空表）

**核实后修正卡的信息**：原表并非"全为空" —— 实际有 **2/21** 条含真实浏览器度量
（`文本单行` / `文本纵向堆叠`，自 `a0ec5923` 起就在），且 `conformance_browser_layout`
对**每个用例**都注入了 measurer（`to_measurer(case)`）⇒ 这两条的几何**确实被真值对拍**。

**但覆盖确实太薄**（2/21，且都未触及最容易错的收缩路径）。本次补 **4 条**：

| 新用例 | 覆盖的失败形态 |
|---|---|
| 文本超宽收缩（度量须按 maxWidth 夹取） | 内核忘了用 maxWidth ⇒ 文本撑破容器 |
| **文本与定宽兄弟同行（flexShrink 参与）** | 文本作为**可收缩项**参与行内分配 |
| 嵌套容器的文本撑开（高度向两级祖先传播） | 高度撑开的**多级传播** |
| 文本框（度量 + 背景 + 边框共存） | 绘制属性**干扰**度量 |

⇒ 用**真实 Chromium** 重跑生成 golden：**25 用例 / 6 条含文本度量**。

### 3.2 ★★补覆盖当场抓到一个**真缺陷**（本卡最有价值的产出）

「文本与定宽兄弟同行」用例**第一次运行即失败**，且是引擎侧：

```
容器 260 装 [60, 文本(内容宽 182), 40]，gap 8
浏览器真值： 51.92 / 157.47 / 34.61   ← 按 flex-basis × flex-shrink 加权收缩（60:182:40）
引擎旧值：   37.00 / 182.00 / 25.00   ← 文本**当成不可收缩**，只压另两个（差 24.53dp）
```

**根因**：`taffy_engine.rs` 把「未显式指定 min-width/min-height」映射为 `auto()`
⇒ taffy 应用 CSS 的 **`min-width: auto` 规则**（flex 项不允许收缩到内容以下）。
而本仓的**既定模型**明确是「与 RN 一致地**不建模**该规则，显式清零」（见
`tests/e2e-layout-core-pixel.test.ts` 文件头「已对齐的两处模型差异」之②，
且浏览器侧翻译**显式注入 `min-width:0; min-height:0`**）⇒ **实现与声明的模型相反**。

**修法**：引擎未指定 min ⇒ `length(0.0)`（与参考实现与浏览器 golden 口径一致）；
**max 保持 `auto()`**（无上限——清零会把所有节点压成 0，语义相反，故拆成两个函数）。
改后 `conformance_browser_layout` **96 节点全过**（原本最大偏差 24.53dp）。

★**为什么改引擎而不是改用例**：golden 是**浏览器实测真值**（独立事实源），
用它迁就引擎就是把真值改坏；且 TS 参考实现 `clampSize`（min undefined ⇒ 不夹取）
本来就等于"min 默认 0" ⇒ 改引擎让**三份实现口径统一**。

### 3.3 连带修正一处 fixture（并说明为何不是"迁就实现"）

修引擎后 `ffi::tests::text_style_key_enables_safe_content_addressing` 变红：
该用例把 **500 行文本塞进 4000 高的列**，此前靠 `min: auto` 撑着不被压缩；
清零后按模型**应当**压缩（500×19 > 4000）⇒ 断言（19/33）不再成立。

**处置**：给这些行加 `flexShrink: 0` —— 这是本仓**列表行的标准写法**
（`check-vapor-perf` 的基准树注释原文：「flexShrink:0 必填，否则行被压缩（本仓实测的基准树缺陷）」）。
该用例的目的是 **textStyleKey 内容寻址**（不同字号互不污染 + 同字号只量一次），
与"行是否可收缩"无关；不写 flexShrink 会把断言从"度量是否正确"偷换成"收缩分配是否恰好"。

## 4. 文本度量注入协议（三通道，均已实现且有判据）

| 通道 | 入口 | 判据 |
|---|---|---|
| ① 建树时注入 | `create` 请求的 `textMeasures` | `conformance_browser_layout`（6 条文本用例，浏览器真值）· `text_style_key_*` |
| ② 追加/更新 | `proteus_layout_set_text_measures` | `update_path_reports_text_updates_and_uses_new_measure`（★断言几何**真的变了**：高 57） |
| ③ 结构变更随行 | `splice` 请求的 `textMeasures` | `splice_insert_row_with_text_keeps_measure`（插入行的文本高 19 来自度量） |

**格式**：`{"<节点id>": {"width": W, "height": H}}`（id 字符串键——与 `create` 的 `textMeasures` 同形）。

## 5. 诚实边界（本决策**不**声称的）

1. **文本度量不由内核计算**：内核**不自研文本**（Profile §L4）——度量必须由平台注入。
   方案 A 保证的是"几何由内核算"，不是"文本由内核排版"。
2. **`min-width/height: auto` 不支持**（有意的模型选择，与 RN 一致）：
   需要该行为请显式写 `minWidth`。此前实现**误**应用了 auto（本次修正）。
3. **断行/换行尚未建模**：当前 measurer 返回**单次度量**（无 min-content/max-content 区分）。
   ⇒ 复杂换行（多行文本、`word-break` 等）的几何一致性**未验证**，属后续课题。
   本次抓到的收缩缺陷正源于此（浏览器有 min-content，我们只有 content size）。
4. **平台字体差异不消除**：三端字体族/字形宽度不同（本仓已实测：同文本三字族宽度
   197/208/193）⇒ 跨端"看起来不同"是**平台事实**，本决策只保证"给定同一度量，几何一致"。
