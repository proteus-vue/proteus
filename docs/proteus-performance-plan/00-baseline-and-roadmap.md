# Proteus 性能路线（App 端）

> **本文回答**：App 竖切跑通之后，往「极致高性能」走**该先修哪一段**——以及四家框架（Flutter / RN 新架构 /
> NativeScript-Vue / Lynx）的机制**哪些能借鉴、哪些不适用**。
> ★本文所有基线数字都是**在本仓 iOS 竖切链路上实测**的（真实 JavaScriptCore，脚本可复跑），
> 不引用别家 benchmark 外推。

---

## 0. 实测基线（2026-09-29，`hosts/ios/bench-bridge.swift`）

环境：macOS arm64 · 真实 JavaScriptCore（`JSContext`）· bundle = Vue 运行时 + render-backend + 入口。

### 0.1 启动成本（拆开看才知道该修什么）

| 项 | 中位数 | 说明 |
|---|---|---|
| `JSContext` 创建 | **0.46 ms** | 固定开销，非优化面 |
| **首次执行 bundle**（解析+编译+执行） | **24.40 ms** | 冷启动真实成本 |
| 重复执行（同 context，代码已编译） | **6.39 ms** | 纯执行 + Vue 运行时初始化 |
| **⇒ 解析 + 编译** | **18.01 ms（占 74%）** | ★**启动成本的大头** |

> **这张表改变优先级**：入门的直觉是「优化渲染」，但实测 74% 在**解析编译**——
> 与 Hermes 的思路一致（官方：字节码预编译使 TTI 改善 18–25%、iOS Mattermost 启动改善 ~40%）。

### 0.2 运行时成本（跨界调用）

| 场景 | 调用数 | 字节数 | 耗时 | 单次成本 |
|---|---|---|---|---|
| 当前演示页（9 视图） | 30 | 987 B | 5.68 ms | — |
| 合成列表 10 项 | 61 | 1.3 KB | 0.10 ms | 9.8 μs/项 |
| 合成列表 100 项 | 601 | 13.3 KB | 0.94 ms | 9.4 μs/项 |
| **合成列表 1000 项** | **6001** | 133.9 KB | **9.87 ms** | **9.9 μs/项** |
| ⇒ 单次跨界调用 | — | — | — | **≈ 1.64 μs** |
| 对照：1000 项「一次性传输」（仅构造上界） | 1 | 96.8 KB | 0.41 ms | — |

**读法**：
- 单次调用 1.64 μs 本身**不差**（RN 旧桥是序列化 + 异步，更贵）；
- 但**每个列表项要 6 次调用**（4 次跨界 + 2 次属性）→ 1000 项 = 6001 次 = **9.87 ms**，
  已经吃掉 60fps 一帧预算（16.7ms）的 59%，**而这还只是桥的成本，不含 UIKit 建视图**。
- ⇒ 真正的浪费在**调用次数**，不在单次成本——这正是批处理（G-40 B4）要解决的。

### 0.3 三个结构性缺口（实测 + 代码核实）

| # | 缺口 | 现状证据 | 影响 |
|---|---|---|---|
| **① 无批处理/帧调度** | SPI 声明了 `scheduleFrame?` / `flush?`（`render-backend/src/spi.ts:89-91`）但**全部未实现**；G-40 B4 设计了 `commitBatch` 从未落地 | 每次 `patchProp`/`setText` 立即跨界（实测 6 次/项） |
| **② 无视图扁平化** | 每个 `p-view` 都变成一个真实 UIView；无 flatten | RN 官方数据：Shadow Tree 600–1000 节点经 flatten 降到 **~200**（约砍 2/3 宿主视图）；iOS 上**建 UIView 比跨界调用贵得多** |
| **③ 无列表回收** | `SEMANTIC_NATIVE_MAPS` 已有 `layout.virtual-list → UICollectionView` 映射，但宿主侧没有 cell 复用实现 | NativeScript 官方原文：滚动中反复创建/销毁视图 "is **not performant at all**" |

## 1. 四家框架机制对照（可借鉴性分析）

### 1.1 横向对照

| 维度 | Flutter | RN 新架构 | NativeScript-Vue | Lynx |
|---|---|---|---|---|
| **桥接** | 无桥（Dart AOT → 机器码）；跨原生走 Channel（二进制序列化、主线程）或 FFI（无序列化） | **JSI：JS 直持 C++ 对象引用、同步、零序列化**；TurboModules 懒加载 | 构建期元数据 + 绑定；原生对象以 wrapper 暴露（**保引用同一性，无 JSON**）；大数组刻意不转换 | 双运行时：主线程 PrimJS（受限子集）↔ 后台 JSC，引擎内部交互 |
| **UI 实现** | **全自绘**（Impeller），绕开平台控件 | 原生视图（ViewGroup/UIView）+ C++ shadow 树 + flatten | **纯原生控件**（`NSVElement` 直接 new 原生 View） | 原生控件（`<view>`→UIView/`<text>`→UILabel） |
| **批处理/帧调度** | UI 线程 + raster 线程各 16ms 预算；RepaintBoundary 隔离重绘 + 光栅缓存 | **Render(JS 同步) → Commit(后台异步布局+晋升) → Mount(UI 线程同步 diff + 原子 mutation 批)**；flatten 在 diff 内免费完成 | 无提交管线：Vue renderer 直接操作原生视图 | 主线程负责首帧渲染（IFR 同步出帧）+ MTS 静态切分高频交互 |
| **性能数字（官方）** | 60/120fps 目标；Impeller 消除运行时 shader 编译（无数字） | Hermes TTI **+18–25%**、iOS Mattermost 启动 **+40%**/内存 **−18%**；Hades GC p99.9 **48ms**；0.76 Android 启动 −15ms | 自测 marshalling：字符串 **49ms** vs RN 186ms vs 原生 14ms；Node-API 包体 −50% | Web 迁移启动 **2–4×**；MTS 字节码加载 **4×** 于文本 |
| **主要代价** | 全自绘：包体/内存大、控件"非原生"、**嵌原生控件很贵**（hybrid composition 会把 raster 线程并入 platform 线程，"lower FPS and frame drops"） | 官方自己写明：**开新架构「不保证立即变快」**；仍留 JNI 挂载层 | **逐调用 marshalling 成本高**（同一语义在 Hermes/JSC 下慢 5–20×）；元数据驱动 → 启动/升级成本 | 双引擎语义漂移（官方警告"不要依赖任何运行时细节"）；benchmark 不透明 |

### 1.2 对本路线**可借鉴**（按性价比排序）

| 机制 | 来源 | 为什么适用 | 落地形态 |
|---|---|---|---|
| **① 批处理 + 帧调度** | RN Fabric（Mount 阶段原子批）| 我们实测 1000 项 = 6001 次调用；SPI 已预留 `scheduleFrame`/`flush` 位置，**零架构变更** | 实现 G-40 B4 的 `commitBatch`：JS 侧攒 mutation 列表 → 每帧一次跨界 |
| **② 视图扁平化** | RN（flatten 在 diff 内免费完成）| 我们**每个 p-view 一个 UIView**；原生建视图是本路线最大单项成本 | 在 Dispatcher 的 `toIRNode` 后加 flatten pass：纯布局节点（无样式/无事件/单子）合并到父 |
| **③ 列表回收** | NativeScript（官方警告）+ Lynx（`<list>` 懒加载与视图复用）| `virtual-list → UICollectionView` 映射**已在映射表里**，只差宿主实现 | 宿主侧实现 cell 复用 + 数据源 diff，而不是每次全量建视图 |
| **④ 启动：减少解析编译** | Hermes（字节码）/ Lynx MTS（"字节码加载快 4×"）| 实测**解析编译占启动 74%**——最大的单项 | JSC 无公开字节码 API → 走「**拆包 + 懒加载**」：首页只加载首屏需要的代码；TurboModules 式懒注册后端 |
| **⑤ 重绘隔离** | Flutter（RepaintBoundary + 光栅缓存）| 我们将来做自绘/复杂子树时的必需项 | 后端接口加 `markDirty(subtree)` / 冻结静态子树 |
| **⑥ 度量契约** | Lynx Monitor（FCP/FMP/Pipeline）+ Flutter（双线程两条 graph）| 「可插拔后端」若没有同构指标就**无法归因对比** | 每后端上报同构指标（首帧/每帧/调用数/字节数），本仓 benchmark 脚本即雏形 |

### 1.3 **不适用 / 需警惕**（避免照搬踩坑）

| 机制 | 为什么不适用 |
|---|---|
| **Flutter 全自绘** | 已选原生控件路线；且 Flutter 官方数据说明「嵌原生控件」本身就贵（hybrid composition 直接掉帧）——**反证：原生控件方案也要有合成策略，不能假设免费** |
| **RN 的「共享 C++ 核心」** | JSI 的零序列化来自 JS 引擎与 C++ 同进程共享对象图；**JSExport 仍跨 Swift/ObjC 边界，单次调用成本无法消除**——只能靠批量化与减少次数补偿。收益必须自测，不能引用 RN 数字外推 |
| **Lynx 双引擎** | Android PrimJS / iOS JSC 双引擎会造成语义漂移（官方自己警告）——本仓应在契约层**显式声明支持的 JS 语义子集** |
| **NativeScript 的全局元数据** | 构建期全量元数据是其启动慢、引擎升级难的根因（V8 GC API 变更、JSC 分支维护 3 人月）——我们用**显式白名单 + codegen** 替代运行时反射 |
| **Hermes 式自研引擎** | JSC 上不可复制（无公开字节码 API）；且"极致性能"应优先**启动与内存**（移动端体感），而非峰值算力 |

## 2. 优先级（按「实测收益 ÷ 风险」排序，不是按直觉）

| 序 | 项 | 现状 | 目标（可验证） | 依据 |
|---|---|---|---|---|
| **P0-a** | **批处理 + 帧调度** | `scheduleFrame`/`flush` 未实现 | 1000 项列表：跨界调用 **6001 → ≤10**；桥耗时 **9.87ms → <1ms** | 实测；G-40 B4 已设计；SPI 已预留 |
| **P0-b** | **视图扁平化** | 零实现 | 纯布局节点（无样式/无事件）不进宿主视图树；**宿主视图数下降 ≥30%** | RN 官方 600–1000→~200；原生建视图贵 |
| **P1-a** | **列表回收** | 映射有、实现无 | `virtual-list` 走 UICollectionView cell 复用；滚动不新建视图 | NativeScript 官方警告 |
| **P1-b** | **启动：拆包 + 懒加载** | 单 bundle 451.7KB，解析编译 18ms | 首屏 bundle **≤150KB**；解析编译 **≤6ms** | 实测 74% 在解析编译 |
| **P2-a** | 布局的原生侧求解 | 现在完全靠 UIKit 缺省（M1 诚实边界） | flex/grid 在原生侧一次 O(n) 求解（对齐 Flutter 单遍布局） | 正确性前置，性能其次 |
| **P2-b** | 度量契约 | benchmark 脚本（本仓） | 每后端同构指标 + 回归门禁 | 无度量则无法归因 |
| **P3** | 重绘隔离 / 光栅缓存 | 未涉及 | 复杂子树冻结与复用 | 依赖自绘或复杂合成场景 |

### 每项的有意取舍

- **P0-a 批处理**：批处理会**延迟一帧**才上屏（攒批的代价）。交互反馈（如点击态）需要"**立即 flush**"的旁路——
  对齐 RN Fabric 的「高优先级更新可打断低优先级」（Concurrent 思路），但**我们第一版只做定时批 + 手动 flush**，不引入优先级调度。
- **P0-b 扁平化**：扁平化会**改变视图层级语义**（某些依赖层级的样式/裁剪会失效）。规则必须保守：
  仅当节点「无样式、无事件、单子、无 transform/裁剪」时才合并——**宁可少合并，不可错合并**。
- **P1-b 拆包**：拆包会增加构建复杂度与「运行时加载失败」面。第一版只做**首屏/非首屏**两段，
  不做细粒度按路由拆分。

## 3. 验收口径（性能也要可证伪）

| 指标 | 怎么量 | 门禁形态 |
|---|---|---|
| 跨界调用数 / 字节数 | `hosts/ios/bench-bridge.swift`（本仓，真实 JSC） | 上限棘轮：调用数不得回升 |
| 解析编译耗时 / bundle 体积 | `bench-parse`（本仓） | 首屏 bundle 体积上限 |
| 宿主视图数（flatten 效果） | 竖切快照 `totalViews` | flatten 后视图数 ≤ 语义节点数的 X% |
| 首帧时延（真实设备） | 模拟器/真机 `CFAbsoluteTimeGetCurrent` 打点 | 需先有模拟器 runtime（本机下载中） |
| 帧时间 / 丢帧 | Instruments（真机） | 人工验收项（CI 不可及，诚实标注） |

> **诚实边界**：以上基线全部在 **macOS + 真实 JavaScriptCore** 上测得，**不代表真机 iOS 数字**
> （真机 CPU 更慢、但有 JIT；模拟器无 JIT）。**UIKit 建视图成本未测**（需模拟器 runtime）——
> 这是 P0-b 的关键输入，落地前必须补测。所有对外性能宣称在真机复测前一律标注"待真机验证"。

## 4. 与既有计划的关系（避免重复立项）

| 既有项 | 关系 |
|---|---|
| G-40 B4（零拷贝 + 批处理） | **P0-a 就是它的落地**；本文补充了实测基线与目标值 |
| G-40.4 铁律（>4KB 必走 ArrayBuffer） | 与本路线一致；我们实测 1000 项 payload 已 96.8KB → **必然要走二进制通道**，字符串 JSON 只是当前上界 |
| fluid P2-8（焦点导航性能） | 独立项（Web 端焦点），不冲突 |
| app-renderer-plan M2/M3 | P0-a/P0-b 落在 M2（diff/commit）；P1-a 落在 M3+（组件映射） |
| host-integration B6（组合矩阵） | 性能门禁应作为矩阵的**第 8 项断言**（每组合的调用数/视图数上限） |

## 5. 下一步（建议顺序）

1. **补测 UIKit 建视图成本**（模拟器 runtime 就绪后）——它是 P0-b 的输入，也决定 P1-a 的紧迫度。
2. **P0-a 批处理**：实现 `commitBatch` + `flush`，用 benchmark 门禁锁住「调用数下降」。
3. **P0-b 扁平化**：保守规则 + 视图数门禁。
4. **P1-b 拆包**：首屏/非首屏两段，锁 bundle 体积与解析时间。

> 纪律：每项落地时必须**带 benchmark 与门禁**——性能项没有门禁等于没做（会静默回退）。
