## 0. 结论先行

1. **benchmark 的问题不是"测不准"，是"没人信"。** 现有 `Proteus_Benchmark案例规格.md` 的口径已经足够严谨（work time 而非 FPS、Perfetto 交叉校验、三强制对照），但它产出的是一张**表格**——评审者只能选择"信"或"不信"。**Dactyl 把表格变成一堵墙：任何人拿手指一划，肉眼就能判断快慢。**

2. **核心发明：延迟显影（Latency Visualization）。** 把不可见的 ms 映射为可见的像素与几何：
   - **幽灵拖尾**：手指的真实历史轨迹（按官方事件时间戳采样）与铁磁流体尖峰顶端的**偏差像素数**，就是延迟的观测量；
   - **延迟环**：手指周围的圆环半径 ∝ 实测 `input_latency_ms`，越接近 1 帧预算越红；
   - **帧格**：背景 vsync 刻度，错过一帧闪一格。
   ⇒ **延迟从"报告里的数字"变成"屏幕上能用眼睛量的距离"**，外部验证者的信任成本归零。

3. **五关负载阶梯，一把天花板刻度尺。** L1 触即应 → L2 跟手 → L3 沸腾 → L4 十指 → L5 崩裂。每一关叠加一类负载（按压反馈 / 单指 / 高频数据 / 多指 / 全叠加），**逐关把延迟顶到崩裂点**。五关的崩裂点并排就是"天花板刻度尺"——多框架同尺对齐，即对外的打榜图。

4. **天花板是一个容量数，不是一个耗时数。** 对外宣称不用"我们 P95 是 3ms"（没概念），而用 **"在 120Hz 下维持 P95 ≤ 1 帧，我们能扛 N 个节点 × M 触点的负载，对手在 N/4 处就崩"**。容量数比耗时数更难被质疑，也更能说明架构代差。

5. **一条自洽性红线：美术不许成为瓶颈。** 所有装饰动效**必须走合成属性**（`translation / scale / alpha`，Morpheus §5-bis：编译期判定合成属性集合，RenderThread 直接更新 RenderNode，主线程零参与）——**否则 demo 自己就是压力源，测的是装饰而不是链路**。这是本方案与"**把炫技当目的**"的 demo 的分界线——**注意：本方案自己也做炫技（§6 四幕），但炫技必须寄生在骨骼上（V1 炫技即取证 · V2 炫技不动指标），不能反过来。**

6. **交付形态**：一份源码（Vue）→ 三端 + Skyline 共用；产物必须是 **IR 产物**（非 VDOM bundle，`Proteus_Benchmark案例规格.md` §10.3）；挂入 Playground **扫码即玩**；量具与外部取证脚本落在 `hosts/shared/dactyl/`。

7. **双层结构：验证层 + 炫技层（§6）。** §3–§5 是骨骼（判据、刻度尺、天花板），负责"可信"；§6 是肌肉（四幕：**立 / 剖 / 破 / 对**），负责"被看见"。两层的连接件是**三条宪法**：**炫技即取证**（每个节目绑 ≥1 条判据）· **炫技不动指标**（`viz=off` 后指标不变）· **幕名不构成代号**。

## 1. 为什么是这个 demo（不重复造轮子）

### 1.1 它与既有 benchmark 的关系

| 维度 | `Proteus_Benchmark案例规格.md` | **Dactyl（本篇）** |
|---|---|---|
| 目的 | 用可复现案例**暴露架构代差** | 把代差**变成肉眼可见、可上手互动**的演示 |
| 读者 | 工程评审 / 竞品分析 | 任何人（含非技术决策者）——扫码即玩 |
| 产出 | 报告 + 对照表 | 一个**能玩的应用** + 一把**能比的天花板尺** |
| 关系 | **方法论母体**（口径、三原则、三禁止全部沿用） | **它的验证载体与对外形态** |

### 1.2 Dactyl 是 bench spec 三原则的"合体"

`Proteus_Benchmark案例规格.md` §0.1 的三条选例标准——**① 节点规模大 · ② 动画期间有数据更新 · ③ 必须由手势驱动**——单条分开测都容易被"调优"糊弄。Dactyl 把三条**同时**压进一屏：

```
① 万级节点        →  L3/L5 的铁磁流体粒子场（10^4 量级）
② 动画中数据更新   →  L3 沸腾：跟手动画进行中，后台每 100ms 更新上万个属性
③ 手势驱动        →  全场唯一输入源就是手指（无自动播放、无定时器驱动的主循环）
```

> 三条同时成立时，"所有框架都跑满 120FPS 白测"的陷阱自动消失——因为**没人能靠调优同时躲过这三条**（`Proteus_Benchmark案例规格.md` §0.1）。

### 1.3 与 `14-input-bridge-latency` 的对照（每一关验证哪条腿）

| Dactyl 关卡 | 验证 14 的哪条腿 | 对外的可证伪判据（14 已声明） |
|---|---|---|
| **L1 触即应** | **S1.1** 按压态内联（零跨界） | `press_feedback_ms ≤ 1 帧` · `bridge_calls_per_tap == 1` |
| **L2 跟手** | **S1.2** 命中缓存 + **S1.3** 平台识别器 | `hit_test_calls_per_gesture == 1` · `input_latency_p95` |
| **L3 沸腾** | **S2** 零拷贝线格式 + **S3** 交互折叠 | `bridge_wire_bytes == 0` · `js_involved_gestures_ratio < 10%` |
| **L4 十指** | **S1.4** 批量指针 ABI | `ffi_calls_per_frame ≤ 1` |
| **L5 崩裂** | **S4** 线程解耦 + **S6** 度量门禁 | `main_thread_block_ms` P95 下降 · 门禁进 CI |

> 这张表是 Dactyl 的**存在理由**：14 是方法论与判据，Dactyl 是**唯一能同时把这些判据搬上真机、并让外人亲手复现**的场景。

### 1.4 明确不做什么（对齐既有坑位清单）

| 不做 | 理由（出处） |
|---|---|
| **不做纯短视频** | 瓶颈在媒体管线，UI 框架优势无处体现（bench spec §0.3） |
| **不做 canvas 计算密集型**（如 2 万小球碰撞） | 考验逻辑层而非渲染层，不占优即失分（Checklist §4.3） |
| **不做自动播放动画** | 不涉及输入延迟，测不出差异（bench spec §0.1 ③） |
| **不用 FPS 当主指标** | vsync 饱和，`p50=p95=p99` 测不出余量（bench spec §0.2） |
| **不用装饰性粒子上限充数** | 装饰必须走合成属性、且不得成为瓶颈（本方案 §8.3） |

## 2. 概念：`Dactyl` · 触感穹顶

### 2.1 命名

- **代号 `Dactyl`**（希腊神话 Δάκτυλοι，"手指"一族）——与本仓既有神话代号体系（Proteus / Vapor / Morpheus / Apollo）一致，且**字面就是"手指"**，寓意"把触摸当第一公民"。
- **中文名「触感穹顶」**——一顶由铁磁流体尖峰构成的穹顶，随手指的位置与压力立起、迁移、塌陷。
- **视觉母题：铁磁流体（ferrofluid）**。选它的三层理由：
  1. **即时性隐喻**：铁磁流体是自然界对"输入"响应最即时的物质——手指即磁极，"磁极一动，尖峰立起"。**慢一拍就会立刻显得假**。
  2. **天然而纯净的压力源**：每一根尖峰都是可独立渲染的元素 → 负载就是"尖峰数量"，旋钮一拧即可加码，且**与视觉冲击力正相关**（越压越壮观）。
  3. **滞后可被眼睛量出**：理想状态下尖峰顶端应与手指**零偏移**；任何延迟都会让尖峰"歪向历史位置"——**延迟直接变成可见的偏角**。

### 2.2 交互循环（一屏之内）

```
                        ┌──────────────────────────────┐
   手指（唯一输入）  →   │  命中（内核 hit.rs，DOWN 一次） │
                        └──────────────┬───────────────┘
                                       ▼
              ┌────────────────────────────────────────────┐
              │  原生即时反馈（S1）── 按压态/涟漪/高光，0 次 JS │
              └───────────────────────┬────────────────────┘
                                      │ 仅"语义事件"过界（S3 折叠后 <10%）
                                      ▼
        ┌───────────────────────────────────────────────────────┐
        │  逻辑层（Vue）—— 只处理真正的业务（计分/记录/切换关卡）  │
        └───────────────────────┬───────────────────────────────┘
                                │ 二进制补丁指令（S2 零拷贝）
                                ▼
        ┌───────────────────────────────────────────────────────┐
        │  内核：布局 + 动画求值（anim.rs）+ 录制 → RenderThread  │
        └───────────────────────────────────────────────────────┘
```

**关键**：整条链路里，"跟手"这件事**根本不进 JS**——它是内核 IR 的 Tier 1（14 §4 S3）。JS 只在"这一关得了多少分""切换关卡""数据跳变"这类真业务上出现。**这正是与 Flutter/RN 拉开差距的地方，也是 demo 要让观众"看得见"的地方**。

## 3. 延迟显影（★ 本 demo 的灵魂）

> 本节是整个方案的**第一性设计**：如果延迟不能被眼睛看见，demo 就退化成又一张需要被"相信"的图表。

### 3.1 三种显影器

| 显影器 | 几何定义 | 读法 | 对应指标 |
|---|---|---|---|
| **① 幽灵拖尾 Ghost Trail** | 用**官方触摸事件时间戳**（非 `Date.now()`，bench spec §2.5）采样手指历史位置，画成一条半透明轨迹；铁磁流体尖峰顶端与轨迹最新点的像素偏差 = `visible_lag_px` | 偏移越大 = 延迟越大；理想为 0 | `input_latency_p95` 的**视觉投影** |
| **② 延迟环 Latency Ring** | 手指外圈一个环，半径 ∝ 实测 `input_latency_ms`（映射刻度：0 → 0px，8.33ms(120Hz 一帧) → 满刻度）；颜色绿→黄→红 | 环短即快；红环 = 已破一帧预算 | `input_latency_p95` 的**定量投影** |
| **③ 帧格 Frame Grid** | 背景铺 vsync 刻度网格，每错过一个 vsync 闪一格红 | 闪红频率 = 掉帧频率 | `jank_rate` 的**节律投影** |

### 3.2 为什么"肉眼可判"是决定性优势

```
延迟(ms) = 手指线速度(px/ms) × 滞后时间
⇒ visible_lag_px = input_latency_ms × finger_speed_px_per_ms
```

手指正常拖动约 **0.5–1.5 px/ms**。于是：

| 实测延迟 | 正常拖动速度下的可见偏移 | 观众判断 |
|---|---|---|
| ≤ 8.3ms（1 帧） | ≤ 4–12 px | **跟手**（尖峰贴住手指） |
| 16.7ms（2 帧） | 8–25 px | **能看出"飘"** |
| 33ms（4 帧） | 17–50 px | **明显脱节，像在拖一团果冻** |

> **这张换算表就是 Dactyl 的"照妖镜"原理**：不必懂 p95，不必信 Perfetto——**伸手一拖，脱节与否一目了然**。它把一个统计量，改写成一个物理距离。

### 3.3 反作弊：显影器必须"诚实"

显影器本身绝不能作弊，否则整个 demo 失信。三条硬约束：

1. **幽灵轨迹的数据源必须是官方事件时间戳**（Android `MotionEvent.getEventTime()` / iOS `UITouch.timestamp`），**禁止用 JS 侧时钟**（bench spec §2.5 明令）。
2. **延迟环的半径来自实测值**，禁止常数美化；无实测值时显示 `--`，不得假定为 0。
3. **帧格来自系统回调**（`Choreographer` / `CADisplayLink`），禁止用动画计时器伪造。

## 4. 五关负载阶梯（详细规格）

> 每关都是**独立的可选场景**（左上角切关），也可以"一路往上打"。负载旋钮在关内可微调，用于**逼近**该关的崩裂点。

### 4.1 总览

| 关 | 名称 | 一句话 | 负载主变量 | 打中的瓶颈 | 视觉 |
|---|---|---|---|---|---|
| **L1** | **触即应** | 一屏磁块，按下即凹陷发光 | 磁块数 N（10²–10⁴） | 按压反馈路径（是否过 JS） | 按下处激起涟漪 |
| **L2** | **跟手** | 铁磁流体尖峰随指迁移 | 尖峰数 N（10³–10⁴） | 输入延迟 / 命中次数 | 手指像磁铁拖拽一片针林 |
| **L3** | **沸腾** | 跟手 + 后台高频数据跳变 | N × 数据更新频率 f（10–200Hz） | **动画与数据更新打架**（架构级死穴） | 液面持续"沸腾"出数字与光点 |
| **L4** | **十指** | 十指同时压上穹顶 | 触点 M（2–10） | 跨边界调用次数 / 批量指针 ABI | 十个磁极把液体撕成多股 |
| **L5** | **崩裂** | 全部叠加，拉到爆 | 全变量联合升档 | 综合（线程争抢 / GC / 录制） | 过载瞬间液体"炸开"，崩裂帧高亮 |

### 4.2 L1 · 触即应（Instant Press）

| 项 | 规格 |
|---|---|
| 场景 | 一屏 **N 个磁块**（网格铺满），每块有按压态（凹陷 + 边缘发光） |
| 输入 | 单指点击 / 长按（DOWN → UP） |
| 负载梯度 | N = 100 / 1000 / 4000 / 10000 |
| 验证 | **S1.1**：按压态编译进内核样式表，DOWN 时原生直接改绘制属性，**零次 JS 跨界** |
| 主判据 | `press_feedback_ms ≤ 8.33ms`（1 帧@120Hz）· `bridge_calls_per_tap == 1`（仅"语义事件"一次） |
| 反派对照 | RN `Pressable` / Flutter `InkWell` **必过逻辑层** → 按下反馈 ≥ 1 个 JS/Dart 往返 + 1 帧 |
| 观感 | 按下即凹陷，**没有任何"等一下才亮"**；涟漪扩散与指尖同帧 |

### 4.3 L2 · 跟手（Track）

| 项 | 规格 |
|---|---|
| 场景 | 一顶 **N 根铁磁流体尖峰**的穹顶；每根尖峰的**朝向与高度**由手指位置决定（距离越近越高、倾角越朝向手指） |
| 输入 | 单指拖拽（无单击） |
| 负载梯度 | N = 1000 / 4000 / 10000 |
| 验证 | **S1.2** 命中缓存（`hit_test_calls_per_gesture == 1`）· **S1.3** 平台识别器 · **S3 Tier 1** 跟手折叠进内核 IR |
| 主判据 | `input_latency_p95 ≤ 8.33ms` · `visible_lag_px ≤ 12px`（正常速度下）· `js_involved_gestures_ratio == 0`（纯跟手不该进 JS） |
| 反派对照 | RN（无 worklet 时）每帧回 JS → 2 帧以上；Flutter 同线程但走 Dart 逐帧重建 |
| 观感 | 针林如影随形；**尖峰顶端贴住指尖**，延迟环尽量短 |

### 4.4 L3 · 沸腾（Boil）★ 最锋利的一关

| 项 | 规格 |
|---|---|
| 场景 | L2 的跟手动画**正在进行**，同时后台高频更新：每个磁块上的数字（点赞/评论/在线数）+ 部分磁块的色相，按频率 **f** 随机跳变 |
| 负载梯度 | N = 4000 固定 × f = 10 / 50 / 100 / 200 Hz |
| 验证 | **S2** 零拷贝线格式（高频小更新最吃序列化）· **S3** 数据更新走 O(1) 槽位直写（Vapor IR） |
| 主判据 | `work_time_p95 ≤ 8.33ms` · `jank_rate ≤ 0.2%` · `gc_pause_count ≈ 0` · `bridge_wire_bytes == 0` |
| 反派对照 | Flutter（Dart GC 在动画+更新叠加时频繁触发暂停，**公开长期问题**）· Vue/React Web（组件级 rebuild 与动画争抢） |
| 观感 | 液面一边跟手一边"沸腾"数字，**画面始终不打架**；掉帧时帧格闪红 |
| 备注 | 这是 bench spec §3.2 判断的"整个 benchmark 最有说服力的一张图"，Dactyl 让它**可玩** |

### 4.5 L4 · 十指（Poly）

| 项 | 规格 |
|---|---|
| 场景 | 支持最多 **M 个同时触点**（M = 2 / 5 / 10），每个触点都是独立磁极 |
| 输入 | 多指同时拖拽（真机可多指；模拟器可用注入多触点） |
| 负载梯度 | M × 每指驱动 N/M 根尖峰 |
| 验证 | **S1.4** iOS 接批量指针 ABI（`proteus_dispatch_pointers`，一帧 N 点一次 FFI）· Android 已有 |
| 主判据 | `ffi_calls_per_frame ≤ 1`（**不随触点数增长**）· 各指延迟一致（`per_pointer_latency_p95` 离散度小） |
| 反派对照 | 单触点串行派发的框架，M 增则延迟线性增 |
| 观感 | 十股液柱同时被拉扯，互不干扰；**触点数翻倍而延迟不翻倍**是核心看头 |

### 4.6 L5 · 崩裂（Rupture）★ 天花板关

| 项 | 规格 |
|---|---|
| 场景 | L1–L4 全叠加；一个"**总负载旋钮**"（0–100%）同时线性放大所有维度 |
| 玩法 | 观众自己把旋钮往上拧，**直到画面第一次明显崩** |
| 崩裂判定 | 首次出现任一：`input_latency_p95 > 8.33ms` 或 `jank_rate > 1%` 或 `visible_lag_px > 阈值` |
| 输出 | 记录**崩裂档位**与该档位的负载向量 → 写入 `hosts/*/results/dactyl-ceiling.json` |
| 观感 | 未崩时"壮丽"（针林越密越炫）；崩裂瞬间**液体炸开 + 闪帧格 + 冻结一帧截图**，标注崩裂点 |
| 诊断 | 崩裂帧可**逐帧回放**（复用 TraceBus / DevTools，决策 #676/#677）→ 定位爆在哪一段（14 §2 的 9 段链路） |

> **设计要点**：崩裂不是失败，是**产品功能**。对手的崩裂点出现在旋钮 20%，我们在 80%，**这个差距本身就是 demo 的结论**。

## 5. 天花板与崩裂点（怎么算"打到天花板"）

### 5.1 定义（可证伪）

```
负载向量  L = ( N节点数 , M触点数 , f数据更新频率 , K动画通道数 , D嵌套深度 )

天花板 CEILING :=  在给定设备上，
                    满足 input_latency_p95 ≤ 1 帧 ∧ jank_rate ≤ 0.2% ∧ gc_pause ≈ 0
                    的 L 的"上确界"（按定义好的标量化顺序取最大可行 L 的档位）

崩裂点 RUPTURE :=  首次违反上述任一预算的负载档位（L5 旋钮的首次违约刻度）
```

> **标量化规则**：为避免"哪个 L 更大"的歧义，定义**升档序**——先升 N，N 到顶再升 f，再升 M，再升 K。因此"天花板"是一个**确定的档位号**，可跨框架对齐。

### 5.2 天花板刻度尺（对外打榜图）

把各框架在同一台设备、同一套负载下测得的**崩裂档位**画成一把并列的尺：

```
        0%        20%        40%        60%        80%       100%
         ├──────────┼──────────┼──────────┼──────────┼──────────┤
Flutter  ██████████✗
RN       ████████████████✗
Lynx     ██████████████████████✗
原生      ██████████████████████████████████████✗
Proteus  ████████████████████████████████████████████████████✗   ← 崩得更晚
         └ 横轴 = 统一负载向量 L 的"总强度"归一化；✗ = 崩裂点
```

配套三个数字（沿用 bench spec §9.5 的呈现方式）：**崩裂档位** · **崩裂前的 `work_time_p95`** · **崩裂瞬间的 GC 暂停**（对 Flutter 的杀手锏）。

> ⚠ **分端表述**（bench spec §9.4）：小程序 Skyline 端的路由/动画由 Skyline 执行，**不得算作"超越 Skyline"**；App 端才是 Proteus 自研。对外一律分端标注。

### 5.3 每关的天花板口径

| 关 | 天花板变量 | 目标档位（App 端，120Hz 中端机） | 合格线 |
|---|---|---|---|
| L1 | N 磁块 | ≥ 4000 | 1000 |
| L2 | N 尖峰 | ≥ 4000 | 1000 |
| L3 | f（N=4000） | ≥ 100Hz | 50Hz |
| L4 | M 触点 | ≥ 5（`ffi_calls_per_frame ≤ 1`） | 2 |
| L5 | 总负载 | 崩裂档位 ≥ 70% | 50% |

> 上述档位是**目标值（待真机标定）**，实现完成后按 `hosts/*/results/dactyl-ceiling.json` 实测回填；**未实测前不得对外宣称**（对齐 `14` §8 诚实边界）。

### 6.2 幕一 · 立（Rise）「万针朝宗」

**动作**：指尖在穹顶上一划，**N 根尖峰在同一帧内同时转向**（朝向 + 高度），整片针林像被磁化一样朝指尖低头。

| 项 | 规格 |
|---|---|
| 负载 | N = 1000 / 4000 / 10000 根尖峰 |
| **炫技点** | **「整齐度」就是带宽**——见下 |
| 副节目 | **十指撕穹**（L4）：十指同按，穹顶被撕成十股；看点是**各股跟手延迟一致** |
| 绑定判据 | L2 `visible_lag_px ≤ 12px` · `js_involved_gestures_ratio == 0`；L4 `ffi_calls_per_frame ≤ 1` |

**★ 核心洞察：「整齐度」就是带宽的视觉投影。**

10000 根尖峰 × (朝向 + 高度) ≈ 80 KB/帧。走 JSON 文本通道时，逐排解析 + 逐排提交是**必然**结果——观众看到的是一条**"波"从针林一端扫到另一端**。走 SPSC 环形缓冲 + 槽位直写时，整片**在同一帧**转向。

> **对外话术**：不讲字节数，只问一句——「**看这堵针墙，是"一起"倒，还是"一排一排"倒？**」

这把 §4.4 L3 里"最吃序列化"的判据，翻译成一个**任何人都能判断的视觉事实**。

### 6.3 幕二 · 剖（X-Ray）「时间显微镜」★ 四幕中最强

**动作**：把一次真实触摸（约 1 秒的操作）**慢放 100 倍**回放（约 10 秒）。屏幕上，这次触摸被拆成**九段光脉冲**，沿 14 §2 的九段链路逐段点亮；每段脉冲的**停留时长 = 该段实测耗时 × 100**。

```
慢放时间轴（示意；数字为口径示例，非实测值）
① 采样 ████████████ 4.17ms   ← 硬件采样周期，物理下限
② 分发 ██ 0.3ms
③ 命中 ▏0.03ms               ← 内核 hit.rs（DOWN 一次）
④ 识别 █ 0.1ms               ← 平台识别器
⑤ 逻辑 ▌0ms                  ← ★ 不进 JS：一条看不见的线
⑥ 布局 █████ 2.0ms           ← 已由 Vapor 兑现
⑦ 录制 ██ 0.8ms
⑧ 提交 ███ 1.0ms
⑨ 上屏 ████████████████████████ 8.33ms  ← vsync 一帧，物理下限
```

**杀伤力在哪**：把同一根时间轴画两条。**Proteus 的 ⑤ 段是一条看不见的线（0ms），对照框架的 ⑤ 段是一整块巨大的实心色块**——因为它们的每一次交互都要过逻辑层。这才是"我们为什么快"的**结构性解释**，而且**无法靠调优抹平**（14 §3.2）。

**加分项：可交互。** 拖动时间游标，逐段展开该段内部（命中链 / 布局节点数 / 录制层数 / 跨界字节数）。**工程师会主动玩它**——这是最有效的技术传播形态。

| 项 | 规格 |
|---|---|
| 数据源 | TraceBus / Perfetto（**外部取证**，非自报；对齐 §7.3 禁自证） |
| 深度 | 展开到 9 段；每段可下钻一层 |
| 对照轨 | 第二条时间轴（对照框架），**同一视觉、同一负载** |
| ⚠ 诚实边界 | ①⑨ 是**物理下限**，必须显式标注"不可优化"——否则等于在卖不可优化的东西 |

### 6.4 幕三 · 破（Collapse）「崩坏即诊断」

**动作**：L5 旋钮拉过崩裂点，穹顶沿**延迟热力图的等值线**碎裂；**裂痕的起点 = 最先违约的那一段链路**。

| 先违约的段 | 崩裂图案（肉眼看出的诊断） |
|---|---|
| ⑤ 逻辑（交互进了 JS） | 裂痕从**指针落点**区域起裂（那里才需要逻辑） |
| ⑦ 录制（层树全量重建） | 裂痕从**尖峰最密**处起裂（层数最多处） |
| ③ 命中（无缓存） | **全网均匀**碎裂（每次 MOVE 都付一次代价） |
| ⑧ 提交（线程争抢） | 裂痕**随机多点**同时出现 |

> **崩裂图案本身就是诊断报告**——不必看 JSON，看裂法就知道死在哪一段。这把 §4.6 的"崩裂不是失败，是产品功能"推到极致：**失败被做成了美学，而且这个美学是有信息量的。**

**配套「崩裂时间胶囊」**：崩裂瞬间冻结一帧 → 生成一张**可分享卡片**（崩裂档位 / `work_time_p95` / GC 暂停 / 热力图 / 首违约段），同步写入 `hosts/*/results/dactyl-ceiling.json` 并导出 PNG。→ **天然传播素材，零额外成本。**

⚠ 实现红线：热力图**必须用预生成静态纹理 + 合成属性调制 alpha**（不得逐帧重绘），否则崩裂动画自己就成了压力源（§8.3）。

### 6.5 幕四 · 对（Duel）「同一根手指，同一时刻」

**动作**：同一台设备上并排 2–4 个面板（Proteus / 原生 / Flutter / RN），由**脚本化手势注入**驱动（保证输入逐字节一致，消掉"人肉差异"），实况"天梯条"随时间生长——**谁先崩，谁的红条先冻结**。

| 项 | 规格 |
|---|---|
| 输入 | 系统级注入（Android `adb shell input` 系列 / instrumentation），**非人工手划** |
| 面板 | 2–4 宫格；**同一视觉、同一负载、同一设备** |
| 结果读出 | 各面板崩裂时刻 + 崩裂档位（实况刻度尺，非事后图表） |
| ⚠ 公平纪律 | 对手用**最佳实践**实现 + 实现代码 **review 并公开**（R5 / bench spec §9.2）；否则整个对决失效 |
| ⚠ 分端声明 | Skyline 端**只作"对齐"**，不得算"超越 Skyline" |
| 位置 | **对外发布版**，随 D5 |

### 6.6 三个"钩子"（前 3 秒决定传播）

1. **3 秒建立信任**：手指按下，针**在同一帧**立起——没有任何"等一下才亮"。
2. **一句话解释**：「**延迟不是数字，是针墙倒下的整齐度。**」
3. **一张图**：崩裂瞬间的热力图卡片（含首违约段标注）。

### 6.7 传播形态（炫技的落地判据）

## 8. 视觉与美术规范（"惊艳"必须与自洽共存）

### 8.1 视觉母题与配色

| 元素 | 规格 |
|---|---|
| 背景 | 深空近黑（`#0A0C10`），低对比噪点纹理（静态，不参与合成） |
| 铁磁流体 | 青→紫渐变高光（`#39D0FF → #A97BFF`），尖峰顶端带辉光 |
| 手指/光标 | 冷白核心 + 外发光；延迟环：绿 `#2ECC71`（<4ms）→ 黄 `#F1C40F`（4–8.33ms）→ 红 `#FF4D4D`（>8.33ms） |
| 幽灵拖尾 | 半透明白，逐段降低不透明度（历史越久越淡） |
| 帧格 | 极暗网格（静态底图）；丢帧格闪红 `#FF4D4D`（一次性，不进合成） |
| 崩裂瞬间 | 全屏白闪 1 帧 + 液体径向炸开 + 冻结截图叠加崩裂点标注 |

### 8.2 动效清单（全部声明式，Morpheus 语法）

| 动效 | 属性 | 类型 |
|---|---|---|
| 尖峰跟随手指（朝向/高度） | `rotation` + `scale` | **合成属性**（RenderThread） |
| 按压凹陷 | `scale` + `alpha`（边缘发光用 `alpha` 叠加层） | **合成属性** |
| 涟漪扩散 | `scale` + `alpha` | **合成属性** |
| 数据数字跳变 | `text` 内容（槽位直写，O(1)） | 内核槽位更新 |
| 崩裂炸开 | `translation` + `scale` + `alpha` | **合成属性** |

### 8.3 ★ 自洽性红线（与"把炫技当目的"的分界）

> **装饰动效只允许使用合成属性**（`translation / scale / alpha / rotation`），由 Morpheus 在**编译期判定合成属性集合**，RenderThread 直接更新 RenderNode、**主线程零参与每帧**（`Proteus_声明式动画引擎Morpheus方案.md` §5-bis.1/§5-bis.2）。

理由：若用需要逐帧重排/重绘的属性做装饰，**demo 自己就成了压力源**，测到的是"装饰有多贵"而不是"链路有多快"。两条附带约束：

1. **尖峰数量放大时，单帧主线程工作量必须"不随 N 增长"**（否则 L2 天花板测的是绘制而不是输入）；
2. 提供**降级美术档**（低端机自动切换：尖峰数减半、辉光关闭、纹理关闭），但**降级只影响观感，不影响指标口径**——降级档必须与标准档**分别出数**，且报告注明。

## 13. 诚实边界

- 本方案的**所有目标档位（§5.3）与预期对比，均为设计目标，尚未真机实测**；实现完成后以 `hosts/*/results/dactyl-*.json` 回填。
- **iOS 现状多为 macOS/模拟器口径**（`14` §8 已声明），Dactyl 的 iOS 数据必须**真机**产出方可对外。
- `visible_lag_px` 依赖手指线速度，**快速甩动时偏移会放大**——归因时必须同时报速度（速度-延迟-偏移三者强相关，不能只报偏移）。
- Harmony 的渲染 ratio（0.106）是**提交级/光栅级**口径，**不代表交互链路**；Dactyl 的 Harmony 交互数据以 `interaction_boot_ms` 为主（现状每次交互重建 VM，预计先崩）。
- "打穿所有框架"的表述**必须分端、必须带外部取证（尤其高速摄影）**，否则降级为"内部对比"。
- **炫技层不构成性能证据**（§6 V1/V2）：四幕中只有「崩裂时间胶囊」导出的数字与「对决」的实测崩裂时刻可作结论引用，**其余视觉表现一律不得当作性能证据**；任何炫技都必须同时给出 `viz=off` 的同批数据。
