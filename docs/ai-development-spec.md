# Proteus AI 开发规范（完整模型 · AI Development Model）

> **一句话**：让**任意数量、任意模型的 AI 会话**与人类维护者，用**同一套判据**协作推进 Proteus——
> 把「多个 AI 同时开发框架」这件事从"靠记忆和运气不撞车"，变成**有生命周期、有边界、有交接、有追溯、有门禁**的工程流程。
>
> **本文件的定位 = 总模型（umbrella）**：它统一「生命周期 + 协作原语 + 判据索引」；
> 三条链路各自的**细则**留在各自文档（本文件只做**指针 + 差异表**，不复制）。
>
> **状态**：v1（2026-10-13 立）。目标读者：任何 AI（Claude / GPT / DeepSeek… × 任意会话）× 任何人类维护者。
>
> **不适用**：单人一次性脚本、与 Proteus 仓库无关的外部项目。

---

## 0. 为什么需要这份规范（缺口与合并）

本仓此前已有**很厚的 AI 相关资产**，但它们分属**两条不同的链路**，且都**不是**"多个 AI 协作开发框架本身"：

| 既有资产 | 覆盖 | **不覆盖（缺口）** |
|---|---|---|
| `docs/ai-cobuild-spec.md` + `Skill(ai-cobuild)` + `check:cobuild` | **框架方 ↔ 外部使用方**缺陷闭环（报告→立项→修→发→回执→独立复测） | 是**缺陷处理**，不是**功能开发** |
| `docs/proteus-ai-agent-plan/`（G-36，`08-rules.md`） | **AI 用框架写业务代码**（Agent 产标准 SFC） | 框架是它的**产物目标**，不是**开发对象** |
| `LLM_IMPLEMENTATION_GUIDE.md` | **单 AI 从零落地**框架（6 阶段） | 是**一次性落地**指南，不含"持续迭代 + 多 AI 并行" |
| `CONTRIBUTING.md` | 人类贡献者 **单线 PR** 流程 | 无"多 AI 分工 / 认领 / 防撞车" |
| 端对齐 **SOP v2**（`docs/proteus-end-alignment-plan/04-batches.md`） | 组件 API **怎么正确做一个**（13 步 + T1–T27 陷阱） | 是"做事规范"，不是"协作规范" |
| **G-32 原语审查清单**（`docs/proteus-semantic-primitives-plus-plan/rules.md`） | 能力/原语**怎么加** | 同上 |
| `PROJECT_MEMORY.md` 会话恢复指引 + `decisions.md` 只增不改号 | **跨会话接棒**（单线） | 无**并行分支**的交接与非撞车 |

**结论**：地基齐（`pnpm verify` 100+ 门禁 + 棘轮基线 + `test:coupled` 定向建议 + hooks 红线，本质就是"不管谁改、判据同一套"——这正是多 AI 协作最难的一块，**已有**）；
**缺的是协作层的成文协议**——本文件补的就是这层，并把上面所有资产**合并进一个模型**。

> **本文件解决的四类静默失败**（与 ai-cobuild 的四铁律同构，只是对象从"外部报告"换成"内部任务"）：
> ① **没人认领**（任务停在 plan 里，以为别人在做）② **撞车**（两个 AI 改同一文件，后写覆盖先写）
> ③ **断在半路**（AI 会话结束，WIP 无人接、无交接）④ **不可追溯**（改了框架代码，说不清哪个决策号/会话/为什么）。

## 1. 完整模型总图

```
        ┌──────────────────────────────────────────────────────────────┐
        │  统一生命周期（第 2 节）—— 任何 AI 任务的"怎么走"               │
        │  Plan → Claim → Implement → Self-verify → Cross-verify        │
        │       → Handoff/Publish → Trace        （7 关，每关有出口判据）│
        └───────────────┬──────────────────────────────────────────────┘
                        │  同一条生命周期，被"链路"参数化
        ┌───────────────▼──────────────────────────────────────────────┐
        │  三条链路（第 3 节）—— "做什么"决定差异判据                     │
        │  A · 开发框架（framework-dev）  ← 本规范主体                   │
        │  B · 用框架（framework-use）    → G-36                        │
        │  C · 外部缺陷（external-fix）   → ai-cobuild                  │
        └───────────────┬──────────────────────────────────────────────┘
                        │  多个 AI 同时走时，靠"协作原语"不打架
        ┌───────────────▼──────────────────────────────────────────────┐
        │  协作原语（第 4 节）—— "多人怎么并行"（填 4 个缺口）            │
        │  任务单元 · 所有权边界 · 认领 · 交接 · 追溯                    │
        └───────────────┬──────────────────────────────────────────────┘
                        │  每一关、每个原语，都由机器判据兜底
        ┌───────────────▼──────────────────────────────────────────────┐
        │  机器判据（第 6 节）—— "谁兜底"                                │
        │  既有 100+ 门禁 + ★新增 check:ai-tasks（任务板自洽）           │
        └──────────────────────────────────────────────────────────────┘
```

**读法**：竖着读是"一个任务的一生"；横着读是"三个人同时做三件事时，靠什么不互相破坏"。

## 2. 统一生命周期（7 关）

**每一关有「入口判据 / 产出物 / 出口判据（机器可查）」**。跳关 = 不合格。

### 关 0 · 立项（Plan）
- **入口**：一个需求 / 想法 / 外部报告 / 自查发现。
- **动作**：判断它属于哪条**链路**（A/B/C）+ 切成**任务单元**（第 4.1 节）。
- **产出**：一个可执行的任务——要么落进 **plan 文档**（大特性），要么落进**任务板**（`docs/ai-tasks.json`，见第 4.3）一行。
- **出口判据**：任务有 **id + type + scope**；大特性有 plan 文档；**凡涉及架构取舍的，留一个决策号**（`decisions.md` 只增不改号）。
- **反模式**：只在对话里"记住了要做"，未落盘 ⇒ 换个会话就丢。

### 关 1 · 认领（Claim）
- **入口**：一个 `status=planned` 的任务单元。
- **动作**：登记 `owner`（会话/agent 标识）+ 边界 `scope`（glob）+（可选）`branch`。**认领 = 写进任务板**，不是口头宣布。
- **出口判据**：`status=in_progress` ⇒ `owner` 非空 **且** `scope` 与其它 `in_progress` 任务**无重叠**（`check:ai-tasks` 强制——这就是"防撞车"的机器判据）。
- **反模式**：直接开干不登记 ⇒ 撞车。

### 关 2 · 实施（Implement）
- **动作**：改代码。**两条铁律**：
  - **同源纪律**：改动与**配套断言同步**（内核改动跑 `pnpm test:coupled`）；SSOT 类改动同步所有消费面（见第 4.2 所有权边界）。
  - **基准纪律**：任何"多端对齐"先问「**Web/标准的真值是什么**」，再问各端差在哪（AGENTS.md 红线）。
- **出口判据**：改动**只碰 `scope` 声明的路径**（越界 ⇒ 要么扩大认领、要么拆任务）。

### 关 3 · 自验证（Self-verify）
- **动作**：跑**定向门禁**（不是全量）；对每条新断言做**破坏性验证**（改坏 ⇒ 必须变红）。
- **出口判据**：定向门禁绿 + 破坏性验证过（"不能红"的测试不算测试，ai-cobuild 同款纪律）。
- **反模式**：只跑全量、靠全量发现问题（用 ~10 倍时间买本该 ~10 秒发现的债——AGENTS.md 点名）。

### 关 4 · 独立验证（Cross-verify）
- **入口**：`Self-verify` 全绿。
- **动作**：由**另一个 AI 会话/子代理**按"原始需求/最小复现"复测——**自测不算独立验证**。
- **出口判据**：独立复测记录（对功能：可复现的通过证据；对缺陷：原始最小复现已消失）。
- **诚实边界**：多 AI 环境下"独立性"= 不同会话/不同上下文，**不是**保证无相关偏差；无法独立时**显式标注 `verification=partial`**（不冒充 passed）。

### 关 5 · 交接 / 发布（Handoff → Publish）
- **动作**：
  - **未完成而中断** ⇒ 写 **handoff**（第 4.4 模板），任务板置 `blocked` + `note`。
  - **完成** ⇒ 提交 + 推送（AGENTS.md「提交 ≠ 交付」红线）；涉及 `website/**` 补 `[deploy]`；涉及发布补版本+回执。
- **出口判据**：`status=done` ⇒ 有 **decision 号 + verification 证据 + 已推送**（`check:ai-tasks` + `check:pushed`）。
- **反模式**：本地提交一堆不推（用户视角=不存在）。

### 关 6 · 追溯（Trace）
- **动作**：闭合"**需求 → 任务 → 决策 → 会话 → 改动**"锚点链。
- **出口判据**：任务板 `done` 项的 `decision` 号**在 `decisions.md` 里真实存在**（`check:ai-tasks` 强制 grep）。
- **为什么**：框架代码的每处能力都要能回答"谁改的、为什么、哪条决策"——这是 G-36.7（业务代码可追踪到 IR）在**框架开发**这一侧的对应物。

## 3. 三条链路（A/B/C）与差异

同一条生命周期，**差异只在"判据"**。下表是**唯一**需要区分的地方：

| | **A · 开发框架**（framework-dev） | **B · 用框架**（framework-use） | **C · 外部缺陷**（external-fix） |
|---|---|---|---|
| **主体** | 本规范 | `proteus-ai-agent-plan/`（G-36） | `docs/ai-cobuild-spec.md` + `Skill(ai-cobuild)` |
| **产物** | 框架源码（`packages/`・`hosts/`） | 业务 SFC（用规范产出代码） | 缺陷修复 + 回执 |
| **立项锚点** | plan 文档 / 决策号 / 任务板 | G-36 铁律 + MCP 工具 | 外部报告节 + 台账条目 |
| **核心判据** | `pnpm verify` 全链 + 链路的专项门禁 | G-36.1 conformance + `verify-llm` | 四铁律 + `check:ledger`/`check:cobuild` |
| **独立验证方** | 另一 AI 会话 / 子代理 | conformance 套件 | **外部使用方**原样复现 |
| **发布** | push（+`[deploy]`/npm 走 changesets） | 无（产代码） | 必须 npm 发布才算数 |
| **细则在哪** | **本文件** | `docs/proteus-ai-agent-plan/08-rules.md` | `docs/ai-cobuild-spec.md` |

**三链交汇点（一个改动可能同时触发多链）**：
- A 改动暴露了外部报告的同类问题 ⇒ 补 C 的台账（`related` 互指）；
- A 改动了 AI 用框架的 **语义面**（原语 / 能力签名）⇒ 同步 B 的 G-32/G-36 规则与文档；
- C 修完要发布 ⇒ 走 A 的 `check:pushed` + 发布链。

> ★**不要重写 G-36 与 ai-cobuild**——它们是 B/C 的**权威细则**。本模型只在 A 链填空白，并把三链的**接线点**讲清。

## 4. 协作原语（多 AI 并行的四个缺口）

### 4.1 任务单元（Task Unit）——切分规则
一个**任务单元** = **一次能被独立验证的最小交付**。判据（满足即一个单元）：
- 有**单一可观察结果**（"`<pg-glass>` 三端渲染" / "能力 X 加 3 个属性" / "修 p-icon import.meta"）；
- 有**定向门禁**能证明它（没有定向门禁 ⇒ 先补一个，否则不算可分）；
- **边界可 glob 化**（能说清只碰哪些路径）。
- **反模式**：把"把玻璃做好"当一个单元（不可验证）——应切成"性能达标 / 折射对齐 / 端到端样例"。

### 4.2 所有权边界（Ownership）——文件级防撞车
**原则**：**能靠边界消除的冲突，不靠"记得协调"**（AGENTS.md「隔离 > 还原」同源）。
把路径分三类：

| 类别 | 含义 | 并行策略 | 例 |
|---|---|---|---|
| **独占（single-owner）** | 有跨文件 SSOT 语义，改它牵动多处 | **一次只允许一个** `in_progress` 任务持有 | `packages/component-ir/src/primitives.ts`（128 原语 SSOT）· `packages/compiler/src/transforms/registry.ts`（规则注册表）· `packages/compiler/src/template.ts` · `packages/plugin-vite/src/plugin.ts` · `scripts/test-coupling.mjs` 的 `COUPLING` |
| **共享可写（shared-append）** | 只在"新增"维度并行安全 | 并行 OK，但**加不改**（改他人行前先跑对方的配套门禁） | 新增 `packages/components/<新组件>/**` · 新增 `docs/*-plan/**` · 新增 `tests/*.test.ts` · `decisions.md`（**只追加**） |
| **只读基准（read-only）** | 生成物 / 快照 / golden，改必须重生成 | 只改**源**、重生成产物，不手改产物 | `docs/generated/**` · `**/generated/**` · golden 快照 |

**边界表 SSOT**：内核改动→配套测试的**精化映射**已经在 `scripts/test-coupling.mjs` 的 `COUPLING`（`pnpm test:coupled -- --explain`）。**改哪块先看它**——本文件不重复该表，只规定"改内核前必查它"。
**撞车机器判据**：任务板里任意两个 `in_progress` 任务的 `scope` **不得重叠**（`check:ai-tasks`）。

### 4.3 认领（Claim）——登记即认领
**认领的唯一形式 = 往 `docs/ai-tasks.json` 写一行**（`status=in_progress` + `owner` + `scope`）。口头/skill 里的"我来做"不算。
**为什么**：与 ai-cobuild「报了必须立项」同源——**没有登记，就没有机制发现"没人做"或"两人做"**。
**Owner 命名**：`session:<短标识>`（如 `session:glass-ios`）或 `agent:<id>`——只要**同一时刻不同会话不同名**。

### 4.4 交接（Handoff）——中断必留
**触发**：任务做到一半要停（会话结束 / 转交给另一个 AI / 阻塞）。
**动作**：任务板该行置 `blocked`（或保持 `in_progress` 但写明 `owner` 变更）+ 在 `note` 写**交接模板**：

```
【Handoff】
- 做到哪：<已完成的关（关 2/3…）+ 具体状态>
- 已改：<文件清单 / 已提交的 commit sha>
- 未做：<清单，按优先级>
- 下一步（可照做）：<一条可执行命令或动作>
- 坑：<踩到的、下一个人会再踩的>
- 判据状态：<哪些门禁绿、哪些红/未跑>
```

**落盘位置**：小交接写任务板 `note`；大交接（跨会话里程碑）追加到 `PROJECT_MEMORY.md` 当月归档 + 任务板互指。

### 4.5 追溯（Trace）——锚点链
**唯一锚点链**：
```
需求/报告  →  任务板 id  →  决策号（decisions.md，只增不改号）  →  会话 owner  →  commit sha
```
- 任务板 `done` 项**必须**有 `decision` 号（`check:ai-tasks` 校验其真实存在）；
- commit message 遵循 `<type>(<scope>): <desc> · 决策 #NNN`（现有约定）；
- 不新增文件格式——追溯靠**已有三个锚点**（id / 决策号 / sha）互指，而非新造系统。

## 5. 能力 / 组件 API 开发流水线（SOP v2 × G-32 合一）

这是 **A 链最常见的任务类型**，把两份既有规范合成**一条线**（避免"做组件查一份、加能力查另一份"）：

```
① 定类       组件（UI 形态）？能力（无形态的 useXxx / 平台 API）？→ 决定走 SOP v2 还是 G-32 清单
② 对账       ★先查存量（S7 存量对账纪律）——已实现的不重写，只补缺口（判据：grep + PRIMITIVE_CATALOG）
③ 语义登记   组件→IR props / 能力→CapabilityHooks 签名（唯一权威源）
④ 实现       组件按 SOP v2 的 2.1–2.4（属性/双端/演示/文档）；能力按 G-32 三端+Result<T>
⑤ 配套断言   属性映射 / 事件契约 / 行为 各有单测，且**破坏性验证**过
⑥ 三端验证   Web（Playwright）+ MP（模拟器）+ App（真机/截图），结论一致
⑦ 门禁       组件：check:mp-attrs / showcase-api-table / test:e2e:showcase
             能力：check:capability-golden / check:bridge-ext / check:capability-priority / tsc
⑧ 文档       演示页 + API 表 ⊇ defineProps/defineEmits（组件）；docs/generated 映射（能力）
⑨ 归档       任务板 done + 决策号 + 推进统计
```

**不可跳项的判据**（来自两份既有规范，此处只汇总）：
- SOP v2 的 13 步 + T1–T27 陷阱表（`docs/proteus-end-alignment-plan/04-batches.md`）；
- G-32 铁律 G-32.1–5 + CMP009–012 审查清单（`docs/proteus-semantic-primitives-plus-plan/rules.md`）；
- Skyline 全部坑单一总账：`docs/skyline-pitfalls.md`。

## 6. 机器判据总表

**每个环节由哪个门禁兜底**（"接线不靠记忆"）：

| 关 / 原语 | 门禁 | 兜住什么 |
|---|---|---|
| 关 0 立项 | `pnpm check:memory`（速览/归档）· 决策号锚点 | 详细叙事内联回主文件 / 决策断链 |
| **关 1 认领 + 4.2/4.3/4.5** | **`pnpm check:ai-tasks`（★本规范新增）** | 无人认领 / 撞车 / done 无决策号 / 边界 typo |
| 关 2 实施 | `pnpm test:coupled`（改内核自动建议+**真跑**配套断言）· `check:gates-sync` | 改了内核忘同步配套断言 |
| 关 3 自验证 | 各链路**定向门禁**（第 5 节）· `check:no-blind-wait` / `check:loop-guard` / `lint` | 盲等 / 循环卡死 / 坏味道新增 |
| 关 4 独立验证 | ai-cobuild 的 `check:cobuild` / `check:ledger`（C 链）· 人工/子代理复测（A 链，**记录制**） | "自测当独立验证" |
| 关 5 交付 | `check:pushed`(+`:strict`) · `check:deploy-pending` · 发布 `pnpm ledger:check` | 提交≠交付 / 官网未上线 / 未收口发布 |
| 关 6 追溯 | `check:ai-tasks`（决策号存在性）· `check:stats`（数字不漂移） | 改了说不清 / 官网数字过时静默上线 |
| 全链收尾 | `pnpm verify`（一轮工作收尾跑一次，≈10 分钟） | 本地盲区（含根 vue-tsc） |
| 行为底线 | `Skill(ai-efficiency-rules)` + 三个 hook（sleep/全量测试/全量门禁） | 盲等 / 重复全量跑 |

> ★**新增门禁必须接线** → `check:gates-sync` 会拦（未接 CI 且未在 `LOCAL_ONLY` 说明 ⇒ 当场红）。

**`check:ai-tasks` 的判据（本规范新增，SSOT = `scripts/check-ai-tasks.mjs`）**：
1. 任务板不存在 ⇒ 打印引导 + 退出 0（干净克隆友好，同 `check:hook-wiring`）；
2. schema：`id` 唯一且格式合法、枚举值合法、`scope` 非空；
3. `in_progress` ⇒ `owner` 非空；`done` ⇒ `decision` 是数字 + `verification` 非空；
4. **`done` 的 `decision` 号必须在 `decisions.md` 真实存在**（追溯闭合）；
5. **任意两个 `in_progress` 任务 `scope` 不重叠**（防撞车）；
6. `scope` 引用的**顶级路径存在**（防 typo / 指向已删目录）；`related` 指向存在的 id。

## 8. 诚实边界 / 演进

- **本文件不创造新的机器设施，只统一已有判据 + 新增 `check:ai-tasks` 一个**。"完整模型"的价值在**接线与索引**，不在堆文档。
- **独立性是概率不是保证**：多 AI 的"独立验证"降低相关偏差，不等于零偏差（无法真独立时标 `verification=partial`）。
- **任务板是协调工件，不是进度看板**：它只回答"谁在做、边界在哪、做完没、对应哪条决策"——不做甘特图/工时。
- **`check:ai-tasks` 的重叠检测是保守近似**（按 glob 静态前缀判嵌套/共享），刻意**宁可少报误报**：它拦"显然撞车"，不追求形式化互斥证明。
- **演进**：随 `test:coupled` 的 `COUPLING` 表扩充，4.2 的边界可进一步"从代码生成"；将来可把任务板并入 `check:cobuild` 的共用对账框架（同一套"断点→判据"范式）。
- **与 `Skill` 的关系**：`ai-efficiency-rules` = 行为底线（对**所有**动作生效）；`ai-cobuild` = **C 链**细则；**本文件 = A 链主体 + 三链总模型**。会话启动仍走 `AGENTS.md §0`（先挂 Skill、读 `PROJECT_MEMORY.md`）。
