# 规约更新提案（G-25 · TV 焦点）

> 本文件是**提案**，不是已生效的规约。合入 `docs/proteus-architecture.md` 需按规约更新流程走。
> 目的：把本方案的三个**结构性决定**写成可长期沿用的规则，而不是一次性实现细节。

---

## 1. 拟新增原则（编号待定，接 #13.90 之后）

### 原则 A · **焦点是渲染无关原语，由形态画像推导**

> **内容**：焦点导航**不得**依赖 DOM、CSS 伪类或某个平台的焦点系统。
> 其唯一输入是 `(candidates: FocusRect[], currentId, direction)`，几何来源由平台注入。
> 焦点的**可用性与形态**由 `formfactor` 的 `input` 字段推导（`input:'remote'` ⇒ 焦点必需；`'touch'` ⇒ 可选）。

**为什么**：
- 这是本仓「一套语义适配不同形态」在 TV 上的**唯一可证伪点**——手机 demo 证明不了，因为所有框架都能跑手机。
- 现有实现（`packages/fluid/src/focus-nav.ts`）已经"吃矩形"，但**归属**是组件配套，没有原则约束；
  一旦有人图省事在组件里写 `el.focus()` + CSS 选择器，跨端一致性立刻失效且**不会有任何门禁报警**。

**可判定性**：`nextFocus` / `ensureVisible` 的入参不含 DOM 类型；`@proteus-vue/focus` 不得 import `vue` / `dom` 类型。

---

### 原则 B · **平台输入归一只在宿主做一次**

> **内容**：平台键码 → 语义键（`up/down/left/right/confirm/back/menu`）的映射**只能存在于宿主**。
> JS 层**不得**出现 `KEYCODE_*` / `keyCode` / `which` 等平台标识。
> 同一语义的**多个平台键码必须全部映射**（如 `confirm` = 23 与 66），并用判据逐项锁住。

**为什么**：
- 归一散落 = 三端语义漂移（本仓已有先例：键盘推送通道装了没人收，决策 #1074）。
- 「只认一个键码」是**现场最难归因的缺陷**：某类盒子上 OK 键完全无反应，日志里一切正常。

**可判定性**：静态门禁扫 `packages/**`（排除 `hosts/**`）不得出现平台键码常量。

---

### 原则 C · **性能判据必须分栏到「JS / 宿主 / 渲染」**

> **内容**：任何"响应时间 / 长任务"类判据，**不得**只报一个总时间。
> 至少分三栏：`js_sync`（JS 同步段）、`host_*`（宿主 native 各相位）、`focus_to_paint`（到下一帧呈现）。
> 归因顺序：先看哪一栏大，再定优化对象；**禁止**在未归因前引入调度原语。

**为什么**：
- 本仓实测：iOS mount 30–93ms，而 **JS 同步段仅 ~3ms**（#1099/#1100）。
  同一条「长任务 100ms」的读数，可以是"JS 卡"也可以是"宿主卡"，**结论完全相反**。
- 已在 #1099 花一整轮纠正过一次；本原则把它变成**默认要求**，防止第四个场景再犯。

**可判定性**：报告 schema 里，性能类字段必须成组出现；只出总数 ⇒ 判据装置不合格。

## 4. 为什么**不**新增 G 号

| 判据（本仓 §8 与 G 编号纪律） | 本方案 |
|---|---|
| 是否引入新的**独立性维度**（新的"不绑 X"）？ | ❌ 否。TV 焦点是 G-25「三维断点 `F=remote`」的**直接下游**，不是新的 SPI/新维度 |
| 是否有独立的 SPI / 可插拔后端？ | ❌ 否。焦点引擎是**单一算法 + 多端几何注入**，不是后端矩阵 |
| 先例 | ✅ `proteus-end-alignment-plan` 之于 G-31（属性级补充，**不占新 G 号**） |

⇒ **登记为 G-25 的执行级子计划**，在 G-25 行内加指针。
