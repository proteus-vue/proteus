# 图片内存治理

> **LRU ≠ 安全**。缓存策略只管淘汰顺序，不管解码后像素总量。Proteus 按字节预算 + 三级缓存统一治理。

---

## 现状：uni-app x 的缓存口径

| 平台 | 实现 | 缓存策略 |
|------|------|---------|
| Android | Fresco 2.5.0 | 自动清理 |
| iOS | SDWebImage 5.10.0 | 默认 7 天缓存 |
| 鸿蒙蒸汽模式 | imageknifepro | 内存 256 个 / 磁盘 512 个，LRU |

⚠️ **"256/512" 是对象数配额，非 MB**。单张图分辨率、像素格式、透明通道可显著改变实际内存。HarmonyOS 官方明确：缓存上限过大 → 内存占用过高 → 影响稳定性。

---

## 峰值来源拆解

```
总内存 = 原始字节 + 解码像素 + 纹理/图层
```

- **原始字节**：下载缓冲区、base64、动图帧
- **解码像素**：Bitmap / ImageBitmap（**这才是大头**，一张 4K 图 ≈ 4K×4K×4 = 64MB）
- **纹理/图层**：GPU 上传后的 texture + 合成层

**常见触发**：大图下载、base64 内联、动图、未降采样的 `aspectFill`、列表快速滚动（并发解码）、`will-change: transform`（额外合成资源）。

> `lazy-load` 只控制可见性，**不限制并发解码**——快速滑动仍可能瞬间创建大量解码任务。

---

## 三级缓存架构

```
L0  原始字节缓存   (默认关闭，按字节 LRU)
L1  解码 Bitmap 池 (对象数 + 字节双限额)
L2  磁盘缓存       (对象数 LRU，不直接构成运行时峰值)
```

- **L1 双限额**：既限对象数（防碎片），也限**总字节数**（防峰值）
- 预算纳入**页面级 + 全局级**统一 Budget（见 `04-resource-owner-model.md`）
- 鸿蒙 imageknife 内存缓存、ArkUI 解码缓存、图形缓存**统一计入**，不独立配置

## 治理策略

### 1. 降采样（最优先）

解码前按显示尺寸计算 `inSampleSize`，**不解码超过显示需要的分辨率**：
```
target = min(displayWidth * density, sourceWidth)
sample = sourceWidth / target   →  取 2 的幂
```

### 2. 并发解码限额

- **页面级 + 全局级两级信号量**（默认 4 并发）
- 快速滚动时**撤销不可见 item 的未完成解码请求**
- 列表场景：低分辨率占位 → 进入视口后加载高清

### 3. 分块解码（超大图）

超阈值图片（如 > 2048px）按瓦片分块，只解码当前可见瓦片。

### 4. trim 策略

| 触发 | 动作 |
|------|------|
| 页面隐藏 | 保留可见窗口，trim 其余 |
| 页面销毁 | trim 至窗口（仅保留当前） |
| `onTrimMemory` / 内存压力 | 清除全部不可见 + L0 原始字节 |
| 后台 | 释放所有临时 + 降采样保留 |

### 5. 引用追踪（诊断关键）

每个 Bitmap 记录：`request → decode → cacheKey → displayView → pageOwner`

→ "退出页面后 Bitmap 为何仍存活"**可直接定位**（详见 `09-diagnostics-ci.md`）。

## 对齐现有 plan

- **Glass**：玻璃组件的噪声纹理、离屏模糊缓冲**纳入同一页面预算**，避免各自在限额内增长、合起来突破设备上限
- **Performance**：图片解码峰值并入帧预算 / 页面预算统计
- **Compiler**：构建期检测超大图片资源（无 `width/height`、超分辨率），给出降采样建议

---

## 不做项（诚实边界）

- ❌ 不宣称"自动永不 OOM"——只保证预算可配置、峰值可观测、trim 可触发
- ⏸ 具体字节阈值由**运行时特征检测 + 设备分级**决定，不写死常量
- ⏸ 鸿蒙/各小程序基础库的深层缓存细节，由 Blueprint 验证阶段补全
