# G-43 资源所有权模型与内存治理

> **定位**：G-42 管「页面怎么销毁」，G-43 管「资源归谁、谁释放、怎么看见」。
> 两者合并才是完整的内存治理体系。
>
> **规划体系**：56 份 plan + 1 哲学 + 1 规约 + 1 官网
> **方法论**：原则 #0 第七次泛化 —— 不绑内存管理范式

---

## 1. 动机：三个真实痛点

### 1.1 开发者难以管理内存

传统跨端框架下，开发者必须**手动配对**资源的申请与释放：

```js
// 定时器：申请了要记得清
const timer = setInterval(tick, 1000)
onUnmounted(() => clearInterval(timer))   // ← 忘了就泄漏

// 事件监听：绑定了要记得解绑
emitter.on('update', handler)
onUnmounted(() => emitter.off('update', handler))   // ← 忘了就泄漏 + 幽灵回调

// 原生句柄：创建了要记得释放
const handle = native.createCamera()
onUnmounted(() => native.releaseCamera(handle))   // ← 忘了就泄漏
```

**根因不是开发者粗心，是"配对"这个模式本身就是错的**——
只要申请和释放是两个分离的动作，就存在中间路径（异常、提前 return、路由跳转）导致漏掉释放。

### 1.2 出问题不好排查

传统 DevTools 给的是**堆快照**，开发者需要做差分对比、靠经验猜：

```
快照1 → 操作 → 快照2 → 对比 → 发现 ArrayBuffer 涨了 8MB
→ 但谁持有着它？为什么没被 GC？在哪行代码申请的？
→ 靠猜。运气好半小时，运气不好一整天。
```

**根因**：GC 只知道"可达性"，不知道"所有权意图"。
一个 8MB 的 ArrayBuffer 没被回收，GC 无法告诉你它是**还在用**还是**忘了放**。

### 1.3 DevTools 看不到内存使用链

堆快照给你的是**一堆对象**，不是**一条引用链**。
开发者真正需要的是：

```
谁持有它 → 它又被谁持有 → 这条链上哪一环是意外的 → 对应哪行源码
```

**传统方案给不了这个信息，因为引用关系从来没被显式登记过。**

### 1.4 G-40 已经把这个洞撕开了

G-40 定义了零拷贝通道：

```js
const buf = host.allocateShared(8 * MB)   // 跨载体共享底层字节
// ↓
// 两个载体（JSI / AOT）都能访问
// 但……谁负责释放？什么时候释放？
// ★ G-40 没有定义。这不是理论问题，是明天写代码就会踩的坑。
```

**G-43 必须回答这个问题。**

## 2. 核心澄清：不是用所有权替代 GC

这是最容易误解的地方，必须先说清楚。

### 2.1 JS 堆内对象由 GC 管，不该引入所有权

```js
const user = { name: 'Alice', age: 30 }
const list = [1, 2, 3]
const text = 'hello'
```

这些对象的内存由 GC 自动管理，**引入所有权模型是自找麻烦**——
GC 已经做得很好，强行加所有权只会增加心智负担。

### 2.2 真正的痛点全在 GC 管不到的地方

| 资源类型 | GC 能管吗 | 现状痛点 |
|---------|----------|---------|
| 普通 JS 对象 / 字符串 / 数组 | ✅ 能 | **无需所有权** |
| **原生 View / Widget 句柄** | ❌ 不能 | 页面销毁漏释放 → 泄漏 |
| **ArrayBuffer（G-40 零拷贝）** | ❌ 不能 | **谁释放？G-40 未定义** |
| 定时器 / 订阅 / 事件监听 | ❌ 不能 | 忘清 → 泄漏 + 幽灵回调 |
| 文件句柄 / 数据库连接 | ❌ 不能 | 忘关 → 资源耗尽 |
| 音视频 / 传感器流 | ❌ 不能 | 忘停 → 耗电 + 崩溃 |
| 跨页面大对象引用 | ⚠️ 能但不会回收 | 页面销毁仍被 store 持有 |

**G-43 的治理对象 = 上表中所有"GC 管不到"的资源。**

### 2.3 一句话定位

> **G-43 不是替代 GC，是治理 GC 的盲区。**
> GC 管"可达性"，所有权管"意图"。
> 两者互补，不冲突。

## 4. Rust 模型 → Proteus 的映射

### 4.1 对应关系

| Rust 概念 | Proteus 对应 | 已有基础 |
|----------|-------------|---------|
| Ownership（唯一所有者） | **IR 实例拥有其全部边界资源** | ✅ G-42 已确立 |
| Move（所有权转移） | 资源从页面 A 转给页面 B | ❌ G-43 定义 |
| Borrow（借用） | 组件临时借用，不得长期持有 | ❌ G-43 定义 |
| Lifetime（生命周期标注） | 页面 / 组件生命周期 | ⚠️ 运行期有，编译期无 |
| Borrow Checker | 编译期静态分析 + 运行时兜底 | ⚠️ G-42 有 L-01~L-05 雏形 |
| `Drop`（确定性析构） | **五原子销毁** | ✅ G-42 已实现 |
| `Rc` / `Weak` | 共享 / 弱引用，打破循环 | ❌ G-43 定义 |

### 4.2 关键结论

> **G-42 已经实现了 Rust 模型里的 `Drop`。**
> G-43 补齐的是剩下四个：**Ownership / Move / Borrow / 借用检查器**。

这不是从零开始，是在已有地基上建第二层。

## 5. 三层次设计

```
┌─────────────────────────────────────────────────┐
│ 层次③  可观测层                                   │
│        DevTools 所有权图 / 泄漏路径定位            │
│        → 把不可见变可见                           │
├─────────────────────────────────────────────────┤
│ 层次②  检查层                                     │
│        编译期借用检查（PSS 内完备）                │
│        + 运行时兜底（PSS 外）                     │
├─────────────────────────────────────────────────┤
│ 层次①  语义层                                     │
│        Owned<T> / Borrow<T> / Weak<T>            │
│        transferTo / borrow / drop / 自动回收      │
└─────────────────────────────────────────────────┘
```

### 5.1 层次①：资源所有权 API

**默认安全，需要时才显式管理**：

```ts
// 【默认路径】框架代管 —— 99% 场景，零心智负担
const timer = pageContext.timer(1000, tick)       // 页面销毁自动清
const sub   = pageContext.subscribe(ch, handler)  // 自动解绑
const req   = pageContext.fetch(url)             // 自动 abort

// 【显式路径】大资源 / 跨页面场景 —— 类型系统强制你处理释放
const buf: Owned<ArrayBuffer> = pageContext.alloc(8 * MB)

buf.transferTo(otherPage)     // ★ Move：转移后本页不可再用
buf.borrow()                  // ★ Borrow：临时借用，有作用域限制
buf.drop()                    // ★ Drop：确定性释放

// 弱引用打破循环
const ref: Weak<PageIR> = pageContext.weak(otherPage)
```

**关键点**：`transferTo()` 之后再访问 `buf`，是**编译期错误**——借用检查器在起作用。

### 5.2 层次②：借用检查（分层保证）

这是本次最重要的升级，见下节。

### 5.3 层次③：DevTools 所有权图

```
┌─ Proteus DevTools · Ownership Graph ─────────────┐
│                                                  │
│  PageB (alive)                                   │
│   ├─ Owned<ArrayBuffer> 8MB      ← 🟢 持有者     │
│   │    ↑ moved from PageA                        │
│   ├─ Owned<VideoStream>                          │
│   │    └─ 🟡 borrowed by ComponentX (2.3s)       │
│   └─ Weak<PageA>  ← 🔴 悬垂，下次 GC 清理         │
│                                                  │
│  ⚠️ 检测到 1 处泄漏路径：                          │
│     PageB.timer → closure → pageA.context        │
│     （已定位到 ProductCard.vue:47）                │
└──────────────────────────────────────────────────┘
```

**为什么传统 DevTools 做不到**：因为它只有"可达性"，没有"意图"。
我们知道哪个是 Owner、哪个是 Borrow、哪个是 Move 过来的——
**所以能直接指出泄漏路径和源码位置，而不是给你一堆快照让你猜。**

## 6. 分层保证：PSS 让完备检查成为可能

### 6.1 问题：任意 JS 做不了完备的编译期检查

闭包捕获、动态属性、`eval`、原型链操作……
这些让静态分析在**一般情形**下不可判定。

所以在"任意 JS"下，借用检查只能"覆盖主路径 + 运行时兜底"。

### 6.2 鸿蒙 ArkTS 的启示：限制换能力

ArkTS 通过**禁止部分动态特性**，换来了 AOT 编译能力：

| ArkTS 禁止 | 换来的 |
|-----------|--------|
| `any` / `unknown` | 完整类型推导 |
| structural typing | 静态布局优化 |
| 对象动态增删属性 | 隐藏类稳定，AOT 可行 |
| 部分闭包捕获场景 | 更精确的作用域分析 |

**代价是表达力，收益是静态可分析性。**

### 6.3 我们的方案：Proteus Safe Subset（PSS）

定义一个**受限子集 PSS**，模块可选择性声明启用：

```ts
// page.config.ts
export default definePageConfig({
  safeSubset: 'strict'     // 'off' | 'loose' | 'strict'
})
```

| 模式 | 限制 | 借用检查保证 |
|------|------|-------------|
| `off` | 无 | 运行时兜底 |
| `loose` | 禁 `any` / 动态属性增删 | 覆盖主路径 |
| **`strict`** | 完整 PSS 限制 | **编译期完备** ✅ |

### 6.4 这把我上轮的"做不到"变成了"分场景做到"

上一版我说"JS 无法做完整的编译期借用检查"——
**这句话在"任意 JS"下成立，但 PSS 内不成立。**

| 层级 | 范围 | 保证 |
|------|------|------|
| **PSS strict 内** | 声明启用的模块 | **编译期完备** ✅ |
| PSS loose / off | 其余模块 | 运行时兜底 + 100% 可观测 |

**这是分层的、渐进的、可选择的** —— 不是强制所有人改写，
而是"想要强保证的模块，付出受限表达力的代价"。

## 7. 鸿蒙设计哲学的系统性吸收

用户提出"鸿蒙那套也可以吸收到框架哲学里"——
这不是简单罗列特性，而是**四个设计范式的迁移**。

详见 `harmony-philosophy.md`，此处摘要：

| # | 鸿蒙设计 | 我们的吸收 | 价值 |
|---|---------|-----------|------|
| 1 | **ArkTS 限制换能力** | **Proteus Safe Subset** | ★ 让借用检查从"兜底"升级为"完备" |
| 2 | **Stage / Ability 生命周期标准化** | 映射为 G-42 容器生命周期的官方实现 | 生命周期契约有现成参照 |
| 3 | **元服务 / 原子化服务** | G-42 新增 `AtomicService` 容器形态 | 可分可合、免安装 |
| 4 | **分布式软总线** | **`Owned<T>.transferToDevice()`** | ★ Move 语义的跨设备版本 |

### 7.1 第 4 点最锋利：跨设备所有权转移

传统跨设备的做法是**"在 B 设备重新加载一遍"**：
- 状态丢失
- 资源重建
- 用户感知到"重新开始"

有了所有权模型，跨设备流转变成**所有权转移**：

```ts
// 传统：B 设备重新加载（状态丢、资源重建）
deviceB.load('page', { fresh: true })

// Proteus：所有权转移（状态不丢、资源不重建）
const buf: Owned<ArrayBuffer> = pageA.ownedBuffer
await buf.transferToDevice('deviceB')
// → 底层字节通过分布式通道迁移
// → 原设备资源自动 drop（Move 语义）
// → 目标设备直接接管，无需重建
```

**这是 Move 语义从"同进程"延伸到"跨设备"，是 G-43 最有想象力的部分。**

| Plan | 协同点 |

## 9. 铁律摘要（详见 rules.md）

| 编号 | 铁律 |
|------|------|
| **G-43.1** | 边界资源必须归属某个 Owner，禁止无主资源 |

| **G-43.4** | 默认路径框架代管，业务零心智负担 |

| **G-43.6** | 确定性 Drop，禁止依赖 GC 时机 |

## 10. 诚实边界

| 限制 | 说明 |
|------|------|
| **PSS 外无法完备检查** | 动态 JS 下借用检查只能兜底，这是可判定性的固有限制，不是设计缺陷 |
| **渐进采用成本** | 存量代码启用 strict 需要改造；设计为可选，非强制 |
| **Vue 响应式交互** | `ref`/`reactive` 包装 `Owned<T>` 时，代理可能破坏所有权语义，需专项设计（见 safe-subset.md §6） |
| **跨设备转移的真实性能** | `transferToDevice` 的实际开销依赖分布式通道实现，本轮为接口定义 + 模拟验证，非实测 |
