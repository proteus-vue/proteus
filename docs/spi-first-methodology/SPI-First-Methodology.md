# SPI-First 工程方法论

> **副标题：把"拆分量化、逐个攻破、迁移复用"从经验升为方法**
> **定位：Proteus 体系的元方法论（Meta-Methodology）**
> **Status: v1 — 2026-09-03**

---

## 0. 这份文档是什么

Proteus 框架在成长过程中，重复应用了同一种拆分手法二十次：

```
G-27/37  不绑渲染引擎       →  RenderBackend SPI
G-29/38  不绑编译器         →  CompilerBackend SPI
G-31/32  不绑平台 API       →  Native Capability SPI
G-39     不绑宿主运行时      →  HostRuntime SPI
G-40     不绑执行载体       →  ExecutionCarrier SPI
G-42     不绑容器形态       →  HostContainer SPI
G-43     不绑内存管理范式    →  Ownership SPI
G-44     不绑测试实现       →  TestBackend SPI
G-45     不绑基座形态       →  DevHost / DynamicBackendModule SPI
G-46     不绑资源容器形态    →  ResourcePool SPI
G-47     不绑测试层级       →  CombinedTest（Backend × Pool 组合）
G-48     不绑小程序运行时形态 →  Runtime SPI + PlatformAdapter SPI
G-49     不绑隔离强度       →  SandboxBackend / CapabilityBridge
G-50     不绑平台/生态形态   →  DeveloperPlatform SPI + AppPackage
G-51     不绑验证执行环境    →  TestIRRunner
G-52     不绑设备形态/验证维度 →  DeviceMatrixRunner（executeOn）
```

起初这只是"我们框架的架构习惯"。后来发现：**这二十次是同一个动作的重复**。把它抽出来、剥离 Proteus 依赖，就得到了本文——一套**不依附于任何具体系统、可套用到任何大工程的通用工程方法论**。

本文的目标读者：面对一个复杂工程、想让它**可控、可替换、可演进**的人。读完你应该能：

1. 扫描任意系统，定位它的"硬编码耦合点"清单；
2. 把任意一个耦合点按五步法改造为可插拔 SPI；
3. 用 conformance 把"可替换"从约定变成机器强制；
4. 判断一个已有的 SPI 是真 SPI 还是**假 SPI**（见 §4）。

---

## 1. 核心洞察：拆分只有沿着"耦合点"切才有效

> **不是随便切模块，而是沿着"接口与实现的耦合点"切。**

"模块化"人人会做——把代码分成 `utils/`、`services/`、`models/` 几个目录。**但这种切法不释放复杂度**，因为切完之后，业务层仍然直接依赖具体实现。换个数据库、换个 UI 库、换个消息队列，改动依然会扩散。

真正的杠杆点只有一个问题：

> **"如果我要换掉 X，需要改多少文件？"**

- 换数据库 → 要改 200 个文件？**耦合点。**
- 换 UI 库 → 要改 3 个适配器？**已解耦。**
- 换鉴权方案 → 要改每个业务模块的 if/else？**耦合点。**

**凡是"改动会扩散到业务层"的，都是候选。** 方法论的全部工作，就是把候选逐个转换成 SPI。

为什么这套切法在**任何**工程里都存在？因为**所有活过十年的大工程，最终都自己长出了这套结构**：

| 系统 | 它自发长出的 SPI |
|------|-----------------|
| 操作系统 | 驱动模型（Driver Model） |
| 数据库 | 存储引擎（Storage Engine） |
| 编译器 | 后端（Backend） |
| IDE | 插件系统（Plugin System） |
| 浏览器 | 渲染引擎 / JS 引擎接口 |
| 消息队列 | Broker / Protocol 插件 |

**它们不是设计了"SPI-First"，而是被复杂度逼到了同一个结构上。** 我们只是把这个结构显式化、可重复、配上了验证手段。

## 2. SPI-First 五步法

### 第一步：找耦合点（The Coupling Audit）

**动作**：扫描系统，列出所有"换 X 要改很多文件"的 X。

**量化工具**：`grep -c "具体实现名" **/*.ts` —— 某个 SDK / 库 / 服务的名字出现在多少业务文件里。**出现次数越高，耦合越深，优先级越高。**

**输出**：一张候选表，形如：

| 耦合点 | 具体实现名 | 业务文件出现数 | 优先级 |
|--------|----------|--------------|--------|
| 支付 | alipay | 37 | P0 |
| 存储 | aws-sdk S3 | 24 | P1 |
| 消息队列 | kafka | 18 | P1 |
| 鉴权 | 硬编码 isAdmin | 散落各处 | P0 |

**判定原则**：**≥ 2 个文件直接引用具体实现 = 候选**；**1 个适配器文件引用 = 已解耦，无需处理**。

---

### 第二步：语义收敛（Define the Semantic）

**动作**：定义"做什么"，**不**定义"怎么做"。接口必须用**业务语言**描述，禁止用**实现细节**描述。

**反例**（泄漏实现）：
```ts
interface SaveToS3(bucket: string, key: string)
```
↑ 接口里出现了 `S3`、`bucket`、`key` —— 换成别的对象存储时，接口本身就要改。**这是假抽象**。

**正例**（纯语义）：
```ts
interface StoreArtifact(id: string, bytes: Uint8Array): StoredRef
```
↑ 接口只说"存一个产物、返回一个引用"。后端可以是 S3、OSS、本地磁盘、内存。**业务层零改动。**

**三条规则**：

1. **接口命名禁用厂商/技术名词**（S3、Kafka、React、MySQL）→ 用领域动词（Store、Publish、Charge、Render）
2. **参数类型用领域类型**，不用 SDK 类型（`Uint8Array` 而非 `S3.PutObjectRequest`）
3. **错误用统一领域错误码**，不用底层异常类型（避免上层 catch 具体异常）

**这是五步里成败最关键的一步。** 接口一旦含实现名词，后端就无法替换——Proteus 二十次泛化里每次都要重新守住这条（G-07 的 `<pg-glass>` 而非 `backdrop-filter`、G-43 的 `Owned<T>` 而非 `Rc`/`Box` 都是同一条原则的应用）。

---

### 第三步：可插拔后端（Pluggable Implementations）

**动作**：为 SPI 提供**至少两个后端实现，其中一个必须是 Headless / Mock**。

**为什么必须两个？——单后端 SPI 是假 SPI。**

一个只有单一实现的"接口"，从未被验证过可替换性。等到真要换时才发现：接口里偷偷引用了实现细节、业务代码绕过了接口直接调用、conformance 没写所以行为不一致。**"可插拔"是测出来的，不是声明出来的。**

**Proteus 里的实例**：
- G-44 TestBackend：Node / JSI / AOT / Host / Device 五个后端，含 Headless
- G-45 DynamicBackendModule：装载前必须能跑 conformance 快检
- G-40 ExecutionCarrier：JSI + AOT 两个，暴露了线程亲和性的能力差异

**最小配对**：`RealProvider`（生产实现）+ `MockProvider`（测试/降级实现）。

---

### 第四步：conformance 验证（The Verifier）

**动作**：为每个 SPI 编写一套 **conformance 测试**——**任何后端实现都必须通过同一套测试才能接入**。

**这是把"拆分"变成"可量化、逐个攻破"的核心一步。**

- **没有 conformance** = 接口靠约定俗成，会随时间漂移（99% 项目的命运：接口签名没变，但行为悄悄分化）
- **有 conformance** = 接口由机器强制，实现可以自由替换而不破坏契约

**conformance 用例的设计原则**：不测"实现细节"，只测"语义契约"。即：**同一份测试代码，对所有后端都跑，结果都可判定。**

**Proteus 里的实例**（可直接迁移）：

| SPI | conformance 要点 |
|-----|-----------------|
| RenderBackend | 同一棵 IR → 各后端产出同 shape 的渲染结果（G-27 conformance / RND002） |
| TestBackend | 同一份 Test IR → 各后端判定结果一致（G-44） |
| DynamicBackendModule | 装载时跑快检，同能力须产出同 shape 结果（G-45 NAT-C） |
| Ownership | use-after-move、活跃借用下 drop 等在所有载体下都被拦截（G-43） |

**把"质量"从"靠人记住"变成"靠断言强制"——这一步是方法论的杠杆点。**

---

### 第五步：诚实边界（The Honesty Layer）

**动作**：**显式声明这套抽象不解决什么。**

**为什么必须有？** 抽象必然有成本——间接层、调试难度、学习曲线、多后端的行为差异。**不承认成本的方法论，会在规模上来时反噬。**

**Proteus 里的实例**：
- G-40 CMP046：未实测的性能数据**禁止对外宣称**（批处理收益明确标为"工程推算，非实测"）
- G-45：明确"Install-Once 是**开发调试 + 内部分发**语义，**不是线上热更新**"（App Store 2.5.2、鸿蒙 HSP 须随宿主打包）
- G-43：承认 JS 无法做完整编译期借用检查，采用"编译期覆盖主路径 + 运行时兜底 + 100% 可观测"的分层策略

**诚实边界让使用者能做出明知的选择，也防止方法论被包装成"银弹"。**

**每个 SPI 至少声明三条边界**：
1. **性能边界**：抽象的运行时开销（间接调用、序列化）是多少？实测数据？
2. **能力边界**：后端之间能力不齐时怎么办？（G-37 的 `Capabilities` 表、降级后端兜底）
3. **适用边界**：什么场景下这套 SPI **不值得**引入？（过度设计的判定）

## 3. 应用实例：把方法论套到 Proteus 之外

### 实例 A：老电商系统的支付模块（硬编码支付宝，37 处引用）

| 步骤 | 动作 |
|------|------|
| ① 找耦合点 | `grep -c alipay` → 37 处 → P0 |
| ② 语义收敛 | `interface PaymentProvider { charge / refund / query }`，**接口内零 alipay 专有名词** |
| ③ 可插拔 | `AlipayProvider`（搬入现有逻辑）+ `WechatProvider`（新增）+ `MockProvider`（测试） |
| ④ conformance | `payment-conformance.ts`：重复扣款幂等、部分退款、网络中断重试等 20 个用例。**加微信支付 = 跑同一套测试即可证明可用** |
| ⑤ 诚实边界 | "SPI 不解决支付渠道的合规差异（如微信/支付宝的异步通知验签），合规由各 Provider 自行负责" |

**结果与 G-27 定义渲染后端、G-28 定义 NativeBackend、G-44 定义 TestBackend —— 结构完全同构。** 做完你会发现：文档结构、命名、验证方式都一模一样。

### 实例 B：数据管道（硬编码 Kafka）

| 步骤 | 动作 |
|------|------|
| ① | Kafka 出现在 18 个业务文件 → P1 |
| ② | `interface MessageBroker { publish / subscribe / ack }` |
| ③ | `KafkaBroker` + `InMemoryBroker`（测试/降级）+ `RedisStreamsBroker`（备选） |
| ④ | conformance：at-least-once 语义、消费者组重平衡、消息顺序（partition 内） |
| ⑤ | "SPI 不解决 Exactly-Once；跨 Broker 的事务性产出需业务侧幂等" |

### 实例 C：前端状态管理（硬编码 Redux）

| 步骤 | 动作 |
|------|------|
| ① | Redux 直接 import 散落 50+ 文件 |
| ② | `interface StateStore { getState / dispatch / select }` |
| ③ | `ReduxStore` + `ZustandStore`（迁移期并行）+ `MockStore` |
| ④ | conformance：reducer 纯函数、订阅通知顺序、selector 缓存 |
| ⑤ | "SPI 不解决派生状态的性能，selector 复杂度由业务自管" |

**三个实例跨越支付/中间件/前端，五步结构完全一致 —— 这就是"可迁移"的含义。**

## 4. 如何识别"假 SPI"（Anti-Patterns）

> 一个只有接口名、没有 conformance、只有单一实现的抽象，**是假 SPI**。它不释放复杂度，只是把耦合点藏到了一个更深的文件里。

| 假 SPI 信号 | 为什么是假的 | 修正 |
|------------|------------|------|
| 只有**一个**实现 | 可替换性从未被验证 | 加 Mock/Headless 实现 |
| 接口里含**厂商/技术名词** | 换实现时接口本身要改 | 用语义动词重命名（§2 第二步） |
| **没有 conformance** | 行为会随时间漂移分化 | 写契约测试套件 |
| 业务代码**绕过接口**直接调底层 | 抽象有漏洞，等于没抽 | 静态扫描禁止直接引用 |
| 接口**只定义类型，不定义行为** | 各实现行为不一致 | conformance 用例化行为 |
| 切换后端**需要改业务代码** | 解耦不彻底 | 适配器层 + 依赖注入 |

**自检清单**（应用到你自己的项目，逐条打勾）：
- [ ] 每个 SPI 是否有 ≥2 个后端？
- [ ] 每个 SPI 是否有 conformance 套件？
- [ ] 接口命名是否 100% 无技术名词？
- [ ] 是否存在 `grep "具体SDK"` 仍能命中业务层的情况？
- [ ] 新加一个后端，是否需要改动业务代码？

**任一条不达标 → 该 SPI 仍是耦合点，未释放复杂度。**

## 5. 方法论自身的诚实边界

这套方法论**不是银弹**，以下场景不值得引入 SPI：

| 场景 | 为什么不适用 |
|------|------------|
| **一次性脚本 / MVP 原型** | 抽象成本 > 收益，YAGNI |
| **实现确实唯一、未来也不会换** | 单后端 SPI 是假 SPI，不如直接调用 |
| **性能极度敏感的热点路径** | 间接层开销不可接受（此时用编译期单态 / 内联） |
| **团队规模小、模块边界清晰** | 过度设计的典型症状 |

**判定原则**：**只有当"未来需要替换 / 需要多实现并存 / 需要第三方扩展"中至少一项为真时，SPI 的引入才划算。** 其余情况，直接调用更简单、更易读、更易调试。

**另一条重要提醒**：**conformance 本身需要维护**。后端越多，契约测试越重。当一个 SPI 有 6+ 后端且 conformance 用例 200+ 时，**契约演进本身会成为负担**——此时要评估是否收敛后端数量、或拆分 SPI。

## 6. 与 Proteus 的关系

Proteus 是这套方法论的**第一性证明**（existence proof）—— 二十次泛化证明五步法在**同一个系统**里重复有效。

但本文**不依赖 Proteus**：它是一份**独立、通用的工程方法论文档**，可作为任何项目的工程规范起点。

**引用关系**：
- Proteus 各 plan 是 **五步法的实例集**；
- 本文是 **五步法的抽象定义**；
- 当 Proteus 出现新一次泛化时，应**先**在此文档登记方法论变更，**再**落地到具体 plan。

> **登记补录（决策 #385）**：第 10~16 次投影（G-46~G-52：资源容器/测试层级/小程序运行时/隔离强度/平台生态/验证执行环境/设备维度）随 2026-09 批次整合入库一并补齐登记（映射表见 `proteus-mapping.md`，与 spi-first 同仓）。
> **登记补录（决策 #391）**：第 17~18 次投影（G-53 移动端验证编排：不绑设备供给方式 / G-54 框架配套开发者工具：不绑 IDE 形态）随 2026-09 批次登记；G-54 原稿自编 G-55 编号避让重编（详见其 rules.md）。

## 7. 一句话总结

> **找到系统中所有"换 X 要改很多文件"的 X，把它们逐一提升为"语义接口 + ≥2 后端 + conformance + 诚实边界"，直到业务层对任何具体实现零知识。**

**把大象切成标准块，且切法换个大象还管用 —— 这就是 SPI-First。**
