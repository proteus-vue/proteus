# SPI-First 五步法速查卡

> 面对任何大工程，按此清单操作一遍 = 完成一次方法论应用。

---

## Step 1｜找耦合点（The Coupling Audit）

```
grep -c "<具体实现名>" **/*.<ext>
```

**判定**：出现次数 ≥ 2 个业务文件 → 候选；只有 1 个适配器文件 → 已解耦。

| 候选 | 具体实现 | 优先级 |
|------|---------|--------|
| 支付 | alipay | P0 |
| 存储 | aws-sdk | P1 |
| 消息队列 | kafka | P1 |
| 鉴权 | 硬编码 isAdmin | P0 |

---

## Step 2｜语义收敛（Define the Semantic）

**接口只用业务语言，禁用技术/厂商名词。**

```
❌ interface SaveToS3(bucket, key)
✅ interface StoreArtifact(id, bytes): StoredRef
```

三条规则：
1. 命名禁用厂商词（S3/Kafka/React）→ 用领域动词（Store/Publish/Charge）
2. 参数类型用领域类型 → 不用 SDK 类型
3. 错误用统一领域错误码 → 不用底层异常类型

---

## Step 3｜可插拔后端（≥ 2 个，含 Mock/Headless）

```
RealProvider   ← 生产实现
MockProvider   ← 测试 / 降级
AltProvider    ← 备选（可选，验证可替换性）
```

**单后端 SPI = 假 SPI**（可替换性从未验证）。

---

## Step 4｜conformance 验证（The Verifier）

同一份测试代码，对所有后端都跑，结果都可判定。

**用例只测"语义契约"，不测实现细节。**

自检：加一个新后端，是否需要改业务代码？→ 若需要，SPI 未解耦。

---

## Step 5｜诚实边界（The Honesty Layer）

每个 SPI 必须声明三条：
1. **性能边界** — 间接开销多少？（实测，非推算）
2. **能力边界** — 后端不齐时如何降级？（Capabilities 表 + 降级后端）
3. **适用边界** — 什么场景不值得引入？（避免过度设计）

---

## 反模式速判（假 SPI 信号）

| 信号 | 修正 |
|------|------|
| 只有 1 个实现 | 加 Mock 后端 |
| 接口含技术名词 | 语义重命名 |
| 无 conformance | 写契约测试 |
| 业务绕过接口 | 静态扫描禁止 |
| 切换需改业务 | 加适配器 |

---

## 不适用场景（避免过度设计）

- 一次性脚本 / MVP 原型（YAGNI）
- 实现确实唯一、未来不换
- 性能极度敏感热点路径
- 小团队 + 边界已清晰

**判定**："未来要替换 / 多实现并存 / 第三方扩展" —— 至少一项为真才引入。
