# 反模式参考（Anti-Patterns）

> 每个反模式 = "以为做了 SPI-First、其实没做到"的典型症状。
> 对照自查：命中任一条 → SPI 未真正解耦，回到对应 Step 修正。

---

## AP-01｜单后端 SPI（Single-Impl SPI）

**症状**：定义了接口，但只有 1 个实现，且短期内不会有第二个。

**为什么假**：可替换性从未被验证。接口里几乎必然泄漏实现细节，等到真要换时才发现改不动。

**修正**：要么加一个 Mock/Headless 后端（强制暴露接口漏洞），要么承认它就是**内部模块边界、不是 SPI**，降级命名、去掉抽象。

**判定**：一个后端活过 6 个月没第二个 → 大概率过度设计。

---

## AP-02｜接口含技术名词（Leaky Naming）

**症状**：
```ts
interface UploadToS3(bucket: string, region: string)
interface SendViaKafka(topic: string, partitionKey: string)
```

**为什么假**：换实现时**接口本身要改**，业务层被迫跟着改 → 解耦失败。

**修正**：用语义动词 + 领域类型重命名（见 cheatsheet 命名转换表）。

**自检**：grep 接口文件，能否找到任何厂商/库/协议名？能 → 未收敛。

---

## AP-03｜无 conformance（Convention-Only）

**症状**：接口签名定义清楚，但**没有契约测试**。各实现靠"约定"保持一致。

**为什么假**：行为会随时间漂移分化。实现 A 升级后悄悄改变了边界情况处理，调用方毫无感知，直到生产环境爆炸。

**修正**：为每个 SPI 写 conformance 套件，**同一份测试对所有后端都跑**。测试只断言语义契约，不测实现细节。

**Proteus 实例**：G-27 要求同一棵 IR 各后端产出同 shape 结果；G-45 NAT-C 要求同能力同 shape。

---

## AP-04｜业务绕过接口（Leaky Boundary）

**症状**：虽然定义了 SPI，但业务代码里仍有 `import '具体SDK'` 或 `if (isPlatformX)`。

**为什么假**：抽象有漏洞，等于没抽。耦合点只是被藏到了更深的文件里。

**修正**：
1. 静态扫描规则（CI 门禁）：禁止业务层直接 import 具体 SDK
2. 适配器层收口所有底层调用
3. `grep -c` 回归检查，出现次数应趋近于 0

---

## AP-05｜接口只定义类型、不定义行为（Type-Only SPI）

**症状**：
```ts
interface Repository<T> {
  find(id: string): T | null
  save(entity: T): void
}
```
签名看起来完整，但对**空结果、并发、事务、错误**只字未提。

**为什么假**：两个实现的"行为"可以天差地别 —— 一个返回 `null`、一个抛异常，调用方崩溃。

**修正**：conformance 用例化行为 —— at-least-once、幂等、顺序、错误语义全部写成可跑的测试。

---

## AP-06｜过度设计（Over-Engineering）

**症状**：为一个"未来可能要换"、实则稳定的实现引入了完整 SPI 层，增加了间接调用、调试难度、学习曲线。

**修正**：适用边界判定 —— **"未来要替换 / 多实现并存 / 第三方扩展"至少一项为真才引入**。否则直接调用更简单。

**典型受害者**：创业公司 MVP、内部工具、一次性数据迁移脚本。

---

## AP-07｜后端爆炸（Backend Explosion）

**症状**：一个 SPI 衍生出 6+ 后端，每个后端的行为差异越来越大，conformance 用例膨胀到 200+。

**为什么危险**：契约演进本身成为负担；后端间差异过大时，**抽象层开始泄漏**（调用方需要 `if (backend === 'X')`）。

**修正**：
1. 收敛后端数量，合并语义相近的
2. 拆分 SPI —— 差异过大的后端其实对应**不同的接口**
3. 引入 `Capabilities` 表，明确后端能力不齐时的降级（参考 G-37）

---

## AP-08｜抽象成本不透明（Hidden Cost）

**症状**：引入了 SPI 但**从不做性能基准**，间接调用开销、序列化成本、跨边界延迟全部未知。

**修正**：诚实边界必须含**实测性能数据**（CMP046 原则）。每次新增后端跑一次基准，记录开销。超过阈值时评估是否走编译期单态 / 内联。

**Proteus 实例**：G-40 记录 JSI HostObject 181ns vs HostFunction 27ns —— 正是这种实测暴露了批处理优化的必要性。

## 反模式自检清单

应用到你的项目，逐条打勾（✅ = 命中 = 需要修正）：

- [ ] AP-01：是否有只有单个实现的"SPI"？
- [ ] AP-02：接口命名是否能 grep 到技术/厂商名词？
- [ ] AP-03：是否有 SPI 完全没有契约测试？
- [ ] AP-04：业务层是否仍能 grep 到具体 SDK 的 import？
- [ ] AP-05：接口是否只定义了类型、没定义行为契约？
- [ ] AP-06：是否存在为"可能要换"而过度设计的抽象？
- [ ] AP-07：是否有 SPI 后端数 ≥ 6 且差异巨大？
- [ ] AP-08：抽象层的性能开销是否有实测数据？

**任一条命中 → 该处 SPI 未真正落地，回到对应 Step 修正。**
