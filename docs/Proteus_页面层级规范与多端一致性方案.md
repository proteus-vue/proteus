# Proteus 页面层级规范与多端一致性方案

> 版本：v1 · 日期：2026-10-02
> 定位：**独立方案**，不并入《多端一致性数值校验方案》《CSS Profile 规格》等已入库文档。仅在本文件内定义层级模型，其他文档引用本文件。
> 参考来源：微信官方 WeUI 层级规范。

---

## 0. 结论摘要（给 LLM / 实现者）

| # | 结论 | 性质 |
|---|---|---|
| 1 | 采用 WeUI 四层模型：**Content → Navigation → Mask → Popout**（低到高） | 定案 |
| 2 | ★ **层级语义化，不暴露数值**——开发者声明"这是 Popout"，框架映射到各端 | **核心设计** |
| 3 | 🔴 **禁止开发者写裸 `z-index` 数值** | 硬约束 |
| 4 | 🔴 **跨容器层级不生效**是最大陷阱（CSS stacking context 与鸿蒙 zIndex 均如此） | 硬约束 |
| 5 | 小程序原生组件（map/video/canvas 等）层级最高，**需同层渲染** | 端特有问题 |
| 6 | Android 用 `translationZ` 而非 `elevation`（后者会带阴影） | 坑 |
| 7 | 必须有**弹层栈管理器**——WeUI 固定值导致嵌套弹层冲突（已知实证） | 必需设施 |
| 8 | 层级是**数值**，可纳入 L2 几何校验 | 与一致性方案对接 |

## 1. WeUI 层级规范原文

### 1.1 四层定义（weui.io 官方「层级规范」页，权威性极高）

> 用于规范 WeUI 页面元素所属层级、层级顺序及组合规范。

**由低到高：**

| 层 | 官方定义 |
|---|---|
| **Content** | 内容层，**承载页面主要内容** |
| **Navigation** | 导航层，**位于内容层之上**，在用户滑动内容层时可**保持位置不动**，通常用于承载导航栏等需要固定在页面的元素 |
| **Mask** | 蒙层，**配合 Popout 层使用**，用于**锁定内容层和导航层操作，不单独使用** |
| **Popout** | 弹出层，作为内容层和导航层的补充，用于承载**弹窗通知、操作菜单、菜单、成功或加载中等状态的 Toast、表单报错提示**等弹出内容 |

### 1.2 数值区间（社区引用，权威性中等）

多个第三方来源给出一致的区间划分：

> z-index 依次为 **1000、100、10、1 起**。如 Content 可选值区间为 **[1-9]**。

| 层 | 起始值 | 区间 |
|---|---|---|
| Content | 1 | [1, 9] |
| Navigation | 10 | [10, 99] |
| Mask | 100 | [100, 999] |
| Popout | 1000 | [1000, +) |

另有源码分析显示 `.weui-dialog` 实际使用 `z-index: 5000`（权威性较低）。

### 1.3 ⚠️ 重要限定

**§1.2 的数值区间来自第三方引用，非官方页面直接给出。** weui.io 官方「层级规范」页（权威性极高）给出的是**四层语义定义**。

> **因此本方案的采用策略是：采用其语义模型，不采用其数值。**
> 数值由 Proteus 自行定义（§3），因为各端层级模型不同，直接搬运 1000/100/10/1 没有意义。

**待核实**：官方页面是否含数值表（§11 待核实 1）。

## 2. 各端层级模型对比（关键差异矩阵）

### 2.1 机制对比

| 平台 | API | 是否需要定位上下文 | 跨容器生效 | 默认值 | 负值 |
|---|---|---|---|---|---|
| **Web / 小程序 CSS** | `z-index` | 🔴 **需要**（position ≠ static） | ❌ 受 stacking context 限制 | auto(0) | ✅ |
| **鸿蒙 ArkUI** | `.zIndex(value)` | ✅ **不需要** | 🔴 **不跨容器** | 0 | ✅ |
| **Android** | `elevation` / `translationZ` | 不需要 | 受 View 层级限制 | 0 | ✅ |
| **iOS** | `layer.zPosition` | 不需要 | 受 layer 树限制 | 0 | ✅ |
| Flutter | `Stack` + children 顺序 | — | 受 Stack 限制 | — | — |

### 2.2 🔴 三条最危险的差异

**① CSS 的 `z-index` 需要配合 `position`，鸿蒙不需要**

鸿蒙官方文档明确：zIndex **对所有组件均生效，无需额外设置定位上下文**，即使组件使用默认布局方式（如 Column 内子组件），zIndex 依然可控。

**后果**：同一份声明——
- 在 Web 端：父元素 `position: static` → `z-index` **静默失效**
- 在鸿蒙端：生效

**这是一个静默的跨端差异**，且不报错。

**② 跨容器均不生效，但规则细节不同**

鸿蒙官方文档（权威性极高）：

> "**不同容器内的组件无法根据 zIndex 值改变跨容器显示层级**"

CSS 的 stacking context 同理，但触发条件复杂得多（`opacity < 1`、`transform`、`filter`、`will-change`、`position: fixed` 等都创建新的 stacking context）。

**后果**：Web 端一个 `transform` 动画会**意外创建 stacking context**，导致原本正确的层级被打乱——而这恰好与 Morpheus 动画叠加发生。

**③ Android 的 `elevation` 语义不是"层级"而是"高度"**

`elevation` 会**同时产生阴影**。用它做层级控制会导致意外的阴影出现。

> **必须用 `translationZ`（只改 Z 序，不产生阴影），不能用 `elevation`。**

## 3. Proteus 层级原语设计（核心）

### 3.1 设计原则：语义化，不数值化

**开发者写的是层级语义，不是数值。**

```
❌ 错误：z-index: 1000
✅ 正确：layer="popout"
```

理由有三：

| # | 理由 |
|---|---|
| 1 | **数值无跨端意义**——CSS 需要 position、鸿蒙不跨容器、Android elevation 带阴影，同一个 1000 在各端语义不同 |
| 2 | **数值是收敛模型的漏洞**——任意数值 = 又一个逃生口，会毁掉 conformance 与 AI 可校验 |
| 3 | **语义可编译期校验**——编译器能判断"Popout 不能出现在 Content 之下"，数值做不到 |

### 3.2 层级原语集（封闭集）

| 原语 | 对应 WeUI 层 | 语义 | 典型内容 |
|---|---|---|---|
| `layer-content` | Content | 页面主内容 | 列表、表单、卡片 |
| `layer-navigation` | Navigation | 固定导航 | navbar、tabbar、吸顶栏 |
| `layer-mask` | Mask | 蒙层 | 配合弹层，**不可单独使用** |
| `layer-popout` | Popout | 弹出层 | dialog、actionsheet、toast、picker |

### 3.3 子层级（层内顺序）

层内需要区分多个元素时，**不开放数值**，提供：

| 机制 | 说明 |
|---|---|
| **声明顺序** | 同层内后声明者在上（各端一致） |
| **弹层栈** | Popout 层内部的多个弹层由**栈管理器**自动分配（§6） |

> 这样开发者永远不接触数值，但层内顺序仍然可控且确定。

### 3.4 各端映射表

| 原语 | Web / 小程序 | 鸿蒙 | Android | iOS |
|---|---|---|---|---|
| `layer-content` | `z-index: 1-9`（需 position） | `zIndex(1-9)` | `translationZ: 0` | `zPosition: 0` |
| `layer-navigation` | `z-index: 10-99` | `zIndex(10-99)` | `translationZ: 10` | `zPosition: 10` |
| `layer-mask` | `z-index: 100-999` | `zIndex(100-999)` | `translationZ: 100` | `zPosition: 100` |
| `layer-popout` | `z-index: 1000+` | `zIndex(1000+)` | `translationZ: 1000` | `zPosition: 1000` |

**具体数值由框架内部常量定义，不暴露给开发者。**

### 3.5 硬约束

- [ ] **禁止开发者写裸 `z-index` 数值**（编译期报错，非警告）
- [ ] 层级原语为封闭集，不可扩展
- [ ] `layer-mask` **不得单独使用**（编译期校验，与 WeUI 规范一致）
- [ ] 各端映射表由框架统一维护，平台层不得自行计算
- [ ] 层级值必须写入指令流（见 §7）

## 4. 六大陷阱

### 4.1 🔴 陷阱一：跨容器层级失效（最危险）

**现象**：弹层写在页面某个深层容器里，在 A 端正常、B 端被遮挡。

**根因**：CSS stacking context 与鸿蒙 zIndex **都不跨容器**。

**规避**：

| 措施 | 说明 |
|---|---|
| **弹层必须提升到根容器** | `layer-popout` / `layer-mask` 节点强制挂载到根容器，不得嵌套在业务容器内 |
| **编译期校验** | 声明了 popout/mask 却位于非根容器 → 编译期报错 |
| **禁止在弹层祖先链上创建 stacking context** | 特别是 `transform` / `opacity < 1` / `filter` |

> **第三条与 Morpheus 直接冲突**：动画常用 `transform` 和 `opacity`，而这两者都会创建 stacking context。
> **必须确保弹层不在任何动画节点的子树内。**

### 4.2 🔴 陷阱二：小程序原生组件层级最高

微信官方文档（权威性较高）：

> "原生组件的层级是**最高**的，所以页面中的其他组件**无论设置 z-index 为多少**，都无法盖在原生组件上。"

原生组件清单：`camera` / `canvas` / `input`（仅 focus 时）/ `live-player` / `live-pusher` / `map` / `textarea` / `video`。

**解法：同层渲染。**

- 官方：**当前所有原生组件（除 input focus 状态）均已支持同层渲染**
- **鸿蒙 OS 下只支持同层渲染**
- Skyline 下更稳定（iOS WKWebView 下同层渲染是取巧实现，易失效）
- `cover-view` 官方已标注"建议使用 view 替代"
- `bindrendererror` 可监听同层渲染失败并降级

**硬约束**：
- [ ] 小程序端必须启用同层渲染
- [ ] **必须监听 `bindrendererror` 并降级**，不得静默
- [ ] 原生组件之上的覆盖物，其层级需求必须显式声明并纳入 conformance

### 4.3 陷阱三：CSS `z-index` 需要 `position`

Web 端 `position: static` 时 `z-index` 静默失效，鸿蒙不需要。

**规避**：Web 端映射时**自动附加 `position: relative`**（或框架统一采用绝对定位布局，本就满足）。

### 4.4 陷阱四：Android `elevation` 带阴影

**必须用 `translationZ`。** 已在 §3.4 映射表中定案。

### 4.5 陷阱五：嵌套弹层层级冲突

已知实证（CSDN，权威性较低但问题描述具体）：

> WeUI 的 `actionSheet` 默认使用**固定 z-index 值**，嵌套或快速连续调用时未动态调整，
> **导致后弹出的 actionSheet 被之前的弹层遮挡**。

**这正是"数值化层级"的固有缺陷**——固定值无法表达栈序。

**解法：弹层栈管理器（§6）。**

### 4.6 陷阱六：转场期间的层级提升

Morpheus 的**共享元素转场**需要把元素提升覆盖在两个页面之上。

这与层级规范直接相关，必须明确：

| 项 | 规则 |
|---|---|
| 共享元素转场层级 | **高于 `layer-popout`**，独立定义 `layer-transition`（框架内部，不开放） |
| 转场结束 | 必须**还原**原层级，不得残留 |
| 转场期间新弹层 | 必须**排队**，不得插入 |

## 5. 与 WeUI 的关系定位

| 项 | 说明 |
|---|---|
| **采用** | 四层**语义模型**（Content / Navigation / Mask / Popout）与"Mask 不单独使用"的组合规范 |
| **不采用** | 具体数值区间（§1.3，来源权威性不足且无跨端意义） |
| **增强** | 语义化原语 + 编译期校验 + 弹层栈管理器 + 各端映射 |

> 对外表述：**"层级模型遵循微信 WeUI 官方规范，并做了跨端语义化改造。"**
> **不要说"我们用了 WeUI 的 z-index"**——那既不准确（我们不用数值），也会引出授权与版本问题。

## 6. 弹层栈管理器（必需设施）

### 6.1 为什么必须有

陷阱五已给出实证：**固定数值无法表达栈序**。

而"后弹出的必须在上"是一个**必然需求**，且它与数值化层级天然冲突。

### 6.2 设计

```
弹层栈（LIFO）
  push(dialog A)  → 分配层级 P0
  push(dialog B)  → 分配层级 P0 + 1
  pop()           → 回收层级
```

| 规则 | 说明 |
|---|---|
| 层级由栈深决定，**不由开发者指定** | 杜绝冲突 |
| 同栈深用声明顺序兜底 | 各端一致 |
| 弹层销毁必须 `pop` | 泄漏会导致层级单调增长直至溢出 |
| **栈深上限** | 必须定义，超过则报错（防递归弹层） |

### 6.3 硬约束

- [ ] 弹层层级**完全由栈管理器分配**，开发者不可指定
- [ ] 栈深上限明确定义并强制
- [ ] 弹层销毁必须出栈，加泄漏检测
- [ ] 快速连续调用（连点）行为确定——需覆盖测试

## 7. 与一致性校验的对接

### 7.1 层级是数值，可进 L2

层级值最终是一个数字，因此**可以纳入 L2 几何快照校验**：

```
节点 i 的层级值 == 预期值（按四层模型与各端映射表换算后）
```

**这是"层级一致性"从"看起来对"变成"机器可判定"的关键。**

### 7.2 校验项

| 项 | 校验内容 |
|---|---|
| 层级值 | 各端换算后是否等价 |
| 层内顺序 | 栈序是否一致 |
| 弹层栈 | 连点后栈深与顺序是否一致 |
| **遮挡关系** | 给定重叠区域，最上层元素是否一致 |

**最后一条最有价值**：它直接验证"用户实际看到谁在上面"，而不只是数字相等。

### 7.3 边界

**本方案只定义层级模型与规则，不定义校验流程。** 校验流程属《多端一致性数值校验方案》，新增卡片在《一致性校验任务卡清单》中另立（§10 LY 系列）。

## 12. 执行指令（给 LLM）

1. **先做 LY0**，它是其余各项的地基，且成本最低。
2. **§3.5 的"禁止裸 z-index"是编译期报错，不是警告**——开放数值会毁掉收敛体系（与"不开放任意原生调用"同理）。
3. **§4.1 是最高优先级陷阱**。弹层提升到根容器必须**编译期强制**，不能靠开发者自觉。
4. **§4.4 必须用 `translationZ`**，用 `elevation` 会产生意外阴影——这是可见缺陷。
5. **LY3 弹层栈必须有栈深上限与泄漏检测**。层级单调增长会溢出，且难复现。
6. **§8 的 Morpheus 交叉风险必须两边都写**——`transform`/`opacity` 创建 stacking context 这件事，只用 Morpheus 的人想不到。
7. **本方案不修改任何已入库文档**。与《一致性校验任务卡清单》的对接通过新增 LY 系列卡片完成。
8. §11 待核实第 3 项（Skyline stacking context）**应在 LY2 小程序端开工前确认**。
9. 与《CSS Profile 规格》可能的重叠：**本方案管层级语义与跨端映射，CSS Profile 管属性支持度**。若出现冲突，以本方案的层级规则为准。

### 13.1 LY0 已落地：契约层 `packages/contracts/src/layers.ts`

- 四层原语（`LAYER_PRIMITIVES`，封闭集）+ `LAYER_SEMANTICS`（WeUI 对应名与中文语义）；
- **跨端映射表** `LAYER_MAPPING`（cssZIndex / harmonyZIndex / androidTranslationZ / iosZPosition）
  + `layerValueFor(layer, platform)`（一致性校验取值入口）+ `popoutStackValue(stackDepth)`
  （弹层栈值——**唯一可用推导入口**）+ `POPOUT_STACK_LIMIT = 16`；
- `LAYER_RESERVED = ['layer-transition']`（框架内部层，开发者声明即报错）。

**诚实边界（关键）**：Android 的 `translationZ` 与 iOS 的 `zPosition` 当前**尚未由内核驱动**
（层序真源 = **树序**）；本表在 web/mp 端**现在即可生效**（CSS z-index），
在 App 两端是**既定契约**（内核接入 zOrder 时按此实现）。不许表述为"五端已全部生效"。
