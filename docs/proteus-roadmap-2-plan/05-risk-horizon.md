## 3. 风险应对原则

### 3.1 关键路径风险优先（R1、R3）
- 关键路径上的风险**必须主动管理**，不能被动等待
- R1 → 立即启动 spike
- R3 → M1 起采集基线

### 3.2 生态风险用机制化解（R2、R9、R10）
- 官方主导 + 社区贡献双轨
- 签名审计 + 质量门禁 + registry
- Backend 版本化 + 兼容矩阵

### 3.3 工期风险用范围换确定性（R4）
- 非关键路径可延迟
- M2 范围可裁剪（先 iOS + Flutter）

### 3.4 竞争风险靠护城河（R5）
- 方法论护城河深（原则 #10 + 双 SPI + IR）
- 竞品跟进需重构架构，**时间窗 ≥ 2 年**

## 4. 长期演进前瞻（Horizon）

### 4.1 2 年：生态成熟期（M3 完成）
- 45 份 plan 全部落地
- 99% 业务场景零原生代码
- benchmark 数据领先
- Website + 社区成熟
- **定位**：跨端框架第一梯队

### 4.2 3–5 年：平台化期
- **Backend 市场**：第三方 Backend 繁荣（类似 npm 生态）
- **AI 原生**：G-23 Agent 进化为"自然语言 → 全栈应用"（v2 架构）
- **新终端**：XR/VR/AR 后端（原则 #10 泛化的验证——只需新增 Backend）
- **Server**：Backend 概念延伸到服务端渲染（HeadlessBackend 演进）

**原则 #10 泛化的长期价值**：未来任何新终端/新渲染引擎，Proteus 只需新增一个 Backend，业务代码不变。**这是竞品架构无法做到的。**

### 4.3 范式跃迁可能
- **AI 生成 IR 直接**：跳过 SFC，LLM 直接生成 LayoutConstraint IR → 任意后端
- **运行时自适应**：根据设备性能自动选择 Backend（如低端机走原生、高端机走 Skia）
- **跨进程渲染**：Backend 可跨进程/跨设备（车机中控 + 手机协同）

这些**依赖双 SPI 架构的存在**——没有 G-27/G-28 的抽象，根本无从谈起。

---

## 5. 不变式（Invariants）

无论演进如何，以下原则不可动摇：

1. ✅ **原则 #10**：统一语义 + 后端实现（整个体系的真理来源）
2. ✅ **双 SPI**：渲染 + 原生能力（架构地基）
3. ✅ **IR 平台无关**：禁止在 IR 层写平台特定代码
4. ✅ **业务零原生**：99% 目标不可降级
5. ✅ **编译期优先**：校验尽量在编译期完成

## 7. 一句话总结

> **最大风险不是技术，是生态节奏**——但只要坚持 M1 把双 SPI 做实、关键路径优先、范围换确定性，18 个月的路径是可达的。而原则 #10 的泛化，让这套架构在未来 5 年都具备"接入任何新终端"的扩展能力。
