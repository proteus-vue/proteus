## 0. 范围与边界

### 0.1 一句话定位

> **错误不是工具链的副产品，错误也是环境差异——同样应该在语义 IR 层被抹平。**

传统跨端框架把下层工具链（webpack / vite / babel / tsc / 各端原生编译器）的错误**原样转发**给开发者。本文档定义 Proteus 如何把这些错误**在语义层重新解释**后再输出。

### 0.2 明确不做

❌ 替代下层工具链的错误格式化
❌ 自研 TypeScript / bundler
❌ 运行时错误捕获与上报（那是《全链路内存安全方案》与《埋点采集方案》的事）
❌ AI 自动修代码（只给建议，不自动改）

### 0.3 与相邻文档的关系

| 文档 | 关系 |

| 《架构收敛模型说明》 | 本方案是收敛模型在**错误维度**的延伸 |

## 1. 痛点诊断

### 1.1 🔴 最硬的一条证据：错误定位指向生成物

Taro 官方 GitHub issue（编号 **16271**，权威性极高，**官方确认为 bug**）：

> 源码编译报错时，**编译器输出的错误定位指向 `dist` 目录下的编译产物，而非开发者实际编写的源码。**

**这条为什么致命**——错误位置指到生成物上，等于告诉开发者"`dist/pages/index.js` 第 3 行错了"，而那个文件是工具生成的、开发者看不懂、也不该改。

**而且它至今未修复。** 这不是"体验不够好"，是**报错了但没用**。

### 1.2 其余痛点：编译失败但不明原因

uni-app 与 Taro 社区中大量"编译失败但不明原因"的反馈，典型表述是"找不到是哪个文件的问题"。

根因是**错误在多层工具链之间传递时丢失了上下文**：

```
源码 → 编译器 → 中间产物 → bundler → 各端原生编译器 → 错误
                                                        ↑
                            到这里，"是谁引发的"已经不知道了
```

### 1.3 这与我们一直在打的是同一类病

| 场景 | 症状 |
|---|---|
| `switchTab` | 静默失败，不触发 success/fail |
| `boundingClientRect` | 返回 0 |
| Skyline `position: fixed` | 失效但不报错 |
| PiP | `pip: context not ready`，只在日志里 |
| 埋点事件名非法 | 微信侧静默丢弃 |
| **构建错误** | **定位到 dist，指错地方** |

**共同点：报错了，但没有用。** 这也是本文档的方法论起点——我们要的不是"更漂亮的错误"，是**可行动的错误**。

## 2. 🔴 必须承认：这块别人做了不少

**这是红海，不是空白。声称首创会被当场拆穿。**

| 已存在的能力 | 出处 |
|---|---|
| 错误码体系（每错一号、可查文档） | TypeScript、rustc |
| **源码定位**（错误指回原始位置） | tsc / esbuild **均内建** |
| 智能建议（"Did you mean…"） | rustc |
| 编译期给出修复建议 | rustc、esbuild |
| 屏蔽无关背景错误，只显示最可能的 | rustc |
| 结构化错误输出（JSON） | esbuild |

**所以"友好错误提示"这件事，业界已经做得相当好了。** 我们能做的差异比想象中窄——但有一条是**只有我们能做的**（§3）。

### 2.1 一个必须修正的常见误解

**esbuild 官方明确：不维护稳定的错误码列表。**

官方理由是"存在许多可能的失败情形……维护稳定列表不切实际"。

> **这条直接改变设计：错误码统一必须是我们自己的映射层，不能指望下层工具提供稳定码。**（见 §6.1）

对比 TypeScript——它**有**稳定的错误码（TS2xxx 系列）。所以不同工具链的成熟度差异很大，**必须按工具分别处理，不能统一假设**。

## 3. 🏆 唯一只有我们能做的：跨工具链语义化

### 3.1 关键区别在于"错误来自哪里"

| 框架 | 错误的来源 |
|---|---|
| 传统跨端框架 | **下层工具链**：webpack / vite / babel / tsc / 各端原生编译器 |
| Proteus | 下层工具链 **+ 我们自己的编译器** |

**传统框架只能转发下层错误**——所以才会出现"指到 dist"的情况：它们不知道 dist 里的第 3 行对应源码的哪里。

**而我们有自己的 IR，知道完整的映射链路**，因此可以**反向归因**。

### 3.2 三件具体能做的事

**① 端到端归因（Attribution）**

注意是**归因**不是**转发**：

```
我们知道：源码位置 → IR 节点 → 生成物位置 → 下层报错位置
所以可以：下层报错位置 → 反向映射 → 源码位置
```

这就是 Taro issue 16271 那个 bug **在我们这里天然不存在**的原因——不是我们修了它，是我们的架构里根本没有这个信息断层。

**② 错误码统一**

不管错误来自 webpack、tsc、还是鸿蒙编译器，**对外是同一个 Proteus 错误码体系**。

开发者不需要分辨"这是谁的错"——这对跨端框架尤其重要，因为同一类问题在不同端会由不同工具报出。

**③ 语义化改写**

把下层工具的"技术描述"翻译成"开发者能懂的原因"：

```
原始：module not found: Error: Can't resolve './Header'
改写：找不到模块 './Header'
      可能原因：路径大小写不匹配（鸿蒙端文件系统大小写敏感，macOS 不敏感）
      源码位置：src/pages/index.vue:12
      建议：改为 './header'，或统一文件命名
```

**这条最有价值**——它把"技术现象"变成"可行动的原因"。

### 3.3 🔴 但改写的前提是"我们知道为什么"

语义化改写不是"把英文翻成中文"。**只有当我们能确定原因时才改写**；不确定的，只能做定位与归类，**不得编造原因**。

> **硬约束：禁止对未知原因的错误生成猜测性"可能原因"。**
> 猜错的原因比不给原因更糟——它会把开发者引向错误的方向。

## 4. ★ 灵魂：错误也是 IR 的一部分

### 4.1 论证

你说过一句话——**"我们框架的灵魂就是语义 IR 抹平各个环境差异"**。

**那么：错误同样是环境差异。**

同一份源码，在 Web 端、小程序端、鸿蒙端会触发**不同的工具链报出不同的错误**。这本身就是最典型的环境差异。

```
        源码
          ↓
      语义 IR  ← 抹平差异的地方
          ↓
   ┌──────┼──────┐
   ▼      ▼      ▼
  Web   小程序   鸿蒙
   ↓      ↓      ↓
 不同的工具链 → 不同的错误表述
   └──────┼──────┘
          ↓
   **错误也应在语义层被抹平**
```

**这不是附加功能，是编译期收敛模型的自然延伸。**

### 4.2 具体机制：Environment Capability 元数据

**语义 IR 的每个节点/指令，都携带各端支持度元数据。**

这与《一致性校验任务卡清单》VC1-d 的 `@support` 矩阵是**同一份数据**（复用，不另建）。

于是当某端报 `unsupported` 时，我们**编译期就知道**：

- 哪个能力不支持
- 该端是否有替代路径
- 替代路径的差异是什么

所以能给出**替代建议**，而不是只说"不支持"。

### 4.3 别人为什么做不到

| | 传统框架 | Proteus |
|---|---|---|
| 何时知道能力支持度 | 运行时 / 报错后 | **编译期** |
| 能否给出替代路径 | ❌ 只能说"不支持" | ✅ 编译期已知 |

**根本差别：他们要先"猜发生了什么"，我们是编译期就知道。**

## 5. 分层设计

```
L0 采集层   捕获所有工具链的结构化错误（JSON / 正则解析 / 退出码）
L1 归因层   生成物位置 → 源码位置 反向映射           ← 关键增值 ①
L2 分类层   映射到 Proteus 统一错误码                ← 关键增值 ②
L3 语义层   结合环境能力元数据生成原因与建议          ← 关键增值 ③
L4 呈现层   分层输出：语义解释（人读）+ 原始错误（调试）
```

**L1 / L2 / L3 是全部差异所在。**

## 6. 错误码体系

### 6.1 🔴 必须自建映射层（因为下层不稳定）

| 工具 | 是否提供稳定错误码 |
|---|---|
| TypeScript | ✅ 有（TS2xxx 系列） |
| **esbuild** | ❌ **官方明确不维护** |
| webpack | ⚠️ 部分有，部分为自由文本 |
| 各端原生编译器 | ❌ 基本无稳定码 |

**结论：Proteus 错误码必须是自己的一层，不能透传任何下层的码。**

### 6.2 编码规则

```
PT-{阶段}{类别}-{序号}
```

| 段 | 含义 | 取值 |
|---|---|---|
| 阶段 | 发生在哪 | `C` 编译期 / `B` 构建期 / `D` 部署期 |
| 类别 | 错误性质 | `S` 语法 / `T` 类型 / `R` 资源 / `E` 环境能力 / `D` 依赖 / `X` 未知 |
| 序号 | 三位数字 | — |

示例：

| 码 | 含义 |
|---|---|
| `PT-CS-001` | 编译期语法错误 |
| `PT-CE-014` | 编译期环境能力不支持（如某端不支持某 CSS 属性） |
| `PT-BR-007` | 构建期资源问题（如域名未配置白名单） |
| `PT-BD-003` | 构建期依赖问题（模块找不到） |

### 6.3 🔴 `X`（未知）类别不可省略

**必须给"我们也不知道"留一个分类。**

原因：强行把未知错误归类到某个已知类别，会让开发者按错误的方向排查。宁可输出"未知，附原始错误"，也不要编造类别。

## 7. 🔴 一个反直觉但必须做的约束：保留原始错误

**语义化改写会丢失信息。**

```
❌ 只给：找不到模块 './Header'，可能是大小写问题
✅ 应给：
   ┌─────────────────────────────────────────┐
   │ Proteus: 找不到模块 './Header'            │
   │ 源码位置：src/pages/index.vue:12          │
   │ 可能原因：路径大小写不匹配…               │
   │ ─────────────────────────────────        │
   │ ▸ 原始错误（点击展开）                    │
   └─────────────────────────────────────────┘
```

**硬约束：任何语义化输出必须可展开到原始错误全文，禁止吞掉原文。**

理由很实际：我们的改写只覆盖了**已知**错误。遇到没覆盖的，原文是开发者唯一的线索。为了"输出干净"把原文删掉，等于在最需要信息的场景屏蔽信息。

**这与《可停靠滚动容器方案》"不得静默"、《网络请求方案》"违规一律报错"是同一条原则。**

## 8. 三类高价值场景

### 8.1 场景一：跨端能力不支持（最高价值）

```
源码：  <view style="position: sticky; top: 20rpx">
鸿蒙端：ArkUI List.sticky 无距顶距离参数

输出：
  PT-CE-021  能力不支持：sticky 距顶偏移
  源码位置：src/pages/list.vue:45
  鸿蒙端 List.sticky(StickyStyle) 仅支持 None/Header/Footer/BOTH，
  不支持指定距顶距离。
  建议：
    ① 改用框架内置 <sticky-section offset-top> 语义（推荐）
    ② 或改用可停靠滚动容器方案（见《可停靠滚动容器方案》§4）
```

**这类错误是我们独有的**——因为只有我们知道"鸿蒙端没有这个能力"，而且知道替代路径。

### 8.2 场景二：生成物位置反向归因

```
原始：  dist/pages/index.js:3:12  Unexpected token
输出：
  PT-CS-001  语法错误
  源码位置：src/pages/index.vue:12   ← 反向映射
  上下文：<template> 内第 2 个表达式
```

**直接解决 Taro issue 16271。**

### 8.3 场景三：构建期环境约束

```
源码：  request('https://new-api.example.com/...')
小程序端：域名未配置白名单

输出：
  PT-BR-011  域名未配置
  源码位置：src/api/user.ts:8
  域名 https://new-api.example.com 未出现在小程序域名白名单中
  ⚠️ 小程序域名白名单每月仅可修改 5 次，请一次性配齐
  建议：运行 proteus domain list 导出全部域名清单
```

**把"一个月只能改 5 次"这个代价前置到编译期**——这是《网络请求方案》§4.1 的能力在错误层的兑现。

## 9. 三个别人报不出来的指标

与"0% 逃生口""确定性回收覆盖率"同类：

| 指标 | 定义 |
|---|---|
| **语义归因率** | 能映射到源码位置的错误数 / 全部错误数 |
| **可操作错误占比** | 含明确修复建议的错误数 / 全部错误数 |
| **跨端归因一致率** | 同一错误在各端归因一致的比例 |

### 9.1 为什么这些指标有价值

**第一个指标（语义归因率）别人报不出来**——他们的错误来自下层工具链，无法统计"有多少能指回源码"。

**而且它可以被测**：注入一组已知的语法/类型/资源错误，看有多少能被正确归因。这与《多端一致性标准方案》的**变异测试**是同一套思路——**"我们的诊断有效"是声称，"能捕获什么"才是证据**。

建议：**把变异测试复用过来**（BX9），注入人为错误，统计捕获率。这是唯一能把这套诊断从"看起来不错"变成"证明有效"的方式。

## 11. 三个决策点

**① 是否默认开启语义化改写？**
建议**默认开启**，但任何情况下可加 `--raw` 拿到纯原文。

**② 未知错误怎么办？**
建议归到 `PT-*-X00`（未知类别），**只做定位不猜原因**，附原文。

**③ 是否做自动修复？**
建议**不做**。只给建议，不自动改代码——自动改会引入"改错了还不说"的新问题，且与收敛模型冲突（改动必须可声明、可校验）。

## 12. 诚实对照

| 维度 | Taro | uni-app | **Proteus** |
|---|---|---|---|
| 错误定位 | 🔴 **指到 dist（官方 bug，未修）** | ⚠️ 部分 | 🏆 **反向映射到源码** |
| 错误码 | ❌ 透传工具链 | ❌ 透传工具链 | 🏆 **统一体系** |
| 跨端一致表述 | ❌ 各端各说各话 | ❌ | 🏆 **同一码同一格式** |
| 能力不支持提示 | ❌ 只说不支持 | ❌ | 🏆 **含替代路径** |
| 归因率可统计 | ❌ | ❌ | 🏆 **可量化** |

### 12.1 必须承认不是我们的

- **源码定位（Source Map）是通用技术**，不是我们发明的
- **错误建议机制 rustc 早已做得很好**
- **结构化错误输出 esbuild 已内建**

### 12.2 我们的差异只有三点

1. **完整编译链信息在手**，所以能反向归因（别人没有这层 IR）
2. **环境能力编译期已知**，所以能给出替代路径
3. **错误码由我们定义**，跨端表述统一

> ✅ 正确表述：**"Source Map 与错误建议都是成熟技术。我们的差异在于：完整的编译链信息在我们手里，因此错误能反向归因到源码，而且环境能力是编译期已知的，能给出替代路径而非一句'不支持'。"**

### 14.1 ✅ BX0 实测已做（2026-10-08）——结论落定

**判据 = 真实工具链的**结构化**输出形状（不是文档）**：

| 工具 | 稳定错误码 | 结构化位置 | 实测证据（本机） | 对设计的影响 |
|---|---|---|---|---|
| **esbuild** | ❌ **无**（`errors[0].id === ''`） | ✅ 有 `location{file,line,column,lineText,length}` + `text` + `notes[]` | `Expected identifier but found "="` / `Could not resolve "./nope"` —— `id` 恒空 | **§6.1 成立**：错误码必须自建映射层（不能透传下层的 `id`） |
| **TypeScript** | ✅ **有**（`TS2322`/`TS2304`…） | ✅ 文本 `file(line,col): error TSxxxx: msg` | `bad.ts(1,7): error TS2322: Type 'string' is not assignable to type 'number'.` | tsc 的 `TSxxxx` 可**保真透传**（作为 `raw` 的一部分）；Proteus 码另给一层 |
| **rustc/cargo** | ✅ 有（`error[E0308]`） | ⚠️ 文本（`--message-format=json` 才有结构化） | `error[E0308]` 前缀 | 结构化需显式开 `--message-format=json`（当前未开） |
| **swiftc** | ❌ 无稳定码 | ⚠️ 文本 `file:line:col: error: msg` | `ProteusApp.swift:70:46: error: cannot convert value of type 'Double' …` | 正则解析 `file:line:col: error: msg`（本仓已用此形态） |
| **Proteus 自身** | ✅ 我们定义 | —— | —— | 统一走 `PT-*` |

**BX0 结论（三条，覆盖 §14 的 1/2 两项）**：
1. **下层错误码不可依赖**（esbuild 空、swiftc 无）⇒ Proteus 码是**唯一对外码**，下层码只进 `raw`。
2. **结构化位置可用**：esbuild 给对象、tsc/swiftc 给文本 `file:line:col`（正则稳定）⇒ **L1 归因层有原料**。
3. **不确定的一律保留原文**（§7 铁律）——这也是本仓首版实现要立即可修的痛点（见 §17）。

## 16. 分发备注（给实现者）

Taro issue 16271 是**官方确认且至今未修**的 bug——这是最容易做出可见差异、也最容易被开发者感知的一条。建议单独先行。

"我们有诊断"是声称，"我们的诊断能捕获什么"才是证据。这与《多端一致性标准方案》CS3 变异测试是同一套方法，建议直接复用其工具链。

## 17. 首版落点（2026-10-08 · 本仓真痛点触发）

**触发（用户原话）**：「**感觉需要先把我们的阿波罗代号方案先做起来了，现在这种错误提示非常懵**」，配图 = `npx proteus dev --target ios` 输出：

```
✗ 打包 debug 宿主  打包失败
✗ swiftc 编译失败：        ← ★冒号后**空的**（详情被吞）
```

**取证（两处同源缺陷）**：
1. **详情被丢弃（`runAppDev`）**：失败分支只过滤 `pk.log` 里以 `✗` 开头的行再打印——而真正的错误详情（缩进的多行）**不含** `✗` ⇒ 被静默丢弃。**这正是 §7「禁止吞掉原文」的反例**。
2. **错误不可行动**：`packageIosHost`/`packageAndroidHost` 的失败只给一行字符串（如 `✗ 无匹配描述文件（bundleId=…）`），无 Proteus 码、无分类、无根因、无可行动建议。

**首版实现（本仓第一批 Apollo，落 `packages/cli/src/diag.ts`）**：
- **L2 分类**：Proteus 码 `PT-{阶段}{类别}-{序号}`（§6.2）；保留 §6.3 的 `X`（未知）类别。
- **L4 呈现**：分层输出 = 语义块（码/标题/位置/根因/建议）+ **原始错误全文（始终打印，不折叠——终端无法折叠，只能不吞）**。
- **L3 语义（仅确定原因）**：如「无匹配描述文件」⇒ 确定根因（签名档未覆盖该 bundleId）+ 可行动建议（`hosts/ios/signing.sh use`）；未确定的一律只归类不猜因（§3.3 硬约束）。
- **`--json`**：结构化输出供 CI（§15.9）。
- **修详情丢弃**：失败处一律经格式化器**完整**输出诊断（含原文）。

**诚实边界（首版不做）**：
- **BX1-a/c（Source Map 反向映射）**未做——本批错误来自**宿主工具链**（swiftc/cargo/codesign），其"源"是宿主工程文件而非用户 `.vue`；生成物→源码的完整反向映射属 JS 编译管线（下一批）。
- **BX3（环境能力元数据）**未接（复用 VC1-d，另批）。
- **BX8/BX9（指标 + 变异测试）**未做。
