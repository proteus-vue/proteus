# Proteus 可停靠滚动容器与滚动编排能力方案

> 状态：v1 · 面向 LLM 实现分发
> 定位：**能力原语层第三类**，与 187 语义原语、Morpheus 动画原语并列，向上支撑内置组件
> 已决策（本轮）：**回弹可配** · **下拉二楼纳入**
> 目标：消灭滚动编排场景的胶水代码，形成相对其他跨端框架的代差

---

## §0 结论摘要

### 0.1 两个场景是同一个模型（本方案的地基）

用户提出的两个场景：

| 场景 | 形态 |
|---|---|
| **A. Sheet 弹层** | 指定起始高度、下拉回弹、上拉协商、露出底部内容 |
| **B. 页面级内容容器** | 顶部导航文字 + 下方内容卡片，可上拉下拉回弹 |

表面看是两个东西，实际只差三件事：

| 维度 | Sheet 弹层 | 页面级内容容器 |
|---|---|---|
| 是否模态 | 是（有遮罩） | 否 |
| 停靠参照系 | 距底 | 距顶 |
| 初始档位 | 半屏 | 全屏/内容位 |

**其余全部相同**：停靠点、overscroll 回弹、嵌套滚动协商、滚动联动。

**所以做成一个统一抽象，不是两个组件。**

> **可停靠滚动容器（dockable scroll container）**
> 模态与参照系是两个参数，不是两个组件。

这个统一带来的直接收益：**一份实现覆盖两类场景**，且两类场景的行为自动一致（不会出现"Sheet 的回弹和页面的回弹手感不一样"）。

### 0.2 本轮两项决策的架构含义

| 决策 | 直接后果 | 代价 |
|---|---|---|
| **回弹可配** | 必须**禁用各端原生 overscroll**，框架自算物理 | 🔴 **手感成为一号风险**，需专项验收 |
| **下拉二楼纳入** | 仅 Skyline 有原生，其余四端**自研** | 状态机 + 路由衔接，工作量显著 |

两项都不是"加个参数"，**都改变了实现路径**。下面 §3、§4 分别展开。

### 0.3 一句话定位（对外）

> **"滚动编排这件事，别的跨端框架要手写四套胶水代码，Proteus 是一行声明。"**

---

## §1 为什么这是"降维打击"，以及这个说法的边界

### 1.1 相对其他跨端框架：成立

| 框架 | 现状 | 事实来源 |
|---|---|---|
| **uni-app** | App 端 `position: sticky` 兼容性极差，官方建议"用 scroll-view + bindscroll 动态控制 fixed"，且**必须给 scroll-view 设固定高度否则 bindscroll 不触发** | 官方文档/社区（权威性较高） |
| **Taro** | 不支持原生 sticky，需"固定 View + 隐藏占位 margin-top"模拟被顶走 | 社区方案 |
| **React Native** | 无原生 sticky（旧版）；`nestedScrollEnabled` **只在 Android 生效**，iOS 内置——同一属性两端语义不同 | RN 文档 |
| **Flutter** | 需 `NestedScrollView` + `SliverOverlapAbsorber`/`SliverOverlapInjector` 手动处理重叠 | Flutter 文档（权威性高） |
| **Web 手写** | 无原生能力，全手写 | — |

**结论：滚动编排是跨端框架的公开弱项区，且普遍需要"多段胶水 + 多端 hack"。**

Proteus 做成声明式封闭集后，开发者从"写四套"变成"声明一次"——**这是代差，不是优化。**

### 1.2 🔴 但这个说法有边界，对外必须限定

**相对原生开发（iOS/Android 原生 App），这个优势不成立。**

| | 原生开发 | Proteus |
|---|---|---|
| Bottom Sheet | iOS 15+ `UISheetPresentationController.detents` / Android `BottomSheetBehavior` | 框架自算 |
| 手感 | 系统级，最优 | 需要自己调到接近 |
| 二楼 | 自研即可 | 自研 |

**所以对外口径必须限定为「相对跨端框架」，不能说成「超越原生」。**

> ✅ 正确：**"滚动编排上，我们对其他跨端框架是代差级优势。"**
> ❌ 错误：**"我们比原生做得更好。"**——这句话会被 iOS/Android 原生开发者一句话拆穿。

**这条边界必须写进叙事文档，否则是第一类对外风险（可被当场证伪）。**

### 1.3 真正的优势不在"能做"，在"可声明 + 可校验"

与 Morpheus 同理：

| | 其他跨端框架 | Proteus |
|---|---|---|
| 能不能做 | 能（手写） | 能（声明） |
| 跨端一致 | ❌ 各端 hack 必然不一致 | ✅ 同一套实现 |
| conformance | ❌ 无从校验 | ✅ 编译期校验 |
| AI 可写可验证 | ❌ | ✅ |

**"能做"不是差异化，"可声明且可验证"才是。** 这与 187 原语、Morpheus 是同一套打法。

## §2 统一抽象：可停靠滚动容器

### 2.1 能力拆解（五件事）

| # | 能力 | 术语 | 确定性 |
|---|---|---|---|
| 1 | 指定起始高度/停靠点 | **detent** | ✅ 几何量，完全确定 |
| 2 | 下拉/上拉回弹 | **overscroll** | 🟡 物理仿真（本轮决策：可配） |
| 3 | 内容滚到边后继续拉 → 扩展容器 | **嵌套滚动协商** | ✅ 可声明 |
| 4 | 滚动位置驱动内容变化 | **滚动联动** | 🟡 依赖求值侧 |
| 5 | 拉到底出现新页面 | **下拉二楼** | 🟡 状态机 + 路由 |

### 2.2 声明式形态（目标写法）

```vue
<!-- 场景 A：Sheet 弹层 -->
<sheet :detents="['40%', '100%']" initial="40%"
       :overscroll="{ damping: 0.55, maxOffset: 120 }"
       scroll-expands="false"
       undimmed-from="40%">
  <sheet-content />
</sheet>

<!-- 场景 B：页面级内容容器（顶部导航 + 内容卡片） -->
<dock-container :detents="['header', 'full']" initial="full"
                :overscroll="{ damping: 0.55, maxOffset: 80 }"
                nested="header-first"
                two-level="next-page">
  <template #header>顶部导航文字</template>
  <content-card />
</dock-container>
```

**关键：两者共用同一套 detents / overscroll / 协商 / 联动实现。**

### 2.3 与 Morpheus 的边界（必须划清）

| 归 Morpheus | 归本方案 |
|---|---|
| 停靠**动画**（spring 到目标位置） | 停靠**判定**（该停在哪一档） |
| 联动**插值** | 联动**绑定**（哪个属性跟随哪个滚动源） |
| — | overscroll **手势与物理** |
| — | 嵌套**协商策略** |
| — | 二楼**状态机** |

**依赖方向：本方案调用 Morpheus，Morpheus 不知道本方案存在。**

这条不划清，SC3 与 MA4 会撞车（两边都想定义"停靠动画"）。

**已有地基**：E23 `useScrollAnimation`（滚动进度 → 插值关键帧）已存在——**联动那部分不用重做**，缺的是停靠、协商、二楼。

## §3 决策一：回弹可配

### 3.1 🔴 这个决策翻转了主路径

各端原生 overscroll **全部不可配**：

| 端 | 能否指定回弹参数 | 事实 |
|---|---|---|
| **iOS** | ❌ | rubber band 算法固定阻尼系数（约 `c=0.55`），不可配；自定义需自写 `UIView + UIPanGestureRecognizer`，官方自述"kind of an over-kill" |
| **Android** | ❌ | `onPull(deltaDistance)` 是**相对 View 高度的比例**，非绝对像素；自定义需重写 `EdgeEffectFactory` + `SpringAnimation` |
| **鸿蒙** | ❌（且有版本分裂） | API 21-23 默认 **Fade**，API 24+ 默认 **Spring**；API 24 才支持 `stiffness/damping` |
| **Web** | ❌ | `overscroll-behavior` 只有 `auto/contain/none`，**只能开关不能调**；且 iOS 上对 body 设置会被忽略 |
| **Skyline** | ❌ | `bounces` 只有布尔开关 |

**所以「可配」= 必须禁用原生 + 框架自算。没有第三条路。**

### 3.2 代价：手感成为一号风险

禁用原生后，以下四件事全部要自己做：

| 项 | 说明 |
|---|---|
| **阻尼曲线** | 位移随拉伸距离的衰减（原生是 `d × c × distance` 型渐近） |
| **释放回弹** | 初速度继承 + spring 回到边界 |
| **与惯性的衔接** | 快速滑动撞边 → 惯性如何转成回弹初速度 |
| **多指与中断** | 手势被系统打断（来电、下拉通知栏）时的状态恢复 |

**第 3 条最容易翻车**——惯性转回弹的衔接不对，用户会明显感觉到"黏"或"弹飞"。

### 3.3 但收益同样明确（且是本决策的正当理由）

**① 跨端一致**：iOS 0.55 阻尼 vs Android stretch vs 鸿蒙 API 21/24 两版默认——**原生方案必然不一致**。

**② 绕开鸿蒙版本分裂**：自算后，API 21 与 24 行为统一，**不需要为低版本写降级分支**。

**③ 可声明、可校验**：`damping: 0.55` 是数值，能进封闭集、能 conformance、能数值比对。**原生 API 做不到这一点。**

**④ 与其他能力统一**：回弹物理与 Morpheus 的 spring 用同一套求值器，手感自动一致。

### 3.4 实现方式：双模，但默认是 custom

| 模式 | 触发 | 说明 |
|---|---|---|
| `system` | **显式声明**才走 | 手感最优，不可配，跨端不一致 |
| **`custom`（默认）** | 默认 | 禁用原生，框架自算，可配可校验 |

**为什么默认不是 system**：本方案的立身之本是"跨端一致 + 可声明"。默认走 system 就把核心卖点丢了一半，且开发者一旦用了 system 就在不同端得到不同手感——**这正是要消灭的打地鼠**。

**但必须允许 system**：不接受手感妥协的场景（如纯 iOS 应用）应能退出。

**强制约束**：走 `system` 时，编译期必须**警告并登记到允许差异清单**（VC5-d），不得静默。

### 3.5 禁用原生的各端做法（含已知坑）

| 端 | 做法 | 坑 |
|---|---|---|
| iOS | `bounces = false` + `alwaysBounceVertical = false` | 需在正确的 scroll view 上设，嵌套时内层要单独设 |
| Android | `overScrollMode = NEVER`（或 `EdgeEffectFactory` 返回空 EdgeEffect） | 部分 ROM 定制会忽略 |
| 鸿蒙 | `.edgeEffect(EdgeEffect.None, { alwaysEnabled: true })` | 🔴 **漏 `alwaysEnabled` 会卡顿**——列表到顶后外层感知不到"已到顶" |
| Web | `overscroll-behavior: contain` | 🔴 **iOS 上对 body 设置被忽略**，须设在滚动容器上 |
| Skyline | `bounces = false` | 文档称仅 iOS 生效，实测 iOS/Android 均有（待核实，见 §9） |

### 3.6 🔴 手感验收（必须做，不可省）

**这是本决策唯一的、也是最大的风险。**

验收方式：

| 项 | 方法 |
|---|---|
| **盲测** | 同一设备，原生 App vs Proteus App，让不知情者分辨 |
| **参数扫描** | damping / maxOffset 网格扫描，找最优区间 |
| **高速滑撞边** | 专项测惯性→回弹衔接 |
| **中断恢复** | 手势中断（下拉通知栏）后状态是否正确 |

**验收判据应为"不可分辨"或"主观偏好"，不是数值达标。** 数值达标但手感差是本决策最可能的失败模式。

## §4 决策二：下拉二楼纳入

### 4.1 只有 Skyline 有原生

Skyline 提供了完整的状态机：

```
Idle → CanRefresh → Refreshing → CanTwoLevel
     → TwoLevelOpening → TwoLeveling → TwoLevelClosing
```

可调参数：`refresher-two-level-threshold`、`refresher-two-level-close-threshold`、`refresher-two-level-pinned`、`refresher-two-level-scroll-enabled`。

官方示例演示了"打开二楼后 `wx.navigateTo` 跳新页面"。

**iOS / Android / 鸿蒙 / Web 均无此原生概念——四端必须自研。**

### 4.2 自研要做的三件事

| # | 内容 | 难度 |
|---|---|---|
| 1 | **状态机** | 中——直接对齐 Skyline 的 7 态，保证语义统一 |
| 2 | **手势阈值** | 中——进入二楼的位移阈值、回退阈值，需可配 |
| 3 | **路由衔接** | 🔴 **高——这是真正的难点** |

### 4.3 🔴 第 3 条：二楼本质是路由行为

**"拉到底出现新页面"不是滚动行为，它触发的是一次页面跳转。**

这带来三个必须解决的问题：

| 问题 | 说明 |
|---|---|
| **手势连续性** | 用户手势还没松手，页面已经跳转——跳转动画与手势如何衔接？ |
| **返回语义** | 从二楼返回，是手势下拉还是系统返回键？两者都要支持吗？ |
| **状态保存** | 二楼页面被销毁后再进入，状态是否保留？ |

**建议**：二楼的路由衔接复用已有路由系统（App 端路由与动画系统设计方案），**不新建机制**。二楼只负责"触发跳转 + 提供转场参数"。

**这条不划清，二楼会变成一个独立的路由子系统，与现有路由打架。**

### 4.4 建议的取舍

| 能力 | 建议 |
|---|---|
| 二楼**打开/关闭手势与状态机** | ✅ 纳入（本轮决策） |
| 二楼**内容渲染** | ✅ 纳入（就是一个普通页面/组件） |
| 二楼**路由跳转** | ⚠️ **只做触发，不做独立路由语义**，复用现有路由 |

**这样既满足"降维打击"，又不把组件复杂化。**

## §5 各端原生能力矩阵与已知坑

### 5.1 停靠点（detents）

| 端 | 原生能力 | 单位 | 档位上限 |
|---|---|---|---|
| iOS 15+ | `UISheetPresentationController.detents`（`.medium()`/`.large()`/`.custom(resolver:)`） | 分数（约 50%） | 无明确上限 |
| Android | `BottomSheetBehavior`：`peekHeight` / `halfExpandedRatio`(默认 0.5) / `expandedOffset` | **px** | — |
| 鸿蒙 API 11+ | `bindSheet` 的 `detents` 数组 | **vp** | 🔴 **最多 3 档，且必须递增** |
| Skyline | `sticky-header.offset-top` / `nested-scroll-*` | px | — |
| Web | 无原生 | — | — |

**三个坑：**

**① 鸿蒙最多 3 档且必须递增**——超出会失败。建议**档位上限取 3**（最小公倍数），超出**编译期报错**，不静默截断。

**② 单位不统一**——iOS 是分数、Android 是 px、鸿蒙是 vp。
**对接**：统一走《单位系统与舍入规范》——声明用逻辑单位，内核产**物理像素整数**。

**③ Android `STATE_HALF_EXPANDED` 有前置条件**——必须 `isFitToContents = false` 且官方标注 **Android 11+**。否则半屏态**静默失效**。

### 5.2 嵌套滚动协商

| 端 | 机制 | 坑 |
|---|---|---|
| **iOS** | 内容滚到边缘继续拉 → 扩展 sheet | 🔴 **默认"扩展"**；关闭需 `prefersScrollingExpandsWhenScrolledToEdge = false` |
| **Android** | `isDraggableOnNestedScroll` 需**显式开启** | 🔴 **默认不扩展** |
| **鸿蒙** | `nestedScroll` 的 `scrollForward` / `scrollBackward` **可独立设置** | ✅ **最干净**——官方示例直接用它做"上滑 Banner 先折叠、下滑 List 先滚回顶部" |
| **Skyline** | `nested-scroll-header/body` + worklet | ✅ 最完整 |
| **Web** | 无原生 | — |

**🔴 最容易产生静默差异的一条：iOS 默认扩展、Android 默认不扩展。**

**必须显式声明协商策略，禁止依赖默认值。**

### 5.3 联动（滚动驱动内容变化）

| 端 | 机制 | 坑 |
|---|---|---|
| Skyline | worklet（JS 跑在渲染线程） | 本质是为了躲跨边界开销 |
| 鸿蒙 | 同 5.2 | — |
| Web | `scroll` 事件 + 手写 | 主线程，每帧回调 |
| iOS/Android | 手写 | — |

**🔴 批处理红线**：联动若走 `onScroll → setState`，是**每帧跨边界调用**——与游戏逻辑、动画求值撞的是同一条红线。

**强制约束**：联动必须**声明式绑定 + Rust 侧求值**，与 Morpheus 同构。

> **Skyline 用 worklet 是为了躲这个开销，Proteus 不需要躲——Rust 侧求值天然不在 JS 线程。**

### 5.4 "露出底部内容"（undimmed）

| 端 | 机制 |
|---|---|
| iOS | `largestUndimmedDetentIdentifier = .medium`——**指定从哪一档开始不遮罩** |
| Android | 无对应属性，遮罩是 Dialog 自带，需自己处理 |
| 鸿蒙 | 未查到对应机制（待核实） |

**鸿蒙与 Android 需框架补**——它关系到"能否与背景内容交互"，不是纯视觉。

### 5.5 各端"必须用特定组件"的结构性约束

这是本轮最值得注意的发现：

| 端 | 约束 |
|---|---|
| **Android** | `NestedScrollView` 会**劫持滚动事件**导致 toolbar 不折叠；官方建议改用 `RecyclerView` |
| **iOS** | `UIScrollView` + large title 有一整套 glitch（滚动速度双倍、大标题不折叠、snap 异常）；社区结论是"**应该用 UITableViewController**" |
| **Web** | 全手写 |

**而这些约束在 Proteus 架构里全部不成立**——列表由 Rust 排版核心驱动，0.08ms 全量重排，**不需要 RecyclerView/TableView 的复用机制来救性能**。

> **这是"绕开原生控件树"这个决策的又一次兑现。**
> 建议写进对外材料——它比"我们性能好"更能说明架构选择的意义。

## §6 声明式封闭集设计

### 6.1 可声明项（封闭集）

| 属性 | 取值 | 说明 |
|---|---|---|
| `detents` | 数组，**最多 3 项**，必须递增 | 停靠点 |
| `initial` | detents 中一项 | 初始档位 |
| `overscroll` | `{ damping, maxOffset, mode }` | 回弹（本轮决策：可配） |
| `nested` | `header-first` / `content-first` / `none` | 协商策略 |
| `scrollExpands` | bool | 内容滚到边是否扩展（**必填，不设默认**） |
| `undimmedFrom` | detents 中一项 | 从哪档开始不遮罩 |
| `twoLevel` | `none` / 路由标识 | 二楼（本轮决策：纳入） |
| `bind` | 声明式联动绑定 | 复用 E23 |

### 6.2 硬性约束

| # | 约束 | 违反处理 |
|---|---|---|
| 1 | **档位最多 3、必须递增** | 编译期**报错**，不静默截断 |
| 2 | **`scrollExpands` 必填**（各端默认值相反） | 编译期报错 |
| 3 | **禁止裸 `z-index`** | 编译期报错（层级规范） |
| 4 | **禁止每帧 JS 回调** | 编译期报错（批处理红线） |
| 5 | **走 `system` overscroll 必须显式声明并登记** | 编译期警告 + 登记 VC5-d |

### 6.3 不许出现的逃生口

|---|---|

| 开放任意回弹物理函数 | 毁掉 conformance 与 AI 可校验 |

| 以命令式 API 操作停靠 | 与"不开放任意原生调用"同理 |

## §10 执行指令（给 LLM）

1. 本方案为**独立方案**，不并入《页面层级规范与多端一致性方案》。
2. 两个场景（Sheet 弹层 / 页面级内容容器）**实现一个统一抽象**，不是两个组件。
3. 模态与参照系（距顶/距底）是**参数**，不是分支。
4. **回弹默认 `custom`（框架自算），`system` 需显式声明并登记允许差异清单。**
5. 禁用各端原生 overscroll，按 §3.5 实现（注意鸿蒙 `alwaysEnabled`、Web 不能设在 body、Android `overScrollMode`）。
6. 手感验收**不可省略**，判据是"盲测不可分辨"，不是数值达标。
7. **`scrollExpands` 必填**，不得依赖各端默认值（iOS/Android 默认相反）。
8. 档位最多 3 且递增，超出**编译期报错**不静默截断。
9. 联动必须声明式 + Rust 侧求值，**禁止每帧 JS 回调**。
10. 二楼**只做触发 + 转场参数**，路由复用现有系统，不新建机制。
11. 停靠动画调用 Morpheus，**本方案不自己实现 spring**。
12. 单位统一走《单位系统与舍入规范》：声明逻辑单位，内核产物理像素整数。
13. **对外口径限定为「相对其他跨端框架」，不得表述为「超越原生」。** 此条须同步进叙事文档。
14. SC0 先做，且鸿蒙 API 21/24 差异并进 HC0 一起测，减少一次往返。

### 13.1 SC2 已落地：声明式封闭集 + 编译期校验 + 门禁
