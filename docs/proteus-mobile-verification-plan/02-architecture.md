# G-53 架构

## 1. 三层分工：成本与覆盖率的权衡

| 层 | 覆盖率目标 | 成本 | 承载 |
|----|-----------|------|------|
| **L0/L1 断言** | 绝大部分 | **0** | 纯 node，开发者本地 + PR CI，秒级 |
| **L2 等价类代表** | 剩余部分 | ¥20/次 | 8 台云真机，CI 自动跑 |
| **长尾监控** | 兜底 | — | 崩溃上报，不提前测 |

**核心策略**：不追求"测所有机型"，追求"**用最小成本覆盖最大真实用户**"。

## 2. 总体架构

```
                    TestSuite (G-51)
                          │
                          ▼
              VerificationOrchestrator
                          │  按能力需求自动选档
    ┌─────────┬───────────┼───────────┬────────────┐
    ▼         ▼           ▼           ▼            ▼
in-memory    web      ios-sim    ios-sim-remote  cloud-device
 (零依赖)  (DOM模拟)  (本机Xcode)  (共享Mac池)   (腾讯优测等)
    │                     │            │              │
    └─────────────────────┴────────────┴──────────────┘
                          │
                          ▼
                  CoverageGate（覆盖率门槛）
                          │
                          ▼
                 MatrixReport (G-52) + 覆盖率标注
```

## 3. 四档降级链

```
in-memory (零依赖, 秒级)           ← 默认，覆盖绝大部分断言
   ↓ 需要渲染
web / DOM 模拟
   ↓ 需要真引擎/真进程
ios-sim 本地                       ← 检测到未装 Xcode → SKIP，不崩
   ↓ 本机没有 Mac
ios-sim 远程（共享 Mac 池）        ← ★ 解决"买不起机型"
   ↓ 需要真机硬件/国产 ROM
cloud-device（云真机）             ← 按分钟付费
```

**每档的能力矩阵**：

| 档位 | 逻辑 | 渲染 | 真引擎 | 硬件 | 国产ROM |
|------|------|------|--------|------|---------|
| in-memory | ✅ | ❌ | ❌ | ❌ | ❌ |
| web | ✅ | ✅ | ❌ | ❌ | ❌ |
| ios-sim (local) | ✅ | ✅ | ✅ | ❌ | ❌ |
| ios-sim (remote) | ✅ | ✅ | ✅ | ❌ | ❌ |
| cloud-device | ✅ | ✅ | ✅ | ✅ | ✅ |

## 4. 与 G-51/G-52 的关系

| | G-51 | G-52 | G-53 |
|--|------|------|------|
| 维度 | 执行环境（文档/模拟/真机） | 设备形态（屏幕/系统/输入/环境） | **设备获取方式**（本地/池化/云） |
| 接口 | `execute()` | `executeOn()` | `SimulatorBackend.runIsolated()` + `Orchestrator.execute()` |
| 关系 | ⊂ G-52 | ⊂ G-53 | **扩展，不重写** |

G-53 在 G-51/G-52 之上加"**设备供给层**"，形成三维验证空间：

```
执行环境 (G-51) × 设备形态 (G-52) × 设备供给 (G-53)
```

## 5. 关键设计：不可用 → SKIP，绝不崩溃

沿用 G-46 RSC-01 精神（"缺失即降级，永不崩溃"）贯穿到验证基础设施：

| 情况 | 返回 | 不返回 |
|------|------|--------|
| 未装 Xcode | `SKIP` + reason | ❌ 抛异常 / FAIL |
| 远程模拟器缺 endpoint | `SKIP` + reason | ❌ 崩溃 |
| 档位能力不足 | `DEGRADED` + missing 列表 | ❌ 静默通过 |
| 无可用后端 | `SKIP` + coverage=0 | ❌ FAIL |

**这样没有 Mac / 没有额度的开发者也能跑通 CI**，只是覆盖率下降——**这正是 G-51 门槛机制（渐进覆盖率）的用法**。

## 6. 覆盖率模型

```
score = 加权市场份额 × 执行率
```

- **加权市场份额**：等价类代表机型覆盖的真实用户比例
- **执行率**：非 SKIP 用例占比
- **score ≥ 门槛** → 放行；否则阻断或告警

门槛可按阶段渐进（MVP 0.3 → 成熟期 0.8），**不一步到位**。

## 7. 自动化框架选型建议

| 框架 | Flakiness | 上手 | 建议 |
|------|-----------|------|------|
| **Maestro** | **<1%** | 5 分钟 | **推荐**：YAML 声明式，与 G-52 TestSuite IR 天然同构；内置重试 + 智能同步 |
| Appium | 10-15% | 1-2 天 | 生态最大，但 Flakiness 对 CI 稳定性是硬伤 |
| Airtest | 中 | 低 | 图像识别，适合游戏/非标 UI |

Maestro 限制：iOS 真机需 Maestro Cloud 付费，本地只支持模拟器。但结合第一层（绝大部分不需要真机），影响很小。

## 8. 成熟度模型

```
L0 文档自检        ← G-50
L1 IR 模拟         ← G-51
L2 真运行时        ← G-51 + G-52 设备矩阵
L3 设备供给编排    ← ★ G-53（本份：本地/池化/云统一调度）
L4 开放生态        ← G-50（依赖 G-49 L3）
```
