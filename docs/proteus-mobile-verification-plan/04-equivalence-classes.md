| # | 等价类 | 代表机型 | 份额 | 关键差异 | 推荐档位 |
|---|--------|---------|------|---------|---------|
| 1 | 鸿蒙 NEXT | 华为 Mate 80 | 20% | 分布式、ArkCompiler | cloud-device |
| 2 | iOS 高端 | iPhone 17 | 19% | 沙盒、推送机制 | ios-sim-remote |

| 5 | HyperOS | 小米 17 | 12% | 省电策略 | cloud-device |
| 6 | MagicOS | 荣耀 | 11% | — | cloud-device |

**合计覆盖 ≈ 95% 真实用户。**（注意：折叠屏与前面几类有用户重叠，故总和非简单相加，加权时取上限 1）

## 3. 为什么这 8 台够了

**四维漂移理论**（G-52）：设备差异来自屏幕 / 系统 / 输入 / 环境。

上述 8 类已覆盖：

- **屏幕**：直板（类 1-6、8）+ 折叠（类 7）+ 低端密度（类 8）
- **系统**：鸿蒙 Ark（1）/ iOS JSC（2）/ Android V8（3-6、8）
- **输入**：触摸主线 + 折叠屏多窗口
- **环境**：国内时区语言为主

**长尾机型在这四维上与代表机型同构**——除非引入新的漂移维度（如卷轴屏、AR 眼镜），否则无需新增代表。

## 4. 代表选择原则

**取份额最高者，不是第一个。**

```javascript
representative() {
  return [...this.devices].sort((a,b) => b.share - a.share)[0]
}
```

（G-52 原实现取 `devices[0]`，G-53 修正为按 share 排序——**份额高的机型发现问题影响面更大**）

## 5. 覆盖份额计算

```javascript
coveredShare() { return this.devices.reduce((s,d) => s + d.share, 0) }
```

加权到总覆盖率时**取上限 1**（防止重叠类相加 >100% 导致虚报）：

```javascript
weightedShare(classes) {
  return Math.min(1, classes.reduce((s,c) => s + c.coveredShare(), 0))
}
```

**★ 这条防虚报很重要**：折叠屏用户同时属于品牌类，简单相加会超过 100%，让覆盖率指标失去意义。

## 6. 什么时候需要新增等价类

| 触发条件 | 动作 |
|---------|------|
| 新品牌份额 > 5% | 新增类 |
| 新屏幕形态商用（卷轴/三折叠） | 新增类 |
| 新系统大版本（Android 大改权限模型） | 在现有类内加设备 |
| 现有类内出现**系统性**差异 | 拆分该类 |

**反例**：某单一机型出现偶发崩溃 → **不新增类**，走崩溃监控兜底。

## 7. 诚实边界

- 份额数据是**季度快照**，非架构常量，需定期更新
- "覆盖 95% 用户"是**加权估算**，非精确统计——**不得作为对外承诺的 SLA**
- 本清单基于**中国市场**，出海需另建清单（印度/东南亚/欧美品牌分布完全不同）
- 折叠屏份额与品牌类有重叠，总和非简单相加
