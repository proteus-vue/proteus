# Proteus 端能力对齐方案（执行文档 v1）

> **目标**：把「以小程序为覆盖度标尺」的端能力对齐，**做成一门可复现、有门禁、能沿用到所有后续端**的基础工程标准。
>
> **一句话**：**小程序负责回答「该有哪些能力」（覆盖度标尺），我们的核心 IR 负责回答「这些能力在我们的语义体系里是什么」（对齐基座）**——两者分工，缺一不可。

---

## 为什么需要这份计划

### 问题（2026-09-13 实测暴露）

覆盖度门禁此前只到**组件名级**（`miniprogram-official-spec.json` 只记 84 个组件**名字**）：

```
"有 p-button" → 记为已覆盖 ✅
```

但属性级缺口**完全不可见**：

| 组件 | 官方属性 | 我们声明 | 真机后果 |
|---|---|---|---|
| `p-button` | 22 | 2 | `size`/`type`/`open-type`/`hover-*` **静默失效** |
| `p-switch` | 4 | 0 | `checked`/`disabled`/`color` 不生效 |
| 34 个已映射组件 | 352 | 65 | **仅 18%** |

**根因不是"忘了写"，是"标尺粒度不够"**：门禁看不见的缺口，就不会被修。

### 为什么这是"最基础的工作"

1. **端能力是全部上层的地基**——演示页、业务代码、生态组件都直接消费组件属性；属性缺失 = 上层无一可用。
2. **方法论要求入口可插拔**（G-31）：G-27/G-28/G-29 让后端可插拔，**但若入口（组件/属性）不完整或不语义化，后端自由也白搭**。
3. **标准要先立**：后续 iOS/Android/鸿蒙/Flutter **每一个端的对齐都按同一套标尺与门禁执行**——本计划就是那套标准的定义处。

## 校准原理（★本计划的方法论核心）

```
┌─────────────────────────────────────────────────────────────┐
│  ① 覆盖度标尺（Completeness Ruler）                          │
│     来源：微信小程序官方文档（当前最全的端能力集）             │
│     作用：回答「有没有这个能力」——不许有缺口                  │
│     产物：miniprogram-official-spec.json（组件名）            │
│            miniprogram-component-attrs.json（属性级）★新增    │
└─────────────────────────────────────────────────────────────┘
                              ↓ 逐条对照
┌─────────────────────────────────────────────────────────────┐
│  ② 对齐基座（Alignment Substrate）= 我们的 Component IR       │
│     来源：packages/component-ir（SSOT）                       │
│     作用：回答「这个能力在我们的语义体系里叫什么、承什么约束」  │
│     原则：属性 = **语义约束**（G-32.5），不是平台属性名直译     │
│     例：官方 <button open-type> → 语义 opentype 能力约束       │
│          官方 <input password>   → 语义 ui.input 的 secret 变体 │
└─────────────────────────────────────────────────────────────┘
                              ↓ 落地
┌─────────────────────────────────────────────────────────────┐
│  ③ 三层绑定（Three-Layer Binding）                            │
│     IR props（语义约束）↔ 组件 props（开发者书写面）           │
│                          ↔ 原生属性（各端实现）                │
│     每层可独立演进：新端只改第三层，前两层稳定                 │
└─────────────────────────────────────────────────────────────┘
```

### 与 G-31 原则的一致性（重要，不是妥协）

G-31 铁律：**「禁止将任何既有平台的组件名、属性名、API 形态直接上升为框架标准」**。

本计划**不违反**该铁律，因为两者分工明确：

| | 小程序的角色 | 我们的角色 |
|---|---|---|
| **覆盖度** | **标尺**——「官方 button 有 22 个能力点」 | 逐条回答「我们是否具备」 |
| **命名/形态** | 只作**参考**（用户熟悉度） | **IR 语义定义**（可归一/可合并/可重命名） |

**判定**：缺口必须以「IR 语义能力」补齐，**允许语义归一**（如官方 `value`/`checked` 在我们的 `ui.*` 语义里统一为 `modelValue` 约束），
**不允许**为了"对齐"把平台私有形态（如 `open-type="getRealtimePhoneNumber"`）原样固化成框架语义而不经 IR 登记。
