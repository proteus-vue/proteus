1. **上报能力已有底子（C34）**：`TrackAPI.track(name, params)` 已在（MP `wx.reportEvent` /

2. **★TR4-a 的"内核单一事件入口"仅自绘端成立**：`hit.rs` 冒泡链已有实现级证据（自绘端）；
   **Web=DOM 事件 / MP=微信事件系统** ⇒ 该端无痕埋点靠**编译期产物注入**。
   **不得宣称"所有端事件都经过内核"。**
3. **TR6-a 的"复用内存方案落盘"= 复用规划态设施**（Mnemosyne MS5 零实现）⇒ 两方案**联合冻结

   不得共用总线**（仅共用落盘）。
4. **依赖时序**：TR5 的"复用滚动容器视口"依赖《可停靠滚动容器方案》**SC2**（现为规划态）；
   **VC1-d / VC5-c 在《一致性校验任务卡清单》里"被引用但未列卡"**（既有小缺口）⇒
   本线新增 VC1-e / VC2-f 时**顺带把缺卡补上**。

## 第一批：TR0 实测（必须先做，1.0 人周）

### TR0-a · 各端退出上报时机实测
**现状**：Web 端退出上报时机不明确，业界数据为 `unload` 86.4% / `pagehide`+`visibilitychange` 92.8%（权威性较高）
**目标**：实测五端（Web / Android / iOS / 鸿蒙 / 小程序）页面隐藏事件的触发时机与可靠性
**验收**：
- [ ] 五端各输出一份触发时序表（事件名 → 触发时机 → 是否可发出请求）
- [ ] Web 端明确记录 `beforeunload`/`unload` 的行为（预期：移动端不可靠）
- [ ] 输出各端推荐触发点
**依赖**：无
**风险**：⚠️ iOS Safari 与 Android WebView 行为差异可能很大

---

### TR0-b · 小程序端隐藏事件时机
**现状**：小程序页面生命周期与 App 端不同（`onHide` vs `onPause`）
**目标**：确认小程序端从"用户切走"到"可发请求"的时间窗口
**验收**：
- [ ] 记录 `onHide` / `onUnload` 触发时序
- [ ] 确认切后台后还能否发起网络请求
**依赖**：无
**风险**：⚠️ 小程序切后台后请求可能被中断，需本地缓存补报

---

### TR0-c · App 端进程将死写盘窗口 ★ 与内存方案 MS0 合并
**现状**：未知
**目标**：测量从"应用即将被杀"到"进程终止"之间的可用毫秒数
**验收**：
- [ ] 五端各输出一个毫秒数
- [ ] 明确该窗口内可完成的写盘量级
**依赖**：无
**风险**：🔴 **此卡与《全链路内存安全方案》MS0 是同一测量，必须合并，严禁各测一次**
**说明**：该数字决定埋点队列落盘策略（完整写 vs 增量写）

---

### TR0-d · `sendBeacon` 配额与兼容性实测
**现状**：`sendBeacon` 与 `keepalive` fetch 共享 **64 KiB 累积配额**（权威性较高）
**目标**：实测真实批量下的配额命中率与各内核支持度
**验收**：
- [ ] 记录 X5 内核（chrome 53）是否支持 `sendBeacon`
- [ ] 记录不同批量下的返回 false 比例
- [ ] 确认发送字符串 vs JSON Blob 的行为差异（后者会引入 OPTIONS 预检）
**依赖**：无
**风险**：⚠️ X5 内核基于 chrome 53，**可能不支持 sendBeacon**，需兜底方案

---

### TR0-e · 各端退出上报捕获率基线
**现状**：业界基线 92.8%
**目标**：建立我们自己的捕获率基线
**验收**：
- [ ] 五端各输出一个捕获率数字
- [ ] 低于 92.8% 的端需记录原因与替代方案
**依赖**：TR0-a / TR0-b / TR0-d
**风险**：🔴 若某端显著低于基线，§5.3 的对外表述必须同步修改

## 第二批：TR1 事件 schema 与编译期校验（1.0 人周）

### TR1-a · 事件模型定义
**现状**：**C34 `TrackAPI` 已有薄接口**（`track(name, params)`——无 schema、无校验）⇒ 本卡在其上补事件模型
**目标**：定义统一事件结构
**验收**：
- [ ] 采用三元结构：`event_id` + `event_type` + `properties`
- [ ] `properties` 强制包含 `platform` / `app_version` / `sdk_version`
- [ ] 定义 PV / 曝光 / 点击 / 自定义四类事件
**依赖**：无
**风险**：⚠️ 字段命名一旦定稿难改，需与数据侧对齐

---

### TR1-b · 事件名与参数边界编译期校验 ★
**现状**：uni-app 实践中确认三类静默失败：事件名含非法字符被静默丢弃、参数越界不上报、布尔写成字符串
**目标**：把静默失败变成编译错误
**验收**：
- [ ] 事件名字符集 `^[a-z][a-z0-9_]{0,63}$` — 违反**报错**
- [ ] 字符串参数 ≤256 — 字面量违反**报错**
- [ ] 数值 \|n\| ≤ 2^53-1 — 违反**报错**
- [ ] 禁止字符串 `"true"`/`"false"` — **报错**
- [ ] 禁止嵌套对象 — **报错**
- [ ] 参数个数 ≤20 — **报错**
- [ ] 🔴 **全部为错误不是警告**，代码级证明不存在 warning 降级
**依赖**：TR1-a
**风险**：🔴 **警告会被忽略，最终退化为静默失败——这正是要消灭的东西**

---

### TR1-c · 合规采集开关
**现状**：未知，个保法可能要求采集前明示同意
**目标**：在 schema 层提供合规开关
**验收**：
- [ ] 提供全局采集开关（同意前不采集）
- [ ] 开关为**框架内建**，业务方不写 if-else
**依赖**：TR1-a
**风险**：⚠️ 容易被忽略但后果严重

## 第三批：TR2 oid 生成（1.5 人周）

### TR2-a · oid 生成规则
**现状**：业界靠 xpath（有赞：位置不固定/名称重复/重构即失效）或运行时遍历树（Flutter：渲染未完成时遍历报错）
**目标**：编译期生成稳定 oid
**验收**：
- [ ] `oid = hash(文件路径 + 组件名 + 声明的语义id)`
- [ ] 🔴 **禁止基于 DOM 位置推导 oid**
- [ ] 声明 `track:id` 时 oid 稳定，重构布局不影响
**依赖**：TR1-a
**风险**：🔴 基于位置推导就是 xpath 换了件衣服，必须代码级证明

---

### TR2-b · 自动 oid 生成与回写
**目标**：未声明 `track:id` 时自动生成并回写源码
**验收**：
- [ ] 自动生成的 oid 不重不漏
- [ ] 回写不破坏源码格式
- [ ] 自动 oid 标记为 `auto`，重构时可能变（需在文档中说明）
**依赖**：TR2-a
**风险**：⚠️ 回写源码有风险，需幂等 + 可回滚

---

## 第四批：TR3 SPM 静态拼接（1.0 人周）

### TR3-a · SPM 编译期静态计算
**现状**：去哪儿 RN 方案为编译注入 + 运行时 `autoPath` 逐层透传拼接
**目标**：编译期算出 SPM 并内联为常量
**验收**：
- [ ] 运行时零拼接开销
- [ ] 🔴 不存在"透传链断裂导致 SPM 不完整"的可能
- [ ] 与去哪儿方案对比：我们的运行时成本为 0
**依赖**：TR2-a
**风险**：⚠️ 需确认层级树在编译期完全可见

## 第五批：TR4 内核事件入口（1.5 人周）

### TR4-a · 内核事件观察者（★仅自绘端，入库对账 ②）
**现状**：**自绘端已有实现级证据**（`hit.rs` 冒泡链语义——target + 全部祖先，单测锁定）；
Web=DOM 事件 / MP=微信事件系统**不经过内核**（该端走编译期产物注入）。
对比：小程序需 hook 事件函数且组件事件不冒泡、RN 需高阶组件包装、Flutter 需遍历树
**目标**：自绘端内核对观察者广播；Web/MP 端由编译期注入采集点
**验收**：
- [ ] 自绘端：无痕埋点**不需要修改业务组件**（登记观察者即可）
- [ ] Web/MP 端：编译期注入采集点（oid 编译期生成优势仍成立），**不得宣称"所有端都经内核"**
**依赖**：TR2-a、C34（复用 TrackAPI 出口句柄）
**风险**：⚠️ 跨端表述必须分端（自绘=内核入口 / Web+MP=编译期注入）

---

### TR4-b · 点击与自定义事件采集
**验收**：
- [ ] 点击事件自动携带 oid + SPM
- [ ] 自定义事件通过声明式 API 触发
**依赖**：TR4-a

## 第六批：TR5 曝光检测（1.0 人周）

### TR5-a · 曝光检测内核统一实现 ★
**现状**：Web 用 IntersectionObserver、小程序用 `createIntersectionObserver`，各端语义不同
**目标**：内核统一实现，复用滚动容器视口状态
**验收**：
- [ ] 🔴 **不得各端使用原生 API**
- [ ] 复用《可停靠滚动容器方案》的视口信息
- [ ] 复用《单位系统与舍入规范》的物理像素整数坐标
- [ ] 可见比例阈值可配置
**依赖**：TR4-a、《可停靠滚动容器方案》**SC2**（规划态——TR5 应在 SC2 之后启动）；★C59 交叉观察能力（`wx.createIntersectionObserver` / web `IntersectionObserver`）**已有业务向封装**，本卡要求的是**内核统一实现**（口径一致），不复用各端原生语义
**风险**：🔴 各端原生 API 语义不同会产生口径差异，这正是要消灭的
