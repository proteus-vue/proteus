## 0. 结论（先给结论）

**路线 A（编译期动画 → IR 指令直驱 Rust 内核）可行，推荐作为默认路径。**

三条判据全部成立：

| 判据 | 结果 |
|---|---|
| **① 动画表达式能否编译为直接驱动 Rust 的指令** | ✅ 可行——曲线求值（查表 + 插值）与字段写入全在 Rust 侧完成，**运行时零 JS 求值、零字符串解析** |
| **② 三个代表性场景端到端可跑** | ✅ 位移 / 缩放 / 路由转场（双属性组合）三场景均跑通，**终值精确落在 `to`**（曲线端点钉死） |
| **③ 指令路径 vs JS 路径的帧耗时差** | ✅ **宿主侧加速比 10.5×～84.5×**（随规模增长；见 §2），且**跨边界数据量从 N×11B 降到 0B** |

## 1. 两条路径的成本构成（本 spike 的实际对比对象）

| | 路径 A（指令驱动） | 路径 B（JS 每帧计算 + 指令流） |
|---|---|---|
| JS 侧（每帧） | **0**（启动时一次性发 N 条 ANIM_START） | N 次缓动求值 + 编码 N 条 SET_STYLE |
| 跨边界（每帧） | **1 次函数调用**（只有 `dt` 一个 f32） | N×11B 指令流 |
| 宿主侧（每帧） | O(动画数) 查表插值 + 写 3 个 f32 字段 | 解码 N 条 + 逐条 apply + 标记 N 节点脏 |
| 每帧指令条数 | **0** | **N** |

★**关键差异不是"谁算得快"，而是"每帧要做的工作量与 N 是否成正比"**——
A 的每帧成本只与**活动动画数**相关（且是几次浮点运算），与**节点总数无关**。

## 2. 实测读数（桌面 release 微基准）

> ★**诚实边界（必读）**：
> · 本表是**桌面微基准**，不是真机读数；结论用于**可行性判断与量级对比**，绝对值不跨机比较（本仓纪律）；
> · 路径 B 的 **JS 侧成本（缓动求值 + 编码）不在本进程内**——它是 Node/QuickJS 的工作。
>   本 exp 只测 B 的**宿主侧**（解码 + 应用）与**字节量** ⇒ **报出的加速比是下界**（B 的真实成本 ≥ 此处）；
> · 未接帧循环、未接真机：**真机帧率验证属 RT2 验收**，本轮不声称。

### 2.1 规模扫描（`translate` 场景 · 120 帧）

| N（节点数） | A 每帧均摊 | B 每帧均摊（仅宿主侧） | 加速比 | B 每帧字节 |
|---|---|---|---|---|
| 50 | 0.16 µs | 1.65 µs | **10.5×** | 588 B |
| 200 | 0.48 µs | 12.53 µs | **26.0×** | 2238 B |
| 1000 | 2.38 µs | 201.08 µs | **84.5×** | 11038 B |

★**加速比随 N 增长**（10.5× → 26× → 84.5×）——这正是"O(1) 每帧 vs O(N) 每帧"的预期形态；
且 A 在 **N=1000（每帧 1000 条动画）时仍是 2.38 µs**，相对 16.7ms 帧预算可忽略。

### 2.2 三个代表性场景（N=200 · 120 帧）

| 场景 | 启动条数 | A 每帧均摊 | B 每帧均摊 | 加速比 | 终值 |
|---|---|---|---|---|---|
| **位移**（translateX 0→200） | 200 | 0.55 µs | 12.21 µs | **22.3×** | ✅ 200 精确 |
| **缩放**（scale 0.5→1.0） | 200 | 0.50 µs | 11.92 µs | **23.8×** | ✅ 1.0 精确 |
| **路由转场**（translateX 390→0 + scale 0.96→1.0，双属性） | 400 | 0.94 µs | 25.43 µs | **27.2×** | ✅ 精确 |
| 每帧字节（转场） | — | **0 B** | 4451 B | — | — |

## 3. 正确性判据（不是"跑通了"，是"两侧同式"）

| 判据 | 位置 | 说明 |
|---|---|---|
| 曲线端点精确（`f(0)=0` / `f(1)=1`） | Rust `anim.rs` 单测 + TS `anim-curve-golden` | 动画起止值不允许浮点残差 |
| 曲线 11 采样点 TS ⇄ Rust 一致（1e-5 容差） | `tests/anim-curve-golden.test.ts` | 期望值 = **Rust 实测**（`rt0_curve_dump`），不是"凭印象" |
| 单调性（4 条非弹性曲线不回退） | Rust 单测 | 位移/缩放不能"倒着走" |
| 查表 vs 精确公式误差 < 2e-3 | Rust 单测 | 采样密度足够（65 点） |
| 同 `(node, kind)` 重复 start ⇒ **替换**（不叠加） | Rust 单测 | 避免同属性两段动画叠加导致速度异常 |
| 目标节点不存在 / 曲线越界 ⇒ **Err**（不静默） | Rust 单测 + FFI | 静默会让"动画不生效"极难排查 |
| `scale` 缺省 = 1（不是 0） | Rust 单测 | 缺省为 0 会让所有缩放动画从"消失"开始 |

★**破坏性验证**：把 TS 侧 `easeOutCubic` 从三次改成二次 ⇒ golden 测试 **3 条当场红**
（证明判据能变红，不是"自己跟自己比"）。

## 5. 诚实边界（本 spike **没有**回答的问题）

1. **未接真机**：以上全是桌面微基准。真机帧率/掉帧率验证属 **RT2 验收**（方案 §9 的转场帧率指标）；
2. **未接帧循环**：tick 由谁驱动（vsync / CADisplayLink / Choreographer）未定——属宿主集成（RT2）；
3. **协议层未把 ANIM_START 编入 ops 二进制流**（本 spike 走独立 FFI 入口 + JSON 启动参数）：
   ★这是**有意的设计选择**（见 `ffi.rs` 注释）：每帧一条 20B 消息只为传一个 `dt` 是把 V2「池按需」
   省下的字节又花回去；启动参数走一次性 JSON（N 条动画一次调用）。
   **是否仍要 ANIM_BIND/ANIM_SEEK 等编入指令流**（方案 §4.2 的完整指令集）属 **RT2 决策**；
4. **未做**：`ANIM_BIND`（槽位绑定）/ `ANIM_SEEK`（手势驱动进度）/ `ANIM_PROGRESS`（路由进度广播）
   ——它们依赖手势与路由状态，属 RT2/RT3 的接口面；
5. **结构变更失效**：动画缓存的节点索引在树**压实/删除**后可能失效 —— 本 spike 以"越界即丢弃并计数"
   兜底（不 panic），生产实现应挂**结构变更回调**（RT2 范围）；
6. **弹簧曲线是近似**（阻尼振荡采样），不承诺与任何平台原生 spring 逐帧一致。
