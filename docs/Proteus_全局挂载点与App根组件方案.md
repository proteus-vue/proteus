# Proteus 全局挂载点与 App 根组件方案

> 目标：打破小程序系「App.vue 无根组件」的历史限制，为超级应用提供**真正可承载的全局挂载点**。
> 关联：《页面层级规范与多端一致性方案》《导航体系与多端一致性方案》《单位系统与舍入规范》《Morpheus 方案》《可停靠滚动容器方案》
> 版本：v1　状态：方案已定，待 GP0 实测

---

## 0 结论摘要

| 问题 | 结论 |
|---|---|
| 传统跨端框架 App.vue 的痛点是否真实存在 | ✅ 真实，且**厂商自己承认**（见 §1.1） |
| 根因是什么 | 不是设计选择，是**小程序双线程架构的产物**：App 是逻辑容器，不是渲染容器 |
| Proteus 能否打破 | ✅ 能，而且是**天然能**——绕开原生控件树后，根节点由我们定义 |
| 挂载点怎么设计 | **三层：Global / Page / Overlay**，声明式、编译期可枚举 |
| 最大风险 | 全局层成为**新的逃生口**（运行时任意挂载），必须有上限与编译期校验 |
| 对外能否说"超越所有跨端框架" | ✅ 能，但**必须限定为"对小程序系框架"**，Flutter/RN/Compose 早就有等价物 |

**一句话**：这不是我们发明了什么新东西，而是**我们把 Web/原生开发的常识还给了小程序开发者**。

## 1 问题诊断：App.vue 为什么没有"根"

### 1.1 ★ 厂商自己承认了这件事

uni-app 官方文档对 App.vue 的定位（权威性极高）：

> **App.vue 不能写模板。** 它仅用于：应用生命周期、**全局样式（global style）**、globalData。

社区实测反馈（权威性中等，但技术链条完整且一致）：

| 现象 | 说明 |
|---|---|
| 在 App.vue 写 template | "**很多 `uni.` 方法无法使用**"、"引发了很多问题，不建议这样写"、"会导致编译异常或运行时错误" |
| 全局注册组件（app.component） | **不会自动出现在任何页面**——每个页面是独立 Vue 实例，App.vue 不参与 DOM 渲染 |
| 想要全局 Toast / 登录弹窗 | **每个页面都要手动引入一次** |

**于是社区诞生了一个专门的插件来绕过它**：`@uni-ku/root`（Vite 插件，MIT 协议）——通过编译期变换**虚拟**出一个根组件（`App.ku.vue`），支持 SFC、热更新、PageMeta。

> **一个官方不支持、需要第三方 Vite 插件才能补上的能力，就是最硬的痛点证据。**

补充旁证：uni-app 在新版（uni-app x）中已**移除 tabBar 的 midButton** 等一批原生配置能力，官方文档原话是"通过 uni-ui x 的自定义导航栏和 tabbar 组件来满足"——**厂商在逐步放弃"静态配置模型"**。

### 1.2 根因：App 是逻辑容器，不是渲染容器

小程序架构下：

```
App Service（逻辑层）        WebView / Skyline（渲染层）
   App()  ────────────────►  无对应视图节点
   Page() ────────────────►  一个独立的页面根节点
   Page() ────────────────►  另一个独立的页面根节点
```

**`App()` 在渲染层根本没有对应物。** 所以"App.vue 里写 template"在架构上无处安放——这不是"不想支持"，是"结构上没有位置"。

**而 Proteus 绕开了原生控件树**，渲染树由我们自己构建：

```
Proteus 渲染树（跨端统一）
   Root
     ├─ GlobalLayer      ← 可承载全局挂载（本方案新增）
     ├─ PageLayer        ← 页面栈
     └─ OverlayLayer     ← 最上层（Toast / 弹窗 / 悬浮球）
```

**根节点是我们定义的，所以全局挂载点天然存在。** 这是"绕开原生控件树"的又一次兑现——和鸿蒙 C-API 那次同构。

### 1.2-bis ★**诚实边界（必读）：这条结论分端成立，MP 端不成立**

上面那句"**根节点是我们定义的**"**只对 App 自绘端成立**（Android / iOS / 鸿蒙自绘宿主——他们的渲染树确实由我们构建）。**小程序端不成立**：MP 端的产物是**标准小程序代码**（wxml + wxss + js），渲染树由**微信引擎**构建，我们只能在它的规则内做（`root-portal` / 页面结构 / 编译期变换）。

| 端 | 渲染树归属 | Global 层能否"单实例跨页面存活" |
|---|---|---|
| Web | 我们（DOM） | ✅ 可以（SPA 根组件跨路由存活） |
| Android / iOS / 鸿蒙自绘 | **我们**（自绘宿主） | ✅ 可以（我们定义根节点与层） |
| **小程序（MP）** | **微信引擎**（我们只产 wxml） | 🔴 **不能**——小程序**每页是独立渲染树**，`root-portal` 只脱离**页面内层叠**、不脱离**页面本身** ⇒ Global 层在 MP 上是**每页一份实例** |

**两条结论（不许含糊）**：

1. **MP 的 Global 层 = 源码声明一次 + 运行时每页一份实例。** 这仍是**真实进步**（对照 uni-app 的"每页手写引入"，我们把它变成**编译期自动注入**——与微信官方 `custom-tab-bar` 同一模式：官方也是"每页注入 + 共享状态"）。但**不得对外说成"单实例跨页面存活"**。
2. **MP 的全局层状态共享要另走状态通道**（与 `custom-tab-bar` 一样靠共享状态而非共享实例）——本方案 §3.4"Global 不参与路由栈"在 MP 上要**加一条注**：状态一致性由状态层保证，不是靠实例存活。

> ★**这条边界若不写在最前面，会直接毁掉 §6 的验收口径**：§6 要求"8 条全部不需要每页引入"——**源码层面**成立（声明一次），**实例层面** MP 不成立（每页一份）。两者必须分开讲，否则就是"不实表述"（本仓对外表述纪律明令禁止）。

### 1.3 为什么超级应用特别需要它

| 超级应用诉求 | 小程序系现状 |
|---|---|
| 全局 Toast / Loading | `uni.showToast` 全局单例、样式固定、类型仅 loading/success/none/error、**无法管理顺序** |
| 全局登录失效弹窗 | 每页引入，或依赖 `uni.$emit` 手动广播 |
| 全局悬浮球（客服 / 播放器） | 每页引入 |
| 全局主题容器 / 暗黑切换 | 只能用 CSS 变量 hack |
| 全局网络状态条 | 每页引入 |
| 全局 IM 未读角标 | 每页引入 |

**"每页引入"在 5 个页面时是小事，在 100+ 页面的超级应用里是系统性负担**——而且每次新增页面都可能漏引，漏了不报错。

## 2 各端原生挂载能力矩阵（事实依据）

| 端 | 机制 | 关键事实 | 权威性 |
|---|---|---|---|
| **Web** | Vue 3 `Teleport to="body"` | 原生支持，`document.body` 存在；Teleport 只移动 DOM，**不移动逻辑与作用域样式**（scoped 仍生效） | 极高 |
| **小程序** | `root-portal` | 基础库 **2.25.2+**；"使整个子树从页面中脱离出来"；**Skyline 完全支持** | 极高 |
| 小程序 | `page-meta` | 基础库 **2.9.0+**；**只能是页面第一个节点**；只能配属性（背景色/字号/滚动），**不能挂内容** | 极高 |
| **Android** | `PhoneWindow` / `DecorView` | Activity 对应一个 PhoneWindow；Dialog 依附 Activity Token；窗口 type 定 Z-order（application 1–99、sub 1000–1999、system 2000–2999） | 较高 |
| Android | `TYPE_APPLICATION_OVERLAY` | **需 SYSTEM_ALERT_WINDOW 敏感权限**（8.0 起） | 极高 |
| **iOS** | 独立 `UIWindow` + `windowLevel` | `normal < statusBar < alert`；自定义 window 需透明背景、重写 `pointInside` 只响应目标区域、监听键盘通知重置层级 | 较高 |
| **鸿蒙** | `WindowStage` 子窗口 | Stage 模型每个 UIAbility 一个 WindowStage；`createSubWindowWithOptions` 创建子窗口（弹窗、悬浮球）；**子窗口生命周期跟随主窗口**；`setWindowZLevel` 设相对层级 | 极高 |
| 鸿蒙 | 全局悬浮窗 | 是独立窗口类型，**应用退至后台仍可显示** | 极高 |
| **Flutter** | `Overlay` + `OverlayEntry` | `Overlay.of(context).insert(entry)`；entry 有 builder / opaque / maintainState；**opaque=true 可跳过下层构建** | 极高 |
| **RN** | `Portal` | RN **没有 z-index**，只能把浮层移到树顶（react-native-paper 即如此实现） | 较高 |
| **Compose** | `Scaffold` + `SnackbarHost` | `SnackbarHostState` 管队列；可用 `CompositionLocal` 全局访问，甚至从 ViewModel 通过 Channel 触发 | 极高 |

### 2.1 ★ 从矩阵读出的三条结论

**① Web 和鸿蒙最强，小程序最弱，但不为零**
`root-portal` + `page-meta` 组合起来能覆盖大部分场景，**Skyline 明确完全支持 root-portal**。所以小程序端不是做不到，是**uni-app 没做**。

**② Android / iOS 原生都有"独立窗口"这条路**
但它有代价：Android `TYPE_APPLICATION_OVERLAY` 要敏感权限、iOS 13+ 直接创建 UIWindow 可能被系统拦截。**所以全局挂载应优先走"同一窗口内分层"，独立窗口只作为高权限场景的例外。**

**③ Flutter / RN / Compose 全都有等价物**
**这说明"全局挂载"不是我们的创新，我们的创新是把它带到小程序系。** 对外表述必须限定（见 §10）。

## 3 Proteus 三层挂载模型

```
Root
├─ GlobalLayer   全局层  跨页面存活，随 App 生命周期
│    ├─ 主题容器 / Provider
│    ├─ 全局网络状态条
│    ├─ 全局悬浮球（播放器 / 客服）
│    └─ 全局音乐播放条
├─ PageLayer     页面层  路由栈，与导航体系联动
│    └─ 当前页面（可多栈，见导航方案）
└─ OverlayLayer  浮层   最上层，模态 / Toast / 登录失效弹窗
     ├─ 弹层栈（见层级规范）
     └─ Toast 队列
```

### 3.1 三层的语义边界

| 层 | 生命周期 | 是否随页面销毁 | 典型内容 | 是否拦截交互 |
|---|---|---|---|---|
| **Global** | App | ❌ 永不 | 主题、播放器、悬浮球、状态条 | ❌ 参与布局/不遮挡（除非声明） |
| **Page** | 页面栈 | ✅ | 页面内容 | — |
| **Overlay** | 显式控制 | ✅ | Toast、弹窗、登录拦截 | ✅ |

**关键区分**：Global 与 Overlay 常被混为一谈，但它们是两件事——

- **Global 是"一直在"**（悬浮球、播放器），参与正常布局流
- **Overlay 是"临时出现"**（Toast、弹窗），浮在最上且拦截交互

uni-app 的 `uni.showToast` 之所以难用，**正是因为它把这两类硬塞进一个全局单例**。

### 3.2 声明式设计（核心约束）

```vue
<!-- App.vue —— Proteus 支持真正的 template -->
<template>
  <app-root>
    <global-layer>
      <theme-provider>
        <network-status-bar />
        <floating-player />
      </theme-provider>
    </global-layer>
  </app-root>
</template>
```

**三条硬约束：**

| # | 约束 | 理由 |
|---|---|---|
| **C1** | 全局挂载点**必须在 App.vue 的 template 中声明**，编译期可枚举 | 防止运行时任意 insert 成为逃生口 |
| **C2** | **全局层挂载节点数量上限**（建议 32），超出编译期报错 | 全局层常驻内存，无限膨胀会拖垮超级应用 |
| **C3** | 全局层**不得包含页面级业务组件** | 编译期静态检查：引用了 `useRoute` / 页面参数即报错 |

**C1 尤其重要**——它决定了这个能力是"架构能力"还是"新逃生口"。开放运行时 `insertGlobal(vnode)` 会让 conformance、AI 可校验同时失效，而且**是静默的**。

> 这与"不开放任意原生调用""TSX 是逃生口"是同一条原则：**收敛模型适用于可枚举的声明，不适用于任意运行时行为。**

### 3.3 与页面层级规范的联动

全局三层的层级**必须在编译期确定**，不能运行时竞争：

```
Overlay  >  Page  >  Global
```

且各层内部遵循《页面层级规范与多端一致性方案》的四层语义（Content / Navigation / Mask / Popout）。

**禁止在 Global 层使用 `layer="popout"`** —— 编译期报错，避免全局层与浮层栈争抢层级。

### 3.4 与路由的联动

- Global 层**不参与路由栈**，切换页面不影响其状态
- Overlay 层中的**登录失效弹窗等模态拦截**，应与路由守卫协同（见《导航体系方案》），但**不新建机制**
- **禁止在 Global 层调用 `navigateTo`** —— 编译期检查（C3 的具体化）

## 4 各端实现映射

| 层 | Web | 小程序 | Android | iOS | 鸿蒙 |
|---|---|---|---|---|---|
| **Global** | 渲染树内节点 | 渲染树内节点 | 同窗口内节点 | 同窗口内节点 | 同窗口内节点 |
| **Page** | 渲染树 | 渲染树 | 渲染树 | 渲染树 | 渲染树 |
| **Overlay** | 渲染树内 / Teleport | **`root-portal`** | 同窗口内 / 子窗口（例外） | 同窗口内 / 独立 `UIWindow`（例外） | **WindowStage 子窗口** |

**★实例数（§1.2-bis 的量化形态——**新增列，决定内存模型与验收口径**）**：

| 层 | Web | 小程序 | Android / iOS / 鸿蒙自绘 |
|---|---|---|---|
| **Global** | **1**（SPA 根组件跨路由存活） | **N = 页面栈深度**（每页一棵独立渲染树） | **1**（我们定义根节点） |
| **Page** | 1（当前路由） | 1（当前页） | 1 |
| **Overlay** | 1 / 按需 | 1（**当前页内**的 root-portal） | 1 |

⇒ **MP 的 Global 层内存开销是 O(页面栈)**（§5.6 的隐患在小程序端**加重 N 倍**）；
⇒ MP 的 C2 节点上限（32）应理解为**每页 32**，实际驻留 = 32 × N——**GP2-c 的校准必须带这条**。

### 4.0 ★既有实现（本批盘点）：Overlay 不是从零开始

**本仓 2026-09-08 起已有 overlay 级传送的完整实现**，本方案 §4 是**收口**而不是新建：

| 既有件 | 位置 | 状态 |
|---|---|---|
| `<teleport>` → `<root-portal>` 编译 | `packages/compiler/src/template.ts`（`template/teleport-root-portal`） | ✅ 已落地 |
| 弹层组件四件套（用 teleport） | `p-drawer` / `p-popover` / `p-page-container`（`p-modal` 走同类结构） | ✅ 已在用 |
| **portal 常驻 + class 驱动**（血泪经验） | `docs/skyline-pitfalls.md` **S47**：portal 内容用 `v-if` 卸载重挂 ⇒ **二次打开卡死 + 页面无法滚动**（glass-easel） | ✅ 已固化 |
| 层级四层语义（Content/Navigation/Mask/Popout） | `packages/contracts/src/layers.ts`（LY0/LY1 编译期校验） | ✅ 已有契约，可直接接 |

★**推论**：**GP3-b 的真实增量 = Global 层**（Overlay 复用既有链路 + 收口）；估算应从 1 人周**拆成两张卡**
（Overlay 收口 ≈0.2 人周 · Global 层新建 ≈0.8 人周，含每页注入机制）。

**设计原则：优先在自有渲染树内解决，原生窗口机制只作为例外。**

理由：自有渲染树内解决 = 与指令流同构 = 可数值校验、可 conformance、层级由我们控制。
原生窗口 = 不受指令流管辖 = 层级、单位、动画全部脱管。

### 4.1 例外通道（需显式登记）

| 场景 | 机制 | 代价 |
|---|---|---|
| 应用退到后台仍显示 | Android `TYPE_APPLICATION_OVERLAY` / 鸿蒙全局悬浮窗 | 需敏感权限，须**用户授权流程** |
| 系统键盘之上 | iOS 独立 `UIWindow` + `windowLevel` | 需处理键盘通知、iOS 13+ 场景管理 |
| 跨 UIAbility 显示 | 鸿蒙全局悬浮窗 | 独立窗口类型，生命周期独立 |

**例外通道必须显式登记**（与 XComponent 自绘、TSX 同一套机制），不得默认开启。

## 5 🔴 六个必须处理的陷阱

### 5.1 Skyline 下 root-portal 的点击穿透

微信服务市场已确认（权威性中等，有官方回复）：

> **基础库 3.8.4 + Skyline：`root-portal` 内组件点击穿透**（3.5.8 正常）。规避方式是**把 `virtualHost` 设为 `false`**（设 true 是为了规避其他场景问题）。

**这是一个版本相关的静默失效**——不报错，就是点不动。必须：

- 编译期固定 `virtualHost=false`（除非业务显式要求）
- 真机矩阵覆盖主要基础库版本回归

### 5.2 Skyline 没有 fixed

Skyline **不支持 `position: fixed`**，官方建议"页面根节点下使用 absolute 即可达到 fixed 效果"；**也不支持原生导航栏**。

所以全局浮层在 Skyline 上**必须挂到 root，不能依赖 fixed**。这正是本方案把 Overlay 做成独立层的原因——不要指望 CSS。

### 5.3 Android 独立窗口的权限门槛

`TYPE_APPLICATION_OVERLAY` 是敏感权限（Android 8.0 起）。**若使用，必须有完整授权流程与拒绝降级**，不能静默失败。

### 5.4 iOS 独立窗口的三个附加成本

- 需**透明背景**
- 需重写 `pointInside` 只响应目标区域（否则拦截全屏点击）
- 需**监听键盘通知重置层级**（键盘本身就是高 windowLevel 的独立窗口）

### 5.5 鸿蒙子窗口生命周期跟随主窗口

`createSubWindowWithOptions` 创建的子窗口**生命周期跟随主窗口**——这既是好处（自动回收）也是约束（无法独立于主窗口存活）。需要"退到后台仍显示"时必须走全局悬浮窗（例外通道）。

### 5.6 ★ 全局层是内存常驻，超级应用的隐形负担

Global 层**永不销毁**。超级应用若在 Global 层塞入：

- 全局 IM 会话列表
- 全局埋点缓冲
- 全局图片预加载缓存

**会形成一块永不释放的内存。** 建议：

| 约束 | 值 |
|---|---|
| Global 层挂载节点数上限 | **32**（C2） |
| Global 层不得持有业务数据集合 | 编译期检查 + 运行时告警 |
| 必须提供 `unmountGlobal(id)` 显式卸载 | 与 `insertGlobal` 对称 |

## 6 超级应用场景验收清单

方案是否真的"承载超级应用"，用这八条验收：

| # | 场景 | 全局层 | ① 源码是否每页手写 | ② MP 实例数 | ③ 自绘端实例数 |
|---|---|---|---|---|---|
| 1 | 全局 Toast（可排队、可自定义样式、可指定位置） | Overlay | ❌ 声明一次 | 1（当前页内） | 1 |
| 2 | 全局 Loading（可多实例、可指定遮罩范围） | Overlay | ❌ | 1 | 1 |
| 3 | 全局登录失效拦截弹窗（不可取消） | Overlay | ❌ | 1 | 1 |
| 4 | 全局悬浮球（播放器 / 客服） | Global | ❌ | **N（页面栈）** | 1 |
| 5 | 全局音乐播放条 | Global | ❌ | **N** | 1 |
| 6 | 全局网络状态条 | Global | ❌ | **N** | 1 |
| 7 | 全局主题容器（暗黑切换，无需刷新页面） | Global | ❌ | **N** | 1 |
| 8 | 全局 IM 未读角标（跨页面同步） | Global + 状态 | ❌ | **N**（状态共享，实例不共享） | 1 |

**★判据（两栏分开，缺一不可——见 §1.2-bis）**：
- **① 源码层面：8 条全部"否"**（声明一次，编译期自动注入）——**这是本方案的核心承诺**，任何一条需要手写引入 ⇒ 方案不成立；
- **② 实例层面：MP 端 Global 层为 N（页面栈深度）**——**这是小程序架构的固有约束，不是缺陷**，
  且与微信官方 `custom-tab-bar` 同一模式（官方也是每页注入 + 共享状态）。
  ⇒ **不得对外宣称"MP 端单实例跨页面存活"**（不实表述，违反 §9 禁语纪律）。

对照 uni-app 现状：这 8 条里**至少 5 条需要每页手写引入或依赖全局单例 hack**（注意：
uni-app 是**①源码层面**的负担——那正是差异所在；不要把它与 MP 的**②实例层面**混淆）。

## 9 对外表述

### ✅ 可以讲

- **"App.vue 支持真正的 template，全局组件声明一次，全应用生效。"**
- **"三层挂载模型：Global / Page / Overlay，语义清晰，编译期可校验。"**
- **"Toast 支持排队、自定义样式与位置，不再是全局单例。"**

### ❌ 禁止讲

| 错误表述 | 问题 |
|---|---|
| "我们首创了全局挂载机制" | **Flutter Overlay、RN Portal、Compose SnackbarHost 都是等价物**，会被拆穿 |
| "我们超越了所有跨端框架" | 必须限定为"**对小程序系框架**" |
| "支持任意组件挂到全局" | 与 C1/C2/C3 冲突，且是逃生口径 |

### 推荐落点

> **"全局挂载不是新发明，Web 和原生开发一直有。我们做的，是把这个常识还给小程序开发者。"**

这句话同时体现了能力边界的诚实与对小程序系真实痛点的直击。

## 10 与既有方案的边界

| 方案 | 边界 |
|---|---|
| 《页面层级规范》 | 层级规范管**层内**的 z-order；本方案管**三层之间**的顺序 |
| 《导航体系方案》 | 路由管 Page 层；Global 层不参与路由，Overlay 层与路由守卫协同但不新建机制 |
| 《Morpheus 方案》 | 全局层组件的动画照常走 Morpheus；但**全局层不得使用 `layer="popout"`** |
| 《可停靠滚动容器》 | Sheet 挂 Overlay 层，页面级容器挂 Page 层 |
| 《单位系统与舍入规范》 | 全局层坐标同走物理像素整数指令流 |
