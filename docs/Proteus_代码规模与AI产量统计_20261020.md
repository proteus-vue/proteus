## 五、口径与边界（诚实账）

1. **立项时间无法从 git 精确得到**：git 历史起点 2026-09-18，`.git` 目录创建于 2026-08-28，归档里最早日期 2026-07-31，08-28 进度快照已记录「350 测试 / 决策 #116」。→ 项目实际跨度约 **82 天（07-31 → 10-20）**，但只有后 33 天有逐提交数据。
2. **行数 ≠ 有效工作量**：产品代码含 22% 注释、5.6% 空行；`scripts/`（33k）与站点示例（80k）不是框架本体。
3. **删除量不可忽略**：33 天删了 17.8 万行，10-05/06 两天净删 9 万行（重构 + 删死代码）。净增口径已扣除，但「总新增 99.9 万行」含返工。
4. **仓库里误提交了构建产物**：`spike/target-qjs/`（Rust rlib/rmeta）与 `hosts/.../libproteus_layout_core.a`（33 MB）被跟踪，占 190 MB 生成物 + 209 MB 二进制的绝大部分。不影响行数统计，但影响 clone 体积，建议后续 `git rm --cached` + LFS。
5. **本统计不含** node_modules、dist 产物、非 git 跟踪的临时文件。
6. 测试用例 6,400 条取自门禁记录（`pnpm test` 输出），未重新跑全量（避免占用并发会话资源）。

## 六、AI 原生口径（本项目定位修正：全 AI 完成、面向 AI 维护）

> 关键前提：**本项目的规模评级不能用人类团队口径直接套。** 人类项目的规模瓶颈是沟通成本（Brooks：n(n−1)/2 条沟通通道），AI 项目的瓶颈是**上下文窗口 + 跨会话记忆漂移 + 验证成本**。同一份代码，对人类是「大型」，对 AI 可能已经是「超大型」。

### 6.1 为什么行数不是 AI 口径的主指标

| 人类口径的规模 | AI 口径的等价约束 |
|---|---|
| 团队人数 × 沟通通道 | **单会话能否闭环一次有意义的改动** |
| 代码行数 / 人月 | **上下文可读量**（多少行能被一次性装进窗口且不丢关键约束） |
| Code Review 成本 | **门禁能否给出机器可判的正确性信号**（AI 无法自我 review） |
| 文档作为交付物 | **文档作为上下文补给**（下次会话的唯一记忆载体） |
| 模块耦合度 | **跨模块契约变更能否被单会话完整验证**（五端同步即超限） |

### 6.2 本仓库实际长出来的「AI 适配」指标（都是可量化的结构性事实）

| 指标 | 数值 | 说明 |
|---|---:|---|
| 代码文件中位行数 | **120 行** | 2,441 个代码文件；均值 219、p90 409、p99 1,904 |
| >500 行文件 | 177 个（7%） | 人类项目常见 30–50%，这里被压到 7% |
| >1000 行文件 | 63 个（2.6%） | 全部在棘轮基线里「只减不增」 |
| 新增文件硬上限 | **1,000 行** | 决策 #872；历史教训 `capability.ts` 曾达 **8,987 行** |
| 文档 : 代码 | **0.54 : 1** | 238,504 : 443,389（人类项目通常 0.05–0.1） |
| 门禁 : 包 | **3.0 条/包** | 152 条 `check:*` / 51 个包 |
| 测试 : 产品 | 1 : 4.3 | 537 个测试文件、约 6,400 用例 |
| 记忆入口 | **153 行 / 40 KB** | `PROJECT_MEMORY.md`（约 1.2 万 tokens，单会话可读完） |
| 记忆归档 | 30,137 行 | `decisions.md` 10,860 行 + 月度归档 19,277 行（按需 grep，不整读） |
| 决策 / AI 任务账本 | 1,134 条 / 107 条 | 跨会话的「已定案」与「待办」 |

### 6.3 两个「上下文爆炸」事故，是 AI 规模边界的直接证据

1. **`PROJECT_MEMORY.md` 曾达 11,118 行 / 2.4 MB**（约 70–80 万 tokens）——任何新会话都读不完，等同于「失忆」。⇒ 2026-10-03 立《收纳规范》：主文件只留 3 条速览，历史全部归档，并配 `check:memory` 门禁（上限 / 结构 / 速览条数 / H3 泄漏）。
2. **`capability.ts` 曾达 8,987 行**——单文件超出「整文件可读」范围后，AI 每次改动都只能看到局部，必然改出跨模块回归。⇒ 决策 #870 拆三层、#872 立 `check:file-size` 棘轮。

这两条说明：**这个项目撞到 AI 规模上限的时间，比撞到人类规模上限的时间早得多**，而且它靠「限制自己写多大」才继续扩展。

### 6.4 修正后的评级

| 口径 | 评级 | 依据 |
|---|---|---|
| 人类 LOC 分级（10万–100万=大型） | **大型（中上）** | 44.3 万行产品代码，距 100 万还差 2.3 倍 |
| 人类功能点口径（>5,000 FP=超大型） | **超大型下沿** | 32 万 SLOC ≈ 4,600–6,400 FP |
| 结构复杂度（跨语言 ABI / 3 宿主 / 51 包） | **超大型形态** | 加一门语言的成本是 O(n) 边界重验，非线性 |
| **AI 可维护容量** | **已进入超大型区** | 单会话已无法独立完成跨端契约变更；必须依赖 152 门禁 + 归档记忆 + 文件上限三重治理才能继续扩展 |
| 团队规模 | 微型（1 人 + AI） | 单人承担超大型结构与「唯一验收者」角色 |

**结论句**：对人类团队它是「大型框架」，对一个 AI 协作体它是**「已到容量上限、正在靠制度化自我约束维持扩展」的超大型工程**——而这个上限不是行数决定的，是 **153 行记忆入口 + 1,000 行文件上限 + 152 条门禁** 这三个数字决定的。任何一个失守，规模就会反向坍缩成「读不动、改不敢改」。

### 6.5 因此，产能指标也应换口径

- 旧口径（人月）：44.3 万行 ≈ 8–15 人资深团队的年产出 —— **对 AI 项目没有意义**，因为 AI 的边际成本不在打字而在验证。
- 新口径（可验证增量）：33 天 1,804 次提交、净增 47 万行、**每次提交都过门禁**，即「每会话一次可判定的闭环」。
- 真正该盯的比率：**fix : feat = 0.61**（返工率）、**门禁数增长 vs 包数增长**（治理密度）、**>1,000 行文件数是否回升**（熵增）。

## 附：统计方法

- 快照：`git ls-files` 全量 → 按扩展名 + 路径规则分桶（CODE / TEST / DOC / DATA / GEN / BIN）→ 逐文件流式计行（跳过 >3MB 与大二进制）。
- 历史：`git log --numstat --format=@@%ad --date=short --no-merges` 流式聚合到「日 × 类别」。
- 分类规则：`*.test.*`、`tests/`、`__tests__/`、`fixtures/` → TEST；`dist/`、`generated/`、`*.d.ts`、`target`、lock → GEN；其余按扩展名。
