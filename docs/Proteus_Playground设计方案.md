# Proteus Playground 设计方案

> 定位：**扫码即玩的端上预览与调试环境**——Vue 源码云端编译为 IR 产物，扫码下载、秒级运行
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4）
> 本文档是《Proteus App 端高性能渲染落地方案》与《Vapor for Proteus IR 设计方案》的配套文档

---

## 0. 先确认两件事（本文档的两处决策）

写文档前我问了两个问题，此处给出**默认选择**，如与你的判断不符请指出，我按你的意见调整：

| # | 问题 | 本文默认选择 | 理由 |
|---|---|---|---|
| ① | 先做纯 JS 最小壳，还是一上来就预置地图/WebView 等原生模块？ | **先做纯 JS 最小壳** | 快速验证核心链路；原生模块通过「扩展壳」机制后续增量加入 |
| ② | 只做开发调试，还是连生产态热更新一起设计？ | **先做开发调试，架构预留生产 OTA** | 生产 OTA 涉及签名、灰度、回滚、合规，是另一条产品线；但架构必须预留，否则事后加不动 |

## 1. 为什么这件事值得做

### 1.1 战略价值：兼得「原生性能 + 动态化」

这是业界长期互斥的两个目标，回顾既有路线的取舍：

| 路线 | 原生性能 | 动态化 |
|---|---|---|
| 编译到原生（UTS / Kuikly） | ✅ | ❌ **基本丧失** |
| Kuikly 的补救 | — | 双模设计（Android 用平台产物保性能；iOS / 鸿蒙退回 JS 保动态化） |
| **Proteus** | ✅ | ✅ **天然支持** |

**差别根源**：Proteus 从没把逻辑层编译到原生。

渲染性能来自**自研渲染管线**（Rust 排版核心，宿主侧实测 1ms），逻辑层始终是 JS。因此动态下发是免费的，**不需要 Kuikly 那种"双模"妥协**。

> 反讽但重要的佐证：uni-app x 蒸汽模式**把 JS 引擎请了回来**，官方给出的理由之一就是动态化。

**闭环第一轮那个问题**：如果当初走了「自研编译语言 / UTS 路线」，逻辑层被编译成 Kotlin/Swift，**这个 playground 根本不存在**。而现在它几乎白送。

### 1.2 推广价值：把试用门槛砍掉

自研框架推广的最大门槛是**试用成本**——要求对方装一整套工具链才能看一眼，转化率极低。扫码即玩直接消除这道门槛。

### 1.3 它是架构体检报告

Playground 强制把「云端编译 → 产物下发 → 端上加载 → 渲染」整条链路跑通，会暴露本地开发时看不到的所有问题（产物体积、加载耗时、版本兼容、降级路径）。**它的存在本身就在倒逼架构变干净。**

## 2. 技术澄清：不能直接跑 Web 端那个 bundle.js

这一点必须先说清楚，否则实现时会对不上。

| bundle 内容 | App 端能跑吗 | 性能 |
|---|---|---|
| Web 端 VDOM 版 bundle.js | ✅ 能跑 | **当前水平（70ms）** |
| **IR 产物**（LayoutTemplate + PatchTable + UpdateProgram） | ✅ | **目标 1ms** |

项目定位是「Web 端零转换直跑标准 SPA」，Web 端那份 bundle 走 VDOM。**App 端要拿到 IR 性能，消费的必须是编译后的 IR 产物。**

### 2.1 正确链路

```
┌─ 开发态（本地迭代）───────────────────────────┐
│ 开发者改代码 → 本地 dev server → 增量编译      │
│        → 推送给手机 → 热重载                   │
└──────────────────────────────────────────────┘

┌─ 分发态（分享 / 预览）────────────────────────┐
│ git push / CLI 上传 → 云端编译 → 产物上 CDN    │
│        → 生成二维码 → 扫码 → App 下载 → 运行   │
└──────────────────────────────────────────────┘
```

两条路径共用同一套产物格式与端上加载器。

## 4. 壳 App 架构

### 4.1 v1 最小壳（决策①的产物）

**只内置不依赖第三方原生 SDK 的能力**，目标是快速跑通链路：

| 类别 | 内容 |
|---|---|
| 运行时 | Hermes + IR 加载器 + Rust 排版核心 + 平台绘制层 |
| 自研组件 | view / text / image / list / scroll-view / rich-text |
| 系统能力 | 网络请求、本地存储、震动、剪贴板、基础传感器 |
| 调试 | 开发者菜单、节点树 inspect、帧耗时打点、日志回传 |

### 4.2 原生模块是硬边界（必须提前认）

**地图、WebView、广告 SDK 这类原生组件无法动态下发**——必须在壳里预编译。这是 Expo Go 的固有局限，不是实现问题。

**缓解机制（v1 就要设计，不能事后补）**：

```
壳的能力清单 (manifest)
      ↓ 产物声明所需能力
      ↓ 端上校验
   ┌──┴──┐
  满足  →  正常运行
  不满足 →  明确报错 + 提示需要「扩展壳」
```

### 4.3 扩展壳机制（对应 Expo 的 development build）

需要自定义原生能力时，用 Proteus CLI 生成一个**包含指定原生模块的自定义壳**：

| | Playground 公共壳 | 扩展壳 |
|---|---|---|
| 获取 | 应用商店安装 | CLI 构建（一次性，分钟级～十几分钟） |
| 原生模块 | 固定预置集 | 项目声明的任意模块 |
| 适用 | 预览、分享、快速验证 | 含原生依赖的真实项目 |
| 原生依赖变更时 | 无需重建 | **需重建** |

**关键设计**：扩展壳与公共壳**共用同一套产物格式与加载器**，只有内置模块集不同。这样切换成本最低。

### 4.4 版本协商（必须做）

产物编译时绑定的 IR 版本 / 排版核心版本 / Profile 版本，必须与端上壳兼容。

**强制要求**：
1. 产物头部写入 `minShellVersion` 与 `irVersion`
2. 端上校验不通过 → 明确提示升级壳，而不是静默崩溃
3. 版本号语义化，禁止用 commit hash 之类的不可比标识

## 5. JS 引擎选型：Hermes

### 5.1 iOS 上 JSC 是被阉割的

**核心事实**：Apple 禁止第三方 App 在运行时分配「可写可执行」内存页（W^X），因此 **JSC 的 JIT 在 iOS 上被禁用，只能解释执行**。JSC 最大的优势直接消失，却仍要承担解释器的开销。

RN 官方文档亦明确：iOS 上 JavaScriptCore 因缺少可写可执行内存而不使用 JIT。

### 5.2 Hermes 不受此限制

Hermes 从设计上就不依赖 JIT——**构建期 AOT 预编译为字节码**，运行时直接加载执行，跳过解析与 JIT 环节。

实测收益（不同来源，口径不同，仅作量级参考）：

| 指标 | 变化 |
|---|---|
| TTI | 4.3s → 2.01s |
| APK 体积 | 41MB → 22MB |
| 内存占用 | 185MB → 136MB |
| 运行时二进制 | < 2MB（JSC 为 8MB+） |
| 字节码体积 | 比 minified JS 小 30–40% |

### 5.3 代价与我们的适配度

**Hermes 无 JIT，长任务计算不如 V8 / JSC 的 JIT 版本。**

**但这个代价对 Proteus 几乎无影响**——逻辑层本来就不是瓶颈（宿主侧 1ms 已证明）。Hermes 擅长的恰恰是启动速度与内存，与需求高度吻合。

需留意：Hermes 对部分 ES 特性支持落后于 JSC/V8，涉及 `Intl`、复杂正则、`Proxy`/`WeakRef` 高级用法时需验证。**Vue 响应式重度依赖 Proxy，此项必须在 v1 就验证。**

### 5.4 ⚠️ 一条需要核实的合规风险

有资料称：**iOS 26 移除了对 legacy JIT runtime 的支持，并阻止非官方的 JavaScriptCore 集成**。该来源权威性较低，**建议立即自行核实**——若属实，则 Hermes（非 JIT）是唯一稳妥选择，选型确定性反而更高。

### 5.5 结论

**选 Hermes。** 且由于「非 JIT」这一性质与 iOS 的安全策略天然兼容，这个选择在 iOS 26 之后只会更硬。

## 6. 产物规格

### 6.1 产物包组成（三份 + 一份）

复用既有方案 §4 与 Vapor IR 方案 §1.1 的定义：

```
playground-bundle/
├── manifest.json          元信息：版本、入口、能力声明、签名
├── layout_template.bin    LayoutTemplate（静态结构，扁平数组）
├── patch_table.bin        PatchTable（动态槽位表）
├── update_program.bin     UpdateProgram（更新程序）★ Vapor IR 方案新增
└── logic.hbc              Hermes 字节码（业务逻辑 + 槽位运行时）
```

### 6.2 为什么 IR 三份产物与 JS 字节码分离

| 部分 | 载体 | 更新频率 |
|---|---|---|
| 结构 + 绑定 + 更新逻辑 | IR 二进制（三份） | 随模板变更 |
| 业务逻辑 / 事件处理 / 状态 | Hermes 字节码 | 随脚本变更 |

分离的好处：**改样式改模板时不必重新编译业务逻辑**，反之亦然。增量更新更细。

### 6.3 序列化

- IR 三份产物：**FlatBuffers 或紧凑二进制**，禁止 JSON（避免运行时解析开销）
- 端上 IR 加载器直接 `mmap` 构造节点树，无解析步骤（与方案 §5.2 的 `tree_build` 一致）

### 6.4 manifest 必备字段

```ts
interface PlaygroundManifest {
  bundleId: string
  irVersion: string           // 语义化版本
  minShellVersion: string     // 端上校验依据
  profileVersion: string      // CSS Profile 版本
  entry: string
  requiredCapabilities: string[]   // 原生能力声明（§4.2）
  signature?: string          // 生产态签名（v2）
  createdAt: number
}
```

## 7. 云端编译流水线

### 7.1 复用既有能力

`proteus-cc-rust` 已是独立 cargo crate，可直接在云端编译服务中调用。**不需要新写编译器**，只需补打包与分发环节。

### 7.2 流水线步骤

```
1. 接收源码（git webhook / CLI 上传 / dev server 增量）
2. 依赖安装（需缓存，这是耗时大头）
3. 语义 IR 编译（Node 或 Rust 后端）
4. 三份 IR 产物序列化
5. 业务逻辑 bundling（Vite / esbuild）
6. hermesc 编译 → .hbc
7. 打包 + manifest 生成
8. 上传 CDN / 推送 dev server
9. 生成二维码（分发态）
```

### 7.3 关键工程约束

| 项 | 要求 |
|---|---|
| 编译耗时 | 目标 < 60s（含依赖安装）。超过则开发者不愿用 |
| 依赖缓存 | **必须做**，否则每次全量安装，耗时不可接受 |
| 编译产物可复现 | 同源码同配置 → 同产物（便于排查与缓存） |
| 失败反馈 | 编译错误必须回传到手机端可读展示，不能只在终端 |

## 8. 开发态：dev server 与热重载

### 8.1 协议设计

参照 Expo Go 的成熟模式：

```
1. proteus playground dev 启动本地服务
2. 终端打印二维码，内容为 proteus://<ip>:<port>?project=<id>
3. 手机扫码 → 壳连接 dev server
4. 下载产物 → 运行
5. 文件变更 → 增量重编译 → 推送 → 端上热重载
```

### 8.2 热重载分级（按代价从低到高）

| 类型 | 触发 | 端上动作 | 目标耗时 |
|---|---|---|---|
| **样式变更** | 仅样式改动 | 重发 `layout_template.bin`，重建节点树 | < 200ms |
| **模板变更** | 结构调整 | 重发三份 IR 产物 | < 500ms |
| **逻辑变更** | script 改动 | 重发 `.hbc`，重启 JS 上下文 | < 1s |
| **配置变更** | proteus.config.ts | 全量重载 | — |

**分级是核心价值**——样式改动不该重启整个 JS 上下文。

### 8.3 网络与隧道

手机需能访问开发机。局域网不通时（办公网 / 酒店网常见）需提供隧道模式：

```
proteus playground dev --tunnel
```

代价是首次加载变慢。**必须提供，否则大量用户卡在这一步。**

### 8.4 状态保持

热重载应尽量保持应用状态（滚动位置、表单输入、当前路由）。**样式/模板变更必须保持；逻辑变更可放弃。**

## 9. 分发态：扫码运行

### 9.1 二维码内容

```
proteus://playground?bundle=<bundleId>&v=<irVersion>
```

或降级为 HTTPS 短链（未安装壳时引导下载）。

### 9.2 端上加载流程

```
扫码 → 解析 URL → 校验壳版本（§4.4）
     → 查本地缓存（bundleId + 版本号命中则直接用）
     → 未命中则下载
     → 校验能力清单（§4.2）
     → 加载 .hbc 到 Hermes
     → mmap 三份 IR 产物 → 构造节点树
     → 渲染
```

### 9.3 缓存策略

- 按 `bundleId + 内容 hash` 缓存
- LRU 淘汰，上限可调
- **必须提供「清除缓存」入口**——缓存导致的问题最难排查

## 10. 安全边界

### 10.1 v1（开发调试态）

| 项 | 要求 |
|---|---|
| 传输 | HTTPS |
| dev server 绑定 | 默认仅局域网，隧道模式需显式开启 |
| 产物校验 | 内容 hash 校验 |

### 10.2 v2（生产 OTA，架构预留）

| 项 | 要求 |
|---|---|
| 产物签名 | 必须，端上验签后才加载 |
| 灰度 | 按设备 / 用户分组下发 |
| 回滚 | 一键回退到上一版本；端上保留上一个可用版本 |
| 降级 | 产物加载失败 → 回退到内置基线版本，**不得白屏** |
| 审计 | 下发记录可追溯 |

### 10.3 明确的边界

**OTA 不能新增原生能力。** 这是硬边界（与 EAS Update 一致），必须在文档和报错中讲清楚。

## 11. 与 Vapor IR 方案的关系

| Vapor IR 里程碑 | Playground 依赖 |
|---|---|
| V0 探针 | 无依赖，可并行 |
| V1 指令集 | 依赖 `OpCode` / `OpBuffer` 定义（产物序列化需要） |
| V2 编译期响应式 | 依赖 `UpdateProgram` 产物 |
| V3 App 端打通 | **Playground 的端上渲染依赖此项** |

**建议排期**：V1 完成后即可启动 Playground 的壳与流水线（用 VDOM 兜底路径先跑通）；V3 完成后切换为 IR 路径，性能从 70ms 档跳到 1ms 档。

**这个衔接点很关键**——Playground 是 Vapor IR 方案的**最佳验证场景**：真机、真实业务、可随时复现。

| 2 | **Hermes 的 Proxy 兼容性** | Vue 响应式重度依赖，必须最早验证 |
| 3 | **云端编译太慢** | 依赖缓存是关键；超过 2 分钟开发者就不会用 |
| 4 | **原生模块硬边界** | v1 就要做能力清单校验，不能事后补 |
| 5 | **版本不兼容静默崩溃** | 强制版本协商 + 明确提示 |
| 6 | **缓存导致的问题** | 必须提供清除入口，且默认行为要可预测 |
| 7 | **局域网不通** | 必须提供隧道模式 |
| 8 | **误以为能跑 Web 端 bundle** | 必须消费 IR 产物，否则拿不到 1ms 性能 |
| 9 | **以为 OTA 能加原生能力** | 硬边界，文档与报错都要讲清楚 |
| 10 | **产物加载失败白屏** | 内置基线版本 + 降级路径，非可选 |
| 11 | **热重载不分級** | 样式改动重启整个 JS 上下文，体验极差 |
| 12 | **编译错误只在终端可见** | 必须回传手机端，否则手机调试寸步难行 |

## 15. 给实现 LLM 的执行指令

1. **PG0 的 iOS 26 核实与 Hermes Proxy 兼容性验证必须先完成**，未通过不得开始 PG1。
2. **产物必须是 IR 产物**，不得直接下发 Web 端 VDOM bundle 充当 App 产物。
3. **版本协商与能力清单校验是 v1 必需项**，不是 v2 优化项。
4. **热重载必须分级**，禁止所有变更都重启 JS 上下文。
5. **产物加载失败必须有降级路径**，白屏视为未完成。
6. **扩展壳与公共壳共用同一套产物格式与加载器**，只有内置模块集不同。
7. **云端编译必须做依赖缓存**，否则不可用。
8. **不新增原生能力是 OTA 的硬边界**，任何"动态下发原生模块"的实现应被拒绝。
9. 复用 `proteus-cc-rust`，**不得新写编译器**。

## 附：关键事实依据

- iOS 上第三方 App 被禁止在运行时分配「可写可执行」内存页（W^X），**JSC 的 JIT 在 iOS 被禁用，只能解释执行**；RN 官方文档亦有相同表述
- Hermes 采用 AOT 预编译字节码（.hbc），不依赖 JIT，故不受 iOS 该限制影响
- Hermes 实测量级：TTI 4.3s→2.01s；APK 41MB→22MB；内存 185MB→136MB；运行时二进制 <2MB（JSC 8MB+）；字节码比 minified JS 小 30–40%
- Hermes 无 JIT，长任务计算弱于 V8/JSC 的 JIT 版本；部分 ES 特性（Intl、复杂正则、Proxy/WeakRef 高级用法）需验证
- 有资料称 iOS 26 移除 legacy JIT runtime 支持并阻止非官方 JSC 集成——**来源权威性较低，须自行核实**
- Expo Go 模式：预装 RN 运行时 + 固定 Expo SDK 模块的空壳 App，扫码后从 Metro 下载 JS bundle 运行；无法加载壳未预置的任意原生代码
- Expo Development Build：通过 expo-dev-client 构建自己的壳，可含任意原生模块；一次性构建成本（分钟级）；原生依赖变更时需重建；日常 JS 改动无需重建
- 生产态 JS bundle 打包进 App 二进制；OTA（如 EAS Update）**不能新增原生能力**
- 局域网不通时需隧道模式（如 `--tunnel`），代价是首次加载变慢
