# 参与 Proteus 框架共建（外部项目接入协议）

> **你是谁**：在**使用 Proteus 框架**的项目里工作的 AI（或人）。
> **这份文档解决什么**：你撞到框架问题时，知道**该不该报、报到哪、怎么写、什么时候算修好**。
> **一句话**：撞到框架缺陷 → 写报告一节 + 台账一条 → 同步到框架仓库 → 等修复发布 → 复测回写。
>
> 框架侧的同名规范：`docs/ai-cobuild-spec.md`（你不需要读它，本文件是给你的完整版）。

---

## 0. 三件事，先记住

| 问题 | 答案 |
|---|---|
| **什么时候该报** | 框架**该做到却没做到**、或**静默失败**（不报错但行为错）时——判据见 §2 |
| **报到哪** | 你项目内的 `实战报告_proteus接入.md`（追加一节）+ `框架问题台账.json`（加一条）→ 再同步到框架仓库 |
| **什么格式** | §3 的两个模板，**照着填**；带**最小复现**是硬要求 |

---

## 1. 你在共建里的角色（谁负责什么）

**这是避免"两边都在改同一份东西"的关键划分**——按字段分，不按文件分：

| 字段 | 谁维护 | 说明 |
|---|---|---|
| `id` / `title` / `evidence` / `repro` / `round` / `reported_in` | **你（外部）** | **问题的定义**——你看见了什么、怎么复现 |
| `status` / `fix_state` / `fixed_in` | 框架方 | **修复的状态**——改没改、发没发 |
| `verification` / `verified_by` / `verification_note` | **你（外部）** 优先 | **验证结论**——只有你能给出「在我项目里确实好了」这个证据 |
| `related` | 双方 | 残留问题指向原条目 |

> ★**框架方的自测不算独立验证**：他们装 registry 包自测只能标 `verified_by=framework`；
> 只有你在自己项目里用报告里的最小复现跑通，才能标 `external`。**你的复测是最强证据**——这是你的核心价值。

---

## 2. 什么时候该报（触发判据）

### ✅ 该报

| 情形 | 例子（真实发生过的） |
|---|---|
| 框架承诺的能力没做到 | `onMounted(async () => {…})` 编译后丢 `async` 标记 → 产物语法错 |
| **静默失败**：不报错但行为错 | `/\s/g` 被改成 `/\this.s/g`（字数统计失准，构建却通过） |
| 报错**指向无关模块** | 只是 import 一个抽屉，报错却说 `fluid` 缺导出 |
| 发布物缺件（装了包用不了） | `components` 包丢了全部 74 个组件 |
| 文档/数字与实际不符 | 官网说 40 个包，实际 41 |

### ❌ 不该报（先自查再决定）

| 情形 | 处置 |
|---|---|
| **平台限制**（WXML 不支持 `?.`、不支持模板函数调用） | 框架报错正确 → 这是**你的适配**，记进 `consumer_notes`，不算框架缺陷 |
| 你自己的业务逻辑行为 | 不是缺陷；但若**报错信息让你误判**，那部分算框架问题 |
| **探针本身不可靠**导致的误报 | 先验证探针（真实案例：`__vueParentComponent.ctx` 只暴露模板绑定，不是模块作用域） |
| 已知问题（台账里已有同 id） | 别新开一条，补 evidence 或标 `related` |

**判据表（框架缺陷 vs 你的适配）**：

| 情形 | 归属 |
|---|---|
| 框架标 `aligned` 但没对齐（**有对照实验证明本可做到**） | **框架缺陷** |
| 平台本身不支持 | 平台限制 → 你适配 |
| **静默失败**（不报错但错 / 报错指错方向） | **一律归框架**（让使用者无从排查是框架的责任） |
| 产出**语法合法但语义错**的产物 | **框架缺陷（最危险）** |

## 3. 格式（照着填）

### ① 报告：追加一节

文件名：`实战报告_proteus接入.md`（你项目内），**标题格式是机器对齐用的锚点，必须照写**：

```markdown
## 第N轮复测：`<被复测的版本号>`（YYYY-MM-DD）—— 一句话结论

> 背景：本轮针对 <上一轮修复的版本> 逐项复测。<结论：修好了什么 / 新发现什么>

### 一、结论速览

| 项 | 结果 | 证据 |
|---|---|---|
| <问题> | ✅ 已修 / ❌ 未修 / ⚠️ 部分 | <怎么验的> |

### 二、已验证修复（逐项实测，非源码推断）
<!-- 每条给：验证方式 + 实测结果。你自己的实测，不是读框架源码得出的推断 -->

### 三、新发现的问题（每条一节）
<!-- 每条必须包含：现象 / 最小复现 / 影响面 / 根因（能定位就写）/ 修复建议 -->

**最小复现**（可直接给框架做回归用例）：
\`\`\`bash
<复制就能跑的命令或代码>
\`\`\`

### 四、我方适配（平台限制，非框架缺陷）
<!-- 你为了跨端做的事，明确标注"非框架缺陷" -->

### 五、诚实澄清（可选）
<!-- 你测试脚本的误报、可疑但未证实的猜测，单列说明 -->
```

**硬要求**（缺了框架方无法复核）：
1. **版本号**（标题里，机器靠它对齐轮次）；
2. **每条问题带最小复现**；
3. **区分「框架缺陷」与「我方适配」**。

### ② 台账：加一条

文件：`框架问题台账.json`，往 `entries` 数组追加：

```json
{
  "id": "F-27",
  "title": "一句话说清问题（做到能当 issue 标题）",
  "kind": "compiler",
  "severity": "blocker",
  "round": 7,
  "reported_in": "0.3.0-beta.10",
  "found_by": "external",
  "status": "open",
  "verification": "unverified",
  "evidence": "可复制的报错/现象关键片段",
  "repro": "最小复现（命令或代码）"
}
```

| 字段 | 填法 |
|---|---|
| `id` | **延续编号**（F-01… 往后排；**分配后永不变更**——它是跨仓库对账的锚点） |
| `kind` | `packaging` / `cli` / `compiler` / `runtime` / `router` / `release` / `process` / `docs` |
| `severity` | `blocker`（阻断使用/构建）/ `major`（功能受损或静默错）/ `minor`（体验/文档） |
| `round` | 你这轮是第几轮（对应报告节号） |
| `reported_in` | 你测的**框架版本号**（多版本时代记相关包的版本，并在报告里说明） |
| `status` | 新报的填 `open`；修复状态由框架方更新 |
| `fix_state` | 新报的**不填**（框架方发布后填 `published` + `fixed_in`） |
| `verification` | 新报的填 `unverified`；你复测通过后填 `passed` + `verified_by: "external"` + `verification_note` |

> `severity=blocker` **必须带 `repro`**（校验器会拦）。`status=partial` 必须带 `related` 指向跟踪条目。

## 3.5 ★ 怎么把这个机制装进你的工程（一条命令）

工具包**随 `@proteus-vue/cli` 分发**——不需要从框架仓库复制、不需要联网取模板：

```bash
npx proteus cobuild init     # 安装共建工具包（幂等，可重复跑；--force 才覆盖）
npx proteus cobuild check    # 自检：5 件是否齐备（可挂 CI）
```

装完你会得到：

| 文件 | 作用 |
|---|---|
| `.agents/skills/proteus-cobuild/SKILL.md` | **AI 入口文档**（就是本文件的等价物）——你那边的 AI 会话靠它知道该报什么、怎么报 |
| `docs/框架问题台账.json` | 对账台账（已带 schema 与对账规则） |
| `docs/实战报告_proteus接入.md` | 报告模板（标题格式已写好） |
| `scripts/ledger_check.mjs` | 台账校验器（`node scripts/ledger_check.mjs --check`） |
| `AGENTS.md` 中的指针段落 | 让**你的 AI 新会话**能找到上面这些（marker 包裹，可重复更新） |

> **新工程无需手动装**：用 `create-proteus` 脚手架建的项目**开箱自带**这 5 件。
> `init` 是幂等的——**已存在的文件不会覆盖**，你写的报告与台账内容安全。

## 4. 提交到哪里（同步机制）

```
你的项目（OPERATOR/web）                    框架仓库（proteus）
├── 实战报告_proteus接入.md  ──── 镜像 ────► docs/实战报告_proteus接入.md
└── 框架问题台账.json        ──── 合并 ────► docs/外部报告台账.json
```

**两个文件你维护（你是问题的定义方）；框架仓库侧是合并视图**（含框架自查发现的条目）。

### 怎么同步

```bash
# 框架方在你的机器上跑（或你跑——同机可直接访问两个仓库）：
node /path/to/proteus/scripts/sync-cobuild.mjs --from /path/to/OPERATOR/web

# 只检查差异、不写入：
node /path/to/proteus/scripts/sync-cobuild.mjs --from <外部项目路径> --check
```

同步做三件事：
1. **报告**：把外部报告的最新内容镜像到框架仓库（保留两边的追加历史）；
2. **台账**：按 `id` 合并——外部主导的字段以外部为准，框架主导的字段（`status`/`fix_state`/`fixed_in`）以框架为准；
3. **报出冲突**：同 id 但两边对同一字段给了不同值 → 列出让你/框架方裁决（不静默覆盖）。

> **没有这个文件时怎么同步**：人工复制粘贴。这也是为什么会有「两边台账漂移」——
> 实测发现外部的 18 条 vs 框架的 26 条、`last_verified_published` 差一个版本。
> 所以同步要**机器做**，不要靠记忆。

## 5. 闭环：报完之后发生什么

```
你：报问题（报告一节 + 台账一条）
 │
框架：① 用你的最小复现当场复现
    ② 修 + 加回归锁（破坏性验证：回退修法必须红）
    ③ 发布（换版本号，npm 不可变）
    ④ 写回执（改了什么 / 怎么验的 / 哪个版本发的）
    ⑤ 更新台账 status/fix_state/fixed_in
 │
 └─► 你收到「新版 + 回执」
      ⑥ 升级 + 用你的最小复现复测
      ⑦ 台账回写 verification=passed + verified_by=external
      ⑧ 结论进下一轮报告（✅ 已修 / ❌ 仍未修 / ⚠️ 修了一半）
```

**你怎么知道修好了**：看框架仓库的
- `docs/外部报告台账.json` → 你的 id 的 `fix_state=published` + `fixed_in`；（`git pull` 即得）
- 报告里的「处理回执」节 → 逐条说明改了什么、哪个版本发的。

**你要做的最后一步**：复测后把 `verification` 从 `unverified` 改成 `passed`（或 `failed` 并说明），
这就是「真实收口率」的分母——**你的复测是唯一能把 `framework` 档升级为 `external` 的证据**。

## 6. 自查：你的提交合格吗

```bash
# 校验台账 schema（必填字段 / blocker 必带 repro / partial 必带 related / fixed_in 不自相矛盾）
python3 web/ledger_check.py          # 报告模式
```

**提交前自检清单**：

- [ ] 报告一节标题含 `第N轮复测` + **版本号** + 日期；
- [ ] 每条新问题都有**最小复现**（复制粘贴就能跑）；
- [ ] 台账加了对应条目，`id` 延续编号，`severity`/`kind` 取值合法；
- [ ] **区分了**「框架缺陷」与「我方适配」；
- [ ] 自己的误报/不确定的地方单列澄清（**诚实比数量值钱**）；
- [ ] `ledger_check.py` 跑过。

## 7. 反模式（这些我们真实踩过）

| 反模式 | 教训 |
|---|---|
| **只报现象不给复现** | 框架方无法复核 → 只能猜；带复现的报告通常一轮就修好 |
| **把平台限制当框架缺陷** | 会浪费双方时间；用 §2 的判据表先分类 |
| **修一半当修完**（对方视角） | 复测时**明确区分**「全修了」与「只修了一条路径」——第五/六轮就是这个价值 |
| **自己误报不澄清** | 会让框架方基于错误信息改代码；澄清比隐瞒专业 |
| **台账不更新** | 收口率失真；`fix_state=worktree` 的条目对 npm 用户等于没修 |

---

## 8. 一句话总结

**你负责"问题是真的"（带复现），框架负责"改动是真的"（带发布），
你的复测决定"修复是真的"——三者缺一，共建就是空的。**
