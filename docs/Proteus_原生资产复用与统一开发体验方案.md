# Proteus 原生资产复用与统一开发体验方案

> 目标：消灭「写原生插件要切 IDE、切语言、切调试链路」的开发体验分裂，让**已有原生资产（SDK / 组件 / 页面）零改写接入**，并把「改原生就必须整包发版」从**每次发生**压缩为**只发生一次**。
> 关联：《原生能力接入方案》（目标与原则层）《Host ABI》《Morpheus》《架构收敛模型说明》《多端一致性标准方案》

**① 术语校准：「不自绘」需按本仓权威定义表述（§3.2 已引，此处点名出处）**
本仓《多端一致性标准方案》§1.1 对"自绘"有**权威定义**（该文档开篇即为此澄清而设）：
> **自绘 = 是否使用原生渲染管线**（不是"是否自己实现 UI 框架"），且必须**三层分开表述**：
> L-A 控件树层（谁做控件）· L-B **布局计算层**（谁算几何）· L-C **光栅化层**（谁把指令变像素）。

按此定义，§3.2 的论断**成立但依据要说准**：
- Proteus 在 **L-B 层是自己算几何**（Rust 内核）——**不是**"用系统布局"，别与 L-A 混淆；
- "原生组件与 Proteus 内容天然同层"的准确依据是 **L-C 层共用系统光栅化/合成管线**
  （系统合成器统一处理），因此**不存在 Flutter 式"两套渲染体系要合并"**。
⇒ 对外表述须落到 L-C（"共用系统合成管线"），**不要**笼统说"我们不画所以天然同层"
（会被误读为 L-A/L-B 也交出去了——而 L-B 恰是我们自研内核的价值所在）。

**② ★证据升级：核心论断（§3.2 / NA0 问题 1）**已有实现级证据**，不是"待从零验证"**

## 0 结论摘要

| 问题 | 结论 |
|---|---|
| 「复用原生很费劲」是否真实 | ✅ 真实，且**三重代价**，见 §1 |
| 最痛的是哪一条 | 🔴 **不是写代码，是动态化断裂**——每写一行原生，这部分需求就从"小时级"降级为"周级" |
| 现有框架有没有解法 | 🟡 有，但**只解决了一半**：RN Codegen 解决类型安全、uni-app UTS 解决 IDE 切换，**都没解决动态化断裂** |
| 我们能做到什么 | **L0 零代码 + L1 资产直连 + L2 契约 codegen + L3 显式逃生口** |
| ★ 真正抄不走的是什么 | **不自绘 → 原生组件嵌入天然同层，无 Flutter 式"渲染税"**（架构性的，Flutter 改不了） |
| 什么抄得走、必须承认 | 「契约 + codegen」RN 已有；「类 TS 写原生」uni-app UTS 已有。**不能说我们发明了这两件事** |
| 归属 | 独立能力层，命名建议 **Janus**（双向门神），备选 Nexus |

**一句话**：我们不是让开发者"更舒服地写原生"，而是**让"需要写原生"这件事本身变得稀少，且只发生一次**。

## 1 问题诊断：痛点到底痛在哪

### 1.1 三重代价，第二重才是致命的

| # | 代价 | 表现 |
|---|---|---|
| 1 | **上下文切换** | 另一个 IDE、另一门语言、另一套调试链路 |
| 2 | 🔴 **动态化断裂** | 改原生 → 必须整包 → 应用商店审核 → 天级/周级 |
| 3 | **知识断层** | 业务开发者做不了，必须原生同学排期 |

第 1 条最直观，但**第 2 条才是真正的成本**：

> 你原来 2 小时能上线的需求，只要碰了原生，就变成 1–7 天。
> **写原生代码的代价不是写代码的时间，是它把迭代闭环整个撕碎了。**

### 1.2 🔴 动态化断裂是行业共识，且有硬约束

**uni-app wgt 热更新的官方边界**（权威性中等，多处一致）：

> 能更新：JS / Vue 页面 / 静态资源
> 不能更新：**新增原生插件、修改 manifest.json 权限与配置、更换第三方 SDK、跨大版本升级**

**React Native（CodePush / EAS Update）**（权威性中等）：

> 可更新：JS 代码、图片资源、样式布局、业务逻辑
> 不可更新：**原生模块代码、第三方 SDK 集成、应用权限配置、新增 Native Module**

**行业通用判定准则**（跨框架一致）：

> 本次改动是否触及原生层（新增/升级原生插件、模块、权限、SDK、manifest 原生配置）？
> **是 → 必须整包；否 → 可热更新。**

**所以这不是某个框架的缺陷，是结构性事实**：只要碰原生，迭代速度就掉一个数量级。

### 1.3 上下文切换也是被官方承认的痛点

uni-app 官方文档在《为什么要把原生插件迁移为 UTS 插件》中列出的优势（权威性极高）：

> "插件开发和业务代码可以通过 HBuilder X 一站式完成，**调试插件再也不需要切换 IDE**"

并且官方已**停止维护**老的原生语言插件：

> "**App 原生语言插件已停止维护**，插件市场不再受理新增 App 原生插件，请开发者使用 uts 插件"

**厂商主动淘汰旧机制、迁移到新机制，是最强的痛点背书。**（与 `@uni-ku/root` 之于全局挂载点同一性质）

## 2 现有方案：解法与局限

### 2.1 React Native：Codegen 解决了类型安全，没解决体验分裂

TurboModules / Fabric Native Components 的流程（RN 官方文档，权威性极高）：

```
1. 用 TypeScript / Flow 定义 spec
2. Codegen 生成 C++ / Obj-C++ / Java 接口
3. ★ 开发者写原生平台代码实现这些接口
```

**第 3 步是关键——RN 的 codegen 只消灭了"手写胶水代码"，原生实现仍然要人写。**

所以你还是要开 Xcode 写 `.mm`、开 Android Studio 写 `.kt`。

### 2.2 uni-app UTS：解决了 IDE 切换，但有新代价

UTS 编译目标（官方文档，权威性极高）：

| 平台 | 编译产物 |
|---|---|
| Web / 小程序 | JavaScript |
| Android | Kotlin |
| iOS | Swift |
| 鸿蒙 | ArkTS |

**UTS 原生混编**（官方，权威性极高）更进一步：可把 Kotlin / Swift / Java / ArkTS 源码**直接放进插件目录调用**，无需封装 aar/framework、无需打自定义基座。

官方列出的痛点正是：
> "如原生代码数量较多，则翻译比较吃力；如封装成 aar 等库，**每次改动都需要打自定义基座，也很麻烦**"

**代价**（社区实测，权威性中等）：
> "对纯 Vue 开发者可能不太友好：必须习惯类型声明、理解异步必须用 Promise、**得直面三端差异（Android 像素单位是 dp，iOS 是 point）**"

还有语法约束：对象字面量禁止携带方法、条件必须是布尔值、函数类型参数禁止 vararg……

**结论**：UTS 是"让前端能写原生"，但仍要求开发者**懂三端差异**——认知负担没有消失，只是转移了。

### 2.3 🔴 Flutter：PlatformView 的"渲染税"是架构性的

Flutter 官方文档原话（**权威性极高**，flutter.cn 与 Flutter SDK 文档一致）：

> "in a typical Flutter app, the Flutter UI is composed on a **dedicated raster thread**. This allows Flutter apps to be fast, as the **main platform thread is rarely blocked**.
> While a platform view is rendered with **Hybrid Composition**, the Flutter UI is composed **from the platform thread**, which competes with other tasks like handling OS or plugin messages, etc."

并且：

> "**Prior to Android 10**, Hybrid Composition **copies each Flutter frame out of the graphic memory into main memory and then copied back to a GPU texture**. As this copy happens per frame, the performance of the entire Flutter UI may be impacted."

**翻译**：Flutter 之所以快，靠的是 raster 线程独立于平台线程。**一旦嵌入原生视图，这个优势就没了**——合成被拉回平台线程，还要与 OS 消息、插件消息抢 CPU。

演进史也能说明问题：

| 模式 | 代价 |
|---|---|
| Virtual Display | 性能高，但键盘/无障碍全废 |
| Hybrid Composition | 交互完美，但**合成税极高**，帧率可跌至 30fps 以下 |
| TLHC | 折中，高速滚动仍有微卡顿与裁剪伪影 |
| **HCPP**（3.44 新增） | 让 SurfaceFlinger 直接合成，但**需 Android 14 + Vulkan + Impeller**，否则自动回退 TLHC |

**Flutter 折腾了四个版本仍在解决这个"渲染税"——因为它源于"自绘"这个根本选择。**

## 3 ★ 我们真正的差异化：什么抄得走，什么抄不走

### 3.1 必须先承认：这两件事别人已经做了

| 能力 | 已有实现 | 我们不能宣称 |
|---|---|---|
| 声明契约 → codegen 生成桥接 | **RN TurboModules / Fabric Codegen** | ❌ 不能说"我们发明了契约+codegen" |
| 用类 TS 语言写原生插件、不切 IDE | **uni-app UTS + 原生混编** | ❌ 不能说"我们首创了统一语言" |

**诚实承认这两点，剩下的优势才有人信。**（与《多端一致性标准方案》主动承认"文本度量不如 Flutter"同一策略）

### 3.2 🏆 抄不走的：不自绘 → 原生嵌入天然同层

这是本方案唯一**架构级**的差异：

| | Flutter | Proteus |
|---|---|---|
| 自己的 UI 渲染 | 自绘（Skia/Impeller，raster 线程） | **系统渲染管线** |
| 原生组件渲染 | 系统管线 | 系统管线 |
| 两者如何共存 | 🔴 **不同层，必须合成**（渲染税） | ✅ **同层，系统合成器统一处理** |

**Flutter 改不掉这个——除非放弃自绘。** 而这正是我们《多端一致性标准方案》CS0 术语定义里"不自绘"原则的又一次兑现。

**这条与 Morpheus 转场的 RenderThread 红利是同源的**：复用系统管线，就不存在"两套渲染体系要合并"的问题。

### 3.3 🏆 收敛模型：契约本身进封闭集

| | RN spec | Proteus 契约 |
|---|---|---|
| 表达能力 | **任意 TypeScript 接口**（可定义任意方法） | **封闭集**，编译期校验 |
| conformance | 无 | ✅ 有 |
| AI 可写可校验 | 弱（任意接口无法判对错） | ✅ 强 |
| 跨端降级 | 手写条件编译 | **编译期判定 + 显式降级** |

### 3.4 🏆 指令流平台无关

别人为每个端单写后端（RN 的鸿蒙分支、Flutter 的鸿蒙化适配），我们**同一份指令流换宿主**。

### 3.5 差异化的核心表述

> ❌ "我们让写原生更舒服"
> ✅ **"我们让『需要写原生』这件事变稀少，且只发生一次"**

## 4 分层设计

```
L0  内置能力       零原生代码        ← 99% 目标（《原生能力接入方案》）
L1  资产直连       已有原生资产零改写接入
L2  契约 + codegen 新能力：写一份契约，只填实现体
L3  逃生通道       显式登记，不静默
─────────────────────────────────────
R   反向复用       原生宿主嵌入 Proteus 页面（渐进式迁移）
```

**关键：L0 是主战场。** L1/L2 是"L0 覆盖不到时的兜底"，不是主力路径。

### 4.1 L0 内置能力（主战场）

已由《原生能力接入方案》定义（99% 覆盖率、Capability Hook、编译期 codegen 静态绑定）。

**本方案对它的补充只有一条**：Capability Hook 的**新增频率**应作为 L0 的健康度指标——频率持续不为零说明原语集未稳定。

### 4.2 L1 资产直连（零改写）

针对**已有**的原生资产：

| 资产类型 | 接入方式 |
|---|---|
| 原生 SDK（支付/地图/推送/统计） | 声明式契约 + 薄适配，不改 SDK 一行代码 |
| 原生 UI 组件（自研地图控件、播放器） | 宿主组件契约，挂进指令流（天然同层，见 §3.2） |
| 原生页面（Activity / ViewController / Ability） | 容器契约，路由层托管 |
| 原生资源（字体/图集/主题） | 资源清单声明 |

**要求**：接入过程**不得修改原资产源码**。若必须改，说明契约设计有问题。

### 4.3 L2 契约 + codegen

新能力接入流程：

```
① 写一份平台中立契约（Janus IDL，见 §5）
② codegen 生成各端桥接骨架
③ 各端只填"实现体"（调用 SDK 的那几行）
④ 编译期校验 + conformance 覆盖
```

**与 RN codegen 的区别不在流程，在约束**：
- 契约是**封闭集**（不是任意 TS 接口）
- 实现体**禁止包含业务逻辑**（否则动态化断裂复发）
- 契约**必须声明各端降级行为**（不支持时怎么办）

### 4.4 🔴 实现体禁止业务逻辑——这条是本方案的生命线

**为什么**：如果实现体里写了业务逻辑，那么每次业务变化都要改原生 → 动态化断裂**每次都发生**，本方案就退化成 RN/uni-app。

**设计目标**：

```
契约（稳定，只写一次）  →  原生侧
业务（频繁变化）        →  JS 侧，可热更新
```

**硬约束（J1）**：实现体只允许做三件事——
1. 参数转换（JS 类型 ↔ 原生类型）
2. 调用 SDK
3. 结果回传

**任何条件分支、状态判断、业务规则 → 编译期警告，需显式标注豁免理由。**

### 4.5 L3 逃生通道

必须存在（总有覆盖不到的），但必须**显式登记 + 埋点统计**。

**禁止静默**：与 TSX、运行时全局挂载是同一条原则——开放了却收不到信号，就是灾难。

### 4.6 R 反向复用（渐进式迁移）

已有原生 App 想渐进迁移：**Proteus 页面作为一个"原生页面"嵌进原生导航栈**。

这与 L1 的"原生组件嵌入"是**镜像关系**，共用同一套容器契约。

## 5 契约设计（Janus IDL）

### 5.1 为什么不用 TypeScript 接口

RN 用 TS/Flow 是因为它本来就在 TS 生态。**但 TS 接口能表达任意方法**——这与收敛模型冲突。

Janus IDL 是**受限 DSL**：

| 约束 | 理由 |
|---|---|
| 方法签名必须来自**声明的封闭类型集** | 可编译期校验 |
| 禁止 `any` / 任意对象 | 否则无法校验、无法生成可靠绑定 |
| 事件必须声明，不能任意回调 | 与批处理红线相关 |
| **必须声明各端支持情况** | 不支持的端编译期报错，不静默 |

### 5.2 形态示意

```ts
// 伪码，最终语法以 NA2 产出为准
declare capability Payment {
  // 方法签名
  method pay(order: OrderId, amount: Money): Promise<PayResult>

  // 事件（必须声明）
  event onPayStateChange(state: PayState)

  // ★ 各端支持度（必填）
  @support(ios: native, android: native, harmony: native,
           web: degraded, mp-weixin: plugin)

  // ★ 不支持时的行为（必填）
  @fallback(web: redirect_h5, mp-weixin: require_plugin)
}
```

**两个必填是关键**：`@support` 与 `@fallback`。缺任一 → 编译期报错。

这与《页面层级规范》里"目标端无引擎 → 编译期报错，禁止静默空白"是同一设计。

### 5.3 codegen 产出

必须产出**静态绑定**，不是运行时查表（沿用《原生能力接入方案》结论）：

```
Janus IDL
  ├→ Rust 侧绑定（指令流可直达）
  ├→ iOS 侧绑定
  ├→ Android 侧绑定
  ├→ 鸿蒙侧绑定
  ├→ Web 侧绑定
  └→ 小程序侧绑定（或降级声明）
```

**静态绑定才能保住 conformance 与 AI 可校验**——运行时查表会把这两样一起丢掉。

## 6 各端映射与已知坑

| 端 | 能力接入机制 | 已知坑 |
|---|---|---|
| **iOS** | 静态绑定 + 原生组件同层 | 系统 SDK 版本差异；**iOS 26 需回归** |
| **Android** | 静态绑定 + 原生组件同层 | ROM 定制可能改变行为（历史教训） |
| **鸿蒙** | NAPI / C-API | **C-API 是 ArkTS 子集**，部分高级组件不可用；`moduleType` 必须 commonjs |
| **Web** | 直接调用 | 🔴 **无原生能力**，只能降级（H5 替代 / 不可用） |
| **小程序** | 🔴 **不能写原生代码** | 只能用平台原生组件（camera/map/video）或官方原生插件（需审核） |

### 6.1 🔴 小程序端是最受限的，必须显式处理

小程序端**根本不存在"写原生"这回事**——这是平台硬约束，不是我们的问题。

所以契约的 `@support` 里小程序端通常只有三档：
- `native`：平台已有原生组件（camera / map / video / canvas）
- `plugin`：需要官方原生插件（需审核，有上架周期）
- `unsupported`：编译期报错

**禁止静默**：不支持就报错，不许运行时变空白。

### 6.2 鸿蒙端：C-API 是子集

华为官方明确：Native 侧是 ArkTS 的**子集**，无声明式语法、无自定义 struct、部分高级组件不可用。

187 原语需逐条核对，不可用且无兜底的，**编译期标记降级**。

（这条边界其实与我们同向——C-API 天然限制了可表达范围，正好贴合封闭集。）

### 6.3 四个通用坑

| # | 坑 | 处置 |
|---|---|---|
| 1 | **原生 SDK 回调在非主线程** | 契约必须声明线程归属，框架负责切回 |
| 2 | **原生组件生命周期 ≠ Proteus 页面生命周期** | 容器契约必须显式定义 onCreate/onShow/onHide/onDestroy 映射 |
| 3 | **原生资产内存不受 JS GC 管** | 必须有显式释放契约，禁止依赖 GC |
| 4 | **原生组件与动画的层级关系** | 与《页面层级规范》交叉：原生组件是否参与 z-order 需声明 |

## 7 与既有方案的边界

| 方案 | 边界 |
|---|---|
| 《原生能力接入方案》 | 那份定义**目标与原则**（99% 覆盖率、不开放任意原生调用）；本方案是它的**工程落地层** |
| 《Host ABI》 | 批处理红线同样适用：**原生回调禁止每帧跨边界** |
| 《Morpheus》 | 原生组件参与动画时，走《页面层级规范》的层内语义 |
| 《页面层级规范》 | 原生组件的 z-order 归属需在本方案声明 |
| 《多端一致性标准方案》 | 契约的 `@support` 矩阵是 VC1 支持度矩阵的输入之一 |
| 《单位系统与舍入规范》 | 原生资产传入的几何值必须换算为**物理像素整数** |

## 9 对外表述与禁语

### 9.1 推荐表述

> ✅ "我们用**同一份编译期收敛的指令流**驱动五端，原生组件与 Proteus 渲染层**由系统合成器统一处理**，不存在 Flutter 式的合成开销。"

> ✅ "传统方案里，每碰一次原生就要整包发版一次。我们把原生适配压成**一次性的稳定契约**，业务变化始终留在可热更新的一侧。"

### 9.2 🔴 禁语

| ❌ 禁止 | 原因 |
|---|---|
| "我们发明了契约 + codegen" | **RN TurboModules 已有** |
| "我们首创了用类 TS 写原生插件" | **uni-app UTS 已有** |
| "我们彻底消灭了原生开发" | 不可能，商业 SDK 闭源，B 档永远不为零 |
| "超越 Flutter / RN 的原生能力" | 无对照数据，且这两家生态成熟度远高于我们 |
| "改原生也能热更新" | 🔴 **违反平台规则**，见 §9.3 |

### 9.3 合规提醒（必须写进对外材料）

Apple 审核指南对动态代码下发有明确限制（Guideline 2.5.2 相关实践）：热更新不得改变应用核心目的与行为；**原生代码动态替换被明令禁止**。

**所以本方案的价值主张只能是**：
> "让**业务**始终留在可热更新的一侧，从而**减少**需要整包发版的次数。"

**不能是**："让原生代码也能热更新。" —— 这句话既做不到，也会引来合规风险。
