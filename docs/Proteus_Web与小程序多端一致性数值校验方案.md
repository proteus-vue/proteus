# Proteus Web 与小程序多端一致性数值校验方案

> 目标：把「Web / 小程序（Skyline + WebView）」多端一致性验证，从**像素级视觉回归**转换为**确定性数值比对**
> 原则：**可机器验证的，一律不靠人眼；不可机器验证的，才走像素兜底**
> 状态：v1 · 待评审
> 关联：CSS Profile 规格、架构收敛模型说明、UC0 兼容度扫描工具规格、Benchmark 案例规格
> **标准层指针**：《Proteus_多端一致性标准方案.md》（指标 M1–M4 / 允许差异清单 / 变异测试）——**本文件是实现层**（L1–L4 分层、探针、容差、VC 系列任务卡）。

## 0. 结论摘要（先读这里）

| 判断 | 结论 |
|---|---|
| 思路成立吗 | ✅ **成立，且比 App 端更该做** |
| 能完全取代视觉验证吗 | ❌ **不能**，L4 像素层必须保留，但样本量会下降一个数量级 |

| 建议起点 | **L1 编译期静态**（成本最低、复用已有 Profile 设施） |

## 1. 为什么传统视觉验证必然失败

### 1.1 死法固定：误报疲劳

业界公开的失败路径高度一致：

```
CI 因一个像素偏移频繁挂掉
  → 工程师人工分辨「噪声 vs 真问题」
  → 审查成本不比人工回归低
  → 几周后静音告警 / 禁用检查点
  → 彻底放弃视觉回归
```

**这不是工具选型问题，是方法问题。**

### 1.2 三条根因：渲染的非确定性

| 根因 | 机制 |
|---|---|
| **字体抗锯齿** | 同一字体的边缘像素分布随 OS / GPU / 渲染库版本变化；即便固定字体文件，hinting 与光栅化策略不同结果也不同 |
| **亚像素吸附（snapping）** | 元素落在分数位置时，像素网格对齐**这次落 A、下次落相邻像素**，无任何代码改动却产生 1px 位移；对重复元素会放大成数百个 flagged 像素 |
| **时序竞态** | 截图早 50ms → WebFont 未换完 / 图片未解码 / 布局未稳定 → 整屏标记为回归 |

### 1.3 现有缓解手段，全部是妥协

| 手段 | 问题 |
|---|---|
| 容错阈值 | **阈值太高漏真 bug，太低放噪声，且"正确阈值"不存在**（一个 50×20 按钮变色只占 0.001%，在 0.01% 阈值下必然漏） |
| 排除区（masking） | 需持续维护；组件一移动就同时产生旧位置误报 + 新位置漏报 |
| AI 判定差异 | **用非确定性系统验证必须确定的系统**；它不解释原因，无法纠正 |
| 环境稳定化 | 只缩小噪声，不能消除——**浏览器从未承诺像素级确定性** |
| 感知算法（SSIM / pHash） | 更宽容，但反向风险：容忍"小差异"会漏掉"轻微但真实"的回归 |

> **核心矛盾**：像素比对关注「数据一致性」，UI 一致性需要的是「视觉一致性」，两者本质不同。

## 2. 我们的转换：从"查视觉"到"比数值"

### 2.1 转换的本质

| | 传统视觉回归 | 本方案 |
|---|---|---|
| 比对对象 | 位图 | **数值流**（几何快照 / 计算样式 / 指令流） |
| 确定性 | ❌ 非确定（抗锯齿 / snapping / 竞态） | ✅ **确定** |
| 失败解释 | "这两张图不一样" | **"第 N 个节点 left 偏差 3.5px"** |
| 误报率 | 高 → 疲劳 → 放弃 | **近零** |
| 可自动化程度 | 需人工复核 | **可全自动判定** |

**0.375dp 就是 0.375dp，不存在"抗锯齿噪声"。**

### 2.2 🔴 关键发现：Skyline 的几何查询 API 可能不可用

微信开放社区有反馈（权威性较高，但**须实测确认**）：

> Skyline 下 `createSelectorQuery().select('#x').boundingClientRect()` 返回的
> `left / top / right / bottom / width / height` **全为 0**，
> 开发者工具与真机均复现。

相关事实：
- `wx.createSelectorQuery()` 官方支持，**鸿蒙 OS 版也支持**，基础库 1.4.0+
- 社区其他用法显示 Skyline 下 `boundingClientRect()` 在 `ready` 生命周期可取到值（如 `res[0].height`）
- 官方建议 Skyline 下"更推荐使用 `scroll-top`/`scroll-left` 这类基于像素的精确控制，**或使用 `createSelectorQuery` 获取元素位置后计算**"

**判定：结论冲突，必须实测。** 可能为特定基础库版本的 bug，也可能仅影响 `text` 组件。

### 2.3 ★ 因此架构必须改为「产出式」而非「查询式」

| | 查询式（不采纳） | **产出式（采纳）** |
|---|---|---|
| 做法 | 从各端 API 查询几何 | **各端注入探针，产出统一格式快照** |
| 依赖 | 受各端 API 能力限制 | **格式由我们定义** |
| Skyline 风险 | 若 API 不可用则整条路断 | ✅ 不受影响 |

各端产出方式：

| 端 | 产出方式 | 可行性 |
|---|---|---|
| **App（Native / iOS / 鸿蒙）** | Rust 内核直接产出几何快照 | ✅ 天然支持 |
| **Web** | `getBoundingClientRect()` 采集 | ✅ 确定可行 |
| **小程序 Skyline** | **注入探针产出**（不依赖查询 API） | 需 VC0 核实 |
| **小程序 WebView** | `createSelectorQuery` 或注入探针 | ✅ 可行 |

## 3. 分层校验架构

```
┌─ L1 编译期静态 ─────────────────────────────┐
│  CSS Profile × 各端支持度矩阵                 │  ✅ 完全确定
│  属性 / 选择器 / 值域 / 特性组合              │  覆盖：样式能力
└──────────────────────────────────────────────┘
                    ↓
┌─ L2 几何快照比对 ───────────────────────────┐
│  节点树几何：x / y / w / h / 层级             │  ✅ 完全确定
│  统一格式，各端产出                           │  覆盖：布局
└──────────────────────────────────────────────┘
                    ↓
┌─ L3 计算样式比对 ───────────────────────────┐
│  解析后的样式值：颜色 / 字体 / 间距 / 边框    │  ✅ 完全确定
│  不是源码文本，是 computed value              │  覆盖：视觉属性
└──────────────────────────────────────────────┘
                    ↓
┌─ L4 像素兜底 ───────────────────────────────┐
│  圆角 / 阴影 / 渐变 / 字形栅格化              │  ❌ 有噪声
│  仅覆盖 L1–L3 够不到的部分                    │  样本量下降一个数量级
└──────────────────────────────────────────────┘
```

### 3.1 L1 编译期静态（优先做）

**已知前提（官方明确）**：

> Skyline 支持的 WXSS 是 **WebView 的子集**，且"未来会一直保持子集状态"。

**官方提供的对齐开关**：

| 开关 | 作用 |
|---|---|
| `defaultDisplayBlock` | 默认布局改为 block，对齐 Web |
| `defaultContentBox` | 盒模型改为 content-box，对齐 Web |
| `tagNameStyleIsolation: legacy` | tag 选择器对齐 WebView（不隔离） |
| `keyframeStyleIsolation: legacy` | `@keyframes` 对齐 WebView |
| `enableScrollViewAutoSize` | scroll-view 自动撑开 |

**这意味着：Skyline 与 WebView 的差异是已知、可枚举、部分可配置的。**

→ 正是 CSS Profile 的用武之地：**把"各端 WXSS / CSS 支持度"做成 Profile 的一个维度，编译期拦住。**

其他已知差异：
- Skyline 默认 flex 布局 + border-box（与 Web 默认不同）
- Skyline **不支持原生导航栏**
- Skyline **不提供全局滚动**，需 `scroll-view`
- Skyline 按页面粒度 / 分包粒度开启，可渐进迁移

### 3.2 L2 几何快照

| 项 | 规格 |
|---|---|
| 数据格式 | 统一 JSON / CBOR 快照：`{ nodeId, path, x, y, w, h, depth, children[] }` |
| 采集时机 | 首帧稳定后 + 指定交互序列后（多点采集） |
| 坐标系 | **统一为视口左上角原点**（避免各端 scrollOffset 差异） |
| 浮点精度 | 固定小数位（建议 3 位），避免格式化噪声 |
| 真值基准 | **Web 端浏览器 = 真值**（`getBoundingClientRect` 是标准实现） |

### 3.3 L3 计算样式

比对**解析后的值**，不是源码：

| 类别 | 说明 |
|---|---|
| 颜色 | 统一转换为 RGBA 归一化数值（避免 `#fff` / `white` / `rgb(255,255,255)` 文本差异） |
| 长度 | 统一转换为 px 数值（避免 `em` / `rem` / `vw` 文本差异） |
| 字体 | 字族 + 字号 + 字重（**不含度量结果**） |
| 边框 / 间距 / 圆角 | 数值化 |

### 3.4 L4 像素兜底

**保留，但样本量会大幅下降**——因为 L1–L3 已过滤掉绝大多数差异。

只在以下场景启用：
- 圆角裁剪边界
- 阴影合成
- 渐变
- **字形栅格化**

#### 3.4.1 ★已落地（2026-10-02）：真截图观测 + 三项工程约束

**装置**：`bash scripts/shoot-l4-fixtures.sh` 在微信模拟器上采集同一夹具的 Skyline / WebView
两版截图（夹具 = `spike/vc0-skyline-geom/pages/l4-{skyline,webview}`，两端 wxml/wxss **逐字一致**，
脚本做 diff 前置校验）；报告由 `node scripts/check-consistency-pixel.mjs` 生成，**非门禁**（`gate:false`）。

实测读数（640×1386 物理像素，ROI 内）：`diff = 2161/693240 = 0.312%`、`hashDistance = 0` ⇒ `noise-level`；
差异全部集中在四项观测目标（字形 AA 1675px、圆角 AA 266px、渐变 219px、阴影 1px）。

**三条必须固化的工程约束（都是实测踩出来的）**：

| # | 约束 | 为什么（实测） |
|---|---|---|
| ① | **观测区域（ROI）必填**——排除设备 chrome | 状态栏时钟每分钟必变（任意两张截图"必然 changed"）+ Home 条 + 画布左缘 1px 伪影；`pixelObservation({ roi })` 把对比限定在应用内容区，region 坐标回传原图口径 |
| ② | **采集判据 = 运行时路由 + 特征色**，不是"盲等/哈希稳定" | 页面切换后模拟器**先黑屏再渲染**，两次黑屏哈希相同 ⇒ "哈希稳定即完成"会存下黑屏；`simulator_open_page` 返回 success 只表示"触发编译"，完成时刻必须查 `getCurrentPages()` 路由 + 截图上命中夹具特征色（`scripts/probe-png-colors.mjs`） |
| ③ | **同一画面跨端比对的噪声底含该端的 AA 本身** | 圆角弧线 AA 在两端就有 266px 差（占块 2.2%）⇒ 跨端 verdict 对它无区分度；"圆角缺失"这类缺陷的检出放**同端注入**（M4 的 L4 算子：与自身原图比，原图 `identical`、注入后差异块定位到四角） |

**能力形态的诚实表述**：L4 对局部小缺陷的价值是**定位**（报告差异块坐标 + 像素数），不是全局判定——
圆角缺失最大可注入信号仅 430px（0.05%），**天然低于 0.5% 全局噪声带**，verdict 恒为 `noise-level`。
圆角/颜色的"通过/失败"判定由 L3 数值比对承担（Web golden 实测含四个 borderRadius 角键）。

## 4. 各端探针设计

### 4.1 统一探针接口

```ts
interface ConsistencyProbe {
  // 产出统一格式几何快照
  captureGeometry(rootSelector: string): GeometrySnapshot;
  // 产出解析后的计算样式
  captureComputedStyle(nodeId: string): ComputedStyleSnapshot;
  // 上一次校验的失败详情（供 AI / 开发者定位）
  lastDiff(): DiffReport;
}
```

### 4.2 各端实现要点

| 端 | 要点 | 风险 |
|---|---|---|
| **Web** | 直接 `getBoundingClientRect` + `getComputedStyle` | 低 |
| **App** | Rust 内核产出，与指令流同源 | 低 |
| **Skyline** | **注入探针，不依赖 `boundingClientRect`** | 🔴 高，需 VC0 |
| **WebView 小程序** | 可用查询 API，但建议统一走注入探针保证格式一致 | 低 |

**强制约束：所有端必须产出同一格式，不允许在比对层做格式适配。**
（格式适配会把差异隐藏在转换里，与"零静默失败"原则冲突）

## 5. 容差设计（关键章节）

### 5.1 唯一不可消除的差异：文本度量

| 端 | 度量引擎 |
|---|---|
| Web | 浏览器内置 |
| App | 平台注入（StaticLayout / CoreText / 鸿蒙） |
| Skyline | 自研渲染引擎 |

**同一段文本三端宽度必然有差异。**

→ 必须显式设计容差带，且**容差按属性分级、可声明**。

### 5.2 属性分级容差表

| 属性类 | 建议容差 | 理由 |
|---|---|---|
| 结构类（位置 / 尺寸） | 严格（如 ≤ 1px 或 ≤ 0.5% 取大） | 确定性高 |
| **颜色类** | **极严格（如 ±1/255）** | **真 bug 高发区，且确定性极高** |
| 字体属性（字族 / 字号 / 字重） | 严格相等 | 确定性 |
| **文本度量结果（宽度）** | **唯一允许宽带** | 三端引擎天然不同 |
| 圆角 / 阴影 / 渐变 | **不比数值，走 L4** | 非确定性 |

### 5.3 🔴 禁止：全局差异阈值

**全局阈值是最危险的做法。**

理由（业界公开结论）：
> 一个 50×20 按钮的变色只占全高清页面的 **0.001%**，
> 在 0.01% 全局阈值下**必然漏报**——而这正是传统方案漏报的根源。

**强制约束**：
- ❌ 禁止"全页差异率 ≤ X% 即通过"
- ✅ 必须按属性类分级
- ✅ 每个校验项单独判定，单项失败即整体失败
- ✅ 容差可声明、可覆盖（组件级 override），但**不得全局放宽**

## 8. 执行指令（给 LLM）

1. **VC0 未完成前，不得开始 VC4**——探针设计依赖其结论
2. **L1 优先于 L2**：输入已知、成本最低、复用既有 Profile 设施
3. **禁止全局差异阈值**，必须按属性分级（§5.3）
4. **所有端必须产出同一格式**，禁止在比对层做格式适配
5. **Web 端为几何真值基准**（浏览器是标准实现）
6. **文本度量必须显式容差**，不得与其他属性共用容差
7. Skyline 官方对齐开关（`defaultDisplayBlock` / `defaultContentBox` / `tagNameStyleIsolation` / `keyframeStyleIsolation`）**应在测试用例中默认开启**，并记录开启前后差异
8. 《各端支持度矩阵》产出后，**同步给 CSS Profile 规格与对标方案**（一次产出，三处受益）
9. 每新增一个校验项，必须同时给出**该属性类的容差依据**，不得凭直觉设值
10. L4 像素层**必须记录每次失败的样本量**，用于验证"L1–L3 过滤后样本下降一个数量级"这一假设

## 10. 对外表述建议

| ❌ 不要说 | ✅ 应当说 |
|---|---|
| "我们不需要视觉回归" | "我们把 90%+ 的一致性验证转为**确定性数值比对**，像素比对仅作兜底" |
| "我们端差异为零" | "端差异在**编译期被拦住**，运行时差异由**分级容差**机器判定" |
