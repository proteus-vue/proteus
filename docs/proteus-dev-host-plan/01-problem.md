# G-45-E1：问题解剖——自定义基座循环为什么是无解的

> 本文档回答两个问题：① 传统跨端框架的原生插件开发循环到底慢在哪；② 为什么在「插件静态编进基座」的架构里，这个问题**修不掉**。

---

## 1. 传统循环（uni-app 为代表）

```
┌─────────────────────────────────────────────────────────┐
│  开发期（纯 JS/页面）                                      │
│    标准基座 + HBuilderX 真机运行：JS 热刷，体验尚可          │
│                                                           │
│  一旦引入原生插件（扫码/推送/支付/自研 SDK…）：               │
│    ① 云打包「自定义基座」（Android APK / iOS IPA 全量构建）   │
│       → 5~20 分钟起步，页面/插件越多越慢                     │
│    ② 卸载标准基座 → 安装自定义基座 → 登录态/本地数据丢失      │
│    ③ 验证插件功能                                          │
│    ④ 发现 bug → 改插件代码 → 回到 ①                        │
│                                                           │
│  ★ 循环往复：插件开发的「保存-刷新」被换成了「保存-打包-安装」 │
└─────────────────────────────────────────────────────────┘
```

竞品横向（同构问题）：

| 框架 | 原生侧改动 | 开发循环 |
|------|-----------|---------|
| uni-app | 原生插件 → 自定义基座云打包 | 分钟级 + 重装 |
| React Native | Native Module → gradle/xcode 重编译 | 分钟级 + 重装 |
| Flutter | Platform Channel 原生侧 → 全量重编译 | 分钟级 + 重装 |
| Taro（RN 壳） | 同 RN | 分钟级 + 重装 |

**共同点：JS 层热刷，原生层全量重编。** 原生插件恰恰是业务价值最高、迭代最频繁的部分之一。

---

## 2. 根因四条（为什么修不掉）

| # | 根因 | 说明 |
|---|------|------|
| 1 | **静态链接** | 插件原生代码在 build-time 编进 App 二进制——原生任何改动 = 全量原生构建。这是「基座是构建产物」这一形态决定的，不是工具优化能解决的 |
| 2 | **无稳定边界** | JS ↔ Native 没有版本化契约。基座无法「只换插件、不动基座」，因为换插件就可能破坏基座假设 |
| 3 | **基座与业务同产物** | 打包把「引擎（稳定层）」和「插件/业务（高频变化层）」绑成单个产物——构建时间随业务规模线性增长（页面越多越慢的真正来源） |
| 4 | **调试与发布同构** | 调试构建没有独立动态加载通道，一切以发布形态为准——发布约束（静态链接、签名）被原样搬进开发循环 |

**结论**：在「基座 = 构建产物」范式内，①打包缓存、②云打包提速、③增量 gradle 都只是缓解。要打破循环必须换范式：**基座从「产物」变成「常驻宿主」**——这正是 Proteus 原则 #0 的领地。

---

## 3. 为什么 Proteus 方法论天然能解

原则 #0（统一语义收敛）的核心公式：**语义定义（框架做）+ 后端实现（平台做）**。

把它投影到「基座-插件」关系上：

```
传统：  业务代码 ──依赖──→ 具体插件（build-time 静态绑定）
                         ↑ 改插件 = 改基座

Proteus：业务代码 ──只依赖──→ 语义接口（useNative() / Capability Hook）
                              ↓ 装载时才绑定
          基座 = SPI 宿主（零插件知识）
          插件 = DynamicBackendModule（运行时装载，装载即验证）
```

**关键洞察**：G-28（NativeBackend SPI）已经把「业务代码零原生耦合」做成了编译期铁律（NAT001 禁止直调 SDK）；G-38（CompilerBackend SPI）已经预留了 `getCacheKey/getArtifactHash` 增量构建接口；G-42 已经有签名安全网关。**G-45 不是发明新能力，而是把三个已有决策点到成一条开发循环——这正是方法论的复利。**

根因 → 解法映射：

| 根因 | G-45 解法 | 详细 |
|------|----------|------|
| 静态链接 | 插件 = 动态后端模块，运行时装载 | 02-architecture §2 |
| 无稳定边界 | 版本化 SPI + 装载即验证（conformance 快检） | 03-spi |
| 基座与业务同产物 | 双层产物 + 独立 cacheKey（构建 O(改动)） | 02-architecture §4 |
| 调试与发布同构 | Dev Host 常驻 + 推送通道；发布回静态链接（诚实边界） | 02-architecture §5 |

## 4. 量化预期（工程推算，需 B4/B5 实测校准）

| 指标 | uni-app 自定义基座 | G-45（Android tier） | 校准点 |
|------|-------------------|---------------------|--------|
| 插件改动 → 可验证 | 5~20 分钟 + 重装 | **秒级**（push + 装载验证） | B4 实测 |
| 基座构建频次 | 每次插件改动 | **每框架版本 1 次** | 参考实现 C-07 已机器证明 |
| 构建时间随页面数 | 线性增长 | **无关**（base cacheKey 不含规模因子） | 参考实现 C-07 |
| 登录态/本地数据 | 每次重装丢失 | **不丢**（不重装） | — |
| iOS 插件改动 → 可验证 | 分钟级云打包 | 秒~分钟级（增量重签 tier） | B5 实测 |

> ★ 未实测数据禁止对外宣称（CMP046 同源纪律）：上表「秒级」为设计目标，B4/B6 落地后以 benchmark 固化。
