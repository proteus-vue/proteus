## §1 ★ 痛点诊断：本质不是"内存大"，是"不可归因"

### 1.1 一句把问题说透的话

React Native 泄漏检测指南原话（权威性中等，但表述极准）：

> 泄漏 *"manifests **gradually**... By the time users report it,
> **you have no stack trace and no obvious culprit**."*

**"渐变" + "无堆栈" + "无明确元凶"**——这三件事同时成立，才是这个痛点真正的形状。

### 1.2 ★ OOM 是唯一一类"现场随进程一起消失"的故障

| 平台 | 终止方式 | 有无堆栈 | 有无回调 |
|---|---|---|---|
| **iOS** | Jetsam 发 **SIGKILL** | ❌ 无 | ❌ 无 |
| **Android** | lmkd 按 minfree 六档杀进程 | ❌ 无 | ❌ 无 |
| **小程序** | 超限后被系统回收 | ❌ 无 | ❌ 无 |
| Web | 标签页崩溃 | ❌ 无 | ❌ 无 |

**全都没有堆栈、没有回调、没有最后的机会。**

所以"不方便定位"**不是工具不够好，是结构上拿不到**。

### 1.3 推论：方案重心不在"优化内存"，在"死之前把归因快照落盘"

这条决定了整份方案的形状——

| 错误方向 | 正确方向 |
|---|---|
| 让框架"用更少内存" | 让框架**知道内存在哪里**，且**进程死前留下遗言** |
| 给开发者更好的 profiler | 让**生产环境的崩溃自带归因信息** |

优化内存是手段，**可归因是目标**。顺序不能反。

## §2 🧱 结构性优势：单一所有权账本

> 这是"绕开原生控件树"的**第四次兑现**。
> 前三次：鸿蒙 C-API 高性能渲染、全局挂载点（App Root）、可停靠滚动容器。

### 2.1 传统框架是"双堆"，天然不可归因

| 框架 | 内存分布 | 排查代价 |
|---|---|---|
| **RN** | JS heap（Hermes）+ Native heap，**分别用不同工具查** | 先判断是哪一堆 |
| **Flutter** | Dart 堆 + 原生纹理 + PlatformView，**三处** | 官方排查路径第一步就是"Dart 堆正常但 RSS 很大 → 问题在 Native 层" |
| 小程序 | WebView 实例 / Skyline 渲染实例 | 页面栈与实例归属不清 |

**双堆的直接后果：泄漏源无法用单一账本表达。**

### 2.2 Proteus：只有一个持有者

```
传统：谁该释放？说不清
      平台控件树 ←→ JS 引用，双向持有

Proteus：内核是唯一 owner
      Rust 内核创建/销毁，业务代码不持有原生节点引用
      释放时机确定 → 可记账
```

**关键前提**：业务代码不持有原生节点引用——这与 **Janus 的 J1 约束**（实现体禁止业务逻辑、只允许参数转换/调 SDK/结果回传）是**同一条约束的两面**。

### 2.3 ★ 这个优势只有一条兑现路径：内核必须把账记全

**如果有任何资源绕过内核直接分配，账本就出现黑洞。**

所以写死一条硬约束（§3.1）：

> 🔴 **所有跨边界资源必须经内核登记，禁止宿主层自持。**

宿主层（iOS/Android/鸿蒙/Web/小程序适配器）若为了"方便"自己缓存一个原生对象，
账本立刻失真——**而失真是静默的**，表现为"账本说一切正常，但 RSS 一直在涨"。

### 2.4 由此得到两个别人报不出来的指标

| 指标 | 定义 | 为什么别人给不出 |
|---|---|---|
| **确定性回收覆盖率** | 内核持有内存 / 进程总内存 | 他们的内存分散在多个持有者手里，分母都定义不了 |
| **内存可归因率** | OOM 事件中带完整归因快照的比例 | 他们没有归因快照机制 |

**这两个指标与 Morpheus 的「0% 逃生口」同类**——不是"我们更好"，是"我们有一个别人在结构上无法给出的数"。

## §3 🔴 必须先破除的误解：Rust 内存安全 ≠ 不泄漏

### 3.1 Rust 防什么、不防什么

| Rust 能防 | Rust **防不了** |
|---|---|
| use-after-free | 忘记从 HashMap 移除 |
| double free | arena 未 reset |
| 数据竞争 | 缓存无上限 |
| 悬垂引用 | 订阅未取消 |

**第二列全是逻辑泄漏，在 Rust 里一样发生。**

而且更危险的是心理暗示：**"没有 unsafe 所以安全"**——
恰恰因为编译期不报错，逻辑泄漏在 Rust 项目里**更容易被忽视**。

### 3.2 真正防泄漏靠三件事

| # | 机制 | 说明 |
|---|---|---|
| 1 | **arena 按帧 / 按页批量释放** | 生命周期天然收敛，不需要逐个 release |
| 2 | **显式生命周期配对** | 编译期检查 create/destroy 成对 |
| 3 | **内核记账** | 运行时知道每个节点的归属与大小 |

**这三条是本方案的骨架**，而非常规的"内存优化技巧"。

## §4 三段防线（不是一段）

| 段 | 机制 | 拦什么 | 阶段 |
|---|---|---|---|
| **第一段** | 生命周期配对、资源必须 release、全局层上限 | **结构性泄漏（占大头）** | 编译期 |
| **第二段** | 分级预算 + 水位三档响应 | 尖峰与缓慢增长 | 运行期 |
| **第三段** | last-will 落盘 → 下次启动上报 | 归因 | 死后 |

### 4.1 第一段：编译期（收益最大、成本最低）

**结构性泄漏占大头**——这是业界共识。能被编译期拦住的，绝不留给运行期。

具体三条：

| # | 检查 | 违反后果 |
|---|---|---|
| C1 | 资源 create 必须有配对 release，或使用 arena 作用域 | 编译期报错 |
| C2 | 全局挂载点节点上限（与 GP 方案 C2 同一约束） | 编译期报错 |
| C3 | 订阅/监听器必须绑定作用域 | 编译期警告，运行时兜底解绑 |

**C3 特别重要**：事件订阅泄漏在超级应用里最常见，且最难查（表现为"页面关了但回调还在跑"）。

### 4.2 第二段：运行期水位三档

**先说清楚：水位响应不是我们的发明。**

| 框架/平台 | 已有机制 |
|---|---|
| Flutter | `didHaveMemoryPressure` |
| 鸿蒙 | `onMemoryLevel` + `hidebug` |
| 华为官方 | PSS 趋势判据 + `RESOURCE_OVERLIMIT` |
| 小程序 | `wx.onMemoryWarning` |
| iOS | `didReceiveMemoryWarning` |

**我们的增量不是"发现水位"，是把响应动作做成框架内建的、可声明的**——
而不是让每个业务自己写 `imageCache.clear()`。

三档设计：

| 档 | 触发 | 动作 |
|---|---|---|
| **normal** | — | 正常 |
| **warning** | 水位 1 | 释放非活跃页面缓存、降图片解码缓存 |
| **critical** | 水位 2 | 销毁非活跃栈视图（保留栈状态，对齐 Android `saveBackStack` 语义） |
| **terminal** | 水位 3 | **同步写 last-will 快照**（§5），不等网络 |

**响应动作必须可声明**——业务方可以指定"我的页面在 critical 档愿意放弃什么"，
框架不替业务方决定（与单位系统里"字体缩放跟不跟随"同一处理原则）。

### 4.3 第三段：死后归因（§5）

见下节。

## §5 ★ 最有价值的设计：last-will（临终遗言）

### 5.1 为什么必须有这一段

传统方案死在"进程没了"。OOM 的唯一现场信息源就是**那个即将消失的进程**。

所以必须：**在死之前把归因快照写到本地**。

### 5.2 机制

```
水位进入 terminal
    ↓
同步写归因快照到本地文件（不等网络，不等异步）
    ↓
进程被杀
    ↓
下次启动 → 读到快照 → 上报 → 清除
```

**关键：同步写、不等网络。** 网络请求在 terminal 档来不及完成。

### 5.3 快照内容（三类）

| 类 | 内容 | 用途 |
|---|---|---|
| **节点级** | 哪个页面 / 组件持有多少节点、层级深度 | 定位泄漏位置 |
| **资源级** | 图片/纹理/句柄的数量与估算大小 | 定位泄漏类型 |
| **时间线** | 最后 N 秒的关键操作序列 | 定位触发路径 |

**第三类最容易被忽略，但最有价值**——
"内存涨上去之前用户刚做了什么"，是泄漏归因的钥匙。

### 5.4 ★ 唯一真门槛：写盘窗口有多少毫秒

> **terminal 档到 SIGKILL 之间有多少毫秒？**

这个数字决定 last-will 成不成立：

| 窗口 | 设计 |
|---|---|
| 数百毫秒 | 可写完整快照 |
| **几十毫秒** | 必须**预写 + 只补尾部**——骨架提前落盘，terminal 时只追加最后几字节 |

**两种设计完全不同。** 所以 **MS0 必须先做，且不可压缩**（§9）。

## §6 白屏要分两类，不要混为一谈

| 类型 | 原因 | 归属 |
|---|---|---|
| **首屏白屏** | 异步 I/O / 网络等待 | ✅ **已有《首屏白屏优化方案》覆盖，本方案不重复** |
| **运行期白屏** | 内容被回收后重建失败 | 🔴 **本方案 §6** |

### 6.1 运行期白屏的成因

页面被回收（内存压力 / 页面栈超限）后重新进入，
**视图已销毁但状态未恢复** → 白屏。

这与导航体系的多栈保活是同一件事的两面：
**保活不足 → 重建失败 → 白屏。**

### 6.2 微信官方给的一个关键事实

| | WebView 模式 | **Skyline** |
|---|---|---|
| 渲染实例 | **每页一个 WebView** | **共享渲染实例** |
| 页面栈 | 最多 **10 层** | 连续 Skyline 页面**无层数限制** |
| 光栅化 | 异步 | **同步** |

**结论：超级应用在 WebView 模式下必然撞墙**——
页面栈 10 层 + 每页一个 WebView，这就是内存墙。

这印证了《导航体系方案》里"多栈 + 保活策略"的必要性——
**两者是同一场仗的两面，不是两个独立问题。**

### 6.3 本方案的处置

| # | 措施 |
|---|---|
| 1 | 回收前保存可恢复状态（与导航方案的栈状态保存同一机制） |
| 2 | 重建失败不得白屏——**必须有降级占位 + 上报** |
| 3 | 白屏事件进埋点，与 OOM 事件关联分析 |

## §7 三个必须标注来源等级的数字

| 数字 | 权威性 | 处置 |
|---|---|---|
| 小程序 iOS 约 200–300MB / Android 150–250MB | 🔴 **较低** | **必须实测**，不得对外引用 |
| iOS 设备阈值（iPhone 8 约 200–300MB） | 🟡 中等 | 可作参考，须注明机型 |
| 5000×4000 RGBA ≈ 76MB | 🔴 较低，**但算法可自算** | ✅ 可用 |

### 7.1 图片是超级应用的头号杀手

无论上面数字来源如何，**"图片是头号杀手"这条结论是稳的**——
因为它是算法决定的（像素数 × 4 字节），不依赖任何外部来源。

所以 §4.2 的预算模型里，**图片必须单列**：

```
单图内存 = 宽 × 高 × 4 字节
× 解码后常驻 + 可能的多份缓存（缩略图/原图/圆角裁剪副本）
```

**特别提醒**：圆角裁剪副本常被忽略——一张图可能在内存里存在 3 份。

## §8 ★ 超级应用的特有矛盾：多栈保活 × 内存预算

### 8.1 矛盾本身

《导航体系方案》的多栈保活（IndexedStack 语义）**本身就是内存负担**——
超级应用几十个模块，若所有 tab 常驻，内存必然爆。

### 8.2 处置：保活策略必须由内存预算反向约束

```
❌ 按交互体验定保活策略 → 体验好但内存爆
✅ 按内存预算定保活上限 → 预算内取体验最优
```

**这是本方案与《导航体系方案》的硬交叉**，已列为 **MS3 的强制输入**。

### 8.3 三处预算单元汇总

| 出处 | 约束 | 归属 |
|---|---|---|
| 全局挂载点 C2 | 节点上限 32（建议值，**需实测校准**） | GP 方案 |
| 导航多栈 | 保活栈数量 | 导航方案 |
| Morpheus | 800 个动画实例 | Morpheus 方案 |

**这三处都是内存的预算单元，必须纳入统一预算模型**——
否则各自优化、总量失控。

## §10 对外表述

### 10.1 推荐落点

> **"传统跨端框架的内存分散在多个持有者手里，OOM 时无堆栈、无元凶。
> Proteus 只有一个所有权账本，且进程终止前会留下归因快照。"**

### 10.2 禁语

| ❌ 不要说 | 原因 |
|---|---|
| "我们用 Rust 所以不会内存泄漏" | ❌ **错误**——Rust 防不了逻辑泄漏（§3） |
| "我们能避免 OOM" | ❌ 任何框架都不能保证 |
| "我们的内存占用更低" | ❌ 无对照数据，且非本方案目标 |
| "内存可归因率 100%" | ❌ 小程序端可能做不到（§9.2） |

### 10.3 可说的

| ✅ 可以说 | 前提 |
|---|---|
| "**单一所有权账本**" | 架构事实 |
| "**确定性回收覆盖率**" | 需 MS7 实测 |
| "**内存可归因率**" | 需 MS7 实测，**且标明分端** |
| "OOM 不再是黑盒" | 有 last-will 即可说 |

## §13 结论

**这个痛点值得做，而且我们的结构性优势是真实存在的（单一所有权账本）。**

但方案的诚实性建立在两点上：

1. **承认 Rust 防不了逻辑泄漏**（§3）——否则整份方案建立在错误前提上
2. **承认水位响应是行业已有做法**（§4.2）——我们的增量是"可声明 + 归因"

真正的独特价值只有两块：

- **last-will**（§5）——让死掉的进程留下遗言
- **两个别人给不出的指标**（§2.4）——量化架构主张

这两块都有前提：**MS0 必须先做。** 写盘窗口如果不够，§5 要推倒重来。
