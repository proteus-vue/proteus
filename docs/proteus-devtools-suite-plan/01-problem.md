## 2. 核心洞察：「框架自己做最方便」的技术根据

"框架配套的总是最顺手"是经验判断，但它的**技术根据**可以更精确——
框架掌握着第三方 IDE 插件**无法获取**的六类知识：

| # | 框架独占知识 | 第三方插件能做吗 | 能换来什么能力 |
|---|------------|----------------|--------------|
| 1 | **IR 结构** | ❌ 只有框架有 | 语义级导航：SPI 调用 → 跳到后端实现（非文本匹配） |
| 2 | **SPI 分层规则** | ❌ | 越层调用实时诊断（L0 直连 L2 → 画红线） |
| 3 | **conformance 断言** | ❌ | 断言失败内联到代码行 |
| 4 | **SPI 拓扑** | ❌ | 真实依赖图（非静态 import 图）+ 循环检测 |
| 5 | **设备等价类**（G-52/53） | ❌ | "这行代码在哪类设备会挂" |
| 6 | **渲染后端语义**（G-27） | ❌ | 改代码即时预览多形态 |

**这六项是框架的知识垄断区**——不是"我们做得更好"，而是**别人拿不到数据**。
这就是「框架自己做最方便」的真正含义，也是本份 plan 的存在理由。

## 3. 关键张力：不绑定 IDE vs 配套最顺手

原则 #0 要求不绑定，但配套工具又要"最顺手"——看似矛盾，实则两面：

> **内核统一（框架自己做，所以最顺手） + 前端可换（所以不绑定）**

**内核只有一个**：能力源自框架知识，天然唯一、天然最准。
**前端随便换**：VSCode / JetBrains / Neovim / CLI / Web，都只是薄适配层。

**这正是 SPI-First 在工具层的投影**——第 18 次泛化：

```
不绑定渲染后端（G-27）→ 不绑定数据池（G-46）→ 不绑定验证环境（G-51）
   → 不绑定设备形态（G-52）→ 不绑定设备供给（G-53）→ ★ 不绑定 IDE 形态（G-54）
```

## 4. 问题陈述

若不把编码期工具化，会导致三个具体损失：

1. **框架知识锁在文档里**——分层规则写在 rules.md，但开发者写代码时看不见，越层只能等 code review
2. **断言与代码脱节**——conformance 失败只在 CI 报，不在编辑器报，反馈周期从秒级变成分钟级
3. **新人上手靠口口相传**——SPI 拓扑、后端选择、设备影响面，全靠读 60 份 plan

## 5. 诚实边界

- **不承诺自研完整 IDE 插件生态**——本份只做能力内核 + 协议 + VSCode 参考适配，其余 IDE 由社区/后续补
- **不承诺取代 G-19**——运行时诊断仍由 G-19 负责，G-54 不重叠
- **LSP 能力受语言限制**——本份以 TS/JS 生态为基准（与既有参考实现一致）
- **不承诺 IDE 插件市场排名/下载量**——那是运营结果，非架构承诺
