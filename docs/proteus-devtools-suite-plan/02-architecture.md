# G-54 架构：三层解耦

## 1. 全景

```
┌─────────────────────────────────────────────┐
│  IDE 适配层（薄，可换）                        │
│  VSCode │ JetBrains │ Neovim │ CLI │ Web     │
└──────────────────┬──────────────────────────┘
                   │ 协议（标准 / 自研）
┌──────────────────▼──────────────────────────┐
│  协议层                                       │
│  LSP（导航/补全/诊断/悬停）                    │
│  DAP（调试）                                  │
│  自研 RPC（SPI 图 / 设备影响面 / inspect）      │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│  ★ 能力内核 FrameworkKnowledgeProvider        │
│  框架独占知识：IR / 分层 / 断言 / 拓扑 /        │
│  设备等价类 / 渲染语义                         │
│  —— IDE 无关，单一实现                        │
└─────────────────────────────────────────────┘
```

## 2. 为什么必须是三层

| 层 | 若合并会怎样 |
|----|------------|
| 内核 ↔ 协议 | 换 IDE 要重写内核 → 违反不绑定 |
| 协议 ↔ 适配 | 协议绑死某个 IDE → 生态锁死 |

**只有三层分离，才能同时满足"内核唯一（最顺手）"和"前端可换（不绑定）"。**

## 3. 协议选择原则

**能用标准协议就用标准，标准不够才自研。**

| 能力 | 协议 | 理由 |
|------|------|------|
| 跳转/补全/悬停/诊断 | **LSP** | 业界标准，VSCode/JetBrains/Neovim 全支持 |
| 断点/单步 | **DAP** | 调试标准协议 |
| SPI 依赖图 | **自研 RPC** | LSP 无此概念 |
| 设备影响面 | **自研 RPC** | 框架特有 |
| 多形态预览 | **自研 RPC** | 框架特有 |

**自研只占 3 项，且都是框架独占能力**——标准协议覆盖了 70% 需求。

## 4. 降级链（沿用 G-53 四档降级链 / G-51 分档纪律）

```
LSP  ─→ DAP ─→ RPC ─→ CLI ─→ raw(内核直调)
```

**关键纪律**：任一档不可用时**降级而非失败**（G-46 RSC-01 精神）。
最坏情况退到 `raw`——内核永远可调用，因为它是纯函数式的知识查询。

## 5. 与既有体系的接缝

| 对接 | 内容 |
|------|------|
| G-19 | 运行时诊断由 G-19 提供，G-54 在 IDE 内**嵌入其入口**，不重新实现 |
| G-50 | CLI 流水线复用 G-17/G-50 A，G-54 只加"IDE 内触发" |
| G-53 | 设备等价类数据直接来自 G-53 清单 |
| G-51 | 检查项（L0/L1/L2 三阶梯度报告）在 IDE 内联展示——原稿「DevTools 加固」未入库，消费面前指 G-51/G-52 |
| G-52 | 设备矩阵报告在 IDE 面板可视化 |

## 6. 成熟度影响

G-54 将 L0（文档自检）之前的**编码期**纳入：
```
L-1 编码期辅助  ← ★ G-54（新增）
L0  文档自检     ← G-50
L1  IR 模拟      ← G-51
L2  真运行时     ← G-51 + G-52
L3  供给编排     ← G-53（本地/池化/云 + 覆盖率门槛）
```
**反馈周期从"CI 分钟级"提前到"敲键盘毫秒级"。**
