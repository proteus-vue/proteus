# Proteus 原生能力接入方案

> 定位：**让开发者 99% 的业务代码不需要原生插件**——通过编译期 codegen + 能力原语化 + 插件成本降低
> ★★**战略定位（2026-09-30 用户裁定）**：本方案**升格为要认真推进的战略线**——
>   「目标就是业务代码 99% 不用手写原生插件」。它与 JS 引擎线的关系：**引擎选型已收口**
>   （默认现状 + 可插拔兜底，见 `Proteus_JS引擎选型与可插拔方案.md`），**原生能力接入是下一步主线**。
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4）
> 依赖：《Host ABI 宿主抽象层设计方案》（批处理红线、能力插件机制）、《UC0 兼容度扫描工具规格》（优先级算法）、
> 《缺口补齐任务卡清单》（C1/C2 已收官——本方案建立在其上）
> 结论前置：**不开放任意原生调用**——那会在编译期封闭体系上开大口子；正确路径是 codegen + 原语化 + 降本
> ★数字口径（2026-09-30 对账）：当前 **82 个 Capability Hook**（`PRIMITIVE_CATALOG` 中 kind=capability）
> · **185 个语义原语**（SSOT）· **111 条编译规则**——本文正文已按此口径修正。

| 问题 | 结论 |

## 1. 目标重新定义：把「99%」拆成可测量口径

「99% 业务代码不需要原生插件」目前是个感觉，**必须先拆开**，否则无法判断该往哪投。

| 指标 | 定义 | 决定什么 |
|---|---|---|
| **A. 内置能力覆盖率** | 业务需要的原生能力中，由**内置能力库直接提供**的比例 | **决定"99%"能否达成** |
| **B. 第三方 SDK 需插件比例** | 业务所需能力中，**必须自写插件**的比例 | 决定"达不成时的痛苦程度" |
| **C. 插件平均开发耗时** | 从"需要某个能力"到"插件可用"的人时 | **决定 B 的代价** |

**三者关系**：
```
A + B ≈ 100%
C 决定 B 有多痛
```

**所以战略是两条腿**：
- 把 A 尽量推高（扩充内置能力库）
- 把 C 尽量压低（codegen 降低插件成本）

**只做一条不够。** 因为 B 永远不为零——商业 SDK 你无法内置。

### 1.1 测量方法（复用既有工具）

用 **UC0 扫描工具**（已有）跑真实项目，统计原生能力调用清单：

- `uni.xxx` 调用清单与位置（已有扫描项）
- JSI / 原生模块调用点
- 按"被几个项目用到"聚合（**跨项目聚合优先于单项目频次**）
- 成本加权（S/M/L = 1/3/8）

**输出物**：《能力实现优先级表》——这张表是本方案的输入，没有它就没法定优先级。

## 2. 现状盘点

### 2.1 已有基础

| 资产 | 说明 |
|---|---|
| **82 个 Capability Hook** | `useCamera` / `useLocation` 等，已是能力入口（C1–C82，含 C82 useWebAssembly） |
| **185 个语义原语** | 编译期封闭集（其中 82 个为 capability 类） |
| **Compiler Plugin API** | IR 可编程访问，覆盖规则实现即获得新能力 |
| **Host ABI 能力插件机制** | 宿主侧能力注册与清单校验 |

**正确方向是扩充它，不是另起一套。** 已有 82 个 Hook 说明这套体系是通的。

### 2.2 82 个 Hook 是体温计

Hook 越多，说明**收敛模型的漏点越多**。

它不是缺陷——它是"185 原语覆盖得够不够"的**监控指标**。建议当**持续监控项**，不是静态配置：

- 新增 Hook 频率持续不为零 → 原语集未稳定
- 单个 Hook 调用频次极高 → 该考虑升级为内置能力

## 3. ★ 核心判断：不开放任意原生调用

这是本方案最重要的一条，理由与"性能"无关，与**架构一致性**有关。

### 3.1 开放调用 vs 编译期封闭

| | 收敛体系（当前） | 开放反射调用 |
|---|---|---|
| 跨端一致性 | ✅ | ❌ Android 的 API 在 iOS 不一定有 |
| conformance | ✅ 可校验 | ❌ 无法校验 |
| AI 可校验 | ✅ | ❌ AI 要理解任意原生 API |
| 编译期报错 | ✅ | ❌ 运行时才崩 |
| 端对齐 | 机器判定 | 靠开发者自觉 |

**开放任意调用 = 在第一王炸上开一个大口子。**

而且这是**静默发生**的——开发者用了，你不会收到任何编译错误。

### 3.2 与"不开放"不矛盾的部分

**不是不让开发者用原生能力**，而是**入口必须是收敛的**：

```
❌ 开发者直接反射调用任意原生 API
✅ 开发者使用 Capability Hook / 内置能力
✅ 确实没有的能力 → 写插件（codegen 辅助）→ 插件本身成为收敛的入口
```

---

## 4. ★ 真正的瓶颈：第三方 SDK 生态

### 4.1 JSI 直达解决不了它

**NativeScript 式的反射调用，只对"系统 API"有效。**

而真实业务最需要插件的这些，全是**商业闭源 SDK**：

| 类型 | 反射调用有效吗 |
|---|---|
| 系统 API（相机、定位、蓝牙） | ✅ 有效 |
| **广告 SDK** | ❌ 无效 |
| **地图 SDK** | ❌ 无效 |
| **支付 SDK** | ❌ 无效 |
| **推送 SDK** | ❌ 无效 |
| 各类厂商 SDK | ❌ 无效 |

**这些 SDK 提供的是自己的 API 与二进制，不是系统 API。**

**结论**：靠"能调原生"提不上去 A，因为阻挡 A 的那些能力不是"原生 API 调用"问题。

### 4.2 所以对 B 的唯一办法是降 C

**B 永远不为零**——你无法内置所有商业 SDK。

因此战略重心必须包含：**把插件开发成本压到极低**。

业界的参照：Expo 官方称写一个自定义模块 wrapper 约 **8 小时** 工程时间。
**我们的目标应该是把它压到 30 分钟级**——靠 codegen 把"手写 JNI / ObjC 桥接"变成"声明一下接口"。

## 5. 建议方案：三条腿

### 腿一：编译期 codegen 取代运行时反射

**借 NativeScript 的 Metadata 思想，但产出物不同**：

| | NativeScript | Proteus 建议 |
|---|---|---|
| Metadata | 编译期从 SDK 头文件生成，嵌入包内 | ✅ 同样思路 |
| 运行时 | 查表 + 反射调用 | ❌ **不用** |
| 产出 | — | ✅ **静态绑定代码**（编译期生成） |

**为什么产出静态绑定而不是运行时查表**：

| 维度 | 静态绑定 | 运行时查表 |
|---|---|---|
| 性能 | ✅ 直接调用 | 查表开销 |
| 类型安全 | ✅ 编译期 | ❌ 运行时 |
| conformance | ✅ 可覆盖 | ❌ 无法覆盖 |
| AI 可校验 | ✅ | ❌ |

**这条与整套架构哲学同构**——编译期收敛，不是运行时灵活。

### 腿二：能力原语化

把高频原生能力**纳入语义原语体系**，而不是做成"外部插件"：

```
能力 → 语义原语 → 编译期校验 → conformance 覆盖 → AI 可校验
```

**扩充 Capability Hook 的优先级算法**（复用 UC0 的）：

1. **跨项目聚合优先**（被几个项目用到 > 单项目调用次数）
2. 成本加权（S/M/L = 1/3/8）
3. 已有 Hook 的高频调用 → 优先升级为内置

**参照 Expo 的模块分类做覆盖对照**：
设备信息、存储、文件系统、媒体（相机/图库/音频）、通信（通知/分享/短信）、
传感器、生物识别、网络状态……

### 腿三：插件开发成本降低

**目标：8 小时 → 30 分钟。**

| 步骤 | 现状（手写） | codegen 后 |
|---|---|---|
| 声明接口 | — | ✅ TS 类型声明 |
| 生成 JNI / ObjC 胶水 | 手写，易错 | ✅ 自动生成 |
| 类型对齐 | 运行时才发现 | ✅ 编译期 |
| 注册与清单 | 手工维护 | ✅ 自动 |

**"声明一下接口"应该是全部工作量。**

## 6. ★ 与批处理红线的隔离（关键工程约束）

### 6.1 JSI 细粒度与批处理红线冲突

JSI 的优势恰恰是**细粒度同步调用**——而我们的性能叙事建立在
**"跨边界调用次数 = 帧数"** 这条红线上。

**若开发者在渲染路径里每次属性变更都调一次原生，乘法效应会吃掉全部性能优势。**

### 6.2 隔离机制

| 路径 | 规则 |
|---|---|
| **渲染路径** | 槽位直写 → IR 指令 → **批量提交**，跨边界次数 = 帧数 |
| **非渲染路径**（能力调用） | 可细粒度，但**不得进入每帧路径** |

**强制约束**：
1. 能力调用的回调**必须回到 platform thread** 才能调入内核（沿用 Host ABI 既有约束）
2. 渲染帧回调内**禁止发起能力调用**
3. CI 静态检查：帧回调路径不得出现能力调用

### 6.3 为什么这条值得写死

**静默失效模式**：开发者在 `onFrame` 里调一次原生，单次看不出问题，
但在 2 万元素列表上会放大成灾难，且**不会报错**。

## 7. NativeScript：可借与不可借

### 7.1 ❌ 不可借：runtime

| 问题 | 说明 |
|---|---|
| iOS 引擎 | 基于 Apple JSC，**JIT 被官方禁用**；2020 年改为 V8 JIT-less 绕开此限制 |
| 我们 | 用 JSC（现状）/ 评估 Hermes / QuickJS——**不存在它当年要绕的那个问题** |

**它的 runtime 是为一个我们不存在的问题设计的。**

### 7.2 ✅ 可借：两项设计

| 项 | 说明 |
|---|---|
| **Metadata 预生成** | 编译期从 SDK 头文件生成元数据，嵌入包内，运行时高效读取 |
| **Marshalling 服务** | 平台类型 ↔ JS 类型的双向转换设计 |

**借这两项，产出静态绑定代码（§5 腿一）。**

### 7.3 ⚠️ 生态风险

作为长期依赖需谨慎：npm 周下载约 8.8k（评级 Small）、近一月零新增 PR、
维护者 3 人；有资料称 Vue 版维护停滞。

**结论**：参考其设计，**不作为依赖**。

## 附：关键事实依据（来自前序调研）

**竞品现状**
- React Native：TurboModules（基于 JSI）+ Codegen 生成类型安全绑定；按需加载；已是新架构默认（0.76+ 起）
- Expo SDK：**100+ 原生模块**；有资料称 SDK 52 覆盖 **95%+ 常用原生 API**
- Expo 官方称：自定义模块 wrapper 编写约 **8 小时**工程时间
- Capacitor / NativeScript：本身即以解决原生接入为定位

**NativeScript**
- iOS runtime 基于 Apple JSC，**官方确认 JIT 在 App Store Apps 中被禁用**
- 2020 年将 iOS runtime 从 JSC 换为 **V8 JIT-less**（绕开 JIT 限制，有性能损失）
- Metadata：编译期从 SDK 头文件生成，嵌入包内，提供高效读取
- Marshalling：处理 ObjC/Java 与 JS 的类型转换
- 生态活跃度：npm 周下载约 8.8k（评级 Small）、近一月零新增 PR、维护者 3 人

**JSI 特性**
- HostObject：JS 直接持有 C++ 对象引用，无序列化、同步调用
- TurboModules：基于 JSI，Codegen 生成类型安全接口，按需加载
- 细粒度同步调用是其优势，但与批处理红线存在张力

> **注**：以上均引自前序调研，凡涉及具体数值（如 95%、8 小时）**应在实施前复核**。
> 部分来源权威性有限，不用于对外宣称。
