# Proteus 万神殿命名规范

> **定位**：本仓**模块/方案代号**的命名**单一事实源（SSOT）**。此前万神殿一直是**习惯命名**（散落在各方案文档的 §1、`board-inventory`、决策链里），**从未有正式规范**；本文件把它**成文 + 汇总总览 + 定义纳名纪律与流程**。
> **关联**：`docs/board-inventory.md`（架构全景索引）· `docs/proteus-architecture.md`（L0 规约）· 各 `docs/Proteus_*方案.md` 的 §1 命名节（**本文件是其上位规范**）。
> **状态**：v1（2026-10-13 立 · 决策 #879）。
> **不适用**：代码标识符命名（那是 ESLint/TS 的事）· G-\* 计划编号（见 §8）· 对外品牌名（见 §3 备注，如 Proteus UI）。

---

## §0 一句话 + 为什么立

**一句话**：本仓的模块代号取自**希腊/罗马神话**，且**「神职即模块职责」**——选一个神，其**神职**恰好对应这个模块在框架里的**职责**。

**为什么立**（用户 2026-10-13）：
- 万神殿**一直是习惯命名**（谁起方案谁自己选词），**没有成文规范** ⇒ 新模块命名靠"记得要对齐"，容易破例（**反例**：液态玻璃组件库初稿用了 `Hyaleos`/`Krystallos` = "玻璃/水晶"**材质普通名词**，破了"神名"轴，被用户当场指出 ⇒ 决策 #878 改 `Aether`）。
- 也**没有总览** ⇒ 每起一个新方案都要 grep 全仓找"哪些名字被占了 / 哪些被排除了"。
- ⇒ 本文件**一次收口**：命名轴 + 纳名纪律 + **总览** + **排除名单** + **新命名流程**。

## §1 命名轴与三条硬纪律

### 1.1 命名轴：**神职即模块职责**

> 权威原话（`docs/Proteus_OS级组件库方案.md:32`）：
> 「框架名 **Proteus**（千变万化）、动画引擎 **Kairos**（时机/时间轴）、CSS 引擎 **Themis**（裁决与律法）、能力组件 **Hephaestus**（锻造）——本命名体系的**语义轴是「神职即模块职责」**。」
>
> ★**代号更名记录（2026-10-20 · 决策 #1108）**：动画引擎原名 **Morpheus**（梦神，morph- 形变词根），
> 但 npm 上 **`morpheus` 这个包正是「A Brilliant Animator」**（JS 动画库，与我们的领域完全重合），
> 另有 `alexk111/SVG-Morpheus`（2.7k★，SVG 图标 morphing）——按 §2 第 4 问「相关领域有知名同名项目 ⇒ 排除」
> （同 Iris/Athena 先例）**必须排除**。⇒ 改用 **Kairos**（καιρός，时机之神）：
> 动画的本质是「在正确的时间产生正确的变化」——**时间轴、缓动、编排**都是"时机"问题，神职对得上且更贴切。
> ★`Kairos` 的 npm 占用为 "A non date-based time calculator"（时间计算器，非动画/UI 域）⇒ 不构成排除。

**选名方法**：先定位模块的**职责**，再找**神职**与之契合的神话名。例：动画引擎 = 时间轴上的变化 → **Kairos**（时机之神，καιρός = 恰当时机）；CSS 引擎 = 裁决/律法 → **Themis**（正义女神）；图标库 = 传令 → **Keryx**（传令官）。

### 1.2 三条硬纪律

| # | 纪律 | 说明 |
|---|---|---|
| **N-1 神名** | **万神殿只收神话神名**（神祇 / 泰坦 / 原初神 / 缪斯 / 神话人物为主；神话生物可，须标注）。**不收**：普通名词 / 材质 / 建筑 / 拉丁语破例 / 技术术语 | 出处：`docs/proteus-performance-plan/15-dactyl-demo.md`（"万神殿只收神话神名"）；反例 `Hyaleos`(#878) |
| **N-2 体系内不得撞名** | 同体系内**一名一模块**；一个名字一旦登记，**别名/备选被别处占用即须排除** | 出处：`docs/Proteus_Themis多端一致CSS引擎产品白皮书.md:42`（Argus 被 Mnemosyne 占用 ⇒ Themis 排除之） |
| **N-3 定名前须商标与包名检索** | 每个代号**定名前**做正式商标与包名检索；**检索通过前不入万神殿已定名清单**（标注"暂定/待检索"） | 出处：各方案头部固定句 + `docs/Proteus_业务代码跨端调试方案.md` R7 |

### 1.3 破例的三种合法形态

- **神话生物**（非神祇）：如 **Chimera**（嵌合体，三方游戏引擎兼容层）——可，但 §3 标注"生物"。
- **语言学/专有名词**（显式破例）：如 **Koine**（κοινή，"共同语"）——**须显式标注"破例 · 非神名"**并写理由（"本层是'语'不是'神'"）。
- **对外品牌名**：可不同于工程代号（如 `Proteus UI` 对外 / `Charites` 对内）——登记时两列并列。

## §2 纳名标准（判"这个名能不能进万神殿"）

按顺序自问，全过才可登记：

1. **是神话名吗？**（N-1）——普通名词/材质/技术术语 ⇒ **否**（除非按 §1.3 显式破例）。
2. **神职对得上模块职责吗？**（§1.1）——对不上 ⇒ 换名，别硬套。
3. **体系内撞名吗？**（N-2）——检查 §3 总览 + §4 排除 + §6 备选；撞即排除。
4. **外部撞名吗？**（N-3 检索）——前端/跨端/相关领域有知名同名项目 ⇒ **排除**（同本仓 Iris/Athena/Theia 先例）。
5. **可寻址吗？**——过短的泛词（`Logos`/`Eos`）⇒ 排除（检索不可靠）。

## §7 新命名的标准流程（七步 · 不得跳步）

1. **定神职**：一句话说清这个模块在框架里的**职责**（§1.1）。
2. **拟候选**：找 2–3 个**神职契合**的神话名（含备选）。
3. **查仓内**：`grep` 全仓（§3 + §4 + §6）；撞名/撞备选 ⇒ 排除。
4. **查外部**：前端/跨端/相关领域检索知名同名项目（Iris/Athena 先例）；领域相近的**一律排除**。
5. **过纳名判据**（§2 五问）。
6. **登记**：在本文件 **§3 总览**加一行（代号 · 神职 · 模块 · 状态 · 出处）；同轮在方案文档 §1 写命名论证。
7. **检索 + 状态**：完成商标与包名检索后才标 ✅；未检索 ⇒ 🟡/🔵，**不得对外**。

## §8 与编号体系的关系（两套并行，勿混）

- **G-\* 计划编号**（`board-inventory`、`check-consistency`）是**执行序**编号，有独立"编号避让"纪律（撞号重编）。
- **神名代号**是**命名**体系，与本文件纪律。
- **两者唯一交点**：多数神名方案**不占 G 序**（登记在 `board-inventory` 方案区块）；**Themis = G-61 的产品白皮书**（唯一与 G 号强绑定）。
- ⇒ 命名规范**不管 G 编号**；G 编号避让见 `board-inventory` §更新规则 与 `scripts/check-consistency.js`。

## §9 门禁（接线不靠记忆）

- **当前**：本文件为**成文 SSOT**；尚无自动门禁（命名是人判 + 检索，机器难以判定"神职契合"）。
- **可机器化的部分（后续评估）**：① 每个 `docs/Proteus_*方案.md` 头部自报的**代号**出现在本文件 §3；② §3/§4/§6 三者**无重复名**（同一名不得同时在"已登记"与"排除"）。若落地，接 `check:pantheon-naming`。
- ★**纪律（对齐本仓文化）**：规范的"可判定部分"应有门禁；"不可判定部分"（神职契合、商标检索）如实标注为**人判**（§10 诚实边界）。
