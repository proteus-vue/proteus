# Proteus 架构收敛模型说明

> 定位：**回答一个架构层面的问题——为什么 Proteus 规避了传统跨端框架的「端对齐无底洞」**
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4 / 微信基础库 2.29.2+）
> 仓库：https://github.com/proteus-vue/proteus
> 阅读对象：新人建立全局认知、对外讲架构、以及判断收敛模型是否已稳定
> 本文不是实现规格，实现规格见各分册（架构总纲 §1）

---

## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 传统跨端框架的复杂度 | **O(N × M)**（源特性 × 目标端） |
| Proteus 的复杂度 | **O(N) + O(M)**（先收敛，再分发） |
| 这个差别是优化吗 | **不是。是复杂度模型换了，量级差异** |
| 真正的机制 | **从"无限输入空间"收敛到"有限封闭集"** |
| 是否完全没有洞 | ❌ **不是。洞被前置到编译期，变成确定的、可枚举的失败** |
| 最大风险 | **收敛点（185 原语）选错时，纠错成本高于不收敛** |

## 1. 传统跨端框架的无底洞：数学来源

设源特性集合为 **S**（Vue 语法 + CSS 组合），目标端数为 **T**。

### 1.1 传统做法：源端直接到目标端

```
每个端都要重新遍历 AST，为 |S| 个特性各写一份映射
   → |S| × |T| 份映射
   → 且端间行为还要互相对齐：C(|T|, 2) 组比对
```

五端即 **5 × |S|** 份映射 + **10 组**端间两两比对。

**而 |S| 是开放集**——CSS 特性在增长，Vue 语法的组合方式无穷。
这就是"无底洞"的数学来源：**无限输入空间 → 有限目标能力，必然有落空的，且不知道在哪。**

### 1.2 三个根源，逐条对照

| 根源 | 传统框架 | Proteus |
|---|---|---|
| **① 源端语义无边界** | 每端都要复刻浏览器 CSS，永远复刻不完 | **CSS Profile 编译期封闭**；Web 端 lint 是设计要求但**尚未落地**（`Proteus_CSS_Profile规格.md` P6 = ❌ 未实现，见 §7.1） |
| **② 端间两两对齐** | `C(|T|,2)` 组人工比对 | **全部对齐到 IR 一个点，只需 |T| 次** |
| **③ 缺乏验证机制** | 靠人肉发现不一致 | **每层 SPI 都有 conformance（32–42 项），CI 自动校验** |

## 2. Proteus 的三层收敛

**这是本文的核心。收敛不只发生在一层，而是三层。**

| 层 | 收敛什么 | 后端面对的复杂度 |
|---|---|---|
| **① 185 语义原语** | Vue 语义 → 有限语义集（`PRIMITIVE_CATALOG` 为 SSOT） | 185 个概念 |
| **② RenderCmd 线性指令流** | 语义 → 绘制指令 | **一组指令，不需要理解语义** |
| **③ 拍平不产生独立指令** | 节点数 → 指令数解耦 | 2 万节点 → 24 个节点级开销 |

### 2.1 为什么"从无限到有限"是真正的机制

传统框架遍历的是 **AST**——AST 是**语法层**，语法是开放集。

Proteus **遍历 AST 只有一次**，产出**语义 IR**——语义 IR 是**封闭集**（185 个原语）。
之后所有后端面对的都是"有限 → 有限"。

> **从无限到有限的这一步，才是规避无底洞的真正机制。**
> conformance、双端 Golden、81 个 Capability Hook，都是建立在这个封闭集之上才可能存在——
> **如果输入空间是开放的，根本没法写出完备的 conformance 套件。**

### 2.2 第 ② 层是 App 端能快速做出来的直接原因

App 端实现的是一个**指令解释器**，它**完全不需要理解 185 个原语的语义**。

这也解释了为什么 **Flutter widget 映射后端（传统路径）** 与 **Native 后端（指令路径）** 能共存：
前者是兜底，后者才是真正的路线。

### 2.3 第 ③ 层的正确性（架构不变量）

`render-cmd.ts` 中"拍平节点不生成独立绘制指令"——
即拍平节点的绘制**并入父级的绘制序列**，而非合成一张新位图。

这正是"2 万元素 → 24 个 RenderNode"的来源。

> ⚠️ **必须写为架构不变量**（与"不自绘"同级）。
> 一旦被破坏，iOS 上曾出现的 +78% 内存会以**更难查的形式**复发——
> 节点数仍是 24，但每个节点的 backing store 变大了。

## 3. RenderCmd 设计的关键选择

### 3.1 绝对坐标（而非变换矩阵栈）

常规做法（Flutter / Skia）是变换矩阵栈 + 相对坐标。Proteus 选绝对坐标，三个收益：

| 收益 | 说明 |
|---|---|
| **① 无状态，天然可裁剪** | 每条指令自带坐标 → 按包围盒过滤视口外指令，无需维护变换栈 |
| **② 可合并** | 同色相邻背景合并为一次 `drawRect`——邻接关系直接从坐标算出 |
| **③ 可测** | 指令流自包含，golden test 可直接比对字节，不依赖执行顺序与状态 |

**① 直接服务于当前唯一瓶颈**：4050 场景里绘制已是最大单项
（绘制 **6ms** vs 布局 **5ms**，`hosts/android/results/acceptance/` 实测）；
列表场景绘制 p95 **5ms**，占 120Hz 帧预算 8.33ms 的 **60%**。
而绘制侧优化的第一条就是 **overdraw culling**——绝对坐标让这件事变成一次坐标比较，而非栈回溯。

### 3.2 必须定死：舍入时机

绝对坐标有一个隐蔽的跨端陷阱。鸿蒙**强制整数像素**
（`flex:1/3` 三列布局时，ArkUI 把 0.333 舍为 0.33，累计误差导致第三列错位）。

| 方案 | 后果 |
|---|---|
| 平台层各自舍入 | 三端策略不同，**误差不可复现、不可测** |
| 内核产出指令时就舍入 | 统一策略；但需改动已定案的主方案条文 |
| **布局保留浮点、写入平台层时统一舍一次**（主方案 §5.5.2 **现行条文**） | 同样统一，且舍入点唯一、可复现 |

★**本节与 `Proteus_App端高性能渲染落地方案.md` §5.5.2 现行条文冲突，属待决策项**：
主方案已标注「M1 定案，不可延后」，要求「布局计算保留浮点，仅在最终写入平台层时做一次舍入」，
且其检查清单中「跨端舍入策略定案」仍为未勾状态。§5.5.2 真正**禁止**的是「平台层各自舍入」——
本节原表格把后者设为唯一对照，掩盖了两方案的同源关系。
⇒ **处置：在正式改主方案 §5.5.2 之前，以主方案为准**（本节仅作决策输入，不自动生效）。
无论采用哪种，"舍入唯一且三端一致"这一要求不变——否则指令流 golden test 全绿、三端画出来差 1px。

### 3.3 paint-hint 必须编码进指令

内存专题定义的 `isMonochrome` / `isPureBackground` / `shareableContent`
是**编译期推导**的，必须成为指令属性，平台层据此决定 backing store 策略。

否则平台层要在运行时猜——**而猜的代价就是那个 78%。**

## 4. 收敛带来的连锁收益

### 4.1 平台适配层被压缩到极薄

指令流平台无关 → 每个平台只需实现一个**指令解释器**。
`platform/` 层剩下：文本度量、指令执行、原生组件挂载。

**鸿蒙端接入成本显著降低**，对 M5 排期是利好。

### 4.2 Host ABI 的批处理红线天然满足

指令流本身就是一批（`proteus_submit_frame(op_buffer, byte_len)`），
**跨边界调用次数 = 帧数**。这条验收项自动达标。

### 4.3 可以每帧全量生成指令

既然全量重排已有 0.08ms 的实测（**vapor + 兄弟平移特调**这一特化路径；
整体重排见 Vapor `relayout` **17.16→1.52ms**），指令流也可**每帧全量生成**，
不需要增量指令生成逻辑——这是"全量重排变成可接受兜底策略"的自然延伸。

> **但需先测一个数**：拍平后每帧的指令条数是多少？
> 若降到几百，全量生成毫无压力；若仍有数千，需计算生成 + 跨边界传输成本。
> **这个数字同时也是绘制侧优化的分母**——culling 与合并的收益上限由它决定。

## 5. 它解决不了的问题（必须诚实）

**指令流保证的是"画什么"一致，不保证"画出来一样"。**

圆角裁剪边界、阴影合成、文本基线——各平台渲染管线行为不同。
这是**原生渲染路线的固有代价**（也是当初拒绝自绘换来的可融合生态优势）。

**只能靠 conformance 门禁兜底**：用浏览器的 `getComputedStyle` /
`getBoundingClientRect` 作真值基准比对。

> 好消息：一致性实测 **0.375 dp**（合格线 0.5），说明这套兜底目前有效。

## 6. 三个风险指标（★ 建议持续监控）

### 6.1 风险一：收敛点选错（最大风险）

**代价**：若发现某个 Vue 特性无法用现有原语表达，要么
**扩原语（所有端都要改）**，要么放弃该特性。

**传统框架没有这个问题**——它可以给某个端单独打补丁。

> **收敛点一旦定错，纠错成本高于不收敛。**

**监控指标**：**扩原语的频率**。
若该数字持续不为零，说明收敛集尚未稳定。

### 6.2 风险二：185 原语 vs 77 个组件（65 个已实现语义）

这个落差需要确认（口径：`check:stats` 的 components = 77 个组件目录 ·
implemented = 65 个已实现语义——后者指在 **≥3 端**有映射的原语）：

- 若剩余的是**不需要落地的内部原语**（Hook / 路由方法等**不产生 C-IR 节点**）→ 正常
- 若是**尚未完成** → "五端对齐"的成色要打折

**建议**：`proteus audit coverage` 已给出机器可读分类（官方 382 项：
已落地 252 · 规划 4 · 私有 106 · 不适用 20）——文档引用该口径即可，不必手写数字。

### 6.3 风险三：81 个 Capability Hook

Hook 是**原语层无法覆盖时的逃逸口**。

> **Hook 越多，说明收敛模型的漏点越多。**

它不是缺陷，但它是"185 原语覆盖得够不够"的**体温计**——
建议作为**持续监控项**，而非静态配置。

## 7. 对外表述：一个容易被误读的点

| ❌ 错误说法 | ✅ 正确说法 |
|---|---|
| "我们没有端差异问题" | **"端差异在编译期就被拦住了"** |
| "规避了无底洞" | **"把洞前置到了编译期，变成确定的、可枚举的失败"** |

**为什么重要**：

- 传统框架：运行时发现行为不一致 → 在 5 个端上分别调试 → 无底洞
- Proteus：编译期报错，明确告知"该特性不在 Profile 内" → 有底

**准确表述才是可验证的**。说"我们没有端差异"会被真机测试打脸。

### 7.1 顺带：Web 端 lint 不可省略

Web 端由浏览器自然支持全部 CSS。若不拦，
开发者写出的 Profile 外样式在 Web 端照常渲染、**App 端才不一致**——
**问题被延迟暴露**，那"编译期封闭"就名存实亡。

**这条设计是对的，但容易被省略，需明确写进执行约束。**

## 8. 一页速览

```
传统跨端
  Vue 源码 ──→ 端 A 映射 ──→ 端 A
          ├─→ 端 B 映射 ──→ 端 B      |S| × |T| 份映射
          └─→ 端 C 映射 ──→ 端 C      C(|T|,2) 组人工比对
  输入空间开放 → 无底洞

Proteus
  Vue 源码
     ↓ 遍历一次 AST
  185 语义原语（封闭集，SSOT）
     ↓ 编译期收敛
  RenderCmd 线性指令流（绝对坐标、平台无关）
     ↓ 拍平：不产生独立指令
  各端只需实现指令解释器
  端间对齐 → conformance 自动校验（各层 32–42 项）

复杂度：O(N) + O(M)，不是 O(N × M)

代价与风险
  ├─ 收敛点选错 → 纠错成本高于不收敛
  ├─ 洞被前置到编译期（确定、可枚举），不是消失
  └─ 指令流保证"画什么"一致，不保证"画出来一样"
        → 靠 conformance + 浏览器真值基准兜底（当前 0.375 dp）
```

## 附：关键事实依据（来自仓库与既有实测）

- 仓库结构：43 个 `@proteus-vue/*` workspace 包；`compiler`（111 条规则 + apply 分派层）、`compiler-backend`（CompilerIR 契约 + NodeBackend + 双端等价 Golden）、`compiler-backend-rust`（cargo crate `proteus-cc-rust` → 同一 CompilerIR）、`render-backend`（渲染 SPI + 五后端 + 混合渲染 + 宿主层）
- CompilerBackend SPI：parse / transform / emit 三阶段 + `IncrementalSession` 增量 + `FallbackBackend` 自动降级；conformance 42 项
- RenderBackend SPI + conformance 门禁；五官方后端：Headless / VueDom / Native×3 / Flutter widget 映射
- 185 语义原语清单（`PRIMITIVE_CATALOG` 单一事实源）→ 77 个组件目录（`check:stats` 口径）· 65 个已实现语义（`implementedPrimitives()`）；81 个 Capability Hook；编译期门禁
- 宿主层：`hostRoot` Host Runtime（bootstrap / worker / engine / native 桥）、六容器策略可插拔、所有权/借用检查、`ExecutionCarrier`（JSI / AOT）
- 验证先于运行：Render / Compiler / Host / Container / Ownership / Test 各层 conformance 32–42 项，CI 自动校验
- 转场预设：`halfScreen` / `slideUp` / `scaleDown`，配置于 `proteus.config.ts`，可用微信预设 `routeType: 'wx://bottom-sheet'`
- 既有实测：布局 0.063 / 绘制 **2.0**（★口径更正：0.667 系「只画色块」子项，整体 6ms vs 原生 3ms；中端机 0.583）；内存增量 0.328；一致性 0.375 dp；长列表 124.5 FPS、复用率 0.997、掉帧 0.16%；RenderNode 创建 24 / 复用 7941；全量重排 0.08ms（**vapor + 兄弟平移特调路径**——整体重排 17.16→1.52ms）；宿主侧 1ms
