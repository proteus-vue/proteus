# Proteus 多端一致性标准方案 v1

> 目标：**建立一套超越 Flutter 的多端一致性标准**——不是"更一致"，而是**可验证的一致**。
> 本方案同时承担一项前置任务：**消除"自绘"一词的歧义**，因为它在鸿蒙方案、Morpheus 方案、桌面端方案、叙事文档中反复出现，若定义不统一，几份文档的论述基础会互相打架。

---

## 0. 一句话结论

**Flutter 的一致性是被假定的，Proteus 的一致性是被验证的。**

Flutter 自建渲染管线，天然假定"同一套代码画出来就一样"——但这个假定已被多次击穿（见 §5.1）。
Proteus 复用系统管线，差异客观存在，但**这些差异可枚举、可声明、可机器判定**。

行业真正缺的不是"更一致"，而是**"能证明自己一致"**。这是 Proteus 可以拿走的标准制定权。

---

## 1. 术语定义（本标准的基础，优先级最高）

### 1.1 "自绘"的准确定义

**自绘 = 是否使用原生渲染管线**，而不是"是否自己实现 UI 框架"。

这是一个关键澄清。此前多份文档混用了"不自绘"一词，容易被误解为"我们不做 UI 框架、直接用系统控件"——这与事实相反，会直接削弱架构叙事。

### 1.2 三层拆分（必须分开表述）

| 层 | 说明 | Flutter | Proteus |
|---|---|---|---|
| **L-A 控件树层** | 是否使用系统原生 View / UIView / ArkUI 组件 | ❌ 绕开 | ❌ **绕开** |
| **L-B 布局计算层** | 谁算几何 | 自己（Dart） | **自己（Rust 内核）** |
| **L-C 光栅化层** | 谁把指令变成像素 | **自己（Skia / Impeller）** | **系统（RenderThread / CoreAnimation / RS / 浏览器）** |

### 1.3 由此得出的三个结论

**① 在 L-A 层，Proteus 与 Flutter 是同一条起跑线。**

原生控件树的碎片化（厂商定制、系统版本差异、默认样式漂移）才是"打地鼠无底洞"的真正来源。这一层两家都已跳出——RN / uni-app / Taro 没有，所以它们承受了全部成本。**这一条必须在对外材料中讲清楚，它是"彻底规避节点映射"的准确含义。**

**② 在 L-B 层，两家都是单点计算，几何天然一致。**

**③ 在 L-C 层，两家路径不同，且这是差异的唯一真实来源。**

| | L-C 实现 | 后果 |
|---|---|---|
| Flutter | Skia / Impeller 统一实现，后端差异仅收在 GPU API 绑定层 | 一致性来自"统一实现" |
| Proteus | 四份独立系统实现（Android / iOS / 鸿蒙 / Web） | 一致性需"被验证" |

**这个差别不是劣势**——见 §3。

### 1.4 一致性目标的重新定义

| 目标 | 判定 | 说明 |
|---|---|---|
| **逐像素一致** | ❌ **不立** | Flutter 自绘也未达成（§5.1）；且追求它会逼我们放弃系统管线 |
| **可验证的一致性** | ✅ **立此目标** | 差异可枚举、可声明、可机器判定 |

## 2. 差异来源全图

理解这张图，才知道哪些差异值得修、哪些必须接受。

```
开发者表达（Vue 模板 + CSS + 动画声明）
        │
        ▼
① 编译期差异   各端 CSS/WXSS 支持度不同         → L1 静态校验
        │
        ▼
② 布局差异     Rust 内核单点计算               → 无差异（L-B 层已解决）
        │
        ▼
③ 文本度量差异 各端字体度量引擎不同             → 唯一需容差带的结构性差异
        │
        ▼
④ 光栅化差异   抗锯齿 / 阴影 / 色彩空间 / DPR   → L4 像素层，不可消除
        │
        ▼
⑤ 运行时行为差异 滚动惯性 / 动画插值 / 手势     → 设计使然，须显式登记
```

**关键判断：①②④⑤ 全部可枚举，只有 ③ 是真正不可消除的结构性差异。**

## 3. 与 Flutter 的分维度诚实对照

对外材料必须能用这张表，**承认不如它的地方**。把短板说清楚，长板才有人信。

| 维度 | Flutter | Proteus | 判定 |
|---|---|---|---|
| **控件树碎片化** | 绕开 | 绕开 | ✅ 平手（同起跑线） |
| **布局几何** | Dart 单点计算 | Rust 单点计算 | ✅ 平手 |
| **文本度量** | Skia 统一度量，但 **fallback 依赖平台 SkFontMgr** | 平台注入（StaticLayout / CoreText） | 🔴 **Flutter 更一致**（但见 §5.1：它也没做到） |
| **像素绘制** | 自绘统一 | 系统管线，抗锯齿/阴影各异 | 🔴 **Flutter 更一致** |
| **可验证性** | 像素 golden，官方承认跨端 flaky | **L1–L3 数值比对，机器判定** | 🏆 **Proteus 远超** |
| **差异可枚举性** | 硬编码平台 switch，不可声明、不可测试 | **可声明、可枚举、可测试** | 🏆 Proteus 更优 |
| **差异空间大小** | `CustomPainter` 开放，开发者可画任意内容 | 183 原语封闭集 | 🏆 **Proteus 更小** |
| **排版能力** | 弱（蒙古文 / 竖排 / 沿路径文本不支持） | 平台注入，站在原生能力上 | 🏆 Proteus 更优 |
| **原生生态融合** | PlatformView 两层合成，Impeller 时代有回归 | 无两层合成问题 | 🏆 Proteus 更优 |

### 3.1 两个容易被忽略的优势

**① 封闭集 vs 开放表达**

Flutter 有 `CustomPainter`——开发者能画任意东西。这是自由度，也是**不一致的入口**。
Proteus 的 183 原语是封闭集，开发者画不出集外的东西。

> **在"什么能被表达"这一层，Flutter 是开放的，Proteus 是封闭的——Proteus 的差异空间反而更小。**

**② 语义级指令 vs 绘制命令**

```
Flutter：drawRRect(rect, radii, paint)   ← 像素级绘制命令
Proteus：cornerRadius = 8dp              ← 语义级属性
```

语义级可以**数值比对**（8 就是 8）；绘制命令只能**位图比对**（所以 Flutter 需要 golden test，所以才 flaky）。

> **Proteus 的指令流天然是可验证的结构，Flutter 的不是。**
> 这不是"谁更一致"的问题，是"谁能证明自己一致"的问题。

## 4. 可借鉴的三点（来自 Flutter）

### 4.1 Golden file 的基线管理流程

Flutter 有 `matchesGoldenFile` + `--update-goldens`：基线入库、变更需人工评审 diff、CI 强制比对[citation:53][citation:65]。

**借鉴概念，替换实现**：

| Flutter | Proteus |
|---|---|
| 基线是 PNG 位图 | **基线是数值快照（JSON）** |
| 变更评审看图片 diff | **变更评审看数值 diff**（第 N 个节点 left 偏差 3.5px） |
| CI 精确匹配，否则失败 | **CI 分级容差，分级门禁** |

流程骨架（基线入库 / 人工评审 / CI 强制）**完全可复用**，这是 Flutter 工程实践里最值钱的部分。

### 4.2 测试时锁定确定性字体

Flutter golden test 默认使用 `Ahem` 测试字体——方块字形，**度量完全确定**，用来消除文本不确定性[citation:53][citation:62]。

**这一招 Proteus 可直接采用**：

- 跑 L2 几何校验时**锁定测试字体** → 文本度量差异被消除 → **几何校验变成完全确定的**
- 文本的真实差异**另行单列**，走容差带（§9）

这样做的好处是：**把"不可消除的差异"和"可消除的差异"彻底分离**，让 L2 具备 100% 确定性。

### 4.3 显式建模平台差异

Flutter 官方 `ScrollBehavior.getScrollPhysics()` 直接 switch 平台：iOS 返回 `BouncingScrollPhysics`、Android 返回 `ClampingScrollPhysics`、macOS 另有 desktop physics[citation:60]。

**这正是 VC5-d「允许差异清单」的原型**——Flutter 也承认差异存在并建模了它。

**但 Flutter 把它硬编码在框架里**：开发者无法声明、无法枚举、无法测试。
**Proteus 做成可声明的**，就比它高一档：

```ts
// Proteus：差异是数据，不是代码分支
allowDifference.register({
  id: 'scroll-edge-behavior',
  category: 'runtime-behavior',
  reason: '平台滚动手感规范不同，属设计使然',
  scope: 'scroller 组件 / 边界交互',
  evidence: 'VC5-d 附录 A-3',
})
```

## 5. 不可借鉴的一点：像素 golden

### 5.1 官方自己承认它 flaky

`LocalFileComparator` 官方文档（权威性极高）：

> "performs a **pixel-for-pixel** comparison... returning true **only if there's an exact match**"[citation:62]

`matchesGoldenFile` 文档明确警告：

> "Custom fonts may render differently across different platforms... a golden file generated on Windows will likely differ from the one produced on another operating system"[citation:53][citation:65]

社区的全部解法都是妥协：

| 解法 | 实质 |
|---|---|
| 只在 Linux CI 生成 golden | 放弃本地可验证性 |
| 自定义 comparator，0.5% 像素容差 | 放弃精确性[citation:59] |
| 锁定字体 / 主题 / surface size / DPR | 大量环境固定成本[citation:56][citation:50] |

**这正是"用非确定性系统验证非确定性系统"的经典死法**：误报 → 人工分辨噪声 → 静音告警 → 放弃。

**结论：像素 golden 不但不能抄，它恰恰是本方案的对照靶子。**

### 5.2 ★ 更重要的发现：Flutter 自绘也做不到逐像素一致

这条是校准目标的关键依据（**案例权威性标注见下**）：

**案例 1（权威性较低，但技术链条完整）**：Flutter 3.38 升级 Skia，commit `a918c0e` 重构了 `find_family_style_character` 的字体 fallback 逻辑——当 familyName 为空时跳过 `fFallbackFor` 检查，导致 **NotoSerifCJK 先于 SECCJK 被命中，中文被渲染成宋体（衬线体）**。且**只影响三星 / OPPO / OnePlus**，小米与模拟器不中[citation:52]。

**案例 2（权威性中等）**：iOS 18 苹果改了苹方设计，系统里现在存在两套苹方（"苹方"与"新苹方"）——**同一份 Flutter 代码，西文的"2"和"y"在不同 iOS 版本上显示不同**[citation:55]。

**案例 3（权威性中等）**：`TextLeadingDistribution` iOS 默认 proportional、Android 默认 even → 16sp 文本行高差 2px[citation:61]。

**案例 4（权威性极高）**：Flutter 3.29 才在 iOS 移除 Skia、3.38 才在 Android 废弃 opt-out——**各端引擎切换本身就不同步**。

> **结论：跨端像素级一致是伪命题，自绘也达不到。**
> Flutter 自绘了排版，但字体 fallback 依赖平台 `SkFontMgr`——一致性同样被平台、设备、甚至 OS 版本击穿。

**这条正是「可验证一致性」这个目标的立论基础**：既然没人能做到绝对一致，行业真正需要的就是"能证明自己一致到什么程度"。

## 6. 可验证一致性指标体系

**Flutter 没有公开的、可量化的一致性标准。谁先定义，谁拿标准制定权。**

### 6.1 四项核心指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **M1 数值一致性覆盖率** | L1+L2+L3 覆盖的属性数 / 全部可表达属性数 | 逐阶段提升，公开报告 |
| **M2 允许差异条目数** | VC5-d 清单条目数 | 越少越好，**每条必须有理由与证据** |
| **M3 CI 门禁通过率** | 每端每 build 的校验通过率 | 100%（不通过即阻断） |
| **M4 一致性回归检出率** | 注入人为缺陷后的捕获率 | **见 §7，最重要** |

### 6.2 指标必须公开报告的理由

M1 与 M2 是**自曝短板**的指标——覆盖率低、差异条目多，数据会不好看。

**但必须公开**，理由有三：

1. 不公开就等于没有标准，只是内部工具
2. 公开才能形成"逐阶段改善"的可信轨迹
3. **竞品无法对等地给出这四个数**——这是不对称优势

## 7. 变异测试（本方案最硬的一块）

### 7.1 为什么必须有

**"我们有校验"是一句声称；"我们的校验能捕获什么"才是证据。**

没有变异测试，M1–M3 都只是自说自话。而**这是 Flutter golden 做不到的**——因为它 flaky，团队早就静音告警了。

### 7.2 设计

```
注入人为缺陷 → 跑校验 → 看是否捕获 → 统计捕获率（M4）
```

**变异算子清单（建议至少覆盖）：**

| 变异 | 注入方式 | 期望被哪层捕获 |
|---|---|---|
| 颜色偏移 | `#FF0000` → `#FE0000` | L3（颜色类极严格容差） |
| 间距偏移 | `margin: 8dp` → `11dp` | L2 几何 |
| 圆角缺失 | `border-radius: 8` → `0` | L3 或 L4 |
| 字体回退 | 指定字体 → 系统默认 | L3 计算样式 |
| 层级错位 | `z-index` 调整 | L2 层级字段 |
| 单端降级 | 仅某端走 fallback 分支 | L1 编译期静态 |
| 滚动位置偏移 | 连续交互后相对间距改变 | L2.6 不变量 |

### 7.3 判据

**M4 未达标的变异算子，必须在指标报告中单列并说明原因**——不能悄悄删掉难测的算子。

### 7.4 一个必须设计的"反例变异"

**故意注入一个真实高危缺陷：按钮变色（小面积、易被噪声淹没）。**

这是传统方案漏报的根源场景（§8.2）。**如果这套校验捕获不了它，那它就不比截图比对强。**

## 8. 像素比对：非门禁的观察模式

### 8.1 做法

在 CI 中**锁定设备、DPR、测试字体**，跑一轮像素比对：

| | 设置 |
|---|---|
| 门禁 | ❌ **不做门禁**——避免 flaky 复现 Flutter 的老路 |
| 用途 | ✅ **只统计差异率并出报告** |

**收益**：既拿到了"像素层面也很好看"的证据，又不承受维护成本。
**这比 Flutter 的"精确匹配否则失败"高一档**——Flutter 只能二选一，我们可以两者都要。

### 8.2 ★ 必须写死的容差设计约束

**禁止全局差异阈值。**

一个 50×20 的按钮变色，在全高清页面上只占约 **0.001%** 的像素。若使用 0.01% 的全局阈值，**必然漏报**。

这正是传统视觉回归方案漏报的根源——一个大阈值同时放过了噪声和真 bug。

**必须按属性分级 + 可声明：**

| 属性类 | 容差 | 理由 |
|---|---|---|
| 结构类（位置 / 尺寸 / 层级） | 严格（如 ±0.5dp） | 确定性高 |
| 颜色类 | **极严格（±1/255）** | 真 bug 高发区，且最易被噪声淹没 |
| **文本度量** | **唯一允许宽带** | 三端度量引擎天然不同，不可消除 |
| 圆角 / 阴影 / 渐变 | 不比数值，走 L4 像素观察 | 非确定性，见 §10 |

## 9. 允许差异清单（VC5-d）

### 9.1 与 Flutter 的本质区别

Flutter 把平台差异**硬编码进框架 switch**[citation:60]；
Proteus 把差异做成**可声明的数据**，且每条必须带理由与证据。

**清单内差异不判失败；清单外一律当 bug。**

**硬约束**：
- 不得为"让测试通过"而新增条目
- 新增条目必须写明理由、范围、证据，并经评审
- 清单条目数本身是对外指标（M2）

### 9.2 ★ 本轮新增的一条：动画插值中间态

**来源**：Morpheus §5-bis 的转场方案——"提交一次 + RenderThread 自主插值"。

**问题**：中间帧是**平台算的**。跨端插值曲线不同 → **动画中间态不一致**（终态一致，过程不同）。

**处置（二选一，需按场景声明）：**

| 场景 | 处置 |
|---|---|
| 转场类（只要求终态一致） | 登记进允许差异清单 |
| 需要过程一致的编排动画 | **改回 Rust 侧自行求值**，不走平台插值 |

**这条必须现在就记进去，否则会在一致性校验里变成难以归因的偶发失败。**

### 9.3 典型条目示例

| ID | 类别 | 内容 | 理由 |
|---|---|---|---|
| A-1 | 文本度量 | 同一文本三端宽度差异 | 度量引擎不同，不可消除 |
| A-2 | 运行时行为 | 滚动惯性衰减 | 各端滚动实现不同，**设计使然** |
| A-3 | 运行时行为 | 滚动边界反馈（回弹 / 硬停） | 平台规范不同 |
| **A-4** | **动画** | **转场插值中间态** | **平台插值曲线不同（§9.2）** |
| A-5 | 光栅化 | 圆角抗锯齿、阴影模糊 | 系统管线实现不同 |

**A-2 的陷阱必须强调**：若不识别为"设计差异"，团队会去修一个不该修的东西——**为了对齐某端而破坏另一端的原生手感**，那才是真正的南辕北辙。

## 10. 与已有校验体系的关系

本方案是**标准层**，已有《Web 与小程序多端一致性数值校验方案》是**实现层**。

| 层 | 文档 |
|---|---|
| 标准层（本方案） | 定义指标、目标、对外表述、与 Flutter 对照 |
| 实现层 | L1–L4 分层、探针、容差、VC 系列任务卡 |

### 10.1 分层对照

| 层 | 校验什么 | 确定性 | 对应指标 |
|---|---|---|---|
| **L1 编译期静态** | CSS Profile × 各端支持度 | ✅ 完全确定 | M1 |
| **L2 几何快照** | 位置 / 尺寸 / 层级 | ✅ 完全确定（锁字体后） | M1、M3 |
| **L2.5 离散交互** | 事件 → 结果态几何 | ✅ 完全确定 | M3 |
| **L2.6 连续交互** | **不变量**（非绝对坐标） | ✅ 完全确定 | M3 |
| **L3 计算样式** | 颜色 / 字体 / 间距数值化 | ✅ 完全确定 | M1 |
| **L4 像素观察** | 圆角 / 阴影 / 渐变 / 字形 | ❌ 有噪声 | **非门禁，仅报告** |

**L4 能用的真正原因不是算法变好，是要比的东西变少了**——L1–L3 过滤后，样本量下降一个数量级。

### 10.2 连续交互的关键约束（沿用并强化）

**禁止比对绝对坐标。**

滚动 100px 后去比"第 50 项应在 Y=1234.5"必然失败——惯性衰减、吸附行为、触摸采样率、滚动精度各端全不同。

改验六类不变量：相对顺序 / 相对间距 / 相对层级 / 包含关系 / 可见性集合 / 结构完整性。

> 校验策略转变：**从"值相等"到"关系不变"。**
> 这与"像素比对 → 数值比对"是同一类思维，只是再进一层。

## 12. 对外表述

### 12.1 核心落点

> **"Flutter 的一致性是被假定的，我们的一致性是被验证的。"**

配套注脚：Flutter 3.38 宋体事件——**被假定的一致性，一次 Skia 升级就崩，而且是设备级随机崩，只能靠用户报**[citation:52]。

### 12.2 第二个落点

> **"我们不靠截图比对，靠数值比对。"**

直接回应业界公开痛点（误报疲劳 → 静音告警 → 放弃），比自证"我们一致性做得好"有说服力得多。

### 12.3 三条禁语

| ❌ 禁止 | ✅ 应当 |
|---|---|
| "我们做到多端逐像素一致" | "我们做到**可验证的一致性**，并提供量化指标" |
| "我们不自绘"（易误解为用系统控件） | "我们**绕开原生控件树**，但**复用系统渲染管线**" |
| "我们比 Flutter 更一致" | "**在可验证性上我们远超 Flutter**；在像素绘制一致性上我们承认不如它" |

**第三条尤其重要**——主动承认短板，长板才有人信。
