# G-55 架构：三层解耦与常驻内核

## 1. 三层

```
┌─ 宿主层（可换，绝不 fork）────────────────────┐
│  VSCode  ·  Zed  ·  Neovim  ·  CLI  ·  Web    │
│  每个适配器只做协议翻译，零业务逻辑             │
└──────────────┬────────────────────────────────┘
               │  协议层
               │  LSP 70%  +  DAP  +  自研 RPC 3 项
               │  （依赖图 / 设备影响面 / 多形态预览）
┌──────────────┴────────────────────────────────┐
│  ★ 内核层（唯一实现，Rust 常驻守护进程）        │
│  FrameworkKnowledgeProvider                    │
│  索引 · 缓存 · 六项能力 · 性能预算              │
└────────────────────────────────────────────────┘
```

## 2. 为什么是守护进程，不是按需起进程

| | 按需起进程 | ★ 常驻守护进程 |
|--|-----------|--------------|
| 每次查询 | 冷启动 + 全量索引 | 内存命中 |
| 首次之后 | 仍要重建索引 | 增量更新 |

**冷启动一次，之后所有查询走内存；文件改动只增量重算受影响子图。**
这是性能的第一杠杆，比任何编辑器选型都重要。

## 3. 协议层占比的纪律

**70% 走标准协议（LSP / DAP），自研 RPC 只占 3 项。**

理由：标准协议能免费获得多编辑器支持；自研部分每多一项，
就多一份"换编辑器要重做"的成本。

| 能力 | 协议 |
|------|------|
| 语义导航 / 诊断 | LSP |
| 断言内联 / 调试 | DAP |
| 依赖图 | 自研 RPC |
| 设备影响面 | 自研 RPC |
| 多形态预览 | 自研 RPC |

## 4. 架构试金石（★ 最有价值的一条规约）

**阶段 2 做完 Zed 适配器后：如果内核真的 IDE 无关，
两个适配器应该只差一层协议翻译。**

> 若加 Zed 适配器时被迫修改内核，说明 G-54 的三层分层没做对。

这比任何文档评审都更能验证架构真伪。已写为可机器断言
（`apiSurface` 冻结，见 conformance INV-PF-06）。

## 5. 降级链（宿主维度）

```
in-memory(CLI) → VSCode → Zed → Neovim → Web(CodeMirror 6) → Skipped
```

宿主不可用返回 **SKIP 而非 FAIL**（沿用 G-51 Result 语义）。
