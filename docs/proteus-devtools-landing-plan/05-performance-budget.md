# G-55 性能预算

## 1. 六项预算

| # | 指标 | 墙钟目标 | ★ 确定性代理指标（CI 实际判定） |
|---|------|---------|------------------------------|
| 1 | 内核冷启动索引 | < 500ms | `touched === fileCount`（O(N)，禁超线性） |
| 2 | 单文件增量索引 | < 100ms | `touched <= changed + reverseDeps` |
| 3 | 语义跳转 | < 50ms | 缓存命中后 `recompute === 0` |
| 4 | 诊断 diagnostics | < 200ms | 只跑受影响检查项，不重扫全项目 |
| 5 | 内核常驻内存 | < 200MB | `cacheSize <= cacheMax`（LRU 硬上限） |
| 6 | 缓存命中率 | > 90% | `hitRate = hits/(hits+misses)` |

## 2. 为什么必须区分「墙钟」与「计数」

**墙钟断言在 CI 上必然 flaky**——机器负载、GC、冷热缓存都会让它抖动。
一条会随机变红的 CI 断言，比没有断言更糟（团队学会无视红色）。

所以：

- **计数断言**（touched / recompute / hitRate / cacheSize）→ **阻断**
- **墙钟断言** → 仅 `warn`，写入报告供观测，**不阻断**

这是 G-55.6 的核心，也是本份最容易被忽略的工程细节。

## 3. 缓存失效策略

```typescript
// 只失效受影响的缓存项，不清空全缓存
for (const [key, entry] of cache) {
  if (entry.deps.some(d => affected.has(d))) cache.delete(key)
}
```

每条缓存记录它依赖哪些文件（`deps`），增量索引时按 deps 精确失效。
**全清空是反模式**——会让"增量索引"退化成"每次全量"，预算 2 直接失效。

## 4. LRU 淘汰的正确性边界

内存有硬上限（预算 5），超出时 LRU 淘汰。
**关键：淘汰只允许降低性能，不允许丢失正确性。**

淘汰后重新查询会 miss → 重算 → 结果必须与淘汰前一致。
已写为断言（NEG-06）。

## 5. 性能数字的处理纪律

| 环节 | 要求 |
|------|------|
| 预算值 | 来自公开 benchmark 对标，**标注为"目标"** |
| CI 断言 | 用计数，不用墙钟 |
| 对外宣称 | **必须先实测**（G-37 未实测不宣称） |
