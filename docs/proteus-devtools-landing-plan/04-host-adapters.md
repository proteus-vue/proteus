# G-55 宿主适配矩阵

## 1. 三档定位

| 宿主 | 档位 | 定位 | 扩展生态 |
|------|------|------|---------|
| **VSCode** | 主档 | 零迁移、生态最大 | 50000+ |
| **Zed** | 性能档 | 输入延迟 2ms、内存 180MB | 约 800 |
| **Neovim** | 极客档 | 终端内、零 GUI 开销 | 丰富 |
| **CLI** | CI 档 | 无头，跑门控 | — |
| **Web** | 兜底 | CodeMirror 6（50KB vs Monaco 2-5MB） | — |

## 2. 能力对齐表

| 能力 | VSCode | Zed | Neovim | CLI | Web |
|------|--------|-----|--------|-----|-----|
| 语义导航 | ✅ | ✅ | ✅ | ⚠️ 文本输出 | ✅ |
| 分层守护 | ✅ | ✅ | ✅ | ✅ | ✅ |
| 断言内联 | ✅ | ✅ | ✅ | ✅ | ⚠️ |
| 依赖图 | ✅ | ⚠️ | ⚠️ | ✅ | ✅ |
| 设备影响面 | ✅ | ⚠️ | ⚠️ | ✅ | ⚠️ |
| 多形态预览 | ✅ | ❌ | ❌ | ❌ | ✅ |

⚠️ = 能力降级但可用；❌ = 不支持，返回 SKIP。

**处理原则**：❌ 不报错、不阻断。宿主缺能力属正常，
返回 SKIP 并在报告标注覆盖率下降。

## 3. 架构试金石（阶段 2 验收）

```
步骤 1：记录内核 apiSurface 快照 S1
步骤 2：新增 Zed 适配器（只写适配层）
步骤 3：记录 apiSurface 快照 S2
断言：S1 === S2
断言：两宿主对同一能力返回结果一致（协议一致性）
```

若需改内核才能接入 Zed，说明内核里混入了宿主假设——**分层失败，需重构**。

## 4. 为什么不做 fork（补充证据）

| 代价 | 实证 |
|------|------|
| 安全滞后 | Cursor/Windsurf 停在 VSCode 1.99.3，80+ NVD 漏洞 |
| 维护成本 | Cursor 专雇 8+ 工程师做上游合并 |
| 生态缺失 | Pylance / C# Dev Kit 闭源扩展不可合法使用 |
| 性能天花板 | Electron 架构无法从 fork 侧改变 |

**唯一需要 fork 的场景**：要拿编辑器运行时状态（标签页/光标/编辑历史）。
Proteus 六项能力均静态可推导，**不需要**。
