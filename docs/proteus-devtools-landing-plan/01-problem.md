# G-55 开发者工具落地形态与性能工程

> 定位：G-54（配套工具能力定义）的工程落地方案。
> 依赖：G-27 / G-46~G-48 / G-53 / G-54 · 编号：G-55

## 1. 问题

G-54 确立了「内核唯一 + 前端可换」，但没回答两个工程问题：

1. **具体用什么形态承载？** 插件 / fork / 自研 / 混合，代价差别巨大
2. **高性能第一原则怎么落地？** 高性能与不绑定 IDE 表面冲突

## 2. 四种落地形态

| 形态 | 代表 | 优势 | 代价 |
|------|------|------|------|
| **VSCode 扩展** | 本方案主档 | 零迁移、生态最大 | 受 Electron 天花板 |
| **VSCode fork** | Cursor / Windsurf | 可改编辑器内核 | 结构性滞后 + 高维护 |
| **自研编辑器** | Zed | 性能数量级领先 | 生态小（约 800 扩展） |
| **CLI / Web** | 兜底 | 零安装 | 无 IDE 集成 |

## 3. fork 为什么对我们不成立

**fork 的真正理由**：拿编辑器运行时状态——打开的标签页、光标位置、编辑历史。
这些 Extension API 拿不到，只能改内核。Cursor / Windsurf / Trae / Kiro 都为此 fork。

**但 Proteus 的六项框架独占能力（IR 结构 / 分层规则 / conformance 断言 /
SPI 拓扑 / 设备等价类 / 渲染语义）全部是静态可推导的**，插件完全够用。

> 为一项根本不需要的能力，付 fork 的全部代价——不成立。

**实证代价**：OX Security 实测发现 Cursor 与 Windsurf 停在 VSCode 1.99.3
（落后 4 个 minor），Chromium 落后 6 个大版本，携带 80+ 个 NVD 已知漏洞。
这不是"维护得好不好"的问题，是**结构性滞后**——VSCode 每月 2-3 次更新，
必须持续合并。Cursor 为此专雇 8+ 工程师；团队小于 4 人时，扩展模型三年
便宜 15-25 倍。此外闭源扩展（Pylance / C# Dev Kit）无法合法使用。

## 4. 关键洞察：性能瓶颈在内核，不在编辑器

Zed vs VSCode 实测差距不是 10%，是数量级：

| 指标 | Zed | VSCode |
|------|-----|--------|
| 冷启动 | 0.4-0.6s | 1.29-3.0s |
| 空闲内存 | 180-222MB | 650-3549MB |
| 输入延迟 | 2ms | 12-25ms |
| 万文件项目 | 0.25s | 3.8s |

根因是架构：VSCode 跑在 Electron 上（23 个进程，Chromium + Node），
Zed 是 Rust + GPUI 直连 GPU（5 个进程，无 DOM、无 CSS）。

**但编辑器那 10ms 级差异不是主要瓶颈。** 真正耗时的是框架知识计算：
索引 IR、跑 conformance、算依赖图、影响面分析——**这些全在内核**。

> 内核用 Rust 写成常驻守护进程，性能就抓住了。
> **高性能与不绑定 IDE 不再冲突**——这是解开这对矛盾的关键。

## 5. 落地结论

```
宿主层（可换，绝不 fork）
  VSCode（主） / Zed（性能档） / Neovim / CLI / Web
      ↓  LSP 70% + DAP + 自研 RPC 3 项
★ 内核层（唯一，Rust 常驻守护进程）
```

## 6. 诚实边界

- Zed 约 800 个扩展 vs VSCode 50000+，**只能做性能档，不能做主宿主**
- Rust 是选型建议不是教条：团队无 Rust 能力可用 Go（性能差一档，
  工程成本低）；**Node 不推荐**（CPU 密集 + 大内存索引是它的弱项）
- 上述性能数字是**目标**，来自公开 benchmark 对标，非本框架实测
