# Proteus 指令与 Vapor 能力缺口调研与补齐方案

> 目标：**承载上百页面级超级应用落地**
> 适用：Proteus v2.47+（Vue 3.4 / Vite 5 / TS 5.4 / 微信基础库 2.29.2+）
> 仓库：https://github.com/proteus-vue/proteus
> 用法：**本文档可直接下发 LLM 逐项落地**——每项自带现状判据、缺口描述、补齐建议、验收标准
> 说明：现状判断基于仓库 README 与既有实测；凡无公开证据支撑的判断均已标注「待核实」

---

## 0. 调研结论摘要

### 0.1 一句话结论

**指令层与 Vapor 层的真实缺口不在"性能"，而在"覆盖面"——
能承载超级应用的 80% 能力已具备，缺的是剩下 20% 的边界情况与工程完备性。**

### 0.2 现状盘点（有公开证据）

| 层 | 状态 | 判据 |
|---|---|---|
| 语义 IR + 184 原语 | ✅ 已落地 | PRIMITIVE_CATALOG SSOT |
| 渲染后端 SPI + 五后端 | ✅ **原型集齐** | README 原文为"五官方后端**原型**集齐" |
| Host Runtime（G-39/G-40） | 🟡 **进行中/规划** | "G-39/G-40 宿主运行时与执行载体实现" |
| **NativeBackend（G-28）** | ❌ **无运行实现** | "规划已入库、尚未有可运行实现：G-28 NativeBackend" |
| Rust 编译后端（G-38） | 🟡 B3 深化中 / B4 WASM Playground 规划 | — |
| 编译器双后端 | 🟡 进行中 | — |
| 宿主层三件套（G-41/42/43） | ✅ 已落地 | 六容器 + 所有权借用检查 |
| 语义组件 | ⚠️ **76 个双端落地** | 非五端 |
| Capability Hook | 81 个 | 收敛模型漏点体温计 |
| 单测 | 3441 全绿 | — |

### 0.3 ★ 三个最关键的发现

**① Vapor 在仓库里几乎没有实质内容**
README 中 vapor **仅出现在文档导航入口**（快速开始 / 配置参考 / 编译原理 / 路由与转场），
**无实质实现描述**。而你对话中提到的"自研 vapor 做了根节点重排的兄弟平移特调、
v-for 嵌套三层、4001 全量重排 0.08ms"——**这套能力尚未在仓库 README 中体现**。

> **这是最大的调研发现**：你已经做出的 vapor 成果**没有被固化为可交付的模块**。
> 建议优先把它产品化（见 GAP-V1）。

**② NativeBackend（G-28）无运行实现**
所有漂亮的 App 端实测数字（布局 0.063 / 绘制 **2.0**（原写 0.667 系子项、已证伪）/ 重排 0.08ms / 124.5FPS / 内存 0.328）
都依赖它。**它是整个 App 端叙事的地基，而地基目前是"规划已入库"。**

**③ "原型"二字是风险**
五后端"原型集齐"≠ 生产就绪。超级应用会暴露原型与生产的全部差距。
**建议对每个后端做一次"生产就绪度评估"**（见 GAP-I6）。

## 2. P0 缺口（立即补齐，阻塞超级应用）

### GAP-V1 · Vapor 成果未产品化 ★ 最高优先级

**现状**
对话中已有成果：根节点重排的兄弟平移特调、v-for 支持嵌套三层、
4001 全量重排 0.08ms（提升四十余倍）。
但仓库 README 中**无对应模块描述**。

**风险**
- 成果**无法被他人复现或验证**
- 无法纳入 CI 与 conformance
- 人员变动时知识丢失

**补齐建议**
1. 抽出独立模块（建议 `@proteus-vue/vapor` 或归入 compiler）
2. 定义公开接口与配置项
3. 纳入单测（现有 3441 全绿应扩展）
4. 补 README 章节 + 架构文档
5. **补可复现的 benchmark**（4001 全量重排场景，与既有 Benchmark 口径一致）

**验收标准**
- [ ] 模块可独立引用
- [ ] 4001 全量重排 ≤ 0.08ms **可复现**（CI 或手动脚本）
- [ ] v-for 嵌套三层用例纳入单测
- [ ] README 有独立章节

---

### GAP-I1 · 指令集未公开定义与版本化

**现状**
`render-cmd.ts` 描述了 RenderCmd 的设计原则（平台无关、线性、绝对坐标、
拍平不产生独立指令），但**无公开的指令集规格表**（opcode 清单、参数、语义）。

**为什么阻塞超级应用**
- 多团队并行开发时，指令是契约；无规格即无法协作
- 后端实现者无从对齐
- 无法做版本协商（Host ABI §6 依赖它）

**补齐建议**
1. 产出**指令集规格表**：opcode / 名称 / 参数 / 语义 / 各端实现要求
2. 指令集**版本化**（`ir_version` 已有机制，复用）
3. 指令集变更走语义化版本，纳入 conformance

**验收标准**
- [ ] 完整 opcode 清单（含 Draw / Anim 两大类）
- [ ] 每条指令有参数定义与语义说明
- [ ] 版本号纳入 Host ABI 协商
- [ ] 变更需走 major/minor 流程

---

### GAP-I2 · 舍入时机未统一 ★ 跨端一致性风险

**现状**
RenderCmd 使用**绝对坐标**。鸿蒙**强制整数像素**
（`flex:1/3` 三列时，ArkUI 把 0.333 舍为 0.33，累计误差导致第三列错位）。

**风险**
若各平台层各自舍入 → 三端策略不同 → **误差不可复现、不可测**。
golden test 全绿但三端画出来差 1px。

**补齐建议**
**硬性规则：内核产出指令时完成舍入，平台层不得再舍入。**

1. 在指令生成阶段统一舍入策略（建议 round-half-up 或明确定义）
2. 平台层移除所有舍入逻辑
3. 加入**跨端像素一致性 conformance**

**验收标准**
- [ ] 舍入仅发生在内核，平台层零舍入（静态检查）
- [ ] 三端同输入产出完全一致的坐标（逐字节比对）
- [ ] 鸿蒙三列布局无错位

---

### GAP-I3 · paint-hint 未编码进指令 ★ 内存风险

**现状**
内存专题定义了 `isMonochrome` / `isPureBackground` / `shareableContent`，
本应**编译期推导**。当前是否编码进指令**待核实**。

**风险**
若平台层运行时猜 → iOS 上曾出现的 **+78% 内存**会复发
（backing store 按最贵格式分配）。

**补齐建议**
1. `paint-hint` 作为**指令属性**编码
2. 编译期从归一化样式推导，**禁止运行时判断**
3. 平台层据 hint 决定 backing store 策略

**验收标准**
- [ ] 指令携带 paint-hint 字段
- [ ] 编译期推导（运行时零判断）
- [ ] iOS 内存增量复测

---

### GAP-I4 · 文本在指令流中的表达未定

**现状**
RenderCmd 设计已定，但**文本如何表达未明确**：
- 方案 A：绘制文本指令 + **内核已度量**的几何（平台层只管画，最薄）
- 方案 B：文本节点 + 测量回调（平台层参与排版）

**为什么关键**
文本是唯一无法完全平台无关的一块。方案 A 才能把平台层压到最薄。

**补齐建议**
**建议方案 A**：内核持平台注入的 `text_measure`（Android StaticLayout / iOS CoreText），
指令流中携带**已度量完成的几何 + 文本内容**，平台层只负责绘制。

**验收标准**
- [ ] 明确选定方案并写入规格
- [ ] 指令含文本度量结果
- [ ] 平台层不参与文本排版
- [ ] 文本跨端一致性纳入 conformance

---

### GAP-C1 · NativeBackend（G-28）无运行实现 ★ 地基风险

**现状**
README 明确："**规划已入库、尚未有可运行实现：G-28 NativeBackend**"。

**风险**
所有 App 端实测数字（布局 0.063 / 绘制 **2.0**（原写 0.667 系「只画色块」子项、已证伪）/ 重排 0.08ms / 124.5FPS / 内存 0.328）都依赖它。
**地基是"规划"状态，而叙事已经建在上面了。**

**补齐建议**
1. 明确 NativeBackend 的**最小可运行范围**（对齐 M1–M2 里程碑）
2. 与 Host ABI 方案 §0.4 的 `platform/` 拆分对齐
3. 优先 Android（既有实测全在此端）
4. 纳入 conformance

**验收标准**
- [ ] 有可运行的 Android 实现
- [ ] 4050 / 长列表 / 内存三项复测达标
- [ ] 纳入 RenderBackend conformance

---

### GAP-C2 · Host Runtime（G-39/G-40）未实现

**现状**
README："进行中/规划：G-39/G-40 宿主运行时与执行载体实现"。

**风险**
ExecutionCarrier（JSI / AOT）是"宿主侧 1ms"的载体。未实现则 JS 桥接成本回来。

**补齐建议**
1. JSI 直连优先（Android）
2. 与 Host ABI 八个接口对齐
3. 批处理保持（跨边界调用次数 = 帧数）

**验收标准**
- [ ] JSI 通路可用
- [ ] 跨边界调用次数 = 帧数（profile 验证）
- [ ] 宿主侧耗时实测仍为 1ms 量级

## 3. P1 缺口（超级应用规模化必需）

### GAP-V2 · 槽位 O(1) 更新未覆盖全部绑定类型

**补齐建议**：梳理绑定类型清单（属性 / 文本 / 样式 / 事件 / 列表 / 条件），
逐一确认是否走槽位直写。未覆盖的纳入 L0 标准路径。

**验收**：单节点更新延迟 ≈ 宿主侧耗时（O(1) 验证）。

### GAP-V3 · 列表更新（LIST_UPDATE）未落地

**补齐建议**：实现 item 级 O(1) 更新指令，避免整个列表重建。

**验收**：4000 行列表中单行更新，耗时不随行数线性增长。

### GAP-V4 · L0/L1 安全判定未实现

**补齐建议**：按 Vapor IR 方案 §4 的 7 条准入条件实现，**判定从严不从宽**
（误判为 L1 会导致静默的 UI 不更新，比慢 10 倍严重）。

**验收**：安全判定用例 100% 通过；误判率为零。

### GAP-I5 · 绘制指令缺失 overdraw culling

**重要性**：绘制是唯一瓶颈（4050 场景占剩余 91%，列表场景占预算 60%）。
绝对坐标让 culling 变成一次坐标比较——**这是投入产出比最高的一项**。

**验收**：视口外指令不 emit；绘制耗时下降可测。

### GAP-I6 · 后端生产就绪度未评估

**补齐建议**：对五后端逐个做"原型 vs 生产"差距评估，
输出每项的能力矩阵与风险清单。**尤其 Native×3 与 Flutter 映射。**

### GAP-I7 · 指令级 conformance 缺失

**补齐建议**：指令流 golden test（字节级比对）+ 跨端像素一致性。
指令流自包含，天然可测——**这是绝对坐标设计送的红利，不用白不用**。

### GAP-V5 · Vapor 与 Web VDOM 行为一致性未验证

**补齐建议**：Web 端保持 VDOM 作为**正确性真值基准**
（浏览器 `getComputedStyle` / `getBoundingClientRect`），
与 App 端指令路径比对（≤ 0.5dp，当前 0.375dp）。

### GAP-C3 · 超级应用规模的编译期性能未测

**补齐建议**：上百页面级项目的**编译耗时、产物体积、增量编译**实测。
超级应用的编译时间直接影响开发体验，**且是原型与生产的分水岭**。

### GAP-C4 · 184 原语完备性未用真实项目验证

**补齐建议**：按《实战采集埋点清单》§2，在编译流水线加漏点计数器
（记录不阻断），拿到"表达不了"的清单。

## 5. 落地顺序建议（关键路径）

```
第一批（并行，P0）
  GAP-V1  Vapor 产品化        ← 固化已有成果，最高性价比
  GAP-I1  指令集规格化        ← 一切协作的契约
  GAP-I2  舍入时机统一        ← 低成本高收益
  GAP-I3  paint-hint 编码     ← 防内存问题复发

第二批（依赖第一批）
  GAP-I4  文本表达定案
  GAP-C1  NativeBackend 实现   ← 地基，最长
  GAP-C2  Host Runtime

第三批（规模化）
  GAP-V2/V3/V4  槽位覆盖 / 列表更新 / 安全判定
  GAP-I5        overdraw culling   ← 唯一瓶颈，投入产出比最高
  GAP-C3/C4     编译期性能 / 原语完备性

第四批
  GAP-I6/I7     就绪度评估 / 指令 conformance
  GAP-V5        跨端一致性验证
  GAP-V6/I8     P2 项
```

## 6. 给实现 LLM 的执行指令

1. **先做 GAP-V1**——把已有 vapor 成果固化，它性价比最高且风险最低。
2. **GAP-I2（舍入）与 GAP-I3（paint-hint）是硬约束**，不是优化项：
   前者防跨端 1px 误差，后者防 iOS +78% 内存复发。
3. **指令集规格（GAP-I1）必须先于任何后端实现**，否则多端无法对齐。
4. **不得修改既有五后端的行为**，所有新增必须保持既有测试全绿。
5. **Vapor 的 L0/L1 安全判定（GAP-V4）判定从严不从宽**——
   误判为 L1 会导致静默的 UI 不更新，比慢 10 倍严重。
6. **每项落地后必须有可复现的验收脚本**，不接受"跑通了"作为验收。
7. **新增 opcode 与规则自带 AI 说明书**（与既有 69 条一致）。
8. 凡标注「待核实」的现状判断，**落地前先核实再动手**。
