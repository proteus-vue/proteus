# G-58 风险与降级

> 八条风险。每条都有降级路径——**除 R3 需靠上游，其余均可自主处置。**

---

## 风险清单

| # | 风险 | 等级 | 降级方案 |
|---|------|------|---------|
| **R1** | 生态冷启动（无插件可用） | 高 | 内置功能即插件（G-58.1 天然缓解） |
| **R2** | WASM 工具链门槛高 | 中 | 声明式优先，多数插件零编译 |
| **R3** | WASM 沙箱逃逸 | 低但致命 | 依赖 wasmtime 上游安全 |
| **R4** | Tier 2 外部进程无沙箱 | 中 | 如实标注 + 显式授权 |
| **R5** | API 设计缺陷 | 中 | 提案机制（可反悔阶段） |
| **R6** | 插件拖慢宿主 | 中 | 资源限额 + 崩溃隔离 |
| **R7** | 供应链安全 | 中 | sha256 + 显式更新确认 |
| **R8** | 插件间冲突 | 低 | 阶段 1 禁止插件互调 |

---

## R1 生态冷启动（最高现实风险）

**问题**：新生态没有插件，用户凭什么迁移？

**降级方案——这是 G-58.1 的意外红利**：

```
内置功能用插件 API 实现
   ⇒ 内置功能本身就是"第一批插件"
   ⇒ 它们的代码就是生态的示例实现
   ⇒ 用户可参考、可 fork、可替换
```

**这把"冷启动"从市场问题变成了架构问题，而架构已经有解。**

补充手段：
- 首批官方插件直接以源码形式公开（作为参考实现）
- Tier 0 插件（主题/片段）迁移成本极低，优先吸引这类作者

---

## R2 WASM 工具链门槛

**问题**：Rust → `wasm32-wasip2` 需要工具链，JS 开发者不熟。

**降级方案**：

| 层级 | 应对 |
|------|------|
| **Tier 0** | 纯 JSON，**零工具链**（覆盖多数插件） |
| Tier 1 | 提供官方模板仓库 + CLI 脚手架 |
| Tier 1 | 未来评估 AssemblyScript 等低门槛路径 |

**已知坑（Zed 官方文档，必须写进插件作者文档）**：

```
cfg 指令在 WASM 下不工作
std::env::var 不返回预期结果
```

> 提前告知，比让作者自己踩坑强。

---

## R3 WASM 沙箱逃逸

**性质**：概率低但后果致命，**且不在我们控制范围内**。

**应对**：

| 措施 | 说明 |
|------|------|
| 使用成熟运行时 | wasmtime（Bytecode Alliance），24/7 模糊测试 |
| 保持更新 | 跟踪上游安全公告 |
| 纵深防御 | 即使沙箱被突破，capability 层仍限制访问 |
| **诚实标注** | **不宣称"绝对安全"** |

> **能力层是第二道防线**——这正是 capability 模型优于
> "沙箱 + 之后裸奔" 的地方。

---

## R4 Tier 2 外部进程无沙箱

**问题**：LSP/DAP 是原生进程，权限等同用户运行的程序。

**应对（延续 G-56.4 如实上报原则）**：

```
Tier 0  无代码 → 无需警示
Tier 1  WASM 沙箱 → 列出 capability
Tier 2  原生进程 → 明确警示"将运行外部可执行程序"
```

**不做的事**：不把 Tier 2 包装成"也在沙箱内"。
> **把风险等级如实告诉用户，比统一宣称"沙箱安全"更专业。**

---

## R5 API 设计缺陷

**问题**：API 一旦稳定就不能改，设计错了代价极高。

**应对**：提案五阶段（学 VSCode）

```
① Idea → ② Proposal → ③ Implemented → ④ Feedback → ⑤ Finalization
```

关键保护：
- 提案阶段**可频繁变更**
- 提案**可能死在半路**（VSCode 明确警告可能 deprecate）
- 提案**禁止发布**（G-58.8 强制校验）

> **允许反悔的机制，比"一次设计对"更可靠。**

---

## R6 插件拖慢宿主

**应对**：

| 机制 | 说明 |
|------|------|
| 资源限额 | `memoryMB` / `cpuMsPerCall` / `timeoutMs` 强制 |
| 超限终止 | 终止单个插件，不影响其他 |
| 崩溃隔离 | trap 隔离，宿主继续 |

延续 G-55 性能预算纪律：**计数断言阻断，墙钟仅 warn**。

---

## R7 供应链安全

**现状（诚实标注）**：清单支持 `sha256`，但**市场侧签名体系未设计**。

**当前措施**：

| 措施 | 状态 |
|------|------|
| 清单 sha256 校验 | ✅ 已设计 |
| 安装期完整性校验 | ✅ 已设计 |
| **市场侧签名** | ❌ **未设计** |
| **自动更新确认** | ✅ 禁止静默更新 |

VSCode 的教训（ReversingLabs，2025）：
恶意扩展**利用已下架扩展名重新发布**。

> **我们的对策：禁止静默自动更新。**
> 每次更新都需用户确认，并重新展示权限变更。

---

## R8 插件间冲突

**应对**：阶段 1 **禁止插件互相调用**。

理由：
- 权限传递（A 借 B 的权限）是难题
- 依赖版本冲突
- 故障定位困难

**代价**：生态能力受限。**这是有意的取舍**——
先做对简单模型，再考虑放开。

---

## 降级总原则

延续 G-51 INV-02 / G-56.6：

```
每一档失败 → 返回 DEGRADED / denied / skipped + 原因
           → 不判 FAIL、不阻断 CI、不崩溃
```

**唯一例外**：G-58.1（内置功能走 API）——
这是架构红线，违反即设计失败，**不给降级路径**。
