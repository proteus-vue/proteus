# G-59 架构

## 1. 五层治理栈

```
┌─────────────────────────────────────────┐
│ L4 治理层   官方不下场 / 废弃策略 / 破坏率看板 │  ← P3 / P5
├─────────────────────────────────────────┤
│ L3 信任层   代码哈希 / 更新重授权 / 审计日志  │  ← P4 延迟激活
├─────────────────────────────────────────┤
│ L2 数据层   敏感度分级（public→secrets）    │  ← P4 第一方 API
├─────────────────────────────────────────┤
│ L1 版本层   WIT 并存 / 破坏率度量          │  ← P2
├─────────────────────────────────────────┤
│ L0 性能层   激活契约 / 启动预算 / 去激活     │  ← P1
└─────────────────────────────────────────┘
           ↓ 全部下沉到
      G-58 插件运行时（WASM 沙箱）
```

## 2. L0 性能层：激活契约

### 三类声明

| 类型 | 示例 | 判定 |
|------|------|------|
| **精确** | `onCommand:ext.foo`、`onLanguage:python`、`workspaceContains:**/*.py` | ✅ 允许 |
| **宽泛** | `onStartup`（有合理场景） | ⚠️ 允许但计入预算且受限 |
| **通配** | `*` | ❌ **拒绝加载** |

**为什么拒绝而不是警告**：`*` 的问题在于个体理性导致集体劣化。
警告会被忽略（作者为求功能可靠，理性地选 `*`），
只有**硬拒绝**才能把成本内部化。

### 预算模型

```
perPluginBudget  单插件激活预算（设计目标 100ms）
totalBudget      全局启动预算（设计目标 800ms）
```

判定：
- 单插件实测激活耗时 > perPluginBudget → **拒绝加载**（不是警告）
- 全局预设成本 > totalBudget → 拒绝**最后加入的**插件，并明确告知

**为什么 100ms / 800ms**：
- 300ms 是社区公认的"单插件构成瓶颈"阈值 → 取 1/3 作为预算
- 1200ms 是用户感知阈值 → 取 2/3 作为全局预算，留余量给宿主自身

⚠️ **这两个数字是设计目标，来自公开阈值推导，非本框架实测。**

### ★ 去激活契约（常被忽略的一半）

实证：「禁用操作仅卸载 UI 层，不终止已启动的子进程」。

所以契约是双向的：
```
activate()   → 分配资源
deactivate() → 必须回收：子进程 / 定时器 / 监听器 / 文件句柄
```
`deactivate()` 未清理 → 记入审计日志并降级该插件信任分。

## 3. L1 版本层：并存 + 破坏率

```
宿主提供 0.1.0 / 0.4.0 / 0.8.0 三份 WIT（并存）
插件声明 apiVersion: "0.4.0"
   → 解析到 0.4.0 那份，不受 0.8.0 新增/改动影响
```

**关键度量：破坏率**

```
breakingRate(old, new) = 不兼容变更条目数 / 该版本总变更条目数
```

作为**对外可见的看板指标**。JetBrains 的做法是公开清单但无比率；
Zed 的做法是结构性避免破坏。**两者都不度量，我们度量。**

> 一条不能被度量的承诺，等于没有承诺。

## 4. L2 数据层：★ 敏感度分级（本份核心修正）

### 为什么 API 危险度分级不够

`vscode.env.clipboard.writeText` 是**第一方、无危险 import、看似无害**的 API，
但它被用于窃取 BIP-39 助记词与以太坊私钥，且**绕过只查危险 Node 导入的静态扫描**。

**所以分级的锚点必须是"数据"，不是"API"。**

### 四级模型

| Tier | 含义 | 典型 |
|------|------|------|
| `public` | 公开信息 | 版本号、扩展自身元数据 |
| `workspace` | 工作区内容 | 文件内容、项目结构、诊断信息 |
| `credentials` | 凭证/可复现身份 | **剪贴板**、环境变量、git 配置、token 文件 |
| `secrets` | 高敏密钥 | SSH 私钥、密钥库、助记词、MFA |

### ★ 关键设计：按 tier 授权，不按 API 列举

```
grant(plugin, 'credentials')
   → 该 tier 下**所有** API 可用（含 clipboard.readText / writeText）
```

**这正是防住 clipboard 案例的机制**：
`clipboard.writeText` 不在任何"危险 API 清单"里，
但它触及 `credentials` 数据 → 必须显式授予 → 用户可见 → 审计可查。

**列出所有危险 API 是追不上的**（新 API 不断加入，组合无穷）；
**按数据分级是收敛的**（数据敏感度是有限集合）。

### 剪贴板为什么是 credentials 而不是 workspace

因为实证里它装的正是助记词和私钥。**按最坏情况定级**，不按典型用法。

## 5. L3 信任层：更新即重新授权

针对「干净版本建信任 → 后续推送武器化更新」+「延迟激活」：

```
install: 记录 codeHash → 授予 capability
update : codeHash 变化 → **自动撤销 capability，要求重新授权**
```

**这一条是整个安全模型里成本最低、收益最高的一击**：
它不试图检测恶意（检测永远滞后），而是**切断"信任可以继承"这条假设**。

审计日志记录每一次高敏数据访问（`credentials` / `secrets` 级），
对应用户可见的"该插件于 X 时读取了剪贴板"。

## 6. L4 治理层：官方不下场（及它的边界）

G-58.1 已规定内置面板必须用插件 API 实现。G-59 延伸为：

> **内置插件的 capability 声明必须与第三方同构，不得超额。**

可断言部分：`assertBuiltinParity()` 比对内置与第三方 capability 集合。

**不可断言部分（必须诚实说明）**：
这个机制**只能约束技术同构，无法约束产品决策**——
官方仍可"用同样的 API 做一个和第三方竞争的功能"。
真正防止这一点的不是技术，是**公开的治理承诺 + 社区监督**。

## 7. 成熟度

```
L0 无契约          ← Atom 式（暴露权力）
L1 有 API 无约束    ← 早期 VSCode
L2 权限模型         ← G-58
L3 +性能/版本/数据契约 ← ★ G-59
L4 +治理与破坏率看板  ← G-59 阶段 3（需真实生态数据）
```
