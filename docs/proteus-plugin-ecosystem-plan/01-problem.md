# G-59 插件生态治理与性能契约

> 原则 #0「不绑定」系列，第 22 次泛化（官方链：…G-54=18、G-56=19、G-57=20、G-58=21，G-55 落地不占序；#396 修正，原稿误作 19）。
> 编号：G-59 · 依赖：G-58（插件 API）· G-55（性能工程）· G-37（未实测不宣称）

## 1. 这份从哪来

G-58 定义了插件 API 的形态与权限模型。但**它是设计导向的取证**——
先定了「WASM + capability」，再去找支撑证据。

补做完整痛点调研后（`00-pain-points.md`），暴露了两类遗漏：

| 遗漏类型 | 具体 |
|---------|------|
| **方向性遗漏** | 启动性能（用户侧最大抱怨）完全没进设计 |
| **实质性漏洞** | capability 模型建立在「API 危险度」上，而实证表明**第一方无害 API 也能致命** |

所以 G-59 不是 G-58 的补丁，是**它的另一半**：

> **G-58 解决「插件怎么安全地跑」；G-59 解决「生态怎么活下来 + 跑得够快」。**

## 2. 核心问题：五条

| ID | 问题 | 证据锚点 |
|----|------|---------|
| **P1** | 激活时机无强制契约 → 个体理性导致集体劣化 | `*` 插件 activationTime 380–620ms，叠加突破 1200ms |
| **P2** | 版本不并存 → 升级即破坏，成本外包给作者 | JetBrains 官方建议"干脆别写 untilBuild" |
| **P3** | 平台下场挤压第三方 → 无人愿写插件 | Webview UI Toolkit 归档无替代；Roo-Code 停运 |
| **P4** | 权限建在 API 危险度上 → 第一方 API 绕过 | `clipboard.writeText` 窃取助记词，无危险 import |
| **P5** | 暴露权力而非接口 → 故障无法归因 | Atom：移除插件"修好了"bug，没人知道为什么 |

## 3. 问题之间的关系

```
P5 架构（暴露权力）
   ├─→ P1 性能（无激活契约，所以每个插件都要 `*`）
   ├─→ P2 兼容（无接口边界，所以改内部即破坏）
   ├─→ P4 安全（按 API 授权，而非按数据授权）
   └─→ P3 治理（官方能用私有 API 做竞品功能）
```

**五条是一条**：Atom 那句 "Power dressed up as flexibility" 是总纲。

## 4. 与 G-58 的分工

| | G-58 | G-59 |
|--|------|------|
| 关注 | **单个插件**怎么跑 | **整个生态**怎么活 |
| 机制 | WASM 沙箱、capability | 激活契约、版本并存、治理规则 |
| 时间尺度 | 运行时 | 生态的整个生命周期 |
| 关系 | G-58 ⊂ G-59 | G-59 扩展 G-58，**重叠处以后者为准** |

**冲突处理**：G-58 的 capability 模型在 G-59 中被**升级**为数据敏感度分级，
不是推翻——原模型是"没有分级"，G-59 补上分级维度。

## 5. 诚实边界

- 五条痛点均有外部实证，但**强度不一**：兼容性/安全是一手，生态萎缩是二手转述
- 本份提出的所有预算数字（100ms/800ms）是**设计目标，非实测**
- 「官方不下场」是**治理承诺**，其可断言性仅限于技术同构层面（capability 声明），
  **无法约束产品决策**——这点必须说清，否则是虚假承诺
- G-59 不解决"如何吸引第一批作者"——那是运营问题，不是架构问题
