# G-59 铁律

## G-59.1 — 激活时机是契约，不是优化项

禁止 `activationEvents: *`。超预算**拒绝加载**，不是警告。
个体理性导致集体劣化，只有硬约束能把成本内部化。

## G-59.2 — 去激活必须对称

`deactivate()` 未清理的资源（子进程/定时器/监听器/句柄）记入审计并降级信任分。
**禁用不等于卸载** —— 这是实证得出的教训。

## G-59.3 — 版本并存，不跟随

新版本以新文件加入，老版本不被删除。老插件永远能解析到它声明的那份。

## G-59.4 — 破坏率必须可度量且公开

不可度量的兼容性承诺等于没有承诺。`breakingRate()` 进看板。

## G-59.5 — ★ 权限建在数据敏感度上，不建在 API 危险度上

`clipboard.writeText` 是第一方"无害"API，却能窃取助记词。
**数据敏感度是有限集合，API 是无限集合——在有限集合上建模才收敛。**
未登记 API 一律按 `secrets` 保守处理。

## G-59.6 — ★ 更新即重新授权

代码哈希变化 → 自动撤销 capability，要求重新授权。
不试图检测恶意（检测永远滞后），而是**切断"信任可继承"这条假设**。

## G-59.7 — 废弃必须提供替代

`deprecate()` 的 replacement 为 null 时必须拒绝。
Webview UI Toolkit 归档且无替代 = 留一个没人填的坑。

## G-59.8 — 内置插件与第三方同构

内置插件的 capability 声明不得超额，`assertBuiltinParity()` 进 CI。

**★ 但必须诚实说明其边界**：这条只能约束技术同构，**无法约束产品决策**。
官方仍可用同样的 API 做与第三方竞争的功能。
真正防止这一点的不是技术，是公开的治理承诺 + 社区监督。

## G-59.9 — 数字三分类标注

对外材料中的数字必须标注强度：
1. 官方/一手（可直接引用）
2. 社区实测（量级可信，具体随环境浮动）
3. 二手转述（**须以原文为准，不得直接宣称**）
