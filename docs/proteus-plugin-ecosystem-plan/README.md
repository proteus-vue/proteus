# G-59 插件生态治理与性能契约

> Proteus 规划体系 · 编号 G-59 · 依赖 G-58 / G-55 / G-37

## 这份解决什么

G-58 定义了插件 API 的形态与权限，但它是**设计导向的取证**——
先定方案再找证据。补做完整痛点调研后暴露两类问题：

| 类型 | 具体 |
|------|------|
| 方向性遗漏 | 启动性能（用户侧最大抱怨）完全没进设计 |
| **实质性漏洞** | capability 建在「API 危险度」上，而实证表明**第一方无害 API 也能致命** |

> **G-58 解决「插件怎么安全地跑」；G-59 解决「生态怎么活下来 + 跑得够快」。**

## 五条痛点一句话版

| # | 痛点 | 一句话根因 |
|---|------|-----------|
| P1 | 启动被 `*` 插件拖垮 | 激活时机没有强制契约 |
| P2 | 升级即破坏 | 版本不并存，成本外包给作者 |
| P3 | 作者流失、平台下场 | 生态位可被官方挤占 |
| P4 | 第一方 API 也能致命 | 权限建在 API 危险度而非数据敏感度上 |
| P5 | 插件互相污染无人负责 | 暴露权力（power）而非接口（interface） |

**总纲**：Atom 那句 "Power dressed up as flexibility"。

## 最重要的两条设计

**① 数据敏感度分级（对 P4）**
`clipboard.writeText` 不在任何危险 API 清单里，却窃取了助记词。
所以按**数据**分四级，不按 API 列举——**数据是有限集合，API 是无限集合**。

**② 更新即重新授权（对 P4 延迟激活）**
不试图检测恶意（永远滞后），而是**切断"信任可继承"这条假设**。

## 诚实边界

- 100ms / 800ms 是**设计目标**，由公开阈值推导，非实测
- -47% 生态萎缩是**二手转述**，须以 VSCode 官方原文为准
- 「官方不下场」**只能约束技术同构，无法约束产品决策**
- 生态冷启动（吸引第一批作者）是运营问题，架构无解
