# G-42 宿主容器契约与页面生命周期治理

> **状态**: v1 · **层级**: L3（宿主容器层，位于 G-39 宿主运行时之上）
> **定位**: 方法论第六次泛化——**不绑容器形态**
> **原则溯源**: 原则 #0（统一语义收敛）· 原则 #11（可插拔必须有可验证支撑）

## 1. 动机：为什么需要容器层

### 1.1 现有体系的缺口

G-39 定义了 `ProteusHostRuntime`（线程/生命周期/桥/执行载体），G-41 定义了宿主如何接入框架。但两者之间**缺一层**：

```
G-39 HostRuntime    → 管"进程怎么跑"（线程/事件循环/原生桥）
G-41 HostIntegration → 管"宿主怎么接"（三方关系/职责边界）
★ G-42 HostContainer → 管"页面怎么组织、内存怎么管、业务怎么隔离"  ← 缺失
```

运行时只保证"能跑起来"，**不保证"跑得久、跑得多、不崩、不泄漏"**。

### 1.2 传统框架的结构性病症

| 病症 | 根因 |
|------|------|
| **页面栈内存泄漏** | 两套生命周期（JS 状态 ↔ 原生 View）靠人工配对，漏一处即泄漏 |
| **超级应用难做** | 容器形态硬编码，无法按需替换策略 |
| **多业务互相拖垮** | 无沙箱/无配额/无崩溃隔离 |
| **宿主 fork 框架** | 仓库形态未定义，宿主复制一份源码 → 永远升不了级 |

**这四条不是 bug，是结构性缺陷**——传统框架（uni-app / RN / Flutter）全部如此。

### 1.3 Proteus 的解法：IR 作为唯一真相

关键差异——**我们多了 IR 这一层，天然就是页面栈的唯一 Owner**：

```
传统：  JS 状态 ←→ 原生 View      （双边配对，易漏）
Proteus：IR 实例 ← 唯一真相 → Backend 挂载点
              ↑ 框架持有，可完全管控
```

于是页面销毁可以做成**原子操作**，从源头消灭泄漏。

## 2. 五层容器栈

```
┌─────────────────────────────────────────────────┐
│ L0  宿主进程 (Host Process)                      │
│     iOS App / Android App / Web Page / ...       │
├─────────────────────────────────────────────────┤
│ L1  宿主运行时 (G-39 HostRuntime)                │
│     线程 / 事件循环 / 执行载体 / 原生桥          │
├─────────────────────────────────────────────────┤
│ L2  ★ 宿主容器 (G-42 HostContainer)              │
│     页面栈 / 业务沙箱 / 资源配额 / 生命周期治理  │
├─────────────────────────────────────────────────┤
│ L3  页面 (Page)                                  │
│     IR 实例 + 组件树 + 页面上下文                 │
├─────────────────────────────────────────────────┤
│ L4  视图 (View)                                  │
│     Backend 挂载点（原生 View / Widget / DOM）    │
└─────────────────────────────────────────────────┘
```

**L2 是本次新增的层**——它让"页面怎么组织"从硬编码变成可插拔策略。

## 3. 六种容器类型（可插拔策略）

| 容器 | 适用场景 | 页面栈 | 多业务 | 配额 |
|------|---------|--------|--------|------|
| `SinglePage` | 单页 App / 卡片 / IoT 屏 | 单页 | ❌ | ❌ |
| `Stack` | 常规导航 App | 栈式 | ❌ | 弱 |
| **`SuperApp`** | 超级应用 | 多栈 | ✅ 沙箱 | ✅ |
| `MiniProgram` | 小程序容器 | 栈式 | ✅ | ✅ |
| `Window` | 桌面多窗口 | 窗口树 | ❌ | 弱 |
| `Embedded` | 嵌入宿主页面 | 无栈 | ❌ | ❌ |

**同一个宿主运行时，插不同的容器策略**——这就是"不绑容器形态"。

## 4. 三方关系：容器 × 运行时 × 框架

```
┌──────────────────┐
│  Proteus Core    │  拥有：IR 定义 / Diff / 页面生命周期契约
│  （框架内核）     │  禁止：碰线程 / 碰原生 View / 碰容器实现
└────────┬─────────┘
         │ 声明需求（我要开一个页面、销毁一个页面）
         ↓
┌──────────────────┐
│  HostContainer   │  拥有：页面栈 / 沙箱 / 配额 / 销毁时机
│  （G-42，可插拔） │  禁止：解析 IR / 干预 Diff / 直接操作组件
└────────┬─────────┘
         │ 调用（创建原生挂载点、回收资源）
         ↓
┌──────────────────┐
│  HostRuntime     │  拥有：线程 / 事件循环 / 载体 / 原生桥
│  （G-39）         │  禁止：感知页面语义 / 干预容器策略
└──────────────────┘
```

**三方正交，各自可独立替换。**

## 5. 页面生命周期契约

### 5.1 状态机

```
                 create
                   ↓
  ┌────────→  created
  │              ↓ mount
  │           mounted ←──────┐
  │              ↓ hide      │ show
  │           hidden ────────┘
  │              ↓ destroy
  │           destroyed
  │              ↓
  └──── recycle（对象池复用）

异常路径：mounted → crashed（崩溃隔离，不影响宿主）
```

### 5.2 五原子销毁

```
detachPage(pageId):
  1. 卸载 Backend 挂载点（原生 View 释放）
  2. 解绑事件/手势（框架登记过的全部）
  3. 清定时器/订阅（框架代管，不是业务自己管）
  4. 销毁 IR 实例
  5. 归还内存配额
  → 五步原子，不可部分执行
```

**框架代管资源是关键**：定时器、订阅、事件监听不再是业务自己 `setTimeout` 然后忘了 `clear`，而是走 `pageContext.timer()`——页面销毁时框架自动回收。

## 6. 铁律（详见 rules.md）

| 编号 | 铁律 |
|------|------|
| **G-42.1** | IR 是页面唯一真相，Backend 挂载点不得独立持有状态 |
| **G-42.2** | 页面销毁必须五原子，禁止部分执行 |
| **G-42.3** | 资源由框架代管，业务不得裸用 `setTimeout`/`addEventListener` |
| **G-42.4** | 容器不得解析 IR / 干预 Diff |
| **G-42.5** | 超级应用容器必须提供崩溃隔离与资源配额 |
| **G-42.6** | **宿主仓库严禁 fork 框架源码** |
