# G-48 兼容式小程序运行容器

> **一句话**：不造新标准，而是把**微信小程序标准当事实标准**，做一个**标准运行时内核 + 各平台 Adapter** 的兼容容器——让任意标准小程序在自有 App 宿主里跑起来，能力调用走统一桥接 + G-46 凭证共享。

> **方法论定位**：原则 #0「不绑定」系列第 12 次投影——**不绑定小程序运行时形态**（G-27 渲染 / G-39 宿主 / G-43 所有权 / G-44 测试 / G-45 基座 / G-46 资源容器 / G-47 组合一致 / ★小程序运行时 G-48 / 进程级沙箱 G-49 / 平台 G-50）。

---

## 1. 问题：为什么"造开发者平台"是错的路

### 1.1 生态冷启动的死循环

自造小程序标准 + 自造开发者平台（IDE / 审核 / 文档 / 社区），本质是**从零拉开发者**——这是巨头级投入，且陷入经典死循环：

```
无开发者 → 无小程序 → 无用户 → 无开发者 ...
```

微信小程序能成，是因为**微信已有 10 亿用户**（需求侧天然存在）。一个普通 App 自造平台，**没有这个起点，几乎必死**。

### 1.2 事实标准已经存在

- **微信小程序标准已成事实标准**：支付宝早期支持 `wx.` 前缀兼容；抖音小程序 IDE 支持微信项目导入；鸿蒙 ArkUI 支持标准小程序结构（`.js`/`.json`/`.wxml`/`.wxss` + AppService/PageFrame 双线程）
- **标准小程序代码结构跨平台高度一致**——差异集中在**平台特有能力**（登录 / 支付 / 分享），而非运行时结构

**结论**：另起炉灶是重复造轮子 + 无生态；**顺势兼容才是高杠杆。**

## 2. 竞品横向：谁在做兼容容器

| 方案 | 做法 | 短板（我们的机会） |
|------|------|------------------|
| **uni-app** | 条件编译，各平台写分支 | 无统一运行时，靠编译器枚举平台 |
| **Taro** | 编译适配，React → 各小程序 | 同上，编译期转换，无运行时桥接 |
| **快应用** | 自有标准（类小程序） | 生态弱，未成事实标准 |
| **美团/京东小程序容器** | 自有运行时 + 部分兼容 | 未开源统一适配规范 |
| **★ Proteus G-48** | **标准运行时内核 + Adapter SPI + 能力桥接 + G-46 凭证共享** | —— |

**关键区分**：uni-app/Taro 是"**编译期适配**"（代码 → 各平台），我们是"**运行期兼容**"（标准小程序 → 统一运行时 → 平台 Adapter）。**前者每加平台改编译器，后者每加平台只需一个新 Adapter（内核零改动）。**

## 3. 核心命题：两件事，一个内核

```
A. 让"标准小程序"能在自有 App 宿主里跑起来   ← G-48 主目标（兼容容器）
B. 让"平台差异"通过 Adapter SPI 抹平          ← 复用 G-28 NativeBackend 模式
```

**这恰好是 G-48 与"造开发者平台"的根本分野**：

| 维度 | 造开发者平台（G-50，后置） | 兼容运行容器（G-48，本轮） |
|------|--------------------------|--------------------------|
| 生态 | 从零拉开发者（极难） | **承接已有微信小程序**（数百万存量） |
| 标准 | 自定（无人跟从） | **微信标准 = 事实标准** |
| 工作量 | 巨大（IDE+审核+社区） | **集中在 Adapter（可并行）** |
| 冷启动 | 死循环 | **无：存量小程序直接跑** |

## 4. 与既有体系的关系（互校，无冲突）

| 依赖项 | G-48 复用 / 新增 |
|--------|----------------|
| G-27 渲染后端 | 小程序**组件**（`map`/`camera`/`live-player`）走 Backend SPI 特殊节点 |
| G-28 NativeBackend | **复用**：Platform Adapter 即 NativeBackend 实现 |
| G-39 宿主运行时 | 标准运行时内核**寄宿于** HostRuntime |
| G-42 容器/安全网关 | 能力调用**过网关**（签名 + 权限校验）；第三方小程序**信任模型**归此（引用 G-42，不重述） |
| G-43 所有权/Drop | 小程序**实例生命周期** → 资源所有权（销毁时级联释放） |
| G-44 测试 IR | conformance 用例复用 runner（多平台跑同一份） |
| G-45 动态装载 | 小程序**代码包** = DynamicBackendModule（下载 → 校验 → 装载 → 回放） |
| G-46 资源池 | **凭证 / 存储按 AppID 隔离**（RSC-01 凭证最小化），登录态宿主级共享 |
| G-47 组合一致 | 运行时 × 资源池 接缝测试（切小程序不动登录态） |

**G-48 不发明新 SPI 体系，全部复用既有 + 一份新的 `PlatformAdapter SPI`（本质是 NativeBackend 的小程序特化）。**

## 5. 诚实边界（先说清不承诺什么）

沿用 G-40（执行载体）/G-45/G-46/G-47 风格，**G-48 明确不承诺**：

1. **不承诺 100% API 兼容**——目标 **90%+ 标准 API**；平台特有能力（支付/登录/分享）走 Capability IR **显式适配**，给出**兼容矩阵报告**，不默默失败
2. **不承诺进程级沙箱**（本轮 MVP）——MVP 做**凭证 / 存储级隔离（AppID 级）**；**进程级隔离（V8 isolate / WASM）属 G-49**
3. **不承诺"任意第三方代码安全运行"**——MVP 面向**自有 + 受控第三方**；开放平台级安全责任属 G-50
4. **不绕过系统权限**——蓝牙/NFC/相机须走系统权限弹窗，框架只提供授权编排 SPI
5. **双线程架构是硬约束**——标准小程序假设 `AppService`（逻辑层）与 `WebView`（视图层）分离，**运行时必须真实实现**（MVP 可单进程模拟，但语义须正确）

详见 `05-adapter-pattern.md`（兼容矩阵）、`07-sandbox-isolation.md`（隔离分级）、`08-security.md`（信任模型）。

> **术语消歧（三组 L，勿混读）**：① 兼容级别 **L0-L3**（运行时兼容矩阵，`05-adapter-pattern.md`）；② 信任级别 **L1-L3**（自有/受控/开放，`08-security.md`）；③ 隔离强度 **L1-L4**（G-49 分层，本包 07 = **L1 基线**：AppID 级逻辑隔离）。

## 6. 路线安排（G-48 / G-49 / G-50 分工）

```
G-48 ★ 本轮：兼容运行容器（整体方案 + 标准运行时骨架 + 微信 Adapter + MVP）
G-49      ：运行时内核深化（真双线程隔离 / 代码包分包加载 / setData 通道 / 进程级沙箱）
G-50      ：小程序开发者平台（IDE / 审核 / 开放平台 / 生态）—— 最后做，依赖 G-48+G-49 稳定
```

**G-48 的 MVP 范围**（已确认）：

- ✅ 微信 Adapter（几乎零适配，验证容器）
- ✅ 单进程**模拟**双线程（先验证架构正确，真隔离后置 G-49）
- ✅ 凭证级隔离（AppID 级，复用 G-46 origin 命名空间）
- ✅ 标准小程序结构解析（AppService / PageFrame / 生命周期 / setData）
- ⏭️ 进程级沙箱 → G-49
- ⏭️ 开放平台 / IDE / 审核 → G-50

## 7. 成功标准（G-48 落地后可验证）

1. 一份**标准小程序**（微信语法）能在自有宿主运行时里完整跑起来（页面渲染 + 逻辑层 + setData）
2. 同一份小程序**切换 Platform Adapter**（微信 ↔ 鸿蒙模拟）**业务逻辑零修改**
3. **平台特有能力**（login/pay/share）走 Capability IR，缺 Adapter 时**降级不崩溃**（原则 #4）
4. **AppID 隔离**：多小程序同宿主，凭证 / 存储互不泄漏
5. **G-46 登录态共享**：宿主登录后，小程序内 `login` 直接复用，无需重新授权
6. **兼容矩阵**：自动生成，标明哪些 API 直接可用 / 需适配 / 不支持
7. **conformance**：标准符合性测试 + 接缝测试（G-47 组合一致）全部 PASS

## 8. 小结

**G-48 的核心判断力**：与其造一个没人来的平台，不如**做一个能让数百万存量小程序直接跑的兼容容器**——用事实标准（微信）+ SPI 模式（Adapter）+ 既有体系（G-27/39/46/47），**把"超级应用"从愿景变成可执行架构**。

**这是方法论第 12 次泛化的载体**：「不绑定小程序运行时形态」——运行时定义标准接口，各平台提供 Adapter。与前 11 次完全同构（定义语义 + 后端实现 + conformance）。
