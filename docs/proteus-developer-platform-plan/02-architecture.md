# G-50 架构全景

> 接续 `01-problem.md`。本文定义平台的**分层结构**与**三条主线**，以及它们如何对接 G-48 / G-49。

---

## 1. 一句话架构

**G-50 = 三条主线围绕同一个"应用包（AppPackage）"运转：**

```
         ┌──────────────────────────────────────────┐
         │         ① 开发者门户（B 生态）             │
         │  注册 → 应用 → 版本 → 提审 → 上架          │
         └────────────────┬─────────────────────────┘
                          │ ① 提交 AppPackage
                          ▼
┌──────────────┐    ┌──────────────────────┐    ┌──────────────┐
│  ② 工具链(A)  │───▶│  AppPackage（核心工件）│───▶│ ③ 运行时(B)  │
│  CLI/脚手架/  │    │  manifest + 代码包 +  │    │  G-48 Runtime│
│  调试/能力生成 │    │  签名(G-45) + 配额    │    │  + G-49 沙箱 │
└──────────────┘    └──────────────────────┘    └──────┬───────┘
                                                      │ ③ 运行
                                                      ▼
                                            ┌──────────────────┐
                                            │  ④ 治理（B）      │
                                            │  风控/审核/下架/   │
                                            │  配额/审计/对账    │
                                            └──────────────────┘
```

**三条主线**：① 门户线（开发者的"后台"）、② 工具链线（开发者的"本地"）、③ 运行时线（用户的"手机"）。
④ 治理贯穿三者（所有操作可审计、可撤销）。

**一个核心工件**：`AppPackage`——它是三条线的**唯一接口契约**，也是 A 与 B 的解耦点。

## 2. 核心工件：AppPackage

```yaml
# app-package.yaml（规范定义见 05-project-scaffold.md）
packageId: com.example.demo    # 全局唯一
version: 1.0.0
sdkVersion: ">= 1.2.0 < 2.0"   # 语义化，对齐 G-48 兼容矩阵
capabilities:                   # ★ 显式能力声明（G-48 Capability IR 的静态化）
  - name: login
    adapter: wechat             # 走哪个平台 Adapter
  - name: payment
    required: true
  - name: bluetooth             # 受限能力 → 需审核（触发 10-submission-review）
    restricted: true
permissions:                     # G-49 CapabilityBridge 的静态声明
  storage: readWrite
  network: unrestricted
  device: [location, camera]
resources:                       # G-46 资源配额（G-49 ResourceQuota）
  quota:
    memory: 256MB
    storage: 100MB
    cpu: 20%                    # 单小程序 CPU 上限
signatures:                      # G-45 签名同源（双签名，见 10-submission-review）
  developer: <base64>           # 开发者签名（本地构建时签）
  platform: <base64>            # 平台审核签名（审核通过后签，运行时校验）
```

**AppPackage 的三个关键设计**：

1. **能力显式声明**（`capabilities`）→ 对接 G-48 Capability IR；未声明的能力**运行时直接拒绝**（G-49 deny-by-default）
2. **权限静态化**（`permissions` + `resources`）→ 对接 G-49 CapabilityBridge 与 ResourceQuota；**运行时不再动态授权**
3. **双签名**（`signatures`）→ 对接 G-45 签名同源；**开发者签名 + 平台审核签名**，任一缺失即拒装（与 G-45.8「manifest 哈希防 MITM」同源；G-45.9 仅限开发态，不延伸线上热更新）

> **诚实判断**：AppPackage 是把 G-45/G-46/G-48/G-49 的**分散约束收敛成一个可校验工件**——
> 这是 G-50 对前四份 plan 的**集成贡献**，也是组合一致（G-47）思想在"应用包"层面的投射。

## 3. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│  L5  开发者门户（B）   注册 / 应用管理 / 密钥 / 成员      │  ← 09-developer-portal
├─────────────────────────────────────────────────────────┤
│  L4  治理层（B）       审核 / 风控 / 分发 / 下架 / 对账    │  ← 10-12
├─────────────────────────────────────────────────────────┤
│  L3  工具链（A）       CLI / 脚手架 / 调试 / 能力生成 / 发布 │  ← 04-08
├─────────────────────────────────────────────────────────┤
│  L2  运行时            G-48 Runtime + PageFrame          │  ← G-48（复用）
├─────────────────────────────────────────────────────────┤
│  L1  沙箱              G-49 Sandbox（L1–L3）+ 多租户      │  ← G-49（复用，核心依赖）
├─────────────────────────────────────────────────────────┤
│  L0  宿主              G-39 HostRuntime + G-46 资源池     │  ← 复用
└─────────────────────────────────────────────────────────┘
```

**关键观察**：G-50 的 **L0–L2 几乎全部复用既有 plan**（G-39/46/48/49），
**真正新增的是 L3（工具链）+ L4（治理）+ L5（门户）**。

> 这印证了方法论的复利：**前四份 plan 的 SPI 设计，让 G-50 只需"组合 + 封装"即可成型，
> 无需发明新的运行时机制。** 这是 uni-app/Taro 做不到的——它们的工具链与运行时耦合，
> 每加一个生态能力都要改编译器。

## 4. 三条主线的接口契约

### 4.1 线 ① → ②（门户 → 工具链）

开发者在门户创建应用 → 下载 `proteus.config.ts` + 密钥 → 本地用 CLI 开发。

**接口**：`DeveloperAPI`（09-developer-portal.md 定义）
- `createApp / listApps / rotateKey / manageMembers`
- 所有调用过 **G-42 安全网关**（能力调用网关，host-container 复用）

### 4.2 线 ② → ③（工具链 → 运行时）

CLI `proteus publish` → 上传 AppPackage → 审核 → 分发到运行时。

**接口**：`PublishPipeline`（08-publish-runtime.md 定义）
- 构建 → 静态扫描 → 签名 → 上传 → 审核回调 → 生成 CDN URL
- 产物格式 = G-48 Runtime 的输入规范（**直接对接，无需适配**）

### 4.3 线 ③ → ④（运行时 → 治理）

运行时加载 AppPackage → 上报运行指标 → 触发风控/配额/审计。

**接口**：`GovernanceSPI`（12-governance-monetization.md 定义）
- `reportMetrics / checkQuota / auditEvent / revokeApp`
- **配额执行复用 G-49 ResourceQuota**；**审计复用 G-49 的 ISOLATION_BREACH 检测**

## 5. 多租户隔离：G-49 的规模化

G-49 定义了"单个小程序的隔离"。G-50 把它**扩展到多租户**：

| 维度 | G-49（单小程序） | G-50（多租户） |
|------|-----------------|----------------|
| 隔离单元 | 一个 PageFrame | **一个 AppPackage（packageId）** |
| 存储 | appId 目录 | **packageId 二级目录**（G-46 资源池按 `developer/package` 隔离） |
| 配额 | 单实例 ResourceQuota | **全局配额池**（总内存上限 + 单包上限，防单租户耗尽） |
| 崩溃 | 单实例 Drop 级联 | **跨包隔离**（一包崩溃不影响其他包 + 宿主） |
| 凭证 | 单包 Cookie/Token | **开发者级 + 应用级二级隔离**（09 定义） |

**核心铁律（G-50.2，详见 rules.md）**：

> **一个 packageId 的资源，只有该 packageId 的代码可访问；宿主凭证与小程序凭证永不通透。**

这是 G-46「凭证按 appId 隔离」+ G-49「跨小程序零共享」的**直接推广**——又一次方法论泛化，
即原则 #0「不绑定」的**第 14 次应用**（沿小程序系列计数：G-46=10 / G-47=11 / G-48=12 / G-49=13）。

## 6. 分期与依赖图

```
G-49 L3（真原生隔离后端）──┐
                            ├──▶ Phase 2 起点（B 生态可用）
A 工具链（04-08）──────────┘
         │
         ├──▶ Phase 1 产物：自有小程序可开发/发布/运行
         │
         └──▶ 持续可用（即使 Phase 2/3 暂缓）

Phase 1（A，可立即启动）         Phase 2（B，等 G-49 L3）      Phase 3（长期）
─────────────────────          ──────────────────────        ──────────────
04 CLI 流水线                  09 开发者门户                 运营后台
05 项目脚手架                  10 提审与审核                 数据平台
06 调试协议                    11 分发与运行                 开放 API
07 能力脚手架                  12 治理与分佣                 插件市场
08 发布与运行                  ──────────────────────
                            ──────────────────────       ★ 非阻塞
```

**关键路径**：`08 发布` 是 A→B 的桥接点；`11 分发` 依赖 G-49 L3；**其余 A 工具链可独立落地**。

## 7. 与既有体系的互校（无冲突，复用为主）

| 体系 | G-50 复用点 | 新增 |
|------|-----------|------|
| devtools（G-34） | TraceBus / 调试协议 | 门户化（多人协作调试） |
| cli-plus（G-33） | `proteus create/dev/build/check` | **扩展 publish/audit/submit** |
| G-42 安全网关 | 能力调用网关 | **开发者 API 网关** |
| G-45 签名同源 | 签名校验机制 | **双签名（开发者 + 平台）** |
| G-46 资源池 | origin 命名空间 | **developer/package 二级隔离** |
| G-47 组合一致 | 接缝测试思想 | **INT（工具链 × 运行时）** |
| G-48 Runtime | PageFrame / setData / Adapter | **多租户 PageFrame 调度** |
| G-49 Sandbox | L1–L3 / CapabilityBridge / Quota | **规模化（全局配额池 + 跨包隔离）** |

**复用率极高**——这正是"先做好基础、再做平台"的复利。
