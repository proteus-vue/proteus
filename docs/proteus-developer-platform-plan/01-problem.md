# G-50 小程序开发者平台 — 问题定义与定位

> **编号**：G-50（小程序系列收官篇）
> **依赖**：G-48（兼容式运行容器）、G-49（进程级沙箱 L1–L3）
> **硬前置**：G-49 L3 落地 + 真原生隔离后端（原则 #13.44：由 G-49 定义，出处见 §3.3）
> **本文档范围**：**仅 plan**，不含参考实现、不含 verify.sh、不含打包脚本与 zip

---

## 1. 一句话定位

**G-50 = G-48（运行容器）+ G-49（隔离）的"开发者界面"与"生态界面"。**

G-48 让标准小程序**能跑**，G-49 让不可信小程序**安全运行**。
但这两份 plan 都**没有定义"谁来开发、怎么发布、怎么治理"**——

> 一个能安全运行第三方小程序的容器，如果没有**开发者注册 → 应用管理 → 审核 → 发布 → 运行 → 治理**的闭环，
> 它就只是一个 SDK，不是一个**平台**。

G-50 补齐这条闭环。它是 Proteus 超级应用能力从"**自用**"走向"**生态**"的唯一缺口。

---

## 2. Scope：A + B 都要（本次明确）

G-49 完成后，开放 G-50 资格的条件已明确（原则 #13.44，由 G-49 定义）。但"开发者平台"在上一轮被识别出
**两种完全不同的东西**，本次一次性全部覆盖：

| 子集 | 名称 | 对标 | 核心问题 |
|------|------|------|---------|
| **A** | **开发者工具链平台** | uni-app CLI / Taro 脚手架 / Vue DevTools | 让开发者**能高效开发、调试、构建、发布**一个小程序 |
| **B** | **开放生态平台** | 微信公众平台 / 字节开放平台 / 支付宝开放平台 | 让**任意第三方**能注册、提审、上架、被用户使用 |

**A 是 B 的子集与前置**：没有 A 的开发者工具链，B 的生态无从谈起。本次 plan 同时覆盖 A 与 B，
但**明确分册**：A = 文档 04–08（A1–A5 五份）、B = 文档 09–12（B1–B4 四份），
03-spi 为 A+B 共用 SPI（不重复计数），允许分阶段落地。

### 与既有 devtools（proteus-devtools-plan / proteus-devtools-plus-plan，官方 G-34）的关系：升级，不重复

体系内已有 `proteus-devtools-plan`（DevTools 本体，聚焦 **TraceBus + 调试面板**）
与 `proteus-devtools-plus-plan`（官方 **G-34**：HMR + DevTools 协议）。
G-50 **不重复** devtools 系列的运行时调试能力，而是：

- **复用** devtools 系列的 TraceBus / DevTools 协议作为 A 的调试底座（见 06-debug-protocol.md）
- **扩展** devtools 未覆盖的：**CLI 流水线、发布运行、开发者门户、审核治理**
- **新增** devtools 完全没有的：**B 的全部（开放生态、应用市场、审核、分佣、运营）**

> **一句话**：devtools = "运行时的透明化"，G-50 = "把透明化封装成平台 + 开放给第三方"。

## 3. 为什么必须是现在（必要性论证）

### 3.1 前四份已闭环"技术能力"，缺"组织能力"

```
G-27 渲染一致（外）
G-46 数据一致（内）
G-47 组合一致（接缝）
G-48 小程序运行时（兼容容器）
G-49 进程级沙箱（L1–L3，安全运行前提）
        ↓  技术闭环已完成
★ G-50 开发者 + 生态平台   ← 本次：把技术闭环"产品化/生态化"
```

**如果停在 G-49**：Proteus 具备"安全运行任意小程序"的能力，但**只能自己用**——
新接入一个开发者，需要手写 SDK 调用、手写发布流程、手写审核规则。
**这不是一个平台，这是一个内部工具。**

### 3.2 "超级应用"的商业闭环要求 B

A（工具链）能让**自己的团队**高效开发小程序；
但"超级 App"（微信/支付宝/抖音）的核心价值是**第三方生态带来的网络效应**。

> **诚实判断**：A 是"提升自身效率"，B 是"建立生态壁垒"。
> 二者工作量差距一个量级（B 巨大），但**A 是 B 的必要前置**，不能跳过 A 直接做 B。

### 3.3 G-49 L3 是 B 的安全资格（不可绕过）

B（开放生态 = 运行任意第三方代码）**必须**以 G-49 L3（进程级隔离）为硬前置：

- 没有 L3，恶意小程序可穿透沙箱 → 窃取宿主凭证（G-46 资源池）→ **平台级安全事故**
- 原则 #13.44 由 G-49 定义（出处：`docs/proteus-sandbox-isolation-plan/architecture-update.md`），整合入库后并入总规约：*"G-50（开发者平台）的'运行任意第三方代码'资格，以 G-49 L3 落地为硬前置"*

**因此 G-50 plan 的结构是**：A 可立即启动（不依赖 L3），**B 的关键路径（运行第三方代码）必须等 G-49 L3 真原生后端落地**。
这是 plan 内的**显式分期**，不是模糊的"以后再说"。

## 4. 竞品横向：同类方案的能力缺口

| 能力 | 微信开放平台 | uni-app CLI | Taro | **Proteus G-50** |
|------|:--:|:--:|:--:|:--:|
| 标准小程序运行时 | ✅ | ⚠️（编译到各平台） | ⚠️（编译到各平台） | ✅（G-48） |
| 进程级沙箱 | ✅ | ❌ | ❌ | ✅（G-49 L3） |
| 凭证/登录态共享 | ✅ | ❌ | ❌ | ✅（G-46 + G-48） |
| 运行时调试面板 | ✅ | ⚠️ | ⚠️ | ✅（devtools-plus（G-34）复用） |
| 能力语义收敛（Capability IR） | ❌（wx 绑定） | ⚠️（条件编译） | ⚠️（条件编译） | ✅（G-48） |
| 跨页渲染后端切换 | ❌ | ❌ | ❌ | ✅（G-27） |
| **以上全部的组合一致性验证** | ❌ | ❌ | ❌ | ✅（G-47 + G-50 conformance） |

**关键差异**：竞品的"工具链"和"运行时"是**两套独立系统**（微信 DevTools ≠ 微信运行时），
Proteus 的 G-48/49/50 **共用一套 SPI-First 方法论 + 同一 Capability IR + 同一 conformance 验证**。

> 这恰是"**为什么先行者被锁死**"：微信的 `wx.*` API、审核规则、运行时是**一体但不可拆解**的耦合，
> 第三方无法复用其运行时而不接受其 API。Proteus 把它们**分层解耦**——
> **运行时（G-48）可独立用、工具链（G-50 A）可独立用、生态（G-50 B）是可选叠加**。

## 5. 诚实边界（先说清不承诺什么）

沿用「未实测不宣称」纪律（CMP046，源自官方 execution-carrier-plan / G-40）、
G-45（签名同源）、G-46/G-49 的诚实边界风格，**明确写入铁律**：

1. **G-50 承诺"平台架构与闭环"，不承诺"已具备微信级生态规模"**——
   生态规模依赖运营与网络效应，非架构可解决
2. **B 的运行安全依赖 G-49 L3 真原生后端**；在 L3 未落地前，B 的"运行第三方"环节为**受限灰度**
3. **审核 / 内容治理 / 风控是长期运营能力**，plan 只定义**机制与 SPI**，不承诺审核准确率
4. **分佣 / 结算涉及资金合规**，属**业务层**，plan 只提供**对账数据 SPI**，不内置支付结算
5. **开发者门户的 UI/UX 不在 plan 范围**，只定义 API 与数据模型
6. **本份 plan 不含可运行参考实现、不含 verify.sh、不含打包**——
   验证方式见 `conformance.md`（文档化断言清单，不写 runner）

## 8. 路线总览（A 先行，B 后置）

```
Phase 1（A 工具链，可立即启动，不依赖 G-49 L3）
  ── 04 CLI / 05 脚手架 / 06 调试 / 07 能力生成 / 08 发布
        ↓ 完成后：自有团队可高效开发 + 发布小程序

Phase 2（B 生态，关键路径等 G-49 L3）
  ── 09 门户 / 10 审核 / 11 分发 / 12 治理
        ↓ 完成后：第三方开发者可注册 → 提审 → 上架 → 运行

Phase 3（规模化，长期）
  ── 运营后台 / 数据平台 / 开放 API / 插件市场
```

**Phase 1 的产物（CLI + 脚手架 + 调试 + 发布）本身就是可用的"小程序 SDK"**——
即使 Phase 2/3 暂缓，Proteus 也已具备"打造属于自己的小程序"的完整能力（回到你最初的目标）。
