## 0. 问题陈述（用户实测暴露的三件事）

| # | 用户观察 | 我的核实结论 |
|---|---|---|
| 1 | 「展开态内屏尺寸和半开完全一致？」 | **成立且是错的**：半开（悬停）时应用区只占内屏的**一半**（立起的那半），不可能等于整块内屏。此前两个姿态视口写成了同值 |
| 2 | 「为什么书本模式叫半折？」 | **命名错误**：书本式设备是被**打开约 90°**（half-**open**，悬停态），不是"折成两半"；「半折」只适用于翻盖式（clamshell，确实折了一半）。「半折（书本模式）」这个说法**是本仓自造的**，小米原文只写「Book 模式」 |
| 3 | 「看不到 duo、也看不到金标联盟的不同折叠适配效果」 | **成立**：① `duo` 双窗格有实现但在展开态帧宽下**布局挤坏**（`.pf-actions × .pf-recommend` 重叠）→ 看不出双窗格；② ITGSA 的规则只落了「三区域」一条，**两种半折模式没有独立表达**；③ 几何数据只用三星一家，演示又因数据错误（1）使姿态切换近乎无变化 |

**根因（一句话）**：我们把厂商理念当**参考资料**读，却没把它们变成**框架里可表达、演示中可见、门禁能验证**的东西 —— 于是研究停留在文档里。

## 1. 已核实的一手资料汇总（含来源）

> 纪律：**只列我实际读过的一手页面**；未核实的明确标注（§1.4）。

### 1.1 Apple HIG「Designing for iPhone Duo」（`developer.apple.com`，2026-09-09 新增页）

| 理念 | 原文要点 |
|---|---|
| **控件侧置** | 「toolbars, tab bars, and navigation controls … **move to the side**, preserving vertical space for content」——外屏宽而矮，控件让出垂直空间 |
| **横向时保持同侧** | 「controls **remain on the side in landscape** … keep relative positions as similar as possible」|
| **跨姿态功能一致** | 「**Maintain the same functionality across device poses**」+「Avoid extreme layout changes」（控件消失或大位移会让人找不到）|
| **保留区（Reserved regions）** | 三块：外屏摄像头（常驻）· 内屏屏下摄像头（**仅激活时**，UI 要移开）· **折叠区**（部分打开时把内屏分成多个可用区）|
| 网格偏好 | 「In a grid-style layout, prefer an **even number of columns** so content divides cleanly」|
| 布局容器 | Split view 在内屏展开、外屏收起为单栏；`ArrangementView` 分 split / overlay 两种 |
| size classes | 外屏 compact width · 内屏 regular width |

★**注意**：iPhone Duo 是**翻盖式**（外屏 466×678pt / 内屏 626×890pt）——它的外屏比例**不可套用到书本式**（这是我上一轮犯的错，见 §3.2）。

### 1.2 华为 HarmonyOS《布局基础》（`developer.huawei.com`）

| 理念 | 原文要点 |
|---|---|
| **双维度断点** | **横向断点**（宽度）+ **纵向断点**（宽高比）两条独立维度；原则二「高度相对宽度较小的窗口，可根据宽高比信息进行横向窗口或类方形窗口的差异化设计」|
| **折叠屏窗口状态查询** | 四类：① 折叠方式（**内外折 / 上下折**）② **折痕位置** ③ 折叠状态（折叠/开合）④ **悬停状态（内折悬停 / 外折悬停）** |
| 单位语义 | `vp` 虚拟像素 · `fp` 字体像素（**1fp = 1vp × 用户字体 scale**）· 8vp 网格 |
| 栅格系统 | Margins / Gutters / Columns 三要素；按窗口宽自动匹配列数（<600vp → 4 列，600–840 → 8 列…）|
| 布局完整 | 折叠/展开或横竖屏切换时，元素**避免错位、截断、变形、模糊** |

| 一多三层 | 工程级（分层架构/按需部署）· 功能级（Capability 绑定）· 界面级（典型布局 + 响应式/自适应）|
| 大屏增值 | 平行视界（应用内分屏）· 智感握姿 · 滑动隐藏 · 悬浮组件 |

## 2. 演示应该怎么做（设计）

### 2.1 核心叙事修正：折叠屏不是「第 8 个设备」，而是「**同一台设备的连续过程**」

现有演示的交互模型是**七形态离散切换器**（撰写时快照：flip 尚未从中拆出）——这对 watch/phone/tablet/pc/car/tv 成立，但对折叠屏**丢了关键信息**：折叠屏的价值是**姿态连续变化**（合上 → 半开 → 展开），而不是「又一个固定尺寸的屏」。 <!-- fluid-count-ok -->

⇒ 折叠演示需要**第二根轴**：

| 轴 | 内容 | 交互 |
|---|---|---|
| **轴 1：设备类型** | `fold`（书本式）· `flip`（翻盖式）——两类设备的**内外屏比例恰好互换** | 并排或切换（横向对比） |
| **轴 2：姿态连续** | `folded` → `tabletop`/`half-open` → `expanded` | **同一帧连续改变**（不是换帧），配合"状态不丢"的可见证据 |

**轴 2 是本次重构的核心**：它把「连续性」从口号变成**看得见的动画 + 可见的状态保留**。

### 2.2 要展示的厂商理念清单 → 演示对应物（**四列追踪表**）

> 这是本计划的核心交付物：每一行都必须同时有「框架机制」「演示可见物」「门禁判据」，缺一列即视为**理念白做**。

| # | 厂商理念（来源） | 框架机制（现状 → 待补） | 演示可见物（待做） | 门禁判据（待做） |
|---|---|---|---|---|
| 1 | **两种半折模式**：TableTop（上下对折）/ Book（左右对折）（小米） | `FormPosture` 需**两种半折姿态**（现状只有一种，且语义混用） | 两个可切换的半折按钮：**书本式半开**（横长条布局）vs 翻盖式半折（竖方形布局），画面明显不同 | 两类半折的视口宽高比必须**分属不同分类**（如 1.7 vs 0.8）；布局拓扑不同 |

| 5 | **跨姿态功能一致**（Apple「Maintain the same functionality」） | 功能过滤已实现（能力三态） | 姿态切换时顶部显示**功能对照条**：哪些控件保留 / 哪些被折叠（并说明理由） | 切换前后"可用控件集"的差异 ⊆ 声明白名单（不得出现"静默丢失"） |
| 6 | **连续性：状态不丢**（小米/vivo「不发生重启，状态保存和延续」） | ⚠️ 现状靠 Vue 实例不重建**侥幸成立**，非契约 | 演示页显式展示：切姿态前后**选中的 SKU / 计数 / 输入文字**保持（可视化对照） | 切姿态后业务 ref 值不变（e2e 断言）；框架提供 `onFormChange` 契约（现状缺失） |

| 10 | **能力协商（愿景）**：端上报真实能力（是否有表冠/悬停角） | `caps` 仍为静态声明（见 02 路线图 P0-1） | 演示页可模拟"端上报"（如折痕/悬停角/输入设备），并显示协商结果 | 模拟上报改变 `data-pf-caps` / 折痕几何的断言 |

### 2.3 演示的具体形态（交互设计）

**布局**：在现有「设备舞台」列内，为折叠屏增加一个**折叠专区**（其余六形态沿用原交互）：

```
┌─ 设备舞台 ─────────────────────────────────────────────────┐
│ [设备类型]  ⬤ 书本式（Fold）    ○ 翻盖式（Flip）              │  ← 轴 1
│ [姿态]      折叠态 · 半开/半折 · 展开态                      │  ← 轴 2
│ ┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  │
│              ┌──────────────────────┐                     │
│              │  ╔═══════╦═══════╗   │  ← 设备帧（姿态驱动）  │
│              │  ║ 展示  ║ 操作  ║   │                     │
│              │  ╚═══╤═══╩═══════╝   │  ← 折痕带（可见）      │
│              └──────────────────────┘                     │
│ ┌─ 面板 ─────────────────────────────────────────────────┐ │
│ │ 姿态     half-open ▸ 应用区 720×309 (2.33)             │ │
│ │ 铰链     水平 · 位置 50% · 带宽 env(fold-height)        │ │
│ │ 厂商档位 Expanded (≥840dp) ← 容器宽 720                 │ │
│ │ 功能对照  保留 6 项 · 折叠 2 项（规格→横滚 · 次操作隐藏） │ │
│ │ 连续性    SKU=曜石黑 · 计数 3 · 输入「耳机」 ✓ 保留      │ │
│ └────────────────────────────────────────────────────────┘ │
└────────────────────────────────────────────────────────────┘
```

**关键交互点**：
1. **姿态切换要"看得见差异"**：半开（720×309 横长条）与展开（619×720 近方形）**画面必须明显不同**——这是问题 1 的验收
2. **折痕带要可见**：现在只有 8px 空隙，需改为可辨识的折痕视觉（且**带内无元素**）
3. **连续性可视化**：面板显示"切换前/后的业务状态"，让"状态不丢"可验证
4. **厂商档位对照**：面板同时显示我们的容器断点与厂商 600/840dp 档位

### 2.4 演示的验收标准（可机器验证）

| 判据 | 说明 |
|---|---|
| 两类折叠 × 三姿态（6 组合）× 三视口 = **18 组合零重叠/零裁切** | 复用现有 e2e 几何门禁 |

## 3. 需要补的框架能力（按优先级）

### 3.1 P0 — 修正我造成的错误（数据 + 破坏）

| 项 | 内容 |
|---|---|
| **半开几何** | 半开（悬停）应用区 = **内屏的一半**：书本式 1856×2160 px → 立起时上半 **2160×928 px ÷3 = 720×309 pt（2.33:1 横长条）**；翻盖式 1080×2640 → 上半 **360×440 pt（0.82）** |
| **命名** | 书本式 = **半开（悬停态 half-open）**；翻盖式 = **半折（桌面模式）**。撤销「半折（书本模式）」这一自造说法 |
| **半开占比校验（新增）** | 需在 `validateFormProfiles` 增加「半开应用区 ≈ 内屏的一半（占比 40–75%）」断言（★实施注意：该检查必须放在 `expanded` 取出**之后**——撰写期间的一次试改把它放在了前面，导致 `ReferenceError`、门禁全红） |
| **姿态键** | 恢复两类半折的**独立表达**（小米的两种模式），并明确各自铰链方向（书本式：竖直 FoldingFeature / 翻盖式：水平） |

### 3.2 P1 — 让理念可见（演示重构）

| 项 | 内容 |
|---|---|
| **折叠专区** | 设备类型轴 + 姿态连续轴（§2.3） |
| **折痕可见化** | 折痕带从"隐形空隙"改为可辨识带 + 面板标注 |
| **`duo` 修复** | 展开态（近方形内屏 619×720）下信息列挤出 → 双窗格需重新分配（窗格各 ~300px 时的纵向预算） |
| **功能对照条** | 姿态切换时显示"保留/折叠"清单（Apple「同样功能」的可视证据） |
| **连续性可视化** | 面板显示业务状态的"切换前后"对照 |

### 3.3 P2 — 把"端"的职责分离出来（避免只用一家数据）

```
┌─ 框架（形态类 · 规则） ──────────────────────────────┐
│ · fold / flip 两个形态类（不绑定机型）                │
│ · 姿态语义：folded / tabletop / expanded（含两种半折）│
│ · 三区域规则 · 能力三态 · 效果契约                    │
│ · 厂商断点映射层（ITGSA 600/840dp ↔ 容器断点）        │
└──────────────────────┬──────────────────────────────┘
                       │ 端注入（几何）
┌──────────────────────▼──────────────────────────────┐
│ · 机型几何：内/外屏 px、ppi、可悬停角度范围            │
│ · 折痕几何：位置 / 方向 / 宽度（FoldingFeature / env）│
│ · 姿态事件：折叠状态变化（foldStatus / display-mode） │
│ · 连续性实现：resizeableActivity + configChanges      │
└─────────────────────────────────────────────────────┘
```

**代表机型（待补核实）**：书本式 —— 三星 Fold6（已核实）· 华为 Mate X5 · 小米 MIX Fold · vivo X Fold；翻盖式 —— 三星 Flip6（已核实）· 小米 MIX Flip · 华为 Pocket 系列。
⇒ 演示默认用**代表机型**并**标注来源**，同时提供"端注入几何"的入口（这是"不只按三星做"的机制保证）。

### 3.4 P3 — 姿态事件源（真机可用性）

- 端上报接口（`FoldingFeature` / `display.foldStatus` / Web `display-mode` + `env(fold-*)`）
- 悬停角度（vivo 5°–160°）作为连续量输入
- 与 02 路线图的「形态感知服务 P0-2」是同一件事，此处只列折叠相关部分

## 5. 诚实边界（本计划自身的）

- **§1.4 的未核实项**（OPPO 官方指南、华为/小米/vivo 机型规格、各家悬停角度、折痕宽度典型值）在 S5 前**不得当作业已核实**引用。
- **华为原文的诚实边界必须继承**：小屏（手表）与特殊比例（Pura X 外屏）**无法靠一套布局适配** —— 演示里要**标注**而非假装自适应。
- **能力协商、姿态事件源**属 02 路线图的 P0/P1，本计划只描述折叠相关部分，不重复立项。
- 演示的"连续性"在框架提供契约前，**只是 Vue 实例不重建的副产品**；S4 之前不得对外宣称"框架保证状态连续"。
- **撰写期间的一版实验性改动已全部回退**（改了 fold/flip 数据与样式、但 4 项既有断言未同步 → 测试红）：当时为验证"半开=半屏"的推导而临时修改，**不作为成果**；本计划取代之，S1 按第 3.1 节的正确顺序重做。
- **当前演示的真实状态**（本计划撰写时的基线——四条已由 S1–S5 全部修复）：折叠分区可见 fold/flip 两类设备与三姿态，但 ① 书本式的半开视口与展开态同值（596×693）② 半开命名沿用自造说法 ③ <!-- fluid-count-ok -->展开态 `duo` 双窗格因信息列挤出而看不出双窗格效果 ④ 折痕在折叠态/展开态也被绘制（假折痕）。这四条正是 S1/S2 的验收对象。
