## 0. 核心原则

### 0.1 三原则：别选比调优的场景，选能暴露架构代差的场景

从既有实测提炼的选例标准：

| 原则 | 说明 | 反例 |
|---|---|---|
| **① 节点规模要大** | O(n) vs O(1) 的差异只在 n 大时显现 | 单个卡片动画，谁都做得到 |
| **② 动画期间要有数据更新** | 动画在渲染线程、数据更新触发逻辑层 rebuild——所有框架的死穴 | 纯静态转场，无数据变化 |
| **③ 必须由手势驱动** | 暴露跨线程通信延迟 | 自动播放动画，不涉及输入延迟 |

**不满足这三条的场景，测出来所有框架都跑满 120FPS——白测。**

### 0.2 已踩过的坑：vsync 饱和

124.5 FPS 那组数据里 `p50 = p95 = p99 = 8ms`，三个分位数完全相同，不是"完美"，是**指标饱和了**：

被 vsync 锁死在 120Hz（8.33ms）时，只要没掉帧，每帧耗时就被量化成"一个 vsync 间隔"。**不管实际干 2ms 还是干满 8.2ms，都显示 8ms。**

| 你看到的 | 真实含义 |
|---|---|
| p99 = 8ms | 1231 帧里没有一帧错过 vsync（尾部延迟为零，含金量高） |
| p50 = p95 = p99 | **测不出还剩多少余量** |

**因此本规格的所有案例，主指标一律改为"每帧真实工作时长（work time）"，不用帧间隔。**

### 0.3 结论先行：不建议做纯短视频

**理由**：短视频滑动的瓶颈是**媒体管线**（视频预加载/解码/秒开、播放器实例管理、滑动与翻页衔接），不是 UI 框架。

做了会发现布局 0.08ms、复用率 0.997 这些优势**完全无处体现**——每次视野里就一两个视频，节点数极少。且 Flutter / RN / 原生都能做得很好，**测不出差异**。

**但"短视频 + 强交互叠加层"有意义**：滑动时叠加实时弹幕、评论流、点赞动画、商品卡浮层。这才是 UI 框架的活，是"大量节点 + 动画 + 高频数据更新"三重叠加。

## 2. B1 · 万级列表 → 共享元素飞入 → 手势返回（P0 主推）

### 2.1 为什么选它

**① 直接复用既有测试资产**
4000 行列表已在跑（124.5 FPS、复用率 0.997、掉帧 0.16%），不必从零搭。

**② 它是 Skyline 官方 demo 的套路**
Skyline 官方示例即「图片列表 → 查看页 → 手势放大/缩小/平移」。**同题竞技，对比才有说服力**——评测者可直接拿你的实现与官方 demo 对照。

**③ 三个环节各自打在不同痛点上**

| 环节 | 打中的痛点 |
|---|---|
| 万级列表滚动 | 节点复用率、GC 压力 |
| 共享元素飞入 | 几何信息本就在 Rust 侧，**无需跨边界查询**——路径比 Skyline / Web 都短 |
| 手势下拉返回 | 手势驱动延迟；且框架自动管理生命周期，无需手动 `didPop` |

### 2.2 场景定义

```
页面 A：图片列表
  - 4000 行，每行 40+ 元素，嵌套 10+ 层（沿用既有测试规格）
  - 每行含：缩略图、标题（多行）、作者、点赞数、标签组
  - 无限滚动加载

点击某行 → 页面 B：详情页
  - 共享元素：缩略图从列表位置飞入详情页大图位置
  - 转场时长 300ms，可配

页面 B 手势操作
  - 下拉手势驱动返回（进度跟随手指）
  - 松手后按阈值决定完成返回或回弹
  - 双指缩放、拖动平移
```

### 2.3 数据模型

```ts
interface FeedItem {
  id: string              // 稳定 key，禁止用 index
  coverUrl: string
  title: string           // 20-60 字，触发多行文本排版
  author: string
  likeCount: number       // B1+ 中持续更新
  tags: string[]          // 3-5 个
  commentCount: number    // B1+ 中持续更新
}
```

**规模参数（可配置，用于生成负载梯度）**：
- 行数：1000 / 4000 / 10000
- 每行元素数：40 / 80
- 嵌套层数：10

### 2.4 测量点

| 阶段 | 指标 | 采集方式 |
|---|---|---|
| 列表滚动 | 每帧 work time P50/P95/P99、掉帧率、复用率、GC 次数 | Perfetto + 自报打点 |
| 点击到转场启动 | 首帧延迟 | 高精度时间戳 |
| 共享元素飞入 | 每帧 work time P95、是否掉帧 | Perfetto |
| 手势拖动 | **输入到画面更新延迟**（ms，P95） | 触摸事件时间戳 → 提交帧时间戳 |
| 手势松手回弹 | 动画帧耗时 P95 | 同上 |
| 内存 | 峰值、滚动 5 分钟后增量 | dumpsys / Instruments |
| 长跑 | 5 分钟后 FPS 衰减率 | 自动化脚本 |

### 2.5 关键：手势延迟怎么测

这是最能暴露架构差异的指标，必须测准：

```
1. 触摸事件到达时的系统时间戳 T0
2. 该帧提交到渲染管线的时间戳 T1
3. 延迟 = T1 - T0
4. 统计 P50 / P95 / P99
```

**注意**：不能用"手指移动到画面变化"的主观感受，也不能用 JS 侧的 `Date.now()`（精度与线程调度都会污染结果）。

## 3. B1+ · 详情页实时数据更新（P0 升级，杀手锏）

### 3.1 做法

在 B1 的详情页里塞**持续变化的数据**：
- 点赞数每 100ms 跳动
- 评论数持续递增
- 在线人数实时刷新

**这样在手势动画进行的同时，数据层还在高频更新。**

### 3.2 为什么这是最锋利的一击

所有框架在这里会**两头打架**：
- 动画跑在渲染线程
- 数据更新触发逻辑层的组件重建（Vue 是组件级 rebuild，React / Flutter 同样）

而 Proteus：
- **槽位直写是 O(1)**（Vapor IR 方案 §3）
- **复用率 0.997 → 无 GC 抖动**
- 动画走 IR 指令，不经过 JS 求值（路由动画方案 §4）

**测法**：手势拖动详情页的同时，后台高频更新数据，观察掉帧率。

| 对照组预期 | 表现 |
|---|---|
| Vue / React | 组件 rebuild 与动画争抢，掉帧 |
| Flutter | Dart GC 在滚动/动画时频繁触发，公开长期未解问题 |
| **Proteus** | O(1) 槽位写入 + 无 GC，预计平稳 |

**这一项如果数据好看，是整个 benchmark 里最有说服力的一张图。**

## 4. B2 · 弹幕风暴（P1）

### 4.1 场景

视频/直播场景的弹幕层：
- 同屏 2000 / 5000 条弹幕同时移动
- 每条独立速度、独立位置
- 持续滚动 60 秒

### 4.2 为什么能暴露 O(n) vs O(1)

其他框架的两种做法都有代价：
- **全量 rebuild**：每帧重建数千节点，直接挂掉
- **每条建独立动画通道**：额外内存与调度开销

Proteus 的槽位直写是 **O(变化的元素数)**，天然适配。

### 4.3 测量点

- 每帧 work time P95
- 同屏弹幕数上限（找到掉帧临界点）
- 内存增量
- 与"位移动画"对比（位移/缩放是否走同一路径）

## 5. B3 · 多元素协同转场（P1）

### 5.1 场景

转场时**前后页面同时动画**（对应 Skyline 的 `primaryAnimation` + `secondaryAnimation`），且页面内数十个元素各走不同曲线：

```
页面 A（被推出）：整体下沉 + 缩放 + 淡出
页面 B（推入）  ：从底部上滑 + 圆角变化 + 内部 40 个元素错峰入场
```

### 5.2 为什么这是 0.08ms 的正面应用

这正是"全量重排 0.08ms"最直接的场景——**别的框架必须精心设计增量更新路径，Proteus 可以直接硬算。**

### 5.3 测量点

- 转场期间每帧 work time P95
- 是否掉帧
- 错峰元素数量梯度（10 / 40 / 100 个）

---

## 6. B4 · 滚动中高频数据更新（P1）

### 6.1 场景

长列表滚动 + 实时价格/库存跳动：
- 4000 行商品列表
- 每行价格每 200ms 随机变动
- 持续滚动

### 6.2 为什么针对 GC

Flutter 的 Dart GC 在滚动时频繁触发较长暂停是**公开且长期存在**的问题；在 120Hz 的 8ms 预算下，即使极短暂暂停也可见。

Proteus 复用率 0.997，**几乎不产生新对象 → 没有 GC 这个环节**。

### 6.3 测量点

- **GC 暂停次数与总时长**（★ 对 Flutter 对比时的杀手锏）
- 每帧 work time P99（尾延迟最能暴露 GC）
- 掉帧率
- 内存曲线（5 分钟）

## 7. B5 · 短视频 + 弹幕 + 商品卡浮层（P2）

### 7.1 定位

不要做纯短视频（理由见 §0.3）。做成**短视频 + 强交互叠加层**：

```
上下滑动切换视频（媒体管线）
  + 弹幕层（B2 的负载）
  + 商品卡浮层（动画 + 数据更新）
  + 点赞动画（手势驱动）
```

### 7.2 用途

综合展示，视觉冲击强，**适合演示与 Playground 挂载**。

不作为核心 benchmark——因为它混入媒体管线成本，归因不干净。

## 8. 统一测量口径（★ 最关键的一节）

### 8.1 主指标：不用 FPS，用 work time

| ❌ 不用 | ✅ 改用 |
|---|---|
| 平均 FPS | 每帧 **work time**（真实工作时长） |
| 帧间隔分位数（会被 vsync 饱和） | work time 的 P50 / P95 / P99 |
| — | **掉帧率**（错过 vsync 的帧占比） |
| — | **GC 暂停次数与时长** |
| — | **输入延迟**（触摸 → 提交） |

### 8.2 权威数据源优先级

沿用既有做法，明确优先级：

| 优先级 | 来源 | 用途 |
|---|---|---|
| 1 | **Perfetto / System Trace** | 渲染线程真实耗时（权威） |
| 2 | `dumpsys gfxinfo` | 帧统计（权威） |
| 3 | app 自报打点 | 分项归因（**需与 1/2 交叉校验**） |

> ⚠️ 上一轮 124.5 FPS 那组里"绘制 5ms"若来自 app 自报，可信度低于 gfxinfo —— 自报通常只统计自己的绘制调用，可能漏掉 Skia / GPU 侧真实耗时。**必须用 Perfetto 交叉验证。**

### 8.3 三项强制对照（不做则结论不成立）

| # | 对照 | 说明 |
|---|---|---|
| 1 | **Release 包** | debug 包不算数 |
| 2 | **中低端机** | 骁龙 6 系 / 天玑 700 级别。旗舰机上大家都漂亮 |
| 3 | **5 分钟长跑** | 看热节流后的衰减，这才是用户真实体验 |

**补充**：长跑期间还要记录**内存是否持平**（复用率 0.997 理论上应持平，需实测确认）。

### 8.4 环境控制（沿用既有成熟做法）

- 每次测试前**杀进程重启**
- 测试前**重启手机静置 2 分钟**
- 用 Perfetto 确认数据跑在**普大核**（跑到大核的数据作废）
- 监控设备温度防降频
- 普通包名，不预载，不预触发 JIT
- 区分初次安装与闲时优化两组数据

## 9. 与 Flutter / Skyline / Vue 的公平对照设计

### 9.1 现状问题

目前所有数字都是**自己测的**，没有跨框架同口径对照。要做成能被外界认可的 benchmark，**对照组的负载构造与口径统一是关键**。

### 9.2 公平对照的三条硬规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | **同一份业务逻辑，各自用目标框架最佳实践实现** | 不是"把 Proteus 代码硬翻成 Flutter"，那是故意让对手写错 |
| 2 | **同一台设备、同一轮测试、同一套采集方式** | 不能拿 A 设备测 Proteus、B 设备测 Flutter |
| 3 | **负载参数完全一致** | 行数、元素数、嵌套层数、数据更新频率、动画时长全部一致 |

### 9.3 对照组选择

| 对照组 | 对比重点 | 特别说明 |
|---|---|---|
| **Flutter** | GC 暂停、内存、深度嵌套 | Impeller 已成熟（iOS 3.16 起、Android 3.22 起默认），**别拿 Skyline 时代老印象比** |
| **React Native** | 长列表、JS 线程阻塞 | 新架构 + Hermes |
| **原生 UIKit / View** | 基线真值 | 定义"原生是什么水平" |
| **Skyline** | 小程序端对齐度 | **注意：这是"对齐"不是"超越"**（见 §9.4） |
| **Vue Web（浏览器）** | 正确性真值基准 | 用 `getComputedStyle` / `getBoundingClientRect` |

### 9.4 ⚠️ 分端表述，不能混

| 端 | 路由/动画实际执行者 | 能否"超越 Skyline" |
|---|---|---|
| 小程序 Skyline 端 | Skyline 自己 | ❌ **不能** |
| App 端 | Proteus 自己 | ✅ 能 |

**对外宣称必须分端**。混在一起说会被质疑，且是事实错误。

### 9.5 对照结果的呈现方式

**最能说明问题的一张图**：横轴为各框架，纵轴为 work time P95，同一负载下并列。

配合：
- GC 暂停次数（对 Flutter 的杀手锏）
- 内存峰值（Flutter 有引擎 + VM 固定税）
- 尾延迟 P99（最容易暴露架构问题）

## 10. 与 Playground 的联动

### 10.1 强烈建议：案例挂进 Playground

几个案例做完，直接挂进 Playground——**扫码就能在真机上体验**。

**这是最强的推广武器**：别人还在看你 PPT 里的 benchmark 数字，你已经让人**亲手滑到**那个列表了。

### 10.2 双重价值

1. **推广**：试用门槛归零
2. **验证**：Playground 是 Vapor IR 与路由动画方案的**最佳验证场景**——真机、真实业务、随时可复现，比本地跑 benchmark 有说服力得多

### 10.3 实现约束

- 案例产物必须是 **IR 产物**，不能是 Web 端 VDOM bundle（否则拿不到性能）
- 需在 manifest 声明所需能力（Playground 方案 §4.2）
- B1 的图片资源用 CDN，不进产物包

## 12. 验收标准

| 指标 | 合格线 | 目标 |
|---|---|---|
| work time P95（各案例） | ≤ 8.33 ms（120Hz） | ≤ 4 ms |
| 掉帧率 | ≤ 1% | ≤ 0.2% |
| 输入延迟 P95 | ≤ 1 帧 | ≤ 8 ms |
| GC 暂停次数（对 Flutter 对照） | 显著更少 | 近零 |
| 5 分钟衰减率 | ≤ 10% | ≤ 5% |
| 内存 5 分钟增量 | 持平 | 持平 |
| 中低端机 | 需单独出数据 | 不得只报旗舰机 |
| 数据来源 | Perfetto / gfxinfo 为主 | 自报仅作归因 |

## 13. 坑位清单

| # | 坑 | 应对 |
|---|---|---|
| 1 | **用 FPS / 帧间隔当主指标** | vsync 饱和，测不出余量。改用 work time |
| 2 | **app 自报当权威数据** | 必须与 Perfetto / gfxinfo 交叉校验 |
| 3 | **只测旗舰机** | 必须含中低端机，否则结论不成立 |
| 4 | **只跑 10 秒** | 必须 5 分钟长跑，看热节流 |
| 5 | **做纯短视频** | 瓶颈在媒体管线，UI 框架优势无处体现 |
| 6 | **对照组用"硬翻"实现** | 必须用各框架最佳实践，否则是不公平对照 |
| 7 | **跨设备对比** | 必须同设备同轮次 |
| 8 | **把 Skyline 端算成"超越 Skyline"** | 分端表述，见 §9.4 |
| 9 | **debug 包出数据** | 一律 release |
| 10 | **为大核优化的数据** | Perfetto 确认跑在普大核，跑到大核作废 |
| 11 | **忘记测内存是否持平** | 长跑必须记录内存曲线 |
| 12 | **GC 数据不采集** | 对 Flutter 对比时这是最有力的证据，必须采集 |

## 14. 给实现 LLM 的执行指令

1. **BM0 测量设施未完成前，禁止开始任何案例。** 没有可信测量，案例数据全是废数。
2. **主指标一律用 work time**，禁止用 FPS 或帧间隔作为结论性指标。
3. **所有数据以 Perfetto / gfxinfo 为权威源**，app 自报仅用于分项归因且必须交叉校验。
4. **必须包含中低端机与 5 分钟长跑**，缺一不可。
5. **对照组必须用各框架最佳实践实现**，禁止"硬翻" Proteus 代码。
6. **对外表述必须分端**（App 端自研 vs Skyline 端对齐）。
7. **不做纯短视频案例**，如做必须是"短视频 + 强交互叠加层"。
8. **B1+ 的实时数据升级必须做**——这是整个 benchmark 最锋利的一击。
9. **产物必须是 IR 产物**，不得用 Web 端 VDOM bundle 充当 App 端案例。
10. **每次测试执行环境控制流程**（杀进程、静置、核调度确认、温度监控）。

## 附：关键事实依据

- 既有实测基线：宿主侧 1ms；4001 节点全量重排 0.08ms（兄弟平移特调）；布局 0.063 / 绘制 0.667（4050 场景）；内存增量 0.328；长列表 124.5 FPS、复用率 0.997、掉帧 0.16%
- vsync 饱和现象：p50 = p95 = p99 = 8ms 表明指标被 120Hz（8.33ms）量化，无法反映真实余量
- 环境控制要点：release 包、杀进程重启、测试前静置 2 分钟、Perfetto 确认跑在普大核（跑到大核数据作废）、监控温度防降频、区分初次安装与闲时优化
- `dumpsys gfxinfo` 为权威帧统计源；app 自报需交叉校验
- Flutter：Dart GC 在滚动时频繁触发较长暂停为公开长期问题；Impeller 自 iOS 3.16 / Android 3.22 起默认，3.38 双平台稳定
- Skyline 官方示例为「图片列表 → 查看页 → 手势放大/缩小/平移」；`share-element` 实现共享元素转场，官方建议前后页面 share-element 子节点结构尽量一致
- Skyline 路由参数：`primaryAnimation`（推入 0→1）、`secondaryAnimation`（被推出 1→0）
- 短视频滑动瓶颈在媒体管线（预加载/解码/秒开、播放器实例管理、手势与翻页衔接），非 UI 框架
