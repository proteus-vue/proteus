Studio 的真实增量只在 `device.native` 与 `form.mobile`。

## 追问：G-55（devtools-landing 知识内核）能否做（同样只读取证）

**结论：能做，但 80% 成本在"补数据源/索引"，不在 Rust daemon。**

六方法数据源取证：
- ① `resolveCall` 语义跳转：落点已有（`slot-runtime/src/layout-template.ts:63,335` 的 `LayoutNode.loc`，dev-gated #713），
  但**无符号表/解析器** ⇒ 缺"谁调谁"。缺口中。
- ② `checkLayering`：`packages/*/package.json` **无 layer/rank 字段**（grep 零命中），分层只活在
  `docs/proteus-architecture.md` 的 G 表里 ⇒ 建 46 行映射表 + 门禁即可。缺口小（最容易）。
- ③ `locateAssertion`：**CMP 编号在代码里零命中**（只在 docs）⇒ tests 需加标记或建映射表。缺口中。
- ④ `buildGraph`：可从 package.json 依赖 + `docs/contract-index.md`(#1137) + `check:contract-index` 推导。缺口小-中。
- ⑤ `affectedDevices`：有 `docs/generated/capability-*`、三端能力对照、`capability-manifest.ts`，
  但"spiId→设备等价类"映射需新建。缺口中。
- ⑥ `previewVariants`：要跑真实渲染，plan 自承 Mock。缺口大（长期）。

**已存在的地基（比 plan 假设的厚）**：
- `packages/compiler-backend/src/g38-session.ts`：`createG38IncrementalSession` 已有 **cacheKey + 反向依赖索引
  + affectedFiles 闭包 + invalidate** ⇒ G-55 增量索引算法**照搬即可**，不必从零设计。
- `packages/mcp/src/stdio.ts` + `http.ts`：现成的协议层（stdio / Streamable HTTP）⇒ G-55 的
  "协议层 LSP/DAP/RPC/CLI" 里 RPC 档已实现。
- #1151/#1152 的持久层缓存（fetch-cache-persist + 字节 LRU）⇒ 冷启动索引的落盘底座现成。

**语言选型分歧（与 plan 05 相反，需实测）**：plan 说"Node 不推荐（CPU 密集/大内存）"，但本仓所有解析能力都在 TS
（compiler/component-ir/slot-runtime），Rust daemon 要么重写解析、要么只能当缓存层 ⇒ **建议先 TS/Node + 固定
JSON-RPC 接口，用计数断言（touched/recompute/hitRate）实测后再决定是否换 Rust**；本仓规模可估（723 TS 文件 /
约 46 包 / 31 页 conformance，十万级节点），先证明瓶颈再换语言，符合 G-55.6 / G-37。
