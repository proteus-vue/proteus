## 审查：柔性系统离「OS 级」还差什么 → `docs/fluid-system-gap-audit.md`

- **用户给出的核心判断**：目标是「**OS 极标准**，不是传统组件库那种堆叠」；柔性系统是多数跨端框架没做的；**安卓未来不再提供横竖屏查询方式** ⇒ 验证方向正确。
- ★**取证（本轮新做，官方原文）——判断成立且证据比"验证"更强**：
  - **Android 16（API 36）**：大屏（sw ≥ 600dp）**系统忽略** `screenOrientation` / `setRequestedOrientation()` / `getRequestedOrientation()` / `resizeableActivity` / `minAspectRatio` / `maxAspectRatio`；`Configuration.screenWidthDp/screenHeightDp` 不再排除系统栏，官方明说"用 Configuration 做布局计算一直不推荐，现在必须迁走"；`Configuration.orientation` 在**近方形设备**上间接受影响。
  - **Android 17（API 37）**：**移除选择停用**（`PROPERTY_COMPAT_ALLOW_RESTRICTED_RESIZABILITY` 失效），目标 API 37 必须适应任意尺寸/方向。
  - **Google 的替代**：`computeCurrentWindowMetrics` / `WindowInsets` / **WindowSizeClass（窗口级，非屏幕级）** → 与 Proteus 容器驱动**同向**。
  - **厂商指南在前**：小米《大屏 UX 指南》原文「**不要用 rotation，按宽高布局**」（本仓 04-closure §1.3 已登记）+ 华为双维度断点 ⇒ **厂商在前、OS 强制在后，两段独立信号同向**。
- ★★**本轮最关键的新发现（上游 04-closure/02-roadmap 未登记）——框架持有两套方向语义，且暴露了错的那个**：
  - `fluid/src/context.ts:43 resolveOrientation(w,h)` = **容器派生**（正确方向）；
  - `fluid/src/env.ts:30 matchMedia('(orientation: landscape)')` + `fluid/src/layout.ts:112 orientationchange` + `api/src/capability-bridges.ts:2642/2666/3991` = **视口媒体查询**（正是被取消的那类信号）。
  - `DeviceEnvState.orientation` 是**一等字段** ⇒ 业务可合法写 `if (orientation === 'landscape')`，而该表达式在 Android 17 大屏上**恒真或恒假**（静默错误）。两者还会互相矛盾（窄容器嵌横屏视口：context 说 portrait、env 说 landscape）。`resolveOrientation` 近方形退化为硬判 landscape，恰是 Android 点名失真的场景。
  - ⇒ **建议 A（成本最低收益最高）：把 orientation 降为一等→派生量**，matchMedia 版标注"Web 兼容层，不得作布局依据"，并在 `check-fluid-wording.mjs` 加**禁用语判据**（禁 `if (orientation === ...)` 式布局分支）。
- **五维体检**：① 信号源 **C**（三层感知模型里②环境探测③容器尺寸**均 Web-only**；`createFormFactor`/`senseForm`/`probePointer` **生产消费者 0**）② 语义层 **B**（`vendorSizeClass` 600/840×480/900 对齐厂商规范，但**没有一处读 OS 算好的窗口尺寸类**——自算而非消费系统结论）③ 多端落地 **C**（Web ✅ / **MP 🟡 L2 未接** / App·iOS·Android·鸿蒙 🟡 未接线）④ 治理 **B-**（FLD001-013 但 **FLD005 死尺寸明确未启用**；入口只有 `check:fluid-wording` 管文案；FLD 只扫 pages/src，**组件自身裸 px 漏网** —— p-formfactor 1410 行 / p-ad 裸 px）⑤ 契约 **C**（无 `onFormChange`/状态迁移/焦点滚动恢复）。

## 18:40 调研：iOS 液态玻璃对背景内容是"模糊"还是"磨砂"

**结论：都不是二选一 —— 是「模糊（blur）+ 折射（lensing）」的合成，模糊是基底、折射是识别特征。**

**证据分层（按可信度）**：
1. **WWDC25 session 219 官方原话**（最高）："It uses **Lensing**, which dynamically bends and concentrates light"、"composed of **multiple layers** that continuously shift tint, shadows, and dynamic range"、"simulates a thicker material with deeper shadows and **more pronounced lensing and refraction**"。
2. **UIKit 实现层硬证据**：`UIGlassEffect` 是 `UIVisualEffect` 子类、装在 `UIVisualEffectView` 上（⇒ 走系统**背景采样**管线，不是一层静态贴图）；且 **UIKit 不暴露 blur radius** ⇒ 模糊不由材质参数控制，而是**系统先在玻璃下方糊背景，玻璃再对"已糊的结果"做折射**（react-native-liquid-glassmorphism 作者跨端 0–25dp 实测对齐）。
3. **诚实边界**：Apple 官方概览文档（Adopting Liquid Glass）**从没把光学行为写清楚** —— 对玻璃背后内容只用 "peek through"（透出）/ "obscure"（遮蔽）；blur / refraction 仅出现在**应用图标图层**章节。lensing 这层只存在于 WWDC 视频。
4. 两变体：**Regular**（自适应磨砂玻璃，默认，用于导航/结构面）vs **Clear**（几乎不模糊、透明折射，**必须配 dim 层**保可读性）；HIG 明确**同一界面不得混用**。

**与毛玻璃的本质差别**（这是回答用户问题的核心）：
- 磨砂/毛玻璃 = **无方向散射**：把邻近像素加权平均 ⇒ 细节被抹平，只剩颜色印象。
- 液态玻璃 = **有方向折射**：像素被**搬移**（位移映射）⇒ 细节仍在，但在边缘被**弯折**。

**对 proteus 的落点（`pg-glass` / Aether 引擎）**：
1. 分层顺序与 Apple 同构：**blur 在底、折射在上**（照搬 Apple 做法即可，无需自创）——正好对上我们 L1「blur+tint 全端必达」/ L3「原生端真实边缘折射」的分档。
2. **Tint 不该是 rgba 平铺**：Apple 的 tint 是"按背景亮度映射出的色阶"（第三方采样实测 `glass_L = 0.58 × backdrop_L + 34`：黑底 L9→L37 = 抬亮 4.3×，亮底 L53→60 = 仅 1.13×）—— 可作为 tint 层数据驱动的改进点（来源：sohumsuthar/liquid-glass 复刻仓，非 Apple 官方数据）。
3. **CSS 做不到折射**：`backdrop-filter` 接受的 10 个函数（blur/brightness/contrast/drop-shadow/grayscale/hue-rotate/invert/opacity/sepia/saturate）**没有一个能移动像素** ⇒ 纯 CSS 只能做 L1/L2；折射必须 `feDisplacementMap`（Chromium-only）或原生自绘（Metal/AGSL/Vulkan）。**我们 guide 里已写的"Web/小程序无折射、原生端有折射"与 Apple 实际做法同构，方向正确。**
4. Clear 变体需 dim 层 —— 我们的 preset 表里可考虑加 `clear` 档并内建 dim。
