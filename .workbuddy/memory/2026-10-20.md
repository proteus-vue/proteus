## 10:0x 调研：用电视盒子验证框架原语（TV 端可行性与方案）

产出：`docs/Proteus_TV端验证方案与可行性调研.md`（未改源码）。

### 结论
- **值得做，但定位为「TV 焦点链 spike」，不是「做个 TV 应用」**；S1 只做一条链：
  方向键 → 焦点移动 → 焦点环 → 确认触发 → 焦点行滚动跟随，六条机测判据。
- **差异化不在「支持 TV」，在「焦点是一等原语 + 由形态画像推导」**。跨框架现状要诚实：
  react-native-tvos 是 Amazon 推的成熟 fork（Android TV+tvOS/Hermes/平台专有 focus 组件），
  Flutter 能跑 Android TV 且有 Focus 系统（focus/remote 成熟度不如 RN TV），
  Compose for TV 只管 Android，Lightning/Enact 只管 Web。没有「完美方案」，但有「成熟方案」。

### 本仓取证（关键）
- **已有（声明面完整）**：`fluid/formfactor.ts:491-511` 的 `tv` 画像（remote / hero-focus-row / focus-row /
  safe 96·54 overscan / 10ft / 暗色 / focus ring / baseFont 18 / caps dpad·focusRows·multiCol）；
  `fluid/focus-nav.ts:50` 的 `navigateFocus()` 纯函数（只吃矩形，天然跨端）；
  `components/p-formfactor/index.vue:301-448,1280-1365` 真接了 keydown→焦点→焦点环→热区放大→overscan；
  `component-ir/primitives.ts:59` L26 形态容器 implemented。
- **缺（App 端整条链为零）**：全仓 `onKeyDown`/`dispatchKeyEvent`/`KEYCODE_DPAD` 零命中（仅小程序 spec），
  Android 只有 `dispatchTouchEvent`；App CSS 无 `:focus-visible`、无 `@container`；
  layout-core-rust 无 focus 概念；Manifest 无 LEANBACK_LAUNCHER/banner/touchscreen required=false；
  native 只编 aarch64；C61 `useVideo` 在 App 仍 planned。
- **TV 不能验证「线程引擎」**（不多给线程），但能验证「执行原语/时间片」：长按重复 10+ 次/秒、
  无触摸反馈掩盖卡顿、1.5–2GB 内存。

### 技术要点（留给后续实现）
焦点链 = 内核 rects → `navigateFocus`（纯函数）→ 渲染器按 focusId 画环；宿主做键值归一
（19/20/21/22/23/4，OK 键可能是 23 或 66）；`ensureVisible` 必须与焦点同批（否则焦点跑出可视区）。
S2 判据 = 同一组 rects 下 Web 与 TV 焦点序列指纹一致。

### 待用户拍板
① 先 Android TV 盒子还是 tvOS；② S1 六条判据是否含「时间片」（含则把昨天的执行原语一起验）；
③ 盒子 ABI/Android 版本/内存（决定阈值）。
