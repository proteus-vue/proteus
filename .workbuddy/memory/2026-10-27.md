## 决策 #1285 · 终端"闪一下就全黑"的真因：`CSI J/K` 的缺省参数是 **0**，我按 1 处理

- 判据：把这份 **816 字节真实夹具**存进 `scripts/fixtures/term-zsh-startup.bin`，㊼ 里**分三块回放**

- ★自己写的断言也翻车一次：行数原先按 `textContent.split('\n')` 数 ⇒ 行是 div、拼接后没有换行符 ⇒ 恒得 1，

## 决策 #1291 · 修正 #1290 的误判：**静止 ≠ 断流**
- 现象：#1290 上线后，iOS 真机**不动屏幕就黑屏**（截图：0.0fps、空转拍 3778、徽标"手机端已停止推流"）；一动就恢复。
- 根因：**iOS 的 ReplayKit 是变化驱动的**——屏幕不变就没有帧，静止时 0fps 完全正常。
  我用"1.5s 没新帧"当断流判据 ⇒ 把静置手机判死。
- 修（把判据从"帧"换成"**链路**"）：
  · `live_stream.h`：读线程 `read()<=0`（管道 EOF）时置 `g_link_lost=1` —— 这才是真的断；
    收到新 AU 时清零（恢复）。
  · `embed_view.m`：断连只看 `g_link_lost`（抹一次黑 + `g_stalled`）；**删除静默时长判据**。
  · fps 语义改成"**当前是否在出帧**"：断连或 idle>1.5s ⇒ 0（"静止时显示 4.8fps 让人以为在跑"）。

    ★`running` **不能**包含 still（`.screen` 靠它决定透明洞，变 false 会盖住最后一帧）。
- 验证（两条对照，都用 `POC_STALL_DIAG=1`）：
  · A 静止：`sh -c 'cat x.h264; sleep 20'` ⇒ `idle=5436ms lost=0 stalled=0` —— **不变黑** ✅
  · B 断连：`cat x.h264`（EOF 即断）⇒ 日志「推流中断（手机端停止直播/连接关闭）⇒ 画布置空」✅
  · 门禁 **68/68**。
- 教训：**"没有数据"和"连接没了"是两件事**，判活要判链路，不能判流量。
  上一轮我把 #1290 的修复当成"完成"，但没覆盖"静止"这个正常态 —— 用户一动一静就抓出来了。

## 决策 #1296 · iOS 画面：灰底变白（颜色范围）+ 跟随延迟（Nagle/关键帧/码率）
- 现象：iOS 投屏里页面**背景全白**（手机上是浅灰）；且切页面半天才更新、"跟随"很慢（到达间隔 p95 766ms）。
- **白底根因**：着色器 `FS_YUV` 一律按 **limited range** 转：`y=(y-16/255)*1.164383`。
  而 ReplayKit/VT 给的是 **full range** ⇒ 浅灰(≈240) 被放大到 ≈261 截成纯白。
  修：加 `uniform uFullRange`，按 `frame->color_range==AVCOL_RANGE_JPEG` 或"源是 nc（iOS）"置 1。
  **客观验证**：用 `POC_DUMP` 把画布读回 PPM →「顶部灰底区 中位 **246**、纯白占比 **0%**」；
  卡片区中位 254（卡片本身是白）⇒ 灰底与白卡终于能区分（修前灰底会被截成 255）。
- **延迟三处**：
  ① **TCP_NODELAY**（最容易被忽略的一条）：手机端 socket 没设 ⇒ Nagle 攒小块等 ACK，稀疏帧被打散；
     adb 是本地管道根本没有这个问题。

- 教训：**"颜色不对"先查范围/矩阵，别先怀疑编码器**；这次是 shader 里的 16/255 硬编码。
- 注意：手动 `PROTEUS_IOS_STREAM_PORT` 启动**不会**起触控监听（9002 只由「一键投屏」里的 `ios_stream_start` 起）。

## 决策 #1319 · 镜像输入把用户鼠标"抢走"：全局 HID 投递改 `CGEventPostToPid`
- 用户实测：在画布上拖动时，**鼠标指针跳到镜像窗口里**，结果每次滑动都在滑镜像。
- 根因：`CGEventPost(kCGHIDEventTap, …)` 是**全局 HID 投递**——它会把**真实指针搬到目标坐标**
  并在那里按下/拖动。这是我的实现选择错误，不是 Apple 的限制。
- 修：`CGEventPostToPid(owner_pid, ev)` —— 事件**直接进目标进程队列**，不动真实指针、不抢焦点。
  同时**去掉 `activate` 窗口**（那个也会让 Studio 失焦）。
- 新错误码 `-3`：拿不到窗口属主 pid（镜像已断开）。
- 教训：**"模拟一次真实鼠标"和"把事件交给某个 app"是两件事**。前者必然动全局指针；
  凡是"用户正在用别的窗口"的场景，都必须用 PostToPid。

## 决策 #1322 · 镜像没画面 = **ScreenCaptureKit 服务卡死**（不是我们的代码）
- 判定链：
  ① 列表能秒级找到窗口（CGWindowList）✓；
  ② `cast` 的 stderr 落盘后看到它停在 `KCDEVICE …` 之后 —— **没到「流已启动」**，即卡在 `SCStream.startCapture`；
  ③ **用户在终端手跑同一条命令也一直卡住、零输出** ⇒ **不是 Studio 特有**，是整机 SCK 挂了。
- 诱因最可能：今天反复 `kill -9` 抓流子进程 + 内存紧张（`Pages free` ≈ 55MB），把 SCK 的跨进程服务（`replayd`）搞挂。
- 处理：`killall replayd`（会自动重启）→ 重新试抓；仍不行则**重启机器**。
- 教训：**抓流子进程不能用 `kill -9`**（我们为了加超时这么干过）。要么让它自己退（`--duration`），
  要么先发 TERM 再等一帧；强杀会把 SCK 服务带进坏状态，症状是"所有抓屏都不出帧、也不报错"。

## 决策 #1323 · 超时不能 `kill -9` 抓屏子进程（今天两次把整机 SCK 搞挂）
- 现象链：先后出现 ①`--list` 挂 8s、②镜像流停在 `KCDEVICE` 后不动、③**用户在终端手跑同样命令也卡住**
  ⇒ 判定为**整机 ScreenCaptureKit（replayd）半死**，`killall replayd` 无法恢复，只能重启 Mac。
- 我的错误：为了让 `run_with_timeout` 有硬上限，直接 `child.kill()`（SIGKILL）。抓屏子进程背后是系统
  常驻服务 `replayd`，强杀会让 SCK 的 XPC 通道进入"所有抓屏都不出帧、也不报错"的坏状态。
- 修：超时改为 **SIGTERM → 等 500ms → 仍在才 KILL**。
- 教训（与 #1322 同源）：**观测装置不能把被观测的系统服务打死**。凡是"为了加超时"而强杀系统进程，
  都要先问一句"它背后有没有常驻服务会被带坏"。

## 决策 #1328 · 滚轮延迟：debounce 用错了 + 每次注入 150ms 固定开销
- 症状：滚轮转了很久画布才动。
- 原因①（主因，我的错）：UI 侧写成了 **debounce**（每个事件 `clearTimeout` 重置），
  ⇒ 只有**停止滚动后**才发一次。滚轮要的是 **throttle/连续流**。
  修：第一个事件**立即发** + 发送期间继续累积 + 发完若有余量立刻再发（串行），末尾 80ms 补发尾巴。
- 原因②：`mirror_begin` 每次都 `activate` + `usleep(80ms)` ⇒ 每次注入 ~150ms。
  修：**已经在前台就不 activate**（只 `usleep(5ms)` 让出调度）。连续滚动时每次省 80ms。
- ★通用教训：**"合并事件"要用 throttle 不是 debounce**。凡是"用户持续输入 + 我按批发送"的场景
  （滚轮、拖拽、码率上报），debounce 都会让用户觉得"没反应"，直到他停手。

## 决策 #1329 · 滚动不够丝滑 ⇒ 改「滚动会话」（begin 一次准备，post 只发热路径）
- 症状：滚轮能用但一格格顿（"没有在镜像里直接滚那么丝滑"）。
- 根因：每条消息都走 `mirror_begin`（藏指针 + 激活 + 80ms 等待）+ `mirror_end`（还原指针 + 抢回焦点）
  ⇒ 单次 30~80ms，串行发送 = 有节奏的顿。
- 修：**会话化**
  · `begin`：一次准备（藏指针、激活镜像 app、把指针停到目标点）；
  · `post`：只投滚动事件（拆 4 小步，每步 4ms，接近触控板），单次 ~1ms；
  · `end`（停手 220ms 后）：还原指针与焦点。
  · UI 每 **16ms**（一帧）发一次累积量；全部调用走**串行队列**（begin<post<end 顺序有保证）。
- ★通用模式：**连续输入 + 每条都有准备工作** 时，把"准备/还原"提到会话边界（begin/end），
  中间只做热路径。这与拖拽、画图、视频采集的"会话化"是同一个手法。

## 决策 #1330 · 滚动的焦点抖动：滚动路径**根本不碰焦点**
- 症状：前几次滚动正常，之后**左上角菜单在 Studio / iPhone 镜像之间来回闪**。
- 根因：滚动会话复用 `mirror_begin`（activate 镜像 app），`end` 再 activate 回 Studio
  ⇒ 每次"开始/结束"都切换一次前台应用。会话频繁启停时就是连续闪烁。
- 关键认知：**macOS 的滚轮事件投给"指针下方的窗口"，不需要该 app 在前台**。
  ⇒ 滚动路径只需"藏指针 + 把指针停到目标点"，**一个焦点都不动**：
  `begin` 只记指针原位+藏指针+移到目标点（`front=0`）；`end` 只还原指针+显示（`mirror_end` 里 front==0 时不 activate）。
- 推论（要告诉用户）：既然不动焦点，**镜像窗口必须露出来（不被 Studio 完全遮住）**，
  否则滚动会落到盖住它的窗口上。

## 决策 #1331 · 滚动被遮挡 ⇒ 双通道（可见走 HID，被遮挡走 PostToPid）
- 症状：焦点正常后，滚动**完全不动**。推断：目标点最上层是 Studio（镜像窗口被盖住），
  HID 滚动落到 Studio 上了（而我们对 wheel 做了 preventDefault ⇒ 看不出任何变化）。
- 修：native `top_window_at(point)` 取该点最上层普通窗口（layer 0，列表前→后有序）：
  · 最上层 == 镜像窗口 ⇒ `CGEventPost(kCGHIDEventTap)`（丝滑）
  · 被遮挡 ⇒ `CGEventPostToPid(镜像 pid)`（不依赖"指针下方是它"，也不动焦点）
  通道切换时会打一行日志：`[mirror] 滚动通道 → PostToPid（被遮挡）（该点最上层=… · 镜像=…）`
- ★这条能直接取证：用户滚一下，日志就告诉我们是"没被遮挡"还是"被遮挡"，

## 决策 #1332 · "滚动时指针不断变化" ⇒ 滚动改成**完全不碰指针**（纯 PostToPid）

## 决策 #1334 · 镜像滚轮定稿：合成为**一次短滑动**（用户选定）

## 决策 #1354 · 「终端未打开」连环报错（有时候正常有时候刷屏）
- 现象：右下角一次叠 4 个「终端未打开」错误卡；有时又完全正常。
- 机制（三层）：
  ① Rust 侧会话是**单例**，"面板显示着" ≠ "会话还在"。切 shell（关旧开新）、推流中断后的重启、
     应用重启后面板被恢复成打开态 —— 任一发生 `SESSION=None`，之后任何按键都返回「终端未打开」。
  ② 面板被 `v-show` 藏起来时 `gridSize()` 可能量到 **0×0**，拿这个尺寸 openpty 只会得到畸形会话
     （或直接失败），于是"有时能开、有时开不起来"。
  ③ toast **本来就设计成堆叠**（"同类操作连点会叠起来"）⇒ 一次会话丢失 = 4 张同样的卡。
- 修：
  · `openSession()` 加**尺寸守卫**（cols≥8 且 rows≥3 才开，否则等 ResizeObserver 再来）；
  · 终端所有写入走 `writeToTerm()`：报「终端未打开」⇒ **自动重开 + 重试一次**（自愈）；
  · `pushToast` 加**同文案 1.5s 去重**（保留最新一条并重置计时器），不再刷屏。

  改样式时若发现"颜色不对但看着像写对了"，先 `grep` 变量是否真的存在。

## ★★事故与修复（16:2x）· 压缩提交时把别人 13227 行一起回退了
- 操作：`git reset --soft origin/main` + commit，想把自己 19 个提交压成一个。
- 事故：`origin/main` 在我 fetch 之后**又前进了**（鸿蒙侧 3 个提交 c27311ad/2f7e6f98…），
  而我的工作树**不含**那些内容 ⇒ `reset --soft` 把它们的差异当成"我的改动"，提交里变成
  **117 文件 / -13227 行**，并且已 push。
- 修复：`git reset --hard 2f7e6f98`（恢复他人内容，我的改动仍安全保存在错误提交对象里）→
  `git checkout <坏提交> -- <我的路径清单>`（只挑自己的 20 个文件）→ 重新提交 →
  `git push --force-with-lease`。现已确认：父链含鸿蒙提交、`tests/api.test.ts` /
  `harmony-host-keys.mjs` 都在，diff vs 2f7e6f98 只有我的 20 文件 +1241/-30。
- ★★纪律（写死）：**压缩/重排提交前必须 `git fetch` 并重新看 `origin/main`**；
  用 `reset --soft origin/main` 前先确认 `git diff origin/main --stat` 只有自己的文件。
  更稳的做法：先在**特性分支**上 squash，再 ff-merge/推送。
