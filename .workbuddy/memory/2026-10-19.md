## 17:5x 调研：要不要自研「运行时线程管理引擎」（结论：不自研引擎，改加执行原语）

产出：`docs/Proteus_运行时线程模型调研与决策建议.md`（未改任何源码）。

### 取证结论（可复用的事实）
- **三端都是单 VM / 主线程**：Android QuickJS（`QuickJsEngine.java:19-20` 明写非线程安全、eval 必须同线程；
  `quickjs_jni.c:39-41` 进程级 static `g_rt/g_ctx`）；iOS JSContext 由宿主驱动在主线程持有
  （`templates-host/ios/shell/ProteusApp.swift:69-75`）；**鸿蒙是一次性 VM**（每次调用建 VM→eval 整包→泵→销毁，
  决策 #540：持久 VM 跨 napi 调用必崩 `HandleScope::Extend`）。
- **G-39 线程模型早已定案**（`docs/proteus-host-runtime-plan/03-lifecycle-threading.md`：
  `runOnThread/createWorker/postMessage/enqueue/nextTick` + G-39.1/2 唯一拥有），
  且已有真实单线程实现 `packages/render-backend/src/quickjs-host.ts`（`threads.background=false`，
  后台调用**抛错记账**、`real:false` 逻辑 worker）。★**但它只被 `tests/quickjs-host.test.ts` 引用，
  未接进生产宿主**（与 #1094「做完了但没接上」同族）。
- 生产已有协作式调度雏形：鸿蒙 `AppRuntimeDriver.ets:150-160` 按 `eval_ms` 自适应批大小（目标 ~80ms/拍）；
  Android UI 泵每 tick `nativeRunPendingJobs()`（`AppActivity.java:231,621,...`）。
- **不可抢占**：`quickjs_jni.c` 无 `JS_SetInterruptHandler`（零命中）⇒ 线程不解决「长任务不可中断」。
- 泄漏可查形态：`quickjs-host` 的 `enqueue` 无上限、挂起时 `pumpFrame` 不推进（队列永久堆积）、
  static 单例只能靠 `resetEngine()`、无主订阅/定时器（G-43 已治一部分）。

### 给出的方案（P0→P3）
P0 长任务/队列水位/堆斜率观测 → P1 执行原语 `postTask/yield/chunk/cancel+deadline`（主线程协作、背压、取消）
→ P2 热点下沉原生（优先 bytes 通道 / patch / 编解码）→ P3 才考虑 `runOnThread('background')` 真后台
（硬前置：鸿蒙持久 VM；且只能服务可序列化的纯计算，Vue 响应式图过不了结构化克隆）。

### 校正用户前提
「主线程被占用 → 内存泄漏」不是一条因果链：占用 ⇒ 掉帧/ANR；泄漏 ⇒ 引用未释放。
调研文档 §1/§7 把两类指标分开，并要求先出基线再谈引擎。

### 待用户确认
具体卡的操作、单次时长、内存证据（是否回落/是否 OOM）——决定 P1 落点与 P2 排序。
