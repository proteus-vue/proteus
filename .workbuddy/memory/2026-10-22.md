## 决策 #1170：Studio PoC B2（Tauri 2 承载）—— 核心形态成立

**做了什么**：最小 Tauri 2 应用（2.12.5）——窗口里 WKWebView 做 UI（透明 + HTML 十字线/面板），
原生 `NSOpenGLView`（复用 B1 管线）垫在 contentView 最底层，30fps 主线程调度。

**实测（三轮 22s）**：`attach rc=0` · `webview found=1 transparent=1` · **30.34 fps** · 迟到 **0%** ·
间隔 p99 **44.5/49.6/45.2ms** · **合计 p50 1.36–1.44ms** · CPU **8.1–8.8%** ⇒ R1–R4 全过。

**与 B1 对账**：单帧成本持平（都 ~1.4ms）；但**间隔 p99 +8ms**（vsync 对齐变松），余量从 13ms 缩到 4ms。

**★六条踩坑（都实测过，写进 README 了）**：
1. `setup()` 里配置窗口**还没建**（`get_webview_window` 返 None），此时遍历 labels 直接在 tao 的
   `did_finish_launching` 里 panic ⇒ abort，**`catch_unwind` 抓不到**；
2. `setup` 里直接 `run_on_main_thread` 同样 abort（事件循环没起）；
3. **后台线程碰窗口对象** ⇒ WKWebView 跨线程 ObjC 异常 ⇒ `Rust cannot catch foreign exceptions`；
4. **`ns_window()` 给的是 `NSWindow`（TaoWindow），不是 NSView** ⇒ `-[TaoWindow bounds]: unrecognized selector`；
5. ObjC 异常必须在 ObjC 侧 `@try/@catch` 兜住 —— **这是定位根因的关键**：先兜住拿到 NSException 文本，
   否则只看到无栈 abort；
6. `generate_context!` 要求图标存在且是 **RGBA** PNG。

**用户提到 github 现在挂了代理可通** —— 记录：本轮已改 ffmpeg 路线，不再需要 libmpv；
若将来要回到 mpv，`brew install mpv` 现在应该可行（此前三重阻碍里的网络一条已消除）。

## 决策 #1172：Studio PoC C（真机投屏流）—— 推翻「投屏就是 30fps」

**流从哪来**：真机（adb `d67e31a3`）`screenrecord --size 1280x720 --bit-rate 8M --time-limit 30 /sdcard/x.mp4` → `adb pull`。
★静止画面时 screenrecord **几乎不出帧**（实测 40s 只有 15 帧）⇒ 必须用连续滑动制造运动。

**流参数（ffprobe）**：h264 High / 720p / **6.17 Mbps** / 标称 **120fps** / 实测 **107.3fps** / 变帧率。

**实测（同一段流）**：
- 离屏：107.32fps · render p50 1.32ms · **迟到 3.40%** · CPU 20.1% ⇒ S2 ❌
- 窗口：107.33fps · compose+present **1.23ms** · **迟到 0.65%** · CPU 21.3% ⇒ 全过
- **补测 60fps（重编码）**：60.04fps · **迟到 0%** · CPU **11.0%** ⇒ 完全宽裕

**三条发现（会改决策）**：
1. **投屏不是 30fps 而是 100–120fps**：帧预算 33.3ms → **9.3ms**，Studio 不能默认 30。
2. **快节奏下离屏(glFinish)代价被放大**（3.40% vs 窗口 0.65%）⇒ 窗口才是产品路径，离屏只适合批处理。
3. **raw H.264 没有容器时间戳**：同一内容 raw 报 25fps、mp4 报 120fps ⇒ 传输必须带 PTS，
   否则只能"解码多快放多快"（这正是 A 早期 224fps 的根因）。

**建议**：Studio 默认镜像 **60fps**（可配）；必须定义迟到策略（丢帧保实时 vs 延迟累积）。

**边界**：只测 Android 一台（120Hz）；iOS ReplayKit 未测；60fps 是重编码非设备直出；无网络抖动/丢包。

popen 拉流 → 拆 NAL → 按 `first_mb_in_slice==0` 判帧 → 到帧时刻打 PTS → 环形队列交主线程。

**三个缺陷（都被画面打回后才发现）**：
1. **全黑**：组 AU 只拼 NAL 负载、丢了起始码 ⇒ `INVALIDDATA(-1094995529)`、0 帧 → 补 `00 00 00 01`；
2. **花屏**：一个 VCL 当一帧，多 slice 帧被切成半帧 → 按 `first_mb_in_slice==0` 判新帧；
3. **仍花屏**：60Hz tick 追不上 120fps、队列积压丢参考帧 → **每拍排空队列**、只渲染最后一帧
   ⇒ `aus 649 / send_ok 649 / recv_ok 649` **零丢包**。

**没解决（如实记）**：
- **VT 硬解在裸流上拒绝**（须 `POC_LIVE_SW=1` 软解）——VT 要 SPS/PPS extradata，而我们是先读流后开解码器；
- 软解下**仍有残留块状失真**（`results/canvas-live-softdecode.png`），但零丢包 ⇒ 不是丢包，怀疑 AU/slice 边界。

**结论口径**：不写"实时投屏完成"，写**"通了但没通干净"**。下一步：抽 SPS/PPS 设 extradata 恢复 VT。

## 决策 #1175：实时投屏收口 —— 两个未解项都修了，另抓两个新缺陷

**VT 硬解恢复**：真因就是缺 extradata。做法 = **先起读取线程 → `live_peek_params` 窥探首个含
SPS+PPS 的 AU（**不取走**，那是首个 IDR）→ 设 `cc->extradata` → 再 `avcodec_open2`**。
实测 `参数集 108 字节（等 180–350ms）· 硬解=1 · open rc=0`。

**★残留失真真因（推翻 #1174 的「AU/slice 边界」猜测）**：拆包循环里，找不到下一个起始码时
`end = n` 就地当完整 NAL 处理，但 `pos` 没推到 `n` ⇒ `rest = n - pos` 把**同一段字节**carry 到
下一轮再拼一次 ⇒ 每个读边界往码流插一段重复字节。修法：无起始码即 `break`，尾部留给下一轮；
只有缓冲塞满（单 NAL > 64KB）才硬切。

**新抓两个缺陷**：
1. **`fread` 是「读满才返回」**（glibc 对管道也循环读）⇒ 64KB 缓冲在 8Mbps 下攒 ~64ms ⇒ AU 成批到达：
   `ticks=309 / empty=228`（74% 空转）+ 延迟平白多 64ms。改 `read(fileno(p), …)` ⇒ `empty 228→28`、
   `frames 51→175`（同 5s 窗口）。
2. **上传按 `g_W` 当 stride**，忽略 `linesize`（可能被对齐）⇒ 新增 `upload_plane()` 逐行回退。

**实测（真机 120fps 流，硬/软各 3 轮 18s，中位）**：
- 硬解 **59.5fps / p50 16.1 · p99 37.7ms / compose 1.30ms / 回拷 0.05ms / CPU 20.5%**
- 软解 59.8fps / p99 37.0ms / compose 1.19ms / CPU 32.7%
⇒ **硬解省 37% CPU，帧率与抖动无实质差别**。默认硬解，`POC_LIVE_SW=1` 逃生口。

**★又推翻自己一次**：本轮中途猜「硬解 p99 差（36 vs 27）是 GPU→CPU 回拷造成」——
实测 `hw_transfer_ms.p50 = 0.05ms`（Apple Silicon 统一内存，回拷几乎免费），**假设不成立**；
首批 3 轮的 p99 差异是机器负载噪声（换批次后 37.7 vs 37.0）。
**教训：机制结论必须多轮 + 直接测量，单批对比不算证据。**（这是本周第三次「先想机制再找证据」翻车）

**边界**：只测 Android 一台；iOS ReplayKit 未接；adb 管道非网络投屏；端到端延迟未量；
`--size 1280x720` 给竖屏加黑边（有效像素仅 ~330×720，浪费 74%）⇒ 产品应按设备宽高比取分辨率。

## 决策 #1177：Studio 延迟实测（原写 1176，被并发会话的 iOS HTTPDNS 占用 ⇒ 改 1177）

**我们这侧（首字节到达 → flushBuffer，同一 CLOCK_MONOTONIC）**：
队列等待 6.1–6.3ms · 解码 2.0–2.1ms · 合成 1.3ms · 上屏 0.4–0.5ms
⇒ **p50 7.7–8.0ms**，p95 13.5–15.1，p99 22.0–22.6。
★起点必须是「首字节」不是「凑齐一整帧」——后者把"等下一帧第一个 VCL 才知道上帧结束"算进去，@120fps 虚高 ~8ms。

**★全链路（跨时钟域）**：用 `screenrecord --bugreport` 把设备时间戳烧进画面（`13:17:34.190 f=607`）+
dump 时输出该帧 `arrive_epoch`/`present_epoch` + 设备↔Mac 时钟偏差换算。
偏差测法：单次 `adb shell` RTT 217ms（±108ms 不可用）→ `exec-out` 冷/热多次取最小 RTT 47ms
⇒ offset **-685.6ms**，三次采样相差 <3ms，保守记 ±23ms。
结果：编码+传输 57.4/60.4/54.4ms，我们 7/9/9ms ⇒ **全链路 64.4/69.4/63.4ms，中位 64.4ms，我们只占 11%**。

**★否掉一个直觉**：`POC_TICK_HZ` 60→120，队列等待 6.57→3.41ms（真的减半），但
**端到端 8.78→9.15ms（没降）**，CPU 25.4→34.7%。因为呈现被 60Hz vsync 锁住，加倍节拍只是把同一帧算两遍。
⇒ 默认保持 60Hz。**"减少排队"不等于"降低延迟"——下游呈现频率会把它吃掉。**

**怎么用**：60ms 对"看手机"够（人眼容忍 100–150ms），对"触摸回传"不够 ⇒ 双向控制要换 RTP/WebRTC 类
低延迟通道。我们这侧 8ms 里 6ms 是 60Hz 取样边界（16.7/2≈8.3），**已接近该架构下限**。

**边界**：跨时钟域 ±23ms；终点是 flushBuffer 不含面板出光；只测 Android 一台 + adb 管道；
全链路只 3 帧对账（分布来自 1000+ 帧统计）。
