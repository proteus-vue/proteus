# AI 共建（LLM 可执行版）

> **一句话**：把「外部实战报告 → 立项 → 修复 → 发布 → 回执 → 独立复测」这条链路的
> **每个断点变成机器判据**，让「报了没修、修了没验、验了没发、发了没人知道」四类静默失败不可能发生。
>
> 完整规范：`docs/ai-cobuild-spec.md`（本 skill 是其可执行形态）。

---

## 1. 四条铁律（违反任一条即不合格）

| # | 铁律 | 机器判据 |
|---|---|---|
| 1 | **报了必须立项** | 报告第 N 轮小节 → 台账该轮 ≥1 条（`check:cobuild` 规则 A/B） |
| 2 | **修了必须发布才算数** | `fix_state=published` + `fixed_in` 可被 `npm view` 验证 |
| 3 | **发了必须被独立验证** | `verification=passed`（维护方自测**不算**） |
| 4 | **闭环必须留回执** | 该轮条目全收口 → 报告须有「处理回执（第 N 轮）」 |

**收口唯一判据**：`status=fixed` ∧ `fix_state=published` ∧ `verification=passed`。

---

## 2. 三份工件

| 工件 | 谁写 | 硬性要求 |
|---|---|---|
| **① 实战报告**（每轮一节） | 使用方 | 标题含`第 N 轮`+**被复测版本号**；每个问题带**最小复现**+影响面；区分「框架缺陷」与「我方适配」；自己的误报单列澄清 |
| **② 台账** `docs/外部报告台账.json` | 维护方 | id 分配后不变；blocker 必带 `repro`；`partial` 必带 `related`；`fix_state` 只有 published/worktree |
| **③ 回执**（报告末尾） | 维护方 | 三样齐全：**改了什么** + **怎么验的（可执行）** + **哪个版本发的**；**必须包含自我批评**（上轮修得不完整要承认） |

---

## 3. 执行协议

### 收到一份新实战报告时

```
1. 读报告新增节 → 提取「轮次 + 被复测版本 + 逐条问题」
2. ★逐条用对方的最小复现**当场复现**（不轻信描述、不凭猜测改代码）
   —— 复现不出来 → 回执里如实说明「未能复现 + 我的环境/步骤」
3. 台账立项：分配 id（延续 F-NN）、severity、round、reported_in、repro、evidence
   —— 一条问题一个 id；若是「上一条的残留/同族」，用 related 互指
4. 修：
   a. ★先数清「同类实现有几处」（grep 特征正则）——修一份等于没修（Bug B 教训）
   b. 改为**唯一实现**（收敛为可复用原语），而不是逐处打补丁
   c. 加回归锁，并做**破坏性验证**（回退修法 → 测试必须红；不能红的测试不算测试）
   d. 真机/真实工程端到端验证（不只跑单测）
5. 发布（换版本号，npm 不可变）→ 台账 `fix_state=published` + `fixed_in`
6. 写回执（三样 + 自我批评）
7. 跑 `pnpm check:ledger && pnpm check:cobuild`——三方对齐才算做完
```

### 发布前自查

```bash
pnpm ledger:check    # 未收口项（未发布/验证不充分/部分修复）→ exit 1，逐条列出还差什么
```

### 使用方复测后（回写）

```
verification=passed（附一句话验证方式）+ 若发现修复不完整 → 新开一条 related 指向原条目
```

## 4. 独立验证的判定（哪些算、哪些不算）

| 验证方式 | 算独立验证？ |
|---|---|
| 使用方在真实项目跑报告里的最小复现 | ✅ 算（**唯一金标准**） |
| 维护方在**干净目录装 registry 包**后跑真实用户旅程 | ✅ 算（模拟用户视角） |
| 维护方跑仓库内单测 | ❌ **不算**（workspace 软链，看不到发布物缺陷） |
| 维护方读源码确认「改了」 | ❌ 不算（陈述，不是证据） |
| 破坏性验证（回退修法 → 测试红） | ✅ 算回归锁的**有效性**证明，但不替代端到端验证 |

---

## 5. 七条反模式（真实踩过，别再踩）

1. **修一半当修完** → 先数实现处数，再改；加结构性断言防新增；
2. **验证了但验的是别的**（`--dry-run` 跳过的那段恰是缺陷所在）→ 演练对着**风险最高**的段落设计；
3. **报了的没立项** → `check:cobuild` 规则 A；
4. **已修 = 用户能用了** → `fix_state=published` 强制区分工作树/已发布；
5. **自测通过 = 修好了** → 必须真实安装形态验证；
6. **文档说了就是做了**（官网数字长期过时）→ 数字要能机器重算；
7. **假阳性当缺陷报** → 报之前先确认探针自己可靠。

---

## 6. 平台适配 vs 框架缺陷的判定

| 情形 | 归属 |
|---|---|
| 框架承诺 `aligned` 但没对齐（含「本可做到却没做」——有对照实验可证） | **框架缺陷** |
| 平台本身不支持（WXML 不支持 `?.`） | 平台限制 → 使用方适配 + 框架给明确报错 |
| **静默失败**（不报错但行为错 / 报错指向无关模块） | **一律归框架**（让使用者无从排查是框架的责任） |
| 产出**语法合法但语义错**的产物 | **框架缺陷（最危险）** → 需产物侧改写特征扫描（普通语法扫描抓不到） |
| 使用方自己的业务逻辑行为 | 使用方 |

---

## 7. 完成判据（DoD）

- [ ] 报告每条都有台账 id，`check:cobuild` 五条规则全绿；
- [ ] 每个修复都有**能红的**回归锁（破坏性验证过）；
- [ ] 端到端验证过（真实工程/真机，非仅单测）；
- [ ] `fix_state` 与实际一致（`npm view <pkg>@<ver>` 能查到才写 published）；
- [ ] 回执含三样 + 自我批评；
- [ ] `pnpm check:ledger && pnpm check:cobuild` 通过。
