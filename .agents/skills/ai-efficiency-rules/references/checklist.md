# 执行效率自检清单

## A. 执行前自检（每次工具调用前）

逐条默念，命中「否」即修正动作后再执行。

| # | 检查项 | 命中时的处置 |
|---|---|---|
| 1 | 这条信息上下文 / 本地磁盘 / 上次调用结果中已有吗？ | 已有 → 直接复用，不发起调用 |
| 2 | 本次调用能否与其他调用合并并行？ | 无依赖 → 合并到同一批次 |
| 3 | 是否使用了固定 `sleep` / 盲等？ | 改为条件探测 + 退避 + 总超时上限 |
| 4 | 是否访问远程资源？本地缓存是否存在？ | 有缓存 → 用缓存；无缓存 → 拉取一次并落盘 |
| 5 | 预期输出是否过大（> 200 行 / 20KB）？ | 加过滤、截断，或先落盘再取片段 |
| 6 | 是否会改变状态或不可逆？ | 先 dry-run / 备份 / 向用户确认 |
| 7 | 是否已知精确路径却在做模糊搜索？ | 直读精确路径 + 行号区间 |
| 8 | 是否要重复执行一个已失败的动作？ | 先做失败归因，说明这次为何会不同 |
| 9 | 是否要重新安装依赖 / 重建环境？ | 先检测已完成状态（`test -d node_modules` 等） |
| 10 | 是否偏离当前目标？ | 收敛，无关探索一律推迟 |

## B. 执行后自检（每轮结束）

| # | 检查项 | 修正动作 |
|---|---|---|
| 1 | 是否重复做过同一件事（同文件、同请求、同命令）？ | 记录结果并复用，后续禁止重发 |
| 2 | 是否存在该并行却串行的调用？ | 下一轮改为批量合并 |
| 3 | 失败重试是否做了归因？次数是否逼近上限（2–3 次）？ | 到上限即停止并上报，换方案 |
| 4 | 临时缓存、下载物、中间文件是否已清理？ | 不再引用即删除 |
| 5 | 是否把大段原始输出灌进了上下文？ | 下一轮改用过滤 / 截断 / 落盘取片段 |
| 6 | 是否存在无意义中间态汇报？ | 仅在阶段完成或决策点汇报 |

## C. Red Flags 违规速查表

| 看到这个 | 判定 | 正确做法 |
|---|---|---|
| `sleep 5` / `time.sleep(10)` / `Start-Sleep` | 盲等 | 条件探测 + 指数退避 + 总超时上限 |
| `while true; do ...; sleep 2; done` | 无退出条件轮询 | 加成功条件 + 超时上限 + 失败分支 |
| 同一 repo 被 clone 两次 | 重复拉取 | 一次浅层拉取 → 缓存 → 复用 |
| 任务结束后缓存目录仍在 | 资源泄漏 | 不再引用即 `rm -rf` |
| 网络请求无 timeout | 潜在挂死 | 显式 timeout（默认 10s，大文件 30s） |
| 循环内逐条发起外部请求 | 请求放大 | 合并批量接口 / 节流并发 ≤ 4 |
| 连续 3 次同一失败命令 | 无归因重试 | 停止，归因后换方案或上报 |
| 重复 `npm install` / `pip install` / `cargo build` | 重复开销 | 执行前检测已完成状态 |
| 连续多次独立 `read` / `grep` | 该并行却串行 | 合并为一批发出 |
| `cat` 一个 5000 行文件 | 上下文爆炸 | 按行号区间分段读（offset/limit） |
| `ls -R` / `find /` / `cat **/*` | 无目标遍历 | 限定路径 + 文件类型 + 排除目录 |
| 全量日志 / 完整 JSON 直接贴出 | 输出失控 | 过滤 + 截断 + 只留关键行 |
| 无 `--wait` 却干等构建完成 | 等待无依据 | 用原生 `--wait` / 状态查询接口 |
| 读 `node_modules/` `dist/` `*.lock` `*.min.js` | 无效读取 | 除非任务明确指向，否则跳过 |
| 反复探测语言版本 / 环境信息 | 重复开销 | 一次性确认，后续复用结论 |
| 为"看效果"重复跑全量测试 | 反馈成本过高 | 跑最小相关子集（指定用例/模块） |

## D. 汇报格式（统一模板）

```
结论：<一句话结果>
依据：<关键证据，含 文件:行号 或 命令摘要，1–3 条>
遗留：<未解决项 / 需用户决策项>
```

## E. 任务级自检（多步任务收尾时）

- [ ] 总轮次是否可用「并行化 / 批量化」显著压缩？若是，记录改进点供下次复用。
- [ ] 是否所有临时目录、下载缓存、中间产物都已清理？
- [ ] 是否有因低效导致的超时 / 限流 / 失败？若有，归因到具体条款。
- [ ] 是否需要把本次踩到的新低效模式补充进规范？
