# AI 执行效率规范（Anti-Inefficiency Rules）

> 适用对象：所有在本仓库/项目中运行的 AI 编码助手与 Agent（含命令行模式、IDE 模式、多 Agent 协作）。
> 定位：这是**强约束的行为规则**，不是建议。可直接整段贴入 `CLAUDE.md` / `AGENTS.md` / 系统提示词。
> 唯一目标：**用最少的轮次、最少的 token、最少的墙钟时间，拿到正确结果。**

---

## 0. 总则：三条不可协商的原则

1. **先判断再动手。** 任何动作执行前，回答一个问题：这一步的信息，是否已经存在于上下文、本地磁盘或上一次调用结果中？是则直接复用，禁止重新获取。
2. **等待必须有条件，获取必须有缓存，重复必须有上限。** 没有退出条件的等待、没有缓存的重复拉取、没有次数上限的重试，一律视为缺陷。
3. **能并行就并行，能批量就批量。** 两次调用之间若无数据依赖或副作用依赖，必须合并到同一批次发出。串行只在真正存在依赖时才被允许。

**违反本规范的判定标准**：引入了本可避免的墙钟延迟、token 消耗或外部请求次数。

## 1. 等待与轮询（禁止盲等）

### 1.1 硬性禁止

- 禁止使用固定时长的盲等作为同步手段：
  - 禁止 `sleep 5`、`sleep 10`、`time.sleep(30)`、`Start-Sleep`、`await new Promise(r => setTimeout(r, 5000))` 这类"等一会儿应该就好了"的写法。
  - 禁止在命令中串联 `&& sleep 3 && ...` 来"给上一个服务一点时间"。
  - 禁止循环体里放固定 `sleep` 充当轮询间隔（如 `while true; do ...; sleep 2; done` 且无退出条件）。
- 禁止无上限等待：任何等待/重试必须同时具备**成功条件、超时上限、失败后的处置分支**。

### 1.2 必须这样做

- **用条件探测替代固定等待**：等待某个就绪状态时，直接探测该状态本身。
  - 服务就绪 → 探测端口/健康检查接口，而非 `sleep`。
  - 文件产出 → 探测文件存在且满足预期（非空、含成功标记、大小稳定）。
  - 异步任务 → 查询任务状态接口，而非按经验时长等待。
- **轮询参数默认值**：初始间隔 1–2s，**指数退避**（×1.5–2），间隔上限 10–15s，**总超时上限 60–120s**（构建/部署类可适当放宽，但必须显式写定值并在提示中说明）。
- **首选原生阻塞能力**：优先使用工具自带的 `--wait`、`--timeout`、事件回调、watch 机制（如 `kubectl wait`、`docker wait`、CI 的 `--watch`），而不是自己造轮询。

### 1.3 标准写法模板

```bash
# ✅ 条件探测 + 退避 + 总超时上限 + 明确失败分支
deadline=$((SECONDS+90)); interval=1
until curl -sf http://localhost:8080/health >/dev/null; do
  (( SECONDS >= deadline )) && { echo "TIMEOUT: service not ready in 90s"; exit 1; }
  sleep "$interval"; (( interval = interval*2 > 10 ? 10 : interval*2 ))
done
```

### 1.4 允许的例外

- 人为演示、教学示例、或用户明确要求"加个延迟看看效果"。
- 规避外部速率限制的退避等待（这属于**有依据的等待**，见 §2.4）。
- 上述例外必须在代码注释或回复中写明理由。

## 2. 外部资源获取（GitHub / API / 网页）

### 2.1 核心模型：一次拉取 → 本地缓存 → 复用 → 用完清理

任何外部资源的默认生命周期是：

```
检查本地缓存 → 命中则直接用 → 未命中则拉取一次并落盘缓存 →
后续所有访问走缓存 → 任务结束后按策略清理
```

### 2.2 硬性禁止

- 禁止在同一任务中**重复拉取同一外部资源**（同一 repo、同一 URL、同一 API 端点、同一文件片段）。
- 禁止把远程资源当本地文件反复读：`git clone` 之后又去 `curl raw.githubusercontent.com` 读同一个文件。
- 禁止无缓存的直接流式消费：需要多次引用某资源时，必须先落盘。
- 禁止忽略超时设置发出网络请求；**每个外部请求必须带显式 timeout**（默认 10s，大文件下载 30s）。
- 禁止在循环/批量任务中逐条发起外部请求（应合并请求或使用批量接口，见 §5）。
- 禁止把密钥、Token 拼进 URL 或日志输出。

### 2.3 必须这样做（GitHub 场景标准流程）

1. **先问"是否真的需要远程"**：仓库是否已在本地？是否已在缓存目录？是否可用 `gh api` / 本地 git 对象直接拿到？能用本地就用本地。
2. **一次完整拉取，优先浅层**：
   ```bash
   git clone --depth 1 --filter=blob:none --no-checkout <url> $CACHE/<repo>
   git -C $CACHE/<repo> sparse-checkout set <需要的子目录>
   ```
   只取需要的分支/子目录/单个 commit，不拉全量历史。
3. **固定缓存根**：统一使用项目内 `.cache/ai-external/<来源>/<标识>/`（并已加入 `.gitignore`）。同一资源在同一任务内路径恒定，避免重复下载。
4. **锁定版本**：以 commit SHA / tag 拉取并显式记录，避免后续请求拿到漂移的内容导致结果不一致。
5. **用完即清**：任务结束（或确认不再引用）后删除该缓存目录，不留垃圾：
   ```bash
   rm -rf .cache/ai-external/github/<repo>
   ```
   判断标准：**该资源在后续步骤中不再被引用，就应立即删除，而不是等任务结束。**
6. **失败降级顺序**：远程失败时，按序降级——本地缓存 → 镜像/备用源 → 已下载的归档包 → 向用户说明缺失并请求提供，而不是原地重试同一请求。

### 2.4 速率限制与超时

- 遇到 `429` / `rate limit` / `Secondary rate limit`：
  - 读取响应头 `Retry-After` / `X-RateLimit-Reset`，按其值等待（这是**有依据的等待**，不属于盲等）。
  - 无该头时，采用指数退避，重试上限 **3 次**；仍失败则切换认证方式（配置 token）、换镜像、或降级到本地/离线方案。
- 遇到超时：单次超时可重试 1 次并延长 timeout；连续 2 次超时即判定该源不可用，切换到备用源或离线路径，禁止继续重试。
- 对同一主机的并发请求需做节流（默认并发 ≤ 4），避免自伤触发限流。

### 2.5 网页/API 通用规则

- 同一 URL 在一次任务内只获取一次，结果落缓存（`.cache/ai-external/web/<hash>.md`）；后续引用走缓存副本。
- 优先使用官方 SDK / CLI（带内建重试与缓存），而非裸 `curl`。
- 需要"最新信息"才联网；能通过本地代码、文档、测试推导出的结论，禁止联网。

## 3. 文件检索与读取

### 3.1 硬性禁止

- 禁止**重复读取同一文件的同一区间**。已读过的内容留在上下文中即视为缓存，需要时回看上下文。
- 禁止无目标的全量遍历：`ls -R`、`find /`、`cat **/*` 这类"先看看有什么"的动作。
- 禁止整读超大文件（> 2000 行或 > 200KB）却不说明用途；必须分段读取。
- 禁止在已知精确路径时用模糊搜索绕圈子；也禁止在已知存在多处匹配时，只搜一次就下结论。
- 禁止读取构建产物、依赖目录、二进制与锁文件（`node_modules/`、`dist/`、`build/`、`.venv/`、`vendor/`、`*.lock`、`*.min.js`、图片/视频/压缩包等），除非任务明确指向它们。

### 3.2 必须这样做

- **先定位，后读取**：`grep` / `rg` / 符号索引 → 命中文件与行号 → 按行号区间读取。
- **限定搜索范围**：始终带上路径、文件类型（`--glob '*.ts'`）、排除目录（`--glob '!**/node_modules/**'`）。
- **大文件分段读**：使用 `offset` / `limit`（或 `sed -n 'a,bp'`、`head`/`tail` 组合），每次只读与当前判断相关的区间。
- **读前估算成本**：输出超过约 200 行或 20KB 的读取动作，先加过滤（`grep` 过滤后读、只看函数签名、只看 diff）。
- **一次搜索覆盖多个模式**：`rg -e 'A' -e 'B' -e 'C'`，而不是连发三次搜索。
- **结果要带定位信息**：搜索时输出文件名 + 行号，便于后续精确读取，避免二次全量扫描。

### 3.3 写入与修改

- 修改文件前必须已读取过目标区间（或确认是新建文件）；禁止凭猜测盲改。
- 优先用精确字符串替换，而非整文件重写；整文件重写仅用于结构性重构或用户明确要求。
- 多处相同修改使用批量替换（`replace_all`）或脚本，禁止逐处手工重复操作。

## 4. 命令执行与重试

### 4.1 硬性禁止

- 禁止**重复执行同一条已经失败的指令**（相同参数、相同环境），期望"这次也许能过"。
- 禁止在同一步骤里重复安装依赖、重复下载、重复初始化环境：`npm install`、`pip install`、`apt-get install`、`cargo build` 这类动作，执行前先检查是否已完成（`test -d node_modules`、版本校验、`--dry-run`）。
- 禁止无差别重试：重试前必须说明**基于什么新信息认为这次会不同**。
- 禁止为"看效果"而重复跑全量测试/全量构建；需要反馈时跑最小相关子集（指定测试名、指定模块）。
- 禁止执行不可逆的破坏性命令（`rm -rf /`、`git reset --hard`、`git push --force`、`DROP TABLE`、覆盖未提交改动）而不先确认或提供备份路径。
- 禁止交互式命令（`npm init`、`git rebase -i`、需要输入 `y` 的命令）而不加非交互参数（`-y`、`--no-edit`、`GIT_SEQUENCE_EDITOR=true`）。

### 4.2 重试的正确姿势（失败归因三步）

失败后按顺序做，禁止跳过：

1. **读完整错误信息**（含堆栈、exit code、stderr），定位到具体文件/行/依赖。
2. **归因分类**：环境问题 / 依赖缺失 / 语法或逻辑错误 / 参数错误 / 权限 / 资源不足 / 外部服务不可用。
3. **针对归因做一次有依据的变更**，再重试。重试仍失败 → 换方案，或停下来向用户报告（附已尝试清单与错误要点）。

- **重试上限**：同类操作最多 **2–3 次**。达到上限即停止，输出：已尝试的动作、每次的错误摘要、下一步建议。**不继续尝试第 4 次。**
- **幂等优先**：优先选择可重复执行且无副作用的命令；会改状态的命令，先做 dry-run（`--dry-run`、`--check`、`terraform plan`）。
- **长命令后台化**：预期耗时 > 30s 的任务，用后台执行 + 日志落文件 + 条件等待（见 §1），而非同步干等。

### 4.3 环境与依赖

- 开始前一次性确认环境（语言版本、包管理器、可用工具），后续步骤复用该结论，不反复探测。
- 依赖安装优先使用已存在的锁定文件与离线缓存；能复用全局缓存就不重新下载。
- 需要新依赖时，先确认是否已被间接引入。

## 5. 并行化与批量化

### 5.1 硬性禁止

- 禁止把**相互独立的调用拆成多轮串行**发出。典型：连续多次独立 `read`、多次独立 `grep`、多次独立 API 查询。
- 禁止"拿一个结果 → 再决定下一个"而不做前置梳理：若后续调用的**目标集合可以提前枚举**，必须一次性并行发出。
- 禁止用串行循环处理可批量的独立项（逐文件调用格式化、逐个 URL 请求、逐个用例查询）。

### 5.2 必须这样做

- **同一批次合并**：所有无依赖的工具调用放在同一个消息块里一次性发出。
- **依赖分层**：先并行执行完第一层，拿到结果后再并行发出第二层；层级数 = 真实依赖深度，不多不少。
- **批量接口优先**：用批量端点、一次命令处理多目标（`rg -e A -e B`、`git add a b c`、一次脚本循环内部处理），而不是多次调用。
- **并发上限**：本地 CPU/IO 密集任务并发控制在合理范围（一般 ≤ CPU 核数）；外部请求并发 ≤ 4（见 §2.4）。
- **顺序敏感的场景例外**：存在副作用依赖（先写后读、先迁移后校验）、需要严格顺序的迁移/部署步骤，允许且必须串行，并在注释中说明原因。

### 5.3 判断口诀

> 这一步需要上一步的输出吗？
> 不需要 → 并行；需要 → 串行，但串行链要尽量短。

## 6. 输出控制与上下文管理

### 6.1 硬性禁止

- 禁止把大段原始输出直接灌入上下文：全量日志、`cat` 整个大文件、完整 JSON 响应、完整依赖树、完整测试输出。
- 禁止重复粘贴同一段内容（日志、代码、错误）到上下文的多个位置。
- 禁止无意义的中间态汇报（"我现在开始读文件 A""读完了，接下来读文件 B"），只在**阶段完成或有决策点**时汇报。
- 禁止为了"保险"保留已确认无用的上下文（废弃方案、已修复的错误、已删除文件的内容）。

### 6.2 必须这样做

- **截断与过滤优先**：`head -n 50`、`tail -n 100`、`grep` 过滤、`jq` 取字段、`--quiet` / `--oneline` / `--format=short`。需要完整输出时，先落盘再按需取片段。
- **信息密度优先**：汇报时给结论 + 关键证据（1–3 行关键日志/行号），而不是原始流水。
- **早停条件**：搜索/遍历类操作显式设定上限（`--max-count`、`head`、`-quit`、结果数阈值），达到即停。
- **上下文复用**：读过的内容不重读；已在上下文的 diff/日志不重新生成。
- **长任务进度节奏**：预计超过 5 步的任务，先给出计划（步骤 + 预计调用次数），执行中在关键节点简短汇报，完成时给结论。

### 6.3 汇报格式（建议）

```
结论：<一句话结果>
依据：<关键证据，含文件:行号 或 命令摘要>
遗留：<未解决项 / 需用户决策项>
```

## 7. 执行前后自检清单

### 执行前（每次工具调用前默念）

- [ ] 这个信息上下文里/本地磁盘上已经有了吗？→ 有则不调。
- [ ] 这次调用能否与其他调用合并并行？→ 能则合并。
- [ ] 是固定 sleep 吗？→ 改成条件探测 + 上限。
- [ ] 是远程资源吗？→ 本地缓存有吗？没有则拉取一次并落盘。
- [ ] 输出会不会过大？→ 加过滤/截断。
- [ ] 会不会改状态或不可逆？→ 先 dry-run / 先备份 / 先确认。

### 执行后（每轮结束自检）

- [ ] 有没有重复做过同一件事（同一文件、同一请求、同一命令）？
- [ ] 有没有该并行却串行的地方？
- [ ] 失败重试是否做了归因，有没有逼近次数上限？
- [ ] 临时缓存、下载物、中间文件是否已按策略清理？
- [ ] 是否偏离目标做了无关探索？→ 立即收敛。

## 8. 违规速查表（Red Flags）

| 看到这个 | 判定 | 正确做法 |
|---|---|---|
| `sleep 5` / `time.sleep(10)` | 盲等 | 条件探测 + 退避 + 总超时 |
| 同一 repo 被 clone 两次 | 重复拉取 | 一次拉取 → 缓存 → 复用 |
| 任务结束缓存目录还在 | 资源泄漏 | 不再引用即删除 |
| 网络请求无 timeout | 潜在挂死 | 显式 timeout（默认 10s） |
| 连续 3 次同一失败命令 | 无归因重试 | 停止，归因并换方案/上报 |
| 重复 `npm install` / `pip install` | 重复开销 | 执行前检测已完成状态 |
| 连续 5 次独立 `read` | 该并行却串行 | 合并为一批 |
| `cat` 一个 5000 行文件 | 上下文爆炸 | 按行号区间分段读 |
| `ls -R` / `find /` | 无目标遍历 | 限定路径 + 类型 + 排除项 |
| 全量日志直接贴出 | 输出失控 | 过滤 + 截断 + 只留关键行 |
| 无 `--wait` 却干等构建 | 等待无依据 | 用原生 wait / 状态查询 |

## 9. 例外与升级

- 用户明确要求某做法（如"就 sleep 10 秒"）时，以用户指令为准，但须**提示更高效替代方案**一次。
- 环境受限（离线、无权限、工具缺失）导致无法满足本规范时，**明确说明受限点与影响**，而不是默默退化成低效实现。
- 规范之间冲突时的优先级：**正确性 > 安全性 > 效率**。绝不为效率牺牲正确性与安全（例如不得为省一次调用而跳过校验、不得为省时间而跳过备份）。
