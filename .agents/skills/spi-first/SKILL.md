# SPI-First（LLM 可执行版）

> **一句话**：找到系统里所有「换 X 要改很多文件」的 X，把它们逐一提升为
> **语义接口 + ≥2 后端（含 Mock/Headless）+ conformance + 诚实边界**，
> 直到业务层对任何具体实现**零知识**。
>
> 方法论出处：`docs/spi-first-methodology/`（Proteus 元方法论，跨 16 次生产泛化验证）。本 skill 是其**通用化、可执行**形态，不绑定任何框架/语言/项目。

---

## 1. 何时使用 / 何时明确不用

**使用**（用户意图命中其一）：
- 想让某块系统可替换（换数据库 / 支付 / 消息队列 / SDK / 渲染 / 存储 / 推送…）；
- 想要多实现并存（双供应商 / A/B 迁移期并行 / 插件化 / 多平台适配）；
- 第三方要基于你的能力做扩展；
- 已有抽象但怀疑是「假 SPI」（单实现、无契约测试、接口含技术名词…）——审查而非新造；
- 想让系统对变化免疫（coupling audit 先行，找出最该动的点）。

**不用**（应明确劝阻，不做抽象）：
- 一次性脚本 / MVP 原型（YAGNI）；
- 实现确实唯一且未来不会换；
- 性能极度敏感热点路径（间接层开销不可接受）；
- 小团队 + 边界已清晰（过度设计）。

**判定原则**：「未来要替换 / 多实现并存 / 第三方扩展」**至少一项为真**才值得引入 SPI。

---

## 2. 执行协议（五阶段）

### Phase 0 — 确认目标与范围

先弄清用户要什么，再动手：
1. **只要审计**（盘点耦合点 + 建议），还是**审计 + 改造试点**？
2. 范围：全仓库 / 某模块 / 只针对某个 X（如"把支付抽象掉"）？
3. 语种/技术栈（决定扫描命令与 conformance 位置）。
4. 改造边界红线：哪些目录不能动（如 shared/、vendor 内代码、正在迁移的分支）。

> 未确认前**不修改任何业务代码**。审计是只读的，可以直接做。

### Phase 1 — 耦合点审计（只读，输出候选表）

对每个疑似耦合点执行量化扫描（**计数对象 = 业务源码**，默认排除 `tests/ examples/ dist/ build/ node_modules/ *_test.*`；如用户要求含测试需先说明）：

```bash
# 通用（按文件数计数）
grep -rln "<实现名>" src/ 2>/dev/null | wc -l
# TS/JS：某 SDK 被多少业务文件 import
grep -rcE "from '<sdk>'|require\('<sdk>'\)" --include="*.ts" --include="*.tsx" --include="*.js" --include="*.vue" src/ | grep -v ':0' | wc -l
# Java/Kotlin / Python / Go / Rust
grep -rc "import <vendor>" --include="*.java" src/ | grep -v ':0' | wc -l
grep -rc "^import <module>" --include="*.py" src/ | grep -v ':0' | wc -l
grep -rc "\"<pkg>\"" --include="*.go" src/ | grep -v ':0' | wc -l
grep -rc "use <crate>" --include="*.rs" src/ | grep -v ':0' | wc -l
```

**除了 import 计数，还要找这四类硬编码信号**：
- 平台/环境分支：`if (isIOS)` `process.env.NODE_ENV` `if (platform === ...)` 散布在业务层；
- 鉴权/配置散落：`isAdmin` 手写判断、连接串/密钥在业务代码里直用；
- 直接调底层：业务层 `new S3Client()`、`axios.get`、`localStorage` 满天飞；
- 唯一后端抽象：已有 interface 但 grep 只有一个实现。

**判定规则**：
- 出现 **≥ 2 个业务文件** = 候选耦合点；
- **只有 1 个适配器文件**引用 = 已解耦，不处理；
- 出现 **0/趋近 0** 但接口存在 = 检查是否假 SPI（单实现、无 conformance）。

**优先级**：
| 级 | 标准 |
|----|------|
| P0 | 出现 ≥ 20 文件 **且** 未来确定要替换/多实现/三方扩展 |
| P1 | 5–19 文件，或有明确演进计划 |
| P2 | < 5 文件，登记观察不处理 |

产出候选表（写在回复里，也建议落一个 `docs/spi-first-audit.md` 给用户，模板见 `audit-template.md`）：

| # | 耦合点 | 具体实现名 | 业务文件数 | 优先级 | 未来动因 | 备注 |
|---|--------|-----------|-----------|--------|---------|------|

### Phase 2 — 汇报候选，选定试点（改代码前必须确认）

- 汇报候选表 + 每项的「改造后收益」一句话 + 建议试点。
- **试点选择标准**：优先「小而完整」——影响面真实但文件数不要爆炸；能覆盖一个完整业务语义（如"支付"优于"发邮件"若前者是核心痛点）；做完立刻能被 conformance 证明。
- 明确告诉用户试点范围（会新建哪些文件、改哪些文件、**不**动哪些）。
- 用户确认后才进入 Phase 3。

> 如果审计结论是「没有值得动的耦合点」或「唯一候选是过度设计」，如实说，不要硬造抽象。

### Phase 3 — 五步改造试点（每次只做一个耦合点）

#### Step 1｜语义接口（成败关键，先想清楚再写码）
定义"做什么"，禁止"怎么做"：
1. 命名**禁用厂商/技术名词**（S3、Kafka、React、MySQL、Redis…）→ 用领域动词（Store/Publish/Charge/Render/Send）。
2. 参数类型用**领域类型**，不用 SDK 类型（`Uint8Array` 而非 `S3.PutObjectRequest`）。
3. 错误用**统一领域错误码/结果类型**，不用底层异常类型（上层不得 catch 具体实现异常）。

命名对照示例：
| ❌ 泄漏实现 | ✅ 纯语义 |
|---|---|
| `SaveToS3(bucket, key)` | `StoreArtifact(id, bytes): StoredRef` |
| `PublishToKafka(topic, partitionKey)` | `PublishEvent(event)` |
| `AlipayCharge(amount, tradeNo)` | `PaymentProvider.charge(order)` |
| `ReduxDispatch(action)` | `StateStore.dispatch(action)` |

接口文件内自检：grep 该文件能否命中任何厂商/库/协议名？能 → 未收敛，重命名。

#### Step 2｜≥2 后端（其中一个是 Mock/Headless）
- `RealProvider`：把现有逻辑**原样搬入**，行为零变化（重构第一步永远先保行为）；
- `MockProvider`：测试/降级用，**必须要有**（单后端 SPI = 假 SPI：可替换性从未被验证）；
- `AltProvider`：可选第二个真实实现，用来证明可替换性不是纸上谈兵。
- 若现实只有一个实现且短期内不会有第二个 → 按 AP-01 处理：不要造抽象，降级为内部模块边界或直接调用。

#### Step 3｜conformance 契约测试（把"约定"变成"机器强制"）
- 放项目测试体系内，建议 `tests/conformance/<x>.test.*`；**同一份用例代码跑所有后端**。
- **只测语义契约**，不测实现细节：幂等/重试/错误语义/边界行为/顺序/并发/空结果——凡是实现可能悄悄分化的行为都要断言。
- 至少含 **1 个负向用例**（一个"坏后端"必须被抓出来——证明套件有牙齿）。
- 新后端接入 = 跑同一套 conformance，通过才允许注册（可写成文档/脚本/CI 门禁）。

#### Step 4｜接线与守界
- 提供 factory / 依赖注入 / 配置入口（如 `createPayment(backend: 'alipay'|'mock')`），业务层只依赖语义接口。
- **禁止业务层直接 import 具体实现**；若项目有静态扫描/CI，可建议加一条规则（grep 到业务层 `import '具体SDK'` 即 fail）。
- 收敛回归：改造后 `grep -c` 具体实现名，业务层出现次数应趋近 0（只允许留在适配器目录）。

#### Step 5｜诚实边界（写进文档/README，不许省略）
每个 SPI 至少三条：
1. **性能边界**：抽象间接开销（调用/序列化）实测多少；未实测必须标注 `measured: false`，禁止宣称数字。
2. **能力边界**：后端能力不齐时如何降级（Capabilities 表 + 降级后端/显式报错），禁止静默失败。
3. **适用边界**：什么场景**不值得**用这套 SPI（防止后人过度设计）；若后端数涨到 6+ 且差异大 → 该拆 SPI 而不是加分支。

### Phase 4 — 验证与反模式自检

1. 跑项目全量测试 + 新增 conformance，全部通过（如实报告失败）。
2. 对照反模式清单逐条自检（`anti-patterns.md`），命中任一条 = 未真正落地，回到对应 Step 修。
3. 回归扫描：具体实现名在业务层的出现次数、接口文件内技术名词 grep —— 二者都应干净。

### Phase 5 — 交付报告

按 `report-template.md` 输出，包含：
- 候选表全量 + 本次试点选择理由；
- 改动文件清单（新建/修改/删除，明确边界）；
- conformance 用例清单与执行结果（含负向用例）；
- 诚实边界三条；
- 反模式自检表（✅/❌ 逐条）；
- 剩余 P1 候选与 P2 积压（下一步建议）；
- 未做的事与风险（如"接口里仍残留 XX 语义，待 v2"）。

## 3. 反模式速查（详细版见 anti-patterns.md）

| 信号 | 本质 | 修正 | 回到 |
|------|------|------|------|
| AP-01 只有 1 个实现 | 可替换性从未验证 | 加 Mock/Headless，或承认是内部边界去掉抽象 | Step 2 |
| AP-02 接口含技术名词 | 换实现时接口本身要改 | 语义动词 + 领域类型重命名 | Step 1 |
| AP-03 无 conformance | 行为随时间漂移分化 | 同一份契约测试跑所有后端 | Step 3 |
| AP-04 业务绕过接口直调底层 | 抽象有漏洞=没抽 | 静态扫描禁直接 import + 适配器收口 | Step 4 |
| AP-05 只定义类型不定义行为 | 各实现行为可天差地别 | conformance 用例化边界/错误/并发语义 | Step 3 |
| AP-06 为"可能换"过度设计 | 间接层成本 > 收益 | 适用边界判定：三动因至少一真才引入 | Phase 0 |
| AP-07 后端爆炸（6+） | 契约演进成负担、抽象泄漏 | 收敛后端 / 拆分 SPI / Capabilities 降级表 | Step 5 |
| AP-08 抽象成本不透明 | 从不做性能实测 | 诚实边界含实测数据，未测禁宣称 | Step 5 |

## 4. 执行纪律（LLM 行为约束）

1. **先审计、后改造；改代码前必须拿到用户对试点的确认。**
2. 一次只改造一个耦合点；不顺手"重构"无关代码。
3. 接口里出现任何厂商/技术名词 → 立即停下重命名，不允许"先这样后面再改"。
4. 没有 conformance 的抽象 = 假 SPI：要么补契约测试，要么拆掉抽象，**不允许留空壳**。
5. 不伪造数据：性能边界没有实测就写 `measured: false`；conformance 没跑就说没跑。
6. 审计与改造产物落盘到用户项目（`docs/spi-first-audit.md` + 试点报告），方便追踪与 CI 对照。
