# 反模式参考（LLM 执行版）

> 每个反模式 = "以为做了 SPI-First、其实没做到"的典型症状。
> 对照自查：命中任一条 → SPI 未真正解耦，回到对应 Step 修正。

## AP-01｜单后端 SPI（Single-Impl SPI）

- **症状**：定义了接口，但只有 1 个实现，且短期内不会有第二个。
- **为什么假**：可替换性从未被验证；接口里几乎必然泄漏实现细节，真要换时才发现改不动。
- **修正**：加 Mock/Headless 后端（强制暴露接口漏洞），或承认它是**内部模块边界、不是 SPI**，去掉抽象。
- **判定**：一个后端活过 6 个月没第二个 → 大概率过度设计。

## AP-02｜接口含技术名词（Leaky Naming）

- **症状**：`interface UploadToS3(bucket, region)` / `SendViaKafka(topic, partitionKey)`。
- **为什么假**：换实现时**接口本身要改**，业务层被迫跟着改 → 解耦失败。
- **修正**：语义动词 + 领域类型重命名（见 cheatsheet 命名对照表）。
- **自检**：grep 接口文件能否命中任何厂商/库/协议名？能 → 未收敛。

## AP-03｜无 conformance（Convention-Only）

- **症状**：接口签名清楚，但**没有契约测试**，各实现靠"约定"保持一致。
- **为什么假**：行为随时间漂移分化；某实现升级悄悄改变边界行为，调用方无感知直到生产爆炸。
- **修正**：每个 SPI 一套 conformance，**同一份测试对所有后端跑**；只断言语义契约，不测实现细节。

## AP-04｜业务绕过接口（Leaky Boundary）

- **症状**：定义了 SPI，但业务代码里仍有 `import '具体SDK'` 或 `if (isPlatformX)`。
- **为什么假**：抽象有漏洞 = 没抽，耦合点只是藏到更深的文件。
- **修正**：① 静态扫描（CI）禁止业务层直接 import 具体 SDK；② 适配器层收口全部底层调用；③ `grep -c` 回归，出现次数趋近 0。

## AP-05｜接口只定义类型、不定义行为（Type-Only SPI）

- **症状**：`interface Repository<T> { find(id): T|null; save(e): void }`——对空结果/并发/事务/错误只字未提。
- **为什么假**：两个实现的"行为"可以天差地别（一个返 null、一个抛异常，调用方崩溃）。
- **修正**：conformance 用例化行为——at-least-once、幂等、顺序、错误语义全部写成可跑测试。

## AP-06｜过度设计（Over-Engineering）

- **症状**：为"未来可能要换"、实则稳定的实现引入完整 SPI 层，徒增间接调用/调试难度/学习曲线。
- **修正**：适用边界判定——"未来要替换 / 多实现并存 / 第三方扩展"至少一项为真才引入；否则直接调用。
- **典型受害者**：创业公司 MVP、内部工具、一次性迁移脚本。

## AP-07｜后端爆炸（Backend Explosion）

- **症状**：一个 SPI 衍生 6+ 后端，差异越来越大，conformance 膨胀到 200+ 用例。
- **为什么危险**：契约演进本身成负担；差异过大时抽象层开始泄漏（调用方需要 `if (backend === 'X')`）。
- **修正**：① 收敛后端数，合并语义相近的；② 拆分 SPI——差异过大的后端其实对应**不同接口**；③ 引入 Capabilities 表，明确能力不齐时的降级。

## AP-08｜抽象成本不透明（Hidden Cost）

- **症状**：引入 SPI 但从不做性能基准，间接调用/序列化/跨边界延迟全部未知。
- **修正**：诚实边界必须含**实测性能数据**；每次新增后端跑一次基准；超过阈值评估编译期单态/内联。
